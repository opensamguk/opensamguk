# 관리자 콘솔

## 월드 생성 요청 후보 (ADMIN-CREATE-B, AC-M3-04 부분)

`admin.world.create`는 현재 세션과 같은 `expectedUserId`, UUID `idempotencyKey`, 이름과 명시한 `endYear`(정수 또는 null)를 받는다. 프리셋을 지정하거나 시나리오·지도·턴 간격을 함께 지정한다. 능력치·병종·초상·규칙 기능·시드는 선택 사항이며 임의 초기 게임 상태는 받지 않는다. 미인증·미동의·현재 권한·제재를 검사한 뒤 요청과 접수 감사를 함께 저장한다. 같은 계정·키의 같은 정규형은 원래 요청을 반환하며 다른 내용은 CONFLICT다. 생략한 시드는 최초 접수 때만 만들고 재전송으로 바꾸지 않는다.

`admin.world.createStatus`는 기대 사용자와 요청 UUID 또는 중복 방지 UUID 중 하나를 받는다. 현재 관리자 본인의 요청만 조회하며 응답은 사용자·요청·키·PENDING/DONE/FAILED·완료 월드 UUID·고정 오류뿐이다. 자원 원문·내부 오류는 내보내지 않는다. 응답을 잃었으면 같은 키로 조회해 확인한다. 엔진이 고정한 게시 자원과 초기 상태 해시를 재확인하고 월드·DONE·적용 감사를 함께 저장하므로 재시작과 중복 소비가 새 월드를 더 만들지 않는다. 이 후보의 실제 PostgreSQL·전체 검사·독립 리뷰·보호 병합과 생성 화면은 미완료다.

> 상태: 역할·감사·제재 API와 화면·공지·조회 병합, 월드 시계 후보는 최종 검증 뒤 보호 병합 대기 · 필요 시점: M3 · 관련 AC: M3-04, M3-05, M3-10
> 참고: core2026 `admin-console.md`, `play-audit-operations.md`, `design/play-audit.md` (부정 플레이 조사 범위만)
> 이 문서가 답할 질문: 운영자가 어떤 화면에서 무엇을 할 수 있고 무엇이 기록되나?

## 1. 권한

T3-05 첫 묶음은 관리자 역할과 명령줄의 권한 부여·회수만 다룹니다. 기존 계정과 새 계정의 기본 역할은 USER이며 자동으로 관리자를 지정하지 않습니다. `admin.whoami`는 로그인·필수 이메일 인증 뒤 DB의 ACTIVE·ADMIN을 매번 확인하고 `{ admin: true }`만 돌려줍니다. 역할을 회수하면 기존 세션에서도 다음 요청부터 거부합니다. 요청의 사용자 ID나 역할 값은 권한 근거가 아닙니다.

관리자 지정·회수 API는 없습니다. 대상과 사유를 확정한 서버 운영자가 올바른 DB 환경을 확인한 뒤 `pnpm admin:grant` 또는 `pnpm admin:revoke`를 실행합니다. 이메일과 사유는 명령 인자에 넣지 않고 표준 입력 JSON으로 전달합니다. 입력 파일은 저장소 밖에 둡니다.

```json
{ "email": "operator@example.invalid", "reason": "운영자 권한 부여" }
```

```sh
pnpm admin:grant < /secure/admin-role-request.json
pnpm admin:revoke < /secure/admin-role-request.json
```

명령은 대상 사용자 행을 잠근 같은 트랜잭션에서 역할과 감사 행을 확정합니다. 같은 역할을 다시 요청해도 `admin.grant`·`admin.revoke`와 `payload.changed:false`로 감사하며 실패하면 역할도 되돌립니다. 출력은 사용자 UUID·역할·변경 여부·감사 ID만 담습니다. 이메일·비밀번호·세션·키는 출력하거나 감사 payload에 넣지 않습니다. 사유는1~200자이며 개인정보를 적지 않습니다.

유효한 계정 전체 또는 월드 제재가 남은 사용자는 ADMIN으로 올리지 못합니다. 먼저 관리자가 제재를 해제해야 합니다. 역할 부여와 제재가 경쟁해도 같은 사용자 행 잠금 아래에서 자격을 다시 확인합니다.

감사 기록은 DB 시각·CLI 행위·대상 UUID·사유·전후 역할을 남기고 UPDATE·DELETE·TRUNCATE를 DB trigger로 거부합니다. 사용자 UUID와 자유 입력 사유의 보존 정책 검토는 남아 있습니다. 이번 검증은 전용 시험 DB만 사용했으며 기존 개발 계정·실제 운영자의 권한은 변경하지 않았습니다. 전체 관리자 화면·월드 조작과 AC-M3-04 인수는 후속 묶음입니다.

## 2. 월드 관리

초기화 후보 `admin.world.requestReset`은 기대 사용자·원본 월드·중복 방지 UUID·정확한 이름·시계 revision·사유와 선택 시드를 받는다. 현재 세션·관리자·제재·인증·동의를 확인하고 원생성 형식3의 PAUSED 월드 요청과 감사만 저장한다. 처음 확정한 새 월드 UUID와 시드는 같은 키 재접수로 바뀌지 않는다. 본인 요청의 `admin.world.resetRequest`로 실제 결과를 확인하며 응답 유실만으로 새 키를 만들지 않는다. 엔진 후보는 현재 관리자·전체 제재와 원생성 자료를 다시 검사하고 원본 종료·새 PREOPEN·매핑·감사를 함께 저장한다. 접수 뒤 로그아웃만으로 취소하지 않는다. 새 월드는 명시 시작을 기다리며 기존 사람·소속·장수·30칸은 자동 복사하지 않는다. 실제 PostgreSQL·복원·독립 리뷰·보호 병합과 초기화 화면·운영자 수락은 미완료이며 현재 후보를 운영에 사용하지 않는다.

명시 종료 화면은 별도 후보에서 구현 중이다. `/admin/worlds`에서 목록을 조회하고 일시정지한 원생성 형식3 월드를 고른 뒤 정확한 이름·사유·영향을 확인한다. 사람 장수가 있는 운영 월드에는 소유자 승인이 필요하다. 화면의 체크는 승인 기록을 대신하지 않는다. 시계 조작과 종료는 함께 실행하지 못하며 상태가 달라지면 다시 확인한다.

종료 요청이 미확정이거나 처리 대기이면 같은 요청 번호의 결과만 수동 조회한다. 실제429는 표시한 대기 시간 뒤 같은 내용으로 수동 접수할 수 있다. 창 전환에는 내용을 숨기고 현재 계정·권한을 다시 확인한다. 로그아웃은 이미 접수한 요청을 철회하지 않는다. 적용 완료는 실제 엔진 결과로만 표시하며 승자 결과를 만들지 않는다. 소스·실제 통합 인수·독립 리뷰·필수CI와 보호 병합은 아직 남아 있다.

강제 종료 백엔드는 현재 후보에서 검토 중이다. 정확한 월드 이름과 시계 revision·사유를 확인한 요청만 접수하고 원생성 형식3의 일시정지 월드만 엔진이 종료한다. 요청 뒤 로그아웃은 자동 취소가 아니며 관리자 회수·전체 제재는 적용 전에 다시 검사한다. 기존 승자 결과를 만들지 않아 일반 종료 화면에는 종료 안내만 나온다. 관리자 사유를 일반 사용자에게 내보내지 않는다. 새 종료 화면·실제 통합 검증·독립 근거 리뷰·보호 병합과 전체 AC는 남아 있다. 운영 중 사람 월드의 종료·초기화는 소유자 승인 없이 실행하지 않는다.

시작·일시정지·재개의 API 접수와 엔진 적용은 후속2일 묶음에서 실제 집중 PostgreSQL·동일시드 재생·전체 검사를 통과했습니다. 현재 세션과 기대 사용자를 확인한 `admin.world.requestClock`은 PENDING 입력과 감사만 저장하고 같은 월드·관리자·요청 UUID로 결과를 확인합니다. `admin.world.clockRequest`로 본인이 접수한 결과를 읽습니다. 실제 상태는 기존 엔진의 리스·World 트랜잭션에서 현재 관리자와 상태를 다시 확인한 뒤 적용하거나 기각합니다. 정확한 세 조치와 재생 형식3만 허용하며 게임 규칙과 예약을 바꾸지 않습니다. 깨끗한641 후보의 전체PG1514건·권한90/428/22/누락0·실제 백업/복원은 통과했고 독립 근거 리뷰도 승인됐습니다. 보호 main294를 정상 결합한0f 후보는 시계 제품·시험19파일을 보존했으며 전체5394건·공개 자산110개·Chromium4건과 기존 인증5건·동의8건도 통과했습니다. 검증 판과 시점을 구분하며 최종 독립 리뷰·새 필수CI·정상 보호 병합과 조작 화면은 남아 있습니다. 생성·종료·초기화와 전체 AC도 미완료입니다.

`admin.world.list()` 구현은 월드 UUID·이름·상태·시나리오/프리셋 키·턴 간격·사람 장수 수와 엔진 heartbeat를 조회합니다. 사람 수는 `General.userId`가 있는 행만 셉니다. heartbeat가 없으면null이며 시각·마지막 tick·지연과 오류 유무만 반환합니다. 오류 원문은 고정 안내로 바꿉니다. 현재 세션과 관리자 자격을 잠금 뒤 다시 확인하고 같은 RepeatableRead에서 읽으며 게임 상태나 감사 행을 쓰지 않습니다. 집중 PostgreSQL·전체 check·공개 검사는 통과했고 전체 PG/권한 원장·최종 증거 리뷰·보호 병합과 목록 화면은 아직 남아 있습니다.

후속 `/admin/worlds` 화면은 목록을 수동 조회하고 위 항목을 읽도록 연결 중입니다. 창 전환·오류·신원 변경에는 이전 결과를 지우며 자동 갱신이나 월드 변경 요청은 없습니다. 엔진 시각은 한국 시각과 ISO 원문으로 확인하고 기록 없음과 오류 없음을 구분합니다. 실제 브라우저 검증·독립 리뷰·선행 조회 API와 화면의 보호 병합은 남아 있으며 생성·정지·재개·종료·초기화 화면을 대신하지 않습니다.

## 3. 사용자 관리

보호 main291을 정상 결합한 깨끗한 후보 `d6b1c20`에서 전체 `pnpm check`297파일5371건(372.40초), 공개109자산·승인 이미지6개·외부 초상0개와 실제 공개 Chromium4건(4.3초)을 통과했다. 같은 후보에서 사용자 상세·새 제재 계약·migration의 실제 PostgreSQL3파일73건(97.41초)도 통과했다. 명령 종료0·자기 DB OID·연결0·정상 삭제와 실행 중22파일 해시 불변을 확인했다. 정상 병합 때 제재 제품·시험10파일과 사용자 상세 의도를 보존했고 결합 router는 제재 화면의 실제 집중 검사판과 같다.

앞선 깨끗한 `120ce0d`의 전체 PostgreSQL94파일1483건(1101.81초)·권한87절차413실행·기존 면제22개·누락0, 필수 이메일 인증 Chromium5건의 시점도 구분한다. 해당 전체 실행의 백업/복원 구성과 실제 근거는 비구현 담당이 승인했다. 새 결합판 전체 검사 근거도 승인됐으며 이번 추가 실제PG·최종 문서 리뷰와 새 필수CI·정상 보호 병합은 남아 있다. 이 결과 보완은 두 문서만 바꾸고 나머지20파일을 보존한다. 제재 화면·월드 조작·로그인/IP/기기 조사와 전체 관리자 AC는 미완료이며 사용자5200을 변경하지 않았다.


깨끗한 최신 main290 결합 후보 `032949b`에서 전체 `pnpm check`297파일5371건(378.96초), 공개109자산·승인 이미지6개·외부 초상0개와 공개 Chromium4건(4.3초)을 통과했다. 전체 실제 PostgreSQL은94파일1476건·1141.09초이며 권한 대조는88절차·418실행·기존 면제22개·누락0이다. 세 명령 종료0·자기 DB OID와 연결0·삭제·검사 중 소스11파일 해시 불변을 확인했다. 구현하지 않은 담당이 코드와 앞선 실제 근거를 승인했다. 이 최종 결합판의 실제 근거·문서 독립 리뷰와 문서 확정 뒤 새 필수 CI·정상 보호 병합 대기열은 남아 있다. 이 문서 변경은 제품·시험 코드를 바꾸지 않는다. 제재 변경 화면·로그인/IP/기기 조사·월드 조작과 전체 AC-M3-04·05는 미완료이며 사용자 점검용5200의 계정·월드는 유지한다.

사용자 상세 API·화면은 현재 후속 묶음에서 검증 중입니다. 사용자 찾기의 상세 보기 또는 사용자 UUID의 상세 조회 버튼을 누르면 계정·참가 장수·제재를 읽습니다. 장수와 제재는 각각 최대50건이며 전체 수와 생략 여부를 표시합니다. 대상이 없는 조회도 감사1행을 확정한 뒤 찾을 수 없음을 반환합니다. 조회 실패·창 전환·계정 교체에는 이전 결과를 지우고 버튼을 눌러 다시 조회합니다. 제재 변경·로그인 자료 화면과 전체 관리자 인수는 남아 있습니다.

제재 API는 보호 main에 병합했으며 제재 변경 화면은 현재 후속 후보에서 구현·검증 중입니다. 사용자 상세를 읽은 뒤 대상·범위·사유·한국 시각 만료를 확인해 생성하거나 보이는 제재를 해제합니다. 미확정 응답은 같은 요청 다시 확인으로 이어가고 계정·권한 거부에는 초안을 지웁니다. 아직 보호 병합이나 전체 관리자 인수 근거가 아닙니다. `admin.sanction.create`는 대상 사용자 UUID, 월드 UUID(전체는null), 사유, 만료 ISO 시각(무기한은null)을 받습니다. 관리자는 본인이나 다른 ADMIN을 제재할 수 없습니다. 만료 시각은 서버 현재보다 뒤여야 합니다. `admin.sanction.lift`는 제재 UUID와 사유를 받으며 이미 해제한 요청도 성공하되 감사에서 변경 여부를 구분합니다. 제재 행과 대상 계정·월드 이력은 자동 삭제하지 않습니다.

이 화면 후보는 실제 PostgreSQL73건·시각 변환3건·공개 Chromium8건과 독립 코드/집중 근거 리뷰를 통과했습니다. 세션 종료·재로그인 거부·해제, 두 정식 월드의 한 월드 차단과 다른 월드 저장·30칸 보존, 실제 응답 유실과429의 동일 요청 재확인, 현재 관리자 전환·권한 회수·늦은 응답을 확인했습니다. 보호 main291을 정상 결합한 뒤 안내 문구와 문서를 정리한 최신 후보도 전체299파일5382건(353.30초)·공개110/승인6/외부0·실제 공개 Chromium4건(4.4초)을 통과했습니다. 세 명령 종료0·실행 중14파일 해시 불변을 확인했고 이 기록 보완은 제품·시험12파일을 보존합니다. 화면에 없는 월드 조작·로그인 조사는 후속이며 최종 문서와 새 head의 필수CI·보호 병합은 남아 있습니다.

깨끗한 후보 `ff075491`의 전체 실제 PostgreSQL94파일1493건(1087.13초)과 권한88절차·418실행·기존 면제22개·누락0, 실제 백업/복원·canonical 대조가 통과했다. 같은 후보의 필수 이메일 인증 Chromium5건(25.3초), 동의 Chromium8건(1.4분)도 통과했다. 자기 서비스 종료0·환경 복원·OID·연결0·자기 DB 삭제·정리 오류0과 실행 중14파일 해시 불변을 확인했으며 비구현 담당이 실제 근거를 승인했다. 이어 보호 병합된292 `e094573`·293 `f7873da`를 정상 통합한 `678294d`는 세 문서만 달라 제품·시험·설정을 보존한다. 같은 선행 계약이 이동한 문서 충돌은 내용이 같은지 대조해 한 번만 유지했고 독립 리뷰도 승인했다. 최종 문서와 새 head의 필수 CI·정상 보호 병합은 남아 있다.

보호 main에 병합한 선행 계약은 생성·해제에 기대 사용자 UUID를 받습니다. 값이 있으면 서버 세션과 일치해야 하며 새 화면은 항상 보냅니다. 생성의 요청 UUID는 사용자별로 한 번 확정한 결과를 확인하는 데 쓰며 같은 요청의 내용이 바뀌면 거부합니다. 동일 요청 재확인은 제재·감사·세션 변경을 반복하지 않습니다. 실제 변경 트랜잭션에서 현재 관리자와 세션·인증·동의를 다시 검사합니다. 이 계약은 독립 리뷰와 필수CI·정상 대기열 검사를 거쳐 PR #293으로 main에 병합됐습니다. 전체 관리자 AC 인수는 남아 있습니다.

계정 전체 제재는 세션을 모두 닫고 새 로그인과 세션 갱신을 거부합니다. 월드 제재는 해당 월드의20개 게임 변경 요청을 거부하며 조회·복구와 다른 월드의 예약은 유지합니다. 접수한 입력과 기존30칸 예약은 취소하지 않고 엔진이 계속 실행합니다. 만료·해제된 제재는 차단하지 않습니다. 본인 조회 `sanction.mine`은 현재 세션의 유효한 월드 제재·월드 이름·사유·만료만 반환하며 타인 사용자 ID를 받지 않습니다.

생성·해제는 같은 트랜잭션에서 `sanction.create`·`sanction.lift` 감사와 확정됩니다. 감사 payload에는 제재 UUID·범위·시각·변경 여부만 담고 이메일·IP·토큰·사유 원문을 중복 넣지 않습니다. 제재 표시 화면·로그인/IP/기기 자료는 별도 묶음입니다.

보호 main에 병합한 `admin.user.search`의 query는 사용자 UUID, 이메일 앞부분3~254자, 또는 `{ worldId, generalName }`을 받습니다. 이름 앞부분은1~30자이며 지정 월드의 사람 장수만 찾습니다. 이메일은 소문자로 정규화하고 `%`·`_`·역슬래시를 검색 문자로 처리합니다. 고유 사용자 최대50명을 생성 시각·사용자 ID 내림차순으로 돌려줍니다. 결과 필드는 `userId`·`email`·`status`·`role`·`createdAt`·`activeSanctions`이며 마지막 값은 서버 현재 유효한 전체·월드 제재 개수입니다. 비밀번호·세션·토큰·로그인 자료는 읽지 않습니다. 사용자 상세·로그인 기록을 빈 값으로 대신하지 않습니다.

결과와 `user.search` 감사는 같은 RepeatableRead 트랜잭션에서 처리합니다. 행위자 User를 공유 잠금으로 다시 확인하고 ACTIVE·ADMIN이 아니면 거부합니다. 감사 targetType은 `User`, targetId는null이며 이름 검색은 월드 ID만 남깁니다. payload는 `queryKind`·`resultCount` 두 키만 담습니다. 검색어·이름·이메일·검색 대상 UUID·결과 UUID는 남기지 않고0결과도 기록합니다. 감사 쓰기가 실패하면 결과를 응답하지 않습니다.

게임 화면 본문 위에는 본인에게 유효한 현재 월드 제재의 사유와 기한이 표시됩니다. 기한은 한국 시각과 ISO 원문으로 확인하며 무기한은 기한 없음으로 표시합니다. 변경 요청이 거부되면 상태를 다시 확인하고 수동 새로 확인도 할 수 있습니다. 조회 실패에는 재시도가 표시됩니다. 계정 확인 중과 계정이 바뀐 응답에는 이전 사용자의 안내를 숨깁니다. 안내가 사라져도 변경 권한은 서버가 최종 검사합니다.

## 4. 공지

공지 API는 로비와 지정 월드를 구분합니다. `admin.notice.list`는 `scope`와 WORLD의 `worldId`를 받으며 숨긴 이력도 발행 시각·ID 내림차순50개와 다음 커서로 반환합니다. 로비 요청에는 월드 ID를 넣지 않습니다. 제목은1~200자, 본문은1~2,000자이며 앞뒤 공백을 지웁니다. 기존 CLI가 발행한 제목 없는 월드 공지와 고정 여부는 보존합니다.

`admin.notice.create`·`update`·`hide`는 각 요청의 UUID `idempotencyKey`를 받습니다. 수정·숨김은 조회한 `expectedRevision`도 보냅니다. 같은 관리자·키·입력의 재전송은 원래 결과만 반환하고 공지나 감사를 더 만들지 않습니다. 다른 입력에 같은 키를 쓰거나 이전 판을 고치면 CONFLICT입니다. 숨김은1~200자 사유를 받으며 행을 보존하고 일반 로비·월드 공지 조회에서 제외합니다. 되살리기 API는 없습니다.

변경 트랜잭션은 월드, 행위자, 세션, 공지 순으로 잠그고 현재 세션·역할·이메일 인증·동의를 다시 검사합니다. 감사와 멱등 결과를 함께 저장하며 감사 실패면 공지 변경도 롤백합니다. 감사 payload에는 전후 판 번호·숨김 여부·요청 UUID만 남기고 제목·본문·해시는 넣지 않습니다. 입력 비교 해시와 원래 결과는 별도 `AdminNoticeRequest`에만 저장합니다. 월드 변경 알림은 커밋 뒤 보냅니다. API 묶음은 독립 리뷰를 통과했고 필수 CI·보호 병합을 진행 중입니다.

`/admin/notices`에서 범위를 고른 뒤 목록을 조회하고 작성·수정·사유를 적은 숨김을 실행합니다. 숨긴 이력도 남고 본문은 텍스트로 표시합니다. 전송 결과를 모르면 입력과 UUID를 유지한 같은 요청 다시 확인만 허용합니다. 실제429의 남은 초 동안 버튼을 잠그고 결과 확인 전 범위·폼·메뉴 이동을 막습니다. 일시적 권한 조회 실패는 작성 내용을 이 탭에 보존하며 복구를 기다립니다. 권한 회수·계정 변경이면 이전 입력을 지웁니다. 실제 두 정식 월드와 로비·권한 회수·계정 전환을 포함한 Chromium7건은 통과했고 전체 검사·최종 리뷰·보호 병합은 남아 있습니다. 전체 관리자 AC는 미완료입니다.
