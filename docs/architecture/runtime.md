# 런타임

> 상태: 로컬 실행 초안 (T1-02) · 서버 배포는 M2 · 참고: core2026 `docs/architecture/runtime.md`
> 이 문서가 답할 질문: 어떤 프로세스가 몇 개 뜨고 무엇을 설정하고 어떻게 켜고 끄나?

## 1. 프로세스

ADMIN-CREATE-B 후보의 기본 감독은 월드 발견 주기마다 `WorldCreateRequest`의 가장 오래된 PENDING 한 건을 소비한다. 한 감독 안에서는 생성 소비가 겹치지 않으며 다른 월드의 발견·재시작을 기다리게 하지 않는다. 여러 감독은 요청 행 잠금으로 중복 생성을 막는다. 종료 신호를 받은 감독은 진행 중 소비의 정착도 기다린다. `--world <ID>` 실행은 전역 생성 요청을 소비하지 않는다. 새 월드는 PREOPEN으로 저장하며 명시 시작을 기다린다. 현재 관리자 권한이나 전체 제재가 바뀌면 거절하고 접수 뒤 로그아웃만 한 경우에는 유효한 요청을 유지한다.

관리자 강제 종료 후보는 기존 API와 감독·엔진 자식만 사용한다. 새 종료 CLI나 별도 daemon은 없다. 접수 API는 입력과 감사만 쓰며 엔진의 리스·월드 트랜잭션이 종료를 확정한다. 접수 뒤 로그아웃은 자동 취소가 아니다. 감독과 `--world` 실행의 실제 기동·대기 입력 정리·재기동·정상 종료 검증은 아직 남아 있다. 구현 검토와 격리 시험만 허용하며 기존 사용자5200과 운영 월드를 종료하지 않는다.

| 프로세스     | 개수                           | 역할                                       |
| ------------ | ------------------------------ | ------------------------------------------ |
| `server`     | 1                              | API, SSE, 정적 화면 제공                   |
| `supervisor` | 1                              | 실행·정지 월드 발견, 자식 시작·종료·재시작 |
| `engine`     | 프로세스 하나가 월드 하나 담당 | 리스가 있는 프로세스만 턴 실행             |
| PostgreSQL   | 1                              | 저장                                       |
| Caddy        | 1                              | HTTPS, 프록시                              |

`pnpm dev`와 인자 없는 `pnpm engine:run`은 감독을 실행합니다. 감독은 10초마다 RUNNING·PAUSED 월드와 PENDING 생성이 남은 ENDED 월드를 조회하고 월드마다 자식 하나를 유지합니다. PREOPEN·처리가 끝난 ENDED·삭제 월드의 자식은 내립니다. `pnpm engine:run --world <ID>`는 기존처럼 지정한 월드 하나만 실행하며 `runEngine` 직접 호출도 유지합니다. `pnpm --filter @opensamguk/engine supervisor`로도 감독을 실행할 수 있습니다.

## 2. 환경변수

루트 `.env`에 둡니다 (`.env.example`을 복사). 비밀값은 운영에서 파일(`/run/secrets`)로만 넣습니다.

| 이름                     | 의미                                                  | 기본값 (로컬)                                                                          | 비밀            | 상태                                                  |
| ------------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------- |
| `DATABASE_URL`           | PostgreSQL 연결                                       | `postgresql://opensamguk:opensamguk@127.0.0.1:5433/opensamguk`                         | 예              | 사용 중                                               |
| `SERVER_PORT`            | API 서버 포트                                         | `3001`                                                                                 | 아니오          | 사용 중                                               |

| `TRUST_PROXY`            | 운영 Caddy 한 단계만 신뢰 (`1`), 소켓 IP만 사용 (`0`) | `0`                                                                                    | 아니오          | 사용 중                                               |
| `SESSION_SECRET`         | 사용하지 않음. 무작위 토큰의 SHA-256을 DB에서 조회    | —                                                                                      | —               | 불필요 (T1-10)                                        |

| `AUDIT_HASH_KEY_VERSION` | 새 키와 함께 올리는 양의 정수 버전                    | 없음                                                                                   | 아니오          | 키와 함께 필수                                        |
| `VITE_IMAGE_BASE_URL`    | 초상 이미지 base URL                                  | 비우면 jsDelivr 고정 커밋 주소 ([이미지 자산 §2](../image-assets.md#2-초상-id와-경로)) | 아니오 (공개값) | 사용 중                                               |

세션 쿠키 `sid`는 HttpOnly·SameSite=Lax·Path=/이며 `NODE_ENV=production`에서 Secure를 붙입니다.
DB에는 토큰 원문 대신 SHA-256만 저장하고 성공한 활동의 응답에서 DB와 쿠키 모두 30일로 연장합니다. 거부한 요청은 갱신 대상 시점이어도 세션 만료를 바꾸지 않습니다.
계정 상태가 ACTIVE가 아니거나 세션이 만료되면 인증하지 않습니다. 요청 로그에는 URL·본문·쿠키·원본 오류를 기록하지 않습니다.

운영 설정에서 Secure를 끄면 서버가 시작하지 않습니다. `/trpc` POST와 SSE 요청은 `Origin`이 `PUBLIC_ORIGIN`과 같아야 합니다. Origin이 없을 때만 `Sec-Fetch-Site: same-origin`을 받습니다. 잘못된 Origin을 다른 헤더로 덮어 허용하지 않습니다. 변경 요청은 `application/json`(선택적 charset 허용)만 받고 다른 형식은 415입니다. Origin 거부는 403이며 인증·본문 처리보다 먼저 실행합니다. CORS를 열지 않습니다.

개발 화면도 Vite의 같은 출처 `/trpc` 프록시를 씁니다. `localhost`로 접속하려면 `PUBLIC_ORIGIN=http://localhost:5173`을 정확히 맞춥니다. HTTP 시험 클라이언트는 같은 화면 출처의 Origin과 JSON을 명시하며 시험용 예외 목록은 두지 않습니다.

`TRUST_PROXY=1`은 Caddy 바로 뒤의 한 단계만 믿는 설정입니다. API는 loopback에 바인딩하며 외부에서 직접 접속할 수 없게 유지합니다. 개발에서는 기본값 `0`으로 두므로 `X-Forwarded-For`로 한도를 바꿀 수 없습니다. 앞단 프록시가 늘면 이 값을 무작정 늘리지 말고 연결 경계를 다시 검토합니다.

프로세스마다 메모리 계수기가 하나입니다. 로그인 IP 30회/15분, 실패한 이메일·IP 조합 5회/15분, 가입 IP 10회/시간, 인증 변경 사용자 120회/분입니다. 창은 epoch 기준이고 재시작하면 계수가 비며 여러 서버 사이에는 공유하지 않습니다. 차단 응답은 429와 정수 초 `Retry-After`, tRPC `TOO_MANY_REQUESTS`, `data.reason=null`입니다. 키·IP·이메일·토큰은 로그·파일·DB에 저장하지 않습니다. 계수기는 T3-04 단독 소유이고 T3-02는 같은 공개형을 import만 합니다.

서버 응답에는 `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`를 붙입니다. CSP·HSTS의 검토용 Caddy 소스와 적용 경계는 [릴리스 운영](../release-operations.md#5-프록시-경로)에 있습니다.

### 로그인 조사 기록 (AC-M3-05 구현 중)

개발에서 조사 키를 설정하지 않으면 기존처럼 기록하지 않습니다. 운영에는 키와 버전이 필요하며 잘못된 값은 DB 연결 전에 고정 안내로 시작을 거부합니다. 운영의 공개 약관·개인정보 정책이 아직 null이면 로그인 복구 경로에서도 조사 기록과 기기 쿠키를 발급하지 않습니다. 이 설정이 정책을 승인하거나 운영 수집을 활성화하지는 않습니다.

수집이 활성화된 가입·로그인은 전체 `ctx.ip`와 무작위 128비트 `did`를 해시로만 기록합니다. `did`는 HttpOnly·SameSite=Lax·Path=/·1년 쿠키이며 운영에서 Secure를 씁니다. 로그아웃은 보존하고 승인된 탈퇴 트랜잭션은 해당 기록을 지운 뒤 쿠키를 삭제합니다. 원문 IP·기기 값·키는 DB·로그·공개 환경변수에 넣지 않습니다. 키를 교체할 때 버전도 올리며 다른 버전의 기록은 같은 묶음으로 합치지 않습니다. 실제 DB·브라우저 검증은 후속이며 최대 90일 조회와 보존 정책은 구분합니다.

### 세션 갱신 오류

인증 단계의 세션 조회 오류는 요청 실패로 처리하며 handler를 실행하지 않습니다. 인증과 handler가 성공한 HTTP 200 응답의 선택적 갱신은 별도로 처리합니다. 이때 세션 조회나 만료 연장에 실패해도 원래 상태 코드와 본문을 보존하고 `세션 갱신 실패`라는 고정 경고만 남깁니다. 오류 원문이나 식별자는 기록하지 않으며 새 `sid` 쿠키를 보내거나 메모리에서 만료를 연장하지 않습니다. DB 갱신 결과가 불명확해도 업무 변경을 다시 실행하거나 되돌리지 않습니다. 거부 응답과 혼합 batch의 207은 계속 갱신 대상에서 제외합니다.

`turns.set`·`turns.edit`는 같은 revision과 본문을 다시 보내면 기존 `STALE` 응답과 최신 snapshot을 돌려줍니다. 클라이언트가 지정하는 requestId 계약은 없습니다. `tools/session-renewal.integration.test.ts`는 파일 전용 DB를 생성해 실제 loopback HTTP로 검증합니다. PostgreSQL trigger의 세션 UPDATE 예외와 InputEvent 커밋에 맞춘 세션 테이블 rename으로 갱신 SELECT 오류를 각각 넣고 `finally`에서 복구합니다. 업무 예턴·InputEvent·revision의 1회 반영, 원래 200 응답, 쿠키·만료 불변과 같은 revision 재전송을 확인합니다. 인증 단계 SELECT 오류, 정상·동시 갱신, 만료·제재·429·잘못된 입력·207, 로그인·로그아웃 쿠키도 같은 시험에서 확인합니다. 소켓·운영 DB 장애를 주입하는 시험은 아닙니다.

## 3. 로컬 실행

```sh
cp .env.example .env   # 처음 한 번
pnpm install
pnpm generate          # Prisma client 생성
pnpm db:up             # PostgreSQL 18, 127.0.0.1:5433
pnpm db:migrate        # 저장소의 migration 적용
pnpm dev               # web 127.0.0.1:5173 · server 127.0.0.1:3001 · engine
pnpm e2e               # 스모크 테스트 (dev 서버가 없으면 자동으로 켬)
pnpm db:down           # DB 끄기 (데이터는 볼륨에 남음)
```

월드 생성 (T1-03):

```sh
pnpm world:create --scenario 1030 --map che --seed demo --turn-term 10 --end-year 300 --name 군웅할거
```

생성된 월드 ID와 초기 상태 SHA-256을 출력합니다. 새 월드는 재생 형식 3이며 `--rule-features a,b`로 규칙 기능을 지정합니다. 운영 기능 등록 목록은 현재 비어 있어 값을 주면 생성 전에 거부합니다. 값을 생략하면 기능 없는 월드를 만듭니다. 상태는 `PREOPEN`, 초기 tick은 0입니다.
이름과 턴 간격(1~2147483647분), 필수 종료 연도(시작 연도 이상 10000 이하 정수)를 검사하고 리소스 검사나 DB 저장 실패 시 부분 월드를 남기지 않습니다. 300은 이 예시의 명시 인자이며 운영 기본값은 없습니다. `saveInitialWorld`도 종료 연도나 통일 전용 `null`을 명시해서 받습니다.
월드 시작·일시정지·재개는 아래 월드 상태 전환 명령을 사용합니다.

- web은 `/trpc` 요청을 server로 프록시합니다. 프록시 대상 포트는 server와 같은 `SERVER_PORT`를 따릅니다
  (프로세스 환경변수 → 루트 `.env` → 3001, `apps/web/apiTarget.ts`).
- server·engine은 `tsx watch`로 실행합니다. Node `--watch`는 macOS에서 파일 감시 한도를 넘어 실패했습니다.
- Claude 실행 환경의 sandbox는 Docker 소켓과 로컬 포트를 막습니다. 그 환경에서는 sandbox 밖에서 실행하거나
  `sandbox.network.allowLocalBinding`을 켭니다.

## 4. 엔진 수명 주기

1. 월드별 `EngineLease`를 획득합니다. 없거나 DB 시각 기준으로 만료된 리스만 가져오며 fencingToken을 증가시킵니다. 획득하지 못하면 1초마다 재시도합니다.
2. 만료 시간은 15초, 갱신은 5초마다입니다. 게임 시계의 manual/realtime 여부와 관계없이 리스는 DB UTC 시각을 씁니다.
3. 리스 행과 월드 행을 잠그고 시계·실행할 장수를 확인합니다. 장수는 `nextTurnTick`, ID 오름차순으로 실행합니다. 빈 사람 예턴은 휴식입니다. 밀린 사건은 64step·250ms 배치로 나눕니다. 상한에 닿으면 `setImmediate`로 양보하고 아니면 100ms 기다립니다. 가속은 벽시계 대신 다음 사건을 목표로 삼습니다. 턴이 없는 realtime 폴링은 전체 적재를 생략하고 시계만 5초마다 체크포인트합니다. 이 간격은 프로세스의 monotonic 시각으로 재며 PAUSED/PREOPEN/ENDED에서는 쓰지 않습니다.
4. 상태 변경·로그·예턴 당김·다음 턴·시계 체크포인트를 한 트랜잭션에 저장합니다. commit 직전에 소유자·토큰·만료를 다시 검사합니다. 리스 행 잠금은 commit/rollback까지 유지되어 실행권 이전과 낡은 쓰기가 겹치지 않습니다.
5. 갱신 실패·토큰 불일치·리스 만료는 프로세스 오류 종료입니다. 실행권 상실은 `LeaseLostError` 이름·이유를 출력하고 DB 오류 원문은 연결 정보 보호를 위해 출력하지 않습니다. SIGINT/SIGTERM은 처리 중 트랜잭션을 취소하고 리스를 해제한 뒤 DB 연결을 닫습니다. 리스 해제는 만료 시각만 바꾸고 토큰을 지우지 않습니다.

엔진은 리스 획득 뒤 첫 월드 잠금에서 `replayOrigin`과 `replayFormat`·`ruleFeatures` 사본을 대조합니다. 버전이나 기능 목록이 어긋나거나 기능 검사가 실패하면 게임 상태를 쓰기 전에 그 월드만 멈춥니다. 감독은 기존 월드별 장애 정책으로 다루고 다른 월드는 계속 실행합니다. 초기 해시는 수출·재생에서 검사합니다. 새 입력 종류를 받는 배포는 엔진 먼저, 서버 나중입니다. 엔진보다 서버를 먼저 올려 모르는 PENDING 종류가 생기면 그 월드를 멈춥니다.

테스트·시뮬레이터는 `TurnLoop.advanceTo(tick)`으로 게임 시간을 직접 주입합니다. 운영은 `poll()`로 DB 시각과 월드 기준 시각에서 tick을 계산합니다. PAUSED/PREOPEN/ENDED에서는 턴을 처리하지 않습니다.

종료 사건과 결과 저장 뒤에는 남은 PENDING 생성을 거부하고 실행권을 해제합니다. `--world` 자식은 코드 0으로 끝나며 감독은 ENDED의 정상 종료를 장애 횟수에 넣지 않습니다. 그 자식의 heartbeat·리스 갱신 루프도 끝납니다. `runEngine`을 월드 지정 없이 직접 부르면 다음 RUNNING 월드를 찾습니다. 정상 종료 뒤 결과를 다시 만들거나 다음 사건을 실행하지 않습니다.

감독은 비정상 종료한 자식을 1·2·4초 순으로 기다려 다시 시작합니다. 최대 대기는 60초이고 5분 이상 살아 있던 자식은 백오프 단계를 초기화합니다. 5분 안에 5회 종료한 월드는 자동 재시작을 멈추고 `EngineHeartbeat.lastError`에 고정 안내를 남깁니다. 원인을 고친 뒤 감독을 다시 시작하면 재시도합니다. 이 중단은 감독 인스턴스별로 적용하며 World 상태와 게임 입력은 바꾸지 않습니다. 감독이 둘이어도 자식의 기존 EngineLease 펜싱이 동시 게임 쓰기를 막습니다.

실행권을 가진 자식은 획득 직후와 이후 30초마다 자기 월드의 EngineHeartbeat를 갱신합니다. 이 쓰기도 리스 잠금·토큰 검사 뒤에만 합니다. `at`은 DB 관측 시각, `lastTick`은 관측 순간 저장된 World.clockTick입니다. 밀린 턴을 모두 처리했다는 뜻은 아닙니다. `lagMs`는 이전 관측 완료 뒤 예정한 30초 시점보다 이번 관측 시작이 늦어진 시간이며 음수가 될 수 없습니다. 첫 관측은 실행권 획득 직후를 기준으로 합니다. 턴 적체 시간은 이 값에 포함하지 않습니다. 정상 관측은 lastError를 비웁니다. 감독의 오류 기록은 기존 at·lastTick·lagMs를 보존하며 아직 관측 행이 없을 때만 현재 tick과 lagMs 0으로 만듭니다.

자식의 DB 오류·리스 상실은 해당 프로세스만 종료시킵니다. 감독의 월드별 오류 기록이 실패해도 다른 월드의 재시작을 기다리게 하지 않습니다. 로그에는 고정 분류만 남기며 DB 오류 원문과 연결 문자열은 출력하지 않습니다. 관측값은 재생 입력·게임 상태·해시에 들어가지 않습니다.

SIGINT·SIGTERM을 받은 감독은 새 자식을 시작하지 않고 자기 자식에 SIGTERM을 보냅니다. 5초 뒤에도 살아 있으면 그 PID에만 SIGKILL을 보냅니다. 모든 자식 종료와 진행 중 오류 기록을 기다린 뒤 자기 DB 연결을 닫습니다. 다른 감독·직접 실행한 엔진·서버 프로세스에는 신호를 보내지 않습니다. 운영 호스트 서비스 설치와 배포는 T2-15에서 따로 합니다.

Windows에서는 부모가 연 IPC 채널로 정상 종료를 요청하며 같은 abort·리스 해제 경로를 거칩니다. 요청이 전달되지 않거나 무시되면 같은 5초 뒤 소유 자식에만 SIGKILL을 보냅니다.

## 5. 월드 상태 전환

`pnpm world:start --world <ID>`로 시작합니다. `world:pause`, `world:resume`, `world:status`도 같은 인자를 받습니다. 정지 중에는 tick이 고정됩니다. 엔진과 운영 명령은 DB의 UTC 시각(`clock_timestamp()`)을 rules에 인자로 주입하며 기준 시각·tick·revision을 저장합니다. 테스트만 시각을 명시적으로 주입합니다. 운영 명령도 먼저 월드 행을 `FOR UPDATE`로 잠근 뒤 최신 상태와 DB 시각을 읽습니다. 실행 중인 턴·체크포인트를 기다려 직렬화하므로 엔진의 revision 증가 때문에 정상 정지·재개가 거부되지 않습니다. 이미 정지한 월드를 다시 정지하는 등 잘못된 상태 전환은 계속 거부합니다.

`pnpm world:accelerate --world <ID>`와 `pnpm world:realtime --world <ID>`로 같은 판의 시계 모드만 바꿉니다. RUNNING·PAUSED에서 다른 모드로만 전환하며 정지·재개는 모드를 보존합니다. 가속 배율이나 강제 종료 명령은 없습니다. `world:status`에서 모드·종료 연도·종료 결과를 확인합니다.

## 공개 지도 사본 (T2-24, AC-M2-20)

엔진과 서버는 같은 `PUBLIC_MAP_DELAY_MINUTES`(기본 10분), `PUBLIC_MAP_INTERVAL_MINUTES`(기본 5분)를 읽습니다. 값은 날짜 범위 안의 양의 십진 정수(분)여야 하며 간격이 지연보다 길면 두 프로세스가 시작을 거부합니다. `packages/shared/src/publicMap.ts`가 두 값을 함께 검사합니다.

`PublicMapSnapshot`은 월드와 실제 기록 시각을 복합 키로 씁니다. RUNNING 월드의 장수 턴이나 월간 정산 뒤, 마지막 사본부터 저장 간격 이상 지났을 때 엔진이 하나를 찍습니다. 턴이 없는 poll, 장수 생성 입력 처리, PAUSED·ENDED에서는 새 사본을 찍지 않습니다. 종료를 확정하는 처리에서도 추가 사본을 찍지 않고 이전 사본을 남깁니다. 저장과 오래된 사본 삭제는 턴과 같은 리스·월드 잠금·트랜잭션 안에서 처리합니다. 지연 cutoff 이하의 사본 중 최신 하나와 그보다 새로운 사본을 보존합니다. 간격 기준은 DB에서 읽으므로 엔진 재시작 뒤에도 유지됩니다. 턴이 없거나 일시정지한 월드는 사본이 15분보다 오래될 수 있으므로 화면은 `takenAt`으로 실제 나이를 표시해야 합니다.

기록 시각은 상태를 반영한 뒤의 DB 시각입니다. 시험에서는 `TurnLoop`의 `publicMapNow` 시계만 주입합니다. 밀린 턴을 처리할 때 월드 시계의 진행 목표는 아직 반영하지 않은 턴보다 앞설 수 있으므로 사본 `tick`은 방금 반영한 장수 턴 또는 월 경계 tick을 씁니다. 연월은 그 tick의 `toGameDate`입니다. 월간 연감의 지난달 정산 연월을 재사용하지 않습니다.

`world.publicMaps()`는 인증 없이 RUNNING·PAUSED 월드를 `createdAt`, `id` 순서로 읽습니다. 월드마다 요청 시각에서 지연 시간을 뺀 cutoff 이하의 최신 사본만 반환합니다. 아직 사본이 공개되지 않았거나 JSON 필수 필드 형식이 깨졌으면 `map: null`이며 현재 도시·국가 정보로 대체하지 않습니다. 시각은 ISO 문자열이고 응답의 지도에는 사본의 연월만 들어갑니다.

저장과 응답 모두 도시의 `key`, `name`, `level`, `x`, `y`, `nationId`, `links`와 국가의 `id`, `name`, `color`만 담습니다. 계획 DTO에 맞춰 도시 key와 연결 key는 문자열입니다. 기존 인증 `world.map`의 숫자 key와 `supplied`는 그대로 유지합니다. 사본 JSON에 다른 필드가 섞여도 서버는 새로 투영해 버립니다. 장수·병력·보급·국고·출병 정보는 공개하지 않습니다. 사본은 게임 상태·RNG·sequence·재생 archive에 넣지 않아 기존 상태 해시와 v1/v2 형식을 유지합니다.

계획의 기존 요청 제한 설명은 현재 구현과 다릅니다. `publicProcedure`에는 횟수 제한이 없고 `protectedProcedure`의 mutation만 기존 사용자 제한을 받습니다. 이 작업은 새 공개 GET 제한 정책을 추가하지 않습니다. 기존 인증·출처 검사·보안 헤더는 유지합니다.

## T4-46 추가 시나리오 초기화

기존 migration을 적용한 뒤 내장 다섯 판을 먼저 넣고 추가 시나리오를 넣습니다.

```sh
pnpm db:init-resources
pnpm db:init-scenarios
```

두 번째 명령은 `packages/db/sql/resources-scenarios.sql`을 한 트랜잭션에서 실행합니다. 기존 내장 판을 확인한 뒤 A9의 내용·해시·상태·출처를 대조합니다. 같은 판은 기존 행으로 세고 다른 판이 같은 키에 있으면 전체 삽입을 되돌립니다. 내장 다섯 판과 `1030`은 덮지 않습니다. 출력에는 삽입·기존 행 수와 실패 키만 남깁니다.

`pnpm resources:sql:scenarios`는 83행 출처 fixture에서 `ready`인 9종만 읽어 별도 SQL을 다시 만듭니다. 기존 `resources:sql`이나 `resources-init.sql`은 바꾸지 않습니다. `ready`는 생성 대상이며 AC 완료가 아닙니다. 원형 복원·두 시드·SQL 바이트는 `tools/scenarios.test.ts`, 초기화·원자 거부·DB 합성·한 달 정산은 `tools/scenarios.integration.test.ts`에서 확인합니다. DB 시험은 조율된 실행창의 자기 전용 `_test` DB에서만 돌리고 정식 증거는 정확한 SHA의 CI에서 남깁니다.

## 계정 토큰과 개발 메일함

탈퇴 API 후보는 `account.get.withdrawalAvailable`로 현재 서버의 실행 가능 여부를 알립니다. 승인된 개인정보처리방침 본문·판과 일치하는 보존 정책의 기본 상수는 null이며 개발·운영 모두 `account.withdraw`를503·무변경으로 거부합니다. HTTP 입력·환경 변수·VITE 값으로 승인하지 않습니다. 신뢰한 시험 생성자에서만 현재 정책을 명시해 전용 DB로 검증합니다. 활성화된 처리도 서버 세션·기대 UUID·현재 비밀번호를 확인하고 사용자당15분5회·IP당15분15회 제한을 적용합니다. 탈퇴 commit 뒤 sid·did 쿠키와 모든 이전 세션의 SSE를 닫으며 다른 계정의 연결을 보존합니다. 화면·정책 승인·전체 공개 인수는 [T3-02](../plans/T3-02.md)의 남은 관문입니다.

공개 실행 이미지와 UID10001·0700/0600 비밀 파일 계약은 [릴리스 운영의 실행 이미지](../release-operations.md#공개-실행-이미지-t2-15-b2a)를 따릅니다. DB URL만 exec 환경에 넣고 메일 키는 파일 경로로 전달합니다. Linux의 두 정식 월드 기동·정상 종료를 확인했으며 Compose/Caddy 배포·실제 운영 메일 인수는 후속입니다.

운영 서버는 이메일 인증을 항상 요구합니다. `EMAIL_VERIFICATION_REQUIRED=0`이나 서버 생성자의 끄기·개발 모드 위장 설정을 거부하며 미설정·1만 허용합니다. 개발 기본값은 기존 계정·예약을 보존하고 `EMAIL_VERIFICATION_REQUIRED=1`로 같은 차단을 검증할 수 있습니다. 그 밖의 값은 시작 오류입니다. 기존 계정의 인증 일시·동의를 채우거나 접수한 예약을 지우지 않습니다.

게임·메시지·공지의 변경 API20개는 기존 세션·요청 한도 뒤 현재 DB의 인증 일시를 확인합니다. 미인증이면403·`EMAIL_NOT_VERIFIED`이며 입력 본문으로 본인이나 인증 여부를 바꿀 수 없습니다. 가입·로그인·로그아웃과 인증·비밀번호 복구7개, 기존 조회는 계속 가능합니다. `account.get`의 `emailVerificationRequired`·`emailVerified`가 서버의 요구와 본인 상태를 알립니다. 이 서버 차단의 첫 묶음에는 동의·탈퇴나 게임 화면 이동 가드가 없습니다.

운영 메일 후보는 `MAIL_TRANSPORT=resend`로 명시할 때만 연결합니다. `MAIL_FROM`은 인증한 발신 도메인의 주소이고 `MAIL_API_KEY_FILE`은 키만 든 비밀 파일의 절대 경로입니다. 키는 환경값·Git·명령 인자·로그나 `VITE_*`에 넣지 않습니다. 목적지는 고정된 `https://api.resend.com/emails`이며 redirect와 자동 재시도 없이 응답 본문 처리까지10초로 제한합니다. 같은 발송의 멱등 키는 본문 해시로 만들고 원문 주소·토큰을 헤더에 넣지 않습니다. 공급자 접수 ID를 확인해도 실제 메일함 수신을 확인한 것은 아닙니다. 사용자 서비스 선택·도메인 인증·실제 수신 인수는 남아 있습니다.

공개 인증·재설정 소비는 `account.token.ip` 공유 버킷으로 IP당15분30회까지 허용하며 초과 시429와 정수 초 `Retry-After`를 받습니다. 무효 재설정 후보는 저장된 용도·미사용·만료·계정 상태를 먼저 읽어 거부하고 비싼 비밀번호 해시를 계산하지 않습니다. 실제 소비 때는 잠금 안에서 조건을 다시 확인합니다.

개발 API 진입점은 `MAIL_TRANSPORT`가 없으면 capture를 선택합니다. `MAIL_CAPTURE_DIR`는 기본 `.mail-outbox`이며 실행 디렉터리를 기준으로 완성된 JSON 메일을 저장합니다. 주소·URL 조각의 원문 토큰이 있으므로 이 디렉터리는 비밀 파일로 다루고 Git·공개 정적 파일·로그에 넣지 않습니다. `PUBLIC_ORIGIN`으로 인증·재설정 링크의 출처를 고정합니다.

`NODE_ENV=production`에서는 capture와 미설정·미지원 전송을 API 시작 전에 거부합니다. Resend 후보도 발신 주소와 올바른 키 파일이 있어야 시작합니다. 실제 서비스 선택·발신 도메인 인증과 수신 인수는 남아 있습니다. `buildServer`의 전송 주입은 실제 PG/HTTP 시험과 같은 내부 생성 경계이며 운영 진입점의 설정 검사를 대신하지 않습니다.

`account.get`은 서버 세션의 사용자 UUID와 본인 이메일·인증 여부·동의 기록을 읽습니다. `account.resendVerification`은 이미 인증됐으면 메일 없이 성공하고 미인증 계정은 분당1번·UTC 하루5번의 공유 계수기를 씁니다. 초과하면429와 정수 초 `Retry-After`를 받습니다. `account.requestPasswordReset`은 정규화한 주소당 시간3번까지만 발송하며 없는 주소·제재·탈퇴·초과·발송 실패도 같은 성공 응답입니다. 한도 초과는 `Retry-After`를 싣지 않습니다.

`account.verifyEmail`과 `account.resetPassword`는 무효·사용·만료 토큰을400·`TOKEN_INVALID`로 거부합니다. 토큰은 SHA-256 해시로만 저장하고 인증24시간·재설정30분·한 번 소비를 적용합니다. 재설정의 비밀번호와 세션 폐기는 같은 트랜잭션이며 commit 뒤 그 세션들의 SSE 종료를 별도 알림으로 전합니다. 다른 계정의 세션·연결은 보존합니다.

게임 진입·루트·알림 설정은 세션과 `account.get`을 새로 확인합니다. 서버가 인증 필수라고 답한 미인증 계정은 인증 화면으로 갑니다. 조회 실패는 재시도로 막고 가입·로그인이 이미 성공했다면 입력을 다시 보내지 않습니다. 열린 화면의 변경 API가403·`EMAIL_NOT_VERIFIED`를 돌려줘도 인증 화면으로 가며 같은 월드·고른 도시·기존 초안은 복귀 뒤 이어집니다. 계속하기와 재로그인 목적지는 정규화 뒤에도 같은 사이트 경로인지 검사하고 토큰 hash를 버립니다. 로비·계정·인증/재설정은 복구 경로입니다. 약관 동의·탈퇴·운영 메일 수신은 남아 있으며 이 연결만으로 공개 계정 인수를 완료하지 않습니다.
