## 0. 이 문서의 위치

D-028 계획 가운데 자원 판의 초안 저장, 복제, 게시를 서버 API로 여는 몫이다. 지도만이 아니라 다섯 종류(지도, 시나리오, 병종, 능력치 규칙, 초상 대응표)를 같은 절차로 다룬다. 화면 계획 T4-81과 T4-87은 이 문서 2절의 절차 이름, 입력, 결과 모양, 오류 코드를 그대로 쓴다.

카탈로그 표(`GameResource`)의 모양은 T4-77, 검증 함수는 T4-76이 같은 날 따로 정한다. 이 문서는 설계 문서의 C-M1~C-M4를 기준으로 쓰고 두 계획과 맞춰야 할 점은 6절 쟁점 표에 둔다. 관리자 권한과 감사 로그는 T3-05 계획(아직 main에 없다)의 `adminProcedure`·`AuditLog`를 그대로 쓴다.

계획 기술 검토(명세 G-03)와 사용자 리뷰를 통과하고 T4-77·T3-05가 main에 들어온 뒤 착수한다.

## 계획 (Claude)

### 목표

운영자 계정이 게시한 자원 판을 복제해 초안을 만든다. 초안은 revision과 함께 저장하고 검증을 통과한 초안만 게시한다. 게시한 판은 API와 DB 양쪽에서 고칠 수도 지울 수도 없다. 두 운영자가 같은 초안을 고치면 늦게 저장한 쪽이 거부된다. 권한 없는 계정(무인증, 일반 계정, 제재 계정)의 요청은 거부되고 DB가 바뀌지 않는다. 초안 생성·저장·폐기와 게시는 그 변경과 같은 트랜잭션에서 감사 로그에 남는다.

AC-P2-27 가운데 이 작업이 내는 증거는 HTTP 권한과 PostgreSQL 몫이다. 화면(E2E)은 T4-81·T4-87, 새 판으로 월드 만들기와 진행 중 월드 보존은 T4-79 몫이다. 이 작업만으로 AC-P2-27을 완료로 세지 않는다.

## 1. 지금 코드 (main `3e5b52a`)

- 자원은 아직 파일이다. 엔진 `loadInitialWorld`가 다섯 파일을 읽는다(`apps/engine/src/world/resources.ts:15-28`). 키 검사는 `^[a-zA-Z0-9_-]+$`이다(`resources.ts:6-9`). DB 카탈로그는 T4-77 몫이라 아직 없다.
- 서버에는 관리자 역할이 없다. 절차는 `publicProcedure`와 `protectedProcedure` 둘이다(`apps/server/src/trpc.ts:15-28`). `adminProcedure`, `User.role`, `AuditLog`는 T3-05 계획에만 있다([T3-05 관리자 권한](./T3-05.md#관리자-권한), [감사 로그](./T3-05.md#감사-로그)).
- 변경 절차는 `protectedProcedure`의 mutation 분기에서 계정당 1분 120번 한도를 받는다(`trpc.ts:18-25`). 관리자 절차도 그 위에 쌓이므로 이 한도를 그대로 받는다.
- 오류 응답의 `data.reason`은 늘 `null`이다(`trpc.ts:9`). 그래서 화면이 구분해야 하는 실패는 오류가 아니라 결과 값으로 돌려준다. 같은 방식이 예턴 저장에 있다. 장수 revision이 다르면 오류를 던지지 않고 `{ ok: false, reason: 'STALE', revision, slots }`를 돌려준다(`apps/server/src/routers/turns.ts:47-48`).
- 권한 대조는 `appRouter`의 모든 절차에 다섯 범주 증거를 요구한다(`apps/server/src/authz/coverage.ts:1`, `:43-50`). 증거는 `authzCase`(`authz/case.ts:6-16`)가 남기고 실제 HTTP 시험은 `tools/authz.integration.test.ts`의 `paths`(`:25-50`)와 반복문(`:132-186`)이다. 거부 사례는 `snapshot()`(`:84-100`)으로 DB 불변을 본다. 제재 범주는 `User.status = SANCTIONED` 계정이다(`:111`).
- 상태 해시는 키를 정렬한 정규 JSON의 SHA-256이다(`packages/shared/src/node/hashState.ts:3-24`). C-M1a의 정규 해시도 같은 규칙이다. T4-77이 이 함수를 그대로 쓸지 따로 둘지 정한다.
- 서버 요청 본문 한도는 Fastify 기본값 1 MiB다(`apps/server/src/server.ts:59-63`에 `bodyLimit` 설정이 없다). 지금 가장 큰 자원은 `resources/scenario/1030.json` 136,442바이트(들여쓰기 포함)다.

## 2. 계약

### 2.1 판의 상태와 키

- 종류는 `MAP`·`SCENARIO`·`UNIT_SET`·`STAT_RULES`·`PORTRAIT_MAP` 다섯이다(C-M1).
- 판 하나는 종류, 이름, 판 번호로 정해진다. `(kind, name, version)`은 유일하다.
- 이름은 `^[a-zA-Z0-9_-]{1,40}$`이다. 지금 키 검사(`resources.ts:6-9`)에 길이만 더했다. `@`는 이름에 쓸 수 없다.
- 키의 정규형은 판 번호가 1이면 이름만(`che`), 2 이상이면 `<이름>@<판 번호>`(`che@2`)다. 입력은 `che`와 `che@1`을 같은 판으로 받는다. C-M1의 별칭 규칙을 모든 이름에 똑같이 적용한 것이다. 그래서 내장 판의 키는 지금 월드의 `mapKey`·`scenarioKey`·`unitSetKey`와 같다.
- 상태는 `DRAFT`와 `PUBLISHED` 둘이다. 바뀌는 방향은 `DRAFT → PUBLISHED` 하나뿐이다.
- 초안은 종류·이름마다 하나만 있다. 초안을 만들 때 판 번호를 그 이름의 가장 큰 번호 + 1로 미리 정한다. 게시하면 그 번호가 그대로 남는다. 초안을 버리면 행이 지워지고 다음 복제가 같은 번호를 다시 쓴다. 버린 초안을 가리키는 월드나 재생 기록은 없으므로 번호를 다시 써도 깨지는 것이 없다. 감사 로그는 행 ID로 구분한다.
- 시나리오 판은 함께 쓸 지도 판의 키 하나를 가진다(C-M3a). 이 문서에서는 `mapKey`라고 부른다(6절 Q-02). 다른 종류는 `null`이다.

### 2.2 저장 모델에 필요한 것

T4-77의 `GameResource` 표에 아래가 있어야 한다. T4-77 migration에 없는 것만 이 작업의 새 migration이 더한다(6절 Q-01).

| 항목 | 모양 | 쓰는 곳 |
| ---- | ---- | ------- |
| `revision` | `Int @default(0)`. 초안 저장마다 1 오른다 | 늦은 저장 거부 (2.6) |
| `updatedBy`, `updatedAt` | 사용자 UUID(내장 판은 `null`), 시각 | 충돌 결과에 누가 언제 저장했는지 |
| `publishedBy` | 사용자 UUID(내장 판은 `null`) | 목록과 감사 대조 |
| `mapKey` | `String?`, 시나리오만 | 2.1, 검증 (2.7) |
| 초안 하나 규칙 | `CREATE UNIQUE INDEX ... ON "GameResource"(kind, name) WHERE status = 'DRAFT'` (Prisma에 부분 유일 색인이 없어 migration SQL에 둔다) | 복제 경합 (2.6) |
| 게시 판 불변 트리거 | 게시 판의 `UPDATE`·`DELETE`를 거부한다. `UPDATE`는 이전 행이 `DRAFT`이고 새 행이 `PUBLISHED`이며 `kind`·`name`·`version`이 그대로일 때만 받는다. `status`를 `DRAFT`로 되돌리는 갱신도 거부한다 | 판 불변 (§6 검증 표) |

초기화 SQL(T4-77)은 내장 판을 처음부터 `PUBLISHED`로 넣는다. 트리거는 `INSERT`를 막지 않으므로 초기화 SQL과 부딪히지 않는다.

### 2.3 권한

- 여섯 절차 모두 T3-05의 `adminProcedure`를 거친다. 세션이 없거나 계정 상태가 `ACTIVE`가 아니면 `UNAUTHORIZED`, DB의 `role`이 `ADMIN`이 아니면 `FORBIDDEN`이다. 역할 검사는 입력 파싱보다 앞이다(T3-05 권한 대조 절과 같다).
- C-M4의 자원 편집 권한은 지금 T3-05의 관리자 역할 하나로 본다. T3-05에는 관리자 등급이 하나뿐이고 여러 등급은 하지 않는 것에 있다. 자원 편집을 관리자 일부에게만 줄지는 7절 U-T78-1이다.
- 행위자는 세션에서 정한다. 입력에 `createdBy`·`updatedBy`·`actorUserId` 같은 칸은 없고 `strictObject`라서 넣으면 `BAD_REQUEST`다.
- 관리자끼리는 서로의 초안을 고칠 수 있다. 초안은 개인 소유가 아니다. 그래서 권한 대조의 다른 사용자 범주는 일반 USER 계정의 `FORBIDDEN`으로 본다.

### 2.4 절차

라우터 키는 `resourceAdmin`이다. 월드별 판 조회(T4-85의 `routers/resources.ts`)와 이름이 겹치지 않게 했다.

```ts
type ResourceKind = 'MAP' | 'SCENARIO' | 'UNIT_SET' | 'STAT_RULES' | 'PORTRAIT_MAP';
type ResourceStatus = 'DRAFT' | 'PUBLISHED';
type Issue = { code: string; message: string; target: unknown }; // T4-76 검증기 결과 그대로 (6절 Q-03)

type ResourceMeta = {
  id: string;                 // 행 ID (UUID)
  kind: ResourceKind;
  name: string;
  version: number;
  key: string;                // 정규형 (2.1)
  status: ResourceStatus;
  revision: number;
  contentHash: string;        // 정규 해시 hex 64자
  mapKey: string | null;      // 시나리오만
  source: string | null;      // 출처 (C-M1a), 복제하면 원본 판의 값을 물려받는다
  sizeBytes: number;          // 정규 JSON의 UTF-8 바이트 수
  createdBy: string | null;   // 내장 판은 null
  createdAt: string;          // ISO 8601
  updatedBy: string | null;
  updatedAt: string;
  publishedBy: string | null;
  publishedAt: string | null;
};

// 조회 (query)
resourceAdmin.list({ kind?, name?, status?, cursor? })
  → { items: ResourceMeta[]; next: string | null }
  // 순서: kind, name 오름차순, version 내림차순. 한 번에 50개. 내용(content)은 싣지 않는다
resourceAdmin.get({ id })
  → { meta: ResourceMeta; content: unknown; issues: Issue[] }
  // issues는 부를 때마다 2.7 규칙으로 다시 돌린 결과. 게시 판도 돌려준다

// 변경 (mutation)
resourceAdmin.clone({ sourceId, name? })
  → { ok: true; meta: ResourceMeta }
  | { ok: false; reason: 'DRAFT_EXISTS'; draftId: string }
  | { ok: false; reason: 'NAME_TAKEN' }
resourceAdmin.save({ id, revision, content, mapKey? })
  → { ok: true; meta: ResourceMeta; issues: Issue[] }
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }   // meta는 지금 DB 값
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
resourceAdmin.publish({ id, revision, reason })
  → { ok: true; meta: ResourceMeta }
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }
  | { ok: false; reason: 'INVALID'; issues: Issue[] }
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
resourceAdmin.discard({ id, revision, reason? })
  → { ok: true }
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
```

입력 규칙:

| 칸 | 규칙 |
| -- | ---- |
| 모든 입력 | zod `strictObject` |
| `id`, `sourceId` | UUID |
| `kind`, `status` | 위 열거값 |
| `name` | 2.1의 이름 규칙 |
| `cursor` | `list`가 돌려준 불투명 문자열, 200자 이하 |
| `revision` | 정수 0 이상 2,147,483,646 이하 (`turns.ts:12`와 같은 범위) |
| `content` | JSON 객체(배열·원시값 불가). 정규 JSON이 900,000바이트를 넘으면 `BAD_REQUEST`. 정규 해시 함수가 받지 못하는 값(유한하지 않은 숫자 등)도 `BAD_REQUEST` |
| `mapKey` | 시나리오 초안에서만 받는다. 다른 종류에 주면 `BAD_REQUEST`. 형식은 키 정규형이나 `<이름>@1`. 그 판이 실제로 있는지는 검증 결과(2.7)로 알린다 |
| `reason` | 앞뒤 공백을 지운 1~200자. 게시에는 필수, 폐기에는 선택. 개인정보를 쓰지 않는다는 안내는 화면 몫이다(T3-05와 같다) |

절차별 동작:

- `clone`: 원본은 게시 판만 받는다. 초안이 원본이면 `BAD_REQUEST`, 없으면 `NOT_FOUND`다. `name`을 비우거나 원본과 같게 주면 같은 이름의 다음 판이 된다. 다른 이름을 주면 그 종류에 그 이름이 없어야 하고 판 번호 1로 시작한다. 이미 있으면 `NAME_TAKEN`이다. 그 이름에 초안이 이미 있으면 새로 만들지 않고 `DRAFT_EXISTS`와 그 초안 ID를 돌려준다. 같은 요청을 두 번 보내도 초안은 하나라서 따로 멱등 키를 두지 않는다. 내용, `source`, `mapKey`는 원본에서 복사하고 `revision`은 0이다. 내용 안의 `id` 칸은 바꾸지 않는다. 월드 키는 카탈로그 키로 정한다(T4-79).
- `save`: 초안의 내용을 통째로 바꾼다. 부분 수정은 없다. 검증 오류가 있어도 저장한다. 초안은 고치는 중인 값이라 그렇다. 돌려준 `issues`로 화면이 오류를 보인다.
- `publish`: 2.6의 잠금 아래에서 검증(2.7)을 다시 돌려 오류가 하나라도 있으면 바꾸지 않고 `INVALID`를 돌려준다. 통과하면 상태를 `PUBLISHED`, `publishedBy`·`publishedAt`을 채운다. 이미 게시된 판에 같은 `revision`으로 다시 게시를 부르면 처음 결과와 같은 `{ ok: true, meta }`를 돌려준다(응답을 받지 못한 재시도). 다른 `revision`이면 `PUBLISHED`다.
- `discard`: 초안 행을 지운다. 게시 판이면 `PUBLISHED`다.
- `list`·`get`은 감사 행을 쓰지 않는다. 자원 내용에는 개인정보가 없다.

### 2.5 오류

오류는 `data.code`로만 구분하고 `data.reason`은 `null`이다(`trpc.ts:9`, T3-05). 화면이 따로 처리해야 하는 실패는 위 결과 값의 `reason`으로 돌려준다.

| `data.code` | 언제 | 문구 |
| ----------- | ---- | ---- |
| `UNAUTHORIZED` | 세션 없음, 계정 상태가 `ACTIVE` 아님(제재 포함) | `로그인이 필요합니다.` (기존 `trpc.ts:17`) |
| `FORBIDDEN` | 관리자가 아님 | T3-05 `adminProcedure`의 문구 |
| `BAD_REQUEST` | 입력 파싱 실패, 내용 크기 초과, 초안을 복제 원본으로 줌, 시나리오가 아닌 종류에 `mapKey` | `요청 값을 확인하세요.`, `자원 내용이 너무 큽니다.`, `게시한 판만 복제할 수 있습니다.`, `시나리오만 함께 쓸 지도를 정합니다.` |
| `NOT_FOUND` | `id`·`sourceId`에 행이 없음(버린 초안 포함) | `자원 판을 찾지 못했습니다.` |
| `TOO_MANY_REQUESTS` | 계정당 변경 한도 (`trpc.ts:18-25`) | 기존 문구 |
| `INTERNAL_SERVER_ERROR` | 감사 행 쓰기 실패 등. 트랜잭션 전체가 롤백된다 | 기존 문구 (`trpc.ts:10`) |

결과 값의 `reason`:

| `reason` | 절차 | 화면이 할 일 |
| -------- | ---- | ------------ |
| `STALE` | `save`, `publish`, `discard` | 다른 운영자가 먼저 저장했다. `meta.updatedBy`·`meta.updatedAt`을 보이고 다시 불러오게 한다. 보낸 내용의 해시가 `meta.contentHash`와 같으면 자기 저장이 이미 들어간 재시도이므로 성공으로 본다 |
| `PUBLISHED` | `save`, `publish`, `discard` | 이미 게시된 판이다. 고치려면 복제한다 |
| `INVALID` | `publish` | `issues`를 보인다. 저장된 초안은 그대로다 |
| `DRAFT_EXISTS` | `clone` | `draftId`의 초안을 연다 |
| `NAME_TAKEN` | `clone` | 다른 이름을 고르게 한다 |

### 2.6 동시 편집과 잠금

- `save`는 한 문장 비교 갱신이다. `UPDATE ... SET content, contentHash, revision = revision + 1, updatedBy, updatedAt WHERE id = $id AND status = 'DRAFT' AND revision = $revision RETURNING *`. 0행이면 같은 트랜잭션에서 행을 다시 읽어 없으면 `NOT_FOUND`, 게시 판이면 `PUBLISHED`, 아니면 `STALE`이다. 두 운영자가 같은 revision으로 동시에 저장하면 PostgreSQL 행 잠금 때문에 하나만 1행을 갱신하고 다른 하나는 `STALE`을 받는다.
- `publish`와 `discard`는 `SELECT ... FOR UPDATE`로 행을 잠근 뒤 상태와 revision을 본다. `publish`는 시나리오면 `mapKey`의 지도 판을 `FOR SHARE`로 읽는다. 잠금 순서는 늘 초안 행 → 참조 판이다. 참조 판은 게시 판이라 바뀌지 않으므로 교착이 생기지 않는다.
- `clone`은 `pg_advisory_xact_lock(hashtext(kind || ':' || name))`으로 그 이름을 잠근 뒤 초안 유무와 가장 큰 판 번호를 읽고 넣는다. 잠금을 빠뜨려도 2.2의 부분 유일 색인과 `(kind, name, version)` 유일 제약이 두 번째 넣기를 막는다. 그 경우 유일 위반을 잡아 `DRAFT_EXISTS`로 바꾼다.
- 저장과 게시가 겹치면 먼저 행을 잡은 쪽이 이긴다. 게시가 먼저면 늦은 저장은 `PUBLISHED`, 저장이 먼저면 게시는 `STALE`이다. 저장되지 않은 내용이 게시되는 일은 없다.
- 트랜잭션 격리 수준은 기본 `READ COMMITTED`다. 위 비교 갱신과 행 잠금으로 충분하다.

### 2.7 검증 호출

검사는 T4-76이 `packages/rules`에 둔 종류별 순수 함수다(C-M3·C-M3a). 서버는 DB에서 필요한 판을 읽어 넘기고 결과를 그대로 돌려준다. 같은 함수를 편집 화면도 부른다.

| 종류 | 서버가 함께 넘기는 것 | 서버가 더하는 결과 |
| ---- | --------------------- | ------------------ |
| `MAP` | 없음 | 없음 |
| `SCENARIO` | `mapKey`의 지도 판 내용 | `mapKey`가 없으면 `scenario-map-missing`, 그 판이 없거나 초안이면 `scenario-map-unpublished` |
| `UNIT_SET`, `STAT_RULES`, `PORTRAIT_MAP` | 없음 | 없음 |

- 지도 판을 게시할 때 그 지도를 쓰는 시나리오 검사(C-M3 셋째 항목)는 하지 않는다. 새 지도 판을 가리키는 게시 시나리오는 아직 있을 수 없고(시나리오는 게시 지도만 가리킨다), 옛 시나리오는 옛 지도 판을 계속 가리킨다. 지도·시나리오 짝의 검사는 시나리오 게시 때 한다. 그래서 도시를 지운 지도 판도 게시할 수 있다. 그 지도를 쓰려면 시나리오를 복제해 `mapKey`를 바꾸고 고쳐서 게시한다. T4-76 검증기의 시그니처와 맞출 점은 6절 Q-03이다.
- 시나리오가 쓰는 병종이 병종 판에 모두 있는지(C-M3a 병종 항목)는 게시 때 보지 않는다. 시나리오는 병종 판을 기록하지 않아서다. 월드를 만들 때 고른 다섯 판의 조합으로 다시 검사한다(T4-79).
- 서버가 더하는 두 코드의 문구는 `함께 쓸 지도를 정하지 않았습니다.`, `함께 쓸 지도 <키>가 게시되지 않았습니다.`이다.

### 2.8 감사 로그

T3-05 `AuditLog`에 변경과 같은 트랜잭션으로 한 행씩 쓴다. 감사 행 쓰기가 실패하면 변경도 롤백되고 `INTERNAL_SERVER_ERROR`다(T3-05 감사 로그 절).

| `action` | 언제 | `reason` | `payload` |
| -------- | ---- | -------- | --------- |
| `resource.draft.create` | `clone` 성공 | 없음 | `{ kind, name, version, sourceId, sourceKey, contentHash, mapKey }` |
| `resource.draft.save` | `save` 성공 | 없음 | `{ kind, name, version, revisionFrom, revisionTo, contentHashFrom, contentHashTo, mapKeyFrom, mapKeyTo, issueCount }` |
| `resource.draft.discard` | `discard` 성공 | 입력의 `reason` | `{ kind, name, version, revision, contentHash }` |
| `resource.publish` | `publish`가 상태를 바꿈 | 입력의 `reason` | `{ kind, name, version, key, revision, contentHash, mapKey }` |

- 모든 행이 `actorKind = ADMIN`, `actorUserId` = 세션 사용자, `targetType = GAME_RESOURCE`, `targetId` = 행 ID, `worldId = null`이다.
- 내용 전체는 넣지 않는다. 해시만 넣는다. 게시 판은 내용이 DB에 영구히 남고 해시로 대조된다. 초안 중간 내용은 남지 않는다(7절 U-T78-2).
- 거부된 요청(권한, 입력, `STALE`, `PUBLISHED`, `INVALID`, `DRAFT_EXISTS`, `NAME_TAKEN`)과 게시 재시도의 성공 응답은 바뀐 것이 없으므로 감사 행을 쓰지 않는다. 그래서 권한 대조의 DB 불변 비교와 맞는다.
- `action` 값 네 개는 T3-05의 `action` 목록(감사 로그 절)에 더한다. T3-05의 감사 조회 필터 `action` 앞부분으로 `resource.`를 주면 이 네 가지가 나온다.
- 초기화 SQL이 넣는 내장 판의 감사 기록은 T4-77 몫이다(6절 Q-05).

## 8. 상대 영역에 필요한 것

- T4-81·T4-87(Claude 화면): 2.4의 절차와 결과 모양, 2.5의 `reason`별 처리. `STALE`이면 지금 DB 값을 다시 불러오고 운영자에게 덮어쓸지 묻지 않는다(덮어쓰기 절차는 없다). `issues`의 `target`으로 편집 화면의 대상을 고른다. 저장은 6절 Q-07대로 운영자 동작에서만 부른다. 화면 권한 가드는 T3-05 `admin.whoami()`다.
