## 0. 이 문서의 위치

D-028 계획 가운데 자원 판의 초안 저장, 복제, 게시를 서버 API로 여는 몫이다. 지도만이 아니라 다섯 종류(지도, 시나리오, 병종, 능력치 규칙, 초상 대응표)를 같은 절차로 다룬다. 화면 계획 T4-81과 T4-87은 이 문서 2절의 절차 이름, 입력, 결과 모양, 오류 코드를 그대로 쓴다(R14).

카탈로그 표(`GameResource`)의 모양은 T4-77, 검증 함수는 T4-76이 정한다. 이 문서는 설계 문서의 C-M1~C-M4와 조율 결정을 기준으로 쓰고 남은 맞출 점은 6절 쟁점 표에 둔다. 관리자 권한과 감사 로그는 T3-05 계획의 `adminProcedure`·`AuditLog`를 쓴다. 이 둘은 아직 main에 없으므로 이 문서에서는 가정이다(R19). 이름은 [T3-05 관리자 권한](./T3-05.md#관리자-권한)과 [감사 로그](./T3-05.md#감사-로그) 절의 이름과 맞췄다.

계획 기술 검토(명세 G-03)와 사용자 리뷰를 통과하고 T4-76·T4-77·T3-05가 main에 들어온 뒤 착수한다.

## 계획 (Claude)

### 목표

운영자 계정이 게시한 자원 판을 복제해 초안을 만든다. 초안은 revision과 함께 저장하고 검증을 통과한 초안만 게시한다. 게시한 판은 API와 DB 양쪽에서 고칠 수도 지울 수도 없다. 두 운영자가 같은 초안을 고치면 늦게 저장한 쪽이 거부된다. 권한 없는 계정(무인증, 일반 계정, 제재 계정)의 요청은 거부되고 DB가 바뀌지 않는다. 초안 생성·저장·폐기와 게시는 그 변경과 같은 트랜잭션에서 감사 로그에 남는다.

AC-P2-27 가운데 이 작업이 내는 증거는 HTTP 권한과 PostgreSQL 몫이다. 화면(E2E)은 T4-81·T4-87, 새 판으로 월드 만들기와 진행 중 월드 보존은 T4-79 몫이다. 이 작업만으로 AC-P2-27을 완료로 세지 않는다.

## 1. 지금 코드 (main `3e5b52a`)

- 자원은 아직 파일이다. 엔진 `loadInitialWorld`가 다섯 파일을 읽는다(`apps/engine/src/world/resources.ts:15-28`). 키 검사는 `^[a-zA-Z0-9_-]+$`이다(`resources.ts:6-9`). DB 카탈로그는 T4-77 몫이라 아직 없다.
- 서버에는 관리자 역할이 없다. 절차는 `publicProcedure`와 `protectedProcedure` 둘이다(`apps/server/src/trpc.ts:15-28`). `adminProcedure`, `User.role`, `AuditLog`는 T3-05 계획에만 있다(가정, R19).
- 변경 절차는 `protectedProcedure`의 mutation 분기에서 계정당 1분 120번 한도를 받는다(`trpc.ts:18-25`). 관리자 절차도 그 위에 쌓이므로 이 한도를 그대로 받는다.
- 오류 응답의 `data.reason`은 늘 `null`이다(`trpc.ts:9`). 그래서 화면이 구분해야 하는 실패는 오류가 아니라 결과 값으로 돌려준다. 같은 방식이 예턴 저장에 있다. 장수 revision이 다르면 오류를 던지지 않고 `{ ok: false, reason: 'STALE', revision, slots }`를 돌려준다(`apps/server/src/routers/turns.ts:47-48`).
- 권한 대조는 `appRouter`의 모든 절차에 다섯 범주 증거를 요구한다(`apps/server/src/authz/coverage.ts:1`, `:43-50`). 증거는 `authzCase`(`authz/case.ts:6-16`)가 남기고 실제 HTTP 시험은 `tools/authz.integration.test.ts`의 `paths`(`:25-50`)와 반복문(`:132-186`)이다. 거부 사례는 `snapshot()`(`:84-100`)으로 DB 불변을 본다. 제재 범주는 `User.status = SANCTIONED` 계정이다(`:111`).
- 상태 해시는 키를 정렬한 정규 JSON의 SHA-256이다(`packages/shared/src/node/hashState.ts:3-24`). C-M1a의 정규 해시도 같은 규칙이다. 카탈로그의 `hash` 열은 T4-77이 이 규칙으로 채운다.
- 서버 요청 본문 한도는 Fastify 기본값 1 MiB다(`apps/server/src/server.ts:59-63`에 `bodyLimit` 설정이 없다). 지금 가장 큰 자원은 `resources/scenario/1030.json` 136,442바이트(들여쓰기 포함)다.
- 지도 내용은 `id`를 가진다(`resources/map/che.json`의 `"id": "che"`). 시나리오와 병종도 `id`가 있고 능력치 규칙과 초상 대응표는 없다. `buildInitialWorld`는 이 `id`를 월드 키로 쓴다(`packages/rules/src/world/bootstrap.ts:264-266`).

## 2. 계약

### 2.1 판의 상태와 키

- 종류는 `MAP`·`SCENARIO`·`UNIT_SET`·`STAT_RULES`·`PORTRAIT_MAP` 다섯이다(C-M1).
- 행은 UUID 기본 키 `id`를 가지고 `(kind, name, version)`이 유일하다(R1). API와 감사는 `id`로 가리킨다. 화면 주소는 `kind`·`name`·`version`을 쓰고 `list`로 `id`를 찾는다.
- 이름은 `^[a-zA-Z0-9_-]{1,40}$`이다. 지금 키 검사(`resources.ts:6-9`)에 길이만 더했다. `@`는 이름에 쓸 수 없다. 이 규칙이 정본이고 T4-77·T4-81이 따른다(R5).
- 키의 정규형은 판 번호가 1이면 이름만(`che`), 2 이상이면 `<이름>@<판 번호>`(`che@2`)다(R4). 입력은 `che`와 `che@1`을 같은 판으로 받는다. 그래서 내장 판의 키는 지금 월드의 `mapKey`·`scenarioKey`·`unitSetKey`와 같다.
- 상태는 `DRAFT`와 `PUBLISHED` 둘이다. 바뀌는 방향은 `DRAFT → PUBLISHED` 하나뿐이다.
- 초안은 종류·이름마다 하나만 있다. 초안을 만들 때 판 번호를 그 이름의 가장 큰 번호 + 1로 미리 정한다. 게시하면 그 번호가 그대로 남는다. 초안을 버리면 행이 지워지고 다음 복제가 같은 번호를 다시 쓴다. 버린 초안을 가리키는 월드나 재생 기록은 없으므로 번호를 다시 써도 깨지는 것이 없다. 감사 로그는 행 `id`로 구분한다.
- 시나리오 판은 함께 쓸 지도 판의 키 하나를 `mapKey` 열에 가진다(C-M3a, R3). 내장 `1030` 1판은 `che`다(R6, T4-77 초기화 SQL). 다른 종류는 `null`이다.
- 지도 초안은 v2 형식만 저장하고 게시한다(R8). 내장 `che` 1판처럼 v1인 게시 판은 그대로 남는다.

### 2.2 저장 모델

| 항목 | 모양 | 누가 만드나 | 쓰는 곳 |
| ---- | ---- | ----------- | ------- |
| `id`, `(kind, name, version)` 유일 | UUID 기본 키와 유일 제약 | T4-77 (R1) | 2.1 |
| `hash` | NOT NULL, 초안에도 있다. 저장마다 다시 계산한다 | T4-77 (R2) | 늦은 저장 판정 보조, 감사 |
| `source` | NOT NULL. 복제하면 원본 값을 물려받는다 | T4-77 (R2) | 출처 |
| `createdBy`, `updatedBy`, `publishedBy` | 사용자 UUID, 내장 판은 `null` | T4-77 (R2) | 목록, 충돌 결과 |
| `updatedAt`, `publishedAt` | 시각 | T4-77 | 목록, 충돌 결과 |
| `revision` | `Int @default(0)`. 초안 저장마다 1 오른다 | T4-77 (R3) | 늦은 저장 거부 (2.6) |
| `mapKey` | `String?`, 시나리오만 | T4-77 (R3) | 2.1, 검증 (2.7) |
| 게시 판 불변 트리거 | 이전 행이 `PUBLISHED`인 `UPDATE`·`DELETE`를 거부한다. 이전 행이 `DRAFT`인 `UPDATE`는 `id`·`kind`·`name`·`version`이 그대로일 때 받는다. 초안 저장(`DRAFT` → `DRAFT`, 2.6 비교 갱신)과 게시(`DRAFT` → `PUBLISHED`)가 여기 든다. 이전 행이 `DRAFT`인 `DELETE`는 받는다(`discard`). 정의는 T4-77 계약 1(`T4-77.md` 모델 절)과 같다 | T4-77 (R3) | 판 불변 (§6 검증 표) |
| 초안 하나 규칙 | `CREATE UNIQUE INDEX ... ON "GameResource"(kind, name) WHERE status = 'DRAFT'` (Prisma에 부분 유일 색인이 없어 migration SQL에 둔다) | 이 작업의 새 migration (R20) | 복제 경합 (2.6) |
| `baseKey` | `String?`. 복제 원본 판의 정규형 키. 초기화 SQL이 넣은 판은 `null` | 이 작업의 새 migration (R20) | 화면의 복제 원본 칸, 지도 게시 검증의 참고 시나리오 (2.7) |

초기화 SQL(T4-77)은 내장 판을 처음부터 `PUBLISHED`로 넣는다. 트리거는 `INSERT`를 막지 않으므로 초기화 SQL과 부딪히지 않는다.

### 2.3 권한

- 여섯 절차 모두 T3-05의 `adminProcedure`를 거친다(가정, R19). 세션이 없거나 계정 상태가 `ACTIVE`가 아니면 `UNAUTHORIZED`, DB의 `role`이 `ADMIN`이 아니면 `FORBIDDEN`이다. 역할 검사는 입력 파싱보다 앞이다(T3-05 권한 대조 절과 같다).
- C-M4의 자원 편집 권한은 지금 T3-05의 관리자 역할 하나로 본다. T3-05에는 관리자 등급이 하나뿐이고 여러 등급은 하지 않는 것에 있다. 자원 편집을 관리자 일부에게만 줄지는 7절 U-T78-1이다.
- 행위자는 세션에서 정한다. 입력에 `createdBy`·`updatedBy`·`actorUserId` 같은 칸은 없고 `strictObject`라서 넣으면 `BAD_REQUEST`다.
- 관리자끼리는 서로의 초안을 고칠 수 있다. 초안은 개인 소유가 아니다. 그래서 권한 대조의 다른 사용자 범주는 일반 USER 계정의 `FORBIDDEN`으로 본다.

### 2.4 절차

라우터 키는 `resourceAdmin`이다. 월드별 판 조회(T4-85의 `routers/resources.ts`)와 이름이 겹치지 않게 했다. 아래 이름과 입출력이 정본이다(R14).

```ts
type ResourceKind = 'MAP' | 'SCENARIO' | 'UNIT_SET' | 'STAT_RULES' | 'PORTRAIT_MAP';
type ResourceStatus = 'DRAFT' | 'PUBLISHED';
type ResourceIssue = import('@opensamguk/rules/resources').ResourceIssue; // T4-76 그대로: { code, severity, message, target, params, resource? } (R11)
type Person = { userId: string | null; label: string };         // label 규칙은 아래 표

type ResourceMeta = {
  id: string;                 // 행 ID (UUID)
  kind: ResourceKind;
  name: string;
  version: number;
  key: string;                // 정규형 (2.1)
  title: string | null;       // 표시 이름. 내용의 name(지도·병종)이나 title(시나리오). 둘 다 없으면 null
  status: ResourceStatus;
  revision: number;
  hash: string;               // 정규 해시 hex 64자. 초안에도 있다
  mapKey: string | null;      // 시나리오만
  baseKey: string | null;     // 복제 원본 판의 정규형 키. 초기화 SQL이 넣은 판은 null
  source: string;             // 출처 (C-M1a)
  sizeBytes: number;          // 정규 JSON의 UTF-8 바이트 수
  createdBy: Person;
  createdAt: string;          // ISO 8601
  updatedBy: Person | null;   // 한 번도 저장하지 않은 초안과 초기화 판은 null
  updatedAt: string;
  publishedBy: Person | null;
  publishedAt: string | null;
};

// 조회 (query)
resourceAdmin.list({ kind?, name?, status?, cursor? })
  → { items: ResourceMeta[]; next: string | null }
  // 순서: kind, name 오름차순, version 내림차순. 한 번에 50개. 내용(content)은 싣지 않는다
resourceAdmin.get({ id })
  → { meta: ResourceMeta; content: unknown; report: { ok: boolean; issues: ResourceIssue[] } }
  // report는 부를 때마다 2.7 규칙으로 다시 돌린 결과. 게시 판도 돌려준다

// 변경 (mutation)
resourceAdmin.clone({ sourceId, name? })
  → { ok: true; meta: ResourceMeta }
  | { ok: false; reason: 'DRAFT_EXISTS'; draftId: string }
  | { ok: false; reason: 'NAME_TAKEN' }
resourceAdmin.save({ id, revision, content, mapKey? })
  → { ok: true; meta: ResourceMeta; report: { ok: boolean; issues: ResourceIssue[] } }
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }   // meta는 지금 DB 값
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
resourceAdmin.publish({ id, revision, reason? })
  → { ok: true; meta: ResourceMeta; report: { ok: true; issues: ResourceIssue[] } } // 경고만 남을 수 있다
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }
  | { ok: false; reason: 'INVALID'; report: { ok: false; issues: ResourceIssue[] } }
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
resourceAdmin.discard({ id, revision, reason? })
  → { ok: true }
  | { ok: false; reason: 'STALE'; meta: ResourceMeta }
  | { ok: false; reason: 'PUBLISHED'; meta: ResourceMeta }
```

`Person.label` 규칙. 감사에는 UUID만 남기는 T3-05 원칙에 맞춰 이메일을 쓰지 않는다.

| 경우 | `label` |
| ---- | ------- |
| `userId`가 `null` (초기화 SQL, 명령줄 도구) | `초기화` 또는 `명령줄` (2.9의 행위자 종류) |
| 관리자 계정 | `관리자 ` + UUID 앞 8자 |
| 탈퇴한 계정 | `탈퇴한 관리자 ` + UUID 앞 8자 |

입력 규칙:

| 칸 | 규칙 |
| -- | ---- |
| 모든 입력 | zod `strictObject` |
| `id`, `sourceId` | UUID |
| `kind`, `status` | 위 열거값 |
| `name` | 2.1의 이름 규칙 |
| `cursor` | `list`가 돌려준 불투명 문자열, 200자 이하 |
| `revision` | 정수 0 이상 2,147,483,646 이하 (`turns.ts:12`와 같은 범위) |
| `content` | JSON 객체(배열·원시값 불가). 정규 JSON이 900,000바이트를 넘으면 `BAD_REQUEST`. 정규 해시 함수가 받지 못하는 값(유한하지 않은 숫자 등)도 `BAD_REQUEST`. 지도 초안은 `version`이 2여야 하고 아니면 `BAD_REQUEST` (R8) |
| `mapKey` | 시나리오 초안에서만 받는다. 다른 종류에 주면 `BAD_REQUEST`. 형식은 키 정규형이나 `<이름>@1`. 그 판이 실제로 있는지는 검증 결과(2.7)로 알린다 |
| `reason` | 앞뒤 공백을 지운 1~200자. 게시는 입력 칸으로 두되 필수 여부는 7절 U-T78-3이다. 정해지기 전에는 필수로 구현하고 비면 `BAD_REQUEST`다. 폐기는 선택. 개인정보를 쓰지 않는다는 안내는 화면 몫이다(T3-05와 같다) |

절차별 동작:

- `clone`: 원본은 게시 판만 받는다. 초안이 원본이면 `BAD_REQUEST`, 없으면 `NOT_FOUND`다. `name`을 비우거나 원본과 같게 주면 같은 이름의 다음 판이 된다. 다른 이름을 주면 그 종류에 그 이름이 없어야 하고 판 번호 1로 시작한다. 이미 있으면 `NAME_TAKEN`이다. 그 이름에 초안이 이미 있으면 새로 만들지 않고 `DRAFT_EXISTS`와 그 초안 `id`를 돌려준다. 같은 요청을 두 번 보내도 초안은 하나라서 멱등 키를 두지 않는다(R14). 복제한 초안은 아래처럼 만든다.
  - 내용은 원본에서 복사한다. 지도 원본이 v1이면 T4-76의 `normalizeMapToV2`로 v2로 올린다(빈 지형 층, 기본 캔버스 700×500. R8). 그래서 v1 원본을 복제한 초안의 `hash`는 원본과 다르다.
  - 내용에 `id` 칸이 있는 종류(지도, 시나리오, 병종)는 `id`를 새 이름으로 바꾼다(R7). 같은 이름의 다음 판이면 값이 그대로다. 지도·병종의 `name` 칸은 원본 `name`이 원본 `id`와 같을 때만 새 이름으로 바꾸고 다르면 둔다. 운영자가 붙인 표시 이름을 지우지 않으려는 것이다.
  - `source`와 `mapKey`는 원본에서 복사하고 `baseKey`는 원본의 정규형 키, `revision`은 0, `hash`는 위 내용의 정규 해시다.
- `save`: 초안의 내용을 통째로 바꾼다. 부분 수정은 없다. 검증 오류가 있어도 저장한다. 초안은 고치는 중인 값이라 그렇다. 돌려준 `report`로 화면이 오류와 경고를 보인다. 지도 초안의 v1 내용은 받지 않는다(위 입력 규칙).
- `publish`: 2.6의 잠금 아래에서 검증(2.7)을 다시 돌린다. `report.ok`가 `false`(심각도 `error`가 하나라도 있음)면 바꾸지 않고 `INVALID`를 돌려준다. 경고(`warning`)만 있으면 게시한다(R11). 통과하면 상태를 `PUBLISHED`, `publishedBy`·`publishedAt`을 채운다. 이미 게시된 판에 같은 `revision`으로 다시 게시를 부르면 처음 결과와 같은 `{ ok: true, meta }`를 돌려준다(응답을 받지 못한 재시도). 다른 `revision`이면 `PUBLISHED`다.
- `discard`: 초안 행을 지운다. 게시 판이면 `PUBLISHED`다. 조율 세션이 map-editor.md C-M4에 이 절차를 더한다(R14).
- `list`·`get`은 감사 행을 쓰지 않는다. 자원 내용에는 개인정보가 없다.

### 2.5 오류

오류는 `data.code`로만 구분하고 `data.reason`은 `null`이다(`trpc.ts:9`, T3-05). 화면이 따로 처리해야 하는 실패는 위 결과 값의 `reason`으로 돌려준다.

| `data.code` | 언제 | 문구 |
| ----------- | ---- | ---- |
| `UNAUTHORIZED` | 세션 없음, 계정 상태가 `ACTIVE` 아님(제재 포함) | `로그인이 필요합니다.` (기존 `trpc.ts:17`) |
| `FORBIDDEN` | 관리자가 아님 | T3-05 `adminProcedure`의 문구 |
| `BAD_REQUEST` | 입력 파싱 실패, 내용 크기 초과, 지도 초안에 v2가 아닌 내용, 초안을 복제 원본으로 줌, 시나리오가 아닌 종류에 `mapKey`, 게시 사유 빔 | `요청 값을 확인하세요.`, `자원 내용이 너무 큽니다.`, `지도 초안은 v2 형식이어야 합니다.`, `게시한 판만 복제할 수 있습니다.`, `시나리오만 함께 쓸 지도를 정합니다.`, `게시 사유를 적어 주세요.` |
| `NOT_FOUND` | `id`·`sourceId`에 행이 없음(버린 초안 포함) | `자원 판을 찾지 못했습니다.` |
| `TOO_MANY_REQUESTS` | 계정당 변경 한도 (`trpc.ts:18-25`) | 기존 문구 |
| `INTERNAL_SERVER_ERROR` | 감사 행 쓰기 실패 등. 트랜잭션 전체가 롤백된다 | 기존 문구 (`trpc.ts:10`) |

결과 값의 `reason`:

| `reason` | 절차 | 화면이 할 일 |
| -------- | ---- | ------------ |
| `STALE` | `save`, `publish`, `discard` | 다른 운영자가 먼저 저장했다. `meta.updatedBy`·`meta.updatedAt`을 보이고 다시 불러오게 한다. 재시도를 성공으로 보는 예외는 `save` 하나뿐이다. 응답을 받지 못한 `save`를 다시 보내 `STALE`이 왔고 보낸 내용의 정규 해시가 `meta.hash`와 같으며 시나리오면 보낸 `mapKey`도 `meta.mapKey`와 같을 때다(`mapKey`는 내용 해시 밖의 열이다). `publish`·`discard`의 `STALE`은 늘 실패다. 실제로 게시하거나 버리지 않았기 때문이다. 응답을 받지 못한 `publish` 재시도는 위 2.4 규칙대로 서버가 같은 결과를 돌려준다 |
| `PUBLISHED` | `save`, `publish`, `discard` | 이미 게시된 판이다. 고치려면 복제한다 |
| `INVALID` | `publish` | `report.issues`를 보인다. 저장된 초안은 그대로다 |
| `DRAFT_EXISTS` | `clone` | `draftId`의 초안을 연다 |
| `NAME_TAKEN` | `clone` | 다른 이름을 고르게 한다 |

### 2.6 동시 편집과 잠금

- `save`는 한 문장 비교 갱신이다. `UPDATE ... SET content, hash, revision = revision + 1, updatedBy, updatedAt WHERE id = $id AND status = 'DRAFT' AND revision = $revision RETURNING *`. 0행이면 같은 트랜잭션에서 행을 다시 읽어 없으면 `NOT_FOUND`, 게시 판이면 `PUBLISHED`, 아니면 `STALE`이다. 두 운영자가 같은 revision으로 동시에 저장하면 PostgreSQL 행 잠금 때문에 하나만 1행을 갱신하고 다른 하나는 `STALE`을 받는다.
- `publish`와 `discard`는 `SELECT ... FOR UPDATE`로 행을 잠근 뒤 상태와 revision을 본다. `publish`는 시나리오면 `mapKey`의 지도 판을, 지도면 2.7의 시나리오들을 `FOR SHARE`로 읽는다.
- 게시는 모든 종류에서 직렬로 돈다. `publish`는 트랜잭션 첫 문장으로 고정 키 하나의 `pg_advisory_xact_lock`(자원 게시 잠금)을 잡고 그다음 게시할 초안 행, 참조 행 순서로 행을 잠근다. 참조 행은 `(kind, name, version)` 오름차순으로 잠근다. 자기 초안부터 잠그는 순서만으로는 지도 초안 게시(지도 → 시나리오)와 그 지도 초안을 가리키는 시나리오 초안 게시(시나리오 → 지도)가 서로 기다려 교착할 수 있다. 게시 잠금이 둘을 한 줄로 세운다. `save`와 `discard`는 자기 행 하나만 잠그고 다른 행을 기다리지 않으므로 이 순환에 끼지 않는다. 그래서 게시 잠금을 잡지 않는다.
- 초안 참조: 시나리오 초안의 `mapKey`가 지도 초안 키를 가리킬 수 있다(`save`가 막지 않는다). 그 시나리오의 게시는 2.7대로 `scenario-map-unpublished`로 막힌다. 지도 초안과 그 시나리오 초안을 함께 게시하려면 지도를 먼저 게시한다. 두 게시가 동시에 들어오면 게시 잠금을 먼저 잡은 쪽이 끝난 뒤 다른 쪽이 돈다. 지도가 먼저면 시나리오는 게시된 지도로 검사한다. 시나리오가 먼저면 `INVALID`(`scenario-map-unpublished`)다.
- 지도 게시와 그 지도를 가리키는 시나리오 초안의 저장이 겹치면 늦은 쪽이 기다렸다가 진행한다. 저장이 먼저 끝나면 게시는 저장된 시나리오로 검사한다. 게시가 먼저 끝나면 저장은 게시 뒤에 들어간다.
- `clone`은 `pg_advisory_xact_lock(hashtext(kind || ':' || name))`으로 그 이름을 잠근 뒤 초안 유무와 가장 큰 판 번호를 읽고 넣는다. 잠금을 빠뜨려도 2.2의 부분 유일 색인과 `(kind, name, version)` 유일 제약이 두 번째 넣기를 막는다. 그 경우 유일 위반을 잡아 `DRAFT_EXISTS`로 바꾼다.
- 저장과 게시가 같은 초안에서 겹치면 먼저 행을 잡은 쪽이 이긴다. 게시가 먼저면 늦은 저장은 `PUBLISHED`, 저장이 먼저면 게시는 `STALE`이다. 저장되지 않은 내용이 게시되는 일은 없다.
- 트랜잭션 격리 수준은 기본 `READ COMMITTED`다. 위 비교 갱신과 행 잠금으로 충분하다.

### 2.7 검증 호출

검사는 T4-76이 `@opensamguk/rules/resources`에 둔 종류별 순수 함수다(C-M3·C-M3a). 서버는 DB에서 필요한 판을 읽어 넘기고 결과를 그대로 돌려준다(R11). 같은 함수를 편집 화면도 부른다.

| 종류 | 부르는 함수와 넘기는 것 | 서버가 더하는 결과 |
| ---- | ----------------------- | ------------------ |
| `MAP` | `validateMap(content, { expectedId: name, scenarios })`. `scenarios`는 아래 | 없음 |
| `SCENARIO` | `validateScenario(content, { map, mapKey, expectedId: name })`. `map`은 `mapKey` 판의 내용 | `mapKey`가 없거나(미지정) 그 키의 판이 카탈로그에 없으면 `scenario-map-missing`, 그 판이 초안이면 `scenario-map-unpublished`. 둘 다 오류이고 T4-76 `ResourceIssueCode`에 들어간다(R11). 이때는 `validateScenario`를 부르지 않는다 |
| `UNIT_SET` | `validateUnitSet(content, { expectedId: name })` | 없음 |
| `STAT_RULES`, `PORTRAIT_MAP` | `validateStatRules(content)`, `validatePortraitMap(content)` | 없음 |

지도 게시 때 시나리오 참조 검사(C-M3 셋째 항목)는 설계대로 서버가 한다(R12). 넘기는 시나리오는 두 묶음이다.

| 묶음 | 고르는 행 | 결과의 심각도 |
| ---- | --------- | ------------- |
| 함께 쓸 시나리오 | `mapKey`가 이 지도 판의 정규형 키와 같은 시나리오 행 전부(초안과 게시). 지도 초안의 키를 가리키는 것은 시나리오 초안뿐이다. 시나리오 게시는 게시 지도만 받아서다 | T4-76 결과 그대로 (오류면 게시를 막는다) |
| 원본 지도의 시나리오 | `mapKey`가 이 초안의 `baseKey`와 같은 게시 시나리오 전부 | 서버가 `warning`으로 낮춘다. 게시를 막지 않는다 |

- 두 번째 묶음을 경고로 두는 까닭: 옛 시나리오 판은 바뀌지 않고 계속 옛 지도 판을 가리킨다. 그것을 오류로 두면 도시를 지운 지도 판을 영영 게시할 수 없다. 경고로 보여 주면 운영자는 새 지도에 맞춰 어느 시나리오를 복제해 고쳐야 하는지 미리 안다(T4-81 Q-81-3).
- 두 묶음 모두 결과 항목에는 T4-76이 다는 `resource: { kind: 'SCENARIO', key }`가 있다. 같은 시나리오가 두 묶음에 다 들면 첫 묶음으로만 넘긴다.
- 시나리오가 쓰는 병종(C-M3a 병종 항목)은 지금 시나리오 형식에 병종 참조가 없어 T4-76의 `unitset-default-missing`이 그 몫 전부다. 병종 게시 때 이미 걸리므로 서버가 따로 보지 않는다.
- 서버가 더하는 두 코드의 문구는 rules `resourceIssue`가 `params`로 고른다. `scenario-map-missing`은 미지정(`params`에 `mapKey`를 넣지 않음)이면 `함께 쓸 지도를 정하지 않았습니다.`, 없는 판이면 `함께 쓸 지도 <키>를 찾지 못했습니다.`이다. `scenario-map-unpublished`는 `함께 쓸 지도 <키>가 게시되지 않았습니다.`이다. 대상은 `{ kind: 'root' }`, `params`는 키가 있으면 `{ mapKey }`, 미지정이면 `{}`다. T4-76 `params` 타입(`string | number`)에 `null`을 넣지 않는다. 세 경우의 코드는 T4-76 3.4와 같다.

### 2.8 감사 로그

T3-05 `AuditLog`(가정, R19)에 변경과 같은 트랜잭션으로 한 행씩 쓴다. 감사 행 쓰기가 실패하면 변경도 롤백되고 `INTERNAL_SERVER_ERROR`다(T3-05 감사 로그 절).

| `action` | 언제 | `reason` | `payload` |
| -------- | ---- | -------- | --------- |
| `resource.draft.create` | `clone` 성공 | 없음 | `{ kind, name, version, sourceId, baseKey, hash, mapKey, upgradedToV2 }` |
| `resource.draft.save` | `save` 성공 | 없음 | `{ kind, name, version, revisionFrom, revisionTo, hashFrom, hashTo, mapKeyFrom, mapKeyTo, errorCount, warningCount }` |
| `resource.draft.discard` | `discard` 성공 | 입력의 `reason` | `{ kind, name, version, revision, hash }` |
| `resource.publish` | `publish`가 상태를 바꿈 | 입력의 `reason` | `{ kind, name, version, key, revision, hash, mapKey, warningCount }` |

- API로 부른 행은 `actorKind = ADMIN`, `actorUserId` = 세션 사용자다. 명령줄 도구가 부른 행은 2.9를 따른다. 모든 행이 `targetType = GAME_RESOURCE`, `targetId` = 행 `id`, `worldId = null`이다.
- 내용 전체는 넣지 않는다. 해시만 넣는다. 게시 판은 내용이 DB에 영구히 남고 해시로 대조된다. 초안 중간 내용은 남지 않는다(7절 U-T78-2).
- 거부된 요청(권한, 입력, `STALE`, `PUBLISHED`, `INVALID`, `DRAFT_EXISTS`, `NAME_TAKEN`)과 게시 재시도의 성공 응답은 바뀐 것이 없으므로 감사 행을 쓰지 않는다. 그래서 권한 대조의 DB 불변 비교와 맞는다.
- `action` 값 네 개는 T3-05의 `action` 목록(감사 로그 절)에 더한다. T3-05의 감사 조회 필터 `action` 앞부분으로 `resource.`를 주면 이 네 가지가 나온다.
- 초기화 SQL이 넣는 내장 판의 감사 기록은 T4-77 몫이다(6절 Q-05).

### 2.9 명령줄 도구가 쓰는 저장소 함수

초상 대응표의 2판부터는 생성기가 SQL을 직접 넣지 않고 이 작업의 저장소 함수를 거쳐 감사를 남긴다(R15).

```ts
type Actor = { kind: 'ADMIN'; userId: string } | { kind: 'CLI' };
cloneResource(db, actor, { sourceId, name? }): Promise<CloneResult>;
saveDraft(db, actor, { id, revision, content, mapKey? }): Promise<SaveResult>;
publishDraft(db, actor, { id, revision, reason }): Promise<PublishResult>;
discardDraft(db, actor, { id, revision, reason? }): Promise<DiscardResult>;
```

- 결과 모양은 2.4의 절차 결과와 같다. 라우터는 세션에서 `{ kind: 'ADMIN', userId }`를 만들어 넘기고 결과를 그대로 돌려준다.
- `CLI` 행위자의 감사 행은 `actorKind = CLI`, `actorUserId = null`이다. 카탈로그 행의 `createdBy`·`updatedBy`·`publishedBy`도 `null`이고 화면 `label`은 `명령줄`이다.
- 생성기(`tools/portrait-map/generate.ts`)를 이 함수에 잇는 것은 생성기를 고치는 작업(T4-77)의 몫이다. 이 작업은 `CLI` 행위자로 복제 → 저장 → 게시하는 통합 시험 하나를 둔다(4.1).

## 3. 접근

1. T4-77 병합본의 `GameResource`를 읽고 2.2 표의 T4-77 몫이 있는지 확인한다. 이 작업의 새 migration으로 `baseKey` 열과 초안 하나 부분 유일 색인을 더한다(R20). 색인은 Prisma가 만들지 못해 migration SQL에 손으로 적는다.
2. `admin/resourceStore.ts`에 키 해석(정규형), 복제(v1 지도 올리기, 내용 `id` 바꾸기), 비교 갱신 저장, 잠금 게시와 검증 호출, 폐기, 감사 행 쓰기를 2.9의 함수로 둔다. 정규 해시는 T4-77의 함수를 쓴다.
3. `routers/resourceAdmin.ts`에 `adminProcedure` 위로 여섯 절차를 둔다. 입력 파싱과 결과 변환만 하고 DB 작업은 2의 함수를 부른다.
4. `router.ts`에 한 줄 등록하고 `tools/authz.integration.test.ts`에 경로와 표를 더한다.
5. 4.1의 통합 시험을 실제 HTTP 소켓과 PostgreSQL로 쓴다.
6. 채울 문서를 쓴다. 그 뒤 `pnpm check`, `pnpm test:int`, `pnpm test:authz`를 돌린다.
