# T2-11 D2 국가 작전판: 데이터·API

> 대기열: T2-11 · AC: AC-M2-15 (API) · 구현: Codex · 리뷰: Claude
> 선행: T2-09, T2-13(활동 기록과 미접속 판정) · 관련: [차별화 D2](../product/differentiation.md#d2-국가-작전판), FR-DIF-02

## 계획 (Claude)

### 목표

수뇌가 작전(목표 도시, 목표 연월, 참여 장수)을 만들면 참여 장수들의 턴 시각과 예턴을 한 타임라인으로 계산해 주고
목표 전에 출병이 실행되지 않거나 준비가 모자란 장수를 표시한다. 작전 참여 시 제안 예턴을 만든다. 관직자는 국가원 전원의
예턴·훈련·사기 표(감찰)를 본다. 다른 국가는 볼 수 없다 (AC-M2-15).

### 범위

- `Operation`, `OperationMember` 테이블
- `packages/rules/src/operation/`: 타임라인 계산, 판정, 제안 예턴 생성 (순수 함수)
- `apps/server/src/routers/operation.ts`, `inspection.ts`(감찰)

### 하지 않는 것

작전대로 예턴을 강제로 바꾸기(제안만, 장수가 확인해야 반영), 상관 지시로 남의 예턴 덮어쓰기(Phase 2).

### 타임라인 계산 결정

계산은 모두 tick으로 한다 (검토 R62-4, 2026-10-21 보강). ISO 시각은 화면 표시값일 뿐 판정에 쓰지 않는다.

- 칸 i의 실행 tick은 `nextTurnTick + i × 10,000`이다(`docs/architecture/game-clock.md:35-36`). 월드가 정지·시작 전·종료여도 tick 계산은 같다.
- 칸의 게임 연월은 `toGameDate(startYear, tick)`이다(`packages/rules/src/clock/clock.ts:66-71`). 열 머리와 맞춘다.
- 목표 tick(사용자 결정 U62-4a, 2026-10-23 승인): 목표 연월의 첫 tick, 곧 `toGameDate`가 목표 연월을 돌려주는 가장 작은 tick이다.
  출병 칸의 실행 tick이 목표 tick보다 작으면 제때다. 같은 tick은 늦음이다. 목표 연월의 첫 tick에는 월간 정산이 먼저 돈다(`game-clock.md:56`).
- ISO 표시: `targetAt`·`cells[].at`·`nextTurnAt`은 기존 `nextTurnAt(world, tick)`(`apps/server/src/queries.ts:64-69`)으로 만든다.
  월드가 RUNNING이 아니거나 기준 시각이 없으면 null이다. 화면은 null이면 시각 대신 게임 연월만 보여 준다. 재개하면 다시 계산된다.

```text
참여 장수마다:
  cells = 지금 예턴 30칸 각각의 { slot, tick, date, turn }
  sortie = 목표 도시로 가는 첫 출병 칸 (없으면 null)
  판정:
    READY    sortie.tick < 목표 tick이고 sortie 시점 예상 병력·훈련·사기가 기준 이상
    WEAK     sortie.tick < 목표 tick이지만 예상값이 기준 미달
    LATE     sortie.tick ≥ 목표 tick
    MISSING  30칸 안에 목표 도시 출병이 없음 (예턴이 모두 휴식인 경우 포함)
  beyondWindow = 30칸 마지막 칸의 tick < 목표 tick (아직 예턴으로 목표까지 채울 수 없음)
```

- 예상 병력·훈련·사기는 예턴의 모병·훈련·사기진작을 규칙의 기대값으로 더해 추정한다(난수 없음). 화면에는 예상이라고 표시한다.
- READY는 예턴만 본 예상이다. 금·쌀, 병종, 경로, 교전 상태는 실행 때 판정하므로 실제 실행을 보장한다고 표시하지 않는다.
- 출병이 목표 다음 달보다 늦으면 `months` 열 머리 밖이다. 화면은 마지막 열 뒤에 그 칸의 연월을 붙여 LATE로 보여 준다(T2-12). `cells`는 늘 30칸이다.
- 기준(최소 병력·훈련·사기)은 작전을 만들 때 정한다.
- 제안 예턴: 남은 칸 안에서 모병 → 훈련 → 사기진작 → 출병(목표 tick 전 마지막 칸)을 맞춘 30칸 사본이다. 실제 명령 인자를 쓴다.
  모병 `{ amount, crewType }`(`packages/rules/src/commands/military.ts:10`), 훈련·사기진작 `{}`, 출병 `{ cityKey }`(정수, `attack.ts:59`).
  `crewType`은 장수의 지금 병종, `amount`는 기준 병력까지 모자란 수다. 배치에 쓰지 않는 칸은 지금 값 그대로 둔다.
  제안한 칸마다 지금 상태로 사전 검사를 돌려 실패하면 `warnings`에 칸 번호와 이유를 넣는다. 저장은 장수가 확인한 뒤 `turns.set`으로만 한다.
- 제안은 장수 상태, 30칸, `turnRevision`을 한 RepeatableRead 트랜잭션에서 읽는다(`apps/server/src/routers/turns.ts:82-90`과 같은 방식).
- 공개 범위: 작전과 감찰은 같은 국가에게만. 작전 목록은 직책자 전체, 작전 상세는 참여 장수와 직책자.

### API 계약

아래 타입 하나가 계약 초안이다 (검토 R62-1, 2026-10-21 정리). 예전 요약은 지웠다. `operation`·`inspection` 라우터는 아직 `AppRouter`에 없다
(`apps/server/src/router.ts:14-24`). 최종 서버 타입은 backend(Codex)가 `AppRouter`로 정하고 화면은 그 타입만 import한다.
도시 키는 기존 계약과 같은 정수다(`schema.prisma:84-127`, `apps/server/src/queries.ts:7`). 화면 요소와의 대조는 [T2-12 v1 근거](./T2-12.md#v1-근거)에 있다.

```ts
type GameDate = { year: number; month: number };
type NationRef = { id: number; name: string; color: string };
type Allowed = { ok: true } | { ok: false; code: string; reason: string }; // T2-07과 같은 모양. 화면은 code로 분기한다
// 지금의 turns.get 칸과 같다. readSlots가 빈 칸을 휴식으로 채우므로 null이 없다(apps/server/src/game/slots.ts:15-24)
type SlotView = { commandKey: string; args: unknown; name: string };
// turns.set 입력 칸. strictObject라 name을 넣으면 거부된다(slots.ts:5-6)
type SlotInput = { commandKey: string; args?: unknown } | null;
type Verdict = 'READY' | 'LATE' | 'WEAK' | 'MISSING'; // 준비됨·늦음·미흡·없음
type Readiness = { crew: number; train: number; atmos: number };

type OperationRow = {
  id: string;
  target: { cityKey: number; cityName: string; nation: NationRef | null }; // 공백지면 null. 지도에 공개된 소유만 쓴다
  targetDate: GameDate;
  targetTick: number; // 판정 기준
  targetAt: string | null; // 표시용. RUNNING이 아니면 null
  status: 'OPEN' | 'CLOSED';
  createdBy: { generalId: number; name: string };
  members: number;
  ready: number; // verdict가 READY인 참여 장수 수
  joined: boolean; // 내 장수가 참여 장수인지
};
type TimelineCell = {
  slot: number; // 예턴 칸 번호 0~29
  tick: number;
  at: string | null; // 표시용 실행 시각
  date: GameDate; // 실행되는 게임 연월. 열 머리와 맞춘다
  turn: SlotView;
};
type MemberTimeline = {
  generalId: number;
  name: string;
  cityKey: number;
  cityName: string;
  isMe: boolean;
  verdict: Verdict;
  beyondWindow: boolean; // 30칸 마지막 칸이 목표 tick보다 앞
  sortie: TimelineCell | null; // 목표 도시로 가는 첫 출병 칸
  expected: Readiness; // sortie 시점의 예상값. sortie가 없으면 마지막 칸 기준. 기대값이라 난수가 없다
  cells: TimelineCell[]; // 지금 30칸 전부. 화면이 목표 전 6개월만 먼저 보여 준다
};
type OperationDetail = Omit<OperationRow, 'joined'> & {
  min: Readiness; // 만들 때 정한 기준
  months: GameDate[]; // 열 머리. 이번 달부터 targetDate 다음 달까지
  timeline: MemberTimeline[]; // nextTurnTick 순, 같으면 장수 ID 순
  canSuggest: Allowed; // 참여 장수이고 OPEN일 때만 ok
  canClose: Allowed; // 만든 장수 또는 군주이고 OPEN일 때만 ok
};
type InspectionRow = {
  generalId: number;
  name: string;
  officerLevel: number;
  cityKey: number;
  cityName: string;
  isHuman: boolean;
  crew: number;
  train: number;
  atmos: number;
  turns: SlotView[]; // 앞 5칸
  nextTurnAt: string | null; // 표시용. RUNNING이 아니면 null
  lastActiveAt: string | null; // 표시용. NPC나 활동 기록이 없으면 null
  idle: boolean; // T2-13의 미접속 판정 함수를 지금 tick으로 부른 값. NPC는 false
};

// operation.create({ worldId, targetCityKey: number, targetYear, targetMonth, min: Readiness, memberIds: number[] }) → { id: string }
//   직책자만. 참여 장수는 우리 국가 장수만. 행위 장수는 세션에서 정한다.
// operation.list({ worldId }) → { canCreate: Allowed; items: OperationRow[] }
//   OPEN 먼저, 그 안에서 targetTick 이른 순, 같으면 id 순.
// operation.get({ worldId, id }) → OperationDetail
// operation.suggest({ worldId, id }) → { revision: number; current: SlotView[]; slots: SlotView[]; changed: number[]; warnings: { slot: number; reason: string }[] }
//   current는 turns.get과 같은 30칸, slots는 제안 30칸이다. 둘 다 같은 트랜잭션에서 읽은 revision 기준이다.
//   changed는 commandKey가 다르거나 args가 다른(키 순서 무시) 칸 번호 오름차순이다.
//   저장하지 않는다. 화면은 changed 칸만 메인 30칸 편집기의 초안에 넣고 그 편집기의 저장 경로로 저장한다(아래 예턴 칸 왕복).
// operation.close({ worldId, id }) → OperationRow
// inspection.members({ worldId }) → { items: InspectionRow[] }
//   직책자만. officerLevel 높은 순, 같으면 장수 ID 순.
```

### 예턴 칸 왕복 (검토 R62-2, 2026-10-21 정리)

- 읽기 칸과 입력 칸은 다르다. `turns.get`은 빈 칸도 이름이 붙은 휴식으로 돌려주고(`slots.ts:15-24`, `packages/rules/src/replay.ts:27`),
  `turns.set`은 `{ commandKey, args }` 또는 null만 받는다(`slots.ts:5-13`, `turns.ts:92-96`). `name`을 넣은 칸은 거부된다.
- 이 변환은 작전판이 새로 만들지 않는다. 지금 메인 편집기에 이미 있다. 읽은 칸은 `toTurn`이 `name`을 버리고(`apps/web/src/turns/draft.ts:22-26`, `useTurnDraft.ts:119`),
  저장할 때 `toSaveSlots`가 휴식을 null로 바꿔 보낸다(`draft.ts:55-58`, `useTurnDraft.ts:178-182`). 30칸, `worldId`, 초안의 `baseRevision`이 그대로 간다.
  이전 계획의 `toSlotInput`은 지웠다. 작전판이 별도 변환을 두면 메인 저장 경로와 갈라지기 때문이다.
- 이 계획은 null 저장의 뜻을 바꾸지 않는다. 지금 M1 계약에서 직접 넣은 휴식과 빈 칸은 같은 값이다(`slots.ts:6-13`). 그 구분은 T2-13의 별도 계약이다.
- 충돌: revision이 어긋나면 `turns.set`은 예외가 아니라 `{ ok: false, reason: 'STALE', revision, slots }`를 돌려준다(`turns.ts:45-48`).
  메인 편집기는 그때 내 편집 목록을 보관하고(`useTurnDraft.ts:162-164`) 최신 30칸에 같은 순서로 다시 적용할지 묻는다(`useTurnDraft.ts:141-151`).
  화면은 최신 30칸으로 다시 제안을 받아 비교를 보여 주되 사용자가 고치던 초안은 버리지 않는다.

#### 직접 휴식 구분이 생길 때의 인계 (검토 R62-2R, 2026-10-22)

T2-13(PR #63)은 빈 칸과 직접 넣은 휴식을 나누는 `explicit`을 제안했다. 그 전환은 서버 칸 모양만 바꿔서는 끝나지 않는다. 지금 메인 편집기의 어댑터가 그 구분을 버리기 때문이다.

| 지금 경로 | 지금 동작 | 전환 때 함께 바꿀 것 |
| --------- | --------- | ------------------- |
| `toTurn` (`draft.ts:22-26`) | `commandKey`·`args`만 남긴다 | 칸 구분을 싣는다 |
| `REST`·`applyOp`의 `put`·`shift`·`repeat` 채움 값 (`draft.ts:19-20,40-49`) | 채우는 칸이 모두 같은 휴식이다 | 서버 `turns.edit`과 같은 채움 규칙 |
| `toSaveSlots` (`draft.ts:55-58`) | 휴식이면 직접 넣은 것도 null로 보낸다 | 직접 휴식은 객체, 빈 칸만 null |
| `sameTurns`·`turnKey` (`draft.ts:60-70`) | 구분 없이 비교한다 | 구분까지 비교 |
| sessionStorage 초안 (`useTurnDraft.ts:33-89`, 키 `opensamguk.turnDraft.v1`) | `isTurn`이 `commandKey`·`args`만 본다 | 저장 형식 번호를 올리고 옛 초안의 뜻은 추정하지 않는다 |
| STALE 다시 적용 (`useTurnDraft.ts:141-151`) | 보관한 편집을 최신 칸에 다시 적용 | 다시 적용한 칸도 구분을 지킨다 |

- 서버 쪽 형식, migration, 재생은 T2-13(Codex) 한 사람이 소유한다. 위 화면 어댑터는 그 화면 짝인 T2-14(Claude)가 같은 전환에서 함께 고친다. T2-11·T2-12는 어느 쪽도 따로 정의하지 않는다.
  `toSlotInput` 같은 새 변환만 더하고 `submit`이 계속 `toSaveSlots`를 부르면 직접 휴식이 사라진다.
- 인계 조건: T2-11 구현은 T2-13의 형식별 재생과 옛 휴식 처리 결정(PR #63 R63-6R·U63-3)이 닫히고 리뷰를 통과한 정확한 커밋 위에서 시작한다. 그 SHA를 구현 기록에 적는다.
  T2-12는 그 시점의 메인 편집기 어댑터를 그대로 쓴다. 남아 있는 M1 초안에 든 휴식이 직접 넣은 것인지는 추정하지 않는다.

### 미접속 정보의 소유 (검토 R62-5, 2026-10-21 정리)

- `General.lastActiveAt`·판정용 활동 tick, 그 갱신 지점(로그인·예턴 저장·방침 바꾸기), 14일 판정 함수는 T2-13(Codex) 하나가 소유한다.
  T2-11은 읽기만 한다. 먼저 구현하는 쪽이 만든다는 조건은 지웠다.
- 그래서 T2-11의 선행은 T2-09와 T2-13이다(`docs/product/phases.md`). 인계 조건은 T2-13 리뷰가 통과한 커밋에 위 필드와 판정 함수가 있는 것이다.
- 14일 경계, null, NPC, 시험용 시각 주입, 로그인 때 갱신할 월드 범위는 [T2-13](./T2-13.md) 계약을 그대로 쓴다. 활동값의 결정성과 경계는 PR #63의 R63-7 잔여라 여기서 따로 정하지 않는다.
- 직렬 통합 (검토 R62-5R, 2026-10-22): PR #63도 `docs/product/phases.md`를 고친다. 그쪽 표의 T2-11 칸은 아직 `T2-09`뿐이다.
