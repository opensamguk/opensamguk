# T2-11 D2 국가 작전판: 데이터·API

> 대기열: T2-11 · AC: AC-M2-15 (API) · 구현: Codex · 리뷰: Claude
> 선행: T2-09, T2-13(활동 기록과 미접속 판정) · 관련: [차별화 D2](../product/differentiation.md#d2-국가-작전판), FR-DIF-02

## 계획 (Claude)

### 목표

수뇌가 작전(목표 도시, 목표 연월, 참여 장수)을 만들면 참여 장수들의 턴 시각과 예턴을 한 타임라인으로 계산해 주고
목표 전에 출병이 실행되지 않거나 준비가 모자란 장수를 표시한다. 작전 참여 시 제안 예턴을 만든다. 관직자는 국가원 전원의
예턴·훈련·사기 표(감찰)를 본다. 다른 국가는 볼 수 없다 (AC-M2-15).

### 범위

- `Operation`, `OperationMember` 테이블
- `packages/rules/src/operation/`: 타임라인 계산, 판정, 제안 예턴 생성 (순수 함수)
- `apps/server/src/routers/operation.ts`, `inspection.ts`(감찰)

### 하지 않는 것

작전대로 예턴을 강제로 바꾸기(제안만, 장수가 확인해야 반영), 상관 지시로 남의 예턴 덮어쓰기(Phase 2).

### 타임라인 계산 결정

계산은 모두 tick으로 한다 (검토 R62-4, 2026-10-21 보강). ISO 시각은 화면 표시값일 뿐 판정에 쓰지 않는다.

- 칸 i의 실행 tick은 `nextTurnTick + i × 10,000`이다(`docs/architecture/game-clock.md:35-36`). 월드가 정지·시작 전·종료여도 tick 계산은 같다.
- 칸의 게임 연월은 `toGameDate(startYear, tick)`이다(`packages/rules/src/clock/clock.ts:66-71`). 열 머리와 맞춘다.
- 목표 tick(사용자 결정 U62-4a, 2026-10-23 승인): 목표 연월의 첫 tick, 곧 `toGameDate`가 목표 연월을 돌려주는 가장 작은 tick이다.
  출병 칸의 실행 tick이 목표 tick보다 작으면 제때다. 같은 tick은 늦음이다. 목표 연월의 첫 tick에는 월간 정산이 먼저 돈다(`game-clock.md:56`).
- ISO 표시: `targetAt`·`cells[].at`·`nextTurnAt`은 기존 `nextTurnAt(world, tick)`(`apps/server/src/queries.ts:84-89`)으로 만든다.
  월드가 RUNNING이 아니거나 가속 모드이거나 기준 시각이 없으면 null이다. 화면은 null이면 시각 대신 게임 연월만 보여 준다. 재개하면 다시 계산된다.

```text
참여 장수마다:
  cells = 지금 예턴 30칸 각각의 { slot, tick, date, turn }
  sortie = 목표 도시로 가는 첫 출병 칸 (없으면 null)
  판정:
    READY    sortie.tick < 목표 tick이고 sortie 시점 예상 병력·훈련·사기가 기준 이상
    WEAK     sortie.tick < 목표 tick이지만 예상값이 기준 미달
    LATE     sortie.tick ≥ 목표 tick
    MISSING  30칸 안에 목표 도시 출병이 없음 (예턴이 모두 휴식인 경우 포함)
  beyondWindow = 30칸 마지막 칸의 tick < 목표 tick (아직 예턴으로 목표까지 채울 수 없음)
```

- 예상 병력·훈련·사기는 예턴의 모병·훈련·사기진작을 규칙의 기대값으로 더해 추정한다(난수 없음). 화면에는 예상이라고 표시한다.
- READY는 예턴만 본 예상이다. 금·쌀, 병종, 경로, 교전 상태는 실행 때 판정하므로 실제 실행을 보장한다고 표시하지 않는다.
- 출병이 `months` 마지막 달보다 늦으면 열 머리 밖이다. 화면은 마지막 열 뒤에 그 칸의 연월을 붙여 LATE로 보여 준다(T2-12). `cells`는 늘 30칸이다.
- 기준(최소 병력·훈련·사기)은 작전을 만들 때 정한다.
- 제안 예턴: 남은 칸 안에서 모병 → 훈련 → 사기진작 → 출병(목표 tick 전 마지막 칸)을 맞춘 30칸 사본이다. 실제 명령 인자를 쓴다.
  모병 `{ amount, crewType }`(`packages/rules/src/commands/military.ts:10`), 훈련·사기진작 `{}`, 출병 `{ cityKey }`(정수, `attack.ts:59`).
  `crewType`은 장수의 지금 병종, `amount`는 기준 병력까지 모자란 수다. 배치에 쓰지 않는 칸은 지금 값 그대로 둔다.
  제안한 칸마다 지금 상태로 사전 검사를 돌려 실패하면 `warnings`에 칸 번호와 이유를 넣는다. 저장은 장수가 확인한 뒤 `turns.set`으로만 한다.
- 제안은 장수 상태, 30칸, `turnRevision`을 한 RepeatableRead 트랜잭션에서 읽는다(`apps/server/src/routers/turns.ts:82-90`과 같은 방식).
- 공개 범위: 작전과 감찰은 같은 국가에게만. 작전 목록은 직책자 전체, 작전 상세는 참여 장수와 직책자.

### API 계약

아래 타입 하나가 계약 초안이다 (검토 R62-1, 2026-10-21 정리). 예전 요약은 지웠다. `operation`·`inspection` 라우터는 아직 `AppRouter`에 없다
(`apps/server/src/router.ts:18-32`). 최종 서버 타입은 backend(Codex)가 `AppRouter`로 정하고 화면은 그 타입만 import한다.
도시 키는 기존 계약과 같은 정수다(`schema.prisma:84-127`, `apps/server/src/queries.ts:7`). 화면 요소와의 대조는 [T2-12 v1 근거](./T2-12.md#v1-근거)에 있다.

```ts
type GameDate = { year: number; month: number };
type NationRef = { id: number; name: string; color: string };
type Allowed = { ok: true } | { ok: false; code: string; reason: string }; // T2-07과 같은 모양. 화면은 code로 분기한다
// c60c328의 turns.get 칸과 같다. displaySlots가 이름을 붙이고 explicit을 싣는다(apps/server/src/game/slots.ts:22-28).
// readSlots는 30칸 모두 객체로 주고 행이 없는 칸은 explicit false 휴식이다(slots.ts:29-45). null이 없다
type SlotView = { commandKey: string; args: unknown; name: string; explicit: boolean };
// turns.set 입력 칸. strictObject라 name을 넣으면 거부된다(slots.ts:12-13). null은 빈칸, 객체는 직접 칸이다(slots.ts:14-21)
type SlotInput = { commandKey: string; args?: unknown } | null;
type Verdict = 'READY' | 'LATE' | 'WEAK' | 'MISSING'; // 준비됨·늦음·미흡·없음
type Readiness = { crew: number; train: number; atmos: number };

type OperationRow = {
  id: string;
  target: { cityKey: number; cityName: string; nation: NationRef | null }; // 공백지면 null. 지도에 공개된 소유만 쓴다
  targetDate: GameDate;
  targetTick: number; // 판정 기준. safe integer. DB는 BigInt로 저장한다
  targetAt: string | null; // 표시용. RUNNING이 아니면 null
  status: 'OPEN' | 'CLOSED';
  createdBy: { generalId: number; name: string };
  members: number;
  ready: number; // verdict가 READY인 참여 장수 수
  joined: boolean; // 내 장수가 참여 장수인지
};
type TimelineCell = {
  slot: number; // 예턴 칸 번호 0~29
  tick: number;
  at: string | null; // 표시용 실행 시각
  date: GameDate; // 실행되는 게임 연월. 열 머리와 맞춘다
  turn: SlotView;
};
type MemberTimeline = {
  generalId: number;
  name: string;
  cityKey: number;
  cityName: string;
  isMe: boolean;
  verdict: Verdict;
  beyondWindow: boolean; // 30칸 마지막 칸이 목표 tick보다 앞
  sortie: TimelineCell | null; // 목표 도시로 가는 첫 출병 칸
  expected: Readiness; // sortie 시점의 예상값. sortie가 없으면 마지막 칸 기준. 기대값이라 난수가 없다
  cells: TimelineCell[]; // 지금 30칸 전부. 화면이 목표 전 6개월만 먼저 보여 준다
};
type OperationDetail = Omit<OperationRow, 'joined'> & {
  min: Readiness; // 만들 때 정한 기준
  months: GameDate[]; // 열 머리. 이번 달부터 targetDate 다음 달, 가장 늦은 cells[29] 달, 이번 달 + 30개월 중 이른 달까지. 최대 31개(아래 입력 경계 뒤 months 절)
  timeline: MemberTimeline[]; // nextTurnTick 순, 같으면 장수 ID 순
  canSuggest: Allowed; // 참여 장수이고 OPEN일 때만 ok
  canClose: Allowed; // 만든 장수 또는 군주이고 OPEN일 때만 ok
};
type InspectionRow = {
  generalId: number;
  name: string;
  officerLevel: number;
  cityKey: number;
  cityName: string;
  isHuman: boolean;
  crew: number;
  train: number;
  atmos: number;
  turns: SlotView[]; // 앞 5칸
  nextTurnAt: string | null; // 표시용. RUNNING이 아니면 null
  lastActiveAt: string | null; // 표시용. NPC나 활동 기록이 없으면 null

// operation.list({ worldId }) → { canCreate: Allowed; items: OperationRow[] }

// operation.get({ worldId, id }) → OperationDetail
// operation.suggest({ worldId, id }) → { revision: number; current: SlotView[]; slots: SlotView[]; changed: number[];

//   warnings: { slot: number; code: string; reason: string }[] }   // 아래 제안 사본 계약 (2026-10-23 정정)
//   current는 turns.get과 같은 30칸, slots는 제안 30칸이다. 둘 다 같은 트랜잭션에서 읽은 revision 기준이다.
//   changed는 T2-13 sameSlot이 false인 칸 번호 오름차순이다. 직접 칸끼리는 commandKey와 args(키 순서 무시)를 비교한다.
//   저장하지 않는다. 화면은 changed 칸만 메인 30칸 편집기의 초안에 넣고 그 편집기의 저장 경로로 저장한다(아래 예턴 칸 왕복).
// operation.close({ worldId, id }) → OperationRow
// inspection.members({ worldId }) → { items: InspectionRow[] }
//   직책자만. officerLevel 높은 순, 같으면 장수 ID 순.
```

### 예턴 칸 왕복 (검토 R62-2, 2026-10-21 정리)

- 읽기 칸과 입력 칸은 다르다. c60c328의 `turns.get`은 30칸 모두 이름과 `explicit`을 실은 객체로 돌려준다(`slots.ts:22-45`, `turns.ts:92-101`).
  `turns.set`은 `{ commandKey, args }` 또는 null만 받는다(`slots.ts:12-13`, `turns.ts:102-107`). null은 빈칸(`explicit: false`), 객체는 직접 칸(`explicit: true`)이다(`slots.ts:14-21`). `name`을 넣은 칸은 거부된다.
- 이 변환은 작전판이 새로 만들지 않는다. 메인 편집기에 이미 있다. 읽은 칸은 `toTurn`이 `name`을 버리고 `explicit`을 지키며(`apps/web/src/turns/draft.ts:27-29`, `useTurnDraft.ts:165`),
  저장할 때 `toSaveSlots`가 직접 칸은 객체로, 빈칸만 null로 보낸다(`draft.ts:61-62`, `useTurnDraft.ts:233`). 30칸, `worldId`, 초안의 `baseRevision`이 그대로 간다.
  이전 계획의 `toSlotInput`은 지웠다. 작전판이 별도 변환을 두면 메인 저장 경로와 갈라지기 때문이다.
- 역사 기록: d4f5b52 이전 M1 계약에서는 직접 넣은 휴식과 빈 칸이 같은 값이었다. 그 구분은 T2-13이 fe7b4f9에서 서버와 화면 어댑터에 넣었고 이 계획은 null 저장의 뜻을 바꾸지 않는다.
- 충돌: revision이 어긋나면 `turns.set`은 예외가 아니라 `{ ok: false, reason: 'STALE', revision, slots }`를 돌려준다(`turns.ts:45-48`).
  메인 편집기는 그때 내 편집 목록을 보관하고(`useTurnDraft.ts:162-164`) 최신 30칸에 같은 순서로 다시 적용할지 묻는다(`useTurnDraft.ts:141-151`).
  화면은 최신 30칸으로 다시 제안을 받아 비교를 보여 주되 사용자가 고치던 초안은 버리지 않는다.

#### 직접 휴식 구분이 생길 때의 인계 (검토 R62-2R, 2026-10-22)

T2-13(PR #63)은 빈 칸과 직접 넣은 휴식을 나누는 `explicit`을 제안했다. 그 전환은 서버 칸 모양만 바꿔서는 끝나지 않는다. 지금 메인 편집기의 어댑터가 그 구분을 버리기 때문이다.

| 지금 경로 | 지금 동작 | 전환 때 함께 바꿀 것 |
| --------- | --------- | ------------------- |
| `toTurn` (`draft.ts:22-26`) | `commandKey`·`args`만 남긴다 | 칸 구분을 싣는다 |
| `REST`·`applyOp`의 `put`·`shift`·`repeat` 채움 값 (`draft.ts:19-20,40-49`) | 채우는 칸이 모두 같은 휴식이다 | 서버 `turns.edit`과 같은 채움 규칙 |
| `toSaveSlots` (`draft.ts:55-58`) | 휴식이면 직접 넣은 것도 null로 보낸다 | 직접 휴식은 객체, 빈 칸만 null |
| `sameTurns`·`turnKey` (`draft.ts:60-70`) | 구분 없이 비교한다 | 구분까지 비교 |
| sessionStorage 초안 (`useTurnDraft.ts:33-89`, 키 `opensamguk.turnDraft.v1`) | `isTurn`이 `commandKey`·`args`만 본다 | 저장 형식 번호를 올리고 옛 초안의 뜻은 추정하지 않는다 |
| STALE 다시 적용 (`useTurnDraft.ts:141-151`) | 보관한 편집을 최신 칸에 다시 적용 | 다시 적용한 칸도 구분을 지킨다 |

위 표의 "지금 동작"과 줄 번호는 2026-10-22 기록이다. c60c328에서는 `toTurn`·`toSaveSlots`·`turnKey`가 구분을 싣는다(`draft.ts:27-29,61-62,71`). 이 계획은 화면 어댑터를 고치지 않는다.

- 서버 쪽 형식, migration, 재생은 T2-13(Codex) 한 사람이 소유한다. 위 화면 어댑터는 그 화면 짝인 T2-14(Claude)가 같은 전환에서 함께 고친다. T2-11·T2-12는 어느 쪽도 따로 정의하지 않는다.
  `toSlotInput` 같은 새 변환만 더하고 `submit`이 계속 `toSaveSlots`를 부르면 직접 휴식이 사라진다.
- 인계 조건: T2-11 구현은 T2-13의 형식별 재생과 옛 휴식 처리(U63-3, 2026-10-23 승인)가 구현되고 리뷰를 통과한 정확한 커밋 위에서 시작한다. 그 SHA를 구현 기록에 적는다.
  T2-12는 그 시점의 메인 편집기 어댑터를 그대로 쓴다. 남아 있는 M1 초안에 든 휴식이 직접 넣은 것인지는 추정하지 않는다.

| 이른 출병 | 블록을 정하기 전에 작업 사본에서 0~k−1의 목표 도시 출병을 모두 직접 휴식으로 바꾼다. k를 첫 출병으로 만들기 위해서다. 블록이 정해진 뒤 블록 밖에 남은 그 칸만 `warnings`에 `SORTIE_MOVED`로 적는다. k 뒤 출병은 그대로 둔다 |
| 블록 | p를 0부터 k까지 늘리며 s = k − p부터 k까지를 블록으로 잡는다. 블록 앞 0~s−1은 이른 출병을 정리한 같은 작업 사본이고 화면 예상과 같은 함수(0단계 식과 아래 표시용 방침 예상)로 s 직전 예상값을 낸다. 그 값에서 준비 칸 수 c를 센다. 모병은 예상 crew가 min.crew보다 작을 때 1칸이고 `{ amount: 그 차이, crewType: 지금 crewType }`다. 이 인자는 실제 `recruit` 명령의 args 스키마(`support.ts`의 양의 정수, amount 최대 1,000,000)를 그대로 다시 써서 검사한다. 통과하지 못하면(차액이 1,000,000 초과, crewType 0 등) 그 p는 쓸 수 없다. 여러 모병으로 나누지 않고 새 수치나 게임 한계를 더하지 않는다. 훈련·사기진작 칸 수는 희석 뒤 값에서 0단계 `prepare`를 되풀이해 min에 닿는 가장 작은 수다. 반복은 p ≤ k ≤ 29 안에서만 하고 센 준비 칸 수가 p를 넘으면 그 p의 계산을 멈추고 다음 p로 간다. 큰 음수 train 같은 DB 손상 값에서도 긴 반복이 없다. c ≤ p이고 모병 인자가 통과하는 첫 p를 쓴다. 준비 c칸은 k 직전 k−c~k−1에 모병·훈련·사기진작 순으로 놓고 남는 s~k−c−1은 직접 휴식으로 채운다. 직접 휴식은 예상값과 방침에 영향이 없어 준비 칸 시작의 예상값이 s 직전과 같다. p = k까지 쓸 p가 없으면, 어느 p에서든 모병 인자가 실제 스키마를 통과하지 못했으면 `UNREACHABLE`, 아니면 `NO_ROOM`이다. 블록 밖 칸은 `explicit`까지 그대로 복사한다 |
| 대조 | 만든 사본을 화면 예상과 같은 함수에 넣어 sortie가 k이고 READY인지 확인한다. 아니면 구현 결함이다 |
| warnings | 사본에서 바꾼 준비·출병 칸마다(채운 직접 휴식은 빼고) 그 명령의 `check`를 지금 상태로 돌려 실패를 `{ slot, code, reason }`으로 싣는다. 앞 제안 칸의 효과는 반영하지 않는다. 그래서 모병 뒤 훈련의 NO_CREW, 희석 뒤 훈련의 AT_MAX처럼 조건부 경고가 나올 수 있고 금 합계는 보지 않는다. 화면은 이것을 지금 상태 기준 검사라고 표시한다 |
| changed | `!sameSlot(current[i], slots[i])`인 i 오름차순. 사본에서 넣은 칸은 모두 직접 칸이다 |

빈칸 방침 예상은 저장값과 표시를 나눈다. 저장값은 바꾸지 않는다. 사본의 빈칸은 `explicit: false`로 남고 방침이 고를 명령을 칸에 쓰지 않는다. 표시용 예상은 방침 모드 월드의 사람 장수만 `choosePolicyCommand(view, generalId, defaultPolicy)`를 다시 쓴다. 칸을 차례로 보며 그때까지의 예상 crew·train·atmos를 넣은 상태 사본으로 명령 키를 고르고 그 키를 0단계 `prepare`로 더한다. `none`은 휴식이다. `runPolicyCommand`의 실제 `check` 실패와 휴식 대체는 실행 때 판정이다. 직접 명령의 자원 검사를 빼듯 예상에 넣지 않는다. 방침은 출병을 고르지 않으므로 sortie 판정은 그대로다. 이 연결(`explicit`, `sameSlot`, `defaultPolicy`, 방침 모드, 루트 export)은 T2-13 리뷰 통과 커밋이 선행이다.

##### 트랜잭션과 지금 tick

- 읽기(`list`·`get`·`suggest`·`members`)는 `readWorld(ctx.db, worldId, …)`의 RepeatableRead 하나에서 한다(`queries.ts:31-44`). 같은 트랜잭션 안에서 새 helper가 전용 select `{ policyFromSequence, actionSequence, unitSet }`로 World를 다시 읽고 `readView(tx)`로 규칙 view를, 전용 select로 General의 `defaultPolicy`·`lastActiveTick`·`lastActiveAt`을, 장수마다 `readSlots`를 읽는다. `queries.ts`·`game/queries.ts`는 고치지 않는다. `requireWorld`의 전체 행은 `result`가 없어 `nextTurnAt`에 넘기지 않는다.
- 지금 tick은 요청마다 하나다. `worldSummary`와 같은 `nowTick({ ...world, clockAnchorAt: world.clockAnchorAt?.getTime() ?? null }, ctx.now)`(`queries.ts:55-56`)이고 지난 연월 판정, `months`, `idle`에 같은 값을 쓴다. 화면 머리의 연월과 같고 시험은 `ctx.now`를 주입한다. 이 값을 활동값 대신 쓰지 않는다.
- 쓰기(`create`·`close`)는 기본 격리 트랜잭션에서 World를 `FOR SHARE`로 잠근 뒤 읽는다. 엔진 턴은 World를 `FOR UPDATE`로 잠그므로(`turnLoop.ts:113`) 그동안 직책·국가가 바뀌지 않는다. 잠금 순서는 World 다음이다(T2-13 B-4). `close`는 `status: 'OPEN'` 조건부 갱신으로 두 번 닫기를 막는다.

##### 행위자와 권한

검사 순서: `protectedProcedure`(무인증·제재·탈퇴·만료) → strict 입력(BAD_REQUEST) → `readWorld`의 NOT_FOUND → `requireGeneral(tx, worldId, ctx.user.id)`의 NOT_FOUND(`queries.ts:49-53`) → 아래 권한. 라우터는 세션·제재를 다시 검사하지 않는다. 입력에 행위 장수 ID를 받지 않는다.

- 직책자는 `nationId !== null && officerLevel >= 5`다(위 공개 범위, `data-model.md:112`). 군주는 12다.
- 참여자는 `OperationMember` 행이 있고 그 장수의 지금 `nationId`가 작전 국가와 같은 장수다.
- 작전 조회는 `{ worldId, id, nationId: 행위 장수 국가 }`로 찾는다. 없는 ID와 다른 국가 작전은 같은 FORBIDDEN이라 존재를 알려 주지 않는다.

| ---- | ---- |
| `create` | 직책자 아님 FORBIDDEN |

- `targetTick`은 BigInt다. Int(2^31 − 1)로 두면 승인된 먼 미래 목표(U62-4c)에 새 제한이 생긴다. 쓸 때 `BigInt(operationTargetTick(…))`, 읽을 때 `Number(row.targetTick)` 뒤 `Number.isSafeInteger`가 아니면 Error(INTERNAL)다. 아래 CHECK 때문에 정상 경로에서는 걸리지 않는 변환 검사다. API와 rules에는 늘 safe integer number만 간다. `min*` 세 열은 Int 그대로다.
- 국가 FK는 Cascade다. 엔진이 국가 행을 지우므로 NoAction이면 멸망 처리가 실패한다. `NationTurn`과 같다(`schema.prisma:261`). 엔진 코드는 바뀌지 않고 멸망한 국가의 작전 행이 함께 지워진다.
- 장수 FK는 `GeneralTurn`·`MessageRead`처럼 Cascade다(`schema.prisma:236,446`). 운영 경로의 장수 삭제는 없다. 도시 FK는 `General.city`처럼 NoAction이다(`:203`).
- migration은 `20261023050000_default_policy` 뒤의 새 파일 하나다. enum, 두 표, FK, 색인, CHECK(`targetTick` 0~9,007,199,254,740,991(`Number.MAX_SAFE_INTEGER`), `minCrew`·`minTrain`·`minAtmos >= 0`)만 만들고 기존 migration과 열은 고치지 않는다. 이 migration은 위 공유 범위 승인으로 T2-11 소유이고 구현 기준 커밋의 마지막 migration 뒤 시각을 쓴다.

##### `months` 표시 범위

`months`는 응답이 열 머리로 보여 줄 달이다. 목표를 만들 수 있는 범위와는 상관이 없고 `targetDate`·`targetTick`·`beyondWindow`는 그대로 목표 전체를 나타낸다. 모양은 기존 `GameDate[]`다.

- 시작은 이번 달, 곧 `toGameDate(startYear, 지금 tick)`이다.
- 끝은 다음 셋 중 가장 이른 달이다. `targetDate` 다음 달, 응답 `timeline`의 모든 장수 `cells[29].date` 중 가장 늦은 달, 이번 달 + 30개월. 칸 0이 이번 달이나 다음 달이라는 전제는 쓰지 않는다. 장수 `nextTurnTick`이 지금보다 훨씬 뒤여도 셋째 끝이 크기를 막는다.
- 이번 달 + 30개월은 `year × 12`로 전체 연도를 곱하지 않는다. 이번 달의 월 차(`month − 1 + 30`)만 12로 나눠 연도에 몫을 더하고 나머지로 월을 정한다. 연월 비교는 (year, month) 사전식이다. 연도 덧셈이 safe integer를 넘는 끝 연월의 표현은 `toGameDate`의 표현 범위를 그대로 따르고 숨은 Int32 목표 상한을 두지 않는다.
- 시작부터 끝까지 한 달씩 넣고 반복은 31번 이하다. 끝이 시작보다 앞이면 빈 배열이고 `timeline`이 비면 `[]`다.
- 최대 31개는 30칸 창에 이번 달을 더한 표시 범위이며 목표를 만들 수 있는 상한이 아니다. `cells`(늘 30칸), `targetDate`, `targetTick`, `beyondWindow`는 이 범위와 상관없이 그대로다.
- 목표가 표시 범위 밖이면 목표 연월 열은 `months`에 없다. 화면은 `targetDate`로 목표를 따로 보여 준다. 열 밖 출병의 표시는 위 타임라인 계산 결정 그대로다.
- T2-12 후속: 이번 달 + 30개월 끝은 T2-12의 `months` 소비에 영향이 있다. T2-12에서 유한한 `months`와 범위 밖 sortie의 연월 표시를 확인하도록 알린다. 이 계획은 화면을 고치지 않는다.

##### 응답 조립

- `SlotView`는 `displaySlots(readSlots(…))` 그대로다. `TimelineCell.turn`도 이 값에서 칸 번호로 고른다. `deadlineTick`은 저장된 `targetTick`이다.
- 목표 도시 소유는 지금 `City.nationId`와 `publicNationDisplaySelect`(`visibility.ts:143-147`)다. 로그인 사용자 공통 지도(`mapCity`, `:25-35`)와 같은 공개 범위이고 공백지면 null이다.
- `targetAt`·`cells[].at`·`nextTurnAt`은 `readWorld`의 행으로 `nextTurnAt(world, tick)`을 부른다.
- 감찰 행은 같은 국가 장수 전부다. `turns`는 `home.get`처럼 `displaySlots(readSlots(…))`의 앞 5칸(`routers/home.ts:21,49`), `lastActiveAt`은 열 값의 ISO 문자열이고 null이면 null이다.
- 작전 조회·제안·감찰은 활동 기록을 갱신하지 않는다(T2-13 계획 활동 결정).

| 장수 | `idle` | `lastActiveAt` |
| ---- | ------ | -------------- |
| NPC(`userId` null) | false. `isInactive`를 부르지 않는다. 위 계약 주석과 T2-13의 NPC 비판정 그대로다 | 열 값의 ISO 문자열, null이면 null |

- 근거: 부모가 정책 담당과 확인해 넘긴 T2-13 원계약이다. "옛 ENDED 월드(F null, 표지 없음)도 같은 none 모양으로 읽는다. T2-11 idle은 lastActiveTick이 null이면 isInactive를 부르지 않고 미접속 아님으로 둔다."(`docs/plans/T2-13.md:350`) null은 판정하지 않는 분기다. 0이나 지금 tick 같은 가짜 활동값을 `isInactive`에 넣지 않는다.

- 작전 절차도 활동값을 쓰지 않으므로 월드 상태로 막지 않는다. 표시용 방침 예상은 `isPolicyMode` true이고 `userId`가 있는 장수만 쓴다. 그때 `defaultPolicy`가 `isPolicyKey`를 통과하지 않으면 Error다(`monthly.ts:37`과 같음). 방침 모드에서 `?? 'none'`을 쓰지 않는다. F null에서는 `defaultPolicy`를 읽지 않고 빈칸을 휴식으로 둔다. 갱신 대기 읽기가 `none`을 주는 것(`game/policy.ts:9`)과 같은 뜻이다.

##### 작전 쓰기의 성격

- `Operation`은 규칙·엔진·재생·해시가 읽지 않는다. 실행 결과를 바꾸지 않는 계획 메타데이터다. API가 InputEvent 없이 쓰는 앞선 예는 `Message`와 `Nation.notice`다(`routers/notice.ts:33-46`).
- 새 InputEvent kind와 디스패처 항목은 더하지 않는다. 예턴은 사용자가 확인한 뒤 기존 `turns.set`으로만 바뀐다. 계약 입력에 멱등 키가 없으므로 두 번 보내면 작전이 둘 생긴다. 키를 더하지 않는다.
- 부모 수용 (2026-10-23, T2-11 한정): `Operation`·`OperationMember`의 생성·종료는 WorldState, 전투·턴, 장수·도시·국가 자원, 예턴, 월간 처리, 재생 입력, `actionSequence`에 영향이 없는 Message·공지 같은 보조 저장이다. 새 InputEvent나 dispatcher 없이 이 두 보조 표만 세션 actor, 위 권한·국가, 월드 경계를 지켜 한 트랜잭션에서 API가 저장한다.
- 이 수용은 AGENTS.md §6과 `data-model.md:10`의 게임 상태 소유 규칙을 전역으로 완화하지 않고 다른 기능의 예외로 넓히지 않는다. 국가 삭제 Cascade(위 저장 모양 절)는 보조 메타데이터의 수명 관리이며 인사 offer 같은 게임 정책의 승인이 아니다. 이 계획은 AGENTS·data-model을 고치지 않는다.

##### 규칙 파일과 export

- 새 순수 파일 둘이 필요하다. `packages/rules/src/operation/forecast.ts`는 0단계 `calculateOperationTimeline`의 칸·sortie에 표시용 방침 예상을 더해 예상값과 판정을 낸다. `suggest.ts`는 위 제안 사본 계약 표 그대로다. 둘 다 `choosePolicyCommand`·`sameSlot`과 명령 정의의 `check`를 다시 쓴다. 준비 칸 수와 `BALANCE` 식은 게임 규칙이라 서버에 두지 않는다.

- rules 패키지는 `.`만 내보낸다(`packages/rules/package.json:5-7`). 서버는 깊은 경로를 import할 수 없다. 위 공유 범위 승인으로 T2-11이 루트 `index.ts`에 operation `calendar`·`timeline`·`forecast`·`suggest`의 공개 export만 더한다. 정책 export는 고치지 않는다. 정책 함수는 이미 루트에 있다.

남은 부모 조율 항목은 없다. 닫힌 항목 (2026-10-23): 공유 schema·root·router는 위 공유 범위 승인으로, 감찰 F null은 T2-13 원계약 인계로, `months` 크기는 위 표시 범위 절로, `targetTick` 저장 범위는 BigInt로, 작전 쓰기와 국가 삭제 Cascade는 위 작전 쓰기 절의 T2-11 한정 수용으로 닫았다. 제안 모병 인자는 위 제안 사본 계약의 `UNREACHABLE`로 닫았다. 아래 둘은 부모 판단이 아닌 확정 경계다.

##### 시험 (착수 뒤, 이번에 실행하지 않음)

DB, 전체 check, 브라우저, 새 설치는 시작하지 않는다. 좁은 unit·type 검사는 부모 전체 check가 끝나 실행이 허용됐지만 이 계획 세션은 아무것도 실행하지 않았다. 구현 때 파일마다 좁은 시험을 먼저 돌리고 실제 API·authz·PG 증거는 DB 시작이 허용된 뒤 낸다.

- rules: 위 제안 반례 표, 방침 예상(방침 모드 사람만, NPC와 F null은 휴식), forecast 판정이 0단계와 같은 입력에서 같은 값. 기존 calendar·timeline 시험은 그대로 통과.
- server PG: 절차 여섯 × 다섯 종류 `authzCase`(면제 추가 없음). 다른 국가·없는 ID FORBIDDEN, 떠난 참여자 제외, 직책 4 거부·5 허용, 군주와 만든 장수의 닫기, CLOSED 두 번 닫기. 지난 연월·시작 전·safe integer 아닌 `targetYear`·safe integer 넘는 목표 tick·잘못된 월 BAD_REQUEST, 30칸 밖 생성 허용, 2^31 넘는 목표 tick의 생성·재조회가 같은 number, 중복·다른 국가 `memberIds` BAD_REQUEST. `months`: 30칸 안 목표는 `targetDate` 다음 달까지, 30칸 밖은 가장 늦은 `cells[29]` 달까지, 이번 달 + 30개월을 넘지 않음, `timeline`이 비면 `[]`. 장수 `nextTurnTick`이 지금보다 수백 년 뒤여도 반복이 31번 이하이고 `cells`·`targetDate`·`beyondWindow`는 그대로. 작전 쓰기: `create`·`close` 앞뒤로 World(`actionSequence` 포함)·장수·도시·국가 행, 예턴과 `turnRevision`, InputEvent 큐, 상태 해시가 같고 효과는 `Operation`·`OperationMember` 행뿐. 감찰: NPC와 사람 null `lastActiveTick`은 방침 모드·갱신 대기·옛 ENDED 모두 거부 없이 `idle` false이고 `lastActiveAt`은 열 값 그대로, 숫자는 `ctx.now`로 14일 경계. 제안 앞뒤 `turnRevision`·30칸 불변. 엔진의 국가 삭제가 열린 작전과 함께 성공.

### 제안 사본 계획 검토 (Codex, 2026-10-23)

- 결과: 실제 Claude 계획 세션 `4b58e232-01cb-4262-ae51-d4e728366621`의 제안 사본 계약을 기술 범위에서 통과시켰다. 제안 코드는 구현하지 않았으며 이 검토는 API·AC 완료 증거가 아니다.
