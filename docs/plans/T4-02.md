## 2. 계약

### 2.1 resolver

새 파일 `packages/rules/src/commands/resolve.ts`가 아래를 낸다. 이름과 메서드 넷은 총괄 결정(명세 C13)이며 T4-02가 바꾸지 않는다.

```ts
export interface EnabledCommands {
  general: readonly string[];
  nation: readonly string[];
}
export interface CommandResolver {
  get(key: string): CommandDef | undefined;
  list(target: 'general' | 'nation'): readonly CommandDef[];
  precheck(view: WorldView, actor: Actor, key: string, args: unknown): Failure | null;
  run(view: WorldView, actor: Actor, key: string, args: unknown, rng: Rng): CommandResult | Failure;
}
export function createCommandResolver(enabled: EnabledCommands | null): CommandResolver;
```

- 기본 명령은 `registry.ts:11-19`의 `commands`이고 늘 켜져 있다. 확장 명령은 `commands/ext/registry.ts`의 `extensionCommands: readonly CommandDef[]`이다. T4-02는 이 목록을 빈 배열로 만든다.
- `enabled`의 두 목록에는 확장 key만 들어간다. 기본 key, 어디에도 없는 key, 대상이 다른 key(예: 장수 명령을 `nation` 목록에), 같은 key 두 번은 `createCommandResolver`가 예외로 거부한다. 고정 프리셋의 잘못을 조용히 넘기지 않기 위해서다. `createExtState`(2.4.3)도 같은 입력을 같은 규칙으로 거부한다. 그쪽은 순환을 피하려고 `extensionCommands` 대신 `extCommandBindings`로 보고, 두 목록이 같다는 것은 `ext/registry.test.ts`가 지킨다(I9).
- `get(key)`: 기본 key면 그 정의, 켠 확장 key면 그 정의, 그 밖에는 `undefined`.
- `list(target)`: 기본 명령을 `registry.ts`의 순서대로, 이어서 켠 확장 명령을 `extensionCommands`의 순서대로 낸다. `enabled` 목록의 순서는 결과에 영향을 주지 않는다.
- `precheck`: (1) 기본에도 확장에도 없는 key는 `UNKNOWN_COMMAND`, (2) 확장에 있으나 켜지지 않은 key는 `COMMAND_DISABLED`, (3) `def.target !== (actor.target ?? 'general')`이면 `BAD_ARGS`, (4) `def.args.safeParse` 실패면 `BAD_ARGS`, (5) 그 밖에는 `def.precheck(view, actor, parsed.data)`. (1)·(3)·(4)의 문구는 `registry.ts:29-32`와 같다.
- `run`: (1)~(4)는 `precheck`와 같고 (5)는 `def.check(view, actor, parsed.data) ?? def.execute(view, actor, parsed.data, rng)`다. 이는 `registry.ts:33`과 같은 순서이며 resolver 자체는 `rng`를 읽지 않는다.
- `runCommand`와 `commandRegistry`는 고치지 않는다. 기존 시험과 NPC가 그대로 쓴다.

### 2.2 실패 코드

`commands/types.ts:14-32`의 합 타입 끝(L32 `'NO_UNIT_SET'` 뒤)에 `'COMMAND_DISABLED'`를 더한다. 문구는 구현 PR이 [글쓰기 규칙](../writing-style.md)에 맞춰 정하고 리뷰가 문구도 본다. 기존 18개 코드의 값과 문구는 그대로다.

`null`의 뜻은 확장을 하나도 켜지 않은 월드다. 그래서 `createCommandResolver(null)`에서도 확장 key는 `COMMAND_DISABLED`다. 지금 `runCommand`는 같은 key에 `UNKNOWN_COMMAND`를 낸다. 바이트 동일의 범위는 기본 37개 key와 확장에도 없는 key의 결과, RNG 소비, 상태 해시다. 지금 저장 경로(`slots.ts:11-12`)는 37개 밖의 key를 받지 않으므로 기존 v1 재생 기록과 DB 예턴에는 확장 key가 들어갈 수 없다. 이 범위 해석은 G-03에서 Codex가 수용해야 계약이 된다.

### 2.3 `runGeneralTurn`과 순수 재생

`runGeneralTurn(state, actor, command, seed, options = {}, resolver?)`로 여섯째 선택 인자를 더한다. `options`(`turn.ts:14`)는 NPC 문맥으로 펼쳐지므로(`turn.ts:22`) resolver를 그 안에 넣지 않는다. 본문은 `turn.ts:38`과 `turn.ts:69`의 `runCommand(...)`를 `resolver ? resolver.run(...) : runCommand(...)`로만 바꾼다. NPC 분기(`turn.ts:30-37`, `:56-68`)와 `rngFor` 스트림 이름은 그대로다.

`runReplayAction(replay, seed, unitSet?, resolver?)`로 넷째 선택 인자를 더하고 `replay.ts:59`에서 넘긴다. `applyRecordedInput`(`replay.ts:67-107`)은 바꾸지 않는다. 저장 검사는 API가, 실행 검사는 resolver가 한다.

엔진 턴(`turnLoop.ts:130`), 엔진 재생(`apps/engine/src/replay.ts:132`), 시뮬레이터(`simulation.ts:47`)가 같은 `World.preset`에서 만든 resolver를 넘기는 연결은 후속이다. 앞의 둘은 T4-03, 시뮬레이터는 T4-47이 맡는다(명세 §7). T4-02 뒤에도 이 세 곳은 인자를 넘기지 않으므로 지금과 같다.

### 2.4 `ext` 순수 경로

이 절의 타입과 규칙은 총괄 run908의 기술 설계 결정이다. `CommandDef`(`types.ts:49-58`)는 바꾸지 않는다. 지금 `CommandDef`에는 상태 조각 참조가 없으므로 명령과 조각의 관계를 거기서 추정하지 않고 따로 둔 순수 자료 `extCommandBindings`로 적는다.

#### 2.4.1 타입

```ts
// model/world.ts
export type JsonValue = null | boolean | number | string | JsonValue[] | { [key: string]: JsonValue };
export type WorldExt = Record<string, JsonValue>;
export interface WorldState {
  // 지금 칸(L3-9)은 그대로
  ext?: WorldExt;
}
```

- `world/bootstrap.ts:83-97`의 `WorldInit`에 `ext?: WorldExt`를 더한다. `tsconfig.base.json:9`의 `exactOptionalPropertyTypes`가 켜져 있으므로 `ext: undefined`는 타입에서도 막힌다.
- 실제 명령 정의는 지금처럼 `ext/registry.ts`의 `extensionCommands`가 가진다. `ext/state.ts`는 조각 목록 `extSlices`와 명령·조각 관계 `extCommandBindings`를 가진다.

#### 2.4.2 명령과 조각의 관계

- `extCommandBindings`에는 확장 명령마다 행이 정확히 하나 있다. 상태가 필요 없는 명령도 `sliceKeys: []`로 행을 둔다. 기본 37개는 행이 없다. 행이 없는 확장 명령을 상태 없음으로 추정하지 않는다.
- 두 명령이 한 조각을 공유하면 두 행의 `sliceKeys`에 같은 key가 있다. 한 명령이 조각 둘을 쓰면 그 행의 `sliceKeys`에 key가 둘 있다.
- `ext/registry.test.ts`는 실제 `extensionCommands`의 (key, target) 집합과 `extCommandBindings`의 (commandKey, target) 집합이 정확히 같은지 대조한다. 행 누락, 남는 행, 대상 불일치가 모두 실패다.

#### 2.4.3 `createExtState`

`createExtState(enabled, context)`는 아래 순서로 동작한다. 둘째 인자 `context`는 확장 상태를 넣기 전의 기초 월드를 읽기 전용으로 받는 것이며 생략할 수 없다.

1. 등록 조합을 검사한다. 같은 조각 key 두 번, 같은 `commandKey` 행 두 번, 한 행 안의 같은 조각 key 두 번, `extSlices`에 없는 조각 key 참조는 예외다.
2. `enabled === null`이면 `undefined`를 낸다. 어떤 조각의 `create`도 부르지 않는다.
3. `enabled`를 검사한다. `extCommandBindings`에 없는 key(기본 key와 어디에도 없는 key), 대상이 다른 key, 같은 key 두 번은 예외다. 규칙은 2.1의 `createCommandResolver`와 같다. `enabled`는 프리셋 해석 결과 그대로이며 이 함수가 G-01의 생략 정책을 고르지 않는다.
4. 켠 명령 행의 `sliceKeys` 합집합을 구한다.
5. 합집합이 비면 `undefined`를 낸다. 호출자는 `ext` 속성을 아예 두지 않는다(명세 C3). 상태 없는 명령만 켠 월드가 여기에 든다.
6. `extSlices`의 등록 순서로 돌며 합집합에 든 조각만 `create(context)`를 정확히 한 번 부른다. 공유 조각을 두 번 만들지 않고 꺼진 조각은 만들지 않는다.
7. 각 반환값을 공통 JSON 검사와 그 조각의 `validate`로 확인한 뒤 등록 순서대로 담아 낸다. 결과의 key 순서는 `enabled` 목록의 순서와 무관하다.

모든 `create`는 같은 `context`만 읽는다. DB, 현재 시각, RNG, 다른 조각의 초기값은 입력에 없다. `create`는 입력을 바꾸지 않고 부를 때마다 새 값을 낸다. 이 함수를 월드 생성·bootstrap에서 실제로 부르는 일은 T4-03이다.

#### 2.4.4 공통 JSON 검사와 실패 위치

공통 JSON 검사는 `null`, 불리언, 문자열, 유한한 숫자, 원형이 `Array.prototype`인 빈칸 없는 배열, 원형이 `Object.prototype`이거나 `null`인 객체만 받는다. `undefined`, `NaN`·`Infinity`, `Date`, `Map`, `Set`, 함수, `bigint`, 기호 key, 순환 참조, `__proto__`·`constructor`·`prototype` key는 거부한다. `hashState`(`packages/shared/src/node/hashState.ts:3-20`)는 `undefined`와 유한하지 않은 숫자를 받지 않는다. Prisma Json 칸은 `Date`·`Map`을 같은 값으로 돌려주지 않는다.

| 검사 위치 | 무엇을 보나 | 실패 |
| --------- | ----------- | ---- |
| `createExtState` 1·3단계 | 등록 조합, `enabled` | 예외 |
| `createExtState` 7단계 | `create` 반환값의 JSON 검사·`validate` | 예외 |
| `toWorldState`(`model/world.ts:13-24`) | `initial`에 `ext` 속성이 있으면 빈 객체가 아닌지, 모든 key가 `extSlices`에 있는지, 값마다 JSON 검사·`validate`. 통과하면 조각의 `clone`으로 복제해 넣는다 | 예외 |
| `cloneWorld`(`model/clone.ts:4-27`) | `view.ext`가 있으면 위와 같은 검사를 복제 입력에 한다. 조각마다 `clone` 결과에도 JSON 검사·`validate`를 한다. key 순서는 `extSlices` 등록 순서다 | 예외 |

- 설정 오류와 복제 오류를 게임 `Failure`로 바꾸거나 조각을 조용히 버리지 않는다. 예외 문구에는 문제의 조각 key나 명령 key를 넣는다. 문구는 [글쓰기 규칙](../writing-style.md)을 따른다.
- 저장된 `ext`의 key 집합이 그 월드의 `enabled`에서 고른 조각과 같은지 보는 복원 검사는 DB 경로이므로 T4-03이다.
- `clone`은 깊은 복제다. 결과는 원본, 다른 월드, 다른 조각과 바뀔 수 있는 참조를 나누지 않는다.
- `runMonthly`(`monthly/index.ts:32`, `:61`, `:83`, `:101`)와 순수 재생(`replay.ts:56`, `:69`)은 `structuredClone`으로 이미 `ext`를 보존한다. T4-02는 이 두 곳을 바꾸지 않고 보존 시험만 더한다. 월간 정산에서 조각이 하는 일은 각 기능 작업 몫이다.

#### 2.4.5 시험용 조각 주입

운영 목록 `extSlices`·`extCommandBindings`·`extensionCommands`는 T4-02에서 빈 배열이고 시험이 전역으로 바꾸지 않는다. 시험용 조각과 관계는 공개 함수가 감싸는 내부 순수 helper에 인자로 넘긴다. `createExtState`, `toWorldState`, `cloneWorld`는 각각 운영 목록을 넘기는 얇은 감싸개이고 같은 파일의 내부 helper가 `{ slices, bindings }`를 받는다. 내부 helper는 `packages/rules/src/index.ts`로 내보내지 않는다.

순수 재생의 장수 턴 분기(`replay.ts:59`)는 명령 안에서 운영 목록의 `cloneWorld`를 거치므로 시험용 조각을 실을 수 없다. T4-02는 이 분기를 끈 월드와 2.6 X16(운영 목록에 없는 조각은 예외)으로 고정한다. 실제 조각이 든 장수 턴 재생의 보존 시험은 처음 조각을 등록하는 작업(명세 §7 순서의 T4-17)의 의무다.

#### 2.4.6 T4-03과의 경계

순수 helper와 그 시험은 T4-02다. 실제 호출(월드 생성·bootstrap의 `createExtState`), `worldLoader`의 `ext` 적재와 복원 key 집합 검사, 턴·월간 저장, 재생 기록 형식은 T4-03이다(명세 C14). T4-02는 게임 명령이나 조각을 하나도 만들지 않는다.

재생 기록 버전 번호는 이 문서가 정하지 않는다. 명세 C14(`5457700` 106줄)는 켠 월드를 version 2로 쓴다고 적었다. 그런데 PR #137 `3a058cd`의 [T1-26 계획](https://github.com/peppone-choi/opensamguk/blob/3a058cd7f526ca05cd226d49c24c9e95d5dfcdda/docs/plans/T1-26.md) 87~113줄이 종료 기록용 `ReplayArchiveV2`(origin은 v1 그대로)를 예약했다. 같은 번호를 따로 쓰면 형식이 섞인다. 총괄 결정에 따라 먼저 정상 통합되는 T1-26의 archive v2가 그 번호의 단일 소유자다. T4-03 상세 계획은 그때 main의 형식을 읽는다. 호환되지 않는 확장 형식에는 다음 미사용 버전(지금 예상은 v3)을 쓴다. 기존 v1과 저장된 해시는 바꾸지 않는다. 읽기 허용 조합과 섞인 모양의 거부도 그 계획에 적는다. 이 문서는 C14의 version 2 문구를 따로 다시 정하지 않는다.
