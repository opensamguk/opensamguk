## 계획 (Claude)

### 목표

명세 AC-P2-02 가운데 순수 규칙 몫을 만든다. 월드마다 켠 확장 명령만 조회·사전 검사·실행되고 끈 월드(`enabled = null`)는 기존 명령 37개의 결과·RNG 소비·상태 해시가 지금과 바이트 단위로 같다. 켠 월드의 확장 상태 `ext`는 명령 복제·월간 정산·순수 재생을 지나도 사라지지 않고 끈 월드에는 `ext` 키 자체가 없다.

### 범위

새 파일은 `packages/rules/src/commands/resolve.ts`, `commands/ext/registry.ts`, `commands/ext/state.ts`와 각 시험 파일이다. 고치는 파일은 `commands/types.ts`, `commands/turn.ts`, `model/world.ts`, `model/clone.ts`, `world/bootstrap.ts`, `replay.ts`, `index.ts`(export 한 줄)다. 모두 `packages/rules` 안이다.

### 하지 않는 것

- 서버·엔진·DB 연결. `parseSlot`, `displaySlots`, `turns.precheck`, `commands.list`, `turnLoop`, `worldLoader`, 재생 기록 version 2, migration은 T4-03 몫이다(명세 C13·C14). 이 문서는 T4-03의 계약을 정하거나 수용하지 않는다.
- 확장 명령 자체. `extensionCommands`는 빈 목록으로 시작한다. 명령은 T4-05 이후와 [누락 명령 문서](./mvp-command-gaps.md)의 T4-57~T4-75가 자기 폴더에서 만든다.
- NPC 판단, `commandRegistry`의 37개, `registry.test.ts`의 37개 대조, RNG 스트림 이름(명세 C1·C11).
- 새 API 이름, 비용, 정책. `World.preset` 해석(G-01)도 하지 않는다.

## 2. 계약

### 2.1 resolver

새 파일 `packages/rules/src/commands/resolve.ts`가 아래를 낸다. 이름과 메서드 넷은 총괄 결정(명세 C13)이며 T4-02가 바꾸지 않는다.

```ts
export interface EnabledCommands {
  general: readonly string[];
  nation: readonly string[];
}
export interface CommandResolver {
  get(key: string): CommandDef | undefined;
  list(target: 'general' | 'nation'): readonly CommandDef[];
  precheck(view: WorldView, actor: Actor, key: string, args: unknown): Failure | null;
  run(view: WorldView, actor: Actor, key: string, args: unknown, rng: Rng): CommandResult | Failure;
}
export function createCommandResolver(enabled: EnabledCommands | null): CommandResolver;
```

- 기본 명령은 `registry.ts:11-19`의 `commands`이고 늘 켜져 있다. 확장 명령은 `commands/ext/registry.ts`의 `extensionCommands: readonly CommandDef[]`이다. T4-02는 이 목록을 빈 배열로 만든다.
- `enabled`의 두 목록에는 확장 key만 들어간다. 기본 key, 어디에도 없는 key, 대상이 다른 key(예: 장수 명령을 `nation` 목록에), 같은 key 두 번은 `createCommandResolver`가 예외로 거부한다. 고정 프리셋의 잘못을 조용히 넘기지 않기 위해서다.
- `get(key)`: 기본 key면 그 정의, 켠 확장 key면 그 정의, 그 밖에는 `undefined`.
- `list(target)`: 기본 명령을 `registry.ts`의 순서대로, 이어서 켠 확장 명령을 `extensionCommands`의 순서대로 낸다. `enabled` 목록의 순서는 결과에 영향을 주지 않는다.
- `precheck`: (1) 기본에도 확장에도 없는 key는 `UNKNOWN_COMMAND`, (2) 확장에 있으나 켜지지 않은 key는 `COMMAND_DISABLED`, (3) `def.target !== (actor.target ?? 'general')`이면 `BAD_ARGS`, (4) `def.args.safeParse` 실패면 `BAD_ARGS`, (5) 그 밖에는 `def.precheck(view, actor, parsed.data)`. (1)·(3)·(4)의 문구는 `registry.ts:29-32`와 같다.
- `run`: (1)~(4)는 `precheck`와 같고 (5)는 `def.check(view, actor, parsed.data) ?? def.execute(view, actor, parsed.data, rng)`다. 이는 `registry.ts:33`과 같은 순서이며 resolver 자체는 `rng`를 읽지 않는다.
- `runCommand`와 `commandRegistry`는 고치지 않는다. 기존 시험과 NPC가 그대로 쓴다.

### 2.2 실패 코드

`commands/types.ts:14-32`의 합 타입 끝(L32 `'NO_UNIT_SET'` 뒤)에 `'COMMAND_DISABLED'`를 더한다. 문구는 구현 PR이 [글쓰기 규칙](../writing-style.md)에 맞춰 정하고 리뷰가 문구도 본다. 기존 18개 코드의 값과 문구는 그대로다.

`null`의 뜻은 확장을 하나도 켜지 않은 월드다. 그래서 `createCommandResolver(null)`에서도 확장 key는 `COMMAND_DISABLED`다. 지금 `runCommand`는 같은 key에 `UNKNOWN_COMMAND`를 낸다. 바이트 동일의 범위는 기본 37개 key와 확장에도 없는 key의 결과, RNG 소비, 상태 해시다. 지금 저장 경로(`slots.ts:11-12`)는 37개 밖의 key를 받지 않으므로 기존 v1 재생 기록과 DB 예턴에는 확장 key가 들어갈 수 없다. 이 범위 해석은 G-03에서 Codex가 수용해야 계약이 된다.

### 2.3 `runGeneralTurn`과 순수 재생

`runGeneralTurn(state, actor, command, seed, options = {}, resolver?)`로 여섯째 선택 인자를 더한다. `options`(`turn.ts:14`)는 NPC 문맥으로 펼쳐지므로(`turn.ts:22`) resolver를 그 안에 넣지 않는다. 본문은 `turn.ts:38`과 `turn.ts:69`의 `runCommand(...)`를 `resolver ? resolver.run(...) : runCommand(...)`로만 바꾼다. NPC 분기(`turn.ts:30-37`, `:56-68`)와 `rngFor` 스트림 이름은 그대로다.

`runReplayAction(replay, seed, unitSet?, resolver?)`로 넷째 선택 인자를 더하고 `replay.ts:59`에서 넘긴다. `applyRecordedInput`(`replay.ts:67-107`)은 바꾸지 않는다. 저장 검사는 API가, 실행 검사는 resolver가 한다.

엔진 턴(`turnLoop.ts:130`), 엔진 재생(`apps/engine/src/replay.ts:132`), 시뮬레이터(`simulation.ts:47`)가 같은 `World.preset`에서 만든 resolver를 넘기는 연결은 후속이다. 앞의 둘은 T4-03, 시뮬레이터는 T4-47이 맡는다(명세 §7). T4-02 뒤에도 이 세 곳은 인자를 넘기지 않으므로 지금과 같다.

### 2.4 `ext` 순수 경로

- `model/world.ts:2-10`의 `WorldState`에 `ext?: WorldExt`를 더한다. `WorldExt`는 확장 조각 key에서 그 조각 값으로 가는 객체이며 `commands/ext/state.ts`가 타입과 조각 목록 `extSlices`를 낸다. T4-02는 조각을 하나도 등록하지 않는다(명세 §7 조각 등록 순서는 T4-02 → T4-17 → …).
- 조각 계약 `ExtSlice<T>`는 `key`, 초기값 함수, 복제 함수, 형식 검사 함수 넷이다. 값은 JSON으로 그대로 오가는 평범한 자료만 쓴다(Map, Date, `undefined` 금지). `hashState`와 Prisma Json 칸을 거쳐도 같은 값이 나와야 하기 때문이다.
- `world/bootstrap.ts:83-97`의 `WorldInit`에 `ext?: WorldState['ext']`를 더한다. `toWorldState`(`model/world.ts:13-24`)는 `commandMeta`·`nationTurns`(L21-22)와 같은 방식으로 `initial.ext`가 있을 때만 복제해 넣는다.
- `cloneWorld`(`model/clone.ts:4-27`)는 `view.ext`가 있을 때만 조각마다 그 조각의 복제 함수로 깊이 복제한다. 등록되지 않은 조각 key가 있으면 예외를 낸다. 모르는 조각을 버리면 C14가 막으려던 조용한 유실이 되기 때문이다.
- 빈 `ext` 객체는 만들지 않는다. 형식 검사는 `ext: {}`를 거부한다. 켤 조각이 없으면 `ext` 키를 두지 않는다(명세 C3).
- 켠 월드의 초기 `ext`를 만드는 순수 함수 `createExtState(enabled)`도 `ext/state.ts`에 둔다. 상태가 필요한 조각이 하나도 없으면 `undefined`를 낸다. 이 함수를 월드 생성·bootstrap에서 부르는 일은 T4-03이다.
- `runMonthly`와 순수 재생은 `structuredClone`으로 이미 `ext`를 보존한다. T4-02는 코드를 바꾸지 않고 보존 시험만 더한다. 월간 정산에서 조각이 하는 일은 각 기능 작업 몫이다.

## 3. 관문과 남은 차이

### G-01 (T2-02 허용 목록 생략의 뜻)

[T2-02 계획](./T2-02.md)은 `77723bf`에서 `commands.general`, `commands.nation`을 허용 명령 key 목록이라 하고 없으면 전체라고 적었다(T2-02.md:29). 허용 목록 밖 명령은 `turns.precheck`와 실행 검사에서 `COMMAND_DISABLED`라고도 적었다(T2-02.md:39). T2-02는 대기열에서 `구현` 단계이고 `packages/rules/src/world/preset.ts`는 아직 없다. 수용된 구현 SHA가 없으므로 핀할 것은 이 계획 문장뿐이다.

명세 C2와 남은 차이는 셋이다. (가) 목록이 없을 때 T2-02는 전체를 켜고 C2 제안은 기본만 켠다. (나) T2-02의 목록은 기본 명령도 끌 수 있게 읽히지만 T4-02 resolver는 기본 37개를 늘 켠다. (다) T2-02는 저장·편집(`parseSlot`)과 `commands.list`를 적지 않았고 C2는 적었다.

T4-02는 이 관문에 막히지 않는다. resolver의 입력은 프리셋을 해석한 결과인 `EnabledCommands | null`이다. `null`은 확장을 하나도 켜지 않은 월드를 뜻하며 허용 목록 생략과 같은 말이 아니다. 프리셋에서 `enabled`를 만드는 함수와 (가)·(나)·(다)의 결론은 T4-03이 T2-02 담당과 맞춘다. 다르면 총괄이 한쪽으로 정한다(명세 G-01).

### G-03 (이 계획의 기술 검토)

풀리지 않았다. 후속 Codex 기술 검토 카드(t_027be599)가 이 문서와 [누락 명령 문서](./mvp-command-gaps.md)를 검토하고 결과를 아래 리뷰 절에 남긴다. 검토 통과는 계약 준비 조건 가운데 하나일 뿐이며 사용자 계획 승인이나 제품 정책 승인을 대신하지 않는다.

## 5. 명령 대응표 도구의 후속 범위

PR #67의 `tools/command-coverage.mjs`(`5457700`)는 `REGISTRY_FILES`(L48-56)에 적힌 기본 명령 파일 일곱 개에서만 `key:`를 읽는다(L58-70). 그래서 확장 명령을 `ext/registry.ts`에 등록해도 도구는 그 key를 registry 밖으로 보고, `engine`·`effectsCostsFailures` 단계를 `partial`이나 `verified`로 적으면 오류를 낸다(L701-707). 대응표의 `queueIds`에 있는 T4 ID는 phases.md나 명세 §6 표에서 `MVP 필수 (D-022)` 상태 행을 찾는다(L556-561, `queueStatus` L161-167).

T4-02의 도구 몫은 PR #67이 main에 들어온 뒤에만 시작한다.

- 도구가 `packages/rules/src/commands/ext/registry.ts`와 그 목록이 가리키는 파일에서 확장 key와 대상을 읽는다. vitest가 그 결과를 실제 `extensionCommands`와 대조한다. 기본 37개를 읽는 지금 방식과 37개 부분집합 이력은 바꾸지 않는다.
- 확장 key가 registry에 있으면서 대응표에 없거나, 대상이 다르면 실패한다. 이는 기본 key의 L713-714 검사와 같은 규칙이다.
- T4-57~T4-75를 대응표 `queueIds`에 넣는 일은 이 문서가 하지 않는다. 지금 도구는 [누락 명령 문서](./mvp-command-gaps.md)를 읽지 않으므로 넣는 순간 L558 검사가 실패한다. 명세 §6에 행을 더할지 도구가 이 문서를 읽을지는 PR #67 정본 통합 뒤 총괄이 정한다(같은 hunk 충돌 위험, 끝의 hotspot 참고).
