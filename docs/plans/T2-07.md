# T2-07 D1 조약서 외교, D16 교역

> 대기열: T2-07 · AC: AC-M2-06, AC-M2-14 · 구현: Codex · 리뷰: Claude
> 선행: M1 전체 · 관련: [차별화 D1](../product/differentiation.md#d1-조약서-외교), [D16](../product/differentiation.md#d16-교역), FR-DIF-01·16

## 계획 (Claude)

### 목표

- 조항을 골라 제안하고 상대가 수락하면 서버가 조항을 자동 집행한다. 종전도 조약으로 맺는다. 파기하면 신의 기록이 남고 다른 국가가 볼 수 있다.
  권한 없는 장수의 제안·수락은 거부된다 (AC-M2-06).
- 교역 허용 조약이 있는 이웃 나라 도시와 교역하면 금·쌀과 내정치가 오른다. 조약이 끝나거나 교전 중이면 실패한다 (AC-M2-14).

### 범위

- `packages/rules/src/diplomacy/treaty.ts`: 조항 타입, 검증, 집행 효과
- `Treaty`, `NationTrust` 테이블 (데이터 모델 차별화 자리)
- 국가 명령 `선전포고`는 그대로, M1의 `종전 제의`·`불가침 제의`·`파기 제의`·`원조`는 **조약 제안으로 대체** (명령 목록에서 뺌)
- 장수 명령 `교역(trade)` 추가
- `apps/server/src/routers/treaty.ts`

### 하지 않는 것

동맹 공동 참전(Phase 2), 조약 문구 자유 입력의 자동 해석, 원작 외교 수치 맞추기.

### 조항 결정 (M2)

| 조항 | 값 | 서버 집행 |
| ---- | -- | --------- |
| `peace` (종전) | — | 수락 즉시 교전 → 중립 |
| `nonAggression` | 기간 1~120개월 | 기간 동안 서로 선포·출병 불가 |
| `passage` | 허용 도시 목록 | 상대 장수가 그 도시로 이동 가능 (출병은 불가) |
| `tribute` | 내는 쪽, 금·쌀 월 금액, 기간 | 월간 정산에서 국고 이체. 국고가 모자라면 그달은 실패 기록 |
| `trade` | 기간 | 교역 명령 허용 (D16) |
| `cityTransfer` | 도시, 주는 쪽 | 수락 즉시 소유 이전 (그 도시 장수는 주는 쪽 수도로) |
| `note` | 자유 문장 (300자) | 집행 없음. 양국에 기록만 |

- 제안·수락·거절·파기는 **즉시 행동** (군주·참모, T2-05 권한 표). 턴을 기다리지 않지만 API가 게임 상태를 바꾸지도 않는다.
  접수와 집행은 아래 [즉시 행동 처리](#즉시-행동-처리-검토-r62-1r62-3-2026-10-21-추가)를 따른다. 제안 기한 6개월.
- 비용: **양쪽이** 수락 순간에 낸다 (myosam 유료 계약). 한쪽이라도 모자라면 수락 실패이고 어느 쪽도 차감하지 않는다.
  첫 세 조항(종전·불가침·기록)의 식은 [2026-10-23 사용자 승인과 착수 범위](#2026-10-23-사용자-승인과-착수-범위)를 따른다. 다른 조항의 비용과 기간 합산은 U62-2a에 남는다.
- 파기: 남은 조항 모두 종료, `NationTrust.brokenTreaties += 1`, 파기 국가의 다른 조약 상대에게 알림. 외교 화면에 신의 기록 공개.
- 대치: 선포 뒤 교전이 되었는데 6개월 동안 두 나라 사이 전투가 없으면 **선포국 수입 −50%** (해제는 전투 1회 또는 종전).
- 조약은 여러 개 동시에 가능. 같은 조항이 겹치면 늦게 끝나는 쪽을 따른다.

### 교역 결정 (D16)

- 조건: 내가 있는 도시가 우리 국가 소유, 그 도시와 연결된 도시 중 `trade` 조항이 유효한 상대국 도시가 있음, 교전 아님.
- 효과: 금·쌀 = 두 도시 상업 평균 × 계수 × U(0.9, 1.1), 내 도시 상업·농업 +1% (최대치 안). 장수 경험·공헌 소폭.
- 비용 없음 (myosam "무료 내정").

### API 계약

아래 타입 하나가 계약 초안이다 (검토 R62-1, 2026-10-21 정리). 예전 요약(국가 하나를 받는 `treaty.trust`, 배열을 돌려주는 `treaty.list`)은 지웠다.
`treaty` 라우터는 아직 `AppRouter`에 없다(`apps/server/src/router.ts:14-24`). 이 문서의 타입은 제안이다. 최종 서버 타입은 backend(Codex)가
`AppRouter`로 정한다. 화면은 그 타입만 import한다 (AGENTS.md §0 API 계약).

- 도시 키는 기존 계약과 같은 정수다. `City.cityKey`·`General.cityKey`가 `Int`이고(`packages/db/prisma/schema.prisma:84-127`), 조회 입력의
  `entityKey`가 정수이며(`apps/server/src/queries.ts:7`), 출병 인자도 정수 `cityKey`다(`packages/rules/src/commands/attack.ts:59`). 문자열 도시 ID를 따로 만들지 않는다.
- 조약 ID와 입력 ID는 문자열이다. 조약 ID는 집행한 입력의 sequence에서 만든다.
- `GameDate`는 표시용 월 단위 값이다. 기한·만료·순서 판정은 엔진이 tick으로 한다.
- 화면 요소와의 대조는 [T2-08 v1 근거](./T2-08.md#v1-근거)에 있다.

```ts
type GameDate = { year: number; month: number };
type NationRef = { id: number; name: string; color: string };
// 버튼을 쓸 수 있는지는 서버가 정한다. 화면은 code로 분기하고 reason을 DisabledReason으로 보여 준다. 문자열 비교로 분기하지 않는다.
// 검사 순서는 권한이 먼저다. 권한이 없으면 NO_PERMISSION만 주고 비용 부족 같은 뒤 검사 결과를 알려 주지 않는다.
type DenyCode = 'NO_PERMISSION' | 'NOT_PARTY' | 'IN_PROGRESS' | 'WRONG_STATUS' | 'EXPIRED' | 'INSUFFICIENT_GOLD';
type Allowed = { ok: true } | { ok: false; code: DenyCode; reason: string };

type Clause =
  | { kind: 'peace' }
  | { kind: 'nonAggression'; months: number } // 1~120
  | { kind: 'passage'; cityKeys: number[] } // 상대 장수가 지나갈 우리 도시
  | { kind: 'tribute'; payerNationId: number; gold: number; rice: number; months: number }
  | { kind: 'trade'; months: number }
  | { kind: 'cityTransfer'; cityKey: number; giverNationId: number }
  | { kind: 'note'; text: string }; // 300자
// enforced는 note만 false다. 화면이 서버가 집행하는 조항과 기록만 남는 조항을 나눠 보여 준다.
// cityNames는 passage·cityTransfer에만 있다.
type ClauseView = Clause & { enforced: boolean; cityNames?: string[] };

type TreatyStatus = 'PROPOSED' | 'ACTIVE' | 'ENDED' | 'BROKEN' | 'REJECTED' | 'EXPIRED';
type TrustRow = { nation: NationRef; brokenTreaties: number; lastBrokenAt: GameDate | null }; // 파기한 적 없으면 0, null
type TreatyRow = {
  id: string;
  from: NationRef; // 제안한 국가
  to: NationRef; // 받은 국가
  incoming: boolean; // 우리 국가가 받은 제안이면 true
  clauses: ClauseView[];
  status: TreatyStatus;
  proposedSeq: number; // 제안을 집행한 입력의 sequence. 정렬 기준이다
  proposedAt: GameDate;
  respondBy: GameDate | null; // PROPOSED일 때 응답 기한(표시용). 그 밖에는 null
  startAt: GameDate | null; // 수락 전에는 null
  endAt: GameDate | null; // 기간 있는 조항이 없으면(종전·도시 이양·기록만) null
  monthsLeft: number | null; // ACTIVE이고 endAt이 있을 때만
  brokenBy: NationRef | null; // BROKEN일 때만
  cost: { mine: number; theirs: number }; // 지금 값으로 계산한 수락 비용. 실제 차감은 엔진 집행 시점의 값이다
  counterpartTrust: TrustRow; // 받은 제안 카드에 보일 상대 신의 기록
  // 아래 셋은 화면 안내용이다. 최종 판정은 엔진 집행 때 한다. 이 조약에 처리 중인 행동이 있으면 IN_PROGRESS
  canAccept: Allowed | null; // incoming이고 PROPOSED일 때만. 우리 국고가 모자라면 INSUFFICIENT_GOLD와 필요 금액
  canReject: Allowed | null; // incoming이고 PROPOSED일 때만. 비용과 무관하다. 국고가 모자라도 거절은 잠그지 않는다
  canBreak: Allowed | null; // ACTIVE일 때만
};
// 화면이 행동 하나마다 만드는 UUID. 응답을 잃어 다시 보낼 때는 같은 값을 쓴다. 서버는 idempotencyKey를 `<kind>:<requestId>`로 적는다
type RequestId = string;
// 제안·응답·파기의 응답. applied일 때만 결과가 확정된 것이다. 엔진이 거절하면 변경 요청은 TRPCError로 이유 코드와 문장을 준다.
// treaty는 지금 세션 장수의 국가가 그 조약의 당사국일 때만 채운다. 그 사이 소속을 잃었으면 null이다.
// 거절 응답(accept false)이 집행되면 status는 applied이고 treaty.status가 REJECTED다.
type InputOutcome =
  | { status: 'applied'; requestId: RequestId; treaty: TreatyRow | null }
  | { status: 'pending'; requestId: RequestId };
// treaty.request의 응답. 엔진 거절도 값으로 준다.
type RequestState = InputOutcome | { status: 'rejected'; requestId: RequestId; code: string; reason: string };
type PendingAction = {
  requestId: RequestId;
  kind: 'propose' | 'respond' | 'break';
  treatyId: string | null; // propose는 집행 전이라 null
  toNation: NationRef | null; // propose일 때만
  accept: boolean | null; // respond일 때만
  requestedBy: { generalId: number; name: string };
};
type RecentAction = {
  requestId: RequestId;
  kind: 'propose' | 'respond' | 'break';
  treatyId: string | null;
  result: 'APPLIED' | 'REJECTED';
  reason: string | null; // REJECTED일 때 이유 문장. 상대 국고·작위·기술·상업 값을 담지 않는다
};
type TreatyTarget = {
  nation: NationRef;
  relation: 'WAR' | 'DECLARED' | 'NON_AGGRESSION' | 'NONE'; // 우리 국가와의 관계. 종전 조항은 WAR·DECLARED일 때만 고른다
  relationEndAt: GameDate | null; // 불가침·선포의 끝. NONE·WAR는 null
  trust: TrustRow;
};
type TradeTarget = { cityKey: number; cityName: string; nation: NationRef; treatyId: string; tradeEndsAt: GameDate };

// treaty.propose({ worldId, requestId, toNationId, clauses: Clause[], expiresInMonths }) → InputOutcome
// treaty.respond({ worldId, requestId, treatyId, accept: boolean }) → InputOutcome
// treaty.break({ worldId, requestId, treatyId }) → InputOutcome
//   행위 장수는 세션에서 정한다. 입력에 장수 ID를 받지 않는다.
// treaty.request({ worldId, requestId }) → RequestState
//   세션 사용자가 보낸 요청 하나의 지금 상태. 남의 requestId나 없는 값은 NOT_FOUND다. 개수나 기간 제한이 없다.
//   kind 인수는 받지 않는다. 두 정확 key가 함께 있으면 CONFLICT다(2026-10-24 정정, 아래 서버 첫 몫 계약).
// treaty.list({ worldId }) → { canPropose: Allowed; targets: TreatyTarget[]; items: TreatyRow[]; pending: PendingAction[]; myRecent: RecentAction[] }
//   items: 우리 국가가 당사자인 조약만. proposedSeq 내림차순(같은 달 제안도 집행 순서로 나뉜다).
//   pending: 우리 국가 장수가 보낸 PENDING 즉시 행동, 접수 순. myRecent: 내 장수가 보낸 즉시 행동 중 끝난 최근 5건, 최신순.
//   pending·myRecent는 목록 안내용이다. 특정 요청의 결과를 되찾는 것은 treaty.request로만 한다.
//   다른 장수의 거절 이유는 myRecent에 넣지 않는다.
//   화면 탭: 받은 제안·보낸 제안 = PROPOSED, 진행 중 = ACTIVE, 끝남 = ENDED·REJECTED·EXPIRED, 파기됨 = BROKEN.
//   targets: 우리 국가를 뺀 모든 국가, 국가 ID 순. canPropose가 ok: false여도 준다(읽기만 하는 장수도 관계를 본다).
// treaty.quote({ worldId, toNationId, clauses }) → { cost: { mine: number; theirs: number }; problems: { index: number; reason: string }[] }
//   조약서를 쓰는 동안 비용과 조항별 문제(기간 범위, 우리 소유가 아닌 도시 등)를 돌려준다. 저장하지 않고 확정 결과도 아니다. 제안 권한자만.
// treaty.trust({ worldId }) → { items: TrustRow[] }
//   국가별 신의 표. 모든 국가, brokenTreaties 많은 순, 같으면 국가 ID 순.
// treaty.tradeTargets({ worldId }) → { fromCityKey: number | null; items: TradeTarget[]; blocked: string | null }
//   예턴 편집의 교역 대상 고르기. 내 장수가 지금 있는 도시와 연결된 도시 중 trade 조항이 유효한 상대국 도시. 도시 키 순.
//   items가 비면 blocked에 이유를 준다(우리 국가 도시가 아님, 교역 조약 없음, 교전 중). 목록에 있어도 실행 때 다시 검사한다.
```

### 즉시 행동 처리 (검토 R62-1·R62-3, 2026-10-21 추가)

아래 요청 식별, 결과 회수, 처리 순서, 저장·재생 형식 절은 검토 R62-3R(2026-10-22)에 맞춰 더했다.
이 절의 입력 처리기, kind 이름, `applyTreatyInput`, 재생 세부는 그때 적은 후보다. 연결할 때 따르는 조건은 아래 [U62-5 기술 조율](#u62-5-기술-조율)에 있다.
고정된 것은 역할 경계다. API는 InputEvent 접수만 하고 양국 국고·외교 관계·조약 상태는 엔진 트랜잭션만 바꾼다.

즉시 행동도 게임 상태는 엔진만 바꾼다 (AGENTS.md §6, D-014 `docs/product/decisions.md:119`). 접수와 대기는 장수 생성
`apps/server/src/routers/general.ts:32-115`의 틀을 따르고 요청 식별과 결과 회수는 아래 절처럼 보강한다. 엔진 집행은 장수 생성 처리 `apps/engine/src/inputs.ts:15-96`과 같은 자리(리스와 World를 잠근 펜싱 트랜잭션)에서 한다.
InputEvent는 `PENDING`일 때 sequence·result가 null이고 `APPLIED`·`REJECTED`일 때 둘 다 있다는 기존 제약을 그대로 쓴다(`schema.prisma:267-284`).

| 단계 | 누가 | 하는 일 |
| ---- | ---- | ------- |
| 접수 | API | 행위 장수와 국가를 세션에서 정한다. 아래 [요청 식별과 재전송](#요청-식별과-재전송) 순서대로 같은 요청을 먼저 찾는다. 새 요청일 때만 입력 모양, 권한(군주·참모), 우리 국가가 당사자인지 보고 `PENDING` InputEvent 하나를 만든다. kind는 `treaty.propose`·`treaty.respond`·`treaty.break`, payload는 `requestId`를 뺀 요청 내용이다. 조약·국고·도시·관계는 읽기만 한다 |
| 대기 | API | 같은 요청 안에서 최대 5초 그 입력을 다시 읽는다. `APPLIED`면 `applied`, `REJECTED`면 기록된 이유 코드로 오류, 시간이 지나면 `pending`을 준다. 두 종료 상태 모두 돌려주기 직전에 세션을 다시 본다([결과 회수와 공개](#결과-회수와-공개)) |
| 집행 | 엔진 | [처리 순서와 sequence](#처리-순서와-sequence)대로 `PENDING` 입력을 꺼낸다. 행위 장수의 계정 상태, 소속, 직책, 조약 상태, 기한, 양쪽 비용, 도시 소유를 다시 검사하고 결과를 한 트랜잭션으로 쓴다 |
| 재조회 | 화면 | `pending`을 받거나 응답을 잃으면 같은 `requestId`로 `treaty.request`를 묻는다. `treaty.list`의 `pending`·`myRecent`는 목록 안내용이다 |

엔진 트랜잭션 하나에 함께 들어가는 것은 양국 국고의 비용 차감, 수락 즉시 집행되는 조항(종전의 관계 변경, 도시 이양의 소유 이전과
그 도시 장수의 수도 이동), 조약의 상태·시작·끝, 파기 때 `NationTrust`, 조약 기록, InputEvent의 `APPLIED`·`sequence`·`result`다.
검사 하나라도 실패하면 게임 상태는 그대로 두고 그 입력만 `REJECTED`와 이유 코드로 바꾼다. 정기 원조 이체와 기한 만료는 월간 정산 트랜잭션 안에서 한다.

- 판정은 `packages/rules/src/diplomacy/treaty.ts`의 순수 함수 `applyTreatyInput(state, input, { tick, sequence })` 한 곳에서 한다. 엔진 집행과 재생이 같은 함수를 부른다.
  접수 단계의 검사와 `quote`·`Allowed`는 화면 안내용이고 최종 판정이 아니다.
- 화면은 `applied`를 받기 전에는 진행 중·파기 완료·비용 지불을 표시하지 않는다. 접수만으로 성공을 보여 주지 않는다.
- 로그: 즉시 행동은 장수 턴이 아니므로 `GeneralLog`에 쓰지 않는다. `GeneralLog`의 `(worldId, generalId, tick)` 유일 제약(`schema.prisma:184-195`)은 풀지 않는다.
  기록은 조약 행(상태·시각·처리 sequence)과 InputEvent `result`에 남기고 외교 화면이 그것을 읽는다. 테이블 모양은 Codex가 정한다.
- 경합: 같은 국가의 다른 직책자가 같은 제안에 응답하거나 응답과 파기가 겹치면 둘 다 접수된다. 엔진이 먼저 꺼낸 입력만 집행되고
  뒤 입력은 상태가 맞지 않아 `REJECTED`(`TREATY_NOT_PROPOSED`·`TREATY_NOT_ACTIVE`)가 된다. 엔진이 트랜잭션 안에서 조약 상태를 다시 보므로 차감은 한 번만 일어난다.
- 기준 시점은 엔진의 검사 시점이다. 접수 뒤 국고가 줄었거나, 응답 기한이 지났거나, 이양할 도시를 잃었거나, 행위 장수가 직책·소속을 잃었거나 계정이 제재되면 `REJECTED`다.
  입력과 턴·정산의 순서는 아래 [처리 순서와 sequence](#처리-순서와-sequence)를 따른다.
- 재시작: commit 전에 엔진이 멈추면 트랜잭션이 롤백되어 입력은 `PENDING`으로 남고 다음 처리에서 한 번 집행된다. commit 뒤에는 `APPLIED`·`REJECTED`이므로 다시 꺼내지 않는다.
- 재생: `applyRecordedInput`(`packages/rules/src/replay.ts:67-107`)에 세 kind를 더한다. `APPLIED`는 기록된 `sequence`와 `result.tick`으로
  `applyTreatyInput`을 다시 불러 같은 결과(조약 ID, 양국 차감액, 상태)가 나오는지 확인한다. 다르면 재생 실패다. `REJECTED`는 지금처럼 건너뛴다.
  조약 ID는 입력 sequence에서 만들고 난수나 시각을 쓰지 않는다. 상태를 어디에 싣고 해시를 어떻게 지키는지는 아래 [저장·재생 형식](#저장재생-형식)이다.
- 위 접수·집행·재생은 모두 T2-07(Codex) 범위다. 다만 형식 정의와 여러 kind를 함께 꺼내는 처리기의 소유자는 U62-5에서 정한다.
  조약만의 독립 처리기나 조약 전용 origin 번호를 이 후보대로 붙이지 않는다.

#### 요청 식별과 재전송

- 화면은 행동 하나마다 `requestId`(UUID)를 만들고 결과를 받을 때까지 같은 값으로 다시 보낸다. 서버는 `idempotencyKey`를 `<kind>:<requestId>`로 적고
  기존 `@@unique([worldId, userId, idempotencyKey])`(`schema.prisma:273,281`)가 중복 행을 막는다. 지금 `general.create`는 서버가 `randomUUID()`로 키를 만들어
  (`general.ts:61`) 완료 뒤 재전송을 가려내지 못한다. 조약은 그 방식을 쓰지 않는다. PR #51의 T2-05 계획(검토 중)도 같은 `requestId` 방식을 제안했다.
- 접수 순서는 이렇다. 인증, 월드, 세션 장수를 먼저 본다. 다음으로 `(worldId, userId, idempotencyKey)`로 기존 입력을 찾는다.
  있으면 payload를 키 순서 없이 비교한다(`general.ts:48-53`처럼). 같으면 그 입력의 지금 상태를 돌려주고(PENDING이면 대기, 끝났으면 기록된 결과) 다르면 `CONFLICT`다.
  이 경로에서는 지금 직책과 조약 상태를 다시 검사하지 않는다. 그래서 완료 뒤 직책을 잃었거나 조약 상태가 바뀌어도 원 결과를 되찾는다.
  기존 입력이 없을 때만 권한·당사자 검사와 새 접수를 한다.
- 다른 `requestId`는 새 요청이다. 같은 장수가 같은 조약(제안이면 같은 상대 국가)에 `PENDING` 입력을 이미 갖고 있으면 `CONFLICT`(`요청을 처리하는 중입니다`)로 막는다.
  이전 입력이 끝난 뒤의 새 `requestId`는 정상적인 새 행동이다. 거절당한 뒤 다시 제안하는 경우가 그렇다.
- 같은 `requestId`를 다른 kind에 다시 쓰면 `CONFLICT`다. 접수는 `treaty.propose:<requestId>`와 `treaty.respond:<requestId>`를 함께 찾고 다른 kind 행이 있으면 새 입력을 만들지 않는다.
  그래서 정상 접수로는 한 `requestId`에 두 행이 생기지 않는다(2026-10-24 정정, [서버 첫 몫 계약](#서버-첫-몫-계약-2026-10-24-실제-claude-작성)).
- 거절 응답(accept false)이 집행되면 입력은 `APPLIED`, 조약은 `REJECTED`다. 화면은 목록에서 제안이 사라진 것으로 결과를 추측하지 않고 `requestId`의 결과를 본다.

#### 결과 회수와 공개

- `treaty.request({ worldId, requestId })`는 세션 사용자가 만든 입력만 읽는다. 다른 사용자의 값은 있어도 `NOT_FOUND`다.
  InputEvent는 재생 기록이라 지우지 않는다(`exportReplay`가 전부 내보낸다, `apps/engine/src/replay.ts:45-48`). 그래서 월드가 있는 동안 개수 제한 없이 회수된다.
  `myRecent` 최근 5건과 목록 폴링은 회수 계약이 아니다.
- 세션 재검사: `APPLIED`와 `REJECTED` 모두 결과를 돌려주기 직전에 세션이 유효하고 계정이 `ACTIVE`인지 본다. 대기 응답과 `treaty.request`가 같다.
  `general.ts:72-82`는 `APPLIED` 분기에서만 보므로 그 코드를 그대로 옮기면 거절 결과가 빠진다. 조약은 두 분기에 모두 넣는다.
  세션 만료, 로그아웃, 제재 뒤에는 `UNAUTHORIZED`이고 결과를 주지 않는다. 다시 로그인한 같은 사용자는 같은 `requestId`로 다시 묻는다.
- 소속·직책 변경: 요청한 사용자에게 원 결과의 상태와 이유 코드는 준다. `treaty`(조약 행)는 지금 세션 장수의 국가가 그 조약의 당사국일 때만 채우고 아니면 null이다.
  조약 내용은 당사국 장수만 본다는 공개 범위를 지키기 위해서다. 이유 문장에는 상대 국고·작위·기술·상업을 담지 않는다.

#### 처리 순서와 sequence

- 지금 엔진은 한 걸음에 장수 생성 입력 하나를 먼저 처리한다. 그런 입력이 없을 때만 기한이 된 턴이나 월간 정산을 처리한다(`apps/engine/src/turnLoop.ts:145-156`, `inputs.ts:20-24`).
  RUNNING이 아닌 월드에서도 생성 입력은 거절로 끝낸다(`turnLoop.ts:112-113`, `inputs.ts:37`). 줄 번호는 main `3e5b52a` 기준이다.
- 조약 입력도 이 자리에 들어간다. 모든 kind의 `PENDING` 입력을 id 순 한 줄로 꺼내 한 트랜잭션에 하나씩 처리한다. 같은 걸음의 턴·정산보다 먼저다.
  kind마다 우선순위를 따로 두지 않는다. RUNNING이 아닌 월드의 조약 입력은 장수 생성처럼 `WORLD_CLOSED`로 거절한다.
- sequence: 엔진은 입력 하나를 끝낼 때 `nextActionSequence`로 sequence를 받는다(`inputs.ts:30,91`). 조약 입력은 그 값을 판정 전에 받아
  그 걸음의 tick(`turnLoop.ts:138-142`)과 함께 `applyTreatyInput`에 넘긴다. 조약 ID는 이 sequence로 만든다. `APPLIED`·`REJECTED` 모두 같은 sequence와 `result.tick`을 적는다.
  재생은 `RecordedInput.sequence`(`packages/rules/src/replay.ts:19-26`)와 `result.tick`을 다시 계산하지 않고 같은 함수에 넘긴다.
- 그 걸음의 tick은 뒤 sequence로 실행되는 밀린 턴의 tick보다 클 수 있다(`turnLoop.ts:152-155`가 입력 뒤에 `nextTurnTick ≤ tick`인 턴을 꺼낸다).
  기한·만료는 기록된 tick으로만 판정하므로 재생은 같다. 엔진이 밀려 tick이 다음 월 경계를 넘었을 때 입력을 정산보다 먼저 처리할지는 U62-5에서 함께 정한다.
- 이 처리기는 T2-05(PR #51)와 T2-13(PR #63)의 새 입력도 함께 쓴다. 누가 만드는지는 U62-5다.

#### 저장·재생 형식

- 2026-10-23 main `3e5b52a` 기준: origin은 1 하나이고 archive는 1과 2(T1-26 종료 기록)다(`apps/engine/src/replay.ts:21-50`, 수출 `:92`, 거부 `:124-133`). 프리셋 월드의 origin 1 `initial`에는 T2-02 WIP의 `presetRules`가 실린다(`world/persistence.ts:27,48-59`).
  예약된 번호는 origin·archive 3(T4-03 확장)과 4(T2-05 인사)의 초안 예약, 부모가 번호만 잡은 5(T2-13 방침)다. 조약 번호는 없다(아래 U62-5 기술 조율). 해시는 `ReplayState` 전체라 빈 조약 필드를 더하기만 해도 해시가 바뀐다.
- 형식 1 월드(이 작업 전에 만든 월드)는 조약 상태를 만들지 않는다. `treaty.*` 쓰기는 `조약 기능 이전에 만든 월드입니다`로 거부하고 읽기는 빈 목록을 준다(초안, U62-6).
  `WorldState`·`ReplayState`에 조약 키가 생기지 않으므로 형식 1 골든과 12개월 재생 해시가 그대로다.
- 새 형식 월드는 조약과 신의를 `WorldState`의 선택 키로 둔다. 비어 있으면 키를 넣지 않는다(`packages/rules/src/model/world.ts:8-9,21-22`의 `commandMeta`·`nationTurns`와 같다).
  운반 경로를 모두 같은 키로 고친다. `loadWorld`(`apps/engine/src/worldLoader.ts:5-38`)가 조약 테이블을 읽고 `loadReplayState`(`monthly.ts:8-21`)가 그것을 담는다.
  `persistMonthly`는 원조 이체와 만료를 `runMonthly` 결과에서 DB에 쓴 다음(`monthly.ts:51-53`의 외교 행과 같은 자리) snapshot 해시를 만든다(`monthly.ts:54-62`).
  `exportReplay`(`replay.ts:38-75`)와 CLI `tools/replay.ts`는 형식 번호를 그대로 싣는다. `replayArchive`는 archive와 origin의 형식이 다르거나 모르는 번호면 거부한다.
- 형식 번호는 이 계획이 정하지 않는다. T2-05 계획은 2026-10-23 정정에서 origin·archive 4를 인사 형식으로 잡았고 T2-13 계획도 칸 모양과 활동 상태로 해시를 바꾼다.
  조약이 그 4를 함께 쓸지, 다음 미사용 번호를 쓸지, 여러 기능을 한 월드에 함께 켜는 형식을 어떻게 만들지와 입력 처리기의 단일 소유자는 U62-5에서 정한다. 그 전에는 조약 상태의 저장·재생을 구현하지 않는다.
  2026-10-23 부모 선택 뒤의 단일 기술안(최상위 `treaties`, capability origin·archive 6, 운반 경로 전체)은 아래 [기록 구조 검사와 형식 6 안](#기록-구조-검사와-형식-6-안)과 그 앞의 상태 보존 경로 표에 있다. 위 `loadWorld`·`loadReplayState`만으로는 턴 복제에서 키가 빠진다. 번호 6은 부모가 채택했고 runtime 구현과 공유 코드 권한은 아직 없다.

공개 범위 (T1-12와 원작 기준):

- 조약 목록과 내용은 당사국 장수만 본다. 쓰기(제안·수락·거절·파기)는 군주·참모만 한다 (T2-05).
  원작도 외교 문서를 자기 국가 안에서만 보여 주고 쓰기는 외교권자에게만 연다. 원작의 소속 기간 제한(오래 소속한 장수만 읽기)은 뺐다.
- 다른 국가가 보는 것은 `TrustRow`(파기 횟수와 마지막 파기 시각)뿐이다.
- `relation`은 우리 국가가 낀 관계만 준다. 원작 중원 정보도 다른 국가끼리의 불가침은 통상으로 가리고 교전·선포만 보여 준다.
  다른 국가끼리의 관계 표는 이번 범위가 아니다.
- `cost.theirs`는 상대가 낼 금액이다. 상대가 낼 수 있는지는 알려 주지 않는다. 상대 국고가 드러나기 때문이다.
- 상대 쪽 사정(상대 국고 부족, 상대 직책자 변동)으로 수락이 거절되면 이유 코드는 `COUNTERPART_UNAVAILABLE` 하나로 묶는다. 금액이나 원인은 알려 주지 않는다.
  그래도 수락 실패 자체에서 상대 국고가 모자란다는 추론은 남는다(아래 사용자 결정 U62-3).
- 비용의 국가 규모는 공개값으로만 계산한다. 첫 세 조항은 각 국가의 자기 도시 수만 쓴다(2026-10-23 승인). 작위(`level`)나 국고를 쓰면 상대 비용으로 비공개 값을 역산할 수 있다.
- `TradeTarget`에 상대 도시의 상업이나 예상 수익을 넣지 않는다. 수익 공식이 상대 도시 상업을 쓰므로 예상 수익만으로도 그 값이 드러난다.
  실제 수익은 실행 뒤 내 장수 로그로 본다. 이것은 원래 요구 기능이므로 가리지 않는다.

### 2026-10-23 사용자 승인과 착수 범위

이 절이 지금 기준이다. 아래 저장소 대조와 정책 정리 초안 두 절은 원 초안 `65bb3bc` 당시의 판단이고 이 절과 다르면 이 절을 따른다.

#### 승인된 것

첫 연결 조항은 `peace`·`nonAggression`·`note` 셋이다. 국가는 각자 공개된 자기 도시 수로 자기 비용을 계산한다. 비용은 금 `ceil(도시 수 × 100 × 불가침 개월 ÷ 12)`이고 종전·기록만 담은 조약은 0이다.
수락 순간 양쪽 국고에서 함께 차감하며 한쪽이라도 모자라면 어느 쪽도 차감하지 않는다(U62-3 중 차감 시점).

NPC 국가는 위 세 조항만 담은 제안 가운데 자기 비용을 낼 수 있는 것을 수락한다. 다른 조항이 하나라도 있으면 거절하고 먼저 제안하지 않는다(Q1).
관계가 `WAR`·`DECLARED`인 두 나라의 불가침은 같은 조약에 `peace`가 있어야 한다(Q7).

#### 승인으로 넓히지 않는 것

통행·정기 원조·도시 이양·교역은 AC-M2-06·AC-M2-14의 전체 목표로 남고 조건은 미결이다. 아래 정책 정리 초안의 나머지 추천도 승인되지 않았다.
다른 조항의 비용과 기간, Q2 여러 기간, Q3 통행이 끝난 장수의 이동, Q4 수도 이양, Q5 원조 범위, Q6 교역 계수, U62-2c 대치, 기존 관계 처리, U62-2b 기존 예턴 전환, U62-6 형식 1 정책이 그렇다.
U62-3의 알림은 `COUNTERPART_UNAVAILABLE` 하나로 묶는 초안 그대로 두고 새 제품값을 정하지 않는다.
한 조약에 불가침이 둘 이상인 경우, 조항이 없는 조약, 규모에 장수 수를 넣을지, `WAR`·`DECLARED`가 아닌 관계의 종전, 불가침 중인 두 나라의 새 불가침도 승인 범위 밖이다.

#### 지금 착수할 수 있는 몫

부모가 지금 허용한 구현은 새 순수 모듈과 단위 시험이다. Codex는 `packages/rules/src/diplomacy/treaty.ts`와 `packages/rules/src/diplomacy/treaty.test.ts` 두 새 파일만 만들고 승인된 세 조항의 계산과 판정을 시험한다.
함수 이름과 세부 모양은 Codex가 정한다. 위 즉시 행동 처리 절의 `applyTreatyInput`은 연결 단계의 함수이고 이번 몫이 아니다.

| 판정 | 받는 것 | 지킬 것 |
| ---- | ------- | ------- |
| 비용 | 자기 도시 수, 불가침 개월 하나(없으면 없음) | 정확한 금액. 불가침이 없으면 0. 조항 배열에서 불가침을 찾거나 합하지 않는다 |

좁은 helper로 시작한다. 비용 함수는 단일 불가침 개월만 받으므로 중복 불가침과 빈 조약의 정책을 정하지 않는다. 개월은 조항 표의 1~120 정수만 받는다.
수락 차감 결과의 거절 이유는 내부 값이다. 화면과 API에 어떤 코드로 보일지는 위 공개 범위의 초안을 연결 단계에서 따른다.

NPC 판단은 공통 검증(조항 모양, 개월 범위, 관계 조건)을 대신하지 않는다. 판단 함수가 검증 결과를 받거나 안에서 같은 검증을 불러 검증에 실패한 조약은 NPC가 수락할 수 없게 한다.

금액은 오차 없이 계산한다. 중간 계산은 BigInt 정수로 한다. `곱 = 도시 수 × 100 × 개월`을 BigInt로 구하고 올림은 `(곱 + 11) / 12`의 정수 몫이다. 부동소수 나눗셈 오차가 금액에 들어가지 않는다.
범위 검사는 최종 반환 금액이 안전 정수(`Number.MAX_SAFE_INTEGER`) 안인지 본다. 중간 곱이 안전 정수를 넘어도 최종 금액이 그 안이면 받는다.
도시 수와 국고 금은 0 이상의 안전 정수, 개월은 1~120 정수다. 이를 어기거나 최종 금액이 범위를 넘으면 잘못된 입력으로 돌려주고 금액을 만들지 않는다. 순수 API의 입력과 반환은 `number`이고 BigInt는 함수 안의 연산에만 쓴다.
이 경계는 반환값을 `number`로 표현할 수 있는 범위를 지키는 계산 안전 장치다. 새 게임 상한이 아니고 도시 수 상한도 두지 않는다.
DB 국고 칸(`schema.prisma:102`의 `Int`)에 들어가는 범위는 연결 단계에서 본다.

하지 않는 것은 `WorldState` 필드 추가, DB·파일·네트워크, 현재 시각, 새 난수, M1 국가 명령(`nation.ts`) 교체, 기존 파일 수정이다. 승인된 100 밖의 밸런스 값을 새로 만들지 않고 `balance.ts`에도 넣지 않는다.
이 몫은 연결 이전 단계다. 끝나도 AC-M2-06·AC-M2-14 완료가 아니고 API·엔진·재생 검증을 통과한 것도 아니다.

```ts
type TreatyApplied = // InputEvent APPLIED의 result. 입력은 자기 조약 하나만 바꾸고 다른 조약을 닫지 않는다
  | { outcome: 'PROPOSED'; tick: number; treatyId: string; respondByTick: number }
  | { outcome: 'ACCEPTED'; by: 'HUMAN' | 'NPC'; tick: number; treatyId: string; cost: { from: number; to: number }; endTick: number | null }
  | { outcome: 'DECLINED'; by: 'HUMAN' | 'NPC'; tick: number; treatyId: string };
type TreatyRejected = { tick: number; code: TreatyRejectCode; message: string }; // InputEvent REJECTED의 result
type TreatyRejectCode =
  | 'WORLD_CLOSED' | 'ACTOR_INACTIVE' | 'NO_GENERAL' // 엔진의 DB 검사
  | 'BAD_INPUT' | 'CLAUSE_NOT_CONNECTED' | 'NO_PERMISSION' | 'BAD_TARGET' | 'NOT_PARTY' | 'TREATY_NOT_PROPOSED'
  | 'EXPIRED' | 'TREATY_RELATION' | 'INSUFFICIENT_GOLD' | 'COUNTERPART_UNAVAILABLE'; // 순수 판정
```

payload에는 비용, 제안국, 행위 장수, 도시 수가 없다. 엔진이 상태에서 다시 구한다. 응답 기한은 조항 결정의 6개월 고정이라(위 조항 결정 절) `expiresInMonths`를 받지 않는다. API 입력에 그 칸이 남으면 API가 6만 받고 payload에는 싣지 않는다.
API는 아래 [기록 구조 검사](#기록-구조-검사와-형식-6-안)의 raw schema를 지난 것만 접수하고 조항을 API 계약 `Clause` 선언 순서(peace, nonAggression, passage, tribute, trade, cityTransfer, note)로 안정 정렬한 뒤 정렬 포함 저장 schema를 지난 payload를 저장한다. 그래서 같은 요청 재전송의 payload 비교가 순서에 흔들리지 않는다.
구조가 정상인 조약의 도메인 모양 검사는 엔진이 한다. 조항이 없거나 같은 종류가 둘 이상이거나 개월·note 길이가 범위 밖이면 `BAD_INPUT`이라 승인된 단일 불가침 개월 형태가 유지된다. 그다음 통행·원조·교역·이양이 있으면 `CLAUSE_NOT_CONNECTED`이고 AC 분모에서 빠지지 않는다.
관계 판정은 출처 있는 것만 쓴다. peace는 `WAR`·`DECLARED`에서만 받고(`TreatyTarget` 주석) 그 관계의 불가침은 peace가 있어야 한다(Q7). 관계 없음의 불가침은 받는다. note는 관계와 무관하다. `NON_AGGRESSION` 중의 peace와 새 불가침은 `TREATY_RELATION`이다.
제품 효과가 갈리는 반례는 이 마지막 칸뿐이다. 시나리오 불가침(`bootstrap.ts:258`) 중인 두 나라는 만료 전에 조약으로 연장할 수 없다. 승인 범위 밖 목록에 이미 있다.

순수 판정은 `diplomacy/treaty.ts`에 더할 `applyTreatyInput(state, { kind, generalId, payload }, { tick, sequence })`가 한다. `{ ok: true; state; result: TreatyApplied }`나 `{ ok: false; result: TreatyRejected }`를 돌려준다.
기록 구조 검사는 이 함수 앞에서 끝나 있다. 함수의 검사 순서는 도메인 모양(`BAD_INPUT`, `CLAUSE_NOT_CONNECTED`), 장수·소속·권한, 상대(당사국이 `state.nations`에 없으면 `BAD_TARGET`)·당사자·상태·기한(아래 T-1), 관계, 제안의 기한 표현 가능성(아래 [상한·자료 크기·조회 후속](#상한자료-크기조회-후속)의 채택 계약), 비용이다. 비용은 각 국가의 `state.cities` 소유 수로 `calculateTreatyFee`를 부른다. 검증을 통과한 것만 NPC 판단으로 가므로 `canNpcAcceptTreaty`의 `valid`는 늘 실제 검증 결과이고 `cost`는 NPC 자기 도시 수로 낸 값이다.
받는 국가가 NPC면(`nations[to].isNpc`, `nation.ts:74`와 같은 플래그) 제안 입력 하나가 응답까지 끝낸다. 제안국 국고가 자기 비용보다 적으면 `INSUFFICIENT_GOLD`로 REJECTED이고 조약 행이 없다. NPC가 거절하면 APPLIED `DECLINED`·`by: 'NPC'`, 차감 없음이다. 수락하면 `settleTreatyFees` 뒤 APPLIED `ACCEPTED`·`by: 'NPC'`다.
이 경로의 userId는 제안한 사람 그대로다. NPC 사용자나 system 입력을 만들지 않고 `chooseNationTurn`도 고치지 않아 NPC가 먼저 제안하는 길이 없다. 결정은 상태만으로 정해져 재생이 같은 함수로 다시 얻는다.
사람 상대 제안은 APPLIED `PROPOSED`이고 비용을 묶지 않는다. 수락 응답은 그 tick의 도시 수로 비용을 다시 계산한다. 자기 쪽이 모자라면 `INSUFFICIENT_GOLD`, 상대 쪽이면 `COUNTERPART_UNAVAILABLE`(U62-3 초안 코드)로 REJECTED이고 조약은 PROPOSED 그대로다. 거절 응답은 비용과 무관하게 APPLIED `DECLINED`·`by: 'HUMAN'`이다.
국가 ID는 재사용되지 않는다(`support.ts:61-73`이 삭제 전에 `nextNationId`를 잡는다).

수명과 집행 시점. 조약 입력은 자기 행 하나만 만들거나 바꾼다. 기한·불가침 끝·당사국 소멸로 닫는 일은 월간 diplomacy 단계 한 곳에서만 하므로 후속 입력이 없어도 월 정산만 지나면 닫힌다. 아래 `T`는 `TICKS_PER_MONTH`, `B`는 월간 정산 tick이다.

| 사건 | Treaty 상태와 칸 | Diplomacy |
| ---- | ---------------- | --------- |
| 사람 상대 제안 | PROPOSED, 상태에 남음. `proposedTick = tick`, `respondByTick = tick + 6T`, start·end null | 그대로 |
| 수락(사람 응답·NPC 수락), 불가침 있음 | ACTIVE, 남음. `startTick = tick`, `endTick = tick + 개월 × T` | peace가 있으면 그 쌍 행을 지우고 `NON_AGGRESSION`·`untilTick = endTick`을 넣어 정렬(`nation.ts:77-87`과 같은 식) |
| 수락, 불가침 없음(종전만·note만·종전+note) | ACTIVE, 남음. `startTick = tick`, `endTick` null(원 계약 `endAt` null) | peace면 그 쌍 행 삭제, note만이면 그대로 |
| 거절(사람·NPC) | REJECTED, 빠짐. `closedSequence` = 입력 sequence | 그대로 |
| 월간 B, PROPOSED이고 `respondByTick ≤ B` | EXPIRED, 빠짐. `closedSequence` = 월간 sequence | 그대로 |
| 월간 B, ACTIVE이고 `endTick !== null`·`endTick ≤ B` | ENDED, 빠짐. 같은 월간 sequence | 같은 `settleDiplomacy`가 같은 B에서 행을 지운다(`untilTick > tick`만 남김, `:104`) |
| 월간 B, 당사국 하나가 `state.nations`에 없음 | PROPOSED→EXPIRED, ACTIVE→ENDED. 같은 월간 sequence | 관계 행은 이미 `removeNation`(`support.ts:70-73`)이 장수 명령 tx에서 지웠다 |

불가침 끝은 M1과 같은 원값이다. `untilTick`은 `settleDiplomacy` 밖에서 읽는 곳이 없어(저장소 검색에서 `monthly/index.ts:104`뿐) 실제 집행 끝은 원값 이상의 첫 월 경계 `ceil(endTick ÷ T) × T`다. 예: tick 1500에 1개월 수락 → `endTick`·`untilTick` 11500. 월간 10000은 관계와 ACTIVE를 둘 다 남기고 20000은 둘 다 닫는다. 수락 tick 10000이면 20000에서 닫는다.
DTO는 DB status 그대로와 `endTick` 원값, 위 식의 `endsAtTick`을 싣는다. 그래서 표시·집행·DB가 같은 B에서 바뀐다.
`endTick`이 null인 ACTIVE(종전·기록만)는 기간 만료가 없고 상태에 남는다. DTO는 원 계약대로 ACTIVE, `endAt`·`monthsLeft` null이다. 위 표의 당사국 소멸 월간 종료는 이 조약에도 그대로 걸린다. 그 밖에 끝내는 길은 원 계약의 파기(남은 조항 종료, `brokenTreaties += 1`, 파기 국가의 다른 조약 상대에게 알림, 신의 기록 공개)이고 파기 후속에서 연결한다. 새 벌점이나 신의 값은 만들지 않는다.
`WorldState`에는 PROPOSED·ACTIVE만 둔다. 닫힌 조약의 상태와 `closedSequence`, 실제 차감액 `costFrom`·`costTo`는 DB Treaty 행과 InputEvent `result`에만 남는다.

순수 `settleTreaties(state, tick)`는 `diplomacy/treaty.ts`에 두고 `settleDiplomacy`가 관계 정리 뒤 같은 `next`에 부른다. 남은 조약은 id 순 그대로 두고 비면 `treaties` 키를 지운다. 키가 없으면 아무것도 하지 않아 조약 없는 월드의 월간 해시가 그대로다.
엔진 `persistMonthly`(`monthly.ts:33`)와 재생 `runReplayAction`(rules `replay.ts:57-60`)이 둘 다 `runMonthly`를 부르므로 같은 함수가 수명을 정한다. 새 월간 단계도, API의 게임 상태 쓰기도 없다.
`persistMonthly`는 diplomacy 행을 다시 쓴 뒤(`:52-53`), `world.update`와 `loadReplayState` snapshot(`:54-55`) 전에 같은 모듈의 순수 `treatyClosures(before, next)`를 부른다. 이 함수는 before에 있고 next에 없는 id를 PROPOSED→EXPIRED, ACTIVE→ENDED로 돌려준다.
엔진은 그 각각을 `updateMany({ where: { worldId, id, status: 이전 상태 }, data: { status, closedSequence: sequence } })`로 쓰고 count가 1이 아니면 throw해 월간 tx 전체를 롤백한다. 그러면 snapshot의 `loadWorld`가 PROPOSED·ACTIVE만 읽어 재생 상태와 해시가 같다.
당사국이 사라진 뒤 첫 월 정산까지는 조약 행이 열린 채 남고 관계 행은 없다. 그 사이 응답은 `BAD_TARGET` REJECTED이며 엔진과 재생이 같은 열린 행을 가진다. `removeNation`·`persistCommandState`와 37개 명령은 고치지 않는다.
겹침: 같은 쌍의 다른 PROPOSED 수락은 그때 관계로 다시 판정하므로 `NON_AGGRESSION` 중의 새 불가침과 peace는 `TREATY_RELATION`이다. note만은 관계를 건드리지 않는다. M1 종전·불가침 제의도 `NON_AGGRESSION` 행을 덮지 않는다(`nation.ts:58-59`). 그래서 기존 관계를 짧게 만드는 경로가 없다.

T-1(응답 기한, 부모가 원 계약의 정확 tick 기한을 수용). 응답 기한은 `respondByTick = 제안 tick + 6T`의 정확한 tick이다. 응답 입력은 PROPOSED를 확인한 뒤 `tick ≥ respondByTick`이면 수락이든 거절이든 REJECTED `EXPIRED`다.
월간 정산은 `respondByTick ≤ B`인 첫 B에서 조약을 EXPIRED로 닫는다. 그 사이 DB status는 PROPOSED로 남고 DTO는 원 계약의 `canAccept`·`canReject`에 원 `DenyCode`의 `{ ok: false, code: 'EXPIRED' }`를 싣는다. 새 DTO 칸, 응답 시간 연장, 새 사용자 질문이 없다.
예: tick 1500 제안 → `respondByTick` 61500. 월간 60000 뒤에는 PROPOSED이고 tick 65000 응답은 REJECTED `EXPIRED`이며 월간 70000에서 EXPIRED로 닫혀 상태에서 빠진다. 응답의 정확 기한과 위 불가침의 월 경계 만료(`ceil(endTick ÷ T) × T`)는 다른 조건이다.

엔진은 새 `apps/engine/src/treatyInput.ts`의 `processTreatyInput(tx, world, event, tick)`이고 중앙 선택자만 부른다. 리스와 World를 잠근 트랜잭션(`turnLoop.ts:108-110`) 안에서 아래 순서로 처리한다.
처음에 PENDING 행의 구조를 본다. `World.treatyFormat`이 1이고 kind가 등록표에 있어야 한다. `userId`, `generalId`(양의 안전 정수), `idempotencyKey`(`<kind>:` 접두), 저장 payload가 아래 [기록 구조 검사](#기록-구조-검사와-형식-6-안)의 PENDING 행 검사를 지나야 한다. 이 단계는 sequence·result가 null인 행을 보며 완성 envelope 1과 result 4는 결과를 쓰기 직전의 완성 기록 검사에서 본다.
API가 만들 수 없는 행이므로 하나라도 어기면 status와 무관하게 throw해 롤백하고 입력은 PENDING으로 남는다. sequence를 받지 않고 새 REJECTED 기록도 만들지 않는다(정책 사본 `inputs.ts:128`의 throw와 같은 처리). 구조가 정상이면 다음으로 월드가 RUNNING인지 보고 아니면 `WORLD_CLOSED`로 거절한다.
User를 `FOR SHARE`로 잠가 ACTIVE를 보고(`inputs.ts:36-39`) General을 `FOR UPDATE`로 잠가 `userId`가 같은지 본다(사본 `inputs.ts:129-135`).
그다음 `loadWorld`로 양국 gold·도시·관계·조약을 읽는다. `nextActionSequence`를 판정 전에 받고 `applyTreatyInput`을 부른다.
ok면 양국 `Nation.gold`, 그 쌍의 Diplomacy 행만, 그 입력의 Treaty 행 하나(제안은 생성, 응답은 `status: 'PROPOSED'` 조건 갱신), InputEvent를 `updateMany({ where: { id, status: 'PENDING' } })` count 1(사본 `inputs.ts:108-112`)로 APPLIED·sequence·result로 함께 쓴다. ok가 아니면 InputEvent만 REJECTED·sequence·result다.
throw는 전부 롤백되고 입력은 PENDING으로 남는다. 국고는 엔진만 쓰므로(AGENTS.md §6) World 잠금으로 직렬화된다. 차감은 비용 ≤ 국고일 때만 하므로 `Int` 칸(`schema.prisma:102`)을 넘지 않는다.
API는 InputEvent만 쓰고 같은 `(worldId, userId, idempotencyKey)`(`schema.prisma:333`)를 먼저 찾는다. 권한·당사자는 안내용으로 미리 보고 최종 판정은 엔진이 한다. `quote`의 `cost.theirs`는 상대 도시 수로만 계산하고 `canAccept`는 우리 국고만 본다. NPC 거절은 원인을 싣지 않는다.
엔진 모듈의 정확한 서명, sequence를 받는 시점, 저장 대상, 남은 공개 선행은 아래 [엔진 조약 모듈 인터페이스 착수](#엔진-조약-모듈-인터페이스-착수-2026-10-23-실제-claude-작성) 절이 정한다. 이 문단과 다르면 그 절을 따른다.

```prisma
enum TreatyStatus { PROPOSED ACTIVE REJECTED EXPIRED ENDED } // BROKEN은 파기 후속에서 더한다
model Treaty {
  worldId        String
  id             Int     // 제안 입력 sequence. API treatyId는 String(id)
  fromNationId   Int     // Nation FK 없음
  toNationId     Int
  clauses        Json    // 정렬된 FirstClause[]
  status         TreatyStatus
  proposedTick   Int
  respondByTick  Int
  startTick      Int?
  endTick        Int?    // 불가침이 있을 때만
  closedSequence Int?    // 상태를 끝낸 입력 또는 월간 정산의 sequence
  costFrom       Int?    // ACCEPTED 실제 차감액
  costTo         Int?
  world          World @relation(fields: [worldId], references: [id], onDelete: Cascade) // 월드 삭제만 따라 지운다
  @@id([worldId, id])
  @@index([worldId, status, id])
  @@index([worldId, fromNationId, id])
  @@index([worldId, toNationId, id])
}
// World에 treatyFormat Int?(null이면 꺼짐)와 treaties Treaty[]를 더한다. 다른 모델은 바꾸지 않는다.
```

Nation FK를 두지 않는 이유는 국가 멸망 때 `commandPersistence.ts:78-83`이 Nation 행을 지우고 기존 관계가 `onDelete: NoAction`(`schema.prisma:307-308`)이라 FK가 삭제를 막거나 cascade로 기록을 지우기 때문이다. 사라진 국가의 이름·색은 RemovedNation(`schema.prisma:362-372`)에서 읽는다.
NationTrust는 파기가 없는 첫 세 조항에 필요 없어 파기 후속으로 미룬다. 신의 기록 목표는 그대로다.

상태는 최상위 `WorldState.treaties?: TreatyState[]`다(부모 선택 B). `ext` 조각이나 확장 명령 binding에 싣지 않고 그 등록표에 보존을 기대지 않는다. `commandMeta`·`nationTurns`(`world.ts:14-15`)처럼 비면 키를 넣지 않는다.
원소는 PROPOSED·ACTIVE만이고 id 오름차순이며 위 DDL에서 world·cost·closedSequence를 뺀 칸이다. `clauses`는 API 계약 `Clause` 선언 순서로 정렬된 배열이다. `WorldInit`에는 이 키를 두지 않는다.
DB 쪽은 World FK만 두고 원 국가 ID를 그대로 적는다. 국가 삭제가 지난 조약 행을 지우거나 막지 않는다(위 Nation FK 문단).
`hashState`는 객체 키만 정렬하고 배열 순서는 그대로이며 `undefined`면 throw한다(`shared/src/node/hashState.ts:3-24`). 그래서 정렬과 null 표기를 엔진과 재생이 똑같이 한다.
`persistMonthly`는 위 수명 문단의 조약 status 쓰기 하나만 snapshot 앞에 더한다.

##### 기록 구조 검사와 형식 6 안

아래는 부모가 고른 A(단일 capability 합성), B(최상위 키), C(명시 선택한 새 월드만 켬)를 한 계약으로 적은 것이다. 부모 재검토용이며 구현 권한이 아니다.
모든 조약 기록에 정확 구조 검사와 게임 의미 검사를 따로 건다. 구조 검사는 status와 code에 앞선다. 그래서 `WORLD_CLOSED`·`ACTOR_INACTIVE`·`NO_GENERAL` 같은 이유 코드로 구조 파손을 가릴 수 없다.
`diplomacy/treaty.ts`가 등록표 `TREATY_INPUTS` 하나를 export하고 kind마다 payload 구조 schema, outcome별 APPLIED 정확 키, 허용 거절 코드를 둔다. API 접수, 엔진 PENDING 처리, `supervisor.ts:164` 조건, archive 6 합성 판독기가 모두 이 표를 import한다.
검사는 단계마다 따로다. 한 validator로 모든 단계를 묶지 않는다.

- API raw 검사. 요청 payload에 아래 3의 schema에서 정렬 조건만 뺀 raw schema를 건다. 지나지 않으면 InputEvent 없이 `BAD_REQUEST`다. 정렬되지 않은 raw 조항은 정상 요청이다.
- API 정규화. raw를 지난 조항을 API 계약 `Clause` 선언 순서로 안정 정렬하고 3의 strict 저장 schema(정렬 포함)로 다시 본다. 이 검사를 지난 payload만 PENDING으로 쓴다.
- PENDING 행 검사(엔진). DB의 PENDING 행은 `worldId`·`userId`·`generalId`·`kind`·`idempotencyKey`·`payload`와 null인 `sequence`·`result`다. 이 검사는 행위자·kind·idempotency 접두·world와 저장 payload 3만 보고 완성 envelope의 6키나 sequence를 요구하지 않는다. 저장 payload가 정렬되지 않았으면 API가 만들 수 없는 행이라 지금처럼 throw다.
- 완성 기록 검사. 엔진이 APPLIED·REJECTED를 쓰기 직전에 sequence·status·result를 채운 `RecordedInput` 6키 envelope를 `validateTreatyRecord`(아래 1~4)에 넣고 실패하면 throw한다. 판독기도 같은 함수를 쓴다. 그래서 판독기가 거부할 기록은 commit되지 않는다.

구조 검사는 아래 1~4다. 하나라도 어기면 status·code와 무관하게 판독기는 거부하고 엔진은 throw해 롤백한다.
1. envelope는 정확 키 `sequence`·`generalId`·`kind`·`status`·`payload`·`result`다. `sequence`는 1 이상 `MAX_ACTION_SEQUENCE` 이하 정수, `generalId`는 양의 안전 정수(null 거부, 조약 입력은 접수 때 세션 장수가 늘 있다), status는 APPLIED·REJECTED다.
2. kind가 `treaty.`로 시작하면 origin 6의 `capabilities.treaty`가 `{ version: 1 }`이어야 하고 kind가 등록표에 있어야 한다. 모르는 `treaty.*`와 조약 기능이 없는 기록의 조약 kind는 REJECTED여도 거부한다.
3. payload는 kind의 strict schema다. `treaty.propose`는 정확 키 `toNationId`(양의 안전 정수)·`clauses`(배열)이고 각 조항은 API 계약 `Clause` 일곱 종류 가운데 하나의 정확 키 모양이며(정수 칸은 안전 정수, `text`는 문자열, `cityKeys`는 안전 정수 배열) 선언 순서로 정렬돼 있다. 정렬 조건은 저장된 canonical payload에만 걸고 API raw 검사에는 걸지 않는다(위 단계 구분). `treaty.respond`는 정확 키 `treatyId`(앞자리 0 없는 십진 양의 정수 문자열)·`accept`(boolean)다. null payload, 객체 `toNationId`, 미등록 조항 kind, 남는 칸(행위 장수, 비용, 제안국, `expiresInMonths`)은 모두 구조 파손이다.
4. result는 객체이고 status와 무관하게 `result.tick`은 0 이상 안전 정수다. 소수, 음수, 문자열, `Number.MAX_SAFE_INTEGER` 초과는 APPLIED든 REJECTED든 구조 파손이다. 그 위에 APPLIED면 아래 표의 outcome별 정확 키 집합이다. REJECTED면 정확 키 `{ tick, code, message }`이고 `message`는 빈 문자열이 아니며 `code`는 그 kind의 허용 목록에 있다.

의미 검사 5~7은 구조 검사를 지난 기록에만 건다.
5. `inputs`의 `result.tick`은 `replay.monthlyTick` 이상이다. 입력은 밀린 월간보다 먼저 처리되므로 `monthlyTick + T`를 상한으로 쓰지 않는다. 상한은 아래 [상한·자료 크기·조회 후속](#상한자료-크기조회-후속)의 기존 Int 상한이다. `afterEnd`의 조약 입력은 REJECTED `WORLD_CLOSED`만 받고 `tick`은 `end.tick` 이상이다. 이 afterEnd 조건은 독립 리뷰를 근거로 부모가 채택했고 archive 6의 조약 kind에만 건다. archive 1·2·5에는 소급하지 않는다.
6. REJECTED는 상태를 바꾸지 않고 건너뛴다. 권한·종료·DB 사유(`WORLD_CLOSED`·`ACTOR_INACTIVE`·`NO_GENERAL`·`NO_PERMISSION` 등)와 도메인 사유(`BAD_INPUT` 등)를 재생에서 다시 만들지 않는다. 구조가 정상인 `clauses: []`의 REJECTED `BAD_INPUT`은 이렇게 통과하는 도메인 거절이다.
7. APPLIED는 기록된 `sequence`·`result.tick`·`generalId`로 `applyTreatyInput`을 불러 `ok`이고 `hashState(result)`가 기록과 같아야 한다. 아니면 재생 실패다. 그래서 `cost`·`endTick`·`respondByTick` 조작은 해시 불일치로 걸린다.

형식별 기존 동작은 그대로 둔다.
- archive 1·2(origin 1)는 모르는 kind의 REJECTED를 건너뛰는 지금 동작(rules `replay.ts:86`)과 모르는 APPLIED 거부(`:135-136`)를 그대로 쓴다. 조약을 켠 월드는 origin 6이라 이 두 형식에 조약 입력이 실리지 않는다.
- archive 5(origin 1)는 `validatePolicyRecordedInput`(`policy/replay.ts:91-130`)이 kind enum(`:41-55`, `:92`)을 먼저 보고 status(`:95-98`)를 본다. 엔진 `validatePolicyArchive`가 `inputs`와 `afterEnd` 전부에 부르고(엔진 `replay.ts:249-253`) `applyRecordedInput`이 REJECTED skip(rules `replay.ts:86`) 전에 부른다(`:85`). 그래서 조약 kind와 모르는 kind는 REJECTED여도 거부된다. 이 순서, 알려진 kind의 REJECTED에서 payload를 보지 않는 관례(`policy/replay.ts:95-98`), F 전후 정책 투영을 소급해 바꾸지 않는다.
- archive 6(origin 6)은 새 합성이다. kind 등록표 하나가 kind마다 소유 기능 하나를 정하고 그 기능의 검사만 부른다(T4-03 E8 (f)). 공통 `turns.set`·`general.create`는 handler 하나이고 정책 F 전후 모양은 정책 규칙을 따른다. 정책 kind는 정책이 켜지고 sequence ≥ F일 때만 받는다. 조약·인사 kind는 정적 capability가 있으면 정책 F 전에도 받는다. 정책 5 전체 validator를 조약·인사 kind에 걸지 않는다. 정책·공통 kind의 REJECTED는 archive 5처럼 사유 모양만 보고 payload를 보지 않는다.
- E8 (f) 보완. E8 (f)는 지원 kind의 REJECTED를 사유 모양 `{ code, message }`만으로 통과시킨다. 새 조약 kind는 그보다 강하게 위 구조 검사 1~4를 status와 무관하게 건다. 정상 구조의 권한·종료 사유 REJECTED만 DB 재검사 없이 통과한다.

번호 안은 `ORIGIN_CAPS = 6`, `ARCHIVE_CAPS = 6` 하나다. archive 6은 origin 6만, origin 6은 archive 6에서만 받는다. archive 1·2·5는 origin 1만 받는 지금 판정 그대로이고 미채택 3·4를 쓰지 않는다.
Codex가 main `3e5b52a`, 통합 `6439d94`, T4-03 `2bc0223`·`900f78e`, 정책 `2c34e20`, 인사 `6702c9d`의 `apps/engine/src`·`packages/rules/src`·`docs/plans`에서 번호 6 할당과 형식 6 예약 표현을 찾았고 모두 0건이었다. 검색식·ref·결과는 증거 폴더의 `format6-reservation-scan.json`에 있다.
이 결과는 그 핀 시점에 중복이 없다는 확인이고 다른 브랜치와 미커밋 상태까지 확정한 것은 아니다. 부모가 이 exact ref 충돌 0 범위에서 `ORIGIN_CAPS = 6`·`ARCHIVE_CAPS = 6`을 기술 선택으로 채택했다. runtime에는 아직 구현되지 않았고 공유 코드 수정 권한도 없다(아래 소유 배정).

- origin 6은 `{ version: 6, initial, initialStateHash, resourceHash, capabilities: { version: 1, treaty?: { version: 1 }, ext?, personnel? } }`다. T4-03 E8의 단일 capability descriptor에 `treaty` 정적 칸을 더했다. 기능 칸이 하나도 없거나 모르는 키가 있거나 `capabilities.version`·`treaty.version`이 1이 아니면 거부한다. `ext`·`personnel` 칸의 모양은 E8과 T2-05가 정한다.
- 해시는 E8 식을 따른다. `initialStateHash = hashState(initial)`이고 `WorldInit`에 조약이 없어 빈 조약은 initial과 해시에 들지 않는다. `resourceHash = hashState({ 지금 resourceHash 입력 다섯 칸, capabilities })`라 descriptor가 해시 입력에 들어간다. origin 1의 `resourceHash(initial)` 식은 그대로다.
- archive 6은 archive 2 모양(`origin`·`config`·`inputs`·`months`·`end`·`afterEnd`)에 `version: 6`이다. config 정확 키는 `endYear`·`outcomeFromSequence`와 선택 칸 `policy`(archive 5와 같은 `{ version: 1, fromSequence, turnTermMinutes }`)다. 정책 F = 0, F > 0, 사람 기준 T의 뜻은 archive 5와 같다.
- 켜기(C). 첫 연결 개발 단계에서는 생성 때 조약을 명시 선택한 새 월드만 켠다. 그 월드는 생성 트랜잭션에서 `World.treatyFormat = 1`과 origin 6을 함께 쓰고 이후 바꾸지 않는다.
  기존 월드에는 조약을 더 켜지 않는다. `treatyFormat`은 null이고 원래 origin(1이거나 다른 capability를 담은 6)과 그 capability를 그대로 둔다. 조약을 고르지 않은 새 월드도 `treatyFormat` null·조약 꺼짐이다. 다른 정적 capability가 없으면 origin 1이고 `ext`·`personnel`을 골랐으면 `treaty` 칸 없는 origin 6이다. 아래 대조와 같은 판정이다. 정책 전환은 origin을 덮어쓰지 않고 조약 켜기에 정책 F를 다시 쓰지 않는다. 이것은 이 개발 단계의 범위다. 기존 월드 지원이나 MVP 전체에서 영구히 빼는 결정이 아니며 기존 월드 upgrade와 U62-6은 여기서 정하지 않는다.
- 대조. `treatyFormat = 1`이면 origin 6이고 `capabilities.treaty`가 `{ version: 1 }`이어야 한다. `treatyFormat`이 null이면 origin 1이거나 `treaty` 칸 없는 origin 6이어야 한다. 엔진 시작, `exportReplay`, `replayArchive`·`replayToEnd`가 이 대조를 쓰기와 투영보다 먼저 한다. 어긋나면 엔진은 멈추고 수출은 파일을 내지 않는다.
- `exportReplay`는 origin 6이면 archive 6(정책 F가 있으면 `config.policy`)을, origin 1이면 지금처럼 F null은 archive 2, F 숫자는 archive 5를 낸다. 지금 판독기는 1·2·5 밖의 archive 번호(사본 `replay.ts:163`)와 origin 1 밖의 origin(`:164`)을 거부하므로 옛 판독기는 archive 6을 받지 않는다.

조약이 없는 형식 1·2·5 월드는 키도 입력도 없어 골든과 12개월 해시가 같다. 확장 binding은 조약 보존과 무관하다. ext·personnel 칸의 세부와 정책 helper 분리(E8 (f) 인계 조건)는 그 계약 담당의 몫이다.

##### 상한·자료 크기·조회 후속

U62-5 기술 조율의 한정 후속이다(2026-10-23, 부모 요청). 구현·실행하지 않았고 새 게임 상한이나 숫자를 고르지 않는다.
근거는 Codex가 로컬을 좁게 읽은 증거 폴더 `review-aaeb-two-fixes/bounds-query-audit.json`과 아래 소스다. 줄 번호는 이 작업실 기준이고 사본이라고 적은 것은 정책 `2c34e20`이다.

tick과 sequence:

- 기존 제약. 라이브 tick은 0 이상 `2_147_483_647 − T`다(`turnLoop.ts:66,144`, T = 10000). Diplomacy `untilTick`(`schema.prisma:305`)과 위 Treaty DDL의 tick 칸은 `Int`, 정책 `policyTickSchema`는 0~2147483647(사본 `policy/replay.ts:8`), sequence 상한은 2147483647이다(사본 엔진 `replay.ts:27`, `inputs.ts:85`).
- 엔진 poll은 한 번에 64걸음 또는 250ms까지이고(`turnLoop.ts:25-26,94`) 걸음마다 입력 하나, 턴 하나, 월간 하나 가운데 하나를 30초 제한 트랜잭션 하나로 한다(`:106-289`). 이 예산은 걸음 사이에만 보고 `advanceTo`(`:65-69`)는 쓰지 않는다.
- 입력 tick은 시계 tick이고(`clock.ts:26-43`, `turnLoop.ts:138-142`) 입력은 밀린 월간보다 먼저 처리된다(`:145`가 `:156`보다 앞). 그래서 입력 tick은 `monthlyTick + T`보다 클 수 있고 그 값을 상한으로 쓰면 정상 입력을 거부한다.
- 안. 기록 구조 검사는 `result.tick`을 0 이상 안전 정수로만 본다(구조 4). 실제 집행과 저장은 기존 라이브 상한과 `Int` 상한을 다시 쓴다. `respondByTick = tick + 6T`와 `endTick = 수락 tick + 개월 × T`는 Treaty 칸과 `untilTick`에 들어가야 하므로 안전 정수 검사로는 모자란다. 경계에서 기간을 잘라 맞추거나 응답 6개월·불가침 개월을 줄이지 않는다.
- 예. 라이브 상한 안의 tick 2147423647에 사람 상대로 1개월 불가침을 제안하면 `respondByTick` 2147483647은 들어가지만 마지막 수락 tick의 `endTick` 2147493646은 넘는다.
- 예전 후보는 사람 상대 제안에 `(respondByTick − 1) + 개월 × T ≤ 2147483647`만 보고 실패 코드를 부모 기술 검토에 남겼다. 이 후보는 아래 채택 계약으로 바뀌었다. `Int` 저장만 보면 닫을 월 경계가 엔진 범위 밖에 남는다.

기한 표현 가능성 계약(2026-10-23 부모 채택). Codex 감사 `adapter-boundary-audit/report.txt`·`arithmetic.json`의 산술을 Claude가 다시 계산해 맞췄다.

- 값. `M = 2147483647`(`Int` 최댓값), `T = 10000`, `L = M − T = 2147473647`(기존 엔진 tick 상한), `Bmax = floor(L ÷ T) × T = 2147470000`(엔진이 도달하는 마지막 월 경계). 넷 모두 기존 엔진 범위에서 나온 값이고 새 제품 한도가 아니다.
- 조건. 제안 tick `p`, `D = p + 6T`, 실제 불가침 개월 `m`(1~120, 없으면 무료)이다. 사람 상대 무료는 `D ≤ Bmax`, 사람 상대 불가침은 `Emax = (D − 1) + m × T ≤ Bmax`다. NPC 상대 무료는 `D ≤ M`, NPC 상대 불가침은 `D ≤ M`과 `p + m × T ≤ Bmax`다. NPC는 같은 입력에서 응답하므로 열린 응답 기간이 없고 `D ≤ M`은 필수 칸 `respondByTick`을 저장하기 위한 조건이다. 120개월을 모든 제안에 미리 적용하지 않고 그 제안의 `m`을 쓴다. 6개월·`m`을 줄이거나 clamp하지 않는다.
- 끝점. 사람 무료 `p` 2147410000(`D = Bmax`), 사람 1개월 2147400001(마지막 수락 2147460000, `endTick = Bmax`), 사람 120개월 2146210001(마지막 수락 2146270000, `endTick = Bmax`), NPC 무료와 NPC 1~4개월 2147423647(`D = M`), NPC 120개월 2146270000이다. 각 값 + 1은 표현 불가다.
- `Int` 저장만 되는 반례. 사람 1개월 `p` 2147413648은 `D` 2147473648, 마지막 수락 2147473647, `endTick` 2147483647로 모두 저장되지만 닫을 월 경계 2147490000이 `L`과 `M`을 넘는다. 사람 120개월 2146223648, 사람 무료 2147423647(`D = M`)도 같다. 셋 다 이 계약에서 표현 불가다.
- 순수 helper. `treaty.ts`가 `canRepresentTreatyProposal(options: Readonly<{ tick: number; nonAggressionMonths: number | null; npc: boolean }>): boolean`을 export한다. 호출자는 도메인 모양과 관계 검사를 통과한 실제 조항의 불가침 개월(없으면 null)과 상대 국가의 NPC 여부를 넣는다. `tick`이 정수가 아니거나 음수이거나 `L`을 넘으면, `nonAggressionMonths`가 1~120 정수나 null이 아니면, `npc`가 boolean이 아니면 throw다. 정상 인자에서 파생 기한만 위 조건을 어기면 false다.
- 매핑. `applyTreatyInput`의 propose는 관계 검사 뒤, 사람 상대 PROPOSED 반환과 NPC 비용·응답 전에 이 helper를 부르고 false면 propose의 기존 허용 코드 `BAD_INPUT`으로 거절한다. 그래서 `D` 계산을 지금 자리(`9e591a2` `treaty.ts:327`)에서 관계 검사(`:353`) 뒤로 옮긴다. 새 거절 코드는 없고 respond 허용 코드에 `BAD_INPUT`을 넣지 않는다. 거절 문장에 상대 국고를 넣지 않는다. 넓은 `RangeError` catch로 거절을 만들지 않는다.
- 응답. 이 검사를 지난 사람 상대 제안은 `tick < respondByTick`인 모든 수락의 `endTick`이 `Bmax` 이하라 정상 응답에서 기한 산술 실패가 없다. respond는 찾은 PROPOSED의 `proposedTick`·`respondByTick`이 새 제안으로 만들 수 없는 값(`respondByTick ≠ proposedTick + 6T`, `proposedTick`의 helper 결과가 false 등)이거나 context가 잘못되면 throw하고 엔진은 롤백한다. 이를 `EXPIRED` 같은 정상 응답 거절로 바꾸지 않는다. 순수 함수는 자기가 읽는 조약 행만 보며 전체 `WorldState` 로더 검증을 대신하지 않는다.
- 같은 정의. API 접수 전 확인과 엔진 판정이 같은 helper를 쓴다. API 확인은 안내용이고 엔진 판정을 대신하지 않는다. `applyTreatyInput`의 live context tick은 0~`L`이고 기록 validator의 저장 tick 0~`M`(위 구조 4·의미 5)과 다른 검사다.
- 별도 경계. Prisma `22003`·`P2020`, 트랜잭션 timeout, `nextActionSequence` 고갈은 이 계약의 거절이 아니고 각각 throw·롤백이다.

- 기간 없는 ACTIVE(종전·기록만)는 당사국이 남아 있는 동안 쌓인다. 월간 canonical 상태 전체와 그 해시, 매 턴 일반 복제가 옮기는 양이 변경 요청 제한이나 poll 64걸음·250ms로 묶인다는 증명은 없다. 요청 제한은 사용자당이고 조약은 시간에 따라 누적된다.

#### U62-5 기술 조율

부모가 Codex와 정한다. 사용자 제품 질문으로 올리지 않는다. 기술 결정이라는 이유로 게임 효과가 바뀌는 순서를 승인된 것으로 보지 않는다.

- 형식 번호(2026-10-23 부모 전달). main이 실제로 쓰는 것은 origin 1과 archive 1·2뿐이다(`apps/engine/src/replay.ts:22,28,43,126-127`). 3(T4-03 확장)과 4(T2-05 인사)는 초안 예약이다. 부모는 origin·archive 5를 T2-13 방침 몫으로 번호만 예약했다.
  capability, 구버전 해시 투영, 기존 월드 upgrade, 여러 기능을 함께 쓰는 형식은 아직 수용되지 않았다. T2-13의 실제 형식과 단일 처리기 구현은 지금 별도 채팅이 맡는다.
  이 문서는 조약의 형식 번호와 재생 capability를 확정하지 않는다. 인사·조약·방침·확장의 결합도 이 조율에 남는다.
- 부모의 현재 통보(2026-10-23). 방침 archive·origin 5 envelope는 방침 kind만 받고 인사·조약 kind는 거부한다.
  T4-03은 composite 900번대와 후속 형식을 준비 중이다. 확장·방침·인사의 합집합, 기능별 handler, 단일 중앙 dispatch를 담지만 채택·연결되지 않았고 조약을 넣을지도 정하지 않았다.
  그래서 예전 계획의 독립 조약 처리기와 별도 origin 번호를 그대로 붙이지 않는다. 당시 이 문서는 새 번호나 capability를 고르지 않았다.
  그 뒤 부모가 단일 capability 합성(A)을 골랐고 [기록 구조 검사와 형식 6 안](#기록-구조-검사와-형식-6-안)이 `ORIGIN_CAPS`·`ARCHIVE_CAPS` 6 안을 낸다. 부모가 기존 exact ref 충돌 0 범위에서 이 번호를 채택했다. runtime에는 아직 구현되지 않았다.
- 첫 세 조항의 API·엔진 연결 조건. 연결 전에 단일 소유자, InputEvent의 kind·payload·result 모양, 조약·양국 국고·외교 관계 상태가 해시에 들어가는 방식, 재생 handoff를 먼저 맞춘다.

rules root는 `selectWorldCapabilities`·`projectTreatyRows`와 타입 `WorldCapabilities`만 내보낸다(`index.ts:38`). `WorldCapsRow`·`TreatyStorageRow`는 `capsWorld.ts:13,66`에만 있고 root export가 없다. 서버는 private 경로를 import하지 않는다.
같은 트랜잭션에서 읽은 Prisma World 행을 selector에 그대로 넘기고 타입 이름이 필요하면 `Parameters<typeof selectWorldCapabilities>[0]`와 `ReturnType`을 쓴다. 서버가 `{ treaty: { version: 1 } }`나 ready 표지를 만들지 않는다.

selector는 `treatyFormat`을 null이나 1로만 받는다(`capsWorld.ts:31`). `replayOrigin`이 null이거나 version 1이면 legacy이고 그때 `treatyFormat`이 1이면 throw다(`:43-54`).
나머지 origin은 `parseCapsOrigin`이 정확 키, descriptor, `initial`의 `treaties` 키 부재를 보고(`replayCapabilities.ts:70-89`) descriptor의 `treaty` 유무가 `treatyFormat = 1`과 같아야 한다(`capsWorld.ts:56-57`). `selectSupportedCapabilities`는 조약만 담은 descriptor만 받고 ext·personnel이 섞이면 throw다(`replayCapabilities.ts:91-108`). 그래서 `caps` 결과는 언제나 조약 on이고 legacy는 off다. 정책 F와 `actionSequence` 대조도 한다(`capsWorld.ts:33-42`).
selector는 `initialStateHash`·`resourceHash`를 다시 계산하지 않고 `initial`은 plain object인지만 본다. 월드를 만들거나 승격하지도 않는다. 그래서 selector 통과는 origin hash와 초기 상태의 유효성이나 enabled-world factory의 증거가 아니다.
서버는 `treatyFormat = 1`만으로 조약 on을 인정하지 않고 preset이나 지금 국가 상태로 capability를 만들지 않는다. 엔진 `processTreatyInput`이 `treatyFormat`만 보는 것(`treatyInput.ts:25`)은 호출자가 cap6 선택을 끝냈다는 전제라 서버 판정의 근거로 쓰지 않는다.

worldId를 뺀 Treaty 저장 행은 12칸이다. `id`·`fromNationId`·`toNationId`·`clauses`·`status`·`proposedTick`·`respondByTick`·`startTick`·`endTick`·`costFrom`·`costTo`·`closedSequence`다(`capsWorld.ts:66-93`, `schema.prisma:71-91`). 이전 준비 보고의 13칸은 틀렸다.
`projectTreatyRows`는 모든 행에 strict 12칸 schema, ID 중복, 같은 당사국, `TREATY_INPUTS['treaty.propose'].payloadSchema`를 건다(`capsWorld.ts:99-104`). 이 payload schema는 조항 구조와 canonical 순서만 본다(`treaty.ts:100-104`). 빈 조약, 종류 중복, 개월 범위, note 길이, 연결하지 않은 조항은 `domainClauses`(`:324-336`)의 몫이라 여기서 걸리지 않는다.
닫힌 status는 `closedSequence`가 null이 아닌지만 보고 `continue`한다(`capsWorld.ts:105-108`). 열린 행만 납부·마감 칸과 `validateTreatyState`를 지나 반환된다. 그래서 이 함수는 닫힌 행의 도메인, status별 비용과 시각, `closedSequence`와 id의 관계, 기한을 보장하지 않고 닫힌 행을 돌려주지도 않는다. 서버는 이 함수를 열린 행 하나의 검사에만 쓴다.

#### 닫힌 저장 행 검사 (순수 선행 1)


입력은 worldId를 뺀 저장 행 12칸 그대로이고 원래 status를 받는다. 어긋나면 throw하고 통과하면 같은 값의 새 객체를 돌려준다. 조항은 원소마다 복사하며 정렬하거나 NFC로 바꾸지 않는다. PROPOSED·ACTIVE도 throw이고 열린 행은 `projectTreatyRows`가 맡는다.
private `domainClauses`·`checkedTickAdd`·`LAST_MONTHLY_TICK`과 공개 `canRepresentTreatyProposal`·`treatyRespondByTick`을 그대로 써야 하므로 `treaty.ts`에 둔다. T4-03 소유 `capsWorld.ts`는 고치지 않는다. 서버에 같은 규칙을 복사하지 않고 status를 PROPOSED·ACTIVE로 바꾼 행이나 꾸민 record·actor·context로 기존 validator를 우회하지 않는다. `validateTreatyState`·`projectTreatyRows`의 의미는 그대로다.
아래 M·L·Bmax·T는 위 [기한 표현 가능성 계약](#상한자료-크기조회-후속)의 값(2147483647, 2147473647, 2147470000, 10000)이고 p는 `proposedTick`, D는 `respondByTick`, m은 불가침 개월이다.

| 검사 | REJECTED | EXPIRED | ENDED |
| ---- | -------- | ------- | ----- |
| 키·범위 | 정확 12칸, worldId 칸은 거부. `id`·두 국가·`closedSequence`는 1~M 정수, 두 국가는 다름. tick·비용 칸은 0~M 정수 | 같음 | 같음 |
| 조항 | canonical 구조·순서이고 `domainClauses`가 null(첫 세 조항만, 비지 않음, 종류 중복 없음, 개월 1~120, note 1~300 code point) | 같음 | 같음 |
| 응답 기한 | p ≤ L이고 `respondByTick === treatyRespondByTick(proposedTick)` | 같음 | 같음 |
| 제안 시각 | `canRepresentTreatyProposal`에 p, m(없으면 null), `npc: true` | 같은 helper에 `npc: false`. PROPOSED는 사람 상대에서만 생긴다(`treaty.ts:222`) | 아래 시작·끝 조건이 NPC 조건을 함의한다 |
| 시작·끝 | 둘 다 null | 둘 다 null | `p ≤ startTick < D`, `startTick ≤ Bmax`. 불가침이 있으면 `endTick = startTick + m × T`이고 Bmax 이하, 없으면 null |
| 비용 | 둘 다 null | 둘 다 null | 둘 다 0~M 정수 |
| `closedSequence` | id 이상 | id 초과 | id 초과 |

`closedSequence`는 writer마다 다르다. NPC 즉시 거절은 제안 sequence로 행을 만들어 `closedSequence = sequence = id`다(`treatyInput.ts:132-150`). 사람 거절은 뒤 응답 sequence이고(`:168-172`) EXPIRED·ENDED는 그 뒤 월간 sequence다(`treatyState.ts:63-70`, 월간도 같은 `nextActionSequence`, `turnLoop.ts:188`).
그래서 REJECTED는 id 이상, 나머지 둘은 id 초과가 공통 보장이다. REJECTED에서 `closedSequence === id`로 NPC 여부를 갈라 다른 기한을 걸지 않는다. 한 월간 sequence를 여러 행이 함께 쓰므로 행 사이 유일성이나 정렬도 보지 않는다.

NPC 기한 대조. 순수 판정은 NPC 상대 제안에 `D ≤ M`과 `p + m × T ≤ Bmax`만 요구한다(`treaty.ts:217-218`). 실제 writer는 NPC DECLINED 이력에 `treatyRespondByTick(result.tick)`을 쓰고(`treatyInput.ts:144`) ACCEPTED는 상태의 `checkedTickAdd(tick, 6)` 값을 저장한다(`treaty.ts:406`, `treatyInput.ts:153-156`). `treatyRespondByTick`은 p를 0~L로 보고 `p + 6T ≤ M`을 요구한다(`treaty.ts:205-209`).
그래서 닫힌 행 전부에 이 함수와 같은 기한을 걸어도 정상 NPC 과거가 깨지지 않는다. 받을 수 있는 가장 큰 p는 2147423647이고 D는 2147483647 = M이다. p 2147423648은 이 함수가 throw하지만 순수 판정에서도 NPC 조건이 false라 `BAD_INPUT`이 되어 조약 행이 생기지 않는다. 기존 validator 리뷰 `352768e8`이 통과로 본 무료 NPC ACTIVE(p 2147423647, D 2147483647, end null)와 NPC 120개월(p 2146270000, end 2147470000)도 같은 결론이다.
반례는 사람 PROPOSED 경계를 닫힌 행 전부에 걸 때 생긴다. 무료 NPC ACTIVE의 p 2147423647은 D가 Bmax보다 13647 커서 사람 무료 조건 `D ≤ Bmax`를 어긴다. NPC 1개월 거절의 같은 p는 `D − 1 + T` = 2147493646 > Bmax다. NPC 120개월 p 2146270000은 `D − 1 + 120T` = 2147529999 > Bmax다. 셋 다 정상 기록이라 REJECTED와 ENDED에는 사람 조건을 걸지 않는다.
사람 조건은 NPC 조건을 함의한다. 무료는 `D ≤ Bmax`면 `D ≤ M`이고 불가침은 `D − 1 + mT ≤ Bmax`면 `p + mT ≤ Bmax − 59999`다. 그래서 `npc: true`가 사람·NPC 두 경로의 공통 하한이다.

ENDED의 `startTick ≤ Bmax`는 도달 가능한 마감 조건이다. `validateTreatyState`의 ACTIVE는 `startTick`을 L까지 받는다(`treaty.ts:194`). 실제 ACTIVE의 시작은 NPC면 p(최대 2147423647)이고 사람이면 D 미만이라 Bmax를 넘지 않는다. ENDED는 시작 tick 이상이고 Bmax 이하인 월 경계에서만 닫힌다. 입력이 같은 걸음의 밀린 월간보다 먼저 처리되므로(위 처리 순서 절) 그 경계가 시작 tick과 같을 수는 있다.
예를 들어 p 2147423647, start 2147473647, end null인 행은 ACTIVE 검사를 지나지만 ENDED로는 받지 않는다. EXPIRED는 사람 조건 `D ≤ Bmax`가 닫을 월 경계를 이미 보장한다.

정적 저장 검사는 저장 칸만으로 만들 수 있는 기록인지 본다. 실제 역사와 맞는지는 재생 대조만 보장한다. 지금 국가의 `isNpc`나 행위자의 지금 소속으로 과거가 NPC였는지 추정하지 않는다. 서버는 비용을 지금 도시 수로 다시 계산하지 않고 저장된 실제 차감액을 보여 준다.

#### 과거 완료 기록 decoder (순수 선행 2)

`validateTreatyRecord`는 `context.treaty`와 `monthlyTick`을 먼저 요구하고(`treaty.ts:258-259`) `result.tick < monthlyTick`이면 throw하며(`:282`) `endTick`이 있으면 `WORLD_CLOSED` REJECTED만 받는다(`:273-281`).
지금 `world.monthlyTick`이나 `WorldResult.endedTick`을 넣으면 정상 옛 APPLIED와 종료 전 기록을 파손으로 판정한다. `monthlyTick: 0` 같은 꾸민 context를 넣고 그 통과를 재생 검증처럼 적는 것도 안 된다. 그래서 context 판정과 로컬 자기 일관성을 나눈 공개 helper를 둔다.

`treaty.ts:260-272`(envelope 6키, kind별 strict payload, status별 strict result, `result.tick` ≤ M)는 private `parseTreatyRecord`로 옮긴다. `:283-304`(treatyId, PROPOSED 기한, `by`, ACCEPTED `endTick`, 적용한 제안의 도메인, 응답 `accept`)는 private `assertTreatyRecordConsistency`로 옮긴다.
`validateTreatyRecord`는 context 검사, parse, context tick 검사, 일관성 검사의 지금 순서를 그대로 지켜 같은 입력에 같은 반환과 같은 throw를 낸다. 서명, root export, 기존 시험 기대값, `replayCapabilities.ts:141-146`과 엔진 `treatyInput.ts:69-73`의 호출은 바꾸지 않는다.
`decodeTreatyRecord`는 parse와 일관성 검사만 부르고 capability·`monthlyTick`·`endTick`을 보지 않는다. status는 APPLIED·REJECTED만 받으므로 PENDING은 envelope에서 throw다. 반환은 검사한 record의 새 객체다.
decoder 통과는 기록 자체에 모순이 없다는 뜻이다. 그 기록이 당시 상태에서 실제로 그 결과를 냈는지는 위 기록 구조 검사의 의미 검사 7(재생)의 몫이고 decoder 통과를 재생 PASS로 세지 않는다. 조약 capability는 서버가 selector로 따로 본다.

`requireTreatyWorld`는 `selectWorldCapabilities(world)`를 부른다. 그 throw는 `INTERNAL_SERVER_ERROR`이고 legacy는 `PRECONDITION_FAILED`(`조약 기능을 쓰지 않는 월드입니다.`)다. 이 문장은 오류 문구이고 U62-6의 기존 월드 정책을 정하지 않는다.
`checkTreatyRow`는 `row.worldId === world.id`를 본 뒤 `const { worldId, ...storage } = row`로 worldId를 뺀 12칸을 status로 나눠 검사한다. 열린 행은 `projectTreatyRows([storage])`가 원소 하나를 돌려줘야 하고 닫힌 행은 `validateClosedTreatyRow(storage)`를 부른다. 그다음 위 `actionSequence` 대조를 한다. 실패는 고정 문장의 `INTERNAL_SERVER_ERROR`이고 행 값을 싣지 않는다. catch는 이 검사 호출만 감싼다.
`toTreatyDetail`은 보는 국가가 null이거나 두 당사국이 아니면 null이다. `closedSequence`, worldId, 어느 국가의 국고·작위·기술·상업도 담지 않는다.
`TrustRow`·`NationRef`·`GameDate`·`ClauseView`·`monthsLeft`와 전체 `TreatyRow`는 이 DTO에 없다. 0이나 null로 채운 가짜 칸도 두지 않는다.

`requireLiveSession`은 `session.findFirst({ where: { id: sessionId, userId, expiresAt: { gt: at }, user: { status: 'ACTIVE' } } })`가 없으면 `UNAUTHORIZED`다. `protectedProcedure`(`trpc.ts:16-28`)는 `ctx.user` 존재와 변경 요청 횟수만 보고 요청 시작의 `authenticate`(`auth/session.ts:12-28`)는 대기·회수 시점을 보장하지 않는다. 그래서 두 함수가 이 검사를 먼저 한다.
`at`은 라우터가 `ctx.now`에 경과 시간을 더해 넘긴다(`routers/general.ts:90`과 같은 식). leaf는 현재 시각을 직접 읽지 않는다. 라우터의 5초 대기는 반환 직전마다 `readTreatyRequest`를 다시 불러 같은 검사를 지난다.

| 2 | `requireLiveSession` | `UNAUTHORIZED` |
| 3 | `requireWorld(tx, worldId, true)`의 World `FOR UPDATE`(`game/queries.ts:7-12`) | `NOT_FOUND` |
| 4 | `requireTreatyWorld(world)` | 위 두 코드 |
| 5 | `TREATY_INPUTS[kind].normalizePayload(payload)`(strict raw, NFC, 안정 정렬, 저장 schema) | `BAD_REQUEST`, InputEvent 없음 |
| 6 | `(worldId, userId)`에서 `idempotencyKey`가 두 정확 key인 행 | 두 행, 또는 다른 kind 한 행은 `CONFLICT`. 같은 kind면 저장 payload를 `payloadSchema`로 읽고(실패는 `INTERNAL_SERVER_ERROR`) 키 순서 없이 깊이 비교한다. 같으면 `{ created: false }`, 다르면 `CONFLICT`. 이 갈래는 7~12를 보지 않는다 |
| 7 | `world.status`가 ENDED가 아님 | `PRECONDITION_FAILED` |

| 9 | `nationId`가 있고 `canExecuteNationCommand(officerLevel, 'nation_pact')` | `FORBIDDEN`, 문장은 권한 없음 하나 |
| 10 | respond만. `Number(treatyId)` ≤ M, 그 Treaty 행이 있고 raw `fromNationId`·`toNationId`에 장수 국가가 있음. 그다음 `checkTreatyRow` | 범위 밖·없음·비당사국은 같은 문장의 `NOT_FOUND`. 검사 실패는 `INTERNAL_SERVER_ERROR` |
| 11 | 같은 장수·같은 kind의 PENDING 가운데 propose는 같은 `toNationId`, respond는 같은 `treatyId` | `CONFLICT`(`요청을 처리하는 중입니다.`). 그 payload 파손은 `INTERNAL_SERVER_ERROR` |
| 12 | `inputEvent.create` 하나. worldId, 세션 userId, 장수 id, kind, `${kind}:${requestId}`, 정규화 payload, PENDING, `sequence`·`result` null | throw. 넓은 catch로 다른 결과를 만들지 않는다 |

7은 기술 선택이다. ENDED 월드의 PENDING을 찾는 `supervisor.ts` 조건이 아직 조약 kind를 보지 않아 새 접수가 끝나지 않는 일을 막는다. PREOPEN·PAUSED는 접수하고 엔진이 `WORLD_CLOSED`로 끝낸다. 10은 안내용이고 상태·기한·`NOT_PARTY`는 엔진이 판정한다. 비당사국에는 조약이 있는지도 알리지 않는다.
API는 PENDING·`sequence` null·`result` null인 InputEvent 하나만 만든다. `nextActionSequence`와 World·Nation·City·General·Diplomacy·Treaty·리스·heartbeat 쓰기는 없다.
지금 중앙 소비자는 조약 kind를 꺼내지 않는다(`apps/engine/src` `inputs.ts`·`turnLoop.ts`·`supervisor.ts`에 조약 kind 없음). 그래서 접수한 입력은 PENDING으로 남는다. 엔진 완료는 Ext 소유 중앙 연결의 후속이고 이 leaf와 시험은 접수·회수까지만 증명한다.

회수는 `RepeatableRead` 트랜잭션 하나에서 부른다(`routers/general.ts:51-59`의 조회와 같다). World를 잠그지 않고 지금 `monthlyTick`·`endedTick`·장수 상태로 결과를 다시 판정하지 않는다.

| 순서 | 검사 | 결과 |
| ---- | ---- | ---- |
| 1 | `requestId`는 UUID | 아니면 `BAD_REQUEST` |
| 2 | `requireLiveSession` | `UNAUTHORIZED`. 완료 결과도 주지 않는다 |
| 3 | `requireWorld(tx, worldId)`, `requireTreatyWorld` | `NOT_FOUND`, 위 두 코드 |
| 4 | `(worldId, userId)`에서 두 정확 key | 0행은 `NOT_FOUND`, 2행은 `CONFLICT`. 행 kind가 key 접두와 다르면 `INTERNAL_SERVER_ERROR` |
| 5 | PENDING | `sequence`·`result` null, `generalId` 양의 안전 정수, payload strict여야 한다. 어기면 `INTERNAL_SERVER_ERROR`. 통과하면 `pending` |
| 6 | APPLIED·REJECTED | `decodeTreatyRecord({ sequence, generalId, kind, status, payload, result })`. 실패는 `INTERNAL_SERVER_ERROR`. REJECTED는 기록의 `code`와 `message`(`reason`) |
| 7 | APPLIED만 | `treatyId`의 Treaty 행이 없으면 `INTERNAL_SERVER_ERROR`. `checkTreatyRow` 뒤 `general.findUnique({ worldId_userId })`의 국가로 `toTreatyDetail`. 장수가 없거나 무소속이거나 비당사국이면 `treaty: null` |

회수는 `requireGeneral`을 부르지 않으므로 장수가 없어도 자기 요청을 찾는다. 정상 옛 APPLIED는 `world.monthlyTick`보다 오래됐거나 월드가 ENDED여도 회수된다. 세션·제재는 결과 공개 권한으로만 다시 본다.
상태, `outcome`, `treatyId`, 거절 `code`·`reason`은 요청한 사용자 본인에게 지금 소속과 무관하게 준다. InputEvent id·`userId`·`idempotencyKey`·`sequence`·`result.tick`과 상대 국고·작위·기술·상업은 DTO와 오류 문장에 없다. 권한이 없는 접수는 9에서 끝나므로 respond 대상의 존재나 당사국 여부를 알 수 없다.
`accept: false`가 집행되면 InputEvent는 APPLIED·`outcome: 'DECLINED'`이고 조약 행은 REJECTED라 회수는 `applied`다. 엔진 거절(InputEvent REJECTED, 예를 들어 `EXPIRED`·`TREATY_NOT_PROPOSED`)은 `rejected`다.

nonce. `requestId`는 클라이언트 UUID이고 서버가 매번 `randomUUID()`로 만들지 않는다. key는 `treaty.propose:<UUID>`와 `treaty.respond:<UUID>` 둘뿐이다. `treaty.request`에 kind 인수를 더하지 않고 schema에 새 unique도 더하지 않는다. 기존 `@@unique([worldId, userId, idempotencyKey])`(`schema.prisma:447`)를 쓴다.
접수의 6이 다른 kind 행을 `CONFLICT`로 막으므로 정상 접수로는 두 행이 생기지 않는다. 두 행이 있으면 접수와 회수 모두 임의 한 건을 고르지 않고 `CONFLICT`로 끝낸다. 남의 사용자 값과 없는 값은 회수에서 `NOT_FOUND`이고 다른 사용자가 같은 UUID를 쓰면 자기 행이 따로 생긴다.
다른 `requestId`의 같은 상대 제안이나 같은 조약 응답은 PENDING이 있는 동안 `CONFLICT`이고 끝난 뒤의 새 `requestId`는 새 입력이다(위 요청 식별과 재전송).

첫 몫에 넣지 않는 것. `quote`의 `problems`는 조항 도메인과 관계 판정이 필요하고 그 판정은 private `domainClauses`·`relationAllows`다. 서버가 그 규칙을 복사할 수 없고 이 묶음은 그 공개 helper를 만들지 않으므로 `quote`는 후속이다. 그때도 `cost.theirs`는 상대 도시 수로만 계산하고 상대 국고와 지불 가능성은 결과·오류에 싣지 않는다.
`routers/treaty.ts`, `router.ts` mount, 5초 대기, 전체 `AppRouter` DTO, `treaty.list`와 쪽 나누기, `pending`·`myRecent`, Trust, 파기, 교역, 나머지 네 조항의 DTO도 후속이다.
schema·migration, 중앙 `inputs.ts`·`turnLoop.ts`·`supervisor.ts`·`monthly.ts`, CLI, enabled-world factory, 프론트, 기존 `readView`·`resolver.ts`·인사 파일, `capsWorld.ts`는 이 몫에서 고치지 않는다. 인사의 `PersonnelReady` 같은 ready 표지나 가짜 helper import도 쓰지 않는다. 자동 검증·global harness·강제 위임을 새로 만들지 않는다.
