# T2-10 메시지·공지 화면, 실시간 갱신

> 대기열: T2-10 · AC: AC-M2-04, AC-M2-07 (화면) · 구현: Claude · 리뷰: Codex
> 선행: T2-09 (API)

## 계획 (Claude)

### 목표

메시지를 범위별로 읽고 쓰며 내 턴 결과·새 메시지·월간 정산이 새로고침 없이 2초 안에 화면에 반영된다.

### 범위

- `apps/web/src/realtime/useWorldEvents.ts`: SSE 연결 → 알림 종류별로 TanStack Query 무효화
- 메시지 패널 (메인 오른쪽 접이식 + `/w/:id/messages` 전체 화면), 위쪽 띠 안 읽음 배지
- 국가 공지 팝업 (바뀐 뒤 첫 접속 1회), 국가 정보 화면의 공지 칸과 고치기, 전체 탭 위 월드 공지
- T1-16의 "남은 시간 0초에 다시 조회" 임시 방식(`apps/web/src/layout/GameLayout.tsx:29-36`)을 SSE로 대체

### 하지 않는 것

알림 소리·브라우저 알림(M3 웹 푸시), 메시지 검색.

### 결정

| 알림 | 다시 조회할 것 |
| ---- | -------------- |
| `turn.result` | `home.get`, `turns.get`, `records.general` |
| `message.new` | `message.list`(해당 범위), `message.unread` |
| `monthly.done` | `world.summary`, `home.get`, `world.map` |
| `offer.new`, `treaty.new` | 발령 상자, 외교실 |
| `notice.updated` nation | `notice.nation.get` |
| `notice.updated` world | `notice.world.list` |
| `ready` | 지금 화면의 query 전부 |

- 연결 상태를 위쪽 띠에 작게 표시 (연결됨 · 다시 잇는 중). 끊긴 동안에도 화면은 쓸 수 있다.
- 재조회는 서버 데이터만 바꾼다 (검토 R63-4). `ready` 전체 재조회와 `turn.result`의 `turns.get` 갱신이 지도 선택, 메인 30칸의 미저장 초안,
  메시지 작성 칸, 공지 고치기 초안을 지우지 않는다. 초안은 query 캐시와 따로 둔다.
- 30칸 초안을 고치는 중에 서버 revision이 바뀌면 초안을 덮지 않고 서버 예턴이 바뀌었다고 알린다. 저장은 초안의 revision으로 보내고 어긋나면 초안 훅 `useTurnDraft`(`apps/web/src/turns/useTurnDraft.ts`)의 STALE 흐름을 탄다.
- 목록은 메시지 id로 중복을 없앤다. `send` 응답으로 먼저 넣은 행, 다른 탭의 재조회, `ready` 재조회, 다음 쪽 불러오기가 겹쳐도 같은 id는 한 줄이고 순서와 안 읽음 수가 맞는다.
- 메시지 탭: 개인 · 국가 · 외교(권한 있을 때만) · 전체. 탭마다 안 읽음 수.
- 보내기 실패(도배 제한 등)는 입력칸 아래에 이유 표시, 입력 내용은 지우지 않는다.
- 연결이 3초 넘게 끊겨야 "다시 잇는 중"을 띄운다. 첫 재시도에서 바로 이어지는 짧은 끊김에는 표시가 깜빡이지 않는다.
- 탭을 열어 첫 쪽이 보이면 그 안의 받은 메시지를 `message.markRead`로 읽음 처리한다. 버튼을 따로 두지 않는다.
- 국가 공지는 팝업을 닫으면 그 팝업에 띄운 응답의 `nationId`와 `revision`으로 `notice.nation.markSeen`을 부른다 (검토 R63-3R). 두 값은 팝업을 열 때 팝업 상태에 따로 담는다.
  닫기 전에 SSE나 `ready` 재조회로 `notice.nation.get` 캐시가 바뀌어도 캐시의 최신 값을 보내지 않는다. 응답의 `unseen`이 아직 true면(그사이 새 공지, 또는 다른 국가로 옮김) 그 응답의 본문으로 팝업을 한 번 더 띄운다. 응답이 null이면(재야가 됨) 띄우지 않는다. 고치기는 국가 정보 화면의 공지 칸에서 군주·참모만 한다(`canEdit`).
- 월드 공지는 메시지 패널 전체 탭 맨 위에 고정 공지부터 보여 준다.

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 실시간 | Playwright: 두 브라우저(사용자 A·B) → A가 보낸 개인 메시지가 B 화면에 2초 안에, 새로고침 없이 |
| 턴 결과 | Playwright: manual 시계로 턴 진행 → 메인 최근 기록이 2초 안에 갱신 |
| 범위 | Playwright: 외교 탭은 군주·참모에게만 |
| 공지 | Playwright: 공지 수정 → 소속 장수 다음 접속 시 팝업 1회 |
| 공지 경합 | Playwright: 팝업을 띄운 채 다른 군주 세션이 공지를 고침 → 팝업 닫기 → 새 공지 팝업이 한 번 더 뜸 |
| 공지 국가 범위 | Playwright(실제 서버·E2E DB): A·B 두 국가 모두 revision 3. A 공지 팝업을 띄운 채 장수를 B로 옮김(`e2e/world.ts:13-27`의 `bindGeneral`처럼 월드 행을 잠근 트랜잭션에서) → 팝업 닫기 → 보낸 요청이 `nationId: A`인지 보고 B 공지 팝업이 뜸. B 팝업을 닫지 않고 새로고침하면 B가 다시 뜨고 닫은 뒤 새로고침하면 뜨지 않음 |
| 재연결 | Playwright(실제 서버): 두 사용자 브라우저에서 연결을 끊었다 다시 이음 → `ready` 뒤 전체 재조회 1회. 지도 선택·30칸 미저장 초안·메시지 작성 칸·공지 고치기 초안 유지, 목록 중복 행 없음. 가짜 EventSource만으로는 인수하지 않는다 |
| 정상 경로 2초 | Playwright: 위 실시간·턴 결과 두 줄을 commit부터 화면 표시까지 잰다 (AC-M2-07은 여기서 판정) |
| 초안과 턴 결과 | Playwright: 30칸 초안을 고치는 중에 턴이 실행됨 → 초안 유지와 서버 예턴 변경 안내, 저장 → STALE 흐름 |
| 목록 병합 | Playwright: 보낸 행이 맨 위에 있는 상태에서 `ready` 재조회와 다음 쪽 불러오기 → 같은 id 한 줄, 안 읽음 수 일치 |
| 접근성 | Playwright: 메시지 패널을 키보드로 열고 닫으면 초점이 여는 단추로 돌아옴, 접힌 패널을 다시 펴도 작성 칸 유지. 보내기 네트워크 실패 뒤 입력 유지와 오류 안내를 스크린리더 이름으로 확인 |

## 구현 기록 (Claude)

- 바꾼 것:
  - `apps/web/src/realtime/useWorldEvents.ts`: 월드 SSE 연결 하나와 재연결. 알림 종류별 무효화 표는 위 결정 표 그대로다. `ready`는 query 전부를 무효화한다.
    브라우저가 스스로 다시 잇는 동안(CONNECTING)은 기다리고 서버가 닫았으면(CLOSED) 1·2·5·10·30초 간격으로 새로 연다. 3초 넘게 끊겨야 다시 잇는 중이 된다.
  - `apps/web/src/messages/`: 메시지 패널(탭·목록·작성), 위쪽 띠 단추와 배지, 오른쪽 접이식 패널, `/w/:worldId/messages` 전체 화면, 국가 공지 팝업과 공지 칸, 전체 탭 위 월드 공지.
    `merge.ts`가 id로 행을 합치고 `drafts.ts`가 작성 칸·고른 탭·공지 고치기 초안을 query 캐시 밖에 둔다.
  - `GameLayout`: SSE 연결, 연결 상태 표시, 메시지 단추·패널, 국가 공지 팝업. 0초 재조회는 SSE가 끊긴 동안에만 돈다.
  - `router.tsx`에 `messages` 경로 한 줄, 메인 국가 정보 칸 아래 공지 칸 한 줄(`NationInfo`), 로그아웃 때 초안 비우기(`LogoutButton`), Vite 개발 서버의 `/sse` 프록시.
  - API는 아직 main에 없어 T2-09 계약 초안을 `apps/web/src/messages/contract.ts` 한 파일에 옮겼다. 쿼리 키는 tRPC 키 모양이라 `AppRouter`로 바꿔도 무효화 키가 같다.
- 계획과 달라진 점과 이유:
  - 0초 재조회(T1-16)를 지우지 않고 SSE가 이어지지 않은 동안의 대체로 남겼다. 연결이 이어지면 쉰다. 끊긴 동안에도 화면을 쓸 수 있어야 하고 T2-09가 들어오기 전에도 M1 화면이 지금처럼 돌아야 해서다.
  - 메시지 패널은 메인만이 아니라 `GameLayout` 아래 모든 월드 화면에서 열린다. 위쪽 띠 단추가 어디서나 보이기 때문이다. 게임 메뉴에는 줄을 더하지 않았다.
  - 국가 공지 칸은 보조 화면 `/w/:worldId/nation/:nationId`가 아니라 메인 국가 정보 칸 아래에 두었다. 핵심 조작은 메인에서 한다는 소유자 UI 정정(D-020)을 따랐다. canEdit이 false면 [고치기]를 점선으로 두고 이유를 보인다.
  - 작성 칸·공지 초안은 sessionStorage가 아니라 탭 메모리에 둔다. 메시지 본문을 브라우저 저장소에 남기지 않으려는 것이고 그래서 새로고침하면 사라진다.
  - `offer.new`·`treaty.new`의 무효화 대상은 T2-06·T2-08 계획의 라우터 이름(`offers`, `personnel`, `treaty`) 경로 키로 두었다. 그 라우터가 없으면 맞는 query가 없어 아무 일도 없다.

### 계약

- 타입은 `inferRouterInputs<AppRouter>`·`inferRouterOutputs<AppRouter>`에서만 꺼낸다. `messages/contract.ts`에는 이 별칭과 `MESSAGE_SCOPES`만 남긴다. `PendingClient`·`api` 캐스트·손으로 쓴 DTO·`messageKeys`·`noticeKeys`는 지운다. 보내기 입력은 `message.send` 입력 타입이라 WORLD가 들어갈 수 없다.
- 조회는 `useTRPC()`의 `queryOptions`(unread, recipients, notice.nation.get, notice.world.list), 쓰기는 `mutationOptions`(send, markRead, notice.nation.set, notice.nation.markSeen)와 `useMutation`이다. 응답을 캐시에 넣을 때도 같은 `queryKey()`를 쓴다.
- 목록 키는 생성된 `trpc.message.list.infiniteQueryKey({ worldId, scope })`다. 설치된 11.19 `getClientArgs`(`apps/web/node_modules/@trpc/tanstack-react-query/dist/index.mjs:160-173`)는 infinite 입력에 `direction`을 늘 붙이고 지금 `message.list` 입력(`routers/message.ts:23`)은 `.strict()`라 `infiniteQueryOptions`를 쓰면 BAD_REQUEST가 난다. 그래서 queryFn은 TanStack이 주는 `{ pageParam, signal }`을 받아 `trpcClient.message.list.query({ worldId, scope, ...(pageParam ? { cursor: pageParam } : {}) }, { signal })`로 부르고 `getNextPageParam`은 `next`다. 취소가 요청까지 닿는다. 서버는 바꾸지 않는다.
- SSE는 tRPC 밖 HTTP 계약이라 타입을 `realtime/useWorldEvents.ts` 안에 둔다(`apps/server/src/realtime/index.ts` 기준). `GET /sse?worldId=`, 이벤트 이름이 kind이고 data는 `{kind, scope?}`뿐이다. 연결마다 `ready`가 먼저 오고 서버 LISTEN이 되살아나면 모든 연결에 다시 온다. `: hb`는 주석이다. 400·401·403·404·503 같은 거절 뒤에도 상태는 단정하지 않는다. `onerror`에서 실제 `readyState`가 CLOSED일 때만 지금의 간격 재연결을 하고 CONNECTING이면 브라우저 재시도를 기다린다.
- 본문 한도는 서버 `bodyLimit`과 같은 `[...value].length <= 1000`이다. UTF-16 단위인 `maxLength`를 빼고 글자 수 표시와 막기를 같은 셈으로 한다. 넘으면 보내기·저장을 막고 서버 문장 `본문은 1,000자까지 쓸 수 있습니다.`를 보인다. 메시지 빈 본문 판정은 지금처럼 `trim()`이다.

### 동작

`merge.ts`의 id 병합과 읽음 OR, 성공한 send 행 맨 위 넣기, 실패 때 본문 유지, `drafts.ts`의 캐시 밖 초안, 팝업을 열 때 담은 nationId·revision과 unseen 재팝업·null 미표시는 그대로 두고 키와 호출만 바꾼다.

send·markRead·notice.nation.set·markSeen은 부를 때의 epoch를 잡아 두고 응답이 왔을 때 epoch가 바뀌었으면 `setQueryData`를 하지 않는다. 늦은 응답이 새 권한의 캐시를 되살리지 않게 하려는 것이다. 이미 띄운 공지 팝업은 원계획대로 열 때의 snapshot을 그대로 두고 닫을 때 그 nationId·revision을 보낸다. markSeen을 부를 때와 응답을 받을 때의 epoch가 같을 때만 응답의 unseen·null로 재팝업을 정한다. 닫는 중 epoch가 바뀌었으면 그 응답은 캐시에도 재팝업에도 쓰지 않고 새로 받은 `notice.nation.get`으로 다음 팝업을 정한다. A 팝업을 띄운 채 이미 B로 옮겨 권한 값이 B가 된 뒤 닫으면 잡은 epoch가 B라서 B 응답을 그대로 따른다.
공지 고치기와 NATION·DIPLOMACY 작성 초안 키에는 nationId를 넣는다. 권한이 같으면 키도 같아 ready 재조회 때 그대로 남고 옮기기 전 국가의 초안은 새 국가로 저장되지 않는다. `canEdit`이 false면 고치기 칸을 닫는다.
단위 사례로 권한 변경 뒤 응답 전 탭·공지 칸 숨김, 첫 값의 캐시 불신, 늦은 send·markRead·set 응답 무시, 권한 변경 중 팝업 snapshot 유지를 둔다.

### 검증 순서와 판정

### 모르는 것

첫 실행은 trace를 끄고 돌렸다. native EventSource의 readyState·onerror, navigator 상태, 새 요청 여부는 모으지 않았다. 확인된 사실은 화면이 10초 동안 연결됨이었다는 것뿐이다. offline이 네트워크를 끊지 않았다고 정하지 않는다. 브라우저 결함이나 기존 stream이 계속 받았다는 것도 정하지 않는다. 쉬고 있는 기존 stream의 오류 통지가 새 요청의 실패와 다를 수 있다는 것은 가설이다.
지금 `useWorldEvents`는 EventSource의 open·error만 본다. 서버 heartbeat는 30초마다 오는 `: hb` 주석이라 브라우저 message로 드러나지 않는다.
참고한 원문은 부모가 준 범위만 쓴다. Playwright `setOffline`은 context의 네트워크 offline 흉내다. v1.64.1 `crNetworkManager.ts`는 `Network.emulateNetworkConditions`(offline, latency 0, throughput -1)를 부른다. CDP 문서에서 이것은 네트워크 흉내이며 navigator 상태(`overrideNetworkState`)와 따로다. HTML SSE 처리 모델은 실제 fetch가 network error면 CONNECTING과 error를 거쳐 다시 잇고 UA가 OS 연결 복귀를 기다릴 수 있다고 한다. `navigator.onLine` 절은 online·offline 사건과 navigator 값이 믿을 만하지 않다고 적는다.

### 최소 방향

window의 online·offline 사건은 연결이 바뀌었을 수 있다는 힌트로만 쓴다. navigator 값으로 상태나 기능을 정하지 않는다.
offline 힌트가 오면 지금 연결을 새 EventSource 하나로 바꾸고 그 새 요청의 실제 open·error·ready를 따른다. 힌트가 틀려 서버에 닿으면 새 요청이 열려 기능을 그대로 쓴다. 정말 끊겼으면 새 요청이 실패해 기존 3초 표시와 CLOSED 간격 재연결을 탄다.
online 힌트는 기다리던 간격 재연결을 취소하고 바로 한 번 새로 연다. 지금 연결이 열려 있으면 아무것도 하지 않는다.
힌트만으로 연결됨·다시 잇는 중을 바꾸거나 query를 무효화하지 않는다. ready의 전체 무효화는 지금 그대로다. 옛 연결의 늦은 사건은 버린다. 힌트가 거듭 와도 살아 있는 연결은 하나다. 멈추면 window 구독과 타이머를 모두 거둔다.
이렇게 하면 상태는 늘 실제 요청 결과에서 오고 새 파일·backend 변경이 없다. 서버 heartbeat를 message로 바꿔 무응답 시간을 재는 방법은 backend 변경이라 택하지 않는다. 권한 epoch, 늦은 응답 차단, 초안, 공지 snapshot은 건드리지 않는다.
