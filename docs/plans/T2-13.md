# T2-13 D12 기본 방침

> 대기열: T2-13 · AC: AC-M2-17 · 구현: Codex · 리뷰: Claude
> 선행: M1 전체 · 관련: [차별화 D12](../product/differentiation.md#d12-기본-방침), FR-DIF-12, FR-GEN-04

## 계획 (Claude)

### 목표

기본 방침을 정한 장수의 빈 예턴 칸은 휴식 대신 방침에 맞는 명령으로 실행된다. 그 명령이 실패하면 휴식으로 대신하고 이유가 로그에
남는다. 장기 미접속 장수는 방침 범위 안에서만 AI가 고른다 (AC-M2-17).

### 범위

- `General.defaultPolicy`, `General.lastActiveTick`(판정)·`lastActiveAt`(표시), `GeneralTurn.explicit` (새 migration)
- `packages/rules/src/policy/`: 방침 → 명령 대응, 미접속 판정, 칸 비교 `sameSlot`. `replay.ts`의 칸·방침·활동 재생
- engine: 턴 실행의 빈칸 처리 분기, `general.setPolicy`·`general.active` 집행, 예턴 당김의 `explicit` 보존
- `apps/server`: `general.setPolicy`와 로그인 활동의 접수, 예턴 저장·편집의 `explicit`과 활동 기록
- 화면 연결은 T2-14(Claude)가 메인 지도와 T1-15의 재사용 30칸 편집기 `TurnEditor`(`apps/web/src/turns/TurnEditor.tsx`, 메인 배치는 합쳐진 T1-16의 `apps/web/src/pages/MainPage.tsx:80`, `:99`)에서 한다

### 하지 않는 것

국가 단위 방침(myosam 국가점수 정책, Phase 2), 장수 삭제·NPC화 정책(지인 테스트 뒤 결정).

### 결정

| 방침 | 빈칸에서 실행 | 실패하면 |
| ---- | ------------- | -------- |
| `farm` 권농 | 농지 개간 | 휴식 + 이유 |
| `commerce` 중상 | 상업 투자 | 〃 |
| `security` 치안 | 치안 강화 | 〃 |
| `defend` 수비 | 수비 강화 → 최대면 성벽 보수 | 〃 |
| `drill` 훈련 | 훈련 → 최대면 사기진작 | 〃 |
| `none` | 휴식 (M1과 같음) | — |

- 빈칸은 사용자가 아무것도 넣지 않은 칸이다. 사용자가 **직접 넣은 휴식은 그대로 휴식**이다 (구분을 위해 저장 형식에 `explicit` 표시, 보존 범위는 아래 [예턴 칸 모양](#예턴-칸-모양과-전환-검토-r63-6-2026-10-21-정리)).
  M1에 저장된 휴식은 직접 넣은 휴식으로 본다(U63-3, 아래 [승인된 사용자 결정](#승인된-사용자-결정-2026-10-23)).
- 직접 넣은 칸(명령과 휴식)은 미접속이어도 그대로 실행한다. 빈칸만 방침으로 채운다(U63-1). 계획 단계의 근거는 FR-GEN-04가 예턴을 다 쓴 뒤의 처리이고
  (`docs/product/requirements.md:55`) v1 미접속 위임도 본인 예약을 우선했다는 것이었다(T2-17 v1 근거, v1 `docs/user/features.md:215-221`).
  예전 초안의 14일 뒤 모든 칸을 AI가 고르는 방식은 U63-1과 맞지 않으므로 만들지 않는다.
- AI가 고른 명령은 예턴 칸에 쓰지 않고 그 턴에만 실행한다. 그래서 다시 접속해도 되돌릴 칸이 없고 사람 예턴이 그대로 이어진다.
- 판정은 현실 시각이 아니라 기록된 tick으로 한다(아래 [활동 기록](#활동-기록과-재생-결정론-검토-r63-7-2026-10-21-정리)).
- 로그: "기본 방침(권농)으로 농지 개간" / "기본 방침 실패: 이미 최대 → 휴식".
- 활동 기록(`lastActiveTick`·`lastActiveAt`)은 로그인과 예턴 저장 성공, 방침 바꾸기 집행에서만 갱신한다. 조회와 SSE 연결, 실패하거나 STALE로 돌아온 저장은 활동으로 세지 않는다. v1 미접속 위임도 조회와 알림 구독을 활동에서 뺐다(v1 `docs/user/features.md:217`, 판정 `app/game-engine/src/main/kotlin/opensamguk/engine/campaign/OfflineDelegationLease.kt:69-72`).

### API 계약

아래 절의 타입이 계약 초안이다. `general.policy`·`general.setPolicy`는 아직 `AppRouter`에 없고 최종 서버 타입은 backend(Codex)가 정한다 (AGENTS.md §0).

```ts
general.policy({ worldId }) → PolicyResponse
general.setPolicy({ worldId, policy: PolicyKey }) → SetPolicyOutcome   // 엔진이 집행한다 (아래). 예턴 revision과 무관
turns.get / turns.set / turns.edit                                     // 칸 모양에 explicit 추가 (아래 예턴 칸 모양)
home.get                                                               // 장수 요약에 policy, 예턴 앞 5칸에 explicit 추가
```

### 방침 바꾸기 처리 (검토 R63-7, 2026-10-21 정리)

방침은 빈칸의 실행 결과를 바꾸므로 게임 상태로 보고 엔진만 바꾼다 (AGENTS.md §6). 지금 재생은 모르는 입력 종류를 거부하므로
(`packages/rules/src/replay.ts:67-107`) 새 종류를 재생에 더하는 것까지 이 작업 범위다. 접수와 대기는 장수 생성
`apps/server/src/routers/general.ts:35-115`를, 집행 자리는 `apps/engine/src/inputs.ts:15-96`을 따른다. 여러 kind를 함께 꺼내는 처리기는 아래 [부모 결정 대기](#부모-결정-대기-기술-2026-10-23) B-4를 따른다.

| 단계 | 누가 | 하는 일 |
| ---- | ---- | ------- |
| 접수 | API | 세션 사용자의 그 월드 장수를 행위자로 정한다. 무인증·제재·월드 없음·장수 없음·종료된 월드는 거부한다. `PolicyKey`를 검사한 뒤 `PENDING` InputEvent `general.setPolicy`(payload `{ policy }`)를 만든다. 같은 장수의 `PENDING` 방침 입력이 있으면 값이 같을 때 그 입력을 기다리고 다르면 `CONFLICT` |
| 대기 | API | 최대 5초 다시 읽는다. `APPLIED`면 `{ status: 'applied', policy }`, `REJECTED`면 이유 코드로 오류, 시간이 지나면 `{ status: 'pending' }`. 결과를 주기 전에 세션을 다시 확인한다(`general.ts:72-86`) |
| 집행 | 엔진 | 입력 id 순으로 꺼내 계정 상태와 장수를 다시 본다. 펜싱 트랜잭션 하나에서 `General.defaultPolicy`, `lastActiveTick`·`lastActiveAt`, InputEvent의 `APPLIED`·`sequence`·`result { policy, activeTick }`를 함께 쓴다. 검사에 실패하면 상태는 그대로 두고 `REJECTED`와 이유 코드 |
| 재조회 | 화면 | `pending`이면 `general.policy`를 다시 읽는다. `pending`이 null이 되면 `current`가 결과다. 거절됐으면 `lastRejected`에 이유가 있다 |

- 같은 장수의 턴이 방침 입력보다 먼저 실행되면 그 턴은 옛 방침을 따른다. 순서는 엔진이 매긴 sequence이고 재생도 같은 순서를 쓴다.
- 재생: `applyRecordedInput`에 `general.setPolicy`·`general.active`를 더한다. 방침과 `lastActiveTick`은 `ReplayState`에 `turns`·`revisions`처럼 장수별로 둔다(`replay.ts:13-18`).

### 활동 기록과 재생 결정론 (검토 R63-7, 2026-10-21 정리)

아래는 활동 tick을 재생 상태에 넣는 지금 계획이다. U63-1에서는 미접속 판정이 턴 결과를 바꾸지 않으므로 넣을지는 [부모 결정 대기](#부모-결정-대기-기술-2026-10-23) B-3이다. 넣는다면 재생에서 같은 값이 나와야 한다 (AC-M1-13). 엔진과 재생은 벽시계를 읽지 않고 InputEvent에 기록된 tick만 쓴다.

- 판정: `isInactive(lastActiveTick, tick, turnTermMinutes)`는 `tick − lastActiveTick > 기준일 × 1,440 ÷ turnTermMinutes × 10,000`이면 참이다(`packages/rules/src/policy/`).
  1 tick이 `turnTermMinutes × 60,000 / 10,000` ms이므로(`docs/architecture/game-clock.md:35`) 월드가 돌아간 날 수다. 정지한 시간은 세지 않는다.
  기준일은 14일이다(U63-2). 정확히 14일은 미접속이 아니다. 나눗셈 없이 정수로 `(tick − lastActiveTick) × turnTermMinutes > 14 × 1,440 × 10,000`을 비교한다.
- `lastActiveTick`은 아래 활동 입력의 `result.activeTick`에서만 온다. 장수 생성 때는 생성 tick이다. `userId`가 null인 NPC는 판정하지 않는다.
- `lastActiveAt`(현실 시각)은 그 InputEvent의 `createdAt`을 옮겨 적은 표시값이다. 감찰 표(T2-11)와 화면 안내만 쓰고 판정에 쓰지 않는다.
- 시험은 엔진 시계(`manual` 모드)와 기록된 tick으로 경계를 맞춘다. 현실 시각을 바꿔 판정을 시험하지 않는다.

| 활동 | 기록 | activeTick | 쓰는 쪽 |
| ---- | ---- | ---------- | ------- |
| 예턴 저장·편집 성공 | 기존 `turns.set` 입력(`apps/server/src/routers/turns.ts:65-77`)의 `result`에 더한다. STALE·실패는 입력이 없으므로 활동이 아니다 | 같은 트랜잭션에서 읽은 `World.clockTick` | API. `turnRevision`처럼 예턴 저장 트랜잭션 안에서 `General.lastActiveTick`·`lastActiveAt`도 쓴다(`turns.ts:60-63`) |
| 방침 바꾸기 | `general.setPolicy` | 엔진이 집행한 tick | 엔진 |
| 로그인 | `general.active`(`PENDING`, payload 없음). 로그인은 계정 단위이고 worldId가 없다(`apps/server/src/routers/auth.ts:57-76`). 로그인이 성공하면 상태가 ENDED가 아닌 모든 월드에서 그 사용자의 장수마다 하나 만든다. 이미 `PENDING`이 있으면 더 만들지 않는다 | 엔진이 집행한 tick | 엔진 |

- `World.clockTick`은 엔진의 체크포인트 값이라 실제보다 최대 5초 늦을 수 있다(`game-clock.md:48`). 판정 단위가 날 수라 무시한다.
- 조회와 SSE 연결은 활동이 아니다(위 결정).

### 사람 장수의 방침 실행 (검토 R63-7, 2026-10-21 추가)

지금 NPC 판단은 사람 장수를 다루지 않는다. `chooseGeneralTurn`은 `userId`가 있으면 후보를 주지 않고(`packages/rules/src/npc/index.ts:85-86`),
NPC에게는 임관·귀환·이동·모병·출병까지 고른다(`npc/index.ts:87-136`). 턴 실행도 `userId`가 null이고 휴식인 칸만 AI를 부른다
(`packages/rules/src/commands/turn.ts:55-67`). 그래서 사람 장수의 방침 실행은 기존 함수를 그대로 불러서 만들 수 없다.

- 사람 장수의 빈칸은 `packages/rules/src/policy/`의 새 함수가 고르고 고르는 자리는 `runGeneralTurn` 안 국가 턴 뒤(`packages/rules/src/commands/turn.ts:58`)다. 군주의 국가 명령이 끝난 상태에서 판정해야 하기 때문이다. 방침이 허용하는 명령만 후보로 만든 뒤에 고른다. 고른 뒤에 걸러 내지 않는다. 방침 함수로 턴 전체를 대신하지 않는다(아래 [기술 계약 제안](#기술-계약-제안-claude-2026-10-23-부모-수용-전) 실행).
- 출병·이동·임관·귀환은 어떤 방침에서도 후보가 아니다. 방침별 후보 범위는 위 결정 표의 명령과 휴식이다. 이것이 U63-1의 승인 범위이며 넓히지 않는다.
- 난수가 필요하면 NPC와 다른 키(`rngFor(seed, 'policy', tick, generalId)`)를 쓴다. 엔진과 재생이 같은 함수를 부른다.
- 장수의 `userId`를 바꾸지 않는다. 사람 장수를 NPC로 넘기는 처리는 이 작업이 아니다(하지 않는 것).
- 직접 넣은 명령과 직접 넣은 휴식은 이 분기를 타지 않는다.

### 화면(T2-14)이 기대하는 응답 모양

```ts
type PolicyKey = 'none' | 'farm' | 'commerce' | 'security' | 'defend' | 'drill';
type CommandRef = { key: string; name: string }; // name은 명령 레지스트리의 화면 이름

type PolicyOption = {
  key: PolicyKey;
  name: string;                  // '권농'·'중상'·'치안'·'수비'·'훈련', none은 '없음'
  emptyCommand: CommandRef;      // 빈칸에서 먼저 하는 명령. none은 휴식
  thenCommand: CommandRef | null; // 먼저 하는 명령이 이미 최대일 때 (수비: 성벽 보수, 훈련: 사기진작). 나머지는 null
};

type PolicyResponse = {
  current: PolicyKey;
  pending: PolicyKey | null;                  // 엔진이 아직 집행하지 않은 내 방침 입력. 없으면 null
  lastRejected: { policy: PolicyKey; reason: string } | null; // 내 마지막 방침 입력이 거절됐을 때만
  options: PolicyOption[];                    // 위 결정 표의 순서 그대로, none이 마지막
  inactiveAfterDays: number;                  // 안내 문장에 쓴다. 월드가 돌아간 날 수. 14 (U63-2)
};
type SetPolicyOutcome = { status: 'applied'; policy: PolicyResponse } | { status: 'pending' };

// SlotView는 아래 예턴 칸 모양에 있다. explicit이 false면 사용자가 비워 둔 칸이고,
// 화면은 이때 name 대신 현재 방침의 emptyCommand를 흐리게 보여 준다.

// home.get의 장수 요약에 더한다
type GeneralPolicySummary = { policy: { key: PolicyKey; name: string } };
```

방침 이름과 명령은 `packages/rules/src/policy/` 한곳에서 오고 화면은 이 응답만 보고 문장을 만든다. 화면에 방침 표를 따로 적지 않는다.

| T2-14 화면 요소 | 쓰는 응답 |
| --------------- | --------- |
| 방침 고르기와 바로 보내기, 처리 중과 거절 표시 | `PolicyResponse.options`, `pending`, `lastRejected`, `general.setPolicy`의 `SetPolicyOutcome` |
| "빈 칸은 X를 합니다. 실패하면 휴식합니다." | 현재 방침의 `emptyCommand`, `thenCommand` |
| 메인 30칸 편집기의 흐린 빈칸 "(권농) 농지 개간"과 진한 직접 휴식 | `SlotView.explicit` + 현재 방침 |
| 미접속 안내 한 줄 | `inactiveAfterDays` |
| 메인 장수 요약의 방침 | `GeneralPolicySummary` |

메인 화면 범위 (검토 R63-8): 빈칸 표시와 방침은 메인의 지도와 T1-15의 재사용 30칸 편집기 `TurnEditor`(`apps/web/src/turns/TurnEditor.tsx`, 메인 배치는 합쳐진 T1-16의 `apps/web/src/pages/MainPage.tsx:80`, `:99`)에서 보여 주고 검증한다.
`home.get`의 앞 5칸은 기존 요약과 호환을 위한 값이고 메인 플레이를 그 5칸으로 줄이지 않는다.

### 예턴 칸 모양과 전환 (검토 R63-6, 2026-10-21 정리)

T2-11 작전판은 구현 시점의 turns 계약을 따른다. 칸 모양과 변환·비교 함수는 이곳 하나뿐이다.

```ts
// 규칙·저장·재생·엔진의 칸. 빈칸은 emptyTurn() = { commandKey: 'rest', args: {}, explicit: false } 하나다
interface QueuedTurn { commandKey: string; args: unknown; explicit: boolean }
// 화면으로 나가는 칸. turns.get·turns.set·turns.edit 응답, STALE 응답, home.get 앞 5칸,
// T2-11의 operation.get·operation.suggest·inspection.members가 쓴다. 30칸 모두 객체이고 null이 없다
type SlotView = { commandKey: string; args: unknown; name: string; explicit: boolean };
// 화면에서 들어오는 칸(turns.set). null은 빈칸, 객체는 직접 넣은 칸이다. 직접 넣은 휴식은 { commandKey: 'rest' }
type SlotInput = { commandKey: string; args?: unknown } | null;
// 화면이 받은 SlotView를 다시 저장할 때의 변환. apps/web 한곳에 둔다
const toSlotInput = (v: SlotView): SlotInput => (v.explicit ? { commandKey: v.commandKey, args: v.args } : null);
// 두 칸이 같은지. packages/rules 한곳에 둔다. T2-11의 changed가 쓴다.
// 빈칸끼리는 같다. 빈칸과 직접 넣은 칸은 다르다. 직접 넣은 칸끼리는 commandKey와 args(키 순서 무시)를 비교한다
declare function sameSlot(a: QueuedTurn, b: QueuedTurn): boolean;
```

지금은 `parseSlot(null)`과 직접 넣은 휴식이 같은 값이고(`apps/server/src/game/slots.ts:7-14`) `GeneralTurn`에도 표시가 없다(`packages/db/prisma/schema.prisma:173-182`).

### 실행 계약 요약 (2026-10-23)

- 칸의 뜻: 행이 없음 → 빈칸. `turns.set`의 null과 새 shift 채움 → 빈칸. 객체 → 직접. 기존 DB 행과 explicit 없는 옛 기록 → 직접(휴식 포함, U63-3). M1 장수 생성·엔진 당김·`turns.edit` 채움이 쓴 휴식 행도 기존 행이라 직접이다.

### 기술 계약 제안 (Claude, 2026-10-23, 부모 수용 전)

두 차례 Claude 기술 리뷰(2026-10-23, 계약 리뷰와 그 정정 리뷰)에서 받아들인 정정과 이 계획 작성자의 제안이다. 부모 수용 전에는 공유 코드에 넣지 않는다. 위 결정 표와 U63 세 결정은 바꾸지 않는다.
범위는 T2-13 백엔드 전체(위 범위 절)이고 T2-13a 순수 규칙만으로 닫히지 않는다.

공유 런타임 소스는 `3e5b52a` 그대로다. `2a27bcf`에서 순수 방침 시험 24개와 옛 재생 시험 26개가 통과했다고 구현 쪽이 보고했다. AC 증거가 아니고 교차 리뷰 통과도 없다.

#### 용어와 상태 구분

- C는 migration 시점의 `World.actionSequence`다. F는 첫 방침 모드 sequence이고 새 열 `World.policyFromSequence Int?`에 둔다.
- 방침 모드는 `F !== null && actionSequence >= F`다. 새 월드는 F = 0, 갱신 월드는 엔진이 표지를 집행하며 받은 실제 sequence(C+1 이상), migration 때 ENDED였던 월드는 null이다.
- 표지는 예약 kind `system.policy.enable`이다. migration만 만들고 API는 받지 않는다.

F가 null인 두 경우(갱신 대기와 옛 ENDED)는 새 열 없이 표지 조회로 가른다. 표지 유일성은 부분 유일 색인 `InputEvent(worldId) WHERE kind = 'system.policy.enable'`가 지킨다.

| `policyFromSequence` | 표지 | 상태 | 칸 읽기 | API 쓰기 |
| -------------------- | ---- | ---- | ------- | -------- |
| 숫자 | F > 0이면 APPLIED이고 sequence = F, F = 0이면 없음 | 방침 모드 | 장수마다 30행, `row.explicit` | 열림 |
| null | PENDING 하나 | 갱신 대기 | 장수마다 30행, `row.explicit`. 해시용 재생 상태는 옛 모양 | `turns.set`·`turns.edit`·`general.setPolicy`는 PRECONDITION_FAILED. 읽기는 열어 둔다 |
| null | 없음 | 옛 월드(migration 때 ENDED, 또는 시험용 옛 형식 옵션) | 행이 없으면 false, 있으면 `row.explicit` | ENDED 거부 그대로 |

그 밖의 조합(F null인데 APPLIED 표지, 숫자 F인데 PENDING 표지, F와 표지 sequence 불일치, ENDED인데 PENDING 표지)은 손상이다. 읽기와 집행 모두 예외를 던진다.

#### B-1 migration (DDL과 채움만)

새 migration 파일 하나다. 기존 migration은 고치지 않는다. 표지를 APPLIED로 쓰는 migration 예외는 채택하지 않는다. 상태 전환은 엔진이 한다(AGENTS.md §6).

- 첫 문장은 `BEGIN`, `SET LOCAL lock_timeout`, `LOCK TABLE "World", "General", "GeneralTurn", "InputEvent" IN ACCESS EXCLUSIVE MODE`다. Prisma가 트랜잭션으로 감싼다고 가정하지 않고 롤백 시험으로 증명한다.
- ENDED가 아닌 월드에 행이 1~29개인 장수가 있으면 전체를 되돌린다. 지금 writer 셋(`turns.ts:50-59`, `persist.ts:42-56`, `inputs.ts:77-85`)은 모두 0행 또는 30행을 쓰므로 알 수 없는 writer나 손상이다. 이미 표지가 있는 월드가 있어도 되돌린다.
- `GeneralTurn.explicit boolean NOT NULL DEFAULT true`로 기존 행을 모두 true로 채운 뒤(ENDED 포함, 예전 휴식 포함) `DROP DEFAULT`한다. Prisma 타입이 explicit을 요구하게 되어 빠진 writer를 컴파일러가 잡는다. CHECK `explicit OR ("commandKey" = 'rest' AND args = '{}'::jsonb)`를 더한다.
- ENDED가 아닌 월드에서 행이 0개인 장수마다 `(rest, {}, false)` 30행을 만든다. 옛 읽기는 행 없음과 이 행을 모두 `{ rest, {} }`로 읽으므로 옛 해시가 같다. 기존 행의 `commandKey`·`args`와 `turnRevision`은 그대로이고 `turns.set` 입력을 만들지 않는다. ENDED 월드는 행을 만들지 않는다. 기록은 그대로이고 기존 행의 explicit 열만 생긴다.
- `General.defaultPolicy`·`lastActiveTick`·`lastActiveAt`은 null 허용 열로 더하고 값을 쓰지 않는다. 값은 엔진 전환이 쓴다(아래 표지 집행). DB 기본값을 두지 않아 전환 전 행과 전환 뒤 행이 섞이지 않는다. `defaultPolicy`는 CHECK로 PolicyKey 또는 null만 받는다. `World.policyFromSequence`도 null로 더한다.
- 부분 유일 색인은 `(worldId, generalId) WHERE status = 'PENDING' AND kind = 'general.active'`, 같은 모양의 `general.setPolicy`, 위 표지 색인 셋이다.
- ENDED가 아닌 월드(RUNNING·PAUSED·PREOPEN)마다 PENDING 표지 하나를 넣는다. `userId` `system:policy`, `generalId` null, `idempotencyKey` `system.policy.enable:5`, payload `{ version: 5, emptySlots }`. `emptySlots`는 바로 위에서 false로 채운 장수 id 오름차순과 칸 0~29 전부다(희소 모양이지만 항상 30칸이다). sequence는 매기지 않고 `actionSequence`도 그대로다.
- 명령, RNG, 규칙을 실행하지 않는다. 옛 origin·입력·월간·result를 쓰지 않는다.

`InputEvent.userId`는 User FK가 없어(`schema.prisma:319-336`) `system:policy`를 저장할 수 있다.

#### 표지 집행 (엔진)

엔진이 리스와 World 잠금을 잡은 펜싱 트랜잭션 하나에서 전환한다. 아래 B-4 디스패처가 id 순으로 표지를 꺼낸다.

- 표지보다 id가 작은 PENDING `general.create`는 먼저 옛 모양으로 집행한다. 휴식 30행 explicit true, result `{ general }`, `activeTick` 없음, 거절 규칙도 그대로다. 버리거나 순서를 바꾸지 않는다. M1 생성 휴식이 직접 휴식인 것(U63-3)과 같다.
- 표지가 PENDING인 동안 그 월드는 턴과 월간 처리 같은 게임 행동을 하지 않는다. 엔진은 표지까지의 입력을 먼저 처리한다.
- 집행 전에 확인한다. 상태가 ENDED가 아니다, F가 null이다, 표지가 PENDING이다, 모든 장수가 정확히 30행이다, false 행 집합이 `payload.emptySlots` × 0~29와 같다, 그 행은 정확히 `rest`·`{}`다, 나열된 장수가 있고 중복·범위 밖이 없다, `nextActionSequence`가 넘치지 않는다. 하나라도 어긋나면 예외로 트랜잭션을 되돌린다. 표지는 PENDING에 남고 월드는 갱신 대기에 머문다. REJECTED로 두면 방침 모드로 갈 길이 없어지므로 쓰지 않는다.
- 같은 트랜잭션에서 F = `nextActionSequence`, `World.policyFromSequence = F`, 표지 APPLIED·sequence F·result `{ fromSequence: F, emptySlots, clockTick: T, turnTermMinutes, baselineActiveTick }`를 쓴다. T는 잠근 그 월드의 `World.clockTick`이다. 칸의 explicit은 고치지 않는다.
- 장수 열은 이렇게 쓴다. 모든 장수의 `defaultPolicy`는 `none`이다. `userId`가 있는 장수(표지 전에 옛 모양으로 생성된 장수 포함)의 `lastActiveTick`은 `baselineActiveTick`이고 NPC는 null이다. 모든 장수의 `lastActiveAt`은 null이다.
- `baselineActiveTick`은 월드마다 숫자 하나이고 그 월드의 tick 단위다. 다른 월드의 tick과 섞지 않는다. 값은 P-1 답에 따라 T(곧 `result.clockTick`) 또는 0이다. 구현은 두 경우를 한 상수로 갈아 끼울 수 있게 두고 답 전에는 어느 쪽도 고정하지 않는다.
- 표지보다 id가 큰 입력(갱신 대기 중 쌓인 로그인 `general.active`, 새 `general.create`)은 F 뒤에 방침 모드 모양으로 집행한다.

`emptySlots`는 F까지 그대로 맞다. 새 엔진은 표지 전에 게임 행동을 하지 않는다. 새 API는 칸 쓰기가 막혀 있다. 표지 전 생성은 30행을 가진 새 장수만 더하고 거절된 생성은 상태를 바꾸지 않는다. 이 작업의 migration 시험은 스스로 새로 만든 `*_test` DB에 자기 프로세스만 차례로 띄우므로 옛 writer가 끼어들 수 없다.
이 작업은 다른 사용자나 채팅이 띄운 로컬 API·엔진 프로세스를 멈추지 않고 공유·운영 DB를 migrate하지 않는다. 실제 배포에서 옛 writer를 어떻게 내릴지는 별도 운영 범위다. 부모가 기술 계약을 수용하면 그 운영 절차를 이유로 구현과 시험을 멈추지 않는다.
운영 절차가 지켜지지 않아도 `DROP DEFAULT` 뒤 옛 코드의 `GeneralTurn` 쓰기는 NOT NULL 위반으로 실패하고 엔진 집행이 행을 다시 확인한다. 옛 엔진의 다른 상태 쓰기(월간 처리 등)는 이 방어로 막지 못한다. 운영 범위에 넘길 사실로 적어 둔다.

#### B-2 형식 (archive 5)

- origin은 모든 월드에서 version 1이고 바이트와 해시가 그대로다. 갈라지는 것은 보관 파일뿐이다. F가 null이면 archive 2를 지금과 바이트까지 같게 내보낸다. 갱신 대기 월드도 표지가 PENDING이라 입력에 없으므로 archive 2다. F가 숫자면 archive 5다.
- archive 5는 archive 2 모양에 `version: 5`, config `{ endYear, outcomeFromSequence, policy: { version: 1, fromSequence: F, turnTermMinutes } }`다. 다른 config 키, origin 1이 아닌 버전, 3·4는 거부한다. 3(T4-03)·4(T2-05)는 초안 예약이고 5가 그것을 포함한다고 주장하지 않는다. 나중에 합치려면 새 형식 번호와 합친 검증기·상태 로더를 따로 만든다.
- coverageEnd는 `end.sequence`, 없으면 마지막 월 sequence다. 0 < F ≤ coverageEnd면 F에 APPLIED 표지가 정확히 하나, F > coverageEnd면 0개, F = 0이면 0개다. `replayArchive`와 `replayToEnd` 둘 다 `applyRecordedInput` 전에 F를 잡고 표지 없이 F를 지나면 거부한다.
- F 전에는 옛 kind(`turns.set`, `general.create`)와 옛 모양만 받는다. explicit과 `activeTick`이 있으면 거부한다.
- F부터는 `turns.set` 30칸 모두 boolean explicit이고 false면 정확히 `rest`·`{}`다. `general.setPolicy`는 payload `{ policy }`·result `{ policy, activeTick }`이고 두 policy가 같으며 장수가 있고 `userId`가 있다. `general.active`는 payload `{}`·result `{ activeTick }`, `general.create`는 result `{ general, activeTick }`이다. afterEnd에는 REJECTED 방침 kind만 들어갈 수 있다.
- v1·v2 검증기에 kind 허용 목록(`turns.set`, `general.create`)을 더하고 inputs·afterEnd의 REJECTED에도 적용한다. 지금은 REJECTED를 kind 확인 없이 넘긴다(`packages/rules/src/replay.ts:81`).
- 표지는 kind, `generalId` null, sequence F, `result.fromSequence` = F = `config.policy.fromSequence`, `payload.emptySlots` = `result.emptySlots`, `turnTermMinutes`는 config와 같아야 하는 정보값, `clockTick`은 F 전 마지막 행동 tick 이상(하한만)인지 확인한다. 보관 파일에는 userId가 없으므로 `system:policy`를 확인했다고 하지 않는다. 서명 없는 보관 파일이라 진위는 보장하지 않는다.
- 재생은 해시 밖에서 손대지 않은 초기 장수 집합을 따라간다. origin 초기 장수로 시작해 옛 턴을 처음 실행하거나 APPLIED `turns.set`이 오면 뺀다. F에서는 이 집합을 그때의 `state.generals` id와 교집합한 뒤 비교한다. 그 교집합 × 0~29가 `emptySlots`와 정확히 같고 나열 칸이 정확히 `{ commandKey: 'rest', args: {} }`여야 한다. `emptySlots`에 지금 없는 장수 id가 있으면 거부한다. 오래된 id를 그대로 믿지 않는다.
- 지금 코드에는 운영 경로의 장수 삭제가 없다. 국가 멸망 `removeNation`은 `nationId`를 null로, `officerLevel`을 0으로 바꿀 뿐이다(`packages/rules/src/commands/support.ts:70`). 그래도 교집합 규칙은 둔다. 나중에 삭제가 생기면 이 규칙이 그 경우를 덮는지 시험으로 다시 확인한다.
- 비교가 맞으면 모든 큐 칸을 explicit true로 바꾸고 나열 칸만 false로 둔다. 방침 지도는 모든 현재 장수 id에 `none`이다. 활동 지도는 `userId`가 있는 현재 장수 id에만 `result.baselineActiveTick`이고 NPC 키는 없다.
- F = 0인 새 월드는 첫 입력 전에 origin 초기 장수마다 빈칸 30칸과 방침 `none`을 만든다. 초기 장수는 모두 NPC(`packages/rules/src/world/bootstrap.ts:219`)라 활동 지도는 비어 있고 기준값이 필요 없다. `saveInitialWorld`는 F = 0, 장수마다 false 30행, `defaultPolicy` `none`, `lastActiveTick`·`lastActiveAt` null을 쓴다. 명시적 옛 형식 옵션은 F null·행 없음으로 지금 origin과 바이트가 같고 v2 fixture(`seasonFixture.ts:79`)가 이 옵션을 쓴다.
- F 전 `ReplayState`는 지금 모양 그대로다. 새 키는 없어야 하고 undefined로 두면 안 된다(`hashState`가 던진다, `packages/shared/src/node/hashState.ts:3-19`). 방침 지도 키는 `state.generals` 키와 같고 활동 지도 키는 그중 `userId`가 있는 id와 같아야 한다. 월 검사마다 확인한다. 표지 result의 `baselineActiveTick`은 정수이고 0 이상이며 `clockTick` 이하다. P-1 답이 정해지면 그 규칙(T면 `clockTick`과 같음, 0이면 0)도 검사한다. `lastActiveAt`은 해시에 넣지 않는다.

#### 읽기·실행 경로

- `loadWorld`, `readWorldState`, 서버 `readView`(`apps/server/src/game/queries.ts:23`)는 새 General 열 셋을 떼어 낸다. 응답 투영은 허용 목록이고 `lastActiveAt`은 T2-11이 요구한 곳에만 싣는다. `loadReplayState`는 방침 모드에서만 explicit과 지도를 싣는다.
- 엔진 턴(`turnLoop.ts:173-181`)과 `shiftTurns`(`persist.ts:40-54`)는 방침 모드에서 행 없음을 휴식으로 바꾸지 않는다. explicit은 칸과 함께 옮기고 끝 칸은 `emptyTurn()`이다. 재생의 생성(`replay.ts:114`)은 F 뒤 `emptySlots()`를 쓴다.
- `normalizeSlot`(`packages/rules/src/policy/index.ts:52-54`)의 `explicit ?? true`는 F 경계 함수에서만 쓴다. F 뒤 explicit이 없는 칸은 거부한다.
- 방침 고르기 조건은 정확히 `policyMode && slot.explicit === false && general.userId !== null`이다. `!slot.explicit`은 F 전 큐의 undefined를 잡으므로 쓰지 않는다. NPC 분기(`turn.ts:59-71`)는 explicit을 보지 않으므로 갱신 월드의 true 휴식에서도 NPC AI가 돈다.
- `policy/execute.ts`의 함수는 고르기·실행 부품이고 `runGeneralTurn`을 대신하지 않는다. 대신하면 사람 군주의 국가 턴이 빠지고 최대치 판정이 국가 턴 전 상태로 되며 `target: 'general'`이 빠진다. 실패하면 같은 함수 안에서 휴식과 이유 로그다. 상태·로그·당김은 한 트랜잭션이다.
- 직접 명령과 직접 휴식은 미접속과 관계없이 그대로다. U63에서 미접속은 실행을 바꾸지 않으므로 `isInactive`는 표시(T2-11 idle, T2-14 안내)에만 쓴다. 후보를 더하지 않는다.

#### B-3 활동

지금 제안은 활동 tick을 재생 상태에 넣는다. 부모가 표시 전용으로 정하면 활동 지도, `general.active` kind와 그 재생 갈래, 표지의 `baselineActiveTick`이 빠진다. 어느 쪽이든 NPC는 판정하지 않고 tick은 장수가 속한 월드의 단위다.

- `lastActiveAt`은 실제로 성공한 활동 입력의 `createdAt`만 옮겨 적는다. 그런 입력이 없으면 null이다. F 뒤 장수 생성은 성공한 입력이므로 생성 tick과 그 입력의 `createdAt`을 쓴다.

- `isInactive`는 `tick ≤ lastActiveTick`이면 false다(`2a27bcf`에 반영). 엔진 시계가 아직 실행하지 않은 턴보다 앞설 수 있기 때문이다(`turnLoop.ts:138-143`). 갱신은 SQL `GREATEST`, 재생은 `max`다.
- `turns.set`·`turns.edit` 성공은 같은 트랜잭션에서 잠근 `World.clockTick`을 `result.activeTick`으로 적고 `GREATEST`로 갱신한다. `lastActiveAt`은 그 InputEvent의 `createdAt`이다.
- 엔진이 집행하는 `general.setPolicy`·`general.active`·`general.create`는 디스패처가 받은 tick(지금 생성에 넘기는 값, `turnLoop.ts:113`, `:145`)을 쓴다.
- 실패, STALE, 조회, SSE는 활동이 아니다(위 결정).

#### B-4 디스패처와 권한

- 디스패처 하나가 지원 kind(`general.create`, `general.setPolicy`, `general.active`, `system.policy.enable`) 중 id가 가장 작은 PENDING을 고른다. RUNNING이 아닌 분기에서도 돈다. 생성의 WORLD_CLOSED 거절은 그대로이고 ENDED는 모두 거절한다. 입력을 처리한 반복에서는 게임 행동을 하지 않는다.
- 엔진은 `User`를 FOR SHARE로 읽어 ACTIVE인지(`inputs.ts:36-39` 모양)와 저장된 `general.userId === event.userId`를 확인한다. `event.generalId`는 API가 세션의 장수로 정해 저장한 값이며 클라이언트 값이 아니다. 엔진에는 세션이 없으므로 세션 확인이라고 쓰지 않는다.
- 잠금 순서는 어디서나 World 다음 General이다.
- 방침 모드가 아닌 월드에서 방침 kind를 만나면 예외다. API가 그런 입력을 만들지 않기 때문이다.
- 처리기 소유(T2-07 U62-5, T2-05 B2)는 부모 대기다.

#### API

- `general.setPolicy`는 세션 사용자의 그 월드 장수를 행위자로 정한다. World 잠금 뒤 F가 null이면 PRECONDITION_FAILED다. 부분 유일 색인에 `ON CONFLICT DO NOTHING`으로 넣고 다시 읽어 같은 값이면 그 입력을 기다리고 다르면 CONFLICT다. 최대 5초 대기한다. applied·rejected·pending 모든 결과를 돌려주기 전에 세션을 다시 확인한다.
- 로그인은 ENDED가 아니고 방침 모드이거나 갱신 대기인 월드에서 장수마다 `general.active`를 `ON CONFLICT DO NOTHING`으로 넣는다. 갱신 대기 중이면 표지 뒤에 쌓인다.
- API는 방침과 로그인 활동을 큐에 넣기만 한다. 게임 상태는 엔진이 리스 아래 쓴다. 예턴 저장의 활동 갱신은 기존 예턴 저장 트랜잭션 안의 일이다(위 활동 표).
- 갱신 대기 중 읽기(기술 제안, 부모 최종 계약 수용 대상이며 새 사용자 질문이 아니다): 엔진 전환 전에는 실행이 옛 휴식 그대로이므로 실제로 적용되는 방침은 `none`이다. `general.policy`는 정해진 응답 모양 그대로 `current: 'none'`, `pending: null`, `lastRejected: null`, 같은 `options`와 `inactiveAfterDays`를 돌려준다. `home.get`의 `GeneralPolicySummary`는 `{ key: 'none', name: '없음' }`이다. `policy: null`이나 오류 같은 새 모양을 만들지 않으므로 T2-14 응답 타입은 그대로다. 열 값이 null인 것은 서버 안의 일이고 응답에 새지 않는다.

#### 남는 위험

- 지금 데이터에서 행이 없는 장수는 아직 턴을 돌지 않은 초기 NPC뿐이다(`packages/rules/src/world/bootstrap.ts:219`). 이것은 코드로 강제되지 않는다. 기존 장수에 `userId`를 주는 경로나 장수 삭제 경로가 생기면 손대지 않은 집합 규칙과 활동 지도 키를 다시 확인한다.
- 시험용 옛 형식 옵션 월드는 F null이라 칸 쓰기가 막힌다. 그 월드에서 API 쓰기를 쓰는 기존 시험이 있으면 구현 전에 부모에게 올린다.

### 답 없이 시작할 수 있는 몫 (T2-13a)

AC-M2-17의 첫 두 문장 가운데 순수 규칙 몫이다. AC를 닫지 않고 대기열·AC·리뷰 상태를 바꾸지 않는다. 이 문서는 계획이며 구현 증거가 아니다. T2-13a가 끝나도 T2-13은 닫히지 않는다. 범위는 백엔드 전체다.

- 파일 소유: 새 `packages/rules/src/policy/` 안의 새 파일과 그 시험만. `packages/rules/src/index.ts`의 export, `replay.ts`의 `QueuedTurn`, DB, 서버, 엔진, 화면은 고치지 않는다.
- 내용: `PolicyKey`, 방침 표(이름·`emptyCommand`·`thenCommand`), 장수 상태로 실행할 명령 하나 또는 휴식과 이유를 돌려주는 함수. 명령 판정은 기존 명령 정의의 `check`를 부른다. 후보는 결정 표의 명령과 휴식뿐이다(U63-1). 위 정수 비교의 `isInactive`도 넣는다(U63-2).
- 연결하지 않는 경계: 턴 실행 분기, explicit, migration, InputEvent, 재생, 해시, 미접속 표시.
- 완료 조건: 단위 시험이 방침 6개 각각, 최대치에서 다음 명령, 둘 다 실패하면 휴식과 이유, `none`은 휴식, 출병·이동·임관·귀환이 후보에 없음, `isInactive`의 정확히 14일은 아님·1 tick 많으면 미접속·`turnTermMinutes` 10·30·60을 확인한다. 기존 골든과 재생 해시는 그대로다. 명령은 `pnpm exec vitest run packages/rules/src/policy --maxWorkers 2`이고 실행은 구현자가 한다.
