# T3-02 이메일 인증·비밀번호 재설정·약관·탈퇴

## 2026-10-28 판별 동의 API 첫 묶음

공개 준비 실행 요청에 따라 AC-M3-02의 판별 동의 API를1~2일 몫으로 구현 중이다. 가입 입력은 정본의 `consents: { terms, privacy }`를 쓰며 현재 두 판을 명시해야 계정·세션·인증 토큰과 동의2행을 같은 트랜잭션에 만든다. `legal.agree`는 서버 세션의 활성 사용자를 먼저 잠그고 현재 판만 한 번 기록한다. 중복 요청은 최초 동의 시각을 보존한다. `auth.me`·`account.get`에 문서별 현재 동의 부족 상태를 더하며 이메일 인증 뒤 동의를 검사한다.

운영자·연락처·본문·시행일·보존 기준은 미정이므로 현재 정책 상수는 null이다. `legal.current`는 준비 중 상태와 null 문서를 반환한다. 정책이 없는 운영 환경의 가입·게임 변경과 모든 환경의 동의 기록은503으로 거부한다. 개발 기본 흐름의 기존 계정·게임은 유지하고 동의를 채워 넣지 않는다. HTTP 입력이나 환경 변수로 승인 상태를 바꾸지 않으며 시험용 판은 신뢰한 서버 생성자에서만 넣는다. 실제 승인 뒤 현재 판을 고정하는 별도 검토가 필요하다.

구현 전 독립 리뷰에서 가입 입력을 정본 형태로 바로잡고 착수 승인을 받았다. 판 검증·실제 절차 분류의 단위16건과 서버·시험 파일의 엄격 타입 검사를 통과했다. 브랜치 전환 뒤 남은 구 Prisma 생성물은 첫 서버 타입 검사가 거부했고 현재 schema로 생성한 뒤 통과했다. 시험 파일의 절차 목록 타입과 필수 월드 ID도 고쳤다. 실패 기록은 남겼다.

실제 PostgreSQL·HTTP3파일63건 중 첫 실행은61건 통과·2건 실패였다. PostgreSQL enum의 TERMS→PRIVACY 순서를 문자열 정렬로 잘못 예상한 시험만 고쳤다. 재검사는63건을23.72초에 통과했다. 두 절차의 권한, 가입2행·세션·토큰의 원자성/롤백·commit 뒤 메일, 중복 입력의 최초 시각·판 변경, 비활성화와 동의의 잠금 경합을 확인했다. 정식191년 두 월드·8개 규칙에서 미동의22변경의403·무변경과 동의 뒤 실제 장수 생성·30칸 예약도 통과했다. 실패한 자기 DB는 보존하고 성공한 자기 DB는 OID·연결0을 확인한 뒤 삭제했다.

독립 리뷰가 제품 코드의 열린 P1/P2는 없고 시험 정착 경계의 P2를 지적했다. 모든 HTTP 요청을 생성 즉시 추적하고 동시 요청을 모두 기다린 뒤 실패를 전파하도록 고쳤다. 잠금 경합은 본문 오류와 잠금 해제·연결 종료·대기 요청의 오류를 함께 보존하며 각 정리를 시도한다. 보완 코드 승인 뒤 같은 실제63건을23.08초에 통과했다. 제한시간·skip·제품 코드는 바꾸지 않았다. 전체 검사·최종 근거 리뷰·CI·보호 병합, 동의 화면·본문 승인·탈퇴와 전체 AC는 남아 있다. 사용자 점검용 Docker와 기존 계정·월드는 변경하지 않는다.

첫 전체 검사는 새 응답 계약과 기존 로그인 화면의 타입 불일치를 잡았다. 가입·로그인 mutation은 각각의 타입을 유지하고 성공 처리만 공유하도록 고쳤다. 이전 캐시를 지운 뒤 실제 `auth.me`에서 인증·동의 상태를 다시 읽고 조회 실패 때 성공한 입력을 재전송하지 않는다. 실시간 시험 fixture도 실제 새 응답 계약에 맞췄다. 웹 타입 검사와 관련41건을 통과했고 비구현 담당이 이 두 파일 연결을 승인했다. 실제 PostgreSQL·API·엔진·Chromium의 인증 필수5건은27.7초에 통과했다. 공개 빌드·자산 검사와 공개 Chromium4건도 통과했으며 자기 서비스3개는0으로 종료하고 자기 DB의 OID·연결0을 확인한 뒤 정리했다. 최종 전체 검사·독립 근거 리뷰·필수 CI·보호 병합은 이어서 확인한다.

수정 뒤 전체 `pnpm check`를 통과했다. 단위 시험은291파일5312건이며 Vitest 소요 시간은282.71초다. 최신 보호 main 통합 뒤 전체 PostgreSQL·권한 목록과 기존 Chromium 회귀를 확인하고 최종 문서·실행 근거의 독립 리뷰를 받는다. 필수 CI·보호 병합과 정책·화면·탈퇴의 후속 범위는 남아 있다.

## 2026-10-28 인증 차단 첫 묶음

사용자의 공개 준비 실행 요청에 따라 다음0.5~1일 몫은 실제20개 변경 절차의 이메일 인증 차단이다. 운영자·약관·보존 정책을 정하지 않아도 구현할 수 있는 AC-M3-01 부분이며 동의·탈퇴는 다음 묶음으로 남긴다. 기존 계정·예약·원장을 바꾸거나 과거 동의를 만들어 넣지 않는다.

운영 모드는 인증을 항상 요구하며 끄는 설정을 거부한다. 개발 모드는 기존 데이터와 실행을 보존하고 명시한 `EMAIL_VERIFICATION_REQUIRED=1` 또는 서버 생성자의 신뢰한 설정으로 같은 차단 경로를 검증한다. 설정은0·1·미설정만 받고 HTTP 입력으로 바꾸지 못한다. 개발 기본값이 운영 우회가 되지 않도록 설정과 실제 운영 서버 생성의 거부를 검사한다.

`trpc.ts`의 `verifiedProcedure`는 기존 세션·사용자 요청 한도 뒤에 현재 DB의 본인 인증 여부를 확인한다. 미인증은 기존 공개 사유 `EMAIL_NOT_VERIFIED`의403이고 조회·로그인·가입·로그아웃·재전송·인증·재설정은 계속 가능하다. 각 변경 절차의 고정 메타데이터와 실제 AppRouter 목록을 대조해 새 변경이 인증 대상으로 분류되지 않으면 시험이 실패한다. `account.get`에 서버의 인증 요구 여부를 더해 화면이 개발·운영 상태를 추측하지 않게 하며 기존 `auth.me`의 신원·세션 계약은 유지한다. 게임 화면 가드는 다음 화면 묶음에서 이 상태를 쓴다.

현재 대상은 `general.setPolicy/create`, `turns.set/edit`, `message.send/markRead`, `notice.nation.set/markSeen`, `operation.create/close`, `treaty.propose/respond/break`, `personnel.appoint/dismiss`, `offers.respond`, `nationTurns.set/edit`, `campaign.relationship/unit`의20개다. 인증·복구 예외는 `auth.signup/login/logout`, `account.resendVerification/verifyEmail/requestPasswordReset/resetPassword`의7개다. 옛 본문의7개·34절차는 당시 기준이며 현재74절차·27변경 목록을 우선한다.

수정 범위는 `apps/server/src/auth/`의 설정·확인 모듈, `context.ts`·`trpc.ts`·`server.ts`, 위 변경 라우터와 `account.get`, 실제 HTTP/PG 통합 시험·현재 절차 분류 시험, `.env.example`·운영 문서다. migration·게임 규칙·인증 일시의 일괄 채움은 없다. 실제 전용 PostgreSQL·HTTP에서20경로의 미인증403/사유·익명/제재401·인증 사용자 입력 검사·위조 필드와 전체 DB 무변경, 인증한 정식 시나리오의 생성/예약 성공과 기존 복구 경로를 검사한다. 단위 설정·타입·전체 check·변경에 맞는 권한/실제 Chromium 회귀와 비구현 담당 리뷰·필수 CI·보호 병합이 있어야 이 묶음의 검증을 완료한다. 이 첫 묶음으로 동의·탈퇴·외부 수신·공개 AC 전체를 완료하지 않는다.

### 첫 인증 차단 구현과 검증

2026-10-28 실제20개 변경 절차를 `verifiedProcedure`로 연결하고7개 인증·복구 절차를 분류했다. 운영 설정·실제 서버 생성은 인증 끄기와 개발 모드 위장을 거부하며 기존 계정의 인증 일시·동의·예약·원장을 바꾸지 않는다. `auth.me`와 세션 응답은 유지하고 `account.get`에 요구 여부만 더했다.

설정·실제 절차 분류 단위9건, 전용 PostgreSQL·실제 HTTP의 기존 계정/토큰 검사와 새 차단67건을 통과했다.20경로 각각의 미인증·위조403/사유, 익명/제재401, 인증 사용자의 입력 검사와 전체 public 테이블 무변경을 대조했다. 실제 인증·복구7경로와 정식191년21국491명에서 인증한 사람 장수 생성·30칸 예약 성공도 확인했다. 개발 기본값의 기존 가입·정식491명 휘하/부곡 UI는 실제 PostgreSQL·Chromium12건을 통과했고 자체 API·web·engine이 모두0으로 종료했다. 이 회귀 검사는 다음 묶음의 필수 모드 화면 가드를 대신하지 않는다.

- 메일 발송 서비스 고르기. T3-01에서 사용자가 정한다. 이 계획은 특정 유료 서비스나 계정을 승인하지 않는다.
- 이메일 주소 변경, 2단계 인증, 소셜 로그인 (D-005).
- 요청 제한 계수기 만들기와 CSRF (T3-04). 이 작업은 T3-04의 계수기로 메일 API 두 개의 한도만 건다.
- 로그인 기록(`LoginRecord`)·제재 사유 모델 (T3-05). `LoginRecord`는 구현 순서와 관계없이 탈퇴 때 지운다 (아래 탈퇴 절).

- `InputEvent` schema 정의나 변경. `InputEvent`는 T1-07 단일 소유다. 이 작업은 게임 상태를 바꾸지 않으므로 `InputEvent`를 쓰지 않는다.

### 탈퇴 때 지우는 자료

탈퇴 트랜잭션 하나에서 아래를 모두 처리한다. 다른 작업이 소유한 모델이라도 그 사용자의 개인정보이면 여기서 지운다.

| 자료 | 모델 소유 | 탈퇴 때 |
| ---- | --------- | ------- |
| 계정 | T1-10·이 작업 | `status = WITHDRAWN`, `email = withdrawn+<userId>@invalid`, `passwordHash`를 무작위 값의 해시로, `emailVerifiedAt = null` |
| `Session` | T1-10 | 그 사용자의 행을 모두 지운다 |
| `AccountToken` | 이 작업 | 그 사용자의 행을 모두 지운다 |
| `NotificationTarget` | T2-20 | 그 사용자의 행을 모두 지운다. `endpoint`는 디스코드 웹훅 주소이고 비밀값이다 |
| `NotificationOutbox` | T2-20 | 그 사용자의 행을 상태와 관계없이 모두 지운다 (미발송, 재시도 대기, 포기, 발송 완료) |
| `LoginRecord` | T3-05 | 그 사용자의 행을 모두 지운다. `ipHash`와 `deviceHash`가 함께 사라진다 |
| 기기 쿠키 `did` | T3-05 | 응답에서 지운다 (T3-05 계획 탈퇴 의무 절) |
| `ConsentRecord` | 이 작업 | 보존안이다. 계정 UUID·시각과 다른 자료의 결합 가능성을 확인하고 기간·근거를 사용자 승인 뒤 확정한다 |
| `Sanction`·`AuditLog` | T3-05 | 보존안이다. 실제 저장 항목·목적·기간·근거를 사용자 승인 뒤 확정한다 |
| 장수·로그·메시지·`InputEvent` | 게임 | 그대로 둔다 |

순서와 잠금:

1. 트랜잭션 첫 문장에서 `User` 행을 `SELECT … FOR UPDATE`로 잠그고 `status`가 아직 `ACTIVE`인지 다시 본다. 아니면 아무것도 바꾸지 않고 끝낸다.
2. 계정 값을 바꾸고 위 표의 행들을 지운다. commit 뒤에 `sid` 쿠키를 지운다 (`LoginRecord`가 들어와 있으면 `did`도).

탈퇴와 알림 발송이 겹칠 때:

- T3-04는 D-021의 선행 구현 허용으로 M2보다 먼저 main에 들어갔다. 그래서 T3-04 완료가 T2-20 완료를 뜻하지 않는다. 지금 main의 schema에는 `NotificationTarget`·`NotificationOutbox`가 없다 (`packages/db/prisma/schema.prisma`의 model 목록). 착수 때의 처리는 아래 알림 모델 인계를 따른다.
- 발송 작업은 POST 직전에 짧은 트랜잭션에서 그 사용자의 `User` 행을 `FOR SHARE`로 잠그고 세 가지를 다시 읽는다. 사용자가 `ACTIVE`인지, `NotificationTarget` 행이 있는지, 그 outbox 행이 아직 있는지. 하나라도 아니면 보내지 않고 outbox 행을 지운다. 셋 다 맞으면 이 트랜잭션에서 읽은 `endpoint`로만 보낸다. 일괄 조회 때 읽은 주소를 POST에 다시 쓰지 않는다.
- 탈퇴(`FOR UPDATE`)와 발송 확인(`FOR SHARE`)은 둘 다 `User` 행을 먼저 잠근다. 그래서 탈퇴 commit 뒤에 확인을 시작한 발송은 보내지 않는다. 탈퇴 commit 전에 확인을 마친 발송 1건은 끝까지 갈 수 있다.
- 발송 결과 기록은 `id`로 `updateMany` 하고 0행이면 무시한다. 지워진 행을 재시도로 다시 만들지 않는다.
- 탈퇴 뒤 엔진이 그 장수의 사건으로 outbox 행을 새로 기록해도 위 확인에서 보내지 않고 지워진다. 엔진 동작은 바꾸지 않는다.
- [T2-20 계획](./T2-20.md)의 탈퇴·제재와 발송 절은 이 확인에 대상 활성 여부, 사건 종류 켜짐, 시도 소유 표시(`claimId`)를 더했다. 그 계약이 이 절의 상위 집합이고 탈퇴 경계(확인을 마친 1건만 끝까지 간다)는 같다. 발송 작업은 T2-20 계약대로 만든다.
- `NotificationOutbox`는 발송 대기열이고 게임 판정·재생의 입력이 아니다. API가 이 행을 지워도 게임 상태를 바꾸는 것이 아니다 (AGENTS.md §6).

알림 모델 인계:

- 이 작업 착수 때 T2-20의 `NotificationTarget`·`NotificationOutbox`와 발송 작업이 main에 있으면 이 작업이 위 표대로 지우고 발송 직전 확인을 발송 작업에 넣는다. 아래 탈퇴 시험의 웹훅 행, 발송 중단 행, 경합 행을 모두 채운다.
- 없으면 T2-20이 자기 모델과 발송 작업을 더할 때 `account.withdraw`의 같은 트랜잭션에 두 모델의 삭제를 더하고 위 발송 직전 확인을 같은 계약으로 만든다. 아래 탈퇴 시험의 웹훅 행, 발송 중단 행, 경합 행도 그 작업이 채운다. 두 작업 중 뒤에 병합되는 쪽이 이 의무를 진다.

`LoginRecord` 인계:

- 이 작업 착수 때 T3-05의 `LoginRecord`가 이미 있으면 이 작업이 탈퇴 트랜잭션에서 지우고 `did` 쿠키를 지우며 아래 시험에 넣는다. main `3e5b52a`에는 없다.
- 없으면 T3-05가 자기 모델을 더할 때 `account.withdraw`의 같은 트랜잭션에 삭제와 `did` 쿠키 삭제를 더하고 아래 탈퇴 시험의 IP 해시·기기 해시 행을 채운다.
- 로그인 기록을 쓰는 트랜잭션이 `User` 행을 `FOR SHARE`로 잠그고 `ACTIVE`를 다시 보는 규칙은 T3-05 몫이다. 탈퇴의 `FOR UPDATE`와 맞물려 탈퇴 뒤에는 `LoginRecord`가 생기지 않는다.

두 인계 의무는 [단계 계획](../product/phases.md)의 M3 절에도 적어 둔다. 뒤에 오는 작업이 의무를 채우기 전에는 AC-M3-02를 통과로 바꾸지 않는다.

현재 보존안은 탈퇴해도 게임 기록을 남긴다. 본문과 보존 기준의 사용자 승인 전에는 이 안을 확정 정책으로 연결하지 않는다.

- `User` 행은 묘비로 남기는 안이다. `General.userId`는 `onDelete: NoAction`이라 연결된 계정 행을 지울 수 없다. 남은 UUID와 게임 기록은 다른 자료의 결합 가능성을 별도로 확인하며 개인정보가 없거나 영구 익명이라고 단정하지 않는다.
- 장수·로그·메시지·`InputEvent`는 그대로 둔다. 화면과 API는 탈퇴 계정의 이메일을 어디에도 내보내지 않는다 (지금도 장수 화면은 이메일을 쓰지 않는다).
- 진행 중인 월드의 장수는 API가 바꾸지 않는다. 게임 상태는 엔진만 바꾼다(AGENTS.md §6). 그 장수는 다시 접속하지 않는 장수와 같은 취급을 받는다 (D12 장기 미접속 처리, T2-13).
- 같은 이메일로 다시 가입할 수 있다. 이전 장수와 연결되지 않는다.
- 탈퇴 뒤 보존 자료는 개인정보처리방침 초안(T3-03)과 함께 사용자 승인을 받는다. 승인 결과가 이 표와 다르면 이 계획을 먼저 고친다.

### 오류 계약

화면은 서버 message를 읽지 않는다. 화면이 읽는 값은 `data.code`와 `data.reason` 둘이다. tRPC는 `TRPCError`의 `cause`를 응답에 싣지 않는다. 지금 main의 `apps/server/src/trpc.ts:3-13`에는 T3-04가 넣은 formatter가 있다. 이 formatter는 `stack`을 빼고(`:5`), `data.reason`을 언제나 `null`로 두고(`:9`), `INTERNAL_SERVER_ERROR`의 message를 고정 문구로 가린다(`:10`). 이 작업은 그중 `reason` 값을 정하는 식 하나만 바꿔 공개 필드에 값을 싣는다.

```ts
// apps/server/src/trpc.ts (이 작업이 고친다. 바꾸는 것은 reason 줄과 아래 export뿐이다)
export const PUBLIC_ERROR_REASONS = ['EMAIL_NOT_VERIFIED', 'CONSENT_REQUIRED', 'TOKEN_INVALID'] as const;
export type PublicErrorReason = (typeof PUBLIC_ERROR_REASONS)[number];
export class PublicReasonError extends Error {
  constructor(readonly reason: PublicErrorReason) { super(reason); }
}
const t = initTRPC.context<Context>().create({
  errorFormatter({ shape, error }) {
    const { stack, ...data } = shape.data;
    void stack;
    const reason: PublicErrorReason | null = error.cause instanceof PublicReasonError ? error.cause.reason : null;
    return {
      ...shape,
      data: { ...data, reason },
      message: error.code === 'INTERNAL_SERVER_ERROR' ? '요청을 처리하지 못했습니다.' : shape.message,
    };
  },
});
// 던질 때: new TRPCError({ code: 'FORBIDDEN', message, cause: new PublicReasonError('EMAIL_NOT_VERIFIED') })
```

- 공개 필드는 `data.reason: 'EMAIL_NOT_VERIFIED' | 'CONSENT_REQUIRED' | 'TOKEN_INVALID' | null` 하나다. 모든 오류 응답에 있고 기본값은 `null`이다. 지금 타입은 `null` 하나이며 이 작업 뒤에 위 합집합이 된다.
- `PublicReasonError` 인스턴스만 값을 싣는다. 문자열 cause는 tRPC가 일반 `Error`로 감싸므로 `null`이 된다. 일반 `Error`, Zod 오류, `reason` 필드를 가진 일반 객체도 `null`이다. cause의 message와 다른 필드는 직렬화하지 않는다.
- 기존 `data.code`·`data.httpStatus`·`data.path`와 HTTP 상태 코드는 그대로 둔다. `stack` 제거와 서버 오류 message 가림도 그대로다. 지금 화면은 `data.code`만 읽으므로(`apps/web/src/auth/credentials.ts:29-35`) 영향이 없다.
- `trpc.ts`에서 이 작업이 고치는 범위는 formatter의 `reason` 식, 위 상수·타입·class export, `verifiedProcedure`다. `protectedProcedure`의 `UNAUTHORIZED` 동작과 변경 요청의 `mutation.user` 한도(`trpc.ts:16-28`)는 바꾸지 않는다. `verifiedProcedure`는 `protectedProcedure` 위에 얹으므로 새 변경 절차도 같은 한도를 받는다.

| 상황 | `data.code` | HTTP | `data.reason` |
| ---- | ----------- | ---- | ------------- |
| 미인증 계정의 막힌 API | `FORBIDDEN` | 403 | `EMAIL_NOT_VERIFIED` |
| 새 판 미동의 계정의 막힌 API | `FORBIDDEN` | 403 | `CONSENT_REQUIRED` |
| 인증·재설정 토큰이 무효·만료·사용됨 | `BAD_REQUEST` | 400 | `TOKEN_INVALID` |
| 입력 형식 오류, 옛 판으로 가입 | `BAD_REQUEST` | 400 | `null` |
| 요청 한도 초과 | `TOO_MANY_REQUESTS` | 429 | `null` (남은 시간은 `Retry-After` 헤더) |
| 그 밖 (`UNAUTHORIZED`, `CONFLICT`, 서버 오류) | 기존 값 | 기존 값 | `null` |

새 사유를 더하려면 이 표와 [T3-03](./T3-03.md)을 함께 고치는 계획 변경을 먼저 한다.

계획 단계 확인(2026-10-20, T3-04 formatter가 들어오기 전): 설치된 tRPC 11.19.0과 Fastify로 실제 HTTP 서버를 띄우고 `@trpc/client`로 불러 봤다 (계획용 임시 탐침, 저장소에 넣지 않음). 기본 설정에서는 `FORBIDDEN` + cause가 403·`data.code = FORBIDDEN`만 나오고 `data.reason`이 없었다. 위 formatter를 넣으면 `httpBatchLink`와 `httpLink` 모두 `data.reason = EMAIL_NOT_VERIFIED`가 왔다. 문자열 cause와 내부 `Error` cause는 `null`이었고 응답 본문에 cause가 없었다. `ctx.reply.header('Retry-After', …)`로 단 값은 클라이언트 오류의 `meta.response.headers`에서 읽혔다. 이 탐침은 제품 증거가 아니며 아래 검증이 증거다.

### 공유 요청 제한 계수기 결정

이 절은 [T3-04](./T3-04.md#공유-요청-제한-계수기-결정)와 같은 내용이다. 한쪽을 고치면 다른 쪽도 같은 커밋에서 고친다.

- 소유: `apps/server/src/security/rateLimit.ts`는 T3-04가 만들고 T3-04만 고친다. T3-02는 import만 하고 계수기를 복제하지 않는다.
- 선행: T3-02의 선행은 T3-01과 T3-04다. T3-04는 T3-02에 의존하지 않는다 (T3-04 선행은 M2).
- 인계: T3-04가 리뷰를 통과해 main에 병합된 커밋 SHA를 T3-02 구현 기록 첫 줄에 적고 그 위에서 착수한다. 계약을 바꿔야 하면 T3-02가 파일을 직접 고치지 않고 대기열에 T3-04 담당 작업을 더한다.
- 공개형:

  ```ts
  export interface LimitRule { namespace: string; key: string; limit: number; windowMs: number }
  export interface RateLimitDecision { allowed: boolean; retryAfterSeconds: number }
  export function createRateLimiter(options: { now: () => number }): {
    check(rules: readonly LimitRule[]): RateLimitDecision;
    consume(rules: readonly LimitRule[]): RateLimitDecision;
  };
  ```

- 시계: `now()`는 epoch ms다. `check`·`consume`은 호출마다 `now()`를 한 번만 읽고 그 값으로 모든 규칙을 판정한다. `buildServer`가 서버의 `options.now`(없으면 `Date.now`)로 프로세스당 하나를 만들어 Context의 `rateLimiter`로 넘긴다. 시험은 같은 주입 시계로 요청 시각과 계수기 시각을 함께 움직인다.
- 버킷: `namespace`·`key`·`windowMs` 셋이 버킷 하나다. `windowMs`가 다르면 같은 namespace·key라도 따로 센다.
- 창: 고정 창이다. 창 번호는 `floor(now / windowMs)`이고 구간은 `[n × windowMs, (n + 1) × windowMs)` 반개구간이다. 경계 시각이 되면 바로 새 창(계수 0)이다. 하루 창은 epoch 기준이라 UTC 자정에 바뀐다. 지난 창의 버킷은 다음 호출 때 지운다.
- `check`: 규칙마다 현재 창 계수가 `limit` 이상이면 차단이다. 계수를 바꾸지 않는다.
- `consume`: 모든 규칙을 먼저 판정한다. 모두 허용일 때만 모든 버킷을 1씩 올린다. 하나라도 차단이면 어느 버킷도 올리지 않는다. 동기 함수이고 안에 `await`가 없어 판정과 증가 사이에 다른 요청이 끼지 않는다.
- `retryAfterSeconds`: 허용이면 0이다. 차단이면 차단된 규칙들의 (창 끝 시각 − now) ms 중 가장 큰 값을 `ceil(ms / 1000)`초로 준다.
- 입력: 빈 규칙 배열은 허용·0이다. `limit`·`windowMs`가 양의 정수가 아닌 규칙을 받으면 계수를 바꾸지 않고 예외를 던진다.
- 차단 응답: 부르는 쪽이 `ctx.reply.header('Retry-After', String(retryAfterSeconds))`를 달고 `TRPCError({ code: 'TOO_MANY_REQUESTS' })`를 던진다. `data.reason`은 `null`이다. 헤더 값은 `retryAfterSeconds` 정수 그대로다.
- 비밀: 키에 이메일·IP가 들어간다. 계수기와 부르는 쪽 모두 키·이메일·IP·웹훅 주소를 로그, 파일, DB, 오류 message에 쓰지 않는다. 계수는 메모리에만 있고 재시작하면 빈다.

| namespace | key | 규칙 | 쓰는 곳 | 거는 작업 |
| --------- | --- | ---- | ------- | --------- |
| `auth.login.ip` | IP | 15분에 30번 | `auth.login` 전체 | T3-04 |
| `auth.login.failure` | 정규화한 이메일 + IP | 15분에 5번 | `auth.login` 실패 | T3-04 |
| `auth.signup.ip` | IP | 1시간에 10번 | `auth.signup` | T3-04 |
| `mutation.user` | userId | 1분에 120번 | 로그인이 필요한 변경 API 전체 | T3-04 (T3-02의 새 변경 API도 같은 미들웨어를 쓴다) |
| `mail.verify.resend` | userId | 1분에 1번, 하루에 5번 (한 번의 `consume`에 두 규칙) | `account.resendVerification` | T3-02 |
| `mail.password.reset` | 정규화한 이메일 | 1시간에 3번 | `account.requestPasswordReset` | T3-02 |
| `account.token.ip` | IP | 15분에30번 | 공개 `account.verifyEmail`·`account.resetPassword`의 합산 소비 시도 | T3-02 |

이메일 정규화는 T1-10 가입·로그인과 같은 방식을 쓴다.

- 로그인 순서: `auth.login.ip`를 `consume`한다. 차단이면 429. 다음에 `auth.login.failure`를 `check`한다. 차단이면 비밀번호를 검사하지 않고 429. 그다음 인증을 시도한다. 실패하면 `auth.login.failure`를 `consume`하고 `UNAUTHORIZED`를 준다. 이 `consume`이 차단이어도 응답은 `UNAUTHORIZED` 그대로다. 성공은 실패 버킷을 지우지 않는다.
- 다시 보내기: 이미 인증된 계정이면 계수 없이 `{ ok: true }`. 아니면 `mail.verify.resend` 두 규칙을 한 번에 `consume`하고 차단이면 429와 `Retry-After`.
- 재설정 요청: 계정 유무와 관계없이 `mail.password.reset`을 `consume`한다. 차단이어도 상태 코드·본문이 같은 성공 응답을 주고 `Retry-After`도 달지 않는다. 메일만 보내지 않는다.

### API 계약

기존 `auth.signup` 입력과 `auth.me` 출력에 필드를 더한다. 기존 필드는 바꾸지 않는다.

```ts
auth.signup({ email, password, consents: { terms: string, privacy: string } })
  → { user: { id, email, emailVerified: false } }        // consents 판이 현재 판과 다르면 BAD_REQUEST(reason null)
auth.me() → { user: { id, email, emailVerified: boolean, consentRequired: ('TERMS' | 'PRIVACY')[] } | null }

account.get() → { email, emailVerified, consents: [{ docType, version, agreedAt }] }   // 로그인 필요, 본인 것만
account.resendVerification()            → { ok: true }    // 로그인 필요, 이미 인증이면 ok만. 한도 초과는 TOO_MANY_REQUESTS
account.verifyEmail({ token })          → { ok: true }    // 무인증 가능. 무효·만료·사용됨은 BAD_REQUEST(reason TOKEN_INVALID) 하나로
account.requestPasswordReset({ email }) → { ok: true }    // 항상 같은 응답
account.resetPassword({ token, password }) → { ok: true } // 무효·만료·사용됨은 BAD_REQUEST(reason TOKEN_INVALID)
account.withdraw({ password })          → { ok: true }    // 로그인 필요, 쿠키 삭제
legal.current()                         → { terms: { version, effectiveAt }, privacy: { version, effectiveAt } }
legal.agree({ docType, version })       → { ok: true }    // 로그인 필요, 현재 판만
```

오류는 위 오류 계약의 `data.code`와 `data.reason`으로 구분한다. 화면은 message가 아니라 이 두 값으로 문구를 정한다. 두 값의 타입은 `AppRouter`에서 추론된다.

`auth.me`는 지금 `ctx.user`(`{ id, email }`)를 그대로 돌려준다(`apps/server/src/routers/auth.ts:101`, `apps/server/src/context.ts:10`). 세션 확인이 이미 `User` 행을 함께 읽으므로(`apps/server/src/auth/session.ts:15`) 인증 시각은 같은 조회에서 얻는다. 동의 상태는 `ConsentRecord`를 한 번 더 읽는다.

### DB 저장 보완 후보

다음 묶음은 위 계획의 새 migration 하나로 `emailVerifiedAt`, `AccountToken`, `ConsentRecord`를 더한다. 기존 계정의 인증 시각은 null로 두며 기존 행을 인증 처리하지 않는다. 동의는 사용자·문서 종류·판의 고유 키를 갖지만 실제 본문·판·가입 동의 경로는 아직 연결하지 않는다.

토큰 저장 함수는 User 행을 먼저 잠그고 활성 계정의 같은 용도 미사용 토큰을 무효화한 뒤 새 해시를 저장한다. 소비는 같은 잠금 안에서 용도·미사용·만료 조건으로 한 행만 갱신한다. 인증 시각 또는 비밀번호와 세션 삭제도 그 트랜잭션에서 적용한다. 제재·탈퇴 계정에는 발급·소비하지 않는다. 비밀번호 해시는 행 잠금 전에 계산하고 원문 토큰은 DB와 로그에 쓰지 않는다.

### 공개 오류 사유의 공통 계약

다음1일 이내 몫은 위 오류 계약의 formatter와 추론 타입이다. PublicReasonError의 허용한3값만 공개 사유로 싣고 나머지 cause는 null로 둔다. 내부 오류 메시지와 stack·cause 비노출, 기존 HTTP·tRPC 코드·경로를 유지한다. 잘못 만든 인스턴스의 허용 밖 값도 공개하지 않는다. 실제 계정 절차·verifiedProcedure·HTTP 클라이언트 연결은 이 묶음에 넣지 않으며 단위 검증만으로 전체 계정 인수를 완료하지 않는다. 코드·시험·독립 리뷰와 후속 CI는 확인 중이다.

### 재설정과 기존 세션 조회의 잠금 대조

다음1일 이내 몫은 AC-M3-01의 세션 폐기 경합이다. 실제 PostgreSQL에서 재설정의 User 배타 잠금과 메시지·실시간 알림의 Session/User 공유 잠금을 겹쳐 교착 여부를 먼저 확인한다. 재현되면 계정 확인과 세션 조회의 순서를 맞추고 세션 폐기 뒤 메시지 저장·알림 전송을 거부하는지 검사한다. 기존 계정·세션은 보존하며 정식 판과 별도 DB에서 검사한다. 이 집중 검사만으로 전체 계정 인수를 완료하지 않는다.

메시지 HTTP의401 예상값이500으로 나오는 반례와 실제 PostgreSQL 교착 기록을 확인했다. SSE도 같은 경합에서 연결 실패 경고가 발생했다. 메시지는 기존 World 공유 잠금 다음에, SSE는 세션·장수 조회 전에 User 공유 잠금을 먼저 얻는다. 기존 활성 계정·유효 세션·장수 권한 재확인과 엔진의 User 공유 잠금은 유지한다.

### 계정 토큰 API 연결 몫

다음1~2일 몫은 AC-M3-01의 `account.get`·`resendVerification`·`verifyEmail`·`requestPasswordReset`·`resetPassword`다. 기존 공유 요청 제한과 공개 오류 사유, 실제 토큰 저장 함수를 연결하고 capture 메일함을 쓰는 실제 HTTP로 검증한다. API는 사용자 지정 ID를 받지 않으며 인증·재설정의 무효·사용·만료를 같은 공개 사유로 거부한다. 재설정 요청은 계정 유무·횟수 제한·메일 실패와 관계없이 같은 성공 응답을 유지한다.

개발 실행은 capture를 사용하고 운영 실행은 운영 전송이 없으면 시작을 거부한다. 운영 서비스·실제 수신, 가입 동의·미인증 게임 변경 차단·탈퇴·화면은 별도 몫이다. 이 연결만으로 전체 AC를 마감하지 않는다. 새5절차의 실제 권한 분류도 추가하고 기존 절차의 검사는 유지한다.

독립 리뷰는 임의 토큰의 비밀번호 해시 비용과 시작 검사 자식의 종료 대기를 지적했다. 공개 인증·재설정 소비는 같은 `account.token.ip` 버킷으로 IP당15분30회를 제한하고 초과 시429·`Retry-After`를 준다. 계수기 구현은 바꾸지 않는다. 재설정은 해시 계산 전에 저장된 후보의 용도·미사용·만료·활성 계정을 저비용으로 확인하며 실제 소비 트랜잭션의 User 잠금·조건부 갱신을 다시 적용한다. 시작 거부 시험은 timeout에서도 소유 자식을 종료하고 출력 스트림까지 닫힌 뒤 판정한다.
