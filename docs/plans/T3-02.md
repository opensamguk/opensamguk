## 계획 (Claude)

### 목표

- 가입할 때 이메일 인증을 거친다. 비밀번호 재설정 링크는 1회용이고 30분 뒤 만료된다 (AC-M3-01).
- 약관·개인정보처리방침 동의가 버전과 함께 기록된다. 탈퇴하면 개인정보가 지워지고 게임 기록은 익명이 된다 (AC-M3-02).

### 하지 않는 것

- 메일 발송 서비스 고르기. T3-01에서 사용자가 정한다. 이 계획은 특정 유료 서비스나 계정을 승인하지 않는다.
- 이메일 주소 변경, 2단계 인증, 소셜 로그인 (D-005).
- 요청 제한 전체와 CSRF (T3-04). 이 작업은 메일을 보내는 API의 횟수 제한만 직접 둔다.
- 로그인 기록·제재 사유 (T3-05). 탈퇴 시 지울 대상에는 넣는다 (아래 탈퇴 절).
- 약관·개인정보처리방침 본문 확정. 본문은 T3-03에서 초안을 쓰고 공개 전에 사용자가 승인한다 (T3-15 점검 항목).
- `InputEvent` schema 정의나 변경. `InputEvent`는 T1-07 단일 소유다. 이 작업은 게임 상태를 바꾸지 않으므로 `InputEvent`를 쓰지 않는다.

### 고정 규칙 확인

사용자 승인을 기다리는 핵심 규칙 변경 10건(행군·자원 5종·縣식 생산·능력치 5종·명망 상한·여러 주공·36순 달력·해전·계책 패·한 화면 통합)은 이 작업과 관계없고 도입하지 않는다.

### 결정: 데이터

새 migration 하나로 더한다. 기존 migration은 고치지 않는다.

| 모델 | 필드 | 메모 |
| ---- | ---- | ---- |
| `User` | `emailVerifiedAt DateTime?` 추가 | data-model.md의 계획 필드. 기존 행은 null로 두고 다음 로그인 때 인증을 받는다 |
| `AccountToken` (새로) | `id`(토큰 SHA-256), `userId`, `purpose`(VERIFY_EMAIL·RESET_PASSWORD), `expiresAt`, `usedAt?`, `createdAt` | 원문 토큰은 저장하지 않는다. `@@index([userId, purpose])` |
| `ConsentRecord` (새로) | `id`, `userId`, `docType`(TERMS·PRIVACY), `version`, `agreedAt` | data-model.md 그대로. 탈퇴해도 지우지 않는다 (동의 사실의 증거, 개인정보 없음) |

### 결정: 흐름

| 흐름 | 규칙 |
| ---- | ---- |
| 가입 | 지금처럼 계정과 세션을 만든다 (T1-14 흐름 유지). 같은 트랜잭션에 현재 판의 약관·개인정보 동의 2행을 기록하고 인증 토큰을 만든 뒤 commit 후 메일을 보낸다. 메일 실패는 가입을 되돌리지 않고 다시 보내기로 푼다 |
| 미인증 계정 | 로그인·로그아웃·`me`·다시 보내기·탈퇴·약관 조회만 된다. 장수 생성과 월드 안의 모든 변경 API는 새 미들웨어 `verifiedProcedure`가 `FORBIDDEN`(`cause: EMAIL_NOT_VERIFIED`)으로 거부한다 |
| 인증 토큰 | 32바이트 base64url, 24시간 만료, 1회용. 새로 보내면 이전 VERIFY_EMAIL 토큰은 무효 |
| 재설정 요청 | 주소가 없거나 탈퇴·제재 계정이어도 같은 응답을 준다 (계정 존재를 드러내지 않는다). 계정이 있으면 메일을 보낸다 |
| 재설정 토큰 | 32바이트 base64url, **30분 만료, 1회용**. `usedAt IS NULL AND expiresAt > now` 조건의 `updateMany`로 원자적으로 소비한다. 새 요청이 오면 이전 RESET_PASSWORD 토큰은 무효 |
| 재설정 완료 | 새 비밀번호를 argon2id로 저장하고 그 사용자의 세션을 모두 지운다. 자동 로그인하지 않는다 |
| 링크 모양 | `${PUBLIC_ORIGIN}/verify-email#token=…`, `${PUBLIC_ORIGIN}/reset-password#token=…`. 토큰을 URL 조각(#)에 두어 서버 접근 로그와 Referer에 남지 않게 한다 |
| 약관 판 | `apps/server/src/legal/versions.ts`가 현재 판(`TERMS`, `PRIVACY`)을 가진다. 판이 바뀌면 `me`의 `consentRequired`에 나오고 동의 전에는 `verifiedProcedure`와 같은 방식으로 게임 변경 API가 막힌다(`cause: CONSENT_REQUIRED`) |
| 탈퇴 | 비밀번호를 다시 받는다. 한 트랜잭션에서 `status = WITHDRAWN`, `email = withdrawn+<userId>@invalid`, `passwordHash`를 무작위 값의 해시로 바꾸고 `emailVerifiedAt = null`. 세션·계정 토큰을 지운다. T3-05의 `LoginRecord`가 먼저 들어와 있으면 그 행도 지운다 |

탈퇴해도 게임 기록은 남는다.

- `User` 행은 묘비로 남는다. `General.userId`는 `onDelete: NoAction`이라 행을 지울 수 없고 남은 값은 개인정보가 없는 UUID다.
- 장수·로그·메시지·`InputEvent`는 그대로 둔다. 화면과 API는 탈퇴 계정의 이메일을 어디에도 내보내지 않는다 (지금도 장수 화면은 이메일을 쓰지 않는다).
- 진행 중인 월드의 장수는 API가 바꾸지 않는다. 게임 상태는 엔진만 바꾼다(AGENTS.md §6). 그 장수는 다시 접속하지 않는 장수와 같은 취급을 받는다 (D12 장기 미접속 처리, T2-13).
- 같은 이메일로 다시 가입할 수 있다. 이전 장수와 연결되지 않는다.

### 결정: 메일

- `MailTransport` 인터페이스 하나: `send({ to, subject, text, html? })`. 템플릿은 `apps/server/src/mail/templates.ts`에 두고 [글쓰기 규칙](../writing-style.md)을 따른다.
- `MAIL_TRANSPORT=capture`: 메일을 `MAIL_CAPTURE_DIR`(기본 `.mail-outbox/`, Git 제외)에 JSON 파일로 쓴다. 개발·통합 시험·E2E의 테스트 메일함이다. `NODE_ENV=production`에서 이 값을 쓰면 서버가 시작을 거부한다.
- 운영 transport는 T3-01 결정 뒤 같은 인터페이스로 더한다. 키는 `.env.production`에만 두고 저장소·명령줄 인자·로그에 넣지 않는다.
- 로그에는 메일 종류와 결과만 남긴다. 주소, 토큰, 링크는 남기지 않는다.
- 메일을 보내는 API 횟수 제한: 인증 메일 다시 보내기는 사용자당 1분에 1번·하루 5번, 재설정 요청은 주소당 1시간에 3번. 다시 보내기가 한도를 넘으면 `TOO_MANY_REQUESTS`를 준다. 재설정 요청은 한도를 넘어도 같은 성공 응답을 주고 메일만 보내지 않는다 (존재 노출 방지). 시계는 주입한다.
- 계수기는 `apps/server/src/security/rateLimit.ts` 하나를 T3-04와 같이 쓴다. T3-02와 T3-04 중 먼저 반영되는 쪽이 이 파일을 만들고 나중 쪽은 그대로 쓴다.

### API 계약

기존 `auth.signup` 입력과 `auth.me` 출력에 필드를 더한다. 기존 필드는 바꾸지 않는다.

```ts
auth.signup({ email, password, consents: { terms: string, privacy: string } })
  → { user: { id, email, emailVerified: false } }        // consents 판이 현재 판과 다르면 BAD_REQUEST
auth.me() → { user: { id, email, emailVerified: boolean, consentRequired: ('TERMS' | 'PRIVACY')[] } | null }

account.get() → { email, emailVerified, consents: [{ docType, version, agreedAt }] }   // 로그인 필요, 본인 것만
account.resendVerification()            → { ok: true }    // 로그인 필요, 이미 인증이면 ok만
account.verifyEmail({ token })          → { ok: true }    // 무인증 가능. 무효·만료·사용됨은 BAD_REQUEST(cause: TOKEN_INVALID) 하나로
account.requestPasswordReset({ email }) → { ok: true }    // 항상 같은 응답
account.resetPassword({ token, password }) → { ok: true } // 무효·만료·사용됨은 BAD_REQUEST(cause: TOKEN_INVALID)
account.withdraw({ password })          → { ok: true }    // 로그인 필요, 쿠키 삭제
legal.current()                         → { terms: { version, effectiveAt }, privacy: { version, effectiveAt } }
legal.agree({ docType, version })       → { ok: true }    // 로그인 필요, 현재 판만
```

오류는 `code`와 `cause` 문자열로 구분한다. 화면은 message가 아니라 이 값으로 문구를 정한다 (T1-14와 같은 방식).

### 검증

통합 시험은 `pnpm test:int`의 실제 PostgreSQL과 capture transport로 한다. 시계는 주입한다.

| AC | 무엇 | 어떻게 |
| -- | ---- | ------ |
| M3-01 | 인증 | 가입 → 메일함에 1통 → 토큰으로 인증 → `me.emailVerified = true` |
| M3-01 | 미인증 차단 | 미인증 사용자의 장수 생성·예턴 저장 → `EMAIL_NOT_VERIFIED`, DB 변경 없음 |
| M3-01 | 인증 토큰 | 만료(24시간 + 1초), 두 번째 사용, 다시 보내기 뒤 이전 토큰 → 모두 `TOKEN_INVALID` |
| M3-01 | 재설정 1회용 | 같은 토큰을 동시에 두 번 → 한 번만 성공 |
| M3-01 | 재설정 30분 | 29분 59초 성공, 30분 0초 실패 (주입한 시계) |
| M3-01 | 재설정 뒤 세션 | 다른 기기 세션이 모두 끊김, 이전 비밀번호로 로그인 실패 |
| M3-01 | 존재 노출 | 없는 주소·있는 주소의 재설정 요청 응답 본문과 상태 코드가 같음 |
| M3-01 | 횟수 제한 | 다시 보내기 1분 안 두 번째 → `TOO_MANY_REQUESTS`, 재설정 4번째 → 메일 없음 |
| M3-02 | 동의 기록 | 가입 → `ConsentRecord` 2행(판·시각). 옛 판으로 가입 → 거부. 판 올림 → `consentRequired` → `legal.agree` → 해제 |
| M3-02 | 탈퇴 | DB 조회: 원래 이메일 문자열이 어떤 테이블에도 없음, 세션·토큰 0행, 장수·로그 행 수 그대로 |
| M3-02 | 탈퇴 재로그인 | 탈퇴 계정 로그인 실패, 같은 주소로 새 가입 성공 |
| 공통 | 권한 다섯 가지 | 새 API마다 성공·무인증·다른 사용자·제재·잘못된 입력 (T3-04 대조 목록에 등록) |
| 공통 | 비밀값 | 로그 스트림에 토큰·링크·주소 없음 (T1-10 시험과 같은 방식) |

화면을 거친 E2E(테스트 메일함 읽기)는 T3-03이 한다. 실제 메일함 수신 1회는 T3-01 결정 뒤 운영 transport로 확인하고 그 기록을 이 문서의 구현 기록에 남긴다. capture 시험만으로 실제 수신을 대신하지 않는다.

### 상대 영역에 필요한 것 (T3-03)

- 위 API 계약과 `cause` 값 목록: `EMAIL_NOT_VERIFIED`, `CONSENT_REQUIRED`, `TOKEN_INVALID`.
- E2E가 읽을 메일함: `MAIL_CAPTURE_DIR`의 JSON (`{ to, subject, text, sentAt }`). Playwright가 같은 폴더를 읽는다.
