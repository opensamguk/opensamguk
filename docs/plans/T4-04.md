## 계획 (Claude)

### 1. 목표와 승인 범위

이미 승인된 MVP와 Phase 2 AC-P2-02·03의 남은 검증 가운데 화면·E2E 몫을 채운다. 켠 월드에서 계략 네 명령을 기존 예턴 편집기로 고르고 대상 도시를 넣어 저장하며 실제 엔진 한 턴 뒤 결과가 최근 실행 결과와 개인 기록에 보이는지 실제 서버·DB·Chromium으로 본다. 끈 월드에서는 계략이 목록에 없고 기본 장수 명령 목록이 그대로인지 본다.

부모의 이번 채택은 새 제품 선택이 아니며 사용자 재승인을 기다리지 않는다. 대상 AC 문장과 상태는 [인수조건](../product/acceptance-criteria.md)의 AC-P2-02·03 행 그대로이고 이 작업으로 바뀌지 않는다. 실제 실행과 반대 리뷰가 끝나도 AC 전체 완료가 아니다. AC-P2-02 (나)의 PostgreSQL 롤백·SIGKILL·재생 몫과 AC-P2-03 (나)의 엔진 통합 몫은 [T4-17 계획](./T4-17.md) (나)의 N1·N2 증거에 귀속되며 이 E2E 증거로 세지 않는다.

### 5. 고정물과 월드 계약

N1은 `apps/engine/test/fixtures/ext-fire-5bd54b2.json`의 `cases.successWithInjury`·`badTargetOwnCity`·`probabilityMiss`, N2는 `apps/engine/test/fixtures/ext-n2-179bea4.json`의 `commands.<key>.cases.success`·`badTargetOwnCity`·`probabilityMiss`를 그대로 읽는다. `initial`은 배열 모양이고 `expected.afterRuleTurnState`는 record 모양(`generals`·`cities`·`nations`)이다. 대조는 `tools/t4-17-ext.integration.test.ts`와 `tools/t4-17-ext-n2.integration.test.ts`의 정상 factory와 투영을 따른다.

월드는 정상 `saveInitialWorld`에 `extFormat: 1`과 원본 프리셋(`t417-fixed-fire`, `t417-fixed-n2`)으로 만든다. actor 1, tick 100, seed, args, initial, 방침 `none`, 규칙·효과·RNG·제품값은 그대로다. 바꾸는 것은 `n1-fixture-actor`·`n1-fixture-defender`, `n2-fixture-actor`·`n2-fixture-defender` 자리 표시를 실제 계정 ID로 바꾸는 것뿐이며 기대값 쪽도 대조할 자리에서만 같은 매핑을 한다. 상태 효과 주입과 seed·RNG 조작은 없다.

13번 off 월드는 같은 정상 `saveInitialWorld`를 기본 끔 옵션(`extFormat` 없음)과 기존 제품 프리셋 `regular`(`commands: null`)로 불러 만들고 장수·도시 모양은 N1 성공 사례 initial을 쓴다. 시험은 그 worldId만 쓴다. 기존 `e2eWorld`의 첫 RUNNING 월드는 다른 작업의 월드를 집을 수 있어 쓰지 않는다. 기대 목록은 `apps/server/src/routers/commands.ts:6-13`의 `commandList`(27개)다.

계정은 `e2e/policyFixture.ts`의 선례대로 계정 행과 `TEST_PASSWORD` 해시만 직접 만들고 세션은 화면 로그인으로 서버가 만든다. 로그인 호출 경로는 정상 그대로 쓴다. 정상 `saveInitialWorld`는 legacy 재생이 아니면 `policyFromSequence: 0`을 넣는다(`apps/engine/src/world/persistence.ts:136`). `apps/server/src/game/policy.ts:50-61`의 `queueLoginActivity`는 그 값이 null이고 PENDING `system.policy.enable` 입력이 없을 때만 건너뛴다. 0은 null이 아니므로 이 고정물 월드에서도 정상 로그인은 `general.active` 입력을 기록하는 경로를 지난다. 시험이 그 입력을 따로 만들지 않고 고정물 기대값도 바꾸지 않는다. 같은 IP 15분 30회 한도 아래로 로그인 총수를 17회로 계획했다(1번 2회, 2~13번 1회씩, 14번 2회, 15번 1회). 한도 우회나 가짜 시계는 없다.

활동 입력은 별도 bookkeeping이라 고정 명령 대조와 섞이지 않는다고 source로 본다. `apps/engine/src/inputs.ts:150-168`은 장수의 `lastActiveTick`·`lastActiveAt`과 그 InputEvent의 status·sequence·result를 바꾼다. sequence는 `:164`의 `nextActionSequence(tx, world.id)`에서 받으며 이 함수는 `World.actionSequence`를 1 올린다(`packages/db/src/inputEvents.ts:5-12`). 이 bookkeeping은 게임 RNG를 쓰지 않는다. `apps/engine/src/turnLoop.ts:162-175`의 입력 처리 단계는 `execution: null`을 돌려주며 `:104`는 null이 아닌 명령 실행만 목록에 넣는다. `apps/engine/src/worldLoader.ts:20`의 규칙 상태 투영은 `lastActiveTick`·`lastActiveAt`·`defaultPolicy`를 뺀다. `packages/rules/src/commands/turn.ts:61`에서 저장한 명시 명령은 빈 칸 방침 선택을 타지 않고 `:84`의 명령 RNG는 `rngFor(seed, 'turn', tick, generalId)`라 활동 입력 sequence와 무관하다. 시험의 `turnInputs`(`e2e/stratagemFixture.ts:407`)는 `turns.set`만 골라 내보낸다. 그래서 실제 `general.active`의 수·종류·처리 결과는 원기록에 없고 관측하지 못했다. 이 문단의 줄 번호는 실행 source `d4ad313`의 줄이다.

정정 내력: source 준비 때 이 문단은 F0·기본 끔 고정물 월드에서 로그인이 `general.active` 입력을 넣지 않는다고 적었다. Codex가 문서 정정 지시에서 숫자 0에 null 분기를 잘못 적용해 생긴 오류다. 실행 코드와 기대값은 그 문장과 상관없이 바뀌지 않았다.

### H1 대상 장수 고르기 (개인 칸, 명령별 후보)

- 지금 `CommandPicker`는 `generals`가 있으면 모든 명령의 `generalId` 칸을 그 목록의 고르기로 바꾸고 번호 칸을 없앤다(`CommandPicker.tsx:270`, 이름표 `:337`). 국가 칸에서는 맞다. 포상·몰수·발령의 대상이 모두 같은 국가 장수이기 때문이다. 개인 칸에 같은 국가 장수 목록을 일괄로 넘기면 기본 명령 `invite`(등용)도 그 목록으로 묶인다. 등용 대상은 재야여야 하므로(`packages/rules/src/commands/personnel.ts`의 `invite` 검사, `재야 장수만 등용할 수 있습니다.`) 등용할 수 없게 된다.
- 그래서 후보를 명령별로 준다. `CommandPicker`에 선택 칸 `generalChoicesFor?: (commandKey: string) => Array<{ id: number; name: string }> | null`을 더한다. 값이 목록이면 그 명령의 `generalId`를 이름으로 고르고 `null`이면 지금처럼 번호 칸이다. 기존 `generals` 칸(`source.ts:57`)은 그대로 두고 국가 칸(T2-06)은 지금처럼 `generals`만 넘긴다. 두 칸이 함께 오면 `generalChoicesFor`가 먼저다.
- 개인 칸의 `generalChoicesFor`는 대상 장수 범위가 `nation`인 확장 명령에만 목록을 준다. 목록은 세션 장수 국가의 장수이며 `nation.get`의 `generals`에서 id와 이름만 쓴다. 기본 명령(등용 포함), 범위가 `any`인 확장 명령, 범위를 적지 않은 명령, 재야 장수는 모두 `null`이라 번호 칸이다. 범위 표는 H2의 파일이 생길 때 그 안에 둔다.
- 후보는 표시를 돕는 값이다. 대상이 맞는지는 서버의 저장·사전 검사가 다시 본다.
- 착수 조건: `generalId` 인자를 받는 확장 일반 명령(예: T4-59 증여, T4-15 선양)이 규칙으로 정의된 뒤. 그 전에는 만들지 않는다.

### H2 확장 인자 표는 필요할 때 만든다

- §3의 판단을 따른다. 기본 이름표(`args.ts`의 `LABELS`·`ENUM_LABELS`)로 그릴 수 있는 명령만 있으면 `apps/web/src/turns/extArgs.ts`를 만들지 않는다.
- 새 인자 key(예: T4-61 숙련전환의 계열 열거, MQ-1 뒤)나 H1의 범위 표, T4-51의 국가 명령 도시 범위가 실제로 필요한 첫 화면 PR이 그 파일을 만든다. 기본 표와 같은 key를 확장 표에 다시 적으면 단위 시험이 실패하게 한다.
- 규칙 작업에 주는 요청: 뜻이 같은 인자는 기본 key를 쓴다(대상 도시 `cityKey`, 대상 국가 `nationId`, 대상 장수 `generalId`, 금·쌀 `resource`, 수량 `amount`, 이름 `name`, 색 `color`). 원작 이름(`destCityId`, `destGeneralID`, `isGold`)을 그대로 옮기지 않는다. 계략 네 명령은 이미 `cityKey`다(§3).

### H3 꺼진 명령 거부의 화면 몫

두 경우를 나눈다.

| 경우 | 지금 base (§9) | 준비 수리 tree `6ae9991` (PG 미실행) |
| ---- | -------------- | ------------------------------------ |
| 확장을 켜지 않은 월드(OFF)에서 확장 key 저장 | HTTP 400 `BAD_REQUEST` `명령과 인자를 확인하세요.` | HTTP 400 `BAD_REQUEST` `이 월드에서 꺼진 명령입니다.`, 오류 `data.reason = 'COMMAND_DISABLED'`(그 tree의 `apps/server/src/trpc.ts:18-21`, `game/slots.ts:22-28`) |
| 켠 월드에서 허용 목록 밖 key 사전 검사 | HTTP 200 `{ ok: false, code: 'COMMAND_DISABLED', message }`(§9의 `turns.ts:159-160`) | 같음(그 tree의 `turns.ts:161`) |

- 준비 수리의 판정은 `READY_FOR_ALLOCATED_PG_ONLY`다. 비PG 단위 12건 통과, HTTP 11건 수집, Codex 준비 리뷰 `PASS_T404_COMMAND_DISABLED_PREPARATION`이며 PG 실행과 그 증거 리뷰는 0이다(`E:/codex-artifacts/opensamguk/backend-integration/t4-04-command-disabled-cbdf8d2/readiness-handoff.json`). 그래서 이 표의 오른쪽은 PG 통과가 아니다.
- 화면은 지금처럼 tRPC 코드와 서버 문구만 본다. 저장 오류는 문구를 그대로 보이고(`useTurnDraft.ts`의 일반 오류 갈래) `data.reason`으로 화면을 가르지 않는다. 그래서 수리가 들어와도 화면 코드는 바뀌지 않는다.
- 후속 E2E: 수리가 PG 증거와 함께 병합되면 §4의 13번과 같은 자기 off 월드에서 확장 key 초안을 저장해 `이 월드에서 꺼진 명령입니다.`가 보이고 칸이 그대로인지 보는 사례 하나를 더한다. 그 전에는 넣지 않는다. 이 사례가 통과해도 AC-P2-02의 서버·DB 몫 판정은 서버 작업의 증거로 한다.
