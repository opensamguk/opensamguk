### main 기준 사실 (2026-10-24, `eb9c16a`)

- 배포 파일은 T3-04 검토용 `game_security` snippet인 `deploy/security.caddy` 하나뿐이다. Dockerfile, 운영 compose, `tools/` 아래 네 shell, HTTP `/healthz`는 없다.
- `docker-compose.yml`은 개발용 `postgres:18-alpine` 하나를 `127.0.0.1:5433`에 띄운다. CI는 `postgres:18.6-alpine@sha256:77f585114c32fbca283dc835b0596f4e52b51b4c6662d7810b2f4084f60a1873`을 쓴다(`.github/workflows/ci.yml:53`).
- server는 `127.0.0.1`에만 listen한다(`apps/server/src/index.ts:23`). 정적 화면을 제공하지 않으며 HTTP 경로는 `/trpc`(`apps/server/src/server.ts:110-111`)와 `/sse`(`apps/server/src/realtime/index.ts:237`)뿐이다. [런타임](../architecture/runtime.md) §1의 정적 화면 제공과 release-operations §5 TODO의 `/api`는 실제와 다르다.
- 상태 확인은 tRPC `health`다(`apps/server/src/router.ts:38-46`). HTTP로는 `GET /trpc/health`이며 DB가 죽어도 200에 `db: 'down'`을 돌려준다. 그래서 상태 코드만으로 성공을 판정하지 않는다. GET은 Origin 검사 대상이 아니다(`server.ts:69-73`).
- `/sse`는 Origin이 있으면 `PUBLIC_ORIGIN`과 같아야 하고 `Sec-Fetch-Site: cross-site`를 거부한다. 응답은 `text/event-stream`과 `x-accel-buffering: no`다(`realtime/index.ts:238-266`). 개발 Vite 프록시도 `/trpc`와 `/sse` 둘만 넘긴다(`apps/web/vite.config.ts:18-22`).
- pino 구조화 로그와 redact(`server.ts:48-58`), 엔진의 `EngineHeartbeat` 기록(`apps/engine/src/main.ts:18-35`)과 감독의 오류 기록은 이미 있다. 이 계획에서 새로 만들지 않는다.
- server와 engine은 `DATABASE_URL` 환경값만 읽는다(`apps/server/src/index.ts:4`, `apps/engine/src/index.ts:11`). `*_FILE` 같은 파일 입력은 없으므로 runtime §2의 `/run/secrets` 전제와 맞지 않는다.
- `packages/db/prisma.config.ts`는 루트 `.env`가 있으면 `process.loadEnvFile`로 읽는다. 이미 있는 값과 어느 쪽이 이기는지 코드가 정하지 않으므로 복원 시험이 이 경로로 개발 DB에 붙을 위험이 있다.
- server는 빌드 산출물 없이 `tsx`로 `src/index.ts`를 실행한다(`apps/server/package.json`). 감독은 자식을 `process.execPath --import tsx apps/engine/src/index.ts --world <ID>`로 띄운다(`apps/engine/src/supervisor.ts:37-41`). 화면은 `vite build`로 `apps/web/dist`를 만든다.
- 재생 도구는 `tools/replay.ts`다. `--world <ID> --output <새 파일>`이 DB에서 재생 기록을 내보내고 `--from <파일> --months <N>`이 초기 상태와 입력으로 월별 해시를 다시 계산해 대조한다. 게임 상태 해시는 `hashState(readWorldState(db, worldId))`(`apps/engine/src/world/persistence.ts:122`)와 월별 `YearbookSnapshot.stateHash`다. 리스·하트비트·시계 기준 시각은 이 해시에 들어가지 않는다(runtime §4).
- 월드 생성·시계 전환·한 달 진행에 쓸 기존 진입점은 `loadInitialWorld`·`saveInitialWorld`, `controlClock`(`apps/engine/src/world/clock.ts:6`), `acquireLease`, `TurnLoop.advanceTo`, 엔진 CLI `--world`, 소유 자식 종료 `stopOwnedChild`(`apps/engine/src/process-lifecycle.ts:47`)다. 운영 명령으로는 `world:create`·`world:start`·`world:pause`·`world:resume`·`world:accelerate`가 있다.
- `TurnLoop.advanceTo(B)`는 월드가 `RUNNING`일 때만 진행하고 목표 tick이 주어지면 시계 모드와 실시간을 보지 않는다(`apps/engine/src/turnLoop.ts:126,146,153-154`). `releaseLease`도 있다(`apps/engine/src/lease.ts:49`). 엔진 CLI `--world`에는 멈출 경계를 받는 옵션이 없어 신호를 받을 때까지 계속 진행한다. `apps/engine/test/monthlyWorker.ts`는 commit 전후에 멈춰 부모가 kill하게 하는 주입용 자식이라 정상 종료하지 않는다.
- migration 없이도 `InputEvent.kind`, `replayOrigin.capability`, JSON 자료 계약은 바뀔 수 있다. 저장된 자료의 형식·capability를 읽어 release별 지원판과 대조하는 helper나 지원판 선언은 `eb9c16a`에 없다.
- 통합 시험은 `tools/*.integration.test.ts`이며 `vitest.integration.config.ts`(파일 직렬, 30초)로 돈다. CI는 `pnpm check`와 `pnpm test:authz`만 돌리고 `pnpm test:int`는 돌리지 않는다. `pnpm test:int`는 먼저 `opensamguk_test`에 migration을 적용한다(`tools/run-integration.ts`).
- 이 계획을 고친 Windows 개발기에는 `C:/Program Files/Git/bin/bash.exe`와 docker·ssh·scp CLI가 있다. PATH의 `bash.exe`는 WSL 실행기다. 네이티브 `pg_dump`·`pg_restore`는 PATH에 없다. Docker daemon, 받아 둔 이미지, WSL, 원격 서버는 확인하거나 띄우지 않았으므로 있다고 가정하지 않는다.

`05464f2`에서 B1 정정 때 더 읽은 사실:

- 리스 TTL은 `LEASE_TTL_MS = 15_000`이다(`apps/engine/src/lease.ts:4`). `acquireLease`는 만료된 행만 가져오고 아니면 `null`이다(`:23-39`). `renewLease`는 같은 owner·fencing token이고 아직 만료 전일 때만 늘리며 아니면 `LeaseLostError`를 던진다(`:41-47`). `releaseLease`는 같은 owner·token 행의 `expiresAt`만 현재 DB 시각으로 당긴다(`:49-54`).
- `runEngine`은 실행권을 얻은 뒤 `LEASE_TTL_MS / 3`(5초)마다 하나의 순차 루프로 `renewLease`를 부르고 실패하면 session을 abort한다. `finally`에서 갱신 루프를 기다린 뒤 `releaseLease`를 부른다(`apps/engine/src/main.ts:88-105,149-155`). 이 함수는 `poll` 루프 전용이라 목표 tick의 `advanceTo`에는 쓸 수 없다.
- `TurnLoop.advanceTo(tick, signal)`는 매 단계 트랜잭션 안에서 `lockLease`, commit 전 `signal.throwIfAborted()`와 `assertLease`를 부른다(`apps/engine/src/turnLoop.ts:77-82,118-131,315-316`). 단계 사이에 abort되면 오류 없이 돌아오므로(`:96`) 호출자가 도달 tick을 따로 확인해야 한다. `TurnLoop`은 생성 때 `publicMapConfig(process.env)`를 읽는다(`:62`).
- `stopOwnedChild`는 5초 뒤 `SIGKILL`을 걸고 `requestShutdown`을 부른다(`apps/engine/src/process-lifecycle.ts:47-60`). Windows에서는 신호 대신 IPC로 `{ type: 'opensamguk:shutdown' }`을 보내고 IPC가 끊겼으면 아무것도 보내지 않는다(`:29-45`). 자식 쪽 `onShutdownRequest`는 SIGTERM·SIGINT와, `process.channel`이 있을 때만 그 IPC 메시지를 받는다(`:6-27`). 감독은 Windows에서만 `stdio`에 `'ipc'`를 넣어 자식을 띄운다(`apps/engine/src/supervisor.ts:37-46`).
- `tools/test-database.ts`는 시험 DB 이름이 `^[a-z][a-z0-9_]*_test$`여야 한다. `tools/node-cli.ts`의 `pnpmCli`는 `npm_execpath`가 `pnpm.cjs`·`pnpm.mjs`·`pnpm.js`일 때만 `process.execPath`로 그 JavaScript CLI를 부르고 아니면 던진다.
- `packages/db/prisma.config.ts`는 `../../.env`가 있을 때만 `loadEnvFile`을 부른다(`:5-6`). `.env`가 없는 작업 사본에서는 이 경로가 열리지 않는다.

### release manifest와 배포 receipt

배포 단위는 release 하나다. 서버에는 성격이 다른 운영 산출물 두 가지를 둔다. 둘 다 저장소 문서가 아니며 서버 쪽 기준 경로는 T2-19에서 정한다.

| 산출물 | 경로 | 쓰는 때 | 바뀌는지 |
| ------ | ---- | ------- | -------- |
| release manifest | `releases/<40자 SHA>/manifest.json` | 배포 단계 1에서 빌드·전송·대조가 모두 끝난 뒤 한 번 | SHA로 정해지는 artifact만 담고 확정 뒤 바꾸지 않는다 |
| 배포 receipt | `deployments/<runId>/receipt.json`. runId는 UTC 시각과 새 UUID 8자 | 배포·되돌리기 단계 0에서 만들고 단계마다 갱신 | 그 실행 동안만 갱신하고 끝나면 고정한다 |

release manifest의 값:

| 값 | 내용 |
| -- | ---- |
| `gitSha` | `git rev-parse --verify "<ref>^{commit}"`로 푼 40자 SHA. 짧은 SHA·브랜치·`latest`는 입력으로만 받고 기록이나 기동에 쓰지 않는다 |
| 소스 | `git archive <SHA>`로 푼 임시 디렉터리. 작업 트리의 수정, 추적하지 않는 파일, `.env`가 들어갈 수 없다. manifest의 파일 해시도 작업 트리가 아니라 이 결과에서 계산해 Windows 줄끝 변환을 피한다 |
| 이미지 | `server`·`engine` 이미지 ID(`sha256:` config digest)와 태그 `opensamguk-server:<SHA>`·`opensamguk-engine:<SHA>`. 기동과 되돌리기는 태그가 아니라 ID로 확인한다. postgres·caddy는 digest를 고정한 참조와 이미지 ID를 남긴다 |
| 화면 | `apps/web/dist`를 묶은 tar의 SHA-256, 파일별 SHA-256 목록, 빌드에 쓴 공개값 `VITE_IMAGE_BASE_URL` |
| 이미지 자산 | 이미지 저장소 커밋 40자 |
| migration | `packages/db/prisma/migrations/*/migration.sql`의 디렉터리 이름과 SHA-256 목록. Prisma `_prisma_migrations.checksum`과 같은 값인지는 B2에서 실제로 대조한다 |
| 자료 계약 판 | migration 없이 바뀌는 `InputEvent.kind`·`replayOrigin.capability`·JSON 자료 형식의 지원판. `eb9c16a`에는 이 판을 선언하는 코드가 없으므로 `unknown`으로 적는다. 선언과 검사가 생기기 전에는 이 값으로 호환을 판정하지 않는다 |

배포 receipt의 값:

| 값 | 내용 |
| -- | ---- |
| 실행 | runId, 종류(`deploy`·`rollback`), 대상 release SHA와 그 manifest의 SHA-256 |
| 이전 release | 단계 0에서 읽은 `current`의 SHA |
| 대상 DB | 비밀 파일이 가리키는 DB의 이름, `pg_database.oid`, `system_identifier`. URL과 비밀번호는 넣지 않는다 |
| 사전 백업 | 단계 3 백업의 파일 이름, SHA-256, 백업 manifest 이름, 내용 해시 |
| 자료 계약 판 | 대상과 이전 release manifest의 값을 그대로 옮긴다 |
| 단계 | 단계마다 시작·끝 시각(UTC), 종료 코드, 결과. 단계 5는 새 server·engine을 띄우기 직전에 `새 writer 기동`을 먼저 기록한다 |
| 실패 처리 | 멈춘 단계와 한 조치(이전 release를 다시 띄운 이미지 ID, 정지 유지, 소유자 판단 대기)와 그 근거(내용 해시 비교 결과 등) |
| 최종 결과 | `in-progress`에서 시작해 `succeeded`·`failed`·`needs-owner` 중 하나로 끝난다 |

- manifest는 `.partial-<runId>`로 쓰고 SHA-256을 확인한 뒤 `mv`로 확정한다. 빌드·전송·대조 중 하나라도 실패하면 확정하지 않고 이번 runId의 partial만 지운다. 임시 값이나 빈 값을 넣은 manifest를 성공으로 남기지 않는다.
- 같은 SHA를 다시 배포하면 다시 빌드하지 않는다. 이미지 빌드가 재현된다고 가정하지 않으므로 새로 만든 이미지 ID와 비교하지 않는다. 확정된 manifest의 이미지 ID가 서버에 있고 화면 파일 해시가 목록과 같을 때만 그 artifact를 그대로 쓰며 빠졌거나 다르면 거부한다. 이전 release·사전 백업·시각은 receipt에만 있으므로 재배포가 이 값 때문에 거부되지 않는다.
- receipt는 단계마다 임시 파일을 쓰고 `mv`로 바꾼다. 최종 결과 `succeeded`는 단계 5 확인과 `current` 교체가 모두 끝난 뒤에만 쓴다.
- `current`는 release SHA 하나를 가리킨다. 단계 6에서 receipt에 단계 5 통과를 먼저 기록한 뒤 임시 파일을 쓰고 `mv`로 바꾼다. 실패하면 receipt를 `needs-owner`로 남긴다.
- 이전 release의 manifest·이미지와 이전 receipt는 지우지 않는다. 보관 개수는 T2-19 디스크 사양을 보고 정하며 그 전에는 지우지 않는다.
- 이미지는 레지스트리 없이 옮긴다. `docker save`를 파일로 쓰고 SHA-256을 기록해 `scp`로 보낸 뒤 서버에서 SHA-256과 `docker load` 뒤 이미지 ID를 다시 대조한다. 파이프로 잇는 곳은 `set -o pipefail`로 각 단계 실패를 전파한다.
- 배포 대상 서버 주소와 SSH 별칭은 T2-19 값이다. SSH는 `BatchMode=yes`로 쓰고 알려진 host key만 받는다.

### 운영 compose와 Caddy 통신

server가 `127.0.0.1`에만 listen하므로 평범한 compose bridge에서 다른 컨테이너의 Caddy는 `server:3001`에 붙을 수 없다. 앱의 bind는 고치지 않고 Caddy와 server가 network namespace를 함께 쓴다.

| 서비스 | 네트워크 | 비고 |
| ------ | -------- | ---- |
| `postgres` | 내부 bridge `backend`. 포트를 publish하지 않는다 | 데이터 볼륨, 공식 이미지의 `POSTGRES_PASSWORD_FILE` |
| `caddy` | `backend`에 붙고 80·443(tcp, udp)을 publish하는 namespace 주인 | host bind 주소는 T2-19 |
| `server` | `network_mode: service:caddy`. Caddy와 같은 loopback을 쓴다 | `127.0.0.1:3001`은 Caddy에게만 보이고 publish하지 않는다 |
| `engine` | `backend` | 인자 없이 감독 실행 |
| `migrate` | `backend`. profile로만 부르는 일회성 서비스, server 이미지 | `prisma migrate deploy` |

- server는 Caddy의 namespace를 통해 `backend`의 `postgres` 이름을 쓴다. 이름 해석과 접속은 B3 실제 Linux 리허설에서 처음 확인한다. 안 되면 bind를 고치지 않고 멈춰 server 소유자에게 선행 문제로 넘긴다.
- Caddy 컨테이너를 다시 만들면 namespace가 바뀌므로 server도 다시 만든다. 배포와 되돌리기는 항상 caddy, server, engine 순서로 다시 만든다.
- 이 구성에서 server가 보는 상대 소켓은 `127.0.0.1`의 Caddy 하나라서 `TRUST_PROXY=1`(바로 앞 한 단계만 신뢰)과 맞는다.
- 로그는 Docker `json-file` 회전을 켠다. 크기와 개수는 B2에서 정해 리뷰받는다.

`deploy/Caddyfile`의 경로 계약:

| 경로 | 처리 |
| ---- | ---- |
| `/trpc`, `/trpc/*` | `reverse_proxy 127.0.0.1:3001` |
| `/sse` | `reverse_proxy 127.0.0.1:3001`, `flush_interval -1`. Origin·Cookie·Sec-Fetch-Site 헤더를 바꾸지 않고 넘긴다 |
| 그 밖 | `root`를 release의 화면 디렉터리로 둔다. `try_files {path} /index.html`과 `file_server`를 쓴다. 목록 보기는 끈다 |

- site 블록은 `deploy/security.caddy`를 import하고 `game_security`를 적용한다. server도 nosniff·Referrer-Policy·X-Frame-Options를 붙이므로 각 헤더가 한 값씩만 나가는지 B3에서 응답으로 확인한다.
- 화면 디렉터리는 `releases/<SHA>/web/`이고 compose가 release env 파일의 경로를 읽기 전용으로 mount한다. Caddy가 내준 `/index.html`과 `assets/` 파일의 SHA-256을 manifest 목록과 대조해 화면과 server 이미지가 같은 SHA에서 나왔는지 확인한다.

### 비밀값 전달

| 항목 | 결정 |
| ---- | ---- |
| 보관 | 서버의 비밀 디렉터리(0700)에 파일(0600)로 둔다. 저장소, `.env.production`, compose 파일, 명령 인자에 값을 넣지 않는다 |

| server·engine·migrate | `deploy/entrypoint.sh`가 `/run/secrets/database_url`을 읽어 `DATABASE_URL`을 export하고 `exec`로 node를 띄운다. `set -x`를 쓰지 않고 값을 출력하지 않는다. 컨테이너 설정에 값이 남지 않으므로 `docker inspect`에도 나오지 않는다. 앱 코드는 그대로다 |
| postgres | 공식 이미지의 `POSTGRES_PASSWORD_FILE` |

### 배포 단계와 실패 처리

`deploy.sh`는 단계마다 receipt를 갱신하고 실패하면 아래 표대로 멈춘다. 이전 release를 자동으로 다시 띄우는 경우는 새 writer가 기동하기 전이거나, 새 writer를 멈춘 뒤 DB 내용 해시가 사전 백업과 같다고 확인한 때뿐이다.

| 단계 | 내용 | 실패하면 |
| ---- | ---- | -------- |
| 0 사전 확인 | 40자 SHA 확정, receipt 생성(runId, 이전 release, 대상 DB 식별), 같은 SHA의 확정 manifest 유무 확인, 서버 디스크와 비밀 파일 권한 확인(값은 읽지 않는다). DB의 적용 migration(완료되고 롤백되지 않은 것)이 새 목록의 앞부분과 이름·checksum까지 같은지 본다. DB에만 있는 migration이나 checksum 불일치는 거부한다 | 서비스는 바꾸지 않고 receipt에 `failed`와 사유만 남긴다. 기존 release는 그대로 돈다 |
| 1 빌드·전송·manifest | 확정 manifest가 없으면 이미지와 화면 산출물 빌드, 전송, SHA-256·이미지 ID 대조 뒤 manifest를 확정한다. 있으면 artifact 존재와 해시만 확인한다 | 같음. 확정하지 않은 partial만 지운다 |
| 2 writer 정지 | engine(감독)에 SIGTERM을 보내 멈추고 server를 멈춘다. `init: true`이고 `stop_grace_period`는 감독의 자식 5초 정리보다 길게 B2에서 정한다. 종료 코드를 기록하고 대상 DB의 다른 연결 0, 모든 `EngineLease.expiresAt`이 DB 시각 이전인지 확인한다. 강제 종료로 리스가 남았으면 만료(15초)까지 기다려 다시 본다 | DB를 바꾸기 전이므로 기존 release를 같은 이미지 ID로 다시 띄울 수 있다. 연결이 끝내 0이 되지 않으면 띄우지 않고 멈춘다 |
| 3 사전 백업 | `backup.sh --reason pre-deploy`. writer가 멈춘 quiesced 백업이며 덤프 전후 내용 해시가 같아야 한다. receipt에 파일 이름·SHA-256·내용 해시를 적는다 | DB 변경 전이다. 기존 release를 다시 띄우고 실패를 보고한다 |
| 4 migration | 새 server 이미지로 `migrate`를 한 번 실행한다. 새 migration이 없으면 건너뛴다 | 실패, timeout, 결과 불명 모두 같은 처리다. writer를 멈춘 채 두고 DB를 그대로 둔다. 새 release도 이전 release도 띄우지 않는다. `_prisma_migrations` 행(이름, finished_at, rolled_back_at)을 receipt에 적고 `needs-owner`로 소유자 판단을 기다린다 |
| 5 기동·확인 | receipt에 새 writer 기동을 적은 뒤 caddy, server, engine 순서로 띄운다. server 컨테이너 안에서 node `fetch`로 `http://127.0.0.1:3001/trpc/health`를 불러 JSON `result.data.server`와 `result.data.db`가 `ok`인지 보고 Caddy를 거친 화면 파일 해시를 대조한다. 공개 주소 확인은 T2-19 도메인이 생긴 뒤 한다 | 새 writer를 멈추고 다른 연결 0을 확인한 뒤 백업 계약의 내용 해시를 다시 낸다. 사전 백업 내용 해시와 같을 때만 이전 release를 같은 이미지 ID로 다시 띄운다. 다르면 migration 유무와 관계없이 아무것도 띄우지 않고 receipt를 `needs-owner`로 남겨 [되돌리기](#되돌리기)의 복원 경로로 넘긴다. schema가 같다는 것만으로 이전 release를 띄우지 않는다 |
| 6 기록 | receipt에 단계 5 통과 기록, `current` 원자 교체, receipt `succeeded` | 서비스는 이미 새 release다. receipt를 `needs-owner`로 남기고 `current`를 수동으로 맞춘다. 이전 release로 자동 복귀하지 않는다 |

### 되돌리기

`rollback.sh <SHA>`는 그 SHA의 manifest와 이미지 ID가 서버에 남아 있을 때만 시작하고 종류 `rollback`의 receipt를 남긴다.

- migration 목록 일치는 필요조건일 뿐 충분조건이 아니다. 이 저장소는 migration 없이도 `InputEvent.kind`, `replayOrigin.capability`, JSON 자료 계약이 바뀐다. 새 writer가 새 형식을 이미 썼으면 schema가 같아도 이전 binary가 그 DB를 읽거나 재생하다 깨질 수 있다.
- 이미지만 바꾸는 되돌리기는 아래가 모두 맞을 때만 한다. 대상 SHA가 `current` release를 만든 배포 receipt의 이전 release와 같다. writer를 멈추고 다른 연결 0을 확인한 뒤 낸 내용 해시가 그 receipt의 사전 백업 내용 해시와 같다. 곧 새 writer가 DB에 아무것도 남기지 않았다. DB의 적용 migration 목록도 대상 manifest와 같다. 이때 대상 이미지 ID와 화면 디렉터리로 다시 띄운 뒤 배포 단계 5와 같이 확인한다.
- 하나라도 맞지 않으면 이미지만 바꾸지 않고 0이 아닌 코드로 끝낸다. 스크립트는 이때 DB를 건드리지 않는다. 새 writer가 기동해 heartbeat나 입력을 한 번이라도 썼다면 migration이 없어도 이 경우다.
- 그 뒤 되돌리기는 기존 복원 경로이며 세 단계다. 먼저 대상 release를 떠난 배포 receipt의 사전 백업을 `restore.sh`로 새 DB에 복원해 검증한다. 소유자가 데이터 손실 범위를 보고 결정한다. 그 뒤 별도로 승인한 cutover에서만 비밀 파일의 DB 이름을 새 DB로 바꾸고 이전 release를 띄운다. cutover 방식은 B2 리뷰에서 정한다.
- 새 writer가 쓴 DB를 살린 채 이전 release로 가는 길(writer를 멈추고 새 복제 DB를 만든 뒤 대상 이전 이미지로 실제 load와 `tools/replay.ts` 재생 호환을 확인하고 소유자가 판단해 cutover)은 B2에 만들지 않는다. 지원판 선언도 저장 자료 검사 helper도 없으므로 호환을 확인했다고 쓰지 않는다. 필요하면 engine·shared 소유자의 선행(release별 지원판 선언과 그 검사)을 받은 뒤 후속으로 계획하고 그 전까지 manifest·receipt의 자료 계약 판은 `unknown`으로 둔다.
- 손실 범위는 사전 백업 시각(writer 정지 뒤)부터 되돌리는 시점까지 새 release가 쓴 모든 기록이며 계정, 장수 입력, 턴 진행이 들어간다. 이를 버릴지 새 release를 고쳐 앞으로 갈지는 소유자가 정한다.
- 옛 DB와 현재 DB는 덮어쓰거나 지우지 않는다. `pg_restore --clean`·`--create`, `DROP DATABASE`, `WITH (FORCE)`를 쓰지 않는다. 남긴 DB의 정리는 따로 결정한다.
- 역 migration을 자동으로 만들지 않는다.

### 백업 계약

| 항목 | 계약 |
| ---- | ---- |
| 실행 | `tools/backup.sh --docker <docker 절대 경로> --container <64자 컨테이너 ID> --system-identifier <숫자> --db-user <role> --admin-db <이름> --source-db <이름> --backup-dir <절대 경로> --reason daily\|pre-deploy\|rehearsal --release-sha <40자 Git SHA>`. 모든 인자가 필수이고 기본값이 없다. `--release-sha`는 정확히 40자리 16진 문자열만 받고 입력 그대로 manifest에 기록한다. 누락·형식 오류는 Docker 호출과 파일 생성 전에 거부한다. `.git` 조회나 fallback은 없다. B1은 검토한 실제 소스 커밋을 명시 전달하고 B2가 운영 current SHA를 얻어 전달할 방법을 정한다. `docker compose`를 부르지 않으며 `COMPOSE_FILE`·`COMPOSE_PROJECT_NAME`·현재 디렉터리의 compose 파일·루트 `.env`·기본 project를 읽거나 그쪽으로 fallback하지 않는다. B2·B3 운영 경로에서 postgres 컨테이너 ID를 어떻게 얻어 넘기는지는 B2에서 정한다 |
| 대상 확인 | 인자 형식 검사 뒤, DB 생성·덤프·복원·삭제 전에 `docker inspect --type container <ID>`로 `Id`가 인자와 같고 실행 중인지 본다. 이어 `docker exec -i <ID> psql`로 `--admin-db`에 붙어 `pg_control_system().system_identifier`가 인자와 같은지 본다. 하나라도 빠졌거나 다르면 docker 호출을 더 하지 않고 거부한다. `--admin-db` 연결은 카탈로그(`pg_database`, `pg_stat_activity`, `pg_control_system()`, `server_version_num`) 읽기와 자기 DB의 `CREATE`·`DROP DATABASE`에만 쓰고 사용자 표는 읽지 않는다 |
| 클라이언트 | 지정한 기존 컨테이너 안의 `pg_dump`·`pg_restore`·`psql`을 `docker exec <ID>`로 쓴다. stdin이 필요한 호출에만 `-i`를 붙이고 `-t`·`-e`·`--env`·`-u`는 쓰지 않는다. 서버와 같은 이미지라 메이저가 맞는다고 가정하지 않고 `pg_dump --version`과 `server_version_num`을 기록해 덤프 도구 메이저가 서버보다 낮으면 거부한다 |
| 접속 | 컨테이너 안 Unix socket과 `--db-user`만 쓴다. 연결 URL이나 비밀번호를 인자·환경에 넣지 않는다. local 인증이 trust인지는 B1 첫 실제 실행에서 확인한다. trust가 아니면 비밀값을 컨테이너에 넣거나 복사하지 않고 미실행으로 끝낸다 |
| 식별 | 덤프 전에 `current_database()`, 그 DB의 `pg_database.oid`, `pg_control_system().system_identifier`, 서버 버전을 읽어 manifest의 source로 남긴다. `--source-db`나 `--system-identifier`와 다르면 거부한다. 이름은 psql 변수로 넘기고 SQL은 stdin으로 보낸다(`-c`는 변수 치환을 하지 않는다) |
| 일관성 | reason으로 정한다. `pre-deploy`·`rehearsal`은 quiesced다. 덤프 전후에 원본 DB의 다른 연결 0과 모든 `EngineLease.expiresAt`이 DB 시각 이전인지 보고 아니면 거부한다. `daily`는 live다. writer가 도는 중이며 `pg_dump` 자체의 한 snapshot만 일관성 근거로 쓴다. 공유 exported snapshot(`pg_dump --snapshot`)은 쓰지 않는다 |
| 형식 | 기존 컨테이너에 백업 bind mount가 있다고 가정하지 않는다. Bash가 `docker exec <ID> pg_dump -Fc -U <role> -d <원본>`의 바이너리 stdout을 host의 자기 파일 `<백업 디렉터리>/.partial-<runId>.dump`로 바로 redirect한다. PowerShell 파이프, Node 문자열 변환, 중간 텍스트 처리는 쓰지 않는다. stdout으로 낸 아카이브에는 데이터 offset이 없어 `-j`가 안 되며 B1은 순차 읽기만 쓴다. 사람이 보는 출력은 고정 상태·사유 코드와 만든 파일 이름뿐이다 |
| 완료 판정 | `pg_dump` 종료 코드 0, 크기 0 초과, 같은 파일을 `docker exec -i <ID> pg_restore --list`의 stdin으로 넣어 성공, SHA-256 계산, `sync`. 적용 migration 목록은 DB를 따로 읽지 않고 같은 파일을 stdin으로 넣은 `pg_restore --data-only --table=_prisma_migrations -f -`로 읽어 live에서도 덤프 snapshot과 같은 목록을 남긴다. stdin 순차 읽기로 이 두 호출이 안 되면 bind mount나 `docker cp`로 우회하지 않고 실패로 멈춘다. 그 뒤 dump를 최종 이름으로 `mv`하고 manifest를 마지막에 `mv`한다. manifest가 있어야 성공한 백업이다 |
| 출력 | 자식(docker·psql·pg_*)의 stderr는 이번 실행의 `.partial-<runId>.err`(0600)로만 보내고 화면에 옮기지 않는다. 그 파일은 trap이 지운다. stdout·stderr에 URL, 비밀번호, raw SQL, 덤프 바이트를 쓰지 않는다 |
| 권한 | `umask 077`, 백업 디렉터리 0700, 파일 0600. Windows에서는 POSIX 권한을 확인할 수 없으므로 권한 검사는 Linux 결과만 증거로 센다 |
| 백업 manifest | 형식, 일관성(`quiesced`·`live`), 도구·서버 버전, source 식별, 시작·끝 시각(UTC), 크기, SHA-256, 아카이브에서 읽은 적용 migration 이름과 checksum, reason, 명시 전달받은 release SHA, 내용 해시, 외부 복사 상태. 내용 해시는 quiesced에만 있고 live는 `null`과 사유 `live-source`다. 연결 정보와 비밀값은 넣지 않는다 |
| 내용 해시 | quiesced에서만 덤프 직전과 직후에 한 번씩 내고 두 값이 같아야 성공이다. 계산은 아래와 같고 psql로 읽기만 하며 새 DB function·extension은 설치하지 않는다 |
| 동시 실행 | 백업 디렉터리의 잠금 디렉터리(`mkdir`)로 하나만 돈다. Git Bash에 `flock`이 없기 때문이다. 남은 잠금을 자동으로 빼앗지 않고 거부한다 |
| 실패 정리 | `trap`이 EXIT·INT·TERM에서 이번 실행이 만든 `.partial-<runId>.*` 파일만 지운다. 와일드카드로 남의 파일을 지우지 않으며 성공한 백업과 이전 manifest는 건드리지 않는다 |
| 외부 복사 | 위치와 도구는 T2-19. 복사 뒤 원격 SHA-256이 같아야 `confirmed`다. 설정 전에는 `not-configured`로 남기고 성공으로 꾸미지 않는다 |
| 보관 | 이번 실행이 성공한 뒤에만 정리한다. 성공한 백업만 세고 7일(가정)보다 오래된 것만 지운다. 외부 복사를 설정한 뒤에는 더 새 `confirmed` 백업이 있을 때만 지운다. 실패한 실행은 아무것도 지우지 않는다 |
| 일정 | 매일 04:00(가정). 서버의 cron이나 systemd timer 설치는 T2-19 서버에서 소유자 승인 뒤에 한다 |

내용 해시 계산(backup·restore가 같은 SQL을 쓴다):

- `psql -X -At`로 `REPEATABLE READ READ ONLY` 트랜잭션을 열고 `SET LOCAL`로 `TimeZone = 'UTC'`, `DateStyle = 'ISO, YMD'`, `IntervalStyle = 'postgres'`, `extra_float_digits = 3`, `bytea_output = 'hex'`를 둔다. 표별 질의는 `\gexec`로 만든다.
- 표 범위는 schema `public`의 일반 표(`pg_class.relkind = 'r'`) 전부이며 `_prisma_migrations`도 들어간다. 표마다 `table<TAB><표 이름><TAB><행 수><TAB><md5>` 한 줄을 낸다. md5는 행마다 `md5(t::text)`(record 텍스트 출력)를 내고 그 값들을 `COLLATE "C"`로 정렬해 구분자 없이 이은 문자열의 md5다. 빈 표는 `md5('')`다.
- `public`의 sequence마다 `SELECT last_value, is_called`로 `sequence<TAB><이름><TAB><last_value><TAB><is_called>` 한 줄을 낸다. sequence는 MVCC가 아니어서 다른 연결 0인 quiesced에서만 넣을 수 있다. live daily에 내용 해시가 없는 이유다.
- 줄은 `table` 다음 `sequence`, 각자 이름을 `COLLATE "C"` 순으로 `\n`으로 잇고 끝 줄바꿈 없이 컨테이너 밖 `sha256sum`으로 SHA-256을 낸다.
- DB 이름, oid, owner, ACL, tablespace, `system_identifier`, 주석은 넣지 않는다. 같은 클러스터의 다른 이름이나 다른 owner로 복원해도 값이 같아야 하기 때문이다.

### 복구 리허설

리허설 원본은 운영 DB나 현재 M1 DB가 아니라 시험이 기존 전용 PG 컨테이너 안에 새로 만든 fixture DB다. B1은 정지 경계 T0에서 다음 월 경계 B = T0 + `TICKS_PER_MONTH`까지 정확히 한 달만 진행한다. 실행권을 쥐는 곳은 1의 fixture 준비, 4의 month 자식, 7의 원본 B 진행 세 곳이며 모두 [리스 유지](#리스-유지) 계약을 따른다.

1. 기존 전용 PG에 `t215_src_<uuid>_test`를 만들고 migration을 적용한다. 기존 시나리오로 월드를 만들고(`loadInitialWorld`, `saveInitialWorld`) 시작한 뒤 실행권을 얻어 `TurnLoop.advanceTo(k·TICKS_PER_MONTH)`로 k개월 진행한다. k는 30초 case 안에 맞는 가장 작은 값이며 기본 1이다. 실행권을 풀고 `controlClock`의 pause로 tick을 고정한 뒤 원본 Prisma client를 닫는다. 이때 `World.monthlyTick`이 T0다.
2. `backup.sh --reason rehearsal`을 실행한다. quiesced이므로 manifest에 내용 해시가 남는다.
3. `restore.sh`로 `t215_dst_<uuid>_test`에 복원하고 quiesced 복원 직후 검사를 통과한다. 원본과 대상의 `hashState(readWorldState())`도 같아야 한다.
4. 대상을 `controlClock`으로 resume만 하고 가속하지 않는다. 목표 tick을 준 `advanceTo`는 `RUNNING`만 요구하고 모드와 실시간을 보지 않기 때문이다. 그 뒤 실제 자식 하나를 아래 [month 자식](#month-자식) 계약으로 띄우고 정상 종료(코드 0)를 기다린다. 자기 기한 안에 끝나지 않으면 `stopOwnedChild`로 그 자식만 멈추고 실패로 끝낸다.
5. 자식이 끝난 직후, pause 전에 대상을 읽는다. `World.monthlyTick`이 B이고 B의 `YearbookSnapshot`이 하나 새로 생겼으며 B 뒤의 snapshot은 없어야 한다. 그 월드의 `EngineLease.expiresAt`이 DB 시각 이전이어야 한다(자식이 실행권을 풀었다).
6. `tools/replay.ts --world <ID> --output <새 파일>`로 대상에서 내보내고 `--from <파일> --months <k+1>`로 모든 월 해시가 일치하는지 본다.
7. 원본도 같은 순서로 resume하고 시험 프로세스에서 실행권을 얻어 `TurnLoop.advanceTo(B)` 한 번으로 진행하고 실행권을 푼 뒤 pause 전에 읽는다. 두 DB가 같은 B에서 아래 canonical 값이 같아야 한다. 이후 두 DB의 pause는 정리용이며 비교하지 않는다.

#### 리스 유지

기존 TTL 15초(`LEASE_TTL_MS`)를 그대로 쓴다. `acquireLease`의 `ttlMs` 인자를 넘기지 않고 TTL을 늘리지 않는다. 30초 case 하나가 TTL보다 길 수 있으므로 case 길이를 근거로 안전하다고 보지 않는다. `runEngine`은 `poll` 전용이라 재사용할 수 없으므로 세 곳은 같은 절차를 각자 따른다.

- `acquireLease(db, worldId)`가 `null`이면 기다리거나 빼앗지 않고 바로 실패한다.
- 얻은 직후 `advanceTo`보다 먼저 갱신 루프를 시작한다. `main.ts`와 같이 하나의 순차 루프에서 `LEASE_TTL_MS / 3`을 기다리고 실제 `renewLease(db, lease)`를 부른다. `setInterval`처럼 겹쳐 부르지 않는다.
- `advanceTo(target, signal)`에 자기 `AbortController`의 signal을 넘긴다. `renewLease`가 던지면(`LeaseLostError` 포함) 오류를 기록하고 abort한다. 진행 중인 단계 트랜잭션은 commit 전 `throwIfAborted`·`assertLease`에서 롤백된다. 호출자는 `advanceTo` promise가 끝날 때까지 기다리며 버려 두지 않는다.
- `advanceTo`는 단계 사이 abort에 오류 없이 돌아오므로 갱신 오류가 없고 `World.monthlyTick`이 목표와 같을 때만 성공이다.
- `finally`에서 abort, 갱신 루프 종료 대기, `releaseLease(db, lease)`, `db.$disconnect()` 순서로 정리한다. `releaseLease`는 자기 owner·token 행만 바꾸므로 다른 소유자 리스에 닿지 않는다. 해제가 실패하면 `EngineLease`를 직접 고치지 않고 실패로 보고하며 TTL 만료에 맡긴다. 이때 다음 quiesced 백업은 리스 검사에서 거부된다.
- 시험 프로세스의 1·7은 vitest case timeout이 promise를 멈추지 않는다는 점을 전제로 한다. 진행 중인 `AbortController`와 promise를 모듈 범위에 두고 `afterAll`과 취소 처리가 abort한 뒤 끝을 기다린 다음에만 DB를 지운다.

#### month 자식

`tools/t2-15-month-child.ts`는 시험 전용 자식이며 운영 명령이 아니다. 인자는 월드 ID와 B 두 개다. `DATABASE_URL`을 자식 환경에서만 읽고 DB 이름이 리허설 대상 허용식에 맞지 않으면 시작하지 않는다. 순서는 `createDb`, 기존 `onShutdownRequest`(`apps/engine/src/process-lifecycle.ts`)로 종료 요청을 자기 `AbortController`에 연결, [리스 유지](#리스-유지) 절차로 `new TurnLoop(db, lease).advanceTo(B, signal)` 한 번, 정리다. 정리의 마지막에 `onShutdownRequest`가 돌려준 해제 함수를 불러 IPC `message` 수신을 떼어 IPC 채널이 정상 종료를 막지 않게 한다. 목표 도달, 갱신 오류 없음, 해제 성공일 때만 코드 0이고 그 밖은 0이 아닌 코드다. stdout·stderr에는 고정 상태 줄(`ok`, `lease-lost`, `aborted`, `failed` 중 하나)만 쓰고 오류 메시지·스택·URL은 쓰지 않는다. 자식 코드는 `publicMapConfig`·`PUBLIC_MAP_*`를 직접 다루지 않고 `TurnLoop`이 부모가 넘긴 allowlist 값([실행 입력과 자식 계약](#실행-입력과-자식-계약))을 읽는다.

부모는 `spawn(process.execPath, ['--import', 'tsx', <사본>/tools/t2-15-month-child.ts, worldId, String(B)], { cwd: <사본 루트>, env: <month 자식 env>, shell: false, windowsHide: true })`로 띄운다. `stdio`는 감독과 같은 규칙으로 Windows에서 `['ignore', 'pipe', 'pipe', 'ipc']`, 그 밖에서 `['ignore', 'pipe', 'pipe']`다. Windows의 `stopOwnedChild`는 IPC 종료 요청을 보내므로 IPC 없이 띄우면 정리 요청이 닿지 않는다. 부모는 두 pipe를 메모리에만 모아 모든 줄이 고정 상태 집합 안인지 보고 원문을 출력하지 않는다. `exit`·`error`로 끝나는 promise를 spawn 직후 한 번 만든다.

부모의 자기 기한은 spawn 뒤 20초다. case 30초에서 `stopOwnedChild`의 강제 5초와 정리 여유를 뺀 값이다. 기한을 넘기거나 취소되면 그 `ChildProcess`에만 `stopOwnedChild`를 부른다. 이름·PID 검색으로 다른 프로세스를 멈추지 않는다. 5초 안에 끝나지 않아 `SIGKILL`이 나갔으면 그 사실을 기록한다. 연결이 끊긴 진행 트랜잭션은 PG가 롤백하고 남은 리스는 TTL로 만료되며 부모는 그 리스를 고치지 않는다. 대상 DB 삭제는 정리 계약대로 다른 연결 0일 때만 한다.

엔진 CLI에 `--until` 같은 옵션을 만들거나 가정하지 않는다. `apps/engine/test/monthlyWorker.ts`는 commit 전후에 멈추고 부모 kill을 기다리는 주입용이므로 이 용도로 재사용하거나 고치지 않는다. 엔진 공통 파일(`lease.ts`, `main.ts`, `process-lifecycle.ts`, `turnLoop.ts`)은 읽고 부르기만 하며 고치지 않는다.

B1의 한 달 진행 뒤에는 정확히 B에서 canonical 값만 비교한다. `hashState(readWorldState())`, 월별 `YearbookSnapshot.stateHash`, 처리된 `InputEvent` sequence가 대상이다. 실행 시각, `World.clockAnchorAt`·`clockRevision`·`startedAt`, 시계 모드 전환, `EngineLease`, `EngineHeartbeat`, `PublicMapSnapshot.takenAt`은 운영 정보라서 비교하지 않는다. 이 값들은 복원 직후의 내용 해시에는 들어간다.

fixture 준비와 1개월 확인을 한 번에 하는 공개 명령은 없다. B1은 시험 파일과 위 자식 하나에서 기존 진입점을 조합하고 없는 함수를 새로 가정하지 않는다. B3 Linux 리허설은 엔진 이미지의 기존 CLI(`world:create`, `world:start`, `world:accelerate`, `world:pause`, `world:resume`, 엔진 `--world`, `tools/replay.ts`)만 쓴다. ACCELERATED의 엔진 `--world`는 경계에서 멈추지 않으므로 부모가 B 이상의 `YearbookSnapshot`을 보고 pause할 때까지 여러 달을 더 갈 수 있다. 그래서 B3 증거는 "적어도 한 달 진행 + 실제로 도달해 기록한 마지막 월 경계 R까지 재생 일치"로만 세고 R을 기록한다. 원본과의 정확한 B 비교(7)는 하지 않으며 B1의 정확한 B 동등성과 섞지 않는다. 정확한 경계에서 멈추는 Linux 운영 helper가 필요하면 engine 소유자의 선행 작업으로 따로 대기열에 올리며 이번 범위에는 넣지 않는다.

### 정리와 보존 증거

성공, 실패, 취소(시험 중단 신호) 모두 같은 정리를 하고 아래를 증거로 남긴다.

| 항목 | 증거 |
| ---- | ---- |
| 자식 프로세스 | 시험이 띄운 PID 목록과 각 종료 코드 |
| DB 연결 | drop 전 원본·대상 DB의 다른 연결 0 |
| 자기 DB | 이번 실행이 만든 원본·대상 두 개의 이름과 생성 직후 oid. drop 직전 이름·oid가 같고 컨테이너 `Id`·`system_identifier`를 다시 확인한 뒤 FORCE 없이 drop한다. 만들다 실패한 DB도 이름·oid가 확인된 것만 같은 조건으로 지운다 |
| 나머지 DB | 기존 전용 PG의 `pg_database`에서 자기 두 개를 뺀 (이름, oid) 목록이 시작과 끝에 같다. `--admin-db` 카탈로그만 읽고 그 DB들에 접속하거나 내용을 읽지 않는다. 증거에는 개수와 정렬 목록의 SHA-256만 남긴다 |
| docker | compose를 부르지 않는다. 지정 컨테이너 하나의 `docker inspect`에서 `Id`, 실행 상태, `State.StartedAt`, `RestartCount`, 이미지 ID가 시작과 끝에 같다. 컨테이너·volume·network를 만들거나 바꾸거나 지우지 않는다 |
| 환경 | 루트 `.env`의 SHA-256과 mtime이 같다(내용은 출력하지 않는다). 시험 프로세스 `process.env`의 키·값 해시가 같다 |
| 포트 | 시작 전후 5433·5173·3001과 전용 PG endpoint 포트의 listen 상태와 PID가 같다. Windows는 `<SystemRoot>/System32/NETSTAT.EXE -ano -p TCP`, Linux는 `/usr/bin/ss -ltnp`를 읽기만 하며 없으면 미관측으로 적는다 |
| M1 | 5433에 접속하지 않고 M1 DB 목록·oid·내용을 조회하지 않는다. M1은 위 포트 행의 PID·listen 관측만 한다. 시험이 연 모든 DB 연결의 포트가 전용 PG endpoint 하나뿐임을 기록한다 |
| 파일 | 이번 run 디렉터리 밖의 파일을 지우지 않는다. 실행 잠금은 `T215_WORK_ROOT` 안의 자기 runId가 적힌 것만 푼다. 비밀번호 파일과 슬롯 배치는 읽기만 한다 |

PID는 시작과 끝의 표본만 본다. 그 사이 잠깐 떴다 사라진 프로세스까지 없었다고 증명하지 못하며 증거에도 그렇게 적는다.

### Windows 개발기와 Linux 서버 검증

| 구분 | 장소 | 확인하는 것 | 확인하지 않는 것 |
| ---- | ---- | ----------- | ---------------- |
| Windows 도구 검증 | 이 개발기, Git Bash 명시 실행 | 스크립트 인자와 거부 경계, 경로·인코딩, 기존 전용 PG 안 새 `_test` DB 두 개의 실제 덤프·복원·엔진 1개월·재생 해시 | Linux 권한, 운영 compose, Caddy, 이미지 빌드, 일정 실행, 외부 복사 |
| Linux 배포 검증 | T2-19 서버 (B3) | 배포, 되돌리기, 운영 compose, Caddy, 비밀 전달, 권한, 일정, 외부 복사, 같은 이미지로 한 복구 리허설 | 운영 DB 복제 |

- bash는 `C:\Program Files\Git\bin\bash.exe`를 절대 경로로 실행하고 PATH의 `bash.exe`(WSL)는 쓰지 않는다. 없으면 시험을 실패로 끝내고 사유를 남긴다. Linux에서는 `/bin/bash`다.
- 스크립트는 `#!/usr/bin/env bash`, `set -Eeuo pipefail`, `export LC_ALL=C.UTF-8`, `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`로 시작한다. `docker exec`에 넘기는 컨테이너 안 인자가 Windows 경로로 바뀌지 않게 하려는 것이며 Linux에서는 영향이 없다.
- 줄끝은 `tools/.gitattributes`의 파일별 규칙(`backup.sh text eol=lf`)으로 고정하고 전역 `core.autocrlf`는 바꾸지 않는다. 시험이 스크립트에 `\r`이 없는지 본다.
- 모든 경로 인자를 따옴표로 감싸고 공백이 든 경로로 시험한다. 출력은 UTF-8로 읽는다.
- 실제 PG 시험의 선행은 부모가 기존 전용 PG 하나를 T2-15 슬롯으로 배정해 둔 것이며 그 컨테이너가 이미 떠 있어야 한다. 이번 정정에서는 컨테이너 이름·ID, 포트, 비밀번호, 슬롯을 조회하지 않았으므로 계획에 값을 적지 않는다. 입력이 없거나 확인에 실패하면 실제 PG 시험은 미실행이며 사유를 그대로 기록한다. B1은 컨테이너를 띄우거나 이미지를 받지 않고 슬롯·비밀 배치를 만들거나 바꾸지 않는다.
- 단위 시험은 이 구분과 무관하다. Docker·DB·슬롯·운영값·`T215_*` 없이 `os.tmpdir()` 아래 소유 임시 폴더에서 돈다. 이 개발기에서 C 드라이브 출력을 피하는 것은 시험 조건이 아니라 실행 방법이며 부모 명령의 `TEMP`·`TMP`·`TMPDIR`를 E 드라이브 소유 경로로 지정해 돌린다([검증 명령](#첫-구현-묶음-b1) 끝).
- 화면 빌드의 pretendard 메모리 부족 같은 Windows 사정은 B1과 무관하다. B2 이미지 빌드는 Linux 빌더 기준으로 검증한다.

#### 실행 입력과 자식 계약

실제 PG 통합 시험만 시험 부모 환경의 아래 입력을 모두 받아야 시작한다. 선행은 부모가 배정한 기존 전용 PG 슬롯이며 아래 값은 그 슬롯에 이미 있는 것을 옮겨 적은 것이다. 기본값도 추정도 없으며 하나라도 없거나 형식이 틀리면 docker를 한 번도 부르지 않고 통합 시험을 미실행 사유와 함께 실패로 보고한다. 단위 시험, `pnpm test`, `pnpm check`는 이 입력을 읽지 않으므로 입력이 없어도 막히지 않는다. 이 계획은 이름과 검사만 정하고 새 값·파일을 만들지 않는다.

| 입력 | 내용과 검사 |
| ---- | ----------- |
| `T215_PG_PASSWORD_FILE` | 배정 슬롯의 접속 비밀번호가 이미 들어 있는 별도 비밀 파일의 절대 경로. 파일이 없거나 읽을 수 없으면 실패한다. 내용을 부모 메모리로 읽기만 하고 파일을 만들거나 옮기거나 바꾸지 않으며 경로와 값을 증거에 남기지 않는다 |
| `T215_PG_CONTAINER` | 64자 컨테이너 ID. 이름은 받지 않는다. `docker inspect`의 `Id`와 같고 실행 중이어야 한다 |
| `T215_PG_ENDPOINT` | `127.0.0.1:<포트>`. 5433이면 거부한다. 같은 inspect의 `5432/tcp` 바인딩(`127.0.0.1`과 그 포트)과 같아야 한다 |
| `T215_PG_SYSTEM_IDENTIFIER` | 숫자. 컨테이너 안 `psql`로 읽은 값과 같아야 한다. 원본 DB를 만든 직후 host endpoint로 붙은 Prisma 연결에서 읽은 값도 같아야 하며 다르면 그 DB를 자기 DB 조건으로 지우고 실패한다 |
| `T215_PG_ROLE` | DB를 만들 수 있는 role 이름. 컨테이너 안 socket 접속과 host URL에 같이 쓴다 |
| `T215_PG_ADMIN_DB` | 카탈로그 읽기와 자기 DB `CREATE`·`DROP`에만 쓰는 접속 DB 이름. 자기 두 DB 이름과 같으면 거부한다 |
| `T215_DOCKER` | 부모가 실제로 확인한 docker 실행 파일 절대 경로. 파일이 없으면 실패한다. PATH 검색을 하지 않는다 |
| `T215_DOCKER_HOST` | 기존 전용 PG를 돌리는 로컬 Docker daemon 주소. Windows는 로컬 named pipe(`npipe:////./pipe/<이름>`), Linux는 로컬 Unix socket(`unix:///<절대 경로>`)만 받는다. `tcp://`·`ssh://`·`http(s)://` 같은 외부·원격 daemon, 다른 scheme, 빈 값은 docker 호출 없이 거부하며 기본 context나 `DOCKER_CONTEXT`로 fallback하지 않는다. 자식에 `DOCKER_HOST`로만 넘기고 빈 `DOCKER_CONFIG`로 사용자 context·config를 읽지 않는다. 실제 값은 이 계획에서 조회하거나 정하지 않는다 |
| `T215_PNPM_STORE` | 이미 있는 pnpm store의 절대 경로. 이 Windows 개발기에서는 실제 경로도 E 드라이브여야 하고 Linux CI에서는 소유자가 배정한 기존 절대 경로를 쓴다. 오프라인 설치에만 쓴다 |
| `T215_WORK_ROOT` | 소유 임시 루트 절대 경로이며 실제 경로가 checkout 밖이어야 한다. 이 Windows 개발기에서는 실제 경로가 E 드라이브여야 한다. Linux CI에서는 작업 소유자가 배정한 기존 소유 절대 임시 경로를 쓴다. 같은 도구의 중복 실행 잠금은 이 루트 안의 `t215.lock` 디렉터리를 `mkdir`로 잡고 자기 runId를 적는다. 이미 있으면 빼앗지 않고 실패한다. 이 잠금은 같은 루트를 쓰는 이 도구끼리만 막으며 다른 작업자의 PG 사용을 막는 전역 예약이 아니다. PG 단독 사용은 부모의 슬롯 배정이 근거다 |

host 접속 URL `postgresql://<role>:<비밀번호>@<endpoint>/<DB>`는 부모 메모리에서만 만들고 자식 env의 `DATABASE_URL`로만 넘긴다. 인자, 로그, 증거, 오류 메시지에 넣지 않는다.

run 디렉터리는 `<T215_WORK_ROOT>/t215-<runId>`이며 이미 있으면 실패한다. 그 안에 `work/`(빈 cwd), `tmp/`, `home/`, `docker-config/`(빈 디렉터리), 공백이 든 `backup dir/`, archive 사본 `copy/`, `evidence/`를 만든다. 모든 temp·archive·덤프·증거는 여기에만 쓰며 이 Windows 개발기에서는 C 드라이브에 설치나 출력을 만들지 않는다. 끝나면 실제 경로가 루트 안이고 이름이 자기 runId와 같은지 확인한 뒤 `evidence/`만 남기고 지운다. 증거에는 비밀값, URL, 덤프를 넣지 않는다. 시험 부모 자체(vitest·tsx)의 임시 출력은 이 규칙이 아니라 부모 명령의 `TEMP`·`TMP`·`TMPDIR`를 따르므로 이 개발기에서는 단위와 같이 E 드라이브 소유 경로로 지정한 셸에서 돌린다.

자식마다 실행 파일, cwd, env를 아래로 고정한다. 어떤 자식도 `...process.env`를 복사하지 않고 `shell: true`를 쓰지 않는다. cwd에 `.env`가 없음을 spawn 직전마다 확인한다. 공통 기본 env는 `SystemRoot`, `TEMP`·`TMP`=`<run>/tmp`, `HOME`·`USERPROFILE`=`<run>/home`이다(Linux는 `SystemRoot` 대신 없음, `TMPDIR`=`<run>/tmp`).

- [복구 리허설](#복구-리허설) 1~7과 [정리와 보존 증거](#정리와-보존-증거) 전부를 실행한다. `finally`에서 성공과 실패 모두 정리하고 취소 신호에서도 같은 정리를 한다. 정리 순서는 진행 중인 실행권 보유자 abort·대기, 자기 자식 `stopOwnedChild`·종료 대기, Prisma 연결 해제, 자기 DB 두 개 drop, 끝 증거, 실행 잠금 해제, run 디렉터리 정리다.

- 이 파일은 `vitest.integration.config.ts`의 glob에 들어가므로 `pnpm test:int`에서도 돈다. 기존 CI의 `pnpm test:authz`도 `tools/run-authz.ts` → `test:int`를 거치므로 이 파일을 수집한다. 입력이 없으면 7개 case가 같은 사유로 실패하고 CI도 실패한다. 기존 CI 서비스 ID·system identifier·새 DB 두 개·소유 경로·별도 비밀 파일은 CI 담당이 명시 바인딩한다. pnpm exec vitest run tools/t2-15-backup-restore.test.ts

PowerShell에서도 같은 명령이며 Git Bash는 시험 안에서 절대 경로로 부른다. 단위 명령은 어느 개발기·CI에서도 추가 입력 없이 돈다. 통합 명령은 [실행 입력](#실행-입력과-자식-계약)을 모두 소유자가 준 기존 값으로 채운 부모 환경에서만 돌리고 없으면 미실행으로 기록한다.

## 구현 기록 (Codex)

- 진행 상태: B1 구현 중. 기준 `58b45a22aa874033194c9c7a61717b231d411d14`, 승인 계획 blob `f237a0629dda52b8643c97a8352f9b016315c9c0`이다. root58 원본 계획과 정정 이력은 외부 증거 경로에 해시와 함께 보존했다.
- 바꾼 것: B1 파일표의 백업·복구 스크립트, 두 줄의 줄끝 규칙, 월 진행 자식, 단위·실제 PG 시험, release-operations §4를 작성했다. 실제 진행은 기존 `TurnLoop.advanceTo`와 15초 리스의 순차 `renewLease`를 쓴다. DB·컨테이너·프로세스 정리는 소유 범위만 다룬다.
- 계획과 달라진 점과 이유: archive 사본에는 `.git`이 없어 release SHA 전달 계약이 빠져 있었다. 총괄의 기술 결정에 따라 backup 필수 `--release-sha`와 40자리 16진 검사를 추가하고 Git fallback을 없앴다. 리허설은 검토된 소스 HEAD를 명시 전달하고 manifest와 대조한다. 운영 current SHA를 얻는 방법과 비밀 파일·cutover는 B2·B3로 남긴다. 운영 복구는 그 계약 전까지 거부한다.
- 검증 결과: release SHA 보완 전 49개, 보완 직후 관련 8개 통과 원문을 보존했다. 첫 독립 Claude 리뷰는 R1 필수 1건으로 수정 필요였다. R1 수정과 CI 경로 정정 뒤 지연 주입 6개·플랫폼 경로 6개를 포함한 현재 단위 67개 전체가 통과했고 skip은 0이다. 집중 ESLint·직접 strict TypeScript·Bash 구문·Prettier·strict 문구·diff 검사도 수행했다. 전체 check·설치·generate·Docker·실제 PG·브라우저는 실행하지 않았다. 기존 E 영수증에서는 M1의 `127.0.0.1:5433`만 확인했으며 B1 전용 컨테이너와 별도 비밀번호 파일은 아직 확인하지 못했다. DB가 없다는 판정은 아니다. 실제 local 인증·stdin 복구·오프라인 준비와 정리 시간은 미검증이다. PG 리허설과 AC 판정은 별도 배정과 증거를 기다린다.
- R1 수정: 기존 Vitest hook·case 30초는 그대로 두고 B1 단계의 자체 기한을 20초로 뒀다. 기한에는 고정 실패 사유를 남기고 abort하며 뒤 단계는 같은 사유로 실패한다. 기한 뒤에도 끝나지 않은 원래 promise는 Set으로 계속 소유하고 정리가 모두 끝날 때까지 기다린 뒤 DB를 다룬다. 늦은 완료는 통과로 적지 않는다. 이 B1 전용 도우미는 월 진행 자식 파일에서 내보내며 전역 기능을 켜지 않는다. 루트 package.json에 없는 workspace 별칭 대신 기존 소스 진입점을 상대 import했다. 임시 루트 별칭을 지운 상태에서 검사했다.
