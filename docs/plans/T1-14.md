# T1-14 로그인·가입 화면

> 대기열: T1-14 · AC: AC-M1-05 (화면) · 구현: Claude · 리뷰: Codex
> 선행: T1-10 (API), T1-13 (화면 기반)

## 계획 (Claude)

### 목표

T1-10의 계정 API로 가입·로그인·로그아웃을 화면에서 한다. 이 화면까지 끝나야 AC-M1-05가 사용자 기준으로 끝난다.

### 범위

`apps/web`의 `/login`, `/signup`, 위쪽 띠의 로그아웃, 로그인 가드가 `auth.me`를 쓰도록 연결.

### 하지 않는 것

이메일 인증·비밀번호 재설정·약관 동의(M3 T3-03).

### 결정

- 입력 검사는 화면에서도 하되(이메일 형식, 비밀번호 10~128자) 최종 판단은 서버 응답.
- 오류 표시: `UNAUTHORIZED` → "이메일 또는 비밀번호가 맞지 않습니다", `CONFLICT` → "이미 가입된 이메일입니다", 네트워크 → 다시 시도 버튼. <!-- lint-text-ignore J-2 -->
- 성공하면 `next` 주소로, 없으면 월드 목록이 생기기 전까지 첫 RUNNING 월드(`/w/:id`)로.
- 비밀번호 칸은 `autocomplete="current-password"`/`"new-password"`, 보이기 토글.
- 제출 중에는 버튼을 막고 진행 표시.

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 흐름 | Playwright: 가입 → 메인 이동 → 로그아웃 → 로그인 → 메인 |
| 오류 | Playwright: 틀린 비밀번호, 중복 이메일 메시지 |
| 가드 | Playwright: 로그아웃 상태에서 `/w/1` → 로그인 → 원래 주소로 복귀 |
| 키보드 | Playwright: Tab·Enter만으로 로그인 |

구현하면서 함께 채운다. 리뷰어는 문서도 확인한다.

  - 오류 문구에 `BAD_REQUEST` → "입력값을 확인하세요"를 더했다 (화면 검사를 우회한 입력). <!-- lint-text-ignore J-2 -->
  - `next`에 다른 사이트 주소(`//evil`, `/\evil`, 탭 포함)를 막는 검사를 더했다. 계획에는 없었지만 열린 리다이렉트를 막기 위해 필요하다.

- Codex 리뷰 반영 (2026-10-20, 2차):
  1. 가드 재확인: `router.tsx`의 `currentUser`를 `ensureQueryData` → `fetchQuery({ staleTime: 0 })`로 바꿔 이동마다 서버에 세션을 묻는다.
     E2E `다른 탭에서 로그아웃하면 이 탭의 다음 이동도 로그인으로 간다`(`next=/w/1/map`까지 확인), `세션이 서버에서 없어지면 다음 이동은 로그인으로 간다` 추가.

     E2E `네트워크 실패 뒤 입력을 고치고 다시 시도하면 고친 값으로 로그인한다`(Codex 재현과 같은 순서) 추가.
  3. **E2E 주소 검사 결함 수정 (리뷰에는 없던 것).** `toHaveURL(/\/w\/1$/)`가 실패해 머문 `/login?next=/w/1`에도 맞아 거짓 통과할 수 있었다.
     모든 `toHaveURL`을 baseURL 기준 정확한 문자열 비교로 바꿨다. 특히 1차의 `Tab과 Enter만으로 로그인한다`는 화면 확인 없이 이 검사만 있어 거짓 통과였을 수 있다.
  - 회귀 확인: 옛 코드(`ensureQueryData`, 기억한 입력으로 재전송)로 잠시 되돌리면 새 E2E 3개가 모두 실패하고(다시 시도 테스트는 주소 검사 수정 뒤 실패: `/login?next=/w/1`에 머묾), 고친 코드로 복원하면 통과한다.
  - 검증: `pnpm e2e` **24개 통과**, `pnpm check` 통과(lint 0건, 타입, 단위 15개 파일/106개), `apps/web` 운영 빌드 통과.

  - `pnpm check`: Prisma 생성·전체 lint·전체 타입 검사·단위 **14개 파일/103개 통과**. 구현 기록 당시의 엔진 lint 오류는 현재 없다.

- 고칠 것:
  1. **[P2] 로그인 가드가 만료된 인증 캐시를 계속 사용한다.** `apps/web/src/router.tsx:29~31`의 `ensureQueryData`는 데이터가 있으면 stale 여부와 관계없이 즉시 반환하고, 이 호출에는 재검증도 없다. `staleTime: 10_000`이 가드의 재확인을 보장하지 않는다. <!-- lint-text-ignore C-11 -->
     - 실제 Chromium 2탭 재현: A에서 `/w/1` 진입 → 같은 context의 B에서 화면으로 로그아웃 → A의 실제 `auth.me` 응답이 `user: null`임을 확인 → 11초 후 A에서 지도 링크 클릭. 기대는 `/login?next=…`, 실제는 `/w/1/map` 보호 화면 진입이다. API 권한 우회를 확인한 것은 아니며, 로그인 가드의 세션 동기화 문제다. <!-- lint-text-ignore C-11 -->
     - 수정: 가드가 적절한 시점에 현재 세션을 다시 확인하도록 하고, 다른 탭 로그아웃·세션 만료 뒤의 SPA 이동을 E2E로 추가한다. `revalidateIfStale`의 백그라운드 갱신만으로 이전 사용자 판정을 계속 허용하지 않도록 한다. <!-- lint-text-ignore C-11 -->
  2. **[P2] 다시 시도가 화면에서 수정한 입력을 무시한다.** `apps/web/src/auth/AuthForm.tsx:118~120`은 현재 폼 대신 마지막 실패 시점의 `lastInput.current`를 전송한다. 오류가 떠 있어도 입력 칸을 수정할 수 있어 보이는 값과 전송되는 값이 달라진다.
     - 실제 Chromium 재현: 틀린 이메일로 로그인 제출 때 요청만 `route.abort`해 네트워크 실패 유도 → 네트워크 복구 → 화면 이메일을 실제 가입 계정으로 수정 → ‘다시 시도’. 실제 API는 이전 이메일을 받아 UNAUTHORIZED를 반환한다. 같은 화면 값을 그대로 두고 일반 ‘로그인’을 누르면 성공하는 대조 확인도 했다. <!-- lint-text-ignore J-2 -->
     - 수정: 다시 시도도 현재 폼을 읽어 검증·전송하거나, 입력 변경 시 이전 재시도 상태를 없앤다. 네트워크 오류 후 이메일·비밀번호 수정 시나리오를 E2E에 추가한다.

## 재리뷰 (Codex, 2026-10-20)

- 결과: **통과**. 앞선 P2 2건이 해결되어 T1-14를 `완료`, AC-M1-05를 ✅로 바꾼다. <!-- lint-text-ignore C-5 -->
- 확인한 것:
  - `currentUser`가 `fetchQuery({ staleTime: 0 })`로 이동 시 서버의 현재 세션을 기다려 확인한다. 다른 탭 로그아웃과 쿠키가 사라진 뒤의 SPA 이동은 로그인으로 돌아간다. 백그라운드 갱신 뒤에 이전 사용자로 통과시키는 방식이 아니다.
  - `lastInput`을 제거하고 다시 시도는 현재 폼의 `requestSubmit()`을 호출한다. 최초 제출과 같은 입력 검사·pending 가드를 거치며 수정한 값을 전송한다.
  - 기존의 URL 정규식이 `/login?next=/w/1`을 성공으로 오인할 수 있던 부분을 정확한 주소 비교로 바꿨다. 새 회귀 3개도 현재 보호 화면 진입·로그인 복귀를 실제로 검증한다.
  - `docs/frontend-ui-guidelines.md §4`의 서버 재확인·현재 입력 재전송 설명이 구현과 일치한다.
