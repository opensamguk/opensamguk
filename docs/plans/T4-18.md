`BattleInput`(`simulate.ts:7-14`)에 선택 칸 둘을 더한다: `attackerModifiers?: BattleModifiers`, `defenderModifiers?: BattleModifiers`. 기존 칸과 뜻은 그대로다.

### 2.2 `applyModifiers` 처리 순서

1. `modifiers.length === 0`이면 `base`를 그대로 돌려준다. 검사도 `min`도 하지 않는다. `-0`도 `-0`으로 남는다.
2. 검사. 하나라도 어기면 `Error`를 던진다: `base`가 유한한 수, `source`가 위 정규식, `op`가 `add`·`mul`, `value`가 유한한 수, `mul`의 `value ≥ 0`, 같은 `(source, op)` 쌍이 두 번 없음, `min`이 있으면 유한한 수.
3. 정렬한 사본을 만든다. 기준은 `source`의 UTF-16 코드 단위 오름차순(`a < b`, `localeCompare` 금지), 같으면 `add`가 `mul`보다 앞이다. 2번의 중복 금지로 순서가 하나로 정해진다. 입력 배열은 바꾸지 않는다.
4. `x = base`. 정렬 순서대로 `add`만 왼쪽부터 더한다: `x = x + value`.
5. 정렬 순서대로 `mul`만 왼쪽부터 곱한다: `x = x * value`.
6. `x`가 유한하지 않으면 `Error`.
7. `min`이 있으면 `Math.max(min, x)`. 1번 경로에서는 적용하지 않는다.

결과식은 `((base + a₁) + a₂ …) × m₁ × m₂ …`이며 결합 순서까지 위와 같다. 반올림과 상한은 이 함수에 없다.

### 2.3 제공자 계약

`collectModifiersWith`는 제공자를 목록 순서대로 부르고 결과를 이어 붙인 새 배열을 돌려준다. 검사는 `applyModifiers`가 한다. 제공자는 다음을 지킨다. 어기면 그 제공자 작업의 리뷰에서 막는다.

- P1. 순수 함수다. 난수를 받지도 쓰지도 않는다(서명에 `Rng`가 없다). `view`를 바꾸지 않는다.
- P2. 같은 `view`, `generalId`, `context`면 같은 배열을 낸다.
- P3. 자기 상태가 없는 월드(확장을 끈 월드, 장비·특기가 없는 장수)에서는 빈 배열을 낸다. 그래서 끈 월드는 제공자를 등록한 뒤에도 무수정자 경로로 간다(C3).
- P4. 명령 정의, `commandRegistry`, `ext/registry.ts`를 import하지 않는다. `investment.ts`와 `attack.ts`가 `modifiers/`를 import하므로 순환이 생긴다(T4-02 `state.ts:75`와 같은 이유).

### 2.4 삽입 위치 (세 곳)

| 단계 | 위치 | 바꾸는 줄 |
| ---- | ---- | --------- |
| `domestic.score` | `investment.ts:89`(전선 배수) 바로 뒤, `:90`(`points`) 바로 앞 | `score = applyModifiers(score, collectModifiers(view, general.id, { stage: 'domestic.score', commandKey: spec.key }), { min: 0 });` |
| `battle.dealt`, `battle.taken` | `simulate.ts:35-44`의 `power` 계산 뒤, `:45`의 반올림 앞 | `power`에 피해를 주는 쪽의 `dealt`를 먼저, 받는 쪽의 `taken`을 다음에 적용. `damage`가 두 쪽의 `BattleModifiers`를 인자로 받는다 |
| 출병 전달 | `attack.ts:66-71`(수비 장수전), `:88-100`(성벽전) | 각 `simulateBattle` 호출 직전(먹이기 뒤) `collectModifiers(state, id, { stage, commandKey: 'attack' })`로 공격 장수와 수비 장수의 `dealt`·`taken`을 모아 넘긴다. 성벽은 장수가 아니므로 `defenderModifiers`를 넘기지 않는다 |

여기서 정해지는 것:

- 난수. 수정자는 내정에서 모든 `rng.next()` 호출(`:85-88`) 뒤에 적용되므로 내정의 호출 수와 순서는 수정자와 무관하게 같다. 전투에서는 페이즈마다 `next` 2회가 그대로다. 다만 피해가 달라져 전투가 일찍 끝나면 페이즈 수가 줄어 호출 수도 준다. 이것은 지금도 병력에 따라 생기는 일이며 틀이 새로 쓰는 난수는 없다.
- 반올림. 기존 자리 그대로다. 내정은 `:90`, `:93`, `:102`, 전투는 `:45`. 수정자는 모두 반올림 앞이다.
- 상한. 기존 자리 그대로다. 내정은 효과 적용(`effects.ts:32-37`), 전투는 `min(상대 병력, max(1, …))`(`simulate.ts:45`). 수정자가 상한을 넘기지 못한다. 틀이 새로 거는 하한은 내정 점수의 `min: 0` 하나이며 수정자가 하나 이상일 때만 걸린다. 음수 점수가 경험·공헌을 깎는 일을 막는다.
- 내정 수정자가 바꾸는 것. `score` 한 자리에 걸리므로 도시 변화량, 경험, 공헌이 함께 따라간다(쟁점 T18-Q1).

### 2.5 무수정자 동등성

운영 제공자 목록이 비어 있으므로 T4-18 병합 직후 모든 경로는 2.2의 1번을 지난다. 수정자를 넘기지 않은 `simulateBattle`도 같다. 그래서 기존 출병·전투·내정·12개월 재생의 결과와 난수 소비, T4-34 시뮬레이터 결과가 바이트 단위로 같아야 한다. 4절 V1~V5가 이를 확인한다.

### 2.6 단계를 더하는 규칙

T4-22·T4-25가 다른 계산(능력치, 확률, 다른 명령)에 수정자가 필요하면 `ModifierStage`에 값을 하나 더한다. 그 삽입 위치와 무수정자 골든을 자기 PR에서 낸다. 이미 있는 세 단계의 위치와 2.2의 순서는 바꾸지 않는다.

### 2.7 export

명시 export 한 줄이다. T4-02 구현 기록처럼 시험 helper(`collectModifiersWith`)와 운영 목록(`modifierProviders`)은 내보내지 않는다. `index.ts` 반영 순서는 T4-33 → T4-30 → T4-02 → T4-18이며 T4-02 줄 바로 뒤에 둔다.

## 구현 기록 (Codex)

- 바꾼 것: `modifiers/`에 결정적인 합산, 빈 운영 제공자 목록, 제공자 수집과 시험을 넣었다. 투자 점수의 전선 보정 뒤와 반올림 앞, 전투 피해의 반올림 앞에 수정자를 연결했다. 출병은 먹이기 뒤에 장수별 수정자를 모으며 성벽에는 수비 장수 수정자를 넘기지 않는다. 운영 제공자와 장비·특기 효과 수치는 추가하지 않았다. 파일 지도에 한 줄을 더했다.
- 계획과 달라진 점과 이유: H·V5를 실제 제공자로 시험하려고 비공개 collector factory와 모듈 한정 `makeInvestmentWithProviders`·`createAttackWithProviders`를 넣는 안을 부모가 수용했다(2026-10-23). 운영 경로는 기존 `makeInvestment`·`attack`과 실제 `collectModifiers`를 쓴다. 루트 export에서 helper와 등록부가 빠지는 시험을 뒀다. 부모가 루트 `index.ts`를 직렬로 고치므로 이 작업은 손대지 않았으며 §2.7의 명시 export 한 줄을 전달한다. 커밋·푸시도 부모 지시에 따라 하지 않았다.
- 검증 결과: V1은 hook 구현 전에 기준 `09604e71806b1f22012ab6df9026e02085d80a38`을 `git archive`로 `/tmp/opensamguk-t4-18-baseline.8UNaKE`에 풀어 실측했다. 투자 8종 × 일반·전선·치명 성공·치명 실패·민심 0·최대치 직전의 48개 결과와 적용 상태 SHA-256, RNG 2·3회와 다음 값을 inline snapshot으로 고정했다. 기준 코드와 구현 전 작업실에서 각각 snapshot 갱신 없이 1개 시험이 통과한 뒤에 생산 코드를 고쳤다. 골든 파일의 Git blob은 `b7be3518101ffb84ab3da6df450489c4d883cd0b`이며 생성 뒤 바뀌지 않았다. 구현 뒤에는 `pnpm exec vitest run packages/rules/src/modifiers packages/rules/src/commands/domestic/investment.test.ts packages/rules/src/commands/attack.test.ts packages/rules/src/battle packages/rules/src/replay.test.ts apps/web/src/battleSim tools/lint-boundaries.test.ts --maxWorkers=2`로 10파일 146개가 통과했다(33.17초). 기존 출병·전투·12개월 재생·T4-34 골든은 고치지 않았다.
