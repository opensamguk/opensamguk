## 계획 (Claude)

### 1. 목표

AC-P2-25(명세 §5 문장 그대로): 확장 실행은 C19의 결정적 입력 시나리오로 증명한다. 확장 명령 key마다 엔진에서 성공·대표 실패 1건 이상, 즉시 행동 kind마다 APPLIED·REJECTED 1건 이상이 실행된다. 확장마다 켠 월드, 모두 켠 월드, 끈 월드의 DB·HTTP·Chromium·롤백·재생 증거가 있다. 모두 켠 프리셋으로 `pnpm sim --seeds 10`이 오류 없이 끝나고 시간이 기록된다. 개발 PC 시간은 AC-M1-18 기준으로 따로 적는다. 새 API 전부가 AC-M3-03의 권한 대조(`compareAuthz`)에서 빠진 범주 0건이다. 모든 T4 작업이 완료이거나 미완료 목록에 이유와 함께 있다.

이 작업은 세 가지를 만든다.

1. 실행 하한 시험. 운영 목록에서 확장 명령 key, 즉시 입력 kind, 규칙 기능 key를 읽어 하한을 스스로 계산하고 결정적 시나리오를 돌려 센다. 목록에 새 key가 생겼는데 시나리오가 없으면 실패한다.
2. 모두 켠 프리셋의 시뮬레이터 실행과 시간 기록.
3. Phase 2 완료 판정 절차와 판정표. 모든 T4 행과 AC-P2 행의 증거를 한 표에 모으고 판정 규칙을 적는다.

T4-47은 다른 작업의 증거를 대신 만들지 않는다. 각 작업의 시험이 낸 증거를 모으고 교차 경로(모두 켠 월드, 끈 월드 골든, 하한)만 새로 시험한다.

### 5. 실행 하한 시험

#### 5.1 시나리오 형식

```ts
interface CoverageScenario {
  key: string; // 확장 이름
  preset: string; // 프리셋 key 또는 판
  ruleFeatures?: string[];
  seed: string;
  months: number | 'fromEvents'; // 가속으로 돌 달 수. 'fromEvents'는 아래 5.3대로 생성된 조각에서 계산
  humans: { name: string; nation: number; city: string }[]; // 사람 장수
  setup?: { human: number; atMonth: number; commandKey: 'found' | 'join'; args: unknown }[]; // 직책이나 소속을 실제 명령으로 얻는다
  turns: { human: number; atMonth: number; slot: number; commandKey: string; args: unknown }[]; // 장수 예턴, 직접 입력 turns.set
  nationTurns: { human: number; atMonth: number; slot: number; commandKey: string; args: unknown }[]; // 국가 예턴, 직접 입력 nationTurns.set (T2-05)
  inputs: { human: number; atMonth: number; kind: string; payload: unknown }[]; // 대기 입력, submitInput (T4-49)
  expect: {
    commands?: Record<string, { success: number; failures: string[] }>; // 실패는 code
    inputs?: Record<string, { applied: number; rejected: string[] }>;
    features?: Record<string, string[]>; // 기능 자리 표식
  };
}
```

- 사람 장수 몫의 예턴과 입력을 미리 넣는다. NPC 정책은 바꾸지 않는다(C11).
- 입력은 경로가 셋이고 모두 실제 API 절차를 지난다. 시험이 상태나 DB 행을 직접 고치지 않는다(T4-03 E1).

| 칸 | 경로 | 처리 | 근거 |
| -- | ---- | ---- | ---- |
| `turns` | `turns.set` 직접 입력. 서버가 같은 트랜잭션에서 적용하고 sequence를 받는다 | 장수 명령만 받는다. 지금 `parseSlot`은 기본 목록의 `target === 'general'`만 받으며(`apps/server/src/game/slots.ts:7-13`) 확장 key는 T4-03 E2의 resolver 연결 뒤에 저장된다 | `apps/server/src/routers/turns.ts:31-80`, T4-03 E2 |
| `nationTurns` | T2-05 `nationTurns.set({ worldId, office: { nationId, officerLevel, tenure }, revision, slots })` 직접 입력. 정확히 12칸 | 실행기는 먼저 그 직책 칸을 읽어 `tenure`·`revision`을 얻고 12칸 전체를 보낸다. `STALE`이면 응답의 최신 `revision`·칸으로 한 번 다시 보낸다. 두 번째도 실패하면 시험 실패다. 확장 국가 명령은 T4-50의 resolver 연결 뒤에 저장된다 | T2-05 계획(직책 칸 12칸, revision·tenure, `STALE`), T4-50 |
| `inputs` | T4-49 `submitInput`으로 기록하는 대기 입력 | 엔진이 꺼내 처리한다. `atMonth`가 될 때까지 가속을 멈췄다가 넣는다 | T2-26 통합 입력 처리기, T4-49 |

- 국가 명령은 군주(또는 T2-05가 정한 직책) 턴에만 실행된다(`packages/rules/src/commands/turn.ts:31-60`). 시나리오 국가의 군주는 NPC라서 사람 장수가 직책을 얻어야 한다. `setup`은 재야 사람 장수가 빈 도시에서 실제 `found` 명령을 예약해 건국하고 군주가 되는 단계다(`packages/rules/src/commands/personnel.ts:7-52`). 건국 뒤 `nationTurns`를 넣는다. 초반 보호(`presetRules.protection.foundUntilMonths`)가 있는 프리셋이면 그 달 뒤로 `atMonth`를 둔다.
- 전략 3종처럼 대상 국가가 필요한 명령은 시나리오 국가를 대상으로 한다. 재사용 대기(T4-06)의 대표 실패는 같은 명령을 대기 안에 다시 예약해 얻는다.
- 대표 실패는 각 명령 계획의 대표 실패 표에서 하나를 고른다(예: 계략은 불가침 대상 `BAD_TARGET`).

#### 5.3 실행 기간

12개월로는 역사 사건 하한을 채울 수 없다. 1030은 191년 1월에 시작하고(`resources/scenario/1030.json`의 `startYear`) 사건 후보의 첫 시점이 194년, 둘째가 196년 8월이다([T4-43 §3](./T4-43.md)). 상태를 직접 고치지 않고 사건 선택 1건과 기본 적용 1건을 얻으려면 첫 두 사건이 모두 적용될 때까지 돌아야 한다.

- `months: 'fromEvents'`는 생성된 `historicEvents` 조각의 `events`에서 시점 순 둘째 사건의 달 번호에 `windowMonths`와 1을 더한 값이다. 사건 표가 RQ43-1·RQ43-2 결정으로 바뀌어도 실행기가 따라간다. 지금 후보와 RQ43-4 최댓값 3이면 196년 8월 + 3 + 1로 약 71개월이다.
- 입력 일정: 첫 사건이 일어난 정산 뒤 같은 달에 고를 자격이 없는 사람 장수의 `historic-events.choose`(REJECTED)와 자격이 있는 사람 장수의 선택(APPLIED)을 넣는다. 둘째 사건은 아무도 고르지 않아 기본 적용 1건이 된다.
- 선택 APPLIED를 실제 경로로 만들 수 있는지는 [T4-43](./T4-43.md) RQ43-7에 달렸다. 1030 시작 국가의 군주는 모두 NPC이고 사람 장수가 그 자리에 오르는 경로가 지금 없다(`packages/rules/src/commands/personnel.ts`의 임관은 `officerLevel = 1`). RQ43-7이 권장안 (가)면 사람 장수가 실제 `join`으로 고르는 국가에 임관한 뒤(`setup` 칸) 고른다. 군주만 고르게 정하면 실제 경로로 APPLIED를 만들 수 없다. 그때는 이 하한을 REJECTED와 기본 적용으로 줄일지 사용자에게 올리고 시험용 상태 주입으로 대신하지 않는다.
- 다른 확장의 명령·입력은 앞 12개월 안에 넣는다. K6의 끈 월드 비교는 12개월 그대로다.
- 72개월 안팎의 가속 실행이 CI 시간 안에 끝나는지 구현 기록에 시간을 적는다. 넘치면 K5를 두 실행으로 나눈다. K5a는 `phase2-all` 월드에서 다른 확장의 명령·입력을 넣고 12개월을 돈다. K5b는 같은 `phase2-all` 프리셋의 새 월드에서 사건 입력 일정과 다른 확장의 앞 12개월 명령·입력을 함께 넣고 `fromEvents` 기간을 돈다. 두 실행 모두 하한을 넘고 K3(두 번 실행 결과 동일)과 K4(수출 → 읽기 → 순수 재생 해시가 엔진 월간 해시와 같음)를 만족해야 K5 통과다. 사건 하한을 기능 하나만 켠 K2 월드에서만 채우는 것은 모두 켠 월드 증거로 세지 않는다. CI 한 작업의 시간 한도를 넘으면 K5b를 따로 된 CI 작업으로 돌리되 같은 판정 SHA에서 돌린다.

### 7. 완료 판정 절차

#### 7.1 판정 순서

1. 판정 대상 SHA를 하나 고른다. 그 SHA의 pull·push CI(단위, PostgreSQL, Chromium, 빌드, `lint:text --strict`)와 simulation 작업이 성공해야 한다.
2. 같은 SHA에서 K1~K8, 권한 대조(`pnpm test:int -- tools/authz.integration.test.ts`의 누락 0), 명령 대응표(`node tools/command-coverage.mjs`)를 돌린다.
3. 모두 켠 프리셋으로 `pnpm sim --preset phase2-all --seeds 10`을 hosted 실행기에서 돌려 오류 없음과 시드별 시간을 기록한다. 개발 PC 시간은 AC-M1-18 기준으로 따로 적는다. 공용 자원 승인 없이 로컬 대규모 실행을 시작하지 않는다(C19).
4. §7.2 T4 판정표와 §7.3 AC 판정표를 채운다.
5. Claude 리뷰가 표의 증거를 SHA와 함께 다시 확인한다. 리뷰가 통과하면 조율 세션이 인수조건 문서에 AC-P2-25 상태를 반영하고 사용자에게 Phase 2 판정을 보고한다.

#### 7.4 Phase 2 완료 규칙

Phase 2는 아래가 모두 참일 때만 완료로 보고한다.

- §7.3의 모든 AC-P2가 인수조건 정본에서 ✅다. 사용자가 결정 기록으로 범위에서 뺀 AC(예: 승인 항목 A-11로 줄인 D4 2차)는 그 결정 번호를 판정표에 적는다. <!-- lint-text-ignore C-5 -->
- §7.2의 모든 T4 행이 완료이거나 결정 기록으로 범위에서 빠졌다. 미완료 목록에 남은 행이 있으면 Phase 2는 미완료이며 그 목록을 그대로 보고한다.
- 판정 SHA에서 K1~K8, 권한 대조 누락 0, `lint:text --strict` 0건, sim 10시드 오류 0이다.

이 규칙은 T4-47 자체의 완료 조건(AC-P2-25)과 다르다. AC-P2-25는 미완료 목록이 이유와 함께 있으면 통과할 수 있지만 Phase 2 완료는 미완료가 없어야 한다.
