### 발령 응답 결정 (D11)

```text
발령 실행 ─┬─ 대상이 NPC → 즉시 이동 (M1과 같음)
           └─ 대상이 사람 → AssignmentOffer(PENDING, expiresTick = 지금 + 2개월)
                 ├─ 수락 (즉시 행동, 턴 소비 없음) → 대상 도시로 이동
                 ├─ 거절 (즉시 행동) → 공헌 −10% (balance.ts), 로그
                 ├─ 기한 지남 → 월간 정산에서 수락 처리
                 └─ 수락 전에 취소 조건 셋 중 하나 → CANCELLED, 벌점 없음 (U2)
```

- 같은 장수에게 PENDING 제안은 하나뿐이다. DB도 부분 유일 색인으로 막는다. 새 발령이 오면 이전 것은 `SUPERSEDED`이고 벌점이 없다.
- 제안 상태: `PENDING`, `ACCEPTED`(응답 또는 기한 지남, `resolvedBy`가 `RESPONSE`·`EXPIRY`), `REJECTED`, `SUPERSEDED`, `CANCELLED`(아래 취소 검사, `cancelReason`이 있다).

#### 수락 전 자동 취소 (U2, 2026-10-23 사용자 답)

사용자 답(D-027): 발령 제안을 수락하기 전에 아래 셋 중 하나가 일어나면 제안은 자동 취소되고 벌점은 없다. 이 밖의 경우로 넓히지 않는다.

| 조건 | 판정 (그 시점의 상태) | `cancelReason` |
| ---- | --------------------- | -------------- |
| 목표 도시 상실 | `cities[offer.cityKey].nationId`가 `offer.nationId`가 아니다 | `CITY_LOST` |
| 대상 탈국 | 대상 장수가 없거나 `nationId`가 `offer.nationId`가 아니다 | `TARGET_LEFT` |
| 발령자 직책 상실 | 발령자가 없거나 `nationId`가 `offer.nationId`가 아니거나 `officerLevel`이 발령 권한 직책(위 권한 표의 포상·몰수·발령 열, 5~12)이 아니다 | `ISSUER_LOST_OFFICE` |

- 직책 상실은 발령 권한이 있는 직책을 모두 잃은 경우로 읽는다. 권한 직책 사이의 이동(예: 수뇌 → 참모)은 상실로 보지 않는다. 이 읽기가 답의 뜻과 다르면 위 판정식만 바꾼다.
- 둘 이상이 함께 맞으면 위 표 순서의 첫 사유 하나만 적는다. 재생 결과를 하나로 고정하려는 순서이며 제품 의미는 없다.
- 취소된 제안은 공헌·위치·직책을 바꾸지 않는다(`dedicationLost` 0과 같은 뜻). 대상 장수에게 장수 로그 한 줄을 남긴다. `commandKey`는 `offer.cancel`이고 문구는 글쓰기 규칙을 따른다.
- 검사 시점: 순수 함수 `closeInvalidOffers(state)`가 PENDING 제안마다 위 표를 보고 맞는 것을 `CANCELLED`로 닫아 `closedOffers`에 싣는다. 세계 상태를 바꾸는 모든 step 끝에서 `syncOffices` 바로 뒤에 같은 자리에서 부른다(턴, 월간 정산, 즉시 행동, 재생). 그래서 해임 뒤 재임명처럼 조건이 깨졌다가 돌아오는 경우도 깨진 step에서 이미 닫힌다.
  도시 소유, 국가 소속, officerLevel을 바꾸는 새 경로(예: T2-07 도시 이양, Phase 2 선양)도 같은 step에서 이 함수를 불러야 한다. `syncOffices`의 적용 범위 규칙과 같다.
- 월간 정산 안의 순서: 기존 월간 처리 → `closeInvalidOffers` → 기한 지난 PENDING 제안 수락 → NPC 군주 인사(3개월마다) → step 끝의 `syncOffices`·`closeInvalidOffers`. 기한 달에 조건이 깨졌으면 기한 수락이 아니라 취소다.
- 응답 처리: 수락·거절 응답은 제안이 PENDING일 때만 집행한다. 위 검사가 매 step 끝에서 먼저 돌므로 PENDING 제안은 늘 세 조건을 지킨다. 엔진은 응답과 기한 수락을 집행하기 전에 같은 판정으로 이 불변식을 확인하고 어기면 트랜잭션을 되돌린다(호출 누락 버그). 이미 닫힌 제안의 응답은 지금처럼 `OFFER_CLOSED`다.
- 취소 로그의 행 번호: 그 step의 sequence와 `ordinal`을 적는다. 턴 step도 sequence를 받는다(main `3e5b52a` `turnLoop.ts:168`). 그래서 대상 장수의 같은 tick 턴 로그(sequence null)와 겹치지 않는다.
- 국가 멸망(`removeNation`)으로 제안의 국가 자체가 없어지는 경우는 U2 답의 범위 밖이다(미결 B1). 멸망 step에서는 위 표의 조건도 함께 맞지만 그것을 근거로 멸망을 U2와 같이 다루지 않는다.
  Codex는 B1 답 전에 그 갈래를 만들지 않는다. 그래서 origin 4 월드에서 PENDING 제안을 가진 국가가 멸망하는 경로는 B1 답 전까지 미완성이고 그 시험과 T2-05 엔진 병합 판정도 B1 뒤다. 위 세 조건의 순수 규칙·엔진 경로와 시험은 지금 만든다.
- **NPC 군주 인사** (월간 정산 뒤, 3개월마다): 소속 사람 장수 중 6개월 넘게 같은 후방 도시에 있는 장수를 전선 도시로 발령,
  국고가 기준 이상이면 공헌 상위 사람 장수에게 포상. 각 결정의 이유를 국가 역사에 한 줄로 남긴다.

### 즉시 행동의 접수와 완료 (R51-1)

임명·해임·발령 응답은 즉시 행동이다. 서버는 접수(InputEvent PENDING)만 하고 엔진이 처리해 APPLIED 또는 REJECTED로 끝낸다 (AGENTS.md §6). 기존 `general.create`(`apps/server/src/routers/general.ts:31-96`)와 같은 틀을 쓴다.

| InputEvent `kind` | 요청 | 결과(`result`) |
| ----------------- | ---- | -------------- |
| `personnel.appoint` | `{ generalId, officerLevel }` | `{ generalId, officerLevel, title }` |
| `personnel.dismiss` | `{ generalId }` | `{ generalId, officerLevel: 1, title }` |
| `offer.respond` | `{ offerId, accept }` | `{ offerStatus: 'ACCEPTED' \| 'REJECTED', city: CityRef, dedicationLost }` |

- 행위자: 서버가 세션 사용자에게서 장수를 정한다. 요청에 행위자 장수 ID를 받지 않는다.
- 접수 식별: 요청마다 화면이 만든 `requestId`(UUID)를 받는다. 세 종류 모두 `idempotencyKey`는 `personnel:<requestId>`이고 기존 `@@unique([worldId, userId, idempotencyKey])`(`schema.prisma:321`)가 중복을 막는다. `general.create`처럼 서버가 키를 만들지 않는다(`general.ts:61`과 다르다). 그래서 `requestId` 하나는 한 사용자·월드 안에서 한 종류의 요청에만 쓰인다.
- 변경 요청의 처리 순서는 아래와 같고 바꾸지 않는다. 개인 예턴 저장도 키 재검사를 다른 검사보다 먼저 한다(`apps/server/src/routers/turns.ts:40-44`).
  1. 세션 사용자 확인 (`protectedProcedure`). 무인증·제재 계정은 여기서 끝난다.
  2. World 행 잠금 (`requireWorld(tx, worldId, true)`, `apps/server/src/game/queries.ts:6-11`). 돌려받은 행의 `replayOrigin.version`이 4가 아니면 여기서 전환 경계 절의 거부로 끝난다.
  3. 같은 `(worldId, userId, idempotencyKey)`의 InputEvent를 찾는다. 있으면 종류와 내용이 같을 때 그 접수의 지금 상태를 돌려준다. PENDING이면 아래 응답 대기로 가고 APPLIED이면 원래 결과, REJECTED이면 원래 오류다. 종류나 내용이 다르면 CONFLICT `같은 요청 번호로 다른 내용을 보냈습니다`.
     이 단계는 권한·제안 상태의 사전 검사보다 먼저다. 그래서 임명 뒤 행위자 직책이 바뀌었거나 제안이 이미 끝났어도 같은 요청의 재전송은 새 효과 없이 원래 결과를 받는다. 이미 수락한 응답을 다시 보내 CONFLICT가 나는 일이 없다.
  4. 같은 접수가 없을 때만 사전 검사를 한다. 권한 표와 지금 DB 상태로 뻔한 거절(권한 없음, 남의 제안, 끝난 제안)을 InputEvent 없이 돌려준다. 통과해도 결과를 약속하지 않는다.
  5. 중복 클릭 검사: 한 행위자에게 PENDING 인사 접수는 하나다. 같은 제안에 PENDING 응답도 하나다. 다른 `requestId`로 또 보내면 CONFLICT `요청을 처리하는 중입니다`.
  6. InputEvent PENDING을 만든다.
- 엔진 처리: 새 `apps/engine/src/personnel.ts`의 `processPersonnel(tx, world, tick)`이 PENDING 접수(위 세 종류)를 id 순으로 한 번에 하나 처리한다. `turnLoop.ts`의 두 `processCreation` 호출(`:105`, `:137`) 바로 뒤에서 `processCreation`이 false일 때만 부른다. `processPersonnel`이 true이면 그 step을 `processCreation`이 true일 때와 같은 방식으로 끝낸다(`:106-116`, `:138-142`). 그래서 접수는 같은 step의 턴·월간 정산보다 먼저 처리된다. 지금 `general.create` 순서와 같고 U62-5가 처리기를 하나로 정하면 그 처리기에 갈래로 옮긴다.
  리스와 World를 잠근 같은 펜싱 트랜잭션에서 사용자 ACTIVE(`inputs.ts:32-35`처럼 `FOR SHARE`), 행위자 장수, 그때의 직책과 소속, 대상, 제안 PENDING을 다시 검사한다. RUNNING이 아닌 월드의 접수는 `WORLD_CLOSED`로 거절한다(`turnLoop.ts:104-105` 분기).
- 응답: 접수 뒤 5초까지 결과를 기다린다(`general.ts:69-95`와 같다). APPLIED이면 세션과 계정 상태를 다시 확인한 뒤(`general.ts:73-82`) 결과를 준다. REJECTED이면 그 코드의 오류를 낸다. 5초가 지나면 pending을 준다. 3번에서 찾은 기존 접수에도 같은 대기와 세션 확인을 한다.
- 최종 결과 재조회: `personnel.request({ worldId, requestId })`. 세션 사용자의 접수만 읽고 남의 `requestId`는 NOT_FOUND다. REJECTED도 값으로 돌려준다.
- 완료 뒤 재접속 복구: `personnel.recent({ worldId })`. 세션 사용자의 그 월드 인사 접수(위 세 종류) 가운데 `createdAt`이 24시간 안인 것을 최신 순으로 많아야 5개 돌려준다. 상태와 관계없이 `requestId`, `kind`, 지금 상태와 결과를 싣는다.
  응답을 못 받은 채 탭을 닫았고 그사이 엔진이 끝냈어도 다시 로그인한 화면이 여기서 `requestId`와 최종 결과를 찾는다. 조건에 `userId`가 들어가므로 남의 접수는 나오지 않는다.
  정리 시점: InputEvent는 재생 기록이라 지우지 않는다. 24시간이 지나면 이 목록에서만 빠지고 `personnel.request`로는 계속 읽는다.
  예전 계획의 `pendingRequest`·`pendingResponse` 필드는 PENDING만 실어 완료 뒤 복구를 못 하므로 지웠다. 복구 경로는 이 API 하나다.
- 대기 중 세션 만료·제재: 기다리는 동안 세션이 지워지거나 계정이 제재되면 결과를 내지 않고 UNAUTHORIZED다. 엔진은 제재된 사용자의 PENDING 접수를 `ACTOR_INACTIVE`로 거절한다. `personnel.request`와 `personnel.recent`도 `protectedProcedure`라 세션 확인을 건너뛰지 않는다.
- InputEvent 상태와 제안 상태는 다르다. 거절 응답이 처리되면 InputEvent는 APPLIED이고 제안은 REJECTED다. 화면은 제안이 목록에서 사라진 것으로 성공을 추측하지 않고 `requestId`의 결과를 본다.
- 화면 대기 계약(T2-06): 버튼은 접수부터 결과까지 막고 `처리 중`을 보인다. 응답을 못 받으면 같은 `requestId`로 다시 보낸다. pending이면 `personnel.request`를 1초마다 묻는다. 다시 접속하면 `personnel.recent`로 대기 중이거나 이미 끝난 접수를 되살린다.

```ts
type RequestState<R> =
  | { status: 'pending'; requestId: string }
  | { status: 'applied'; requestId: string; result: R }
  | { status: 'rejected'; requestId: string; code: string; message: string }; // personnel.request·recent에서만. 변경 요청은 오류로 낸다
type PersonnelKind = 'personnel.appoint' | 'personnel.dismiss' | 'offer.respond';
type PersonnelRecord = { kind: PersonnelKind; state: RequestState<AppointResult | RespondResult> };
// personnel.appoint({ worldId, requestId, generalId, officerLevel }) → RequestState<AppointResult> (rejected 제외)
// personnel.dismiss({ worldId, requestId, generalId })                → RequestState<AppointResult> (rejected 제외)
// offers.respond({ worldId, requestId, offerId, accept })            → RequestState<RespondResult> (rejected 제외)
// personnel.request({ worldId, requestId })                           → PersonnelRecord
// personnel.recent({ worldId })                                       → PersonnelRecord[]   최신 순, 24시간 안, 많아야 5개
type AppointResult = { generalId: number; officerLevel: number; title: string };
type RespondResult = { offerStatus: 'ACCEPTED' | 'REJECTED'; city: CityRef; dedicationLost: number };
//   city는 처리 뒤 내 장수가 있는 도시. dedicationLost는 거절이면 줄어든 공헌, 수락이면 0
```

### 저장·재생·원자성 (R51-2)

새 migration 하나에 넣는 것:

- `AssignmentOffer`: `id`(`<createdTick>-<issuerGeneralId>-<targetGeneralId>`, 재생에서 같은 값이 나온다), `worldId`, `nationId`, `issuerGeneralId`, `targetGeneralId`, `cityKey`, `status`, `resolvedBy`, `cancelReason`(`CANCELLED`일 때만), `createdTick`, `expiresTick`, `resolvedTick`.

- `GeneralLog.sequence Int?`와 `GeneralLog.ordinal Int NOT NULL DEFAULT 0`. 유일 조건을 둘로 나눈다.
  턴 로그는 지금처럼 `sequence`가 null이고 `(worldId, generalId, tick) WHERE sequence IS NULL`로 장수·tick당 한 행이다. 지금 색인은 `GeneralLog_worldId_generalId_tick_key`(`engine_turns` migration `:34`, 스키마 `schema.prisma:235`)이고 쓰는 곳은 `turnLoop.ts:196-205`다.

  즉시 행동 로그는 그 InputEvent의 sequence를 적는다. 월간 인사 로그(기한 수락, NPC 군주 발령·포상)에는 InputEvent가 없다. 그래서 그 월간 정산이 받은 sequence(`turnLoop.ts:157`, `persistMonthly`의 `sequence` 인자)를 적고 한 정산이 같은 장수에게 여러 줄을 남기면 `ordinal`을 0, 1, 2로 붙인다.

  U2 취소 로그도 이 방식으로 그 step의 sequence와 `ordinal`을 적는다(위 수락 전 자동 취소 절).

- U2 취소 검사 `closeInvalidOffers`는 `runReplayAction`과 `applyRecordedInput`이 `features`가 있을 때 `syncOffices` 바로 뒤에서 부른다. 엔진과 같은 자리라 취소 시점과 해시가 같다.

#### 직책 칸 실행 (origin 4)

- `runGeneralTurn`(`packages/rules/src/commands/turn.ts:26-55`)의 군주 30칸 갈래는 `features`가 없을 때만 탄다. `features`가 있으면 행위자의 officerLevel이 국가 예턴 권한 직책(5~12)일 때 `officeTurns[nationId][officerLevel][0]`을 실행하고 12칸으로 당긴다. 칸이 `nation_rest`이고 NPC 국가 군주면 지금처럼 `chooseNationTurn`(`:33-40`)을 쓴다. 난수 이름(`nation-turn`, `npc-nation`)은 그대로다.
- 엔진은 그 장수 턴의 트랜잭션에서 `NationOffice` 행을 `FOR UPDATE`로 잠근 뒤 칸을 읽는다(장수 행 잠금 `turnLoop.ts:161`과 같다). 저장 뒤 `turnRevision = 읽은 값` 조건으로 1 올리고 바뀐 행이 1이 아니면 되돌린다(`:207-211`과 같다).
- 사람 직책자의 `nation_rest` 칸도 실행으로 센다. 지금 국가 칸이 있는 월드에서 군주가 `nation_rest`를 실행할 때와 같이 국가 역사 줄을 남긴다(`turnLoop.ts:181-195`). 이 줄이 직책 수만큼 늘어나는 문제는 미결 B4다.

#### 월간 저장 순서

- `persistMonthly`(`monthly.ts:23-78`)는 지금 도시·국가·장수·외교만 쓴다(`:35-53`). origin 4에서는 `runMonthly`가 낸 `closedOffers`, `assignmentOffers`, 직책 칸, `NationOffice`, 월간 인사 로그와 국가 역사를 같은 트랜잭션에서 먼저 쓴다.
- 그다음 `loadReplayState`(`:54`)로 다시 읽어 `stateHash`를 만든다. `loadReplayState`가 새 표를 읽어야 해시에 들어간다. 연감(`result.yearbook`)은 지금처럼 같은 행에 저장한다.

원자성과 경합:

- 즉시 행동 하나, 턴 하나, 월간 정산 하나는 각각 펜싱 트랜잭션 하나로 확정한다(`turnLoop.ts:96-266`의 `step`, 커밋 직전 `beforeCommit`과 `assertLease`). `nationTurns.set`은 엔진을 거치지 않고 개인 칸 저장(`apps/server/src/routers/turns.ts:31-80`)처럼 서버 트랜잭션 하나로 확정한다. 그 안에서 InputEvent 상태·sequence·result, 제안 생성·교체·응답·기한 수락·U2 취소, 장수 위치·공헌·직책, 직책 칸 비우기와 revision·tenure, 장수 로그, 국가 역사를 함께 쓴다. 하나라도 실패하면 모두 되돌리고 접수는 PENDING으로 남는다.
- 응답과 기한 수락, 새 발령은 모두 World 행 잠금 뒤에 줄을 선다. 제안 상태 바꾸기는 `status = 'PENDING'` 조건으로 하고 바뀐 행이 1이 아니면 트랜잭션을 되돌린다. 먼저 끝난 쪽이 이기고 나중 응답은 `OFFER_CLOSED`로 거절한다.

로그 읽기와 국가 역사의 공존:

- 지금 장수 기록은 tick 내림차순 31행을 읽고(`apps/server/src/routers/records.ts:9-15`) 30행 뒤 마지막 tick보다 작은 행만 다음 장에서 받는다(`apps/server/src/queries.ts:91-96`). 한 tick에 여러 행이 생기면 장 경계에서 행이 빠진다.
- 이 작업에서 장수 기록(`records.general`)과 메인 최근 기록(`home.ts:24-28`)의 정렬을 `(tick 내림차순, id 내림차순)`으로 바꾼다. `records.general`의 커서는 `<tick>:<id>` 문자열이고 다음 장은 tick이 더 작거나, tick이 같고 id가 더 작은 행이다.
  `page`·`beforeCursor`와 커서 검사(`queries.ts:8-16`)는 장수 기록용을 따로 둔다. 국가·세계 기록은 tick당 한 행이라 지금 커서를 그대로 쓴다.
  화면은 커서를 그대로 돌려보내므로(`apps/web/src/main/Records.tsx:37-38`) 바뀌지 않는다. `AppRouter`의 커서 타입도 string 그대로다.
- 국가 역사의 인사 사건은 `appendNationHistory`(`apps/engine/src/commandPersistence.ts:97-113`)로만 덧붙인다. 월간 수치는 `persistMonthly`의 병합 upsert(`monthly.ts:65-75`)가 기존 사건을 보존한다. 같은 국가·tick에서 어느 쪽이 먼저 와도 사건과 월간 수치가 함께 남는다. 이 작업은 국가 역사에 createMany나 덮어쓰기를 새로 쓰지 않는다.

### 국가 예턴 (R51-3)

개인 30칸은 그대로 다시 쓴다. `turns.get/set/edit/precheck`(`routers/turns.ts:12-30,81-122`), `game/slots.ts`, 장수 명령만 거르는 `routers/commands.ts:5-12`는 바꾸지 않는다.

국가 직책 칸은 따로 만든다.

- 저장: 새 표 `NationOfficeTurn(worldId, nationId, officerLevel, slot)`, slot 0~11. revision과 tenure는 `NationOffice`. 빈 칸은 `nation_rest`. 행이 없는 칸도 `nation_rest`로 읽는다.
- 내 직책: 서버가 세션 장수의 지금 국가와 officerLevel로 정한다. 쓰기 권한의 근거는 이것뿐이다. 국가 예턴 권한이 없는 직책이면 `국가 예턴 권한이 없습니다`.
- 본 직책 확인: 읽기 응답의 각 탭은 `office: { nationId, officerLevel, tenure }`를 싣는다. 쓰기 요청은 화면이 본 그 값을 그대로 돌려보낸다. 이 값은 권한 근거가 아니며 화면이 어느 칸을 보고 고쳤는지 확인하는 데만 쓴다.
  서버는 세션 장수의 지금 국가·직책·그 직책의 tenure와 비교한다. 하나라도 다르면 저장하지 않고 PRECONDITION_FAILED `직책이 바뀌었습니다. 국가 예턴을 다시 불러오세요`로 거부한다. 다른 칸으로 바꿔 읽어 저장하지 않는다.
  같은 사람이 해임 뒤 다시 임명돼도 tenure가 올랐으므로 예전 초안은 거부된다. revision 숫자가 우연히 같은 다른 직책 칸에도 저장되지 않는다.
- `nationTurns.set({ worldId, office, revision, slots })`: slots는 정확히 12칸. `nationTurns.edit({ worldId, office, revision, op })`: `turns.edit`의 put·shift·repeat와 같되 범위는 0~11, shift는 −11~11, repeat는 `to` 10 이하·`times` 11 이하.
- 칸 입력 형식: 칸 하나는 개인 칸 입력과 같은 `{ commandKey, args }` 또는 null이다(`apps/server/src/game/slots.ts:5-6`의 strict 객체). 읽기 칸의 표시용 `name`을 보내면 BAD_REQUEST다. 화면은 개인 편집기처럼 `toTurn`·`toSaveSlots`(`apps/web/src/turns/draft.ts:23,56`)로 `name`을 빼고 보낸다.
- 성공은 `{ ok: true, revision, slots }`이다. 직책은 같고 revision이 다르면 `{ ok: false, reason: 'STALE', revision, slots }`이다. STALE의 두 값은 같은 트랜잭션에서 읽은 그 직책 칸의 최신 스냅샷이다(`turns.ts:47-48`과 같다).
- 저장할 때 `NationOffice` 행을 `FOR UPDATE`로 잠그고 InputEvent `nationTurns.set`을 APPLIED와 sequence로 남긴다(`turns.ts:65-77`과 같다).
- 칸 해석: 국가 명령이고 내 직책이 실행할 수 있는 명령만 받는다(`slots.ts:7-14`의 장수 명령 해석과 따로 둔다). 그 밖은 `명령과 인자를 확인하세요`.
- `nationCommands.list({ worldId })`: 내 직책이 쓸 수 있는 국가 명령의 키·이름·인자 스키마. `nationCommands.precheck({ worldId, commandKey, args })`: 지금 상태로 `Allowed`.
- 실행: origin 4 월드에서 국가 예턴 권한이 있는 장수의 턴은 자기 직책 칸 0번을 먼저 실행하고 당긴다. 엔진은 칸을 소비할 때 `NationOffice`를 잠그고 revision을 올린다.
- 경합: 엔진 소비, 임명·해임의 칸 비우기, 편집이 같은 `NationOffice` 행에서 줄을 선다. 엔진 소비는 편집 때문에 실패하지 않는다.
  편집이 먼저 확정되면 엔진은 편집된 0번 칸을 실행하고 revision을 1 올린다. 엔진이 먼저 확정되면 그 뒤 도착한 편집이 STALE을 받고 당겨진 칸을 스냅샷으로 받는다. 해임된 사람의 편집은 권한 검사에서 거부된다.

전환 경계 (지금 국가 칸 13~30번째):

- 지금 `NationTurn`은 국가당 30칸이고 군주만 쓴다(`commands_war` migration `:3-12`, `rules/commands/turn.ts:26-55`, 30칸 당기기 `:51-54`). M1에는 국가 예턴 편집 API가 없다.
- migration은 `NationTurn` 표, 행, slot 검사(0~29)를 건드리지 않는다. 12칸 범위는 새 표의 CHECK와 rules·서버 입력 검사가 지킨다.
- 기존 월드는 origin 1 그대로 두고 origin 4로 올리지 않는다. origin 1 월드는 지금처럼 군주 30칸으로 돈다. 그 월드의 `personnel.*`, `offers.*`, `nationTurns.*`, `nationCommands.*`는 `인사 기능 이전에 만든 월드입니다`로 거부한다(PRECONDITION_FAILED). 그래서 13~30번째 칸을 조용히 지우거나 잘라 읽는 경로가 없다.
- origin 4 월드에는 `NationTurn` 행이 생기지 않는다. 엔진 시작 대조에서 origin 4 월드에 `NationTurn` 행이 있으면 쓰기 전에 멈춘다.
- origin 3 월드(T4-03)도 인사 기능이 없다. 같은 절차를 거부하되 위 문구가 그 월드에는 맞지 않으므로 문구는 미결 B3에서 함께 정한다.

### API 계약

이 절의 타입이 계약이다. 예전 짧은 요약(`officers` 배열, `offers.mine`의 `fromNation`·`expiresAt`·`status`)은 지웠다. 구현 뒤에는 `AppRouter` 타입이 이 모양을 그대로 낸다.

```ts
type Allowed = { ok: true } | { ok: false; reason: string }; // reason은 화면 문구 그대로 (예: 군주만 임명할 수 있습니다)
type CityRef = { cityKey: number; name: string };
type DisplaySlot = { commandKey: string; args: unknown; name: string }; // T1-11 turns.get의 칸과 같다

// personnel.officers({ worldId }) → PersonnelBoard
type PersonnelBoard = {
  appoint: Allowed; // 임명·해임을 할 수 있는가 (군주만)
  levels: { officerLevel: number; title: string; holderId: number | null }[]; // 줄 수 있는 직책 11, 10~5. 군주(12)는 없다
  members: PersonnelMember[]; // 소속 장수 전부. officerLevel 높은 순, 같으면 generalId 순
};
type PersonnelMember = {
  generalId: number;
  name: string;
  officerLevel: number;
  title: string; // permissions.ts 표의 직책 이름
  isHuman: boolean;
  city: CityRef;
  dedication: number;
};

// nationTurns.get({ worldId }) → { tabs: NationTurnTab[] }   직책 높은 순, 군주 칸이 처음
type NationTurnTab = {
  office: { nationId: number; officerLevel: number; tenure: number }; // 쓰기 요청에 그대로 돌려보낸다. 권한 근거가 아니다
  officerLevel: number;
  title: string;
  holder: { generalId: number; name: string } | null; // 빈 자리면 null
  edit: Allowed; // 내 직책 칸만 ok
  revision: number; // nationTurns.set/edit의 충돌 검사용. 같은 office 안에서만 뜻이 있다
  slots: DisplaySlot[]; // 12칸. 쓰기 때는 name을 빼고 { commandKey, args }만 보낸다
};
// nationTurns.set({ worldId, office, revision, slots: ({ commandKey, args? } | null)[12] })
// nationTurns.edit({ worldId, office, revision, op })
//   → { ok: true; revision; slots: DisplaySlot[] } | { ok: false; reason: 'STALE'; revision; slots: DisplaySlot[] }
//   office가 지금 세션 장수의 국가·직책·tenure와 다르면 PRECONDITION_FAILED (국가 예턴 절)
// nationCommands.list({ worldId }) → { key: string; name: string; argsSchema: unknown }[]
// nationCommands.precheck({ worldId, commandKey, args }) → Allowed

// offers.mine({ worldId }) → AssignmentOfferView[]   PENDING만. 같은 장수의 PENDING은 하나뿐이라 길이는 0이나 1
type AssignmentOfferView = {
  id: string;
  issuer: { generalId: number; name: string }; // 발령 명령을 실행한 군주·참모·수뇌
  targetCity: CityRef;
  expires: { year: number; month: number; monthsLeft: number }; // 기한의 게임 연월과 남은 개월 수
  rejectCost: { dedicationPercent: number; dedication: number }; // 거절하면 줄어드는 공헌 (balance.ts 비율과 실제 값)
  respond: Allowed; // 응답 대기 중이면 { ok: false, reason: '응답을 처리하는 중입니다' }
};
// 변경 요청과 재조회의 응답 타입은 위 즉시 행동 절의 RequestState와 PersonnelRecord다.
// 대기 중이거나 끝난 접수의 복구는 personnel.recent 하나로 한다. 예전 pendingRequest·pendingResponse는 지웠다.
```

- 공개 범위: `personnel.officers`는 같은 국가 장수만 부른다. 재야와 무인증은 거부한다. 공헌은 순위(T2-22)에서도 공개하는 값이다. `nationTurns.get`은 국가 예턴 권한이 있는 직책(군주·참모·수뇌)만 부르고 일반 장수는 이유와 함께 거부한다.
  `offers.mine`과 `offers.respond`는 세션 장수에게 온 제안만 다룬다. 남의 제안 ID는 NOT_FOUND, 이미 처리된 제안은 CONFLICT다. 엔진의 `OFFER_CLOSED`도 CONFLICT로 낸다.
  U2로 취소된 제안도 이미 처리된 제안이다. `offers.mine`에서 빠지고 그 뒤 응답은 CONFLICT다. 위 타입은 바뀌지 않는다(`RespondResult.offerStatus`에 `CANCELLED`를 더하지 않는다. 응답이 취소를 만들지 않기 때문이다).
- 화면 요소와 필드의 대조는 [T2-06](./T2-06.md)의 v1 근거 표 오른쪽 칸에 있다. 권한 판단은 `appoint`·`edit`·`respond`만 쓰고 화면이 `officerLevel`로 권한을 추측하지 않는다.
