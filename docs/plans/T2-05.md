## 계획 (Claude)

### 목표

- 군주가 수뇌를 임명하고 포상·몰수·발령을 한다. 권한 없는 장수의 같은 요청은 거부된다 (AC-M2-05).
- 발령받은 사람 장수가 턴을 쓰지 않고 수락·거절한다. 기한 안에 답이 없으면 수락이다. NPC 군주는 정해진 주기마다 사람 장수에게
  발령·포상하고 이유를 로그에 남긴다 (AC-M2-16).

### 범위 (모두 Codex)

- `packages/rules/src/personnel/`: 직책 표, 국가 명령별 권한 표, 발령 응답 규칙, NPC 군주 인사 판단
- `packages/rules/src/replay.ts`: 새 입력 종류 4개의 순수 재생과 재생 형식 2
- `packages/rules/src/commands/support.ts`: 국가 명령의 군주 검사(`:19-39`)를 권한 표 검사로 바꾼다
- `packages/db`: 새 migration (아래 저장 절). 기존 migration은 고치지 않는다
- `apps/engine`: 즉시 행동 처리(`inputs.ts` 옆), 직책 칸 실행, 월간 정산의 기한 처리와 NPC 군주 인사, 상태 저장
- `apps/server/src/routers/personnel.ts`, `offers.ts`, `nationTurns.ts`, `nationCommands.ts`

- 관직 주재 효과(D17, M3 T3-09), 인사 화면(T2-06).

### 발령 응답 결정 (D11)

```text
발령 실행 ─┬─ 대상이 NPC → 즉시 이동 (M1과 같음)
           └─ 대상이 사람 → AssignmentOffer(PENDING, expiresTick = 지금 + 2개월)
                 ├─ 수락 (즉시 행동, 턴 소비 없음) → 대상 도시로 이동
                 ├─ 거절 (즉시 행동) → 공헌 −10% (balance.ts), 로그
                 └─ 기한 지남 → 월간 정산에서 수락 처리
```

- 같은 장수에게 PENDING 제안은 하나뿐이다. DB도 부분 유일 색인으로 막는다. 새 발령이 오면 이전 것은 `SUPERSEDED`이고 벌점이 없다.
- 제안 상태: `PENDING`, `ACCEPTED`(응답 또는 기한 지남, `resolvedBy`가 `RESPONSE`·`EXPIRY`), `REJECTED`, `SUPERSEDED`.
- 수락·기한 수락을 처리할 때 목표 도시가 아직 자기 국가 도시인지, 대상이 아직 그 국가 소속인지 다시 검사한다. 검사에 실패했을 때의 제안 상태와 벌점은 사용자 결정 U2다.
- **NPC 군주 인사** (월간 정산 뒤, 3개월마다): 소속 사람 장수 중 6개월 넘게 같은 후방 도시에 있는 장수를 전선 도시로 발령,
  국고가 기준 이상이면 공헌 상위 사람 장수에게 포상. 각 결정의 이유를 국가 역사에 한 줄로 남긴다.

### 사용자 결정 (구현 착수 전에 필요)

- U2 발령 취소와 벌점: 수락 처리 때 목표 도시를 잃었거나 대상이 국가를 떠났을 때, 발령한 사람이 그 사이 직책을 잃었을 때 제안을 어떤 상태로 끝내는지와 벌점이 있는지. 기존 계약(AC-M2-16, D11)에 없는 정책이라 계획에서 정하지 않는다.
  정해질 때까지 Codex는 이 분기를 만들지 않고 계획 문서에 적힌 결정만 구현한다.

### 즉시 행동의 접수와 완료 (R51-1)

임명·해임·발령 응답은 즉시 행동이다. 서버는 접수(InputEvent PENDING)만 하고 엔진이 처리해 APPLIED 또는 REJECTED로 끝낸다 (AGENTS.md §6). 기존 `general.create`(`apps/server/src/routers/general.ts:56-115`)와 같은 틀을 쓴다.

| InputEvent `kind` | 요청 | 결과(`result`) |
| ----------------- | ---- | -------------- |
| `personnel.appoint` | `{ generalId, officerLevel }` | `{ generalId, officerLevel, title }` |
| `personnel.dismiss` | `{ generalId }` | `{ generalId, officerLevel: 1, title }` |
| `offer.respond` | `{ offerId, accept }` | `{ offerStatus: 'ACCEPTED' \| 'REJECTED', city: CityRef, dedicationLost }` |

- 행위자: 서버가 세션 사용자에게서 장수를 정한다. 요청에 행위자 장수 ID를 받지 않는다.
- 접수 식별: 요청마다 화면이 만든 `requestId`(UUID)를 받는다. `idempotencyKey`는 `<kind>:<requestId>`이고 기존 `@@unique([worldId, userId, idempotencyKey])`가 중복을 막는다.
- 재전송: 같은 `requestId`에 같은 내용이면 새 행을 만들지 않고 그 접수의 지금 상태를 돌려준다. 같은 `requestId`에 다른 내용이면 CONFLICT `같은 요청 번호로 다른 내용을 보냈습니다`.
- 중복 클릭: 한 행위자에게 PENDING 인사 접수는 하나다. 같은 제안에 PENDING 응답도 하나다. 다른 `requestId`로 또 보내면 CONFLICT `요청을 처리하는 중입니다`.
- 사전 검사: 서버는 접수 전에 권한 표와 지금 DB 상태로 뻔한 거절(권한 없음, 남의 제안, 끝난 제안)을 InputEvent 없이 돌려준다. 통과해도 결과를 약속하지 않는다.
- 엔진 처리: 리스와 World를 잠근 같은 펜싱 트랜잭션에서 사용자 ACTIVE(`inputs.ts:32-34`처럼 `FOR SHARE`), 행위자 장수, 그때의 직책과 소속, 대상, 제안 PENDING을 다시 검사한다. RUNNING이 아닌 월드의 접수는 `WORLD_CLOSED`로 거절한다(`turnLoop.ts:86` 분기).
- 응답: 접수 뒤 5초까지 결과를 기다린다(`general.ts:69-95`와 같다). APPLIED이면 세션과 계정 상태를 다시 확인한 뒤(`general.ts:73-82`) 결과를 준다. REJECTED이면 그 코드의 오류를 낸다. 5초가 지나면 pending을 준다.
- 최종 결과 재조회: `personnel.request({ worldId, requestId })`. 세션 사용자의 접수만 읽고 남의 `requestId`는 NOT_FOUND다. REJECTED도 값으로 돌려준다.
- 대기 중 세션 만료·제재: 기다리는 동안 세션이 지워지거나 계정이 제재되면 결과를 내지 않고 UNAUTHORIZED다. 엔진은 제재된 사용자의 PENDING 접수를 `ACTOR_INACTIVE`로 거절한다.
- InputEvent 상태와 제안 상태는 다르다. 거절 응답이 처리되면 InputEvent는 APPLIED이고 제안은 REJECTED다. 화면은 제안이 목록에서 사라진 것으로 성공을 추측하지 않고 `requestId`의 결과를 본다.
- 화면 대기 계약(T2-06): 버튼은 접수부터 결과까지 막고 `처리 중`을 보인다. 응답을 못 받으면 같은 `requestId`로 다시 보낸다. pending이면 `personnel.request`를 1초마다 묻는다. 다시 접속하면 `offers.mine`의 `pendingResponse`와 `personnel.officers`의 `pendingRequest`로 대기 상태를 되살린다.

```ts
type RequestState<R> =
  | { status: 'pending'; requestId: string }
  | { status: 'applied'; requestId: string; result: R }
  | { status: 'rejected'; requestId: string; code: string; message: string }; // personnel.request에서만. 변경 요청은 오류로 낸다
// personnel.appoint({ worldId, requestId, generalId, officerLevel }) → RequestState<AppointResult> (rejected 제외)
// personnel.dismiss({ worldId, requestId, generalId })                → RequestState<AppointResult> (rejected 제외)
// offers.respond({ worldId, requestId, offerId, accept })            → RequestState<RespondResult> (rejected 제외)
// personnel.request({ worldId, requestId })                           → RequestState<AppointResult | RespondResult>
type AppointResult = { generalId: number; officerLevel: number; title: string };
type RespondResult = { offerStatus: 'ACCEPTED' | 'REJECTED'; city: CityRef; dedicationLost: number };
//   city는 처리 뒤 내 장수가 있는 도시. dedicationLost는 거절이면 줄어든 공헌, 수락이면 0
```

### 저장·재생·원자성 (R51-2)

새 migration 하나에 넣는 것:

- `AssignmentOffer`: `id`(`<createdTick>-<issuerGeneralId>-<targetGeneralId>`, 재생에서 같은 값이 나온다), `worldId`, `nationId`, `issuerGeneralId`, `targetGeneralId`, `cityKey`, `status`, `resolvedBy`, `createdTick`, `expiresTick`, `resolvedTick`.
  `(worldId, targetGeneralId) WHERE status = 'PENDING'` 부분 유일 색인.
- `NationTurn.officerLevel Int NOT NULL DEFAULT 12`, 기본키를 `(worldId, nationId, officerLevel, slot)`으로. 직책 칸의 revision을 둘 `NationOffice(worldId, nationId, officerLevel, turnRevision)`.
- `GeneralLog.sequence Int?`: 즉시 행동 로그는 그 InputEvent의 sequence를 적는다. 유일 조건을 둘로 나눈다. 턴 로그는 `(worldId, generalId, tick) WHERE sequence IS NULL`로 지금처럼 장수·tick당 한 행이다(`schema.prisma:181-192`).
  즉시 행동 로그는 `(worldId, generalId, sequence) WHERE sequence IS NOT NULL`이다. 같은 tick에 턴 로그와 즉시 행동 로그가 함께 남는다. 지금 유일 조건에 기대는 쓰기(upsert 등)는 구현 때 찾아 맞춘다.

재생과 상태:

- `WorldState`에 선택 필드 `offers`(PENDING 제안만)와 `officeTurns`(국가 → 직책 → 12칸)를 더한다. 비어 있으면 키를 넣지 않는다(`model/world.ts:22`의 `nationTurns`와 같은 방식). 형식 1 월드의 상태 해시는 그대로다.
- `applyRecordedInput`(`replay.ts:67-105`)에 `personnel.appoint`, `personnel.dismiss`, `offer.respond`, `nationTurns.set`을 더한다. 각 종류는 요청과 그때 상태로 효과를 다시 계산하고 기록된 `result`와 다르면 예외를 낸다(`general.create` 분기처럼). REJECTED는 지금처럼 건너뛴다.
- 기한 수락과 NPC 군주 인사는 `runMonthly` 안의 순수 규칙이라 재생이 그대로 따라간다. 월간 `stateHash`(`monthly.ts:62`)와 연감 해시에 `offers`·`officeTurns`가 들어간다.
- 재생 형식: 지금 `replayOrigin.version`은 1이다(`world/persistence.ts:34`, `replay.ts:17,83-84`). 이 작업 뒤 새로 만드는 월드는 2다. 형식 1 월드는 지금 재생 경로(국가 30칸 군주 전용)를 그대로 쓴다.

원자성과 경합:

- 즉시 행동 하나, 턴 하나, 월간 정산 하나는 각각 펜싱 트랜잭션 하나로 확정한다. 그 안에서 InputEvent 상태·sequence·result, 제안 생성·교체·응답·기한 수락, 장수 위치·공헌·직책, 직책 칸 비우기와 revision, 장수 로그, 국가 역사를 함께 쓴다. 하나라도 실패하면 모두 되돌리고 접수는 PENDING으로 남는다.
- 응답과 기한 수락, 새 발령은 모두 World 행 잠금 뒤에 줄을 선다. 제안 상태 바꾸기는 `status = 'PENDING'` 조건으로 하고 바뀐 행이 1이 아니면 트랜잭션을 되돌린다. 먼저 끝난 쪽이 이기고 나중 응답은 `OFFER_CLOSED`로 거절한다.

### 국가 예턴 (R51-3)

개인 30칸은 그대로 다시 쓴다. `turns.get/set/edit/precheck`(`routers/turns.ts:12-29,92-103`), `game/slots.ts`, 장수 명령만 거르는 `routers/commands.ts:5-11`은 바꾸지 않는다.

국가 직책 칸은 따로 만든다.

- 저장: `(worldId, nationId, officerLevel, slot)`, slot 0~11. revision은 `NationOffice.turnRevision`. 빈 칸은 `nation_rest`.
- 내 직책: 서버가 세션 장수의 지금 officerLevel로 정한다. 요청에 직책을 받지 않는다. 국가 예턴 권한이 없는 직책이면 `국가 예턴 권한이 없습니다`.
- `nationTurns.set({ worldId, revision, slots })`: slots는 정확히 12칸. `nationTurns.edit({ worldId, revision, op })`: `turns.edit`의 put·shift·repeat와 같되 범위는 0~11, shift는 −11~11, repeat는 `to` 10 이하·`times` 11 이하.
- 성공은 `{ ok: true, revision, slots }`, revision이 다르면 `{ ok: false, reason: 'STALE', revision, slots }`. STALE의 두 값은 같은 트랜잭션에서 읽은 최신 스냅샷이다(`turns.ts:47-48`과 같다).
- 저장할 때 `NationOffice` 행을 `FOR UPDATE`로 잠그고 InputEvent `nationTurns.set`을 APPLIED와 sequence로 남긴다(`turns.ts:65-77`과 같다).
- 칸 해석: 국가 명령이고 내 직책이 실행할 수 있는 명령만 받는다(`slots.ts:7-12`의 장수 명령 해석과 따로 둔다). 그 밖은 `명령과 인자를 확인하세요`.
- `nationCommands.list({ worldId })`: 내 직책이 쓸 수 있는 국가 명령의 키·이름·인자 스키마. `nationCommands.precheck({ worldId, commandKey, args })`: 지금 상태로 `Allowed`.
- 실행: 형식 2 월드에서 국가 예턴 권한이 있는 장수의 턴은 자기 직책 칸 0번을 먼저 실행하고 당긴다. 엔진은 칸을 소비할 때 `NationOffice`를 잠그고 revision을 올린다.
- 경합: 엔진 소비, 임명·해임의 칸 비우기, 편집이 같은 `NationOffice` 행에서 줄을 선다. 늦은 편집은 STALE이다. 해임된 사람의 편집은 권한 검사에서 거부된다.

전환 경계 (지금 국가 칸 13~30번째):

- 지금 `NationTurn`은 국가당 30칸이고 군주만 쓴다(`commands_war` migration:3-11, `rules/commands/turn.ts:19-35`). M1에는 국가 예턴 편집 API가 없다.
- migration은 기존 행을 지우지 않는다. 기존 행은 officerLevel 12가 되고 DB의 slot 검사(0~29)도 그대로 둔다. 12칸 범위는 rules·서버 입력·엔진 저장 검사가 지킨다.
- 형식 1 월드는 지금처럼 군주 30칸으로 돈다. 그 월드의 `personnel.*`, `offers.*`, `nationTurns.*`는 `인사 기능 이전에 만든 월드입니다`로 거부한다. 그래서 13~30번째 칸을 조용히 지우거나 잘라 읽는 경로가 없다.

### API 계약

이 절의 타입이 계약이다. 예전 짧은 요약(`officers` 배열, `offers.mine`의 `fromNation`·`expiresAt`·`status`)은 지웠다. 구현 뒤에는 `AppRouter` 타입이 이 모양을 그대로 낸다.

```ts
type Allowed = { ok: true } | { ok: false; reason: string }; // reason은 화면 문구 그대로 (예: 군주만 임명할 수 있습니다)
type CityRef = { cityKey: number; name: string };
type DisplaySlot = { commandKey: string; args: unknown; name: string }; // T1-11 turns.get의 칸과 같다

// personnel.officers({ worldId }) → PersonnelBoard
type PersonnelBoard = {
  appoint: Allowed; // 임명·해임을 할 수 있는가 (군주만)
  levels: { officerLevel: number; title: string; holderId: number | null }[]; // 줄 수 있는 직책 11, 10~5. 군주(12)는 없다
  members: PersonnelMember[]; // 소속 장수 전부. officerLevel 높은 순, 같으면 generalId 순
  pendingRequest: { requestId: string; kind: 'personnel.appoint' | 'personnel.dismiss'; generalId: number } | null; // 내 PENDING 인사 접수
};
type PersonnelMember = {
  generalId: number;
  name: string;
  officerLevel: number;
  title: string; // permissions.ts 표의 직책 이름
  isHuman: boolean;
  city: CityRef;
  dedication: number;
};

// nationTurns.get({ worldId }) → { tabs: NationTurnTab[] }   직책 높은 순, 군주 칸이 처음
type NationTurnTab = {
  officerLevel: number;
  title: string;
  holder: { generalId: number; name: string } | null; // 빈 자리면 null
  edit: Allowed; // 내 직책 칸만 ok
  revision: number; // nationTurns.set/edit의 충돌 검사용
  slots: DisplaySlot[]; // 12칸
};
// nationCommands.list({ worldId }) → { key: string; name: string; argsSchema: unknown }[]
// nationCommands.precheck({ worldId, commandKey, args }) → Allowed

// offers.mine({ worldId }) → AssignmentOfferView[]   PENDING만. 같은 장수의 PENDING은 하나뿐이라 길이는 0이나 1
type AssignmentOfferView = {
  id: string;
  issuer: { generalId: number; name: string }; // 발령 명령을 실행한 군주·참모·수뇌
  targetCity: CityRef;
  expires: { year: number; month: number; monthsLeft: number }; // 기한의 게임 연월과 남은 개월 수
  rejectCost: { dedicationPercent: number; dedication: number }; // 거절하면 줄어드는 공헌 (balance.ts 비율과 실제 값)
  respond: Allowed; // 응답 대기 중이면 { ok: false, reason: '응답을 처리하는 중입니다' }
  pendingResponse: { requestId: string; accept: boolean } | null;
};
// 변경 요청과 재조회의 응답 타입은 위 즉시 행동 절의 RequestState다.
```

- 공개 범위: `personnel.officers`는 같은 국가 장수만 부른다. 재야와 무인증은 거부한다. 공헌은 순위(T2-22)에서도 공개하는 값이다. `nationTurns.get`은 국가 예턴 권한이 있는 직책(군주·참모·수뇌)만 부르고 일반 장수는 이유와 함께 거부한다.
  `offers.mine`과 `offers.respond`는 세션 장수에게 온 제안만 다룬다. 남의 제안 ID는 NOT_FOUND, 이미 처리된 제안은 CONFLICT다. 엔진의 `OFFER_CLOSED`도 CONFLICT로 낸다.
- 화면 요소와 필드의 대조는 [T2-06](./T2-06.md)의 v1 근거 표 오른쪽 칸에 있다. 권한 판단은 `appoint`·`edit`·`respond`만 쓰고 화면이 `officerLevel`로 권한을 추측하지 않는다.

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 권한 | API: 직책 5종 × 행동 5종 표 전부 (허용·거부). 단위: 국가 명령별 권한 표 전부 |
| 공개 범위 | API: 다른 국가의 `personnel.officers`, 일반 장수의 `nationTurns.get`, 남의 제안 `offers.respond`, 남의 `requestId` 모두 거부. 응답 키는 위 타입과 같다 |
| 보안 | API: 무인증, 제재 계정, 잘못된 입력(직책 범위 밖, 12칸이 아닌 slots, 군주 12로 임명)을 각 변경 API에서 거부 |
| 접수와 완료 | 통합: 엔진 정지 → pending, 엔진 재개 → `personnel.request`가 applied. 엔진 지연 5초 초과 → pending 뒤 applied |
| 재전송 | 통합: 같은 `requestId` 두 번 → InputEvent 1행, 같은 결과. 같은 `requestId`에 다른 내용 → CONFLICT. 다른 `requestId`로 연타 → CONFLICT, 효과 1번 |
| 대기 중 만료·제재 | 통합: pending 중 세션 삭제 → UNAUTHORIZED, 결과 없음. pending 중 계정 제재 → 엔진이 `ACTOR_INACTIVE`로 거절 |
| 재접속 | API: pending 중 새로 고침 → `offers.mine.pendingResponse`, `personnel.officers.pendingRequest`가 그 `requestId` |
| 임명 | 통합: 군주가 수뇌 임명 → 수뇌가 자기 칸 편집 가능, 그 직책 칸이 비워짐. 해임 뒤 편집 거부. 군주 아닌 장수의 임명 거부 |
| 국가 칸 | 통합: set·edit 성공, STALE의 revision·slots가 최신 동일 스냅샷, 12칸 경계(0, 11, 12 거부), 타직책·타국·타월드 칸 쓰기 거부, 참모·수뇌 실행 허용표 |
| 국가 칸 경합 | 통합: 편집과 엔진 소비가 겹침 → 하나만 성공, 늦은 쪽 STALE. 편집 중 해임 → 거부. 임명과 편집이 겹침 → 칸이 비워진 뒤 편집은 STALE |
| 개인 칸 회귀 | 기존 `turns` 통합 시험이 그대로 통과. 개인 30칸에 국가 명령 거부 |
| 발령 응답 | 시나리오: 수락 → 이동 / 거절 → 공헌 감소, InputEvent APPLIED와 제안 REJECTED / 2개월 무응답 → 기한 수락 / 새 발령 → 이전 SUPERSEDED |
| 제안 경합 | 통합: 응답과 기한 수락이 같은 tick → 하나만 적용, 나중 응답 `OFFER_CLOSED`. 응답 대기 중 새 발령 → 응답 `OFFER_CLOSED`. PENDING 둘 만들기 → DB 색인이 거부 |
| 원자성 | 통합: `beforeCommit`에서 실패시킴 → 제안·장수·로그·InputEvent 모두 그대로, 재시작 뒤 한 번만 적용 |
| 로그 공존 | 통합: 같은 tick에 턴 로그와 즉시 행동 로그 2개 → 3행 모두 남음 |
| 재생 | 통합: 임명·발령·응답·기한 수락·NPC 인사가 섞인 12개월 → 재생 해시가 기록과 같고 이동·공헌 변화 횟수가 적용된 기록 수와 같다(중복 0건) |
| 형식 1 | 통합: 기존 M1 재생 시험의 해시가 그대로. 형식 1 월드의 인사 API 거부, 국가 30칸 행 수 그대로 |
| NPC 군주 | 시나리오: 후방 6개월 사람 장수 → 3개월 주기에 발령 + 역사 로그 이유 |
