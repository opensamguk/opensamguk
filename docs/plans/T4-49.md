## 0. 이 문서의 위치

명세 C15는 즉시 행동의 수명을 T4-49가 확정하라고 적었고 관문 G-02는 T2-05의 `personnel.appoint` 처리 경로와 하나로 맞추라고 했다. 그 뒤 D-029가 단일 처리기를 T2-26에 두기로 정했다. T2-26 원고는 모든 대기 입력을 id 순으로 하나씩 꺼내는 `processInputs`, 입력 종류 등록 목록 `InputKindDefinition`, 처리 tick 기록, 달 경계를 넘긴 엔진의 처리 순서(C2), 켜지 않은 기능의 `FEATURE_DISABLED` 거절을 정했다.

그래서 이 계획은 처리기를 새로 만들지 않는다. T2-26 처리기 위에 확장 즉시 행동(부대 T4-20, 경매 T4-28, 토너먼트 T4-31)이 함께 쓸 계약 한 층을 얹는다. 그 층은 kind별 payload·result 스키마, 멱등 접수와 대기, 재접속 조회, 처리 시점 재검사, 일시정지 중 보류, sequence에 묶인 RNG, 재생 검사 도우미다. T2-05가 손으로 쓴 접수 6단계를 공통 함수로 뽑은 모양이다.

G-02는 D-029와 T2-26 병합으로 풀린다. T2-26이 병합되기 전에는 이 계획의 엔진·서버 몫을 시작하지 않는다(단계 표).

### 기술 계약

#### I1 kind 계약 (rules)

```ts
// packages/rules/src/inputs/contract.ts. DB·시각·네트워크를 쓰지 않는다.
export interface InputContract<P = unknown, R = unknown> {
  namespace: string; // 멱등 키 앞머리. /^[a-z][a-z0-9-]{0,31}$/
  payload: z.ZodType<P>; // 요청 본문. 행위자 ID를 넣지 않는다
  result: z.ZodType<R>; // APPLIED 결과
  rejectCodes: readonly string[]; // 이 kind가 REJECTED로 낼 수 있는 코드. I3 공통 코드를 포함한다
  pendingPerActor: boolean; // true면 한 사용자에게 이 namespace의 PENDING이 하나뿐이다
  precheck?(view: WorldView, actor: { generalId: number; tick: number }, payload: P): Failure | null; // 접수 전 뻔한 거절
}
// T2-26의 InputKindDefinition에 선택 칸 하나를 더한다 (쟁점 X1)
interface InputKindDefinition {
  // kind, feature, route, apply는 T2-26 그대로
  contract?: InputContract;
}
```

- `contract`는 `route: 'queued'`이고 `feature`가 null이 아닌 kind만 가진다. T2-26의 `turns.set`과 `general.create`에는 없다. 단위 시험이 등록 목록 전체에서 이 조건을 본다.
- `namespace`는 kind마다 다를 필요가 없다. 같은 기능의 kind 여럿이 namespace 하나를 함께 쓰면 그 사이에서 `requestId`가 겹칠 때 충돌로 거부된다(I4 3단계). 부대 가입·탈퇴가 `troop` 하나를 쓰는 식이다.
- payload에 행위자 장수·사용자 ID를 넣지 않는다. 행위자는 서버가 세션에서 정해 `InputEvent.userId`·`generalId`에 쓴다(AGENTS §7).
- `precheck`는 순수 함수이고 결과를 약속하지 않는다. 처리 시점 판정은 엔진 처리기가 다시 한다.

#### I2 RNG

- 처리기와 재생 `apply`는 `inputRng(seed, kind, sequence)` 하나만 쓴다. 정의는 `rngFor(seed, 'input', kind, sequence)`다.
- sequence는 T2-26이 판정 전에 받은 값이다(T2-26 통합 입력 처리기 3단계). 같은 입력은 엔진과 재생에서 같은 sequence를 가지므로 같은 수열을 받는다.
- 접수 시각(`createdAt`), 처리 tick, DB 시각을 난수 씨앗에 넣지 않는다. 장수·국가 턴 스트림 이름(`nation-turn`, `npc` 등)과 겹치지 않는다.
- 난수를 쓰지 않는 kind는 스트림을 만들지 않는다. 그래도 엔진과 재생의 결과는 같다.

#### I4 접수와 대기 (서버)

`submitInput(ctx, { worldId, requestId, kind, payload })`가 아래 순서를 한 함수로 한다. 확장 kind의 라우터 절차(`troop.join` 등)는 이 함수를 부르기만 한다.

1. `protectedProcedure`가 세션 사용자를 정한다. 무인증은 `UNAUTHORIZED`, 제재 계정은 지금 세션 확인대로 끝난다. 이 단계는 기존 요청 조회보다 먼저이며 재전송도 이 검사를 지난다.
2. `requireWorld(tx, worldId, true)`로 World 행을 잠근다(`apps/server/src/game/queries.ts`). 이 함수는 월드의 존재와 잠금만 본다. 여기서는 월드 상태와 기능을 보지 않는다.
3. 기존 요청 조회: 키 `<namespace>:<requestId>`로 같은 월드·같은 사용자의 InputEvent를 찾는다. 범위는 지금 고유키 `(worldId, userId, idempotencyKey)`(`schema.prisma:333`)와 같다. 있으면 kind와 payload(정렬 키 정규 JSON 비교, JSONB가 키 순서를 바꾸기 때문이다. 지금 `general.ts:48-52`가 같은 문제를 다룬다)가 같을 때 그 입력의 지금 상태로 대기 단계에 간다. 다르면 `CONFLICT` `같은 요청 번호로 다른 내용을 보냈습니다.`다. 이 단계는 4~7단계보다 먼저다. 그래서 처리 뒤 월드가 ENDED가 되거나 기능이 꺼지거나 행위자 장수·직책이 바뀌었어도 같은 요청의 재전송은 새 효과 없이 원래 결과(APPLIED 결과, REJECTED 오류, 또는 PENDING 대기)를 받는다.
4. 신규 접수의 월드 상태: 같은 요청이 없을 때만 본다. `ENDED`·`PREOPEN`이면 `PRECONDITION_FAILED`다(쟁점 X7).
5. 신규 접수의 기능: kind의 기능이 꺼졌으면 T2-26의 `requireRuleFeature`가 `PRECONDITION_FAILED` `이 월드에서 켜지 않은 기능입니다.`를 낸다.
6. 신규 접수의 행위자와 내용: 세션 장수를 찾고(없으면 `PRECONDITION_FAILED`) payload를 kind 스키마로 검사한다(실패면 `BAD_REQUEST` `요청 내용을 확인하세요.`). `precheck`가 있으면 `readView` 상태로 부르고 실패면 `PRECONDITION_FAILED`와 그 문구를 InputEvent 없이 돌려준다. `pendingPerActor`이면 같은 사용자·같은 namespace의 PENDING이 이미 있을 때 `CONFLICT` `요청을 처리하는 중입니다.`다.
7. InputEvent를 `status: 'PENDING'`, `generalId`는 세션 장수, `payload`는 스키마를 지난 값, 키는 3단계의 키로 만든다.

- 대기: 커밋 뒤 5초까지 100ms 간격으로 다시 읽는다(`general.ts:69-95`와 같다). APPLIED면 세션과 계정 상태를 다시 확인한 뒤(`general.ts:73-82`) result 스키마를 지난 값을 준다. REJECTED면 그 코드의 tRPC 오류를 낸다(코드 대응표는 I7 끝). 시간이 지나면 pending이다.
- 응답 타입은 T2-05·T2-06과 같다.

```ts
type RequestState<R> =
  | { status: 'pending'; requestId: string }
  | { status: 'applied'; requestId: string; result: R };
// 변경 요청의 거절은 tRPC 오류로 낸다. 재조회(I7)에서만 rejected를 값으로 돌려준다.
```

- `requestId`는 UUID 문자열이다(`z.uuid()`). 화면이 만들고 응답을 못 받으면 같은 값으로 다시 보낸다. `TOO_MANY_REQUESTS`는 기록 전에 끝나므로(`trpc.ts:18-25`) 다시 보내도 중복이 생기지 않는다.
- kind별 추가 한도는 rules 계약이 아니라 서버 어댑터의 칸이다. `apps/server/src/game/inputIntake.ts`에 `serverInputOptions: Record<kind, { rateLimit?: { limit; windowMs }; rejectStatus?: Record<string, TRPC_ERROR_CODE_KEY> }>`를 두고 rules `InputContract`에는 tRPC 타입을 넣지 않는다. `rateLimit`을 쓰면 `ctx.rateLimiter`의 `input.<namespace>` 이름공간으로 세고 1단계 뒤, 3단계 전에 본다. 이 작업에서는 쓰는 kind가 없다.
- PAUSED 월드도 접수한다(C15). 처리는 I5를 따른다.

#### I5 처리 감싸기 (엔진)

T2-26의 kind 처리기(`QueuedInputHandler`)를 `withContract(contract, handler)`로 감싼다. 감싼 처리기는 이 순서로 판정한다.

1. 저장된 payload를 스키마로 다시 읽는다. 실패면 `BAD_PAYLOAD`로 REJECTED.
2. 월드 상태: `ENDED`면 `WORLD_CLOSED`. PAUSED 월드의 계약 kind는 아래 보류 조건 때문에 이 처리기까지 오지 않는다.
3. 행위자 재검사(`apps/engine/src/inputs/actor.ts`): 사용자 행을 `FOR SHARE`로 잠그고(`inputs.ts:36`과 같다) ACTIVE가 아니면 `ACTOR_INACTIVE`. `event.generalId`의 장수가 없거나 `userId`가 다르면 `NO_GENERAL`.
4. 감싼 처리기를 `{ tick, sequence, rng: inputRng(seed, kind, sequence), actor }`로 부른다. 소속 국가·직책·부대 같은 재검사와 게임 상태 쓰기는 그 kind의 처리기 몫이다.
5. 돌려받은 값을 검사한다. APPLIED면 result 스키마를 지나야 하고 REJECTED면 코드가 `rejectCodes`에 있어야 한다. 어기면 예외로 트랜잭션을 되돌린다. 규칙 버그이므로 그 월드 엔진은 멈춘다.

PAUSED 보류: T2-26 원고의 `processInputs`는 종류와 상관없이 가장 작은 id의 PENDING 하나를 꺼낸다. 그대로면 보류할 입력이 맨 앞에 있을 때 뒤의 입력까지 막히거나 보류를 할 수 없다. 그래서 선택 조건을 하나 더한다.

- C15(`docs/plans/phase2-expansion.md:121`)대로 PAUSED 월드는 기록만 받고 재개 뒤 처리한다. 그래서 월드가 PAUSED인 걸음(`turnLoop.ts:112` 갈래)에서는 계약이 있는 kind를 모두 선택에서 뺀다(`kind NOT IN (...)`). kind별로 PAUSED 중 거절하는 정책은 두지 않는다. 필요하면 사용자 결정 U49-1로 열고 그 답과 이 계획의 재검토 전에는 적용하지 않는다. 남은 PENDING은 지금처럼 id 순으로 하나 처리한다. `general.create`는 계약이 없으므로 지금처럼 `WORLD_CLOSED`로 거절된다.
- 재개 뒤 RUNNING 걸음에서는 조건이 없으므로 보류됐던 입력이 id 순서대로 처리된다. 처리 tick은 그때의 tick이고 T2-26 C2가 지켜지므로 재생 검사 F15의 월 창 안에 있다.
- PREOPEN·ENDED 걸음은 조건이 없다. ENDED에서는 2번 판정이 `WORLD_CLOSED`로 닫고 T2-26대로 `afterEnd`에 남는다.
- 보류는 sequence를 받지 않는다. T2-26이 sequence를 판정 전에 받기 때문에 선택 단계에서 빠진 입력은 sequence를 쓰지 않는다.

같은 트랜잭션 범위: 처리기가 쓰는 게임 상태·자기 표와 InputEvent 갱신은 T2-26의 펜싱 트랜잭션 하나다. 부대장 이탈·국가 멸망 때의 부대 정리(T4-20), 입찰금 선차감과 이전 최고 입찰자 환불(T4-28), 토너먼트 보상의 장수별 1회(T4-31)는 각 kind 처리기가 이 트랜잭션 안에서 한다. 이 작업은 그 시험에 쓸 도우미(`beforeCommit` 실패 주입과 전후 비교)만 둔다.

#### I6 재생과 기록 검사 (rules)

- `apply(replay, input)`는 T2-26 등록 칸이다. 계약이 있는 kind는 `applyContractInput(contract, replay, input, compute)`로 쓴다. 이 도우미는 payload·result를 스키마로 읽고 `compute(replay, payload, { sequence, tick, rng: inputRng(...) })`로 결과를 다시 계산한 뒤 기록된 result와 정렬 키 정규 JSON으로 비교한다. 다르면 예외다(`general.create` 재생과 같은 검사).
- 형식 검사는 T2-26 head `d7c571a`가 더한 기능 검사 자리 `RuleFeatureDefinition.checkArchive(context: { origin; inputs })`(그 원고 `docs/plans/T2-26.md:86`)에 둔다. `apply`는 APPLIED만 받으므로 REJECTED와 `afterEnd`는 이 자리에서만 볼 수 있다. T2-26의 `readArchive`가 F1~F14를 마친 뒤 재생 전에 켠 기능마다 오름차순으로 `checkArchive`를 한 번 부르고 거부하면 F16이다(그 원고 `:150`, `:153`). 그 `inputs`는 `inputs`와 `afterEnd`를 sequence 순으로 이은 것이며 REJECTED와 즉시 입력도 들어 있다.
- 이 작업은 `readArchive`를 고치지 않는다. 계약 kind를 가진 기능(T4-20의 `troop` 등)의 `checkArchive`가 `checkContractInputs(registry, featureKey, inputs)`를 부르고 이 함수가 그 기능의 계약 kind 입력마다 본다. T2-26이 이 자리 없이 병합되면 1단계를 시작하지 않고 이 계획을 다시 맞춘다.
  - payload가 스키마를 지난다.
  - APPLIED이면 result가 result 스키마를 지난다. REJECTED이면 result가 `{ code, message }`이고 code가 `rejectCodes`에 있다.
  - `generalId`가 null이 아니다.
  - 같은 `(userId, idempotencyKey)`가 두 번 나오지 않는다. 기록에 키가 없으면 이 줄은 T2-26 수출 형식이 키를 싣는지에 따른다(쟁점 X8).
- 확장 기능을 켜지 않은 월드는 `checkArchive`가 불리지 않으므로 지금 판정과 같다.

#### I7 재접속 조회

새 라우터 `inputs`에 두 절차를 둔다. 둘 다 `protectedProcedure`이고 세션 사용자의 입력만 읽는다.

```ts
// inputs.get({ worldId, namespace, requestId }) → InputRecord
// inputs.recent({ worldId, namespace }) → InputRecord[]   최신 순, createdAt 24시간 안, 많아야 5개
type InputRecord = {
  kind: string;
  state:
    | { status: 'pending'; requestId: string }
    | { status: 'applied'; requestId: string; result: unknown } // kind의 result 스키마를 지난 값
    | { status: 'rejected'; requestId: string; code: string; message: string };
};
```

- 조건에 `userId = 세션 사용자`가 들어간다. 남의 `requestId`와 계약이 없는 kind(`general.create`, T2-05 `personnel.*`)는 `NOT_FOUND`다.
- `namespace`는 등록된 계약의 namespace여야 한다. 아니면 `BAD_REQUEST`다.
- 24시간과 5개는 T2-05 `personnel.recent`와 같은 값이다(쟁점 X5). InputEvent는 재생 기록이라 지우지 않으며 24시간이 지나면 `recent`에서만 빠지고 `get`으로는 계속 읽는다.
- 대기 중 세션 만료·제재는 `UNAUTHORIZED`다.
- 거절 코드의 tRPC 대응: `FEATURE_DISABLED`·`WORLD_CLOSED`는 `PRECONDITION_FAILED`, `ACTOR_INACTIVE`는 `UNAUTHORIZED`, `NO_GENERAL`은 `PRECONDITION_FAILED`, `BAD_PAYLOAD`는 `BAD_REQUEST`. kind 고유 코드는 I4의 서버 어댑터 칸 `serverInputOptions[kind].rejectStatus`로 정하고 없으면 `PRECONDITION_FAILED`다.

#### I8 공개 범위

- result 스키마에는 행위자 본인이 볼 수 있는 값만 둔다. 다른 국가의 비공개 값이 필요하면 그 kind가 `apps/server/src/visibility.ts` 경로를 쓴다(C9). 이 작업은 `visibility.ts`를 고치지 않는다.
- `inputs.get`·`recent`는 payload를 돌려주지 않는다. 화면은 자기가 보낸 값을 이미 안다.

### 선행과 착수 조건

- 0단계: 선행 없음.
- 1단계: T2-26 병합(G-02가 D-029로 풀린 상태를 SHA로 핀, `checkArchive` 자리 포함), T4-03 1단계의 엔진 공유 파일 병합 순서. 명세 §6의 병합 선행 T4-12·T4-18은 `router.ts`·`index.ts` 줄 순서다.
- 2단계: T4-20의 첫 운영 kind.
- 계약 준비: 이 계획의 Codex G-03 수용과 AC-P2-11·14·15 즉시 행동 몫의 정식 반영.

### 열린 사용자 결정

이 작업은 C15대로 PAUSED 중 모든 계약 kind를 보류한다. 그와 다른 정책은 아래 U49-1로 열어 두고 답과 재검토 전에는 적용하지 않는다. 나머지는 이 틀 위의 kind가 기다리는 결정이며 이 계획이 대신 정하지 않는다.

- U49-1 PAUSED 중 일부 즉시 행동(예: 경매 입찰)을 보류하지 않고 거절할지. 거절하면 C15 문장을 바꾸는 결정이다.

- U-08 경매 방식(마감 기준, 최소 입찰 단위, 입찰 한도의 필요 여부). `rateLimit` 값이 여기에 닿는다.
- U-09 토너먼트 주기·종목·보상.
- U-18 NPC가 확장 명령·즉시 행동을 쓸지.
- U26-3 엔진이 밀린 동안의 즉시 입력 처리(T2-26).
