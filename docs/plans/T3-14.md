### main 기준 사실 (2026-10-22, `76d56d0`)

- `docs/release-operations.md`와 `docs/admin-console.md`는 main에서 아직 뼈대다. 채워진 것은 릴리스 운영 §5의 T3-04 보안 헤더와 운영 설정 문단(`docs/release-operations.md:29-33`)뿐이다. 나머지 절은 T2-15, T3-05, T3-06, T3-11의 채울 문서가 채운다. 그 전에는 리허설할 절차가 없으므로 선행이 끝나기 전에 시작하지 않는다.
- `deploy/`에는 T3-04의 검토용 `deploy/security.caddy`만 있다. 운영 compose `deploy/compose.yml`과 `tools/deploy.sh`·`rollback.sh`·`backup.sh`·`restore.sh`는 [T2-15](./T2-15.md)가 만든다. 아래 표의 명령 이름은 T2-15 병합본을 따른다.
- A는 T3-11의 공용 풀 예약 수단이 있어야 시작한다. 2026-10-22 이 계획을 고친 작업 노드는 macOS이고 예약 수단이 없어 T3-11 심사가 `pool_unconfigured`로 거부한다. 이 상태가 바뀌기 전에는 A를 시작하지 않는다.
- B의 대상 서버는 T2-19(사용자 작업, 대기열 `구현`)가 준비한다. main에는 서버가 준비됐다는 기록이 없다. 이 계획은 서버가 있다고 가정하지 않으며 B는 그 서버가 생긴 뒤의 일이다.
- D-021의 공개 승인은 B 실행 승인이 아니다. D-021은 새 비용, GCP 기동, 운영·게임 초기화 권한을 승인에 넣지 않았다. B는 아래대로 따로 승인받는다.

### 하지 않는 것

- 공개 배포, 운영 기동, 기존 운영 서버 교체, GCP 기동, 새 비용. 이 작업은 이들을 실행하거나 승인하지 않는다.
- 실제 운영 DB나 사람이 참여한 월드의 종료·초기화. 리허설의 월드 조치는 리허설 전용 DB에서만 한다.
- 새 운영 기능. 문서에 있는데 없는 기능을 발견하면 원래 작업으로 돌린다.
- 사용자 승인을 기다리는 핵심 규칙 변경 10건.

### A. 로컬 리허설

격리 조건은 T3-11과 같다: 자기 compose 프로젝트, `127.0.0.1` 빈 포트, 리허설 전용 DB와 볼륨, 끝나면 자기 프로젝트만 `down -v`. 운영 compose(`deploy/compose.yml`)는 그대로 쓰고 아래만 덧씌운다.

시작 전에 T3-11의 자원 입장 심사(`tools/load/admission.ts`)를 같은 규칙으로 받는다. 고정된 호스트 여유 숫자만 보고 시작하지 않는다.

- A는 공유 호스트 모드로만 돈다. 예약 수단, 주인, 수명, 해제, 거부 사유는 [T3-11 공유 호스트의 공용 풀 예약](./T3-11.md#공유-호스트의-공용-풀-예약)을 그대로 따른다. 합산 예산을 그 수단으로 예약한 뒤에만 `docker build`를 부르고 자기 프로젝트의 `down -v`가 끝난 뒤 예약을 푼다. 수단이 아직 없거나 설정이 빠졌거나 조회·예약이 실패하거나 풀 표본이 오래되었으면 A를 시작하지 않고 자원 대기로 둔다.
- 덧씌움 compose는 모든 서비스(postgres, server, engine 감독, caddy, 가짜 웹훅 수신기)에 `cpus`·`mem_limit`을 둔다. 관리자 화면을 다룰 브라우저도 예산에 더한다. 이 합이 리허설 예산이다. 이미지 빌드는 T3-11의 준비 예산으로 먼저 따로 심사한다.
- CPU·메모리 80% 한도, 남이 잡은 시작 예약과 자기 시작 예약 128MiB, cgroup 메모리·CPU 여유와 압박, 디스크 8GiB 예비를 모두 본다.
- 거부되면 아무것도 띄우지 않고 기다린다. 실행 중 표본 관찰과 OOM 뒤 정리는 예약을 대신하지 않는다. 다른 작업을 멈추거나 남의 프로세스·컨테이너를 건드리지 않는다. 기다린 시각과 거부 사유를 리허설 기록에 남긴다.
- 통과한 판정과 표본(`admission.json`의 값)을 리허설 기록의 첫 줄에 남긴다. 리허설 중 메모리 여유가 0이 되거나 컨테이너가 OOM으로 죽으면 그 절을 무효로 하고 자기 프로젝트만 내린 뒤 다시 심사받는다.

- 도메인 대신 `opensamguk.localhost`, Caddy는 `tls internal`.
- 디스코드 대신 `deploy/rehearsal/`의 가짜 웹훅 수신기. 받은 본문을 파일로 남긴다.
- 백업 외부 사본은 수신기와 같은 방식의 로컬 폴더로 대신하고 B 항목으로 표시한다.
- 비밀값은 리허설 때 새로 만든 값만 쓰고 끝나면 지운다. 운영 `.env.production`을 읽거나 복사하지 않는다.

리허설 순서는 문서의 절 순서를 따른다. 문서에 없는 명령을 끼워 넣지 않는다. 문서대로 했는데 막히면 그 자리에서 멈추고 기록한 뒤 문서를 고치고 그 절을 처음부터 다시 한다.

| 문서 | 절차 |
| ---- | ---- |
| 릴리스 운영 §2 배포 | `tools/deploy.sh`로 배포 → `/healthz` 200 → 로비 열림 |
| 릴리스 운영 §3 되돌리기 | 다음 버전 배포 → `tools/rollback.sh <태그>` → 이전 버전 동작. migration이 있는 경우의 경고 확인 |
| 릴리스 운영 §4 백업과 복구 | 백업 실행 → 새 DB에 복구 → 월드 1개월 진행 → 해시 확인 |
| 릴리스 운영 §5 프록시 | `/api`, `/sse`, 정적 화면, 직접 주소 접근과 새로고침. T3-04가 적은 운영 값이 실제 구성에서 켜졌는지: Caddy 응답의 CSP·HSTS(`deploy/security.caddy`의 `game_security`), 서버 응답의 보안 헤더 3개(`apps/server/src/server.ts:60-63`), 다른 Origin POST 403과 JSON 아닌 POST 415(`:70-77`), Secure를 끈 운영 설정과 틀린 `PUBLIC_ORIGIN`의 시작 거부(`docs/release-operations.md:33`). T3-04의 보안 시험을 다시 만들지 않고 문서의 값과 실제를 대조만 한다 |
| 릴리스 운영 §6 장애 대응 | 엔진 감독 정지 → 알림 → 문서의 확인 순서(로그, 리스, 재시작) → 회복 알림 |
| 릴리스 운영 §7 모니터링 | `/healthz/engine` 503·200, 디스크·DB 용량 경고 (T3-11 시험과 같은 방법), `tools/monitor/uptime.ts`를 로컬 주소와 리허설용 로컬 상태 저장소(bare Git)로 서로 다른 실행 2번 실패 → 가짜 웹훅 알림 1건 → 성공 → 회복 1건 |
| 관리자 콘솔 §1 권한 | `pnpm admin:grant`·`admin:revoke`를 문서대로 실행 → 감사 로그 |
| 관리자 콘솔 §2 월드 | 화면으로 생성 → 시작 → 일시정지 → 재개 → 일시정지 → 초기화 → 새 월드 시작 → 일시정지 → 종료 |
| 관리자 콘솔 §3 사용자 | 찾기 → 월드 제재 → 사용자 화면 안내 확인 → 해제 → 계정 전체 제재 → 해제 |
| 관리자 콘솔 §4 공지 | 로비·월드 공지 작성 → 숨김 |
| 관리자 콘솔 §5 조사 | 같은 기기로 만든 두 계정이 묶여 보임 |
| 관리자 콘솔 §6 엔진 상태 | 화면의 하트비트 값이 `/healthz/engine`과 맞음 |
| 둘 다 | 감사 로그 화면에 위 관리 조치가 모두 있음 |

### B. 대상 서버 리허설 (승인 뒤에만)

소유자 승인 없이 시작하지 않는다. 승인 요청에는 A의 결과, 실행할 명령 목록, 서버에 생기는 변화, 되돌리는 방법을 붙인다. 공개 전이라 사람이 참여한 월드가 없어야 하며 하나라도 있으면 멈추고 묻는다.

- 실제 도메인의 HTTPS 인증서와 Cloudflare DNS
- 실제 서버에서 배포 → 되돌리기 → 다시 배포
- 백업의 외부 사본 생성과 그 사본으로 복구
- 운영 디스코드 채널로 알림 1회와 회복 1회
- 저장소 `uptime.yml`이 실제 공개 주소로 1번 성공. 그다음 대상 서버의 공개 경로를 일부러 막은 채 서로 다른 실행 2번이 연속 실패하면 장애 알림 1건, 막은 채 30분 안의 다음 실행은 알림 없음, 막은 것을 풀고 다음 성공 실행에서 회복 알림 1건. 실행은 예약 실행이나 입력 없는 수동 실행(`prod` 키)이며 T3-11의 2번 실패 기준을 그대로 쓴다. 시험용 임계값이나 시각은 주입하지 않는다. 실행 ID와 `ops/uptime-state`의 `uptime/prod.json` 커밋을 기록한다
- 관리자 계정 지정과 감사 로그 1건 (월드 종료·초기화는 하지 않는다)

### 기록

- 리허설 기록은 `docs/release-operations.md` 끝의 리허설 기록 절에 표로 남긴다: 날짜, 커밋 SHA, 단계(A·B), 절, 실행한 명령이나 화면, 기대, 실제, 결과, 고친 문서 줄. 비밀값, 이메일, IP, 웹훅 주소, 스크린샷 속 비밀은 넣지 않는다.
- 일회성 실행 로그와 에이전트 메모는 커밋하지 않는다.
- 문서 수정은 같은 작업 안에서 한다. 리뷰어가 문서와 기록을 대조한다.
