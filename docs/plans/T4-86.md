## 계획 (Claude)

### 목표

전투 시뮬레이터가 저장소의 `resources/unitset/basic.json`을 번들에 넣지 않고 T4-85의 `resources.worldRules`로 받은 그 월드의 병종표로 계산한다. 계산은 지금처럼 브라우저의 Web Worker가 `simulateBattle(input, createRng(seed))`를 한 번 실행한다. 내장 병종표로 만든 월드에서는 같은 입력과 시드의 결과가 바꾸기 전과 같다. E2E 기대값도 저장소 JSON이 아니라 그 월드의 DB 값으로 계산한다. 이 작업이 병합되면 T4-77이 `resources/unitset/basic.json`을 지워도 웹 빌드와 전투 시뮬레이터 시험이 깨지지 않는다.

AC-P2-26 전체가 아니다. JSON 삭제, 초기화 SQL, 재생 해시 대조는 T4-77 몫이다. AC-P2-16 (가)의 계약(같은 함수, 같은 시드, 막히지 않는 입력, 비공개 값 조회 없음)은 그대로 지킨다. 다만 T4-34가 정하고 E2E가 증거로 삼은 이 화면은 tRPC를 부르지 않는다는 계약은 바뀐다. 그래서 사용자 결정 D2가 먼저다.

### 화면 흐름

```text
/w/$worldId/simulator
  useWorldRules(worldId) ── 불러오는 중 ─▶ [병종표를 불러오는 중입니다.] (role=status)
                         ── 실패 ───────▶ [이 월드의 병종표를 불러오지 못했습니다.] (role=alert) + [다시 불러오기]
                         ── 성공 ───────▶ <BattleSimForm key={worldId} unitSetKey unitSet />
                                              폼 · 실행 · 결과 (지금 화면 그대로)
                                              useBattleWorker(unitSet) ─ 새 Worker마다 rules 메시지 먼저
```

- `useWorldRules`는 `trpc.resources.worldRules.queryOptions({ worldId })`에 `staleTime: Infinity`, `retry: retryUnlessClientError`(`game/queries.ts`의 다른 조회와 같은 방식)를 둔다. 월드의 병종표는 월드를 만든 뒤 바뀌지 않으므로(map-editor C-M1, T4-85) 화면에 머무는 동안 다시 받지 않는다. 다른 화면을 다녀오면 같은 캐시를 쓴다.
- 폼 부품은 월드 ID를 `key`로 받는다. 같은 화면에서 다른 월드 주소로 옮기면 폼과 Worker를 새로 만든다. 앞 월드의 병종표가 남지 않는다.
- 불러오는 중과 오류일 때 제목과 가정 문단은 보이고 폼은 그리지 않는다. 기본 병종을 정할 수 없기 때문이다. [다시 불러오기]는 `refetch()`다. 오류 문구는 서버 문구를 그대로 쓰지 않고 위 한 문장으로 고정한다.
- 소개 문장의 병종표는 기본 병종표(basic) 기준입니다를 이 월드의 병종표(`unitSetKey`) 기준입니다로 바꾼다. 결과 칸의 병종표 줄은 지금처럼 Worker가 돌려준 `unitSetId`(병종표 내용의 `id`)다. 조율 결정 R4의 키 정규형(1판은 `basic`, 2판부터 `basic@2`)에서 2판 이상 월드의 키가 판 번호를 달아도 결과 칸 값은 내용의 `id` 그대로다. 화면은 키를 해석하지 않고 받은 글자를 그대로 보인다.
- 장수 병종 목록, 기본 병종, 병종 이름은 받은 병종표에서 `unitChoices.ts`가 만든다. 함수는 지금 `publicUnitSet.ts:10-16`과 같은 식이다.
- 병종표에 성벽(1000, `armType` 0)이 없으면 수비 종류의 성벽 선택지를 `DisabledReason`으로 막고 이 병종표에는 성벽(1000)이 없습니다.를 보인다. 실제 출병은 병종표에 1000이 없으면 출병 자체를 막고(`packages/rules/src/commands/attack.ts:43`) 성벽 교전에 병종 1000을 고정해 쓴다(`attack.ts:114-133`). 내장 병종표에는 1000이 있다. 이 처리는 T4-87로 고친 병종표를 위한 방어이고 쟁점 Q3과 맞춘다.
- 375px 폭과 44px 누름 대상 기준은 새 상태의 문구와 버튼에도 같다.

### Worker 메시지 계약 (T4-34에서 바뀌는 곳)

T4-34는 Worker가 메시지로 병종표를 받지 않고 자기 묶음의 공개 표만 쓴다고 정했다. 이제 묶음에 표가 없으므로 화면이 Worker를 만들 때 한 번 보낸다. 실행 요청과 답의 모양은 바꾸지 않는다.

```ts
// request.ts에 더한다
export type BattleRulesMessage = { type: 'rules'; unitSet: unknown };
// 화면 → Worker 메시지는 BattleRulesMessage | BattleRunRequest
```

- `useBattleWorker(unitSet, create?)`의 `ensureWorker`는 Worker를 만들고 듣기를 붙인 바로 뒤에 `{ type: 'rules', unitSet }`를 보낸다. `postMessage`는 보낸 순서대로 도착하므로 첫 실행 요청보다 먼저 닿는다. 취소·오류 뒤 새 Worker를 만들 때도 다시 보낸다. [다시 실행]은 새 Worker에 병종표와 같은 요청 본문을 보낸다.
- 인자 `unitSet`의 참조가 바뀌면 지금 Worker를 끝내고 대기 상태로 돌린다. 폼이 `key`로 다시 만들어지므로 보통은 생기지 않는 경우이고 방어로 둔다.
- `compute.ts`에 `createWorkerHandler(): (message: unknown) => BattleRunReply | null`을 더한다. 첫 `rules` 메시지에서 `createCompute(message.unitSet)`를 만들고 답하지 않는다(`null`). 두 번째부터의 `rules`는 버린다. `rules`보다 먼저 온 실행 요청에는 `{ type: 'error', requestId, code: 'UNIT_SET_INVALID' }`를 답한다. 그 밖에는 지금의 `compute`를 그대로 부른다. 병종표 검사(schema, id 중복, 기본 병종)는 `createCompute`가 지금처럼 처음 한 번 한다.
- `battle.worker.ts`는 처리 함수를 부르고 `null`이 아니면 답한다. 예외는 지금처럼 `FAILED`다.
- 신뢰 경계: 병종표는 같은 출처 서버의 로그인 조회에서 온다. 사용자가 입력한 값이 아니다. 그래도 Worker는 받은 값을 지금과 같은 기준으로 다시 검사하고 실패하면 모든 실행에 `UNIT_SET_INVALID`를 답한다. 화면의 오류 문구는 지금의 병종표를 읽지 못했습니다.다.

Worker 하나에 병종표 하나다. 실행 요청마다 병종표를 싣는 방법도 봤다. 그러면 Worker가 요청마다 병종표를 다시 검사하고 `request.ts`의 요청 검사와 복사(`:61`, `:160-181`)에 병종표 칸이 섞인다. 그래서 고르지 않았다.

### 시험 고정물

`testUnitSet.ts`는 이 작업에서 새로 정한 수치의 병종표다. `basic.json`을 옮겨 적지 않는다. 그래서 출처 고지가 필요 없고 T4-77이 JSON을 지워도 남는다. 병종은 성벽 1000(`armType` 0)과 장수 병종 세 개(1100·1200·1300, `armType` 1~3)다. 성벽 병종 번호는 `request.ts`의 `WALL_CREW_TYPE`과 맞춘다. `id`는 `t486-fixture`다. 화면 코드는 이 파일을 import하지 않고 묶음 확인에서 `t486-fixture` 글자열이 없음을 본다.

### 사용자 결정이 필요한 것

결정 번호는 T4-85 문서와 이어 쓴다. T4-85의 D1(장수 생성 화면의 능력치 규칙)은 그 문서에 있다.

- D2. 전투 시뮬레이터가 월드 병종표를 서버에서 받게 할지. T4-34는 이 화면이 위쪽 띠 조회 말고는 tRPC를 부르지 않고 Worker는 묶음 안의 공개 병종표만 쓴다고 정했다. 이 계약은 D-023으로 채택한 AC-P2-16 (가)의 구현 계약이고 `e2e/battleSim.spec.ts:184-185`가 증거로 확인한다. AC-P2-16 (가) 정본 문장은 다른 국가의 비공개 값을 조회하거나 자동으로 채우지 않는다이며 공통 규칙 자료인 병종표 조회는 이 문장에 걸리지 않는다. 그래도 채택된 계약의 증거가 바뀐다. 고를 수 있는 길은 아래 네 가지다.

| 안 | 내용 | T4-34 계약 | 월드별 병종표 | 비용과 위험 |
| -- | ---- | ---------- | ------------- | ----------- |
| 가 (이 문서의 계획) | 화면이 `resources.worldRules`를 한 번 부르고 Worker에 `rules` 메시지로 넘긴다 | tRPC를 부르지 않는다는 문장을 월드 병종표 조회 한 번만 부른다로 고친다. Worker 메시지 계약도 고친다 | 맞다 | 가장 작다. E2E의 요청 0건 증거를 조회 한 번 증거로 바꾼다 |
| 나 | 경로 진입 때 라우터 `loader`가 같은 조회를 캐시에 받아 두고 화면 부품은 캐시만 읽어 Worker에 넘긴다 | 화면 부품은 tRPC를 부르지 않는다는 글자는 남는다. 네트워크 요청은 가와 같은 한 번이라 E2E 증거는 똑같이 바뀐다 | 맞다 | `router.tsx`(명세 §7 공유 파일)를 고친다. 계약의 뜻이 바뀌는 것은 가와 같아서 얻는 것이 적다 |
| 다 | 위쪽 띠가 이미 부르는 `world.summary` 응답에 병종표를 싣고 화면은 그 캐시를 읽는다 | 요청 목록이 위쪽 띠 조회뿐이라는 증거가 글자 그대로 남는다 | 맞다 | 모든 화면이 1분마다 다시 받는 응답이 병종표만큼 커진다. 서버 공유 조회(`queries.ts`)를 고쳐 다른 작업과 얽힌다 |
| 라 | 웹 빌드 때 DB나 초기화 SQL에서 내장 병종표를 꺼내 묶음에 굽는다. 화면은 지금처럼 서버를 부르지 않는다 | 바뀌지 않는다 | 맞지 않다. 고친 병종표(T4-87)로 만든 월드에서 실제 전투와 결과가 다르다 | map-editor C-M1b(병종 자료는 월드의 판을 돌려주는 API로 받는다)와 어긋난다. 빌드가 DB나 SQL을 읽어야 한다 |
