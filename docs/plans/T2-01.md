# T2-01 다중 월드: 월드별 엔진, 장애 격리

> 대기열: T2-01 · AC: AC-M2-01 · 구현: Codex · 리뷰: Claude
> 선행: M1 전체 · 관련: D-006, [런타임](../architecture/runtime.md), [T1-06](./T1-06.md)

## 계획 (Claude)

### 목표

월드 2개(시나리오·턴 간격이 다름)가 동시에 진행된다. 한 월드를 멈추거나 그 엔진을 죽여도 다른 월드는 계속 진행된다 (AC-M2-01).

### 범위

- `apps/engine/src/supervisor.ts`: 실행 중인 월드마다 엔진 자식 프로세스를 띄우고 지켜보는 감독 프로세스
- `apps/engine/src/main.ts`: `--world <id>` 하나만 맡는 기존 엔진 (T1-06)
- `pnpm dev`와 운영 실행이 감독 프로세스를 쓰도록 변경

### 하지 않는 것

여러 서버(머신)에 엔진 나누기, 월드별 DB 분리, 배포 자동화(T2-15).

### 결정

| 항목 | 결정 | 이유 |
| ---- | ---- | ---- |
| 격리 단위 | **월드마다 엔진 프로세스 하나** | 한 월드의 무한 루프·메모리 폭주·크래시가 다른 월드에 번지지 않는다. 런타임 문서의 경고 표시 해결 |
| 감독 | 감독 프로세스가 `World.status`가 RUNNING·PAUSED인 월드를 주기적으로(10초) 읽어 자식을 띄우거나 내린다 | 운영자가 월드를 시작·종료하면 자동으로 따라간다 |
| 재시작 | 자식이 죽으면 지수 백오프(1·2·4…최대 60초)로 다시 띄우고 5분 안에 5번 죽으면 멈추고 오류 기록 | 반복 크래시가 CPU를 태우지 않게 |
| 중복 방지 | 실행권은 여전히 `EngineLease`가 보장한다. 감독이 둘이 떠도 리스를 못 잡은 자식은 대기한다 | T1-06 계약 그대로 |
| 상태 보고 | 자식이 `EngineHeartbeat(worldId, at, lastTick, lagMs, lastError)`를 30초마다 쓴다 | T2-15 알림과 관리자 화면의 근거 |

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 동시 진행 | 통합: 월드 A(10분 턴)·B(60분 턴)를 manual 시계로 각각 3개월 진행 → 서로 독립된 결과 |
| 격리 | 통합: B의 자식 프로세스를 kill → A는 계속 진행, B는 백오프 뒤 재시작해 이어서 진행 |
| 일시정지 | 통합: A를 PAUSED → A의 tick 고정, B 진행 |
| 반복 크래시 | 단위: 5분 안 5회 크래시 → 재시작 중단, 오류 기록 |

## 구현 기록 (Codex)

- 담당: Codex, Kanban `t_5d0882e5`. 기반 `origin/main` 888a4df. 감독·최소 CLI/heartbeat 연결·EngineHeartbeat 모델과 새 migration·이 문서와 runtime/code-map/phases의 T2-01 부분만 수정한다.
- 착수 근거: 총괄이 사용자 병행 지시에 따라 다중 월드 감독의 독립 착수를 허용했다. M1 전체 선행은 최종 관문 인수에 그대로 남기며 미완료 M1을 완료로 바꾸지 않는다.
- 바꾼 것: RUNNING·PAUSED 월드를 10초마다 발견해 자식 하나씩 관리한다. 1·2·4초에서 최대 60초 백오프, 5분 안 5회 종료 시 해당 감독의 재시작 중단과 안전 오류 기록, 종료·삭제 월드 정리와 SIGINT·SIGTERM 소유 자식 정리를 추가했다. 기존 EngineLease와 턴 저장 코드는 바꾸지 않았다.
- 관측 계약: EngineHeartbeat의 worldId는 World FK 겸 PK이며 cascade 삭제한다. at은 timestamptz(3), lastTick·lagMs는 Int이고 DB CHECK로 lagMs >= 0을 보장한다. 리스를 가진 자식만 최초와 매 30초 관측을 쓴다. lastTick은 저장된 World.clockTick이며 lagMs는 관측 예정 시점 대비 시작 지연이다. 턴 적체·정산 완료 지표가 아니다. 관측은 재생 입력과 해시에서 제외한다.
- 계획과 달라진 점과 이유: 저장소의 정식 시나리오는 1030 하나라 실제 자식 통합 시험의 B는 이를 바탕으로 시작 연도·등장 시기를 바꾼 별도 시나리오 fixture를 쓴다. A 10분·B 60분 간격을 유지하고 격리 테스트 DB의 시계 체크포인트를 수동 주입한다. 실제 runEngine 자식이 턴과 정산을 처리하며 각 월간 해시를 재생과 대조한다. 운영 DB·호스트 서비스는 건드리지 않는다.
- 프론트 통합: Claude의 `t_825cc502`가 PR94의 `e2e/game.ts`·`e2e/turns.spec.ts`를 수정했고 Codex가 검토한 뒤 원 PR66에 fast-forward했다. 정상 월드는 최근 heartbeat를 기다린다. 대기 월드는 PREOPEN에서 시험이 실제 EngineLease를 먼저 잡고 시작한 뒤 계속 갱신한다. 같은 실행권으로 TurnLoop를 켜고 끄므로 두 번째 요청도 pending으로 남으며 afterAll에서 실행권을 놓는다. PREOPEN 그대로는 서버와 엔진이 생성을 거부하므로 이 방식을 쓴다.
- 최신 main 통합: `ab6f803`을 정상 merge했고 검증 중 들어온 `c1fd4a8`과 strict 연결 `77723bf`도 추가로 결합했다. `e2e/game.ts` 충돌은 main의 Origin 헤더·전용 DB 검사와 PR94의 readiness·리스 제어를 함께 보존해 풀었다. 게임 규칙·기존 리스·턴 저장 코드는 바꾸지 않았다. T2-01을 리뷰로 넘기되 M1 관문과 AC 최종 승인은 그대로 남긴다.
- 검증 결과: 첫 구현 `2e4f91d`에서 실제 PG·SIGKILL/12개월 재생은 통과했지만 E2E 40개 중 3개가 실패했다. PR94 `91960cc`의 필수 네 CI는 단위 355개·실제 PG 155개(감독 통합 7개)·E2E 40개·build를 모두 통과했다. 이는 원 stacked-base 결과다. 최신 main 결합 head의 필수 CI와 원본 로그는 별도로 확인해 PR66과 Kanban `t_5d0882e5`의 구현 인계에 SHA·run·job별로 남긴다. AC 최종 승인 전이다.
- main `ab6f803` 결합 검증: `07548f0`의 hosted CI `39735402589` 원본 로그에서 EXPECTED_SHA 일치와 단위 460개·실제 PG 335개·Chromium 60개·build 통과를 확인했다. 감독 통합 7개와 기존 SIGKILL/12개월 재생을 포함한다. `c1fd4a8` 결합 head는 이 성공을 승계하지 않고 별도로 검증한다.
- main `c1fd4a8` 결합 검증: `78b0232`의 준비 CI `39736783681`과 원 PR66 push `39738489300`·PR `39738492880`의 필수 job 6개 원본 로그를 대조했다. 같은 checkout SHA에서 단위 460개·실제 PG 335개·Chromium 61개·build·권한 대조 23/97/18/0이 모두 통과했고 skip·flaky는 0이다. 마지막 `77723bf` 결합은 `pnpm check`의 strict까지 새 SHA에서 검증한다.

## 리뷰 (Claude)

- 결과: 통과 (2026-10-22, t_93f40d4f). PR #66 head `48c4db1e9d30247ee043d1119af6ed007236e2fd`를 리뷰했다. 백엔드 구현 `2e4f91d`·`66ac2c6`, 시험 fixture `91960cc`(PR #94), main `77723bf`까지의 결합 커밋 세 개로 이루어진다. AC-M2-01을 통과로 바꾸고 인수조건 요약표와 README의 M2 줄을 통과 2·미착수 17로 맞춘다. M1 관문, M2 관문 전체, 공개 완료는 이 리뷰로 승인하지 않는다. 병합은 `t_a1fca67c`가 맡는다.
- 확인한 것:
  - main 대비 바뀐 파일은 15개다. 엔진 감독·heartbeat·CLI, 감독 시험, EngineHeartbeat 모델과 새 migration, 이 계획과 runtime·code-map·phases의 T2-01 부분, E2E 도우미 두 개다. 기존 migration, 리스, 턴 저장, 게임 규칙 코드는 main과 같다.
  - EngineHeartbeat 계약을 schema와 migration에서 대조했다. `worldId`는 PK 겸 World FK이고 삭제 시 cascade다. `at`은 `TIMESTAMPTZ(3)`, `lastTick`·`lagMs`는 INTEGER이며 `lagMs >= 0` CHECK가 있다. `lastError`는 감독의 고정 안내 두 가지만 들어가고 DB 오류 원문은 들어가지 않는다.
  - heartbeat는 리스를 가진 자식만 쓴다. 리스 행을 잠그고 토큰을 검사한 뒤 자기 월드 한 행만 고치고 commit 전에 다시 검사한다. 획득 직후와 이후 30초마다 쓰며 `at`은 DB 시각, `lastTick`은 저장된 `World.clockTick`이다. `exportReplay`는 World·연감·입력 기록만 읽으므로 관측값이 재생 입력과 해시에 들어가지 않는다. 시험도 heartbeat 갱신 전후 해시가 같음을 확인한다.
  - 감독은 10초마다 RUNNING·PAUSED 월드를 읽고 월드마다 자식 하나를 둔다. 백오프는 1·2·4초에서 60초까지이고 5분 안 5회 종료면 그 감독에서 재시작을 멈춘다. 발견 조회가 실패해도 기존 자식을 내리지 않는다. 종료·삭제 월드와 SIGINT·SIGTERM에서는 자기 자식에 SIGTERM, 5초 뒤 그 PID에만 SIGKILL을 보낸다. DB 연결 문자열은 환경변수로만 넘기고 명령줄 인자에 넣지 않는다.
  - exact-head push [39742317016](https://github.com/peppone-choi/opensamguk/actions/runs/39742317016)와 PR [39742320690](https://github.com/peppone-choi/opensamguk/actions/runs/39742320690)의 필수 네 job 원본 로그를 직접 읽었다. 네 job 모두 `EXPECTED_SHA`가 head와 같고 frozen 설치를 썼다. `pnpm check`는 strict 195파일 0건, 포맷, 타입, 단위 75파일 460개, 웹 빌드를 통과했다. DB·브라우저 job은 실제 PostgreSQL 18파일 335개와 Chromium 61/61개가 통과했고 건너뛴 시험은 없다.
  - 감독 통합 7개는 실제 PostgreSQL에서 실제 감독 프로세스와 실제 엔진 자식으로 돈다. 원본 로그에서 아래 줄을 각각 확인했다. A(1030, 10분)·B(시작 연도를 바꾼 fixture, 60분)를 manual로 3개월씩 따로 진행하고 B만 SIGKILL했다. B는 1초 백오프 뒤 새 토큰으로 이어 갔고 A의 자식은 한 번도 다시 뜨지 않았다. A를 정지한 동안 tick은 고정되고 B는 5개월까지 갔으며 A의 heartbeat는 30초 뒤 다시 쓰였다. B를 5회 죽인 뒤에는 중단·고정 안내가 남고 A는 계속 진행했다. 감독 둘의 중복 자식은 리스 하나만 썼고 낡은 토큰의 heartbeat는 거부됐다. 월드별 DB 오류 원문은 로그에 없었다.
  - 기존 SIGKILL 전후 재시작과 12개월 재생 시험도 같은 실행에서 통과했다.
- 막지 않는 것:
  - 감독의 오류 기록은 리스 없이 쓴다. 다른 감독의 자식이 정상이면 30초 안에 지워지지만 그 사이 잘못된 안내가 보일 수 있다. 관측 행이 없을 때 만드는 `at`도 DB 시각이 아니라 호스트 시각이다. T2-15 알림에서 이 값을 쓸 때 정한다.
  - 자식의 표준 출력을 버리고 감독 로그에는 사건 종류만 남아 어느 월드인지 보이지 않는다. 감독이 SIGKILL로 죽으면 자식이 남는다. 리스 펜싱 때문에 게임 상태는 안전하다. 운영 서비스 설정과 로그 수집은 T2-15에서 다룬다.
  - 리뷰어 로컬 frozen 설치는 공용 자원 admission이 두 번 종료 코드 75로 끝내 실행하지 못했다. 통과로 세지 않았고 제한을 우회하지 않았다. 무거운 검증은 위 exact-head 실행 결과다.
- 고칠 것: 없음.
