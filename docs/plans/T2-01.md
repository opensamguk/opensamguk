# T2-01 다중 월드: 월드별 엔진, 장애 격리

> 대기열: T2-01 · AC: AC-M2-01 · 구현: Codex · 리뷰: Claude
> 선행: M1 전체 · 관련: D-006, [런타임](../architecture/runtime.md), [T1-06](./T1-06.md)

## 계획 (Claude)

### 목표

월드 2개(시나리오·턴 간격이 다름)가 동시에 진행된다. 한 월드를 멈추거나 그 엔진을 죽여도 다른 월드는 계속 진행된다 (AC-M2-01).

### 범위

- `apps/engine/src/supervisor.ts`: 실행 중인 월드마다 엔진 자식 프로세스를 띄우고 지켜보는 감독 프로세스
- `apps/engine/src/main.ts`: `--world <id>` 하나만 맡는 기존 엔진 (T1-06)
- `pnpm dev`와 운영 실행이 감독 프로세스를 쓰도록 변경

### 하지 않는 것

여러 서버(머신)에 엔진 나누기, 월드별 DB 분리, 배포 자동화(T2-15).

### 결정

| 항목 | 결정 | 이유 |
| ---- | ---- | ---- |
| 격리 단위 | **월드마다 엔진 프로세스 하나** | 한 월드의 무한 루프·메모리 폭주·크래시가 다른 월드에 번지지 않는다. 런타임 문서의 경고 표시 해결 |
| 감독 | 감독 프로세스가 `World.status`가 RUNNING·PAUSED인 월드를 주기적으로(10초) 읽어 자식을 띄우거나 내린다 | 운영자가 월드를 시작·종료하면 자동으로 따라간다 |
| 재시작 | 자식이 죽으면 지수 백오프(1·2·4…최대 60초)로 다시 띄우고 5분 안에 5번 죽으면 멈추고 오류 기록 | 반복 크래시가 CPU를 태우지 않게 |
| 중복 방지 | 실행권은 여전히 `EngineLease`가 보장한다. 감독이 둘이 떠도 리스를 못 잡은 자식은 대기한다 | T1-06 계약 그대로 |
| 상태 보고 | 자식이 `EngineHeartbeat(worldId, at, lastTick, lagMs, lastError)`를 30초마다 쓴다 | T2-15 알림과 관리자 화면의 근거 |

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 동시 진행 | 통합: 월드 A(10분 턴)·B(60분 턴)를 manual 시계로 각각 3개월 진행 → 서로 독립된 결과 |
| 격리 | 통합: B의 자식 프로세스를 kill → A는 계속 진행, B는 백오프 뒤 재시작해 이어서 진행 |
| 일시정지 | 통합: A를 PAUSED → A의 tick 고정, B 진행 |
| 반복 크래시 | 단위: 5분 안 5회 크래시 → 재시작 중단, 오류 기록 |

## 구현 기록 (Codex)

- 담당: Codex, Kanban `t_5d0882e5`. 기반 `origin/main` 888a4df. 감독·최소 CLI/heartbeat 연결·EngineHeartbeat 모델과 새 migration·이 문서와 runtime/code-map/phases의 T2-01 부분만 수정한다.
- 착수 근거: 총괄이 사용자 병행 지시에 따라 다중 월드 감독의 독립 착수를 허용했다. M1 전체 선행은 최종 관문 인수에 그대로 남기며 미완료 M1을 완료로 바꾸지 않는다.
- 바꾼 것: RUNNING·PAUSED 월드를 10초마다 발견해 자식 하나씩 관리한다. 1·2·4초에서 최대 60초 백오프, 5분 안 5회 종료 시 해당 감독의 재시작 중단과 안전 오류 기록, 종료·삭제 월드 정리와 SIGINT·SIGTERM 소유 자식 정리를 추가했다. 기존 EngineLease와 턴 저장 코드는 바꾸지 않았다.
- 관측 계약: EngineHeartbeat의 worldId는 World FK 겸 PK이며 cascade 삭제한다. at은 timestamptz(3), lastTick·lagMs는 Int이고 DB CHECK로 lagMs >= 0을 보장한다. 리스를 가진 자식만 최초와 매 30초 관측을 쓴다. lastTick은 저장된 World.clockTick이며 lagMs는 관측 예정 시점 대비 시작 지연이다. 턴 적체·정산 완료 지표가 아니다. 관측은 재생 입력과 해시에서 제외한다.
- 계획과 달라진 점과 이유: 저장소의 정식 시나리오는 1030 하나라 실제 자식 통합 시험의 B는 이를 바탕으로 시작 연도·등장 시기를 바꾼 별도 시나리오 fixture를 쓴다. A 10분·B 60분 간격을 유지하고 격리 테스트 DB의 시계 체크포인트를 수동 주입한다. 실제 runEngine 자식이 턴과 정산을 처리하며 각 월간 해시를 재생과 대조한다. 운영 DB·호스트 서비스는 건드리지 않는다.
- 프론트 통합: Claude의 `t_825cc502`가 PR94의 `e2e/game.ts`·`e2e/turns.spec.ts`를 수정했고 Codex가 검토한 뒤 원 PR66에 fast-forward했다. 정상 월드는 최근 heartbeat를 기다린다. 대기 월드는 PREOPEN에서 시험이 실제 EngineLease를 먼저 잡고 시작한 뒤 계속 갱신한다. 같은 실행권으로 TurnLoop를 켜고 끄므로 두 번째 요청도 pending으로 남으며 afterAll에서 실행권을 놓는다. PREOPEN 그대로는 서버와 엔진이 생성을 거부하므로 이 방식을 쓴다.
- 최신 main 통합: `ab6f803`을 정상 merge했다. `e2e/game.ts` 충돌은 main의 Origin 헤더·전용 DB 검사와 PR94의 readiness·리스 제어를 함께 보존해 풀었다. 게임 규칙·기존 리스·턴 저장 코드는 바꾸지 않았다. T2-01을 리뷰로 넘기되 M1 관문과 AC 최종 승인은 그대로 남긴다.
- 검증 결과: 첫 구현 `2e4f91d`에서 실제 PG·SIGKILL/12개월 재생은 통과했지만 E2E 40개 중 3개가 실패했다. PR94 `91960cc`의 필수 네 CI는 단위 355개·실제 PG 155개(감독 통합 7개)·E2E 40개·build를 모두 통과했다. 이는 원 stacked-base 결과다. 최신 main 결합 head의 필수 CI와 원본 로그는 별도로 확인해 PR66과 Kanban `t_5d0882e5`의 구현 인계에 SHA·run·job별로 남긴다. AC 최종 승인 전이다.
