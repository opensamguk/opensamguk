## 2026-10-29 확인·판정·전달 연결 (AC-M3-09 부분)

## 2026-10-29 Git 상태 저장 연결 (AC-M3-09 부분)

비구현 담당이 승인한0.5~1일 몫으로 기존 순수 가동 판정에 Git 상태 저장을 연결한다. 정확한 `refs/heads/ops/uptime-state`와 prod·분리된 drill 키만 받고 매 호출 새 임시 저장소에서 해당 ref만 읽는다. 확인한 부재만 초기 상태로 쓰며 읽기 오류는 실패한다. 읽은 부모와 다른 키·blob을 보존한 normal push를 쓰고 거절/불명확한 결과는 새로 읽은 상태에서 같은 입력으로 최대2번 더 계산한다. 기존 연속2실패·회복·pending·실행 ID·기한 규칙은 유지한다.

운영 remote는 인증 정보·query·fragment 없는 HTTPS만 받는다. 로컬 bare는 시험용 신뢰 생성자 인자로 구분한다. 비대화형 Git·명령30초·출력 상한·자기 프로세스 종료와 close 확인 뒤 정리를 적용한다. 종료를 확인하지 못하면 임시 폴더를 보존하고 재시도하지 않는다. Git 원문 오류와 인증 도우미 출력은 노출하지 않으며 본문·정리 오류를 함께 보존한다.

첫 실제 집중 검사는116건 중114통과·2실패로38.85초에 종료했다. 옛 실행의 주입 시각을 실제로 역행시킨 시험 자료를 고치고 전역 hooksPath가 수신 hook을 바꾸지 않도록 Git 환경·설정을 자기 임시 파일로 격리한다. 독립 코드 리뷰는 환경 상속·숫자형 실행 ID 사전 거부·timeout 뒤 작업 정착과 PID 정리3건을 지적했다. OS 실행 필수 값만 상속하고 Git TLS/protocol/config/trace는 물려주지 않는다. 문자열 타입을 Git 호출 전에 확인하고 시험 본문을 생성 즉시 추적해 정착 뒤 정리한다. 자식·손자의 별도 정리도 본문 실패와 함께 전파한다. 최초 실패를 보존하며 보완판의 실제 재검증·독립 리뷰·CI·보호 병합은 남아 있다.

새 Node 자식과 실제 임시 bare의 동시성·중복·재시작·거부·읽기 오류·다른 파일 보존 및 자기 자식/손자의 종료를 검증한다. CLI·웹훅·워크플로·실제 원격 ref·예약·사용자 점검용5200은 바꾸지 않는다. 운영 인증 전달과 실제 원격 연결은 후속이다. 전체 용량 감시·공개 수신과 AC-M3-09는 미완료다.

세 P2 보완을 비구현 담당이 승인했다. 보완판의 실제 Git·새 Node 자식·기존 상태/HTTP probe3파일117건은32.82초에 통과했다. 실제 bare의 동시 push·정확한 부모/다른 blob 보존·실제 수신 hook3회 거부·중복/옛 실행·응답 유실 재조회·읽기 실패·pending 인계와 ack, 상속 Git 설정 비노출을 확인했다. 자기 자식·손자의 timeout 종료와 close 미확인 때 폴더 보존, 별도 자기 PID 정리도 검사했다. 명령 종료0·실행 중5파일 해시 불변을 확인했다. 전체 검사·최종 독립 증거 리뷰·CI·보호 병합은 남아 있다.

첫 전체 검사는5,348건 중5,347통과·1실패로312.30초에 종료했다. 실제 orphan의 보존 판정 뒤 자기 Git 임시 폴더 삭제에서 Windows `EBUSY`가 났다. 정확한 잠금 소유자는 확인하지 않았다. 손자의 cwd를 자기 시험 폴더로 지정하고 PID 종료 확인 뒤 경계를 확인한 자기 폴더만 유한하게 삭제 재시도한다. 최종 오류는 전파한다. 별도로 이미 exit한 Windows 부모 PID를 다시 종료하지 않도록 고쳤다. 실제 손자의 IPC 준비 응답과 정상 부모 exit 기록을 쓰는 native JS 시험 자료로 고정200ms 가정을 없앴다. 기존2초 timeout·100ms grace와 보존·PID 종료·부모/손자 단언은 유지한다. 독립 담당이 이 보완 계획을 승인했으며 보완판의 실제 검사는 남아 있다.

보완판 집중3파일117건은34.42초, 전체 `pnpm check`의294파일5348건은310.31초에 통과했다. 도구의 엄격 타입 검사와 공개 빌드109자산·승인 이미지6개·외부 초상0개, 실제 공개 Chromium4건(4.6초)도 통과했다. 네 명령의 종료0·실행 중6파일 해시 불변을 확인했다. 비구현 담당은 보완 코드를 열린 P1/P2 없이 승인했다. 최종 근거·문서 리뷰와 새 필수 CI·정상 보호 병합은 남아 있으며 전체 AC는 미완료다.

- 부하 생성기 자체가 병목이면 측정이 틀린다. 생성기 CPU가 제한의 70%를 넘은 구간이 있으면 그 실행은 무효다.

### 실행 장소와 자원 입장 심사

같은 호스트를 다른 프로젝트와 함께 쓴다. 이 호스트의 공용 자원 규칙은 CPU·메모리 80% 한도, 디스크 8GiB 예비, cgroup 여유, 시작 예약이다. 고정된 호스트 여유 숫자 하나만 보고 시작하지 않는다. 실행에 들어가는 모든 것을 더한 예산으로 심사를 받는다.

계획 시점(2026-10-20)에 이 호스트는 2 vCPU·메모리 7.9GiB였다. 측정 실행의 합산 예산(대상 2 vCPU·4GiB + 생성기 1 vCPU·1GiB = 3 vCPU·5GiB)은 이 호스트의 코어 수보다 크므로 심사를 통과할 수 없다. 그래서 장소를 나눈다.

| 실행 | 장소 | 합산 예산 |
| ---- | ---- | --------- |
| `pnpm load:m3` (AC 증거) | GitHub 표준 실행기 `ubuntu-24.04` (공개 저장소 기준 4 vCPU·16GiB). `.github/workflows/load-m3.yml`을 `workflow_dispatch`로만 돌린다. 공개 저장소의 표준 실행기라 새 비용이 없다. 실행기 사양도 아래 심사로 실제 값을 확인한다. 4 vCPU에서 3 vCPU 예산은 80% 한도 안에 겨우 들어가므로 준비 단계가 끝난 뒤 `--wait 10`으로 CPU 평균이 내려오기를 기다려 심사한다 | 측정 3 vCPU·5GiB·디스크 5GiB |
| `pnpm load:smoke` | `load-smoke.yml`로 GitHub 표준 실행기. 이 호스트에서는 아래 공용 풀 예약 수단이 생긴 뒤에만 | 제한을 줄인 compose: postgres 0.5 vCPU·1GiB, server 0.25 vCPU·512MiB, engine 0.25 vCPU·512MiB, 생성기 0.25 vCPU·512MiB. 합 1.25 vCPU·2.5GiB·디스크 3GiB |
| 이미지 빌드·의존성 설치 (두 실행의 준비) | 실행과 같은 곳 | 측정과 따로 먼저 심사한다. 1 vCPU·2GiB·디스크 4GiB |

T2-19 운영 서버 사양과 생성기를 더한 예산이 표준 실행기에도 들어가지 않으면 더 큰 유료 실행기를 쓰지 않는다. 멈추고 사용자에게 묻는다.

심사는 `tools/load/admission.ts`가 한다. `docker build`와 `docker compose up`을 부르기 전에 돈다.

- 실행 모드는 공유 호스트와 GitHub 실행기 둘이다. GitHub 모드는 인자 `--site github-hosted`와 두 변수 `GITHUB_ACTIONS=true`·`RUNNER_ENVIRONMENT=github-hosted`가 함께 있을 때만이다. 이 인자는 `load-m3.yml`·`load-smoke.yml`만 넘긴다. 인자는 있는데 두 변수 중 하나라도 다르면 `site_mismatch`로 거부한다. 인자가 없으면 변수와 관계없이 공유 호스트 모드다. 설정이 빠졌다고 GitHub 모드가 되는 경로는 없다.
- 예산은 그 실행의 compose 파일에서 서비스마다 `cpus`·`mem_limit`을 읽어 더한다. 제한이 없는 서비스가 하나라도 있으면 거부한다. 준비 단계는 위 표의 준비 예산으로 따로 심사한다.
- 통과 조건은 아래를 모두 만족하는 것이다. 한도는 `LOAD_ADMISSION_CPU_PERCENT`·`LOAD_ADMISSION_MEMORY_PERCENT`(기본 80), 디스크 예비는 `LOAD_ADMISSION_DISK_RESERVE_MIB`(기본 8192), 자기 시작 예약은 128MiB다.

  | 항목 | 조건 | 거부 사유 |
  | ---- | ---- | --------- |
  | CPU | 예산 vCPU ≤ 코어 수, 그리고 `(한도% − 최근 1분 평균 CPU%) × 코어 수 ÷ 100 ≥ 예산 vCPU` | `cpu_limit` |
  | 메모리 | `MemAvailable − MemTotal × (1 − 한도%) − 남이 잡은 시작 예약 − 128MiB ≥ 예산 메모리` | `memory_limit` |
  | 시작 예약 | 공유 호스트 모드: 아래 공용 풀 예약으로 합산 예산을 먼저 확보한다. 남이 잡은 예약은 위 메모리 식에 뺀다. 예약 수단 설정이 없으면 `pool_unconfigured`, 풀 상태 조회가 실패하면 `pool_unavailable`, 풀 표본이 2분보다 오래되면 `pool_stale`, 예약이 거절되면 `pool_reservation_denied`. GitHub 모드: 1회용 VM이라 남의 예약을 0으로 본다 | 왼쪽 사유 중 하나 |
  | cgroup | 컨테이너가 들어갈 부모 cgroup(docker 기본 `system.slice`)과 명령을 띄운 cgroup 각각에서 `memory.max − memory.current ≥ 예산 메모리`(값이 `max`면 호스트 값으로 본다), `cpu.max` 할당 ≥ 예산 vCPU, `memory.pressure`의 some avg10 < 10, full avg10 < 1 | `cgroup_headroom` |
  | 디스크 | docker 데이터 경로와 `.load-reports/`가 있는 파일시스템 각각의 여유 − 디스크 예비 ≥ 예산 디스크. GitHub 실행기는 1회용 VM이라 예비를 2048MiB로 준다 | `disk_reserve` |

- 통과하면 판정, 표본, 공유 호스트 모드의 예약 번호를 `.load-reports/<runId>/admission.json`에 쓰고 띄운다. 공유 호스트 모드에서는 예약을 잡기 전에 아무것도 띄우지 않는다.
- 실행 중에도 5초마다 같은 표본을 남기고 메모리 여유가 0이 되거나 컨테이너가 OOM으로 죽으면 그 실행을 무효로 하고 자기 프로젝트만 내린다. 이 관찰과 정리는 예약을 대신하지 않는다.
- 거부되면 아무것도 띄우지 않는다. 종료 코드 75와 거부 사유 하나를 출력한다. `--wait <분>`을 주면 1분마다 다시 심사하고 그 시간이 지나면 같은 코드로 끝난다. 다른 작업을 멈추거나 남의 프로세스·컨테이너에 신호를 보내지 않는다. 실행 담당은 자원 부족 대기로 보고하고 다른 작업을 한다.

격리 조건은 장소와 관계없이 같다.

- compose 프로젝트 이름 `opensamguk-load-<runId>`로 postgres·server·engine 감독·부하 생성기를 따로 띄운다. 포트는 모두 `127.0.0.1`의 빈 포트, DB 이름은 `opensamguk_load_<runId>`다. 개발 DB와 공용 `opensamguk_test`를 쓰지 않으므로 공용 DB 시험 잠금을 잡지 않는다.
- 대상 시스템 제한은 T2-19에서 정한 운영 서버 사양과 같게 둔다. 사양이 정해지기 전에는 기준값 2 vCPU·4GiB(postgres 1 vCPU·2GiB, server 0.5 vCPU·1GiB, engine 0.5 vCPU·1GiB)로 돌리고 리포트에 적는다. 부하 생성기는 따로 1 vCPU·1GiB다.
- 실행 중 5초마다 호스트 CPU를 기록한다. 우리 컨테이너 밖 사용률 때문에 호스트가 90%를 넘은 구간이 있으면 그 실행은 오염으로 보고 다시 돈다.
- 끝나면 `docker compose -p opensamguk-load-<runId> down -v`로 자기 프로젝트만 지운다. 실행 전체는 20분을 넘기지 않는다.

### 공유 호스트의 공용 풀 예약

2026-10-20에 이 호스트에서 확인한 공용 풀의 모습이다.

- 호스트 하나의 잠금 아래 예약 원장을 두고 작업자와 하위 에이전트가 시작할 때마다 고정 크기 384MiB의 시작 예약을 잡는다. 예약의 주인은 프로세스 번호, 프로세스 시작 시각, 부팅 ID다. 주인 프로세스가 끝나거나 재부팅하면 원장에서 지워지고 작업자는 시작 뒤 약 30초 안에 예약을 푼다. 예약 합계는 공개 상태 파일의 `startupReservedMiB`와 표본 시각으로 나온다.
- 바깥 명령이 임의 크기(vCPU·메모리·디스크)의 예약을 잡는 공개 수단은 없다. 예약에서 실제 사용량을 빼는 계산도 작업자 cgroup 아래만 본다. docker 컨테이너는 `system.slice`에서 돌므로 이 계산에 들어가지 않는다.
- 상태 파일을 읽고 빼기만 하면 두 시작자가 같은 여유를 보고 함께 시작할 수 있다. 그러므로 지금 이 호스트에는 부하·리허설의 합산 예산을 확보할 수단이 없다.

그래서 이렇게 정한다.

- 아래 계약을 만족하는 예약 수단이 이 호스트에 생기고 그 연결이 리뷰를 통과하기 전까지, 공유 호스트 모드의 심사는 항상 거부한다(설정이 없으면 `pool_unconfigured`). 이 호스트의 `pnpm load:smoke`와 [T3-14](./T3-14.md) A는 자원 대기로 두고 시작하지 않는다. 도구 검증은 GitHub 모드와 아래 가짜 풀 시험으로 한다.
- 예약 수단이 갖출 계약:

  | 항목 | 계약 |
  | ---- | ---- |
  | 원자성 | 호스트 하나의 잠금 안에서 새 표본, 남의 예약 합, 자기 합산 예산을 한 번에 비교하고 통과할 때만 예약을 기록한다. 비교와 기록 사이에 다른 시작자가 끼지 못한다 |
  | 주인 | 실행 내내 살아 있는 `tools/load` 프로세스. 프로세스 번호, 시작 시각, 부팅 ID로 식별한다 |
  | 수명 | 준비 단계의 `docker build` 전에 잡고 자기 프로젝트의 `down -v`가 끝난 뒤 푼다. 상한은 실행 상한 20분에 정리 5분을 더한 25분이다. 준비와 측정 예산이 다르면 큰 쪽으로 잡는다 |
  | 계산 | 예약이 살아 있는 동안 예산 전체를 남이 쓴 것으로 보이게 한다. 컨테이너의 실제 사용량을 빼지 않는다. 이중 계산은 거부 쪽으로만 틀린다 |
  | 해제 | 정상 종료, 실패, 신호 모두 정리 뒤 푼다. 주인이 강제 종료되면 원장이 예약을 지운다. 그때 남은 자기 컨테이너는 `mem_limit` 안에서 호스트 표본에 실제 사용량으로 잡히고 실행 담당이 `admission.json`의 프로젝트 이름으로 자기 것만 내린다 |
  | 상태 | 예약 결과와 표본 시각을 돌려준다. 표본이 2분보다 오래되었거나 원장을 읽지 못하면 예약하지 않는다 |

- 이 수단은 오픈삼국 저장소 밖 호스트 공용 풀의 일이며 이 계획에서 만들지 않는다. 총괄에게 호스트 공용 풀 담당 배정을 요청한다. 수단이 생기면 연결 방법(명령 이름과 설정 이름)을 이 절에 더하고 다시 리뷰받는다.

### 재현 명령

```sh
pnpm load:m3 --run <runId>            # 띄우기 → 준비 → 2분 준비 운동 → 15분 측정 → 리포트 → 정리
pnpm load:m3 --run <runId> --keep     # 정리하지 않고 남김 (원인 조사용, GitHub 모드에서만)
pnpm load:report .load-reports/<runId> # 저장된 원자료로 리포트 다시 계산
pnpm load:smoke                        # 월드 2개 × 동시 접속 10 × 1분, 도구가 깨지지 않았는지만 본다
```

- `--keep`은 공유 호스트 모드에서 거부한다. 예약 주인인 도구 프로세스가 끝난 뒤에도 컨테이너가 남기 때문이다.
- 원자료와 JSON 리포트는 `.load-reports/<runId>/`(Git 제외)에 남는다. 커밋 SHA, 실행 장소, 제한값, 자원 심사 결과(`admission.json`), 호스트 정보, 측정값, 판정을 담는다. `load-m3.yml`은 이 폴더를 Actions 산출물로 올린다.
- `load-smoke.yml`은 `workflow_dispatch`로만 도는 GitHub 표준 실행기 작업이다. 판정은 하지 않고 도구가 끝까지 도는지만 본다. PR마다 돌리지 않는다.
- AC 증거는 `load-m3.yml` 실행의 판정 요약을 `docs/architecture/performance.md`에 옮긴 표(명령, 실행 ID, SHA, 실행 장소, 제한값, 심사 판정, p95, 최대 지연, 오류 수)다. 원자료 파일은 커밋하지 않는다.

### 모니터링

알림은 T2-15의 운영 디스코드 웹훅(`OPS_DISCORD_WEBHOOK_URL`)과 같은 중복 규칙을 쓴다. 같은 알림은 30분에 한 번이고 문제가 이어지면 30분마다 다시 1건, 회복하면 회복 알림 1건이다. 이 규칙을 판단하는 상태를 어디에 두는지는 감시마다 다르다.

- 서버 안 감시(엔진 하트비트, 디스크, DB 용량)는 서버 프로세스 하나에서 계속 도는 T2-15 감시 작업이 한다. 상태는 그 작업의 메모리에 둔다. 서버가 재시작되면 상태가 비므로 문제가 이어지는 중이면 알림이 1건 더 갈 수 있다. 이 차이를 release-operations §7에 적는다.
- 사이트 가동 확인은 실행마다 새 GitHub 실행기에서 돈다. 파일과 메모리가 다음 실행에 남지 않으므로 아래 상태 저장소를 쓴다.

| 감시 | 방법 | 알림 조건 |
| ---- | ---- | --------- |
| 사이트 가동 | `.github/workflows/uptime.yml`이 10분마다 GitHub 표준 실행기에서 `tools/monitor/uptime.ts`로 공개 주소의 `/healthz`와 `/healthz/engine`을 부른다. 서버가 통째로 죽어도 서버 밖에서 알 수 있다 | 서로 다른 실행에서 연속 2번 실패 (아래 상태 저장소). 저장소 변수 `PUBLIC_URL`이 비어 있으면 아무것도 하지 않고 성공으로 끝난다 |
| 엔진 하트비트 | 서버에 `/healthz/engine`을 더한다. RUNNING·PAUSED 월드의 `EngineHeartbeat`가 2분 넘게 없거나 지연이 5분을 넘으면 503. 응답은 `{ ok, worlds, stale }` 개수만 주고 월드 ID·오류 내용은 주지 않는다. 5분 정지 알림은 T2-15 것을 그대로 쓴다. 이 경로의 서버 구현은 Ops 채팅 소유로 정정하며 가동 확인은 부르기만 한다([아래 정정](#가동-확인-정정)). 판정 경계, 실패 본문, 조회 방식은 [Ops 건강 HTTP 정정](#ops-건강-http-정정)을 따른다 | T2-15 규칙 |
| 디스크 | 서버 감시 작업이 5분마다 `fs.statfs`로 `MONITOR_DISK_PATHS`(postgres 데이터, 백업 폴더)를 본다 | 사용률 80% 경고, 90% 위험 |
| DB 용량 | 같은 작업이 `pg_database_size(current_database())`를 읽는다 | `DB_SIZE_WARN_BYTES` 이상 경고 |

- 임계값과 주기는 환경변수로 바꾸며 시험은 짧은 값을 주입한다. 알림 본문에 비밀값·이메일·웹훅 주소를 넣지 않는다.

### 가동 확인의 실행 간 상태

연속 실패 수, 30분 중복 억제, 아직 보내지 못한 알림을 서로 다른 GitHub 실행 사이에서 이어 가려고 저장소 안에 상태를 둔다. 새 서비스나 비용은 쓰지 않는다. `tools/monitor/uptimeState.ts`가 읽기·쓰기를 맡는다.

| 항목 | 결정 |
| ---- | ---- |
| 저장소 | 같은 GitHub 저장소의 전용 브랜치 `ops/uptime-state`. main과 이력을 공유하지 않는 orphan 브랜치이며 상태 파일만 담는다 |
| 키 | 파일 경로 `uptime/<key>.json`. 예약 실행과 입력 없는 수동 실행은 `prod`. 시험 실행(`workflow_dispatch` 입력 `drill_key`)은 `drill-<drill_key>`이며 `prod` 파일을 건드리지 않는다 |
| 값 | `{ version: 1, consecutiveFailures, alerting, lastAlertAt, lastRecoveryAt, updatedAt, lastRunId, pending, lastDelivered }`. 앞의 값들은 확인 결과로 정한 판정 상태다. `pending`은 판정이 만들었지만 발송 완료를 아직 기록하지 못한 알림의 목록이고 항목은 `{ id, kind, decidedAt, decidedRunId, attempts, lastAttemptAt }`이다. `kind`는 `down` 또는 `recovery`, `id`는 `<key>:<kind>:<실행 ID>.<실행 시도 번호>`로 한 번 정하면 바뀌지 않는다. `lastDelivered`는 마지막으로 완료를 기록한 `{ id, kind, at }`이다. `consecutiveFailures`는 0~2이고 2에서 멈춘다. 다만 관측을 적용한 새 실행마다 `updatedAt`·`lastRunId`가 바뀌므로 장애가 이어져도 그 실행마다 판정 커밋이 1개 생긴다. 실행 ID가 `lastRunId` 이하인 실행은 판정 커밋을 만들지 않는다([아래 정정](#가동-확인-정정)). 주소, 웹훅, 응답 본문은 넣지 않는다 |
| 쓰기 권한 | `uptime.yml`의 감시 작업 하나만 `permissions: contents: write`이고 그 밖은 read다. 저장소 기본 워크플로 권한은 지금처럼 read로 둔다. 스크립트는 `refs/heads/ops/uptime-state` 하나에만 push하며 다른 ref가 설정되면 시작하지 않는다. main은 기존 보호 규칙(필수 검사)으로 막혀 있다. `GITHUB_TOKEN`으로 한 push는 새 워크플로를 띄우지 않으므로 상태 커밋마다 CI가 돌지 않는다 |
| 직렬화 | 워크플로 `concurrency: uptime-<key>`, `cancel-in-progress: false`로 같은 키의 실행은 하나씩 돈다. push는 읽은 커밋을 부모로 하는 fast-forward만 하고 강제 push는 하지 않는다. 거절되면 다시 받아 같은 확인 결과로 새 상태를 다시 계산하고 2번까지 재시도한다. 다시 계산할 때 받은 상태의 `pending`은 그대로 이어받는다. 그래도 거절되면 알림 없이 실패로 끝난다. 다시 계산은 새로 받은 커밋의 자기 키 파일에서 시작하고 다른 키 파일은 건드리지 않는다(아래 정정) |
| 판정 | 실패는 `/healthz`나 `/healthz/engine`이 10초 안에 200이 아닌 것이다. 실패면 `consecutiveFailures`를 1 올린다(받은 상태의 `lastRunId` 이하 실행 ID의 관측은 성공과 실패 모두 적용하지 않는다, 아래 정정). 2가 되었고 `alerting`이 아니거나 `lastAlertAt`에서 30분이 지났으면 `pending`에 장애 1건을 더하고 `alerting = true`와 `lastAlertAt`을 바꾼다. 단, `pending`의 마지막 항목이 아직 못 보낸 장애이면 30분 재알림은 더하지 않고 `lastAlertAt`도 그대로 둔다. 성공이면 `consecutiveFailures = 0`이고 `alerting`이었으면 `pending`에 회복 1건을 더하고 `alerting = false`와 `lastRecoveryAt`을 바꾼다 |
| 순서 | 확인 → 판정 상태와 `pending` 계산 → 상태 push → `pending`을 오래된 것부터 한 건씩 보내기 → 한 건이 2xx를 받을 때마다 그 항목을 지우고 `lastDelivered`를 바꾼 커밋을 push. 보내는 실행은 방금 상태 push에 성공한 실행과 관측을 적용하지 않은 실행(아래 정정)뿐이다. 판정 상태는 되돌리지 않는다. 앞선 실행이 남긴 `pending`도 이번 확인 결과와 관계없이 같은 차례에 보낸다. 그래서 회복 판정 뒤 계속 정상이어도 못 보낸 회복은 다음 실행이 보낸다. 보내기가 실패하면 그 항목의 `attempts`·`lastAttemptAt`을 올린 커밋을 push하고(이 push가 실패해도 넘어간다) 남은 항목은 보내지 않은 채 실행을 실패로 끝낸다. 완료 push가 거절되면 다시 받아 그 `id`가 남아 있으면 지우는 것으로 2번까지 재시도한다. 그래도 실패하면 남은 항목을 보내지 않고 실패로 끝난다(아래 정정) |
| 전달 보장 | 판정 push로 원격에 들어간 `pending` 항목을 맨 앞부터 다시 보내 적어도 한 번을 노린다. 실제 수신은 지금 조건만으로 보장하지 않는다(조건은 아래 정정). 웹훅 수신과 Git 기록을 한 트랜잭션으로 묶을 수 없으므로 정확히 한 번은 약속하지 않는다. 상태 push 뒤 보내기 전에 끝나거나, 보내기 실패 뒤 `attempts` push까지 실패해도 앞서 push한 `pending`이 남아 다음 실행이 보낸다. 웹훅이 받은 뒤 완료 push 전에 끝나거나 완료 push가 끝내 실패하면 다음 실행이 같은 `id`로 다시 보낸다. 이런 중단 한 번 뒤 다음 실행이 보내기와 완료 push에 모두 성공하면 중복은 1건에서 그친다. 완료 기록이 거듭 실패하면 같은 `id`가 실행마다 다시 갈 수 있다(아래 정정). 본문에 `id`를 넣어 같은 알림임을 알아볼 수 있게 한다. 유실은 상태 파일이 깨졌거나 브랜치가 지워진 경우, `pending`이 4건을 넘어 가장 오래된 것을 버린 경우, 24시간 넘게 보내지 못한 항목을 버린 경우뿐이며 모두 실행 요약에 경고를 남긴다 |
| 복구 | 브랜치나 파일이 없다고 확인되면 초기 상태(0, `alerting = false`)로 보고 처음 쓸 때 만든다(Git 조회 실패는 없음이 아니다, 아래 정정). JSON이 깨졌거나 `version`이 다르면 실행 요약에 경고를 남기고 초기 상태로 본다(JSON은 맞지만 schema 검사를 통과하지 못한 파일도 같다, 아래 정정). `updatedAt`이 60분보다 오래되었으면(예약이 밀리거나 꺼졌던 경우) `consecutiveFailures`만 0으로 되돌리고 `alerting`과 `pending`은 유지해 회복 알림을 잃지 않는다 |
| 꺼짐 | `PUBLIC_URL`이 비어 있으면 확인도 상태 쓰기도 하지 않는다. 웹훅 비밀이 없으면 판정 상태는 같은 규칙으로 쓰되 `pending`에 더하지 않고 실행 요약에 판정과 알림 대상 없음을 남긴다. 이미 있던 `pending`은 보내지 않고 두며 24시간 규칙을 따른다 |

- 공개 저장소의 예약 워크플로는 저장소 활동이 60일 없으면 GitHub가 끈다. 이 점과 다시 켜는 방법을 release-operations §7에 적는다.
- 예약 실행은 기본 브랜치(main)의 워크플로만 돈다. main에 병합되기 전의 확인은 아래 시험 실행으로 한다.

`uptimeState.ts`에는 아래 함수를 둔다. 시각 입력은 epoch ms 정수이고 저장 값은 `toISOString()` 문자열이다.

| 함수 | 입력 | 출력 |
| ---- | ---- | ---- |
| `initialState()` | 없음 | `{ version: 1, consecutiveFailures: 0, alerting: false, lastAlertAt: null, lastRecoveryAt: null, updatedAt: null, lastRunId: null, pending: [], lastDelivered: null }`. `updatedAt`·`lastRunId`가 null인 값은 메모리에만 있고 파일로 쓰지 않는다 |
| `restoreState({ key, raw, now })` | `raw`는 파일 내용 문자열. Git 조회가 성공해 브랜치나 파일이 없다고 확인된 경우만 null이고 읽기 오류면 부르지 않는다 | `{ state, source: 'missing' \| 'file' \| 'reset', warnings }`. `reset`은 손상·version·schema 때문에 초기 상태로 돌린 경우다. 경고는 `{ code, field? }`이고 `code`는 `corrupt_json`·`unknown_version`·`invalid_schema`·`stale_reset` 중 하나. 시각 역행이면 상태 없이 `{ error: 'clock_regressed' }` |
| `observe(state, { key, runId, runAttempt, now, ok, webhookConfigured })` | 복원한 상태와 이번 확인 결과 | `{ result, state, counted, added, suppressed, dropped }`. `result`는 `applied`·`skipped`·`clock_regressed`, `added`는 이번에 더한 항목(0~1개), `suppressed`는 `pending_down`·`no_webhook`·null, `dropped`는 `{ id, reason: 'ttl' \| 'cap' }` 목록 |
| `nextDelivery(state, { now })` | 상태 | `pending`의 맨 앞 항목. 비었거나 맨 앞의 `now − decidedAt`이 24시간을 넘었으면 null |
| `recordAttemptFailure(state, { id, now })` | 보내기에 실패한 항목 | 맨 앞이 그 `id`면 `attempts + 1`, `lastAttemptAt = now`로 바꾼 `{ result: 'recorded', state }`. 아니면 바꾸지 않은 `{ result: 'not_head' \| 'missing', state }` |
| `acknowledge(state, { id, now })` | 2xx를 받은 항목 | 아래 ack 규칙의 `{ result, state }` |
| `serializeState(state)` | 파일로 쓸 상태 | 키 순서를 고정한 JSON과 끝 줄바꿈. 같은 상태는 같은 바이트다 |

첫 단계에서는 시험이 모든 값을 넘긴다. 후속 CLI는 확인이 끝난 시각을 한 번 읽어 `now`로 넘기고 다시 계산할 때도 같은 값을 쓴다. ack 시각은 2xx를 받은 뒤 따로 읽는다. `runId`·`runAttempt`는 GitHub가 주는 `GITHUB_RUN_ID`·`GITHUB_RUN_ATTEMPT`, `ok`는 `uptimeProbe`의 결과, `webhookConfigured`는 웹훅 비밀이 비어 있지 않은지, `key`는 워크플로 입력에서 온다.

`uptimeProbe.ts`는 `probeHealth({ baseUrl, timeoutMs })` 하나를 둔다. `baseUrl`은 `URL`이고 그 origin에 `/healthz`와 `/healthz/engine`을 붙인다. `baseUrl`의 path, query, fragment는 쓰지 않는다. `PUBLIC_URL`에 path를 허용할지는 후속 CLI의 설정 검사가 정하고 adapter는 그 결정과 관계없이 origin만 쓴다. `timeoutMs`는 기본값 없이 호출자가 넘기며 후속 CLI는 기존 값 10초를 넘긴다. 두 경로를 모두 부르고 요청마다 `GET`, `redirect: 'manual'`, 자기 `AbortSignal.timeout(timeoutMs)`를 쓴다. 쿠키, `Origin`, 인증 헤더는 붙이지 않는다. 상태 줄을 받으면 본문은 읽지 않고 취소한다. 출력은 `{ ok, targets: [{ path, outcome, status? }] }`다. `outcome`은 정확히 200인 `ok`, 그 밖 상태 코드(다른 2xx 포함)인 `status`, 따라가지 않은 3xx인 `redirect`, 제한 시간을 넘긴 `timeout`, 연결 거부·이름 풀이·TLS처럼 `fetch`가 거부된 `network` 중 하나다. `ok`는 두 경로가 모두 `ok`일 때만 참이다. 본문, 응답 헤더, 오류 메시지, 전체 주소는 결과에 넣지 않는다. Ops의 `/healthz`가 main에 들어오면 같은 adapter를 `buildServer`를 loopback에 띄운 실제 서버에 붙이는 시험을 후속으로 더할 수 있다.

#### 복원과 schema

Git 조회가 성공해 브랜치나 파일이 없다고 확인되면 경고 없이 초기 상태다. 조회 실패는 아래 Git 단계를 따르고 초기 상태로 보지 않는다. JSON이 깨지면 `corrupt_json`, `version`이 1이 아니면 `unknown_version`, JSON과 version은 맞지만 아래 검사에 걸리면 `invalid_schema`이고 셋 다 초기 상태로 돌아간다. 이때 `pending`을 잃으므로 유실 경고로 센다. 경고에는 `code`와 필드 경로(`pending[2].id` 같은)만 넣는다. 원문, 필드 값, `JSON.parse` 오류 메시지(입력 일부가 들어간다)는 넣지 않는다. 검사를 통과한 파일의 `updatedAt`이 `now`보다 60분 넘게 앞서면 `consecutiveFailures`만 0으로 하고 `stale_reset`을 남긴다. `alerting`, `lastAlertAt`, `lastRecoveryAt`, `pending`, `lastDelivered`, `lastRunId`는 그대로다. `PUBLIC_URL`이 비었을 때와 웹훅 비밀이 없을 때의 기존 정책(위 꺼짐 행)은 바뀌지 않는다. `PUBLIC_URL`이 비면 후속 CLI가 이 모듈을 부르기 전에 끝낸다. 웹훅 비밀이 없으면 `webhookConfigured = false`로 들어온다.

| 필드 | 검사 |
| ---- | ---- |
| `consecutiveFailures` | 정수 0, 1, 2. 2이면 `alerting`이 참 |
| `alerting` | boolean. 참이면 `lastAlertAt`이 null이 아니다 |
| `lastAlertAt`·`lastRecoveryAt` | null 또는 시각 |
| `updatedAt` | 시각. 파일에서는 null이 아니다 |
| `lastRunId`·`pending[].decidedRunId` | 실행 ID. 파일의 `lastRunId`는 null이 아니다. `pending[].decidedRunId`와 `lastDelivered.id`의 실행 ID는 모두 BigInt로 비교해 `lastRunId` 이하다 |
| `pending` | 길이 0~4. `id`는 서로 다르고 `decidedAt`은 앞에서 뒤로 줄지 않는다 |
| `pending[].id` | `<key>:<kind>:<decidedRunId>.<시도 번호>`. `key`는 이 파일의 키, `kind`는 항목의 `kind`와 같다 |
| `pending[].decidedAt` | 시각이고 `updatedAt` 이하 |
| `pending[].attempts` | 0 이상 정수. 0이면 `lastAttemptAt`이 null이고 1 이상이면 `decidedAt` 이상인 시각 |
| `lastDelivered` | null 또는 `{ id, kind, at }`. `id` 형식과 `kind` 일치는 `pending`과 같고 그 `id`는 `pending`에 없다 |
| 그 밖 | 모르는 필드가 있으면 실패 |

시각은 `toISOString()` 결과와 정확히 같은 UTC 문자열이고 실행 ID와 시도 번호는 앞자리 0이 없는 양의 10진 정수 문자열이다. version 1의 `lastRunId`와 `decidedRunId`는 실행 ID만 담고 시도 번호는 `id` 끝에만 둔다. `lastRunId`는 마지막으로 적용한 가장 큰 실행 ID다(아래 관측 전이). 기존 필드의 뜻을 좁힌 것이며 새 필드와 version 변경은 없다. 이 작업에서 원격 상태 ref와 상태 파일의 존재는 조회하지 않았으므로 실제 연결 전에 먼저 확인한다. 상태 파일이 있으면 원문을 백업해 보존하고 기존 필드의 type과 뜻, 특히 `lastRunId`·`decidedRunId`·`id`에 든 실행 ID가 이 절의 뜻과 같은지 확인한 뒤 연결한다. schema를 통과하더라도 관측 `id`의 뜻이 다른 legacy 값을 성공으로 이어 쓰지 않는다. 뜻이 다르거나 확인할 수 없으면 연결하지 않고 그 처리를 따로 계획한다. 연결 뒤 schema 실패로 초기화한 파일의 원문은 강제 push를 하지 않으므로 Git 이력에 남는다. 나중에 필드를 더하려면 version 값과 이전 경계를 따로 계획해 리뷰받는다. 이 정정에서는 정하지 않는다. 키는 `prod` 또는 `drill-<drill_key>`이고 `drill_key`의 허용 문자는 기존 계획에 없다. 첫 단계는 `id` 구분자와 파일 경로를 깨지 않도록 키가 비었거나 `:`·`/`·`\`를 담거나 `..`를 담으면 거부만 한다.

시각 역행은 저장 파일 손상과 따로 다룬다. `restoreState`, `observe`, `recordAttemptFailure`, `acknowledge`는 상태에 든 시각(`updatedAt`, `lastAlertAt`, `lastRecoveryAt`, `pending[].decidedAt`·`lastAttemptAt`, `lastDelivered.at`) 가운데 하나라도 `now`보다 뒤면 입력 문맥 오류인 `clock_regressed`를 돌려주고 상태를 바꾸지 않는다. `nextDelivery`도 같은 조건에서 null을 돌려준다. `restoreState`는 JSON, version, schema를 먼저 보고 그것을 통과한 파일에만 이 검사를 한 뒤 묵음 검사를 한다. 시각 역행이면 초기 상태로 돌리지 않는다. 호출자는 관측, 쓰기, 보내기를 하지 않고 실행을 실패로 끝내며 원격 파일은 그대로 남는다. 그래서 `updatedAt`이 `now`보다 뒤인 파일은 묵지 않은 파일로도 손상된 파일로도 보지 않는다.

#### 관측 전이

`observe`는 아래 차례로 한 번에 계산한다. 2회, 10초, 30분, 60분, 4건, 24시간은 위 결정의 값 그대로다. 비교 경계는 이 정정의 기술 계약이다. 30분은 그 시간 이상이면 지난 것이고 60분과 24시간은 그 시간을 넘어야 지난 것이다.

1. 시각 역행이면 `clock_regressed`로 끝낸다.
2. 받은 상태의 `lastRunId`가 null이 아니고 `BigInt(runId) <= BigInt(lastRunId)`이면 `skipped`로 끝낸다. 성공과 실패가 같다. 상태는 받은 그대로이며 24시간·4건 정리, 판정 필드, `updatedAt`, `lastRunId`, `pending` 어느 것도 바꾸지 않는다. `counted = false`, `added`·`dropped`는 빈 목록, `suppressed`는 null이다. 호출자는 실행 요약에 `run_not_newer` 진단을 남긴다.
3. `now − decidedAt`이 24시간을 넘은 항목을 버린다(`ttl`).
4. 성공이면 `consecutiveFailures = 0`이다. `alerting`이었으면 `alerting = false`, `lastRecoveryAt = now`로 하고 웹훅이 있으면 회복 1건을 더하고 없으면 `no_webhook`이다.
5. 실패면 `consecutiveFailures`를 1 올리되 2에서 멈춘다. 2이고 `alerting`이 아니면 `alerting = true`, `lastAlertAt = now`로 하고 장애 1건을 더한다. 2이고 `alerting`이며 `lastAlertAt`에서 30분이 지났으면 재알림이다. 이때 `pending` 마지막 항목이 장애이면 더하지 않고 `lastAlertAt`도 두며 `pending_down`이다. 그렇지 않으면 `lastAlertAt = now`로 하고 장애 1건을 더한다. 웹훅이 없으면 판정 필드는 같게 바꾸고 항목만 더하지 않는다(`no_webhook`).
6. `pending`이 4건을 넘으면 넘친 만큼 맨 앞부터 버린다(`cap`).
7. `updatedAt = now`, `lastRunId = runId`로 하고 `applied`다. 그러므로 `applied` 실행은 언제나 상태가 바뀌고 `skipped` 실행은 직렬화 바이트까지 그대로다.

새 항목은 `{ id: '<key>:<kind>:<runId>.<runAttempt>', kind, decidedAt: now, decidedRunId: runId, attempts: 0, lastAttemptAt: null }`다. `id`는 키, 종류, 실행 ID, 시도 번호에서만 나오므로 다시 계산이나 프로세스 재시작, 보내기 재시도에서도 바뀌지 않는다. 세 숫자는 서로 다르다. `runAttempt`는 GitHub 다시 실행의 시도 번호로 `id`에만 들어간다. fast-forward 거절 뒤 다시 계산하는 횟수(최대 2번)는 프로세스 안의 값이라 어디에도 저장하지 않는다. `pending[].attempts`는 보내기 실패 횟수다.

`lastRunId`는 마지막으로 적용한 가장 큰 실행 ID다. 값은 앞자리 0이 없는 양의 10진 문자열이므로 BigInt로 정확히 비교한다. 문자열 비교는 `9`와 `10`의 순서를 거꾸로 본다. 적용되는 실행의 `runId`는 받은 `lastRunId`보다 크고 schema가 `pending`과 `lastDelivered`의 실행 ID를 모두 `lastRunId` 이하로 묶으므로 새 `id`는 `pending`에도 `lastDelivered`에도 없다. 앞 정정처럼 같은 실행 ID만 막으면 생기는 반례를 이것으로 닫는다. `alerting = true`, `consecutiveFailures = 2`, `lastAlertAt`이 30분 전, `lastRunId = '20'`, `lastDelivered.id = 'prod:down:10.1'`, `pending = []`인 상태에 실행 `10`의 시도 `1`이 지금 실패를 내면 앞 정정은 재알림 `prod:down:10.1`을 `pending`에 더해 schema를 어긴다. 이 계약에서는 `10 <= 20`이라 `skipped`다.

같은 실행 ID의 GitHub 다시 실행, 같은 실행의 다시 계산, push가 실제로는 들어간 뒤의 재시도, 사이에 다른 실행이 낀 뒤의 옛 실행은 모두 `skipped`다. 성공이어도 회복 항목이나 `alerting` 변경을 만들지 않는다. 먼저 원격에 적용된 실행의 결과가 고정되고 뒤늦은 옛 관측은 진단으로만 남는다. GitHub의 같은 키 `concurrency`는 두 실행이 함께 돌지 않게 할 뿐 실행 ID 순서대로 돈다고 보장하지 않으므로 이 경계를 둔다. 큰 실행 ID를 새 관측으로 보는 것은 기술 가정이다. 이 가정이 어긋나도 `id` 유일성은 그대로이며 그 관측 하나가 `skipped`될 뿐이다. 전역 정확히 한 번 반영은 약속하지 않는다.

다시 계산은 언제나 새로 받은 원문을 `restoreState`부터 다시 하고 자기가 앞서 계산한 결과에 다시 적용하지 않는다. 차례는 복원(손상 초기화, 시각 역행, `stale_reset`), 실행 ID 비교, 그다음 `applied`일 때만 24시간 정리, 판정, 4건 정리다. `stale_reset`은 관측이 아니어서 `lastRunId`·`updatedAt`을 바꾸지 않으므로 그 뒤의 비교도 원격 값으로 한다. 그래서 한 원격 관측을 두 번 세지 않는다. 초기 상태에서는 서로 다른 두 실행이 실패해야 장애 1건이 생긴다. 회복을 못 보낸 채 다시 장애가 되면 `pending`은 회복, 장애 순서이고 그 순서대로 보낸다.

#### 보내기와 ack

판정 push에 성공한 실행과 `skipped` 실행만 `nextDelivery(state, { now })`의 맨 앞 하나를 보낸다. `skipped` 실행은 판정 커밋 없이 받은 원격 상태에서 보내므로 이미 원격에 들어간 항목만 보낸다. 24시간을 넘은 맨 앞 항목은 `nextDelivery`가 null을 돌려 보내지 않고 그 정리는 다음 `applied` 실행이 한다. `skipped` 실행의 완료·`attempts` 커밋에는 복원의 `stale_reset` 결과가 함께 들어갈 수 있으나 판정을 새로 세지는 않는다. `clock_regressed` 실행은 보내지 않는다. 웹훅이 없으면 보내지 않는다. 2xx를 받으면 `acknowledge`, 2xx가 아니거나 시간 초과·네트워크 오류면 `recordAttemptFailure`를 부르고 그 뒤 항목은 보내지 않는다.

| `acknowledge` 경우 | 결과 |
| ------------------ | ---- |
| `id`가 맨 앞 | 그 항목을 지우고 `lastDelivered = { id, kind, at: now }`. `removed` |
| `id`가 `pending`에 없음 | 바꾸지 않는다. `already_removed`. 같은 `id`를 두 번 부른 경우와 완료 push 거절 뒤 다시 받은 상태에서 이미 지워진 경우가 여기 든다. 커밋하지 않고 다시 받은 상태로 이어 간다 |
| `id`가 있지만 앞에 다른 `id`가 있음 | 바꾸지 않는다. `not_head`. 호출자는 보내기를 멈추고 실행을 실패로 끝낸다 |

완료 push가 거절되면 다시 받아 복원한 상태에 `acknowledge`를 다시 부른다(최대 2번, 기존). 끝내 실패하면 남은 항목을 보내지 않고 실패로 끝낸다. 위 순서 행에 없던 빈칸을 맨 앞 실패 규칙과 같게 채운 것이다. `attempts` push가 실패해도 판정 push로 들어간 원래 항목이 남으므로 다음 실행이 같은 `id`로 다시 보낸다.

웹훅 수신과 Git 커밋은 원자적이지 않으므로 전체를 정확히 한 번으로 만들 수 없다. 이 설계는 판정 push로 원격에 들어간 `pending`을 맨 앞부터 하나씩 FIFO로 다시 보낸다. 실제 수신은 지금 조건만으로 보장되지 않는다. 한 항목이 실제로 수신되려면 `decidedAt`부터 24시간 안이고 4건 상한에 밀려 나가지 않았으며 상태 파일이 깨지거나 초기화되거나 브랜치가 지워지지 않아야 한다. 그에 더해 앞선 항목이 모두 그 기한 안에 완료되거나 버려져 그 항목이 맨 앞이 되어야 하고 그 기한 안에 `PUBLIC_URL`과 웹훅이 설정된 실행이 보내기에 성공할 기회가 있어야 한다. 맨 앞 항목이 계속 실패하면 뒤 항목은 한 번도 보내지 않은 채 24시간 규칙으로 버려질 수 있다. 네트워크나 웹훅이 계속 실패하면 수신은 0건이다. 판정 push가 모두 거절된 실행의 판정은 원격에 없으므로 처음부터 대상이 아니다.

FIFO는 송신 호출의 순서이고 수신처가 관측하는 순서와 다르다. 응답이 불확실해 다시 보낸 항목이나 같은 키의 동시 sender가 보낸 항목은 중복되거나 늦게 도착할 수 있으므로 수신 순서까지 보장하지 않는다. 중복은 2xx 뒤 완료 push 전에 끝나거나 완료 push가 끝내 실패할 때 생긴다. 웹훅이 받았는데 응답이 시간 초과나 네트워크 오류로 끝나 실패로 기록될 때도 생긴다. 기존의 중단 한 번마다 중복 최대 1건은 그다음 실행이 보내기와 완료 push에 모두 성공한다는 가정에서만 맞는다. 불확실한 끝남이 되풀이되면 같은 `id`가 실행마다 1건씩, 그 항목이 24시간 규칙이나 상한으로 버려질 때까지 다시 갈 수 있다. 한 실행은 맨 앞 하나를 보내고 결과가 확정되지 않으면 멈추므로 실행 하나에서 같은 `id`는 최대 1건이다. 워크플로 `concurrency`를 거치지 않은 같은 키의 동시 프로세스는 같은 `id`를 함께 보낼 수 있다.

#### Git 후속 단계

첫 단계에 넣지 않는다. 별도 단계로 `tools/monitor/uptimeGit.ts`와 `tools/monitor/uptimeGit.test.ts`를 두고 계약 검토를 다시 받는다.

- 상태 ref는 `refs/heads/ops/uptime-state` 하나다. 설정된 ref가 정확히 이 값이 아니면 fetch, 확인 요청, 쓰기, 보내기를 하나도 하지 않고 실패한다. 강제 push(`--force`, `--force-with-lease`, `+` refspec)는 쓰지 않는다.
- 실행마다 새 임시 작업 폴더에서 원격의 그 ref만 받아 복원한다. 이전 실행의 clone, 캐시, 로컬 브랜치를 쓰지 않는다. 원격 조회가 성공하고 그 ref가 없다고 확인된 경우만 `restoreState`에 `raw = null`을 넘겨 초기 상태로 하고 첫 커밋은 부모가 없다. ref는 있고 받은 커밋 트리에 자기 키 파일이 없다고 확인된 경우도 그 키만 초기 상태다.
- fetch, 인증, 통신, 객체 읽기의 실패는 ref나 파일이 없다는 확인이 아니다. 이런 알 수 없는 읽기 오류면 `restoreState`를 null로 부르지 않으며 초기화, 쓰기, 보내기를 하지 않고 실패한다. 다시 계산 중의 fetch 실패도 같다.
- 판정 커밋은 읽은 커밋을 부모로 하고 그 트리에서 자기 키 파일만 바꾼다. 거절되면 다시 받아 새 커밋의 자기 키 파일로 복원하고 같은 입력으로 `observe`를 다시 부른다. 그 결과가 `skipped`이면(자기 push가 실제로 들어갔거나 더 큰 실행 ID가 먼저 들어간 경우) 판정 커밋 없이 보내기로 간다. 새 커밋의 다른 키 파일과 이력은 그대로 이어진다. prod와 drill은 키가 달라 서로의 실패를 세지 않는다.
- 판정 push가 끝내 실패하면 앞 실행이 남긴 항목도 보내지 않는다. 보내기와 ack는 위 절을 따른다.
- `applied` 실행마다 판정 커밋 1개가 생기고 `skipped`·`clock_regressed` 실행은 판정 커밋 0개다. 2xx를 받은 항목마다 완료 커밋 1개, 보내기 실패 때 `attempts` 커밋 최대 1개가 더해진다.
- 검증은 임시 폴더의 로컬 bare 저장소를 원격으로 주고 실행마다 새 node 하위 프로세스(`tools/node-cli.ts` 방식)와 새 작업 폴더를 쓴다. 시험은 DB가 필요 없으므로 `tools/monitor/*.test.ts`에 둔다. 이 시험은 Git 전이만 확인하며 실제 GitHub 원격, `GITHUB_TOKEN` 권한, 예약 실행을 확인하지 않는다.
- 이 단계의 시험은 위 검증 표의 가동 확인 상태, 상태 경합과 복구, 못 보낸 알림 인계 세 행에 더해 다음을 본다. ref가 다르면 git 호출·HTTP 요청·웹훅이 0건이다. prod와 drill을 동시에 돌리면 두 파일이 다 남고 각자 한 번씩만 센다. 판정 push가 3번 거절되면 웹훅 0건이다. 장애가 이어지는 `applied` 실행마다 판정 커밋 1개다. 더 큰 실행 ID가 먼저 들어간 뒤 옛 실행 ID로 돌리면 판정 커밋 0개이고 기존 `pending`만 위 규칙대로 보낸다. 원격 읽기를 실패시키면(없는 bare 경로, 또는 ref가 있는 bare 저장소에 시험 훅으로 주입한 fetch 실패) 초기 상태 파일을 만들지 않고 커밋 0개, 웹훅 0건, 실행 실패이며 ref가 있던 bare 저장소의 커밋은 그대로다. 인증 실패는 로컬 bare로 재현하지 않고 같은 읽기 오류 분기로 본다.

CLI `tools/monitor/uptime.ts`와 웹훅 보내기는 그다음 단계다. CLI가 읽을 환경변수 이름은 아직 정하지 않았고 그 단계 계획에서 정한다. CLI는 상태 ref를 먼저 본다. 정확히 `refs/heads/ops/uptime-state`가 아니면 git 호출, 확인 요청, 쓰기, 보내기 없이 실패한다. ref가 맞고 `PUBLIC_URL`이 비었으면 fetch, 확인, 쓰기, 보내기 없이 꺼짐 성공으로 끝난다. 시험 실행은 위 기존 문장대로 `PUBLIC_URL`을 쓰지 않는다. `PUBLIC_URL`에 path를 허용할지는 그 단계의 설정 검사로 정하며 첫 단계 adapter는 origin만 쓴다. `uptime.yml`과 실제 실행은 M2, Ops의 `/healthz`, 소유자 설정 뒤에 한다.

### Ops 건강 HTTP 정정

2026-10-24 `3290630` 기준으로 AC-M3-09 가운데 서버의 `GET /healthz`·`GET /healthz/engine` 첫 단계만 좁혀 고친다. 위 담당 표, 모니터링 표의 엔진 하트비트 행, 가동 확인 정정의 Ops 문장과 이 절이 어긋나면 이 절을 따른다. 부하(AC-M3-07), 서버 안 감시(디스크·DB 용량·웹훅 알림), 가동 확인의 상태 모듈과 probe 계약, 위의 기준값, 과거 사실과 검증 이력은 그대로 둔다. 2분·5분 기준과 `{ ok, worlds, stale }` 응답은 위 모니터링 표의 값이고 이 절은 경계, 실패 본문, 조회 방식, 파일을 정한다. 가동 확인은 정확히 200만 성공으로 보므로 아래 200·503 구분과 그대로 맞는다.

이 절의 초안은 소스만 읽어 작성한 정정안이다. 총괄이 응답 계약과 조회 방식, 경계, 파일, 검증 한계를 검토해 채택하고 구현을 배정했다. 기존 T3-11 실제 기록은 보존하며 이 단계의 구현·검증은 뒤에 따로 기록한다. 이 정정과 구현 배정은 AC 완료를 뜻하지 않는다.

대상은 `RUNNING`·`PAUSED` 월드다. 하트비트 행이 없거나 `nowMs − at > 120000` 또는 `lagMs > 300000`이면 stale이다. 정확히 120000ms와 300000ms는 정상이고 1ms 넘으면 stale이다. 한 월드는 이유가 여러 개여도 1로 센다. `at`이 `nowMs`보다 뒤인 음수 나이는 이 규칙상 stale이 아니며 새 조건을 더하지 않는다. lease 만료, heartbeat owner 추정, `lastError`는 판정에 쓰지 않는다. 확인하지 못한 수를 0으로 채우지 않는다.

본문 키는 위 셋뿐이다. 월드 ID, 오류 문구, 주소, 비밀, 상태 원문, `error` 필드는 넣지 않는다. 두 경로 모두 상태와 관계없이 `Cache-Control: no-store`를 붙인다. 새 CORS 헤더, 세션, 역할, tRPC 절차는 없다. Origin, 쿠키, query는 결과도 조회 대상도 바꾸지 않는다.

`countEngineHealth`는 `nowMs`가 유한한 정수가 아니면 `null`이다. 행의 `engineHeartbeat`가 null이면 stale이다. null이 아닌데 `at`이 `Date`가 아니거나 `getTime()`이 유한하지 않거나 `lagMs`가 정수가 아니면 한 행 때문에도 전체를 `null`로 하고 부분 집계를 내지 않는다. `worlds`는 행 수다.

엔진 조회는 이 모양이다.

```ts
const read = await db.$transaction(
  async (tx) => {
    const [row] = await tx.$queryRaw<Array<{ now: Date }>>`SELECT statement_timestamp() AS now`;
    const rows = await tx.world.findMany({
      where: { status: { in: ['RUNNING', 'PAUSED'] } },
      select: { engineHeartbeat: { select: { at: true, lagMs: true } } },
    });
    return { now: row?.now, rows };
  },
  { isolationLevel: 'RepeatableRead' },
);
```

`now`가 유효한 `Date`이면 `getTime()`으로 epoch ms를 한 번 만들어 `countEngineHealth`에 넘긴다. 아니면 `null`이다. 서버 host의 `Date.now()`와 `buildServer`의 `options.now`는 이 판정에 섞지 않는다. 정상 `at`은 DB 시각이라 host 시각과 비교하면 host와 DB의 시계 차이가 2분 경계에 그대로 들어간다. `options.now`는 세션·요청 제한용 시계다. 감독이 행을 새로 만들 때 쓰는 host 시각은 위 사실대로 이 단계에서 바로잡지 않는다. 옵션은 `isolationLevel`만 넘기고 `timeout`·`maxWait`는 Prisma 기본값 그대로다. 새 시계 환경값이나 임의 제한 시간은 만들지 않는다. 월드 ID, `lastError`, `engineLease`는 projection에 넣지 않으므로 응답에도 로그에도 원문이 닿지 않는다.

PostgreSQL 기본 READ COMMITTED는 문장마다 새 snapshot을 잡는다. schema에 `relationJoins`가 없어 Prisma가 관계 select를 월드와 하트비트 쿼리로 나눌 수 있다. 그러면 시각을 읽은 뒤와 월드 목록, 하트비트 목록 사이에 상태 전이나 하트비트 쓰기가 끼어 서로 다른 시점의 값이 섞인다. REPEATABLE READ는 트랜잭션의 첫 문장에서 snapshot을 한 번 잡고 뒤 문장이 모두 그 snapshot을 본다. 첫 문장을 `statement_timestamp()`로 두면 `now`는 snapshot을 잡은 문장의 시작 시각이고 목록과 하트비트는 같은 snapshot에서 나온다. `now()`(트랜잭션 시작 시각)는 BEGIN과 첫 문장 사이의 지연만큼 snapshot보다 앞설 수 있어 쓰지 않는다. 그 문장 시작 직후에 들어간 하트비트는 `at`이 `now`보다 조금 뒤일 수 있고 위 규칙대로 정상으로 센다.

`/healthz`는 트랜잭션 없이 `db.$queryRaw` `SELECT 1`을 부르고 예외를 잡아 위 본문을 낸다. 두 경로 모두 실패하면 오류 객체, 월드 ID, 연결 문자열 없이 고정 문장 하나만 `server.log.warn`으로 남긴다.

`server.ts`에는 `onSend` 훅이 끝난 `:107` 바로 뒤, `dummyPasswordHash`(`:108`)와 tRPC 플러그인 등록(`:110`) 전에 `registerOpsHealth(server, options.db);` 한 줄을 넣는다. root `onRequest`의 보안 헤더는 그대로 붙고 출처 검사는 `/trpc` 밖이라 걸리지 않는다. `createContext`를 거치지 않으므로 `onSend`가 `authenticate`나 쿠키 갱신을 부르지 않는다. `/sse` 경로, `/trpc`의 Origin·Content-Type 조건, 쿠키 갱신, tRPC `health`, 권한은 바뀌지 않는다. 처리기 안에서 예외를 모두 잡으므로 기존 오류 처리기의 `error` 본문은 이 경로에서 나오지 않는다.

#### 남은 증거와 한계

단위 시험은 실제 tx 대신 같은 client를 넘기므로 REPEATABLE READ snapshot, `statement_timestamp()`가 `PrismaPg`에서 `Date`로 오는지, 상태 필터가 실제로 PREOPEN·ENDED를 빼는지, `writeHeartbeat`가 쓴 실제 행의 경계를 증명하지 않는다. 실제 소켓으로 부른 응답과 가동 확인 adapter 연결도 증명하지 않는다. 그래서 이 단위 시험만으로 AC-M3-09나 위 검증 표의 엔진 하트비트 행을 완료라 쓰지 않는다.

필수 후속 증거는 셋이다. 실 PG 시험은 기존 `test:int` 관문에 `apps/server/src/ops/health.integration.test.ts` 같은 파일로 두어 DB 시각 기준 경계 행, 상태 필터, DB 중단 503을 본다. 실 HTTP 시험은 `buildServer`를 loopback에 띄워 소켓으로 두 경로를 부른다. 위 검증 표의 격리 compose 감독 정지 행도 남는다. 셋 모두 부모가 슬롯과 범위를 배정할 때 하며 지금은 허용되지 않았다. 미완료 인계로 남기며 이 정정이 공유 문서나 인수조건 상태를 바꾸지 않는다. 공개 경로라 계정 권한·제재 차이를 만들지 않지만 실제 계정 권한·제재 증거를 단위 시험으로 대체했다고 쓰지 않는다.

#### 소유 단계

상태는 `none → creating → owned { name, oid } | ambiguous → dropped`로만 움직인다. DROP은 `owned`일 때만 한다.

| 단계 | 하는 일 | 실패할 때 |
| ---- | ------- | --------- |
| S1 admin | `adminUrl`로 `pg` `Client` 연결. `error` 이벤트 수신기를 붙여 오류를 정리 목록에 넣는다 | 아래 정리 후 실패 |
| S2 이전 목록 | `SELECT datname, oid::text AS oid FROM pg_database ORDER BY datname`을 메모리에 보관 | 정리 후 실패 |
| S3 부재 확인 | CREATE 직전 `SELECT 1 FROM pg_database WHERE datname = $1`이 0행 | 1행 이상이면 CREATE하지 않고 상태 `none`으로 실패 |
| S4 CREATE | 이름을 정규식으로 다시 확인한 뒤 상태를 `creating`으로 두고 `CREATE DATABASE "<이름>"` | 예외면 서버에서 실행됐는지 알 수 없으므로 상태 `ambiguous`. 존재 확인이나 DROP을 하지 않고 이름만 남기고 실패 |
| S5 OID 기록 | CREATE 성공 직후 `SELECT oid::text AS oid FROM pg_database WHERE datname = $1`이 정확히 1행이면 상태 `owned { name, oid }` | 예외, 0행, 2행 이상이면 `ambiguous`로 보존하고 실패 |
| S6 migration | 아래 방식으로 자기 DB에 현재 migration 적용 | 정리 후 실패 |
| S7 정체성 | reader로 `current_database()`와 그 OID를 읽어 S5의 `{ name, oid }`와 같음을 확인. reader의 `application_name` 확인, `World` 0개 확인, writer·observer `SELECT 1` | 정리 후 실패 |

#### migration 적용 방식

`tools/t4-03-ext.integration.test.ts:55-60` 선례를 따른다. `readdir`로 migration 폴더를 읽어 숫자로 시작하는 이름만 골라 정렬하고 18개이며 마지막이 `20261023073000_treaties`임을 확인한다. 자기 DB 주소의 별도 `pg` `Client` 하나로 각 `migration.sql`을 `readFile`로 읽어 `client.query(sql)`로 차례로 실행한 뒤 그 client를 `end()`한다. 이 방식은 새 자기 DB에만 쓴다. `prisma migrate deploy`, `packages/db/prisma.config.ts`의 `.env` 로드, Prisma CLI, 하위 프로세스는 쓰지 않는다. 앞 준비 기록의 migrate deploy 적용 계획은 이 방식으로 바꾼다.

#### 정리

정리는 함수 하나로 두고 처음 부를 때 만든 Promise를 캐시한다(`cleanup ??= runCleanup()`). `beforeAll` 실패 경로와 `afterAll`이 같은 Promise를 기다리므로 DROP을 두 번 보내지 않는다. 정리는 먼저 저장해 둔 setup Promise가 끝나기를 기다려 setup과 겹치지 않는다. 단계마다 성공 여부와 오류 이름만 기록하고 앞 단계가 실패해도 다음 단계를 시도한다(`e2e/timelapseSeed.ts:442-488` 선례).

| 순서 | 단계 | 조건 |
| ---- | ---- | ---- |
| C1 | `app.close()` | 서버가 있을 때 |
| C2 | reader·writer·observer `$disconnect()` | 각각 따로 시도 |
| C3 | migration client `end()` | 아직 열려 있을 때 |
| C4 | 연결 0 대기 | `owned`일 때. `SELECT count(*)::int AS n FROM pg_stat_activity WHERE datid = $1::oid`를 100ms 간격 최대 50번 본다. 끝까지 0이 아니면 DROP하지 않고 보존, 실패 |
| C5 | 정체성 재확인 | 이름으로 찾은 OID가 정확히 1행이고 S5의 OID와 같을 때만 다음으로. 다르거나 없으면 보존, 실패 |
| C6 | DROP | 이름 정규식을 다시 확인하고 `DROP DATABASE "<이름>"` 한 번. `FORCE`, `IF EXISTS`, `pg_terminate_backend`는 쓰지 않는다 |
| C7 | 부재·보존 확인 | `WHERE datname = $1 OR oid = $2::oid`가 0행. S2 목록의 모든 이름·OID가 같은 OID로 남아 있음 |
| C8 | `admin.end()` | admin이 연결됐을 때 |

H08의 닫힌 포트 서버와 client는 지금처럼 그 사례의 `finally`에서 닫는다(`:255-261`). C1보다 먼저 끝나므로 C4가 그 연결을 기다리지 않는다. Probe는 요청마다 `fetch`만 쓰고 남기는 자원이 없다.

C7의 보존 판정은 이전 목록이 그대로 있는지 본다. 같은 서버를 다른 작업실이 함께 쓰므로 실행 중에 남이 만든 새 DB는 이 파일의 실패로 보지 않고 개수만 기록한다. 부모가 완전 일치를 원하면 이 한 줄만 바꾼다.

`ambiguous`, OID 불일치, 연결 0 미달이면 자기 이름 패턴의 DB가 남을 수 있다. 자동으로 지우지 않고 실패 메시지에 자기 DB 이름만 넣어 사람이 확인하게 한다. hook 제한 시간을 넘겨 setup이 멈춘 경우도 같다.

#### 오류

- setup이 실패하면 `beforeAll` 안에서 캐시한 정리를 기다린다. 정리 오류가 없으면 원래 오류를, 있으면 `new AggregateError([원래 오류, ...정리 오류], 고정 문장)`을 던진다. `afterAll`은 같은 정리를 기다리고 setup이 이미 던지지 않은 정리 오류만 `AggregateError`로 던진다. 사례 실패는 Vitest가 따로 보고하므로 정리가 가리지 않는다.

## 2026-10-29 분리한 가동 확인 드릴

`uptimeDrill.ts`는 자기 loopback HTTP 서버와 분리한 자식 CLI로 기존 가동 확인을 실행한다. 입력은 ASCII 영숫자·밑줄·하이픈 1~64자의 연습 키와 HTTP200 또는500이다. 빈 입력·부분 입력·다른 상태값은 실패한다. 운영 URL과 웹훅을 연습 자식에게 넘기지 않으며 `drill-`로 시작하는 자기 키만 기존 상태 ref에 저장한다. 운영 `prod`와 다른 키의 바이트는 보존한다. 저장의 중복·충돌·실패는 기존 CAS 규칙과 유한 기한으로 처리하고 자기 HTTP 연결·서버와 Git 자식을 정리한다. 정리 실패도 실행 실패다.

워크플로의 입력 없는 실행은 기존 운영 경로를 쓰고 입력이 있으면 연습 경로만 쓴다. 둘은 별도 concurrency로 취소 없이 직렬화한다. main 제한·정확 SHA checkout·토큰의 환경 전달·강제 push 금지는 유지한다. 새 입력으로 운영 주소를 임의 HTTP 서버로 바꿀 수 없다.

독립 코드 리뷰를 받은 7파일의 실제 CLI/HTTP/bare Git 집중 검사는 8파일147건159초에 통과했다. 초기 격리 Linux 검사는12건 중 실제 pre-receive hook 거부 반례1건이 실패했다. 같은 설정의 `/tmp`가 `noexec`임을 실제 mount 목록과 실행 권한이 있는 자기 hook의 Permission denied/종료126으로 재현했다. 시험 전용 `/tmp`에 `exec`를 명시한 다음 원래 소스·단언·기한을 보존한 Linux12건이10.60초에 통과했다. UID10001·네트워크 없음·읽기 전용 root·capability 제거·no-new-privileges는 유지했다. 실패 기록을 보존했고 비구현 담당이 정확 HEAD/7파일 해시와 집중·Linux 근거를 독립 승인했다.
