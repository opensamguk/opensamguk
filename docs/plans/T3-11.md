### main 기준 사실 (2026-10-22, `76d56d0`)

계획을 쓴 2026-10-20 뒤로 T3-04(요청 제한·CSRF·세션 갱신), T2-22·T2-23 순위, T1-16 메인 화면(D-020)이 main에 들어왔다. 부하 시나리오와 감시는 아래 실제 코드에 맞춘다.

- 가입은 같은 IP에서 1시간에 10번(`apps/server/src/routers/auth.ts:32-35`), 로그인은 같은 IP에서 15분에 30번(`:58`)만 받는다. 생성기는 IP 하나에서 나가므로 계정 218개를 API로 만들거나 로그인할 수 없다. 준비 단계는 기존 시험처럼 격리 DB에 계정과 세션을 바로 만든다(`newSession` `apps/server/src/auth/session.ts:8-11`, 같은 방식 `tools/authz.integration.test.ts:66-69`, `e2e/account.ts:5-7`). 서버의 한도는 그대로 켜 둔다. 한도를 끄는 설정이나 시험용 우회 경로는 만들지 않는다.
- 부하 장수 109명은 계정마다 `general.create`로 만든다. 이 요청은 `InputEvent`를 남기고 `pending`을 돌려줄 수 있다(`apps/server/src/routers/general.ts:56`, `:93`). 준비 단계는 엔진이 모두 반영할 때까지 기다린 뒤 준비 운동을 시작한다.

- 요청 구성의 절차는 지금 이렇게 맞춘다. 메인 요약은 D-020 메인 화면이 부르는 `home.get`과 `world.summary`(`apps/web/src/turns/TurnEditor.tsx`), 지도 `world.map`, 도시 `city.get`, 국가 `nation.get`, 예턴 조회 `turns.get`, 예턴 저장 `turns.set`, 순위 `ranking.generals`·`ranking.nations`(`apps/server/src/routers/ranking.ts:33`, `:63`), 로비 `world.list`다.
- 메시지 목록·보내기와 SSE는 main에 절차가 없다(`apps/server/src/router.ts:14-35`). 모두 T2-09가 만든다. T3-11의 선행 M2에 T2-09가 있으므로 AC 증거 실행(`load-m3.yml`)은 T2-09 병합 뒤에만 한다. 그 전에 가까운 조회로 바꾼 실행은 도구 확인일 뿐이며 AC 증거로 세지 않는다.

- 2026-10-22 이 계획을 고친 작업 노드는 macOS다. `/proc`과 cgroup v2가 없으므로 공유 호스트 모드로 판정되고 예약 수단이 없어 `pool_unconfigured`로 거부된다. 지금은 어느 공유 노드에서도 로컬 부하를 시작하지 않는다.

### 실행 장소와 자원 입장 심사

같은 호스트를 다른 프로젝트와 함께 쓴다. 이 호스트의 공용 자원 규칙은 CPU·메모리 80% 한도, 디스크 8GiB 예비, cgroup 여유, 시작 예약이다. 고정된 호스트 여유 숫자 하나만 보고 시작하지 않는다. 실행에 들어가는 모든 것을 더한 예산으로 심사를 받는다.

계획 시점(2026-10-20)에 이 호스트는 2 vCPU·메모리 7.9GiB였다. 측정 실행의 합산 예산(대상 2 vCPU·4GiB + 생성기 1 vCPU·1GiB = 3 vCPU·5GiB)은 이 호스트의 코어 수보다 크므로 심사를 통과할 수 없다. 그래서 장소를 나눈다.

| 실행 | 장소 | 합산 예산 |
| ---- | ---- | --------- |
| `pnpm load:m3` (AC 증거) | GitHub 표준 실행기 `ubuntu-24.04` (공개 저장소 기준 4 vCPU·16GiB). `.github/workflows/load-m3.yml`을 `workflow_dispatch`로만 돌린다. 공개 저장소의 표준 실행기라 새 비용이 없다. 실행기 사양도 아래 심사로 실제 값을 확인한다. 4 vCPU에서 3 vCPU 예산은 80% 한도 안에 겨우 들어가므로 준비 단계가 끝난 뒤 `--wait 10`으로 CPU 평균이 내려오기를 기다려 심사한다 | 측정 3 vCPU·5GiB·디스크 5GiB |
| `pnpm load:smoke` | `load-smoke.yml`로 GitHub 표준 실행기. 이 호스트에서는 아래 공용 풀 예약 수단이 생긴 뒤에만 | 제한을 줄인 compose: postgres 0.5 vCPU·1GiB, server 0.25 vCPU·512MiB, engine 0.25 vCPU·512MiB, 생성기 0.25 vCPU·512MiB. 합 1.25 vCPU·2.5GiB·디스크 3GiB |
| 이미지 빌드·의존성 설치 (두 실행의 준비) | 실행과 같은 곳 | 측정과 따로 먼저 심사한다. 1 vCPU·2GiB·디스크 4GiB |

T2-19 운영 서버 사양과 생성기를 더한 예산이 표준 실행기에도 들어가지 않으면 더 큰 유료 실행기를 쓰지 않는다. 멈추고 사용자에게 묻는다.

심사는 `tools/load/admission.ts`가 한다. `docker build`와 `docker compose up`을 부르기 전에 돈다.

- 실행 모드는 공유 호스트와 GitHub 실행기 둘이다. GitHub 모드는 인자 `--site github-hosted`와 두 변수 `GITHUB_ACTIONS=true`·`RUNNER_ENVIRONMENT=github-hosted`가 함께 있을 때만이다. 이 인자는 `load-m3.yml`·`load-smoke.yml`만 넘긴다. 인자는 있는데 두 변수 중 하나라도 다르면 `site_mismatch`로 거부한다. 인자가 없으면 변수와 관계없이 공유 호스트 모드다. 설정이 빠졌다고 GitHub 모드가 되는 경로는 없다.
- 예산은 그 실행의 compose 파일에서 서비스마다 `cpus`·`mem_limit`을 읽어 더한다. 제한이 없는 서비스가 하나라도 있으면 거부한다. 준비 단계는 위 표의 준비 예산으로 따로 심사한다.
- 통과 조건은 아래를 모두 만족하는 것이다. 한도는 `LOAD_ADMISSION_CPU_PERCENT`·`LOAD_ADMISSION_MEMORY_PERCENT`(기본 80), 디스크 예비는 `LOAD_ADMISSION_DISK_RESERVE_MIB`(기본 8192), 자기 시작 예약은 128MiB다.

  | 항목 | 조건 | 거부 사유 |
  | ---- | ---- | --------- |
  | CPU | 예산 vCPU ≤ 코어 수, 그리고 `(한도% − 최근 1분 평균 CPU%) × 코어 수 ÷ 100 ≥ 예산 vCPU` | `cpu_limit` |
  | 메모리 | `MemAvailable − MemTotal × (1 − 한도%) − 남이 잡은 시작 예약 − 128MiB ≥ 예산 메모리` | `memory_limit` |
  | 시작 예약 | 공유 호스트 모드: 아래 공용 풀 예약으로 합산 예산을 먼저 확보한다. 남이 잡은 예약은 위 메모리 식에 뺀다. 예약 수단 설정이 없으면 `pool_unconfigured`, 풀 상태 조회가 실패하면 `pool_unavailable`, 풀 표본이 2분보다 오래되면 `pool_stale`, 예약이 거절되면 `pool_reservation_denied`. GitHub 모드: 1회용 VM이라 남의 예약을 0으로 본다 | 왼쪽 사유 중 하나 |
  | cgroup | 컨테이너가 들어갈 부모 cgroup(docker 기본 `system.slice`)과 명령을 띄운 cgroup 각각에서 `memory.max − memory.current ≥ 예산 메모리`(값이 `max`면 호스트 값으로 본다), `cpu.max` 할당 ≥ 예산 vCPU, `memory.pressure`의 some avg10 < 10, full avg10 < 1 | `cgroup_headroom` |
  | 디스크 | docker 데이터 경로와 `.load-reports/`가 있는 파일시스템 각각의 여유 − 디스크 예비 ≥ 예산 디스크. GitHub 실행기는 1회용 VM이라 예비를 2048MiB로 준다 | `disk_reserve` |

- 통과하면 판정, 표본, 공유 호스트 모드의 예약 번호를 `.load-reports/<runId>/admission.json`에 쓰고 띄운다. 공유 호스트 모드에서는 예약을 잡기 전에 아무것도 띄우지 않는다.
- 실행 중에도 5초마다 같은 표본을 남기고 메모리 여유가 0이 되거나 컨테이너가 OOM으로 죽으면 그 실행을 무효로 하고 자기 프로젝트만 내린다. 이 관찰과 정리는 예약을 대신하지 않는다.
- 거부되면 아무것도 띄우지 않는다. 종료 코드 75와 거부 사유 하나를 출력한다. `--wait <분>`을 주면 1분마다 다시 심사하고 그 시간이 지나면 같은 코드로 끝난다. 다른 작업을 멈추거나 남의 프로세스·컨테이너에 신호를 보내지 않는다. 실행 담당은 자원 부족 대기로 보고하고 다른 작업을 한다.

격리 조건은 장소와 관계없이 같다.

- compose 프로젝트 이름 `opensamguk-load-<runId>`로 postgres·server·engine 감독·부하 생성기를 따로 띄운다. 포트는 모두 `127.0.0.1`의 빈 포트, DB 이름은 `opensamguk_load_<runId>`다. 개발 DB와 공용 `opensamguk_test`를 쓰지 않으므로 공용 DB 시험 잠금을 잡지 않는다.
- 대상 시스템 제한은 T2-19에서 정한 운영 서버 사양과 같게 둔다. 사양이 정해지기 전에는 기준값 2 vCPU·4GiB(postgres 1 vCPU·2GiB, server 0.5 vCPU·1GiB, engine 0.5 vCPU·1GiB)로 돌리고 리포트에 적는다. 부하 생성기는 따로 1 vCPU·1GiB다.
- 실행 중 5초마다 호스트 CPU를 기록한다. 우리 컨테이너 밖 사용률 때문에 호스트가 90%를 넘은 구간이 있으면 그 실행은 오염으로 보고 다시 돈다.
- 끝나면 `docker compose -p opensamguk-load-<runId> down -v`로 자기 프로젝트만 지운다. 실행 전체는 20분을 넘기지 않는다.

### 공유 호스트의 공용 풀 예약

2026-10-20에 이 호스트에서 확인한 공용 풀의 모습이다.

- 호스트 하나의 잠금 아래 예약 원장을 두고 작업자와 하위 에이전트가 시작할 때마다 고정 크기 384MiB의 시작 예약을 잡는다. 예약의 주인은 프로세스 번호, 프로세스 시작 시각, 부팅 ID다. 주인 프로세스가 끝나거나 재부팅하면 원장에서 지워지고 작업자는 시작 뒤 약 30초 안에 예약을 푼다. 예약 합계는 공개 상태 파일의 `startupReservedMiB`와 표본 시각으로 나온다.
- 바깥 명령이 임의 크기(vCPU·메모리·디스크)의 예약을 잡는 공개 수단은 없다. 예약에서 실제 사용량을 빼는 계산도 작업자 cgroup 아래만 본다. docker 컨테이너는 `system.slice`에서 돌므로 이 계산에 들어가지 않는다.
- 상태 파일을 읽고 빼기만 하면 두 시작자가 같은 여유를 보고 함께 시작할 수 있다. 그러므로 지금 이 호스트에는 부하·리허설의 합산 예산을 확보할 수단이 없다.

그래서 이렇게 정한다.

- 아래 계약을 만족하는 예약 수단이 이 호스트에 생기고 그 연결이 리뷰를 통과하기 전까지, 공유 호스트 모드의 심사는 항상 거부한다(설정이 없으면 `pool_unconfigured`). 이 호스트의 `pnpm load:smoke`와 [T3-14](./T3-14.md) A는 자원 대기로 두고 시작하지 않는다. 도구 검증은 GitHub 모드와 아래 가짜 풀 시험으로 한다.
- 예약 수단이 갖출 계약:

  | 항목 | 계약 |
  | ---- | ---- |
  | 원자성 | 호스트 하나의 잠금 안에서 새 표본, 남의 예약 합, 자기 합산 예산을 한 번에 비교하고 통과할 때만 예약을 기록한다. 비교와 기록 사이에 다른 시작자가 끼지 못한다 |
  | 주인 | 실행 내내 살아 있는 `tools/load` 프로세스. 프로세스 번호, 시작 시각, 부팅 ID로 식별한다 |
  | 수명 | 준비 단계의 `docker build` 전에 잡고 자기 프로젝트의 `down -v`가 끝난 뒤 푼다. 상한은 실행 상한 20분에 정리 5분을 더한 25분이다. 준비와 측정 예산이 다르면 큰 쪽으로 잡는다 |
  | 계산 | 예약이 살아 있는 동안 예산 전체를 남이 쓴 것으로 보이게 한다. 컨테이너의 실제 사용량을 빼지 않는다. 이중 계산은 거부 쪽으로만 틀린다 |
  | 해제 | 정상 종료, 실패, 신호 모두 정리 뒤 푼다. 주인이 강제 종료되면 원장이 예약을 지운다. 그때 남은 자기 컨테이너는 `mem_limit` 안에서 호스트 표본에 실제 사용량으로 잡히고 실행 담당이 `admission.json`의 프로젝트 이름으로 자기 것만 내린다 |
  | 상태 | 예약 결과와 표본 시각을 돌려준다. 표본이 2분보다 오래되었거나 원장을 읽지 못하면 예약하지 않는다 |

- 이 수단은 오픈삼국 저장소 밖 호스트 공용 풀의 일이며 이 계획에서 만들지 않는다. 총괄에게 호스트 공용 풀 담당 배정을 요청한다. 수단이 생기면 연결 방법(명령 이름과 설정 이름)을 이 절에 더하고 다시 리뷰받는다.

### 재현 명령

```sh
pnpm load:m3 --run <runId>            # 띄우기 → 준비 → 2분 준비 운동 → 15분 측정 → 리포트 → 정리
pnpm load:m3 --run <runId> --keep     # 정리하지 않고 남김 (원인 조사용, GitHub 모드에서만)
pnpm load:report .load-reports/<runId> # 저장된 원자료로 리포트 다시 계산
pnpm load:smoke                        # 월드 2개 × 동시 접속 10 × 1분, 도구가 깨지지 않았는지만 본다
```

- `--keep`은 공유 호스트 모드에서 거부한다. 예약 주인인 도구 프로세스가 끝난 뒤에도 컨테이너가 남기 때문이다.
- 원자료와 JSON 리포트는 `.load-reports/<runId>/`(Git 제외)에 남는다. 커밋 SHA, 실행 장소, 제한값, 자원 심사 결과(`admission.json`), 호스트 정보, 측정값, 판정을 담는다. `load-m3.yml`은 이 폴더를 Actions 산출물로 올린다.
- `load-smoke.yml`은 `workflow_dispatch`로만 도는 GitHub 표준 실행기 작업이다. 판정은 하지 않고 도구가 끝까지 도는지만 본다. PR마다 돌리지 않는다.
- AC 증거는 `load-m3.yml` 실행의 판정 요약을 `docs/architecture/performance.md`에 옮긴 표(명령, 실행 ID, SHA, 실행 장소, 제한값, 심사 판정, p95, 최대 지연, 오류 수)다. 원자료 파일은 커밋하지 않는다.

### 모니터링

알림은 T2-15의 운영 디스코드 웹훅(`OPS_DISCORD_WEBHOOK_URL`)과 같은 중복 규칙을 쓴다. 같은 알림은 30분에 한 번이고 문제가 이어지면 30분마다 다시 1건, 회복하면 회복 알림 1건이다. 이 규칙을 판단하는 상태를 어디에 두는지는 감시마다 다르다.

- 서버 안 감시(엔진 하트비트, 디스크, DB 용량)는 서버 프로세스 하나에서 계속 도는 T2-15 감시 작업이 한다. 상태는 그 작업의 메모리에 둔다. 서버가 재시작되면 상태가 비므로 문제가 이어지는 중이면 알림이 1건 더 갈 수 있다. 이 차이를 release-operations §7에 적는다.
- 사이트 가동 확인은 실행마다 새 GitHub 실행기에서 돈다. 파일과 메모리가 다음 실행에 남지 않으므로 아래 상태 저장소를 쓴다.

| 감시 | 방법 | 알림 조건 |
| ---- | ---- | --------- |
| 사이트 가동 | `.github/workflows/uptime.yml`이 10분마다 GitHub 표준 실행기에서 `tools/monitor/uptime.ts`로 공개 주소의 `/healthz`와 `/healthz/engine`을 부른다. 서버가 통째로 죽어도 서버 밖에서 알 수 있다 | 서로 다른 실행에서 연속 2번 실패 (아래 상태 저장소). 저장소 변수 `PUBLIC_URL`이 비어 있으면 아무것도 하지 않고 성공으로 끝난다 |
| 엔진 하트비트 | 서버에 `/healthz/engine`을 더한다. RUNNING·PAUSED 월드의 `EngineHeartbeat`가 2분 넘게 없거나 지연이 5분을 넘으면 503. 응답은 `{ ok, worlds, stale }` 개수만 주고 월드 ID·오류 내용은 주지 않는다. 5분 정지 알림은 T2-15 것을 그대로 쓴다 | T2-15 규칙 |
| 디스크 | 서버 감시 작업이 5분마다 `fs.statfs`로 `MONITOR_DISK_PATHS`(postgres 데이터, 백업 폴더)를 본다 | 사용률 80% 경고, 90% 위험 |
| DB 용량 | 같은 작업이 `pg_database_size(current_database())`를 읽는다 | `DB_SIZE_WARN_BYTES` 이상 경고 |

- 임계값과 주기는 환경변수로 바꾸며 시험은 짧은 값을 주입한다. 알림 본문에 비밀값·이메일·웹훅 주소를 넣지 않는다.
- GitHub 쪽 웹훅은 저장소 비밀 `OPS_DISCORD_WEBHOOK`에 둔다. 비밀과 변수 등록은 소유자가 하며 등록 전에는 감시가 꺼진 상태다.

### 가동 확인의 실행 간 상태

연속 실패 수, 30분 중복 억제, 아직 보내지 못한 알림을 서로 다른 GitHub 실행 사이에서 이어 가려고 저장소 안에 상태를 둔다. 새 서비스나 비용은 쓰지 않는다. `tools/monitor/uptimeState.ts`가 읽기·쓰기를 맡는다.

| 항목 | 결정 |
| ---- | ---- |
| 저장소 | 같은 GitHub 저장소의 전용 브랜치 `ops/uptime-state`. main과 이력을 공유하지 않는 orphan 브랜치이며 상태 파일만 담는다 |
| 키 | 파일 경로 `uptime/<key>.json`. 예약 실행과 입력 없는 수동 실행은 `prod`. 시험 실행(`workflow_dispatch` 입력 `drill_key`)은 `drill-<drill_key>`이며 `prod` 파일을 건드리지 않는다 |
| 값 | `{ version: 1, consecutiveFailures, alerting, lastAlertAt, lastRecoveryAt, updatedAt, lastRunId, pending, lastDelivered }`. 앞의 값들은 확인 결과로 정한 판정 상태다. `pending`은 판정이 만들었지만 발송 완료를 아직 기록하지 못한 알림의 목록이고 항목은 `{ id, kind, decidedAt, decidedRunId, attempts, lastAttemptAt }`이다. `kind`는 `down` 또는 `recovery`, `id`는 `<key>:<kind>:<실행 ID>.<실행 시도 번호>`로 한 번 정하면 바뀌지 않는다. `lastDelivered`는 마지막으로 완료를 기록한 `{ id, kind, at }`이다. `consecutiveFailures`는 0~2이고 2에서 멈춘다. 그래서 장애가 이어져도 실행마다 커밋이 생기지 않고 값이 바뀔 때만 쓴다. 주소, 웹훅, 응답 본문은 넣지 않는다 |
| 쓰기 권한 | `uptime.yml`의 감시 작업 하나만 `permissions: contents: write`이고 그 밖은 read다. 저장소 기본 워크플로 권한은 지금처럼 read로 둔다. 스크립트는 `refs/heads/ops/uptime-state` 하나에만 push하며 다른 ref가 설정되면 시작하지 않는다. main은 기존 보호 규칙(필수 검사)으로 막혀 있다. `GITHUB_TOKEN`으로 한 push는 새 워크플로를 띄우지 않으므로 상태 커밋마다 CI가 돌지 않는다 |
| 직렬화 | 워크플로 `concurrency: uptime-<key>`, `cancel-in-progress: false`로 같은 키의 실행은 하나씩 돈다. push는 읽은 커밋을 부모로 하는 fast-forward만 하고 강제 push는 하지 않는다. 거절되면 다시 받아 같은 확인 결과로 새 상태를 다시 계산하고 2번까지 재시도한다. 다시 계산할 때 받은 상태의 `pending`은 그대로 이어받는다. 그래도 거절되면 알림 없이 실패로 끝난다 |
| 판정 | 실패는 `/healthz`나 `/healthz/engine`이 10초 안에 200이 아닌 것이다. 실패면 `consecutiveFailures`를 1 올린다. 2가 되었고 `alerting`이 아니거나 `lastAlertAt`에서 30분이 지났으면 `pending`에 장애 1건을 더하고 `alerting = true`와 `lastAlertAt`을 바꾼다. 단, `pending`의 마지막 항목이 아직 못 보낸 장애이면 30분 재알림은 더하지 않고 `lastAlertAt`도 그대로 둔다. 성공이면 `consecutiveFailures = 0`이고 `alerting`이었으면 `pending`에 회복 1건을 더하고 `alerting = false`와 `lastRecoveryAt`을 바꾼다 |
| 순서 | 확인 → 판정 상태와 `pending` 계산 → 상태 push → `pending`을 오래된 것부터 한 건씩 보내기 → 한 건이 2xx를 받을 때마다 그 항목을 지우고 `lastDelivered`를 바꾼 커밋을 push. 보내는 실행은 방금 상태 push에 성공한 실행뿐이다. 판정 상태는 되돌리지 않는다. 앞선 실행이 남긴 `pending`도 이번 확인 결과와 관계없이 같은 차례에 보낸다. 그래서 회복 판정 뒤 계속 정상이어도 못 보낸 회복은 다음 실행이 보낸다. 보내기가 실패하면 그 항목의 `attempts`·`lastAttemptAt`을 올린 커밋을 push하고(이 push가 실패해도 넘어간다) 남은 항목은 보내지 않은 채 실행을 실패로 끝낸다. 완료 push가 거절되면 다시 받아 그 `id`가 남아 있으면 지우는 것으로 2번까지 재시도한다 |
| 전달 보장 | 적어도 한 번이다. 웹훅 수신과 Git 기록을 한 트랜잭션으로 묶을 수 없으므로 정확히 한 번은 약속하지 않는다. 상태 push 뒤 보내기 전에 끝나거나, 보내기 실패 뒤 `attempts` push까지 실패해도 앞서 push한 `pending`이 남아 다음 실행이 보낸다. 웹훅이 받은 뒤 완료 push 전에 끝나거나 완료 push가 끝내 실패하면 다음 실행이 같은 `id`로 다시 보낸다. 이런 중단 한 번마다 중복은 최대 1건이다. 본문에 `id`를 넣어 같은 알림임을 알아볼 수 있게 한다. 유실은 상태 파일이 깨졌거나 브랜치가 지워진 경우, `pending`이 4건을 넘어 가장 오래된 것을 버린 경우, 24시간 넘게 보내지 못한 항목을 버린 경우뿐이며 모두 실행 요약에 경고를 남긴다 |
| 복구 | 브랜치나 파일이 없으면 초기 상태(0, `alerting = false`)로 보고 처음 쓸 때 만든다. JSON이 깨졌거나 `version`이 다르면 실행 요약에 경고를 남기고 초기 상태로 본다. `updatedAt`이 60분보다 오래되었으면(예약이 밀리거나 꺼졌던 경우) `consecutiveFailures`만 0으로 되돌리고 `alerting`과 `pending`은 유지해 회복 알림을 잃지 않는다 |
| 꺼짐 | `PUBLIC_URL`이 비어 있으면 확인도 상태 쓰기도 하지 않는다. 웹훅 비밀이 없으면 판정 상태는 같은 규칙으로 쓰되 `pending`에 더하지 않고 실행 요약에 판정과 알림 대상 없음을 남긴다. 이미 있던 `pending`은 보내지 않고 두며 24시간 규칙을 따른다 |

- 공개 저장소의 예약 워크플로는 저장소 활동이 60일 없으면 GitHub가 끈다. 이 점과 다시 켜는 방법을 release-operations §7에 적는다.
- 예약 실행은 기본 브랜치(main)의 워크플로만 돈다. main에 병합되기 전의 확인은 아래 시험 실행으로 한다.
- 시험 실행은 `workflow_dispatch` 입력 `drill_key`와 `drill_status`(200 또는 500)를 받는다. 실행기 안 `127.0.0.1`에 그 상태를 돌려주는 가짜 서버를 띄워 확인하고 `PUBLIC_URL`과 웹훅 비밀은 쓰지 않는다. 판정은 실행 요약에만 남긴다.
