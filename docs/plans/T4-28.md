## 0. 이 문서의 위치

명세 §6 T4-28 행을 적는다. 경매 열기·입찰은 즉시 행동이라 API가 InputEvent로만 기록하고 엔진이 처리한다(C4). 마감은 사람이 보내는 입력이 아니라 시계에 따른 처리이며 T4-27 안(AU-1 (가))대로 월간 정산 트랜잭션 안에서 일어난다. 그래서 입찰금 선차감과 이전 최고 입찰자 환불은 입찰 입력의 트랜잭션, 낙찰·대금·유찰 환급은 월간 정산 트랜잭션 하나에 각각 들어간다(C15 같은 트랜잭션 범위, C5).

착수 조건은 이 문서의 G-03 수용, T4-27 결정과 구현 병합, T4-49 상세 계획의 G-03 수용과 §6 쟁점 합의, T4-23 병합, AC-P2-14의 정식 반영, §2.7 켜짐 일반화의 소유 결정과 그 계약의 G-03 수용, T2-26 병합이다. AU-1에서 실제 시각 마감을 고르면 §2.5를 다시 쓴다.

## 계획 (Claude)

### 목표

- 경매를 켠 월드에서 장수가 경매를 열고 입찰하면 C15 계약의 InputEvent로 기록된다. 엔진이 처리해 `APPLIED` 또는 이유 코드가 있는 `REJECTED`로 끝난다. 입찰금 차감과 이전 최고 입찰자 환불은 그 입력과 한 트랜잭션에 저장된다.

## 2. 계약

### 2.1 저장

경매 상태는 T4-27의 `auction` 조각 하나이며 T4-03 `WorldExtSlice` 행(key `auction`)에 저장한다. 지난 경매 결과는 조각의 `closed`(최근 30건)에 둔다. 그래서 schema와 migration을 고치지 않는다. 명세 C8의 S5 자리는 쓰지 않는다. 더 오래된 결과를 보여야 하면 그때 따로 표를 계획한다(T28-Q1).

### 2.2 즉시 행동 kind

| kind | payload (zod strict) | 판정 (T4-27) | 있을 때 |
| ---- | -------------------- | ------------ | ------- |
| `auction.open` | `{ kind: 'sell_rice' \| 'buy_rice'; amount; startBid; finishBid; closeMonths }` (모두 양의 정수) | `openAuction` | AU-2가 장수가 여는 경매를 넣을 때 |
| `auction.bid` | `{ auctionId; amount }` (양의 정수) | `placeBid` | 늘 |

- 행위 장수는 InputEvent `userId`로 처리 때 다시 찾는다. 접수 때 `generalId`와 다르면 `ACTOR_CHANGED`(T4-20과 같다).
- `applyAuctionInput(state, kind, payload, { generalId, tick, sequence })`가 판정을 부르고 `{ state, result }`를 낸다. 엔진과 순수 재생이 이 함수 하나를 부른다. 난수를 쓰지 않는다.
- result: `APPLIED` `{ auctionId; closeTick; refunded: { generalId: number; amount: number } | null }`, `REJECTED` `{ code; message }`. 처리 tick과 sequence는 result에 넣지 않고 공통 처리기가 InputEvent `tick`·`sequence` 열에 쓴다(T2-26 6단계). 코드는 T4-27 `AuctionCode`에 처리기 재검사 코드(`WORLD_CLOSED`, `ACTOR_INACTIVE`, `ACTOR_CHANGED`)를 더한 것이다. 기능 `auction`이 꺼진 월드의 `FEATURE_DISABLED`만 공통 처리기가 낸다(T2-26 4단계). 월드 상태 판정은 T2-26 공통 처리기의 몫이 아니라 처리기 몫이다(`general.create` 처리기가 지금 `inputs.ts:37`의 `WORLD_CLOSED`를 그대로 옮기는 것과 같다).

### 2.3 API (`auction` 라우터)

```ts

type AuctionRow = {
  id: number;
  kind: 'sell_rice' | 'buy_rice' | 'equipment';
  host: { id: number; name: string } | null; // null은 중립 경매
  lot: { resource: 'gold' | 'rice'; amount: number } | { equipmentKey: string; name: string };
  pay: 'gold' | 'rice';
  startBid: number;

  closes: { tick: number; year: number; month: number }; // 마감하는 월간 정산의 연월
  extendable: boolean; // 연장 상한까지 남았는지

};
type InputOutcome = { status: 'applied'; requestId: string; auctionId: number } | { status: 'pending'; requestId: string };
```

### 2.4 엔진 입력 처리

`apps/engine/src/auction.ts`가 kind 처리기를 T2-26 `QueuedInputHandler` 꼴로 등록한다. [T4-20](./T4-20.md) 2.4와 같은 순서다. 월드 상태 검사(아래) → 계정 `ACTIVE`·장수 일치 재검사 → `loadWorld` → `applyAuctionInput(state, kind, payload, { generalId, tick: context.tick, sequence: context.sequence })` → 성공이면 T4-03 `writeWorldExtChanges`로 `auction` 행과 장수 행(입찰자 차감, 이전 입찰자 환불, 열 때 주최자 차감)을 쓰고 `{ status: 'APPLIED', result, generalId }`를 돌려준다. 실패면 상태를 쓰지 않고 `{ status: 'REJECTED', result }`. 처리기는 InputEvent를 쓰지 않는다. 종료 상태·sequence·tick·result는 공통 처리기가 `status: 'PENDING'` 조건 갱신 한 번으로 쓴다. 모두 한 트랜잭션이다.

월드 상태 검사는 [T4-20](./T4-20.md) 2.4의 1단계와 같다. 잠근 World 행의 `status`가 `RUNNING`이 아니면 게임 상태를 읽거나 쓰지 않고 `{ status: 'REJECTED', result: { code: 'WORLD_CLOSED', message } }`를 돌려준다. T2-26 C2에서 공통 처리기가 처리기를 부르는 RUNNING 밖 걸음은 PREOPEN, ENDED, 경계를 넘기지 않은 PAUSED다. 그래서 종료 뒤 남은 PENDING 입찰과 열기는 이 검사로 거절되어 `afterEnd`로 간다. 경계를 넘긴 PAUSED 월드의 입력은 공통 처리기가 부르지 않아 PENDING으로 남는다.

장수 행 쓰기는 T2-26 5단계(처리기가 게임 상태와 자기 표를 쓴다)대로 이 처리기가 한다. 판정 전후 상태를 비교해 금·쌀이 바뀐 장수 행만 갱신한다. 월간 저장의 장수 갱신(`apps/engine/src/monthly.ts:47-51`)과 같은 비교 꼴이다(쟁점 T28-Q2).

### 2.5 마감

- 마감은 T4-27 `settleAuctions`가 `runMonthly` 안에서 한다. 엔진 `persistMonthly`(`monthly.ts:24-79`)는 이미 바뀐 장수 행을 같은 트랜잭션에 쓰고(`:47-51`), T4-03이 `ext` 행 쓰기를 더한다. 그래서 낙찰·대금·유찰 환급은 별도 코드 없이 월간 트랜잭션 하나에 들어간다.
- 순수 재생도 같은 `runMonthly`를 부르므로(`packages/rules/src/replay.ts:59`) 마감이 재생된다.
- 엔진이 밀려 한 번에 여러 달을 처리해도 달마다 `runMonthly`가 한 번씩 돌고 그 달 경계 tick으로 닫는다. 마감 tick이 지난 경매 입찰은 처리 때 `CLOSED`로 거절된다.
- 입력과 월간의 순서는 [T2-26](https://github.com/opensamguk/opensamguk/pull/220) C2(`fa516aa` `docs/plans/T2-26.md` 224~230줄)를 따른다. 형식 3 월드의 RUNNING 걸음에서 그 걸음의 tick이 다음 월 경계 이상이면(`catchUp`) 입력을 처리하지 않고 경계 앞의 밀린 턴과 월간 정산을 먼저 처리한다. 경계 앞이면 지금처럼 입력이 먼저다.
- 그래서 경계를 넘긴 엔진에서는 마감 달의 월간 정산이 PENDING 입찰보다 먼저 닫는다. 입찰은 그다음 걸음에서 새 월 창 안의 tick으로 판정되고 그 경매가 이미 닫혔으면 `CLOSED`로 거절된다. 접수가 마감 전이었어도 엔진 처리가 경계 뒤면 거절된다. 판정 기준은 접수 시각이 아니라 처리 tick이며 재생도 기록된 그 tick(archive 3 `input.tick`)을 쓴다.
- 형식 3이고 PAUSED이면서 월 경계를 넘긴 월드(`monthlyTick + TICKS_PER_MONTH ≤ clockTick`)에서는 입력을 처리하지 않고 PENDING으로 둔다. 재개 뒤 정산이 먼저다. ENDED 월드의 입력은 거절되어 `afterEnd`로 간다.
- 이 순서가 지켜지면 대기 입력의 처리 tick은 늘 재생 상태의 월 창(`monthlyTick ≤ tick < monthlyTick + TICKS_PER_MONTH`) 안이다. T2-26 재생 검사 F15가 이것을 확인한다.

### 2.6 재생

순수 재생은 T2-26 `InputKindDefinition`에 두 kind를 `{ feature: 'auction', route: 'queued', apply }`로 등록한다. `apply`는 APPLIED만 받고 기록된 `input.sequence`와 `input.tick`으로 `applyAuctionInput`을 다시 불러 같은 result인지 확인한다. 처리 tick의 월 창 검사는 T2-26 F15가 같은 `input.tick`으로 한다. result에 tick이 없어 두 값이 어긋날 자리가 없다. 마감은 월간 정산 재생으로 따라온다.

### 2.7 경매 기능만 켠 월드의 저장·복원·재생

경매 조각을 만들기만 하면(T27-Q2) 그 월드를 저장하고 다시 읽을 수 없다. T4-03 원고가 확장 켜짐을 명령 목록 하나로만 보기 때문이다.

| T4-03 계약 | 내용 | 경매만 켜고 확장 명령은 없는 월드에서 |
| ---------- | ---- | ------------------------------------ |
| E5 `restoreExtState` | 확장 목록이 `null`인데 조각 행이 있으면 거부 ([T4-03](./T4-03.md) 117줄) | 적재가 거부된다 |
| E8 R4 | origin 1에 `initial.ext`가 있으면 거부 (188줄) | origin 1로 쓸 수 없다 |
| E8 R5 | origin 3은 `commands`가 `null`이거나 두 목록이 비면 거부 (189줄) | origin 3으로도 쓸 수 없다 |
| 시작 대조 D1·D2 | 확장 목록이 `null`인데 행이 있음, origin 1인데 확장 목록 있음 (202~203줄) | 엔진이 첫 step 전에 멈춘다 |

켜짐의 표시는 [T2-26](https://github.com/opensamguk/opensamguk/pull/220)(PR #220 `fa516aa`, 채택 전) 규칙 기능 목록을 쓴다. 새 origin 칸을 만들지 않는다.

- T2-26은 규칙 기능을 `ruleRegistry.features`에 등록하고 켠 기능을 `initial.ruleFeatures`(비지 않은 오름차순 배열, 켠 기능이 없으면 키 자체를 넣지 않음)에 둔다. 갈림은 `hasRuleFeature(state, key)`다. 기능 자료는 `featureData`(자료가 있는 기능만, 비면 칸 없음)에 두고 `resourceHashV3`는 `featureData`가 없으면 `resourceHash(initial)`와 같은 값이다. T4-03의 `commands`·`preset`·`resources`·`sliceKeys`는 기능 `ext`의 `featureData.ext`로 옮겨진다(T2-26 옮길 점 표 T4-03 행).
- 경매는 규칙 기능 `auction` 하나로 등록한다. `requires: ['ext']`다. 조각 저장·복원 검사가 `ext` 기능의 몫이기 때문이다. 그래서 경매만 켠 월드의 `initial.ruleFeatures`는 `['auction', 'ext']`이다. 경매는 자기 기능 자료가 없어 `featureData.auction`을 만들지 않는다.
- rules `ext/state.ts`: `extFeatureBindings: readonly { feature: string; sliceKeys: readonly string[] }[]`에 `{ feature: 'auction', sliceKeys: ['auction'] }` 한 줄. `createExtState`, `extSliceKeys`, `restoreExtState`의 첫 인자를 `{ commands: EnabledCommands | null; ruleFeatures: readonly string[] }`로 넓히고 조각 집합은 명령 결합과 기능 결합의 합집합이다.
- 기능 `ext`의 검사(T2-26이 T4-03의 R4~R8을 옮긴 `checkOrigin`): `featureData.ext.commands`가 `null`이거나 비어도 `extSliceKeys`가 비지 않으면 받는다. 둘 다 비면 지금처럼 거부한다. `sliceKeys`는 넓힌 `extSliceKeys`와 대조한다. 시작 대조 D1~D5도 같은 넓힌 집합으로 본다.
- 서버 `readView`와 엔진 `loadWorld`는 상태의 `ruleFeatures`와 `featureData.ext.commands`(월드 행에서 같은 값)를 함께 넘긴다.

해시·바이트 보존 규칙은 셋이다. 이 규칙이 F5를 지킨다.

1. 형식 1 월드(`replayFormat: 1`): 경매 코드가 닿지 않는다. origin 1·archive 2 바이트와 해시가 이 변경 전 기준 고정 파일과 같다. 기능 없는 형식 3 월드(T2-26 뒤 새 월드의 기본): `ruleFeatures` 키와 `featureData` 칸이 없다. 바이트는 형식 1과 다르므로 비교하지 않고 상태 해시·`initialStateHash`·`resourceHash`가 같은 입력의 형식 1 월드와 같은지 본다(T2-26 74줄, 116줄). 같은 형식 3 기록끼리는 이 변경 전후 바이트도 같다.
2. 확장 명령만 켠 형식 3 월드(`ruleFeatures: ['ext']`): `auction`이 목록에 없으므로 기능 결합이 비고 `extSliceKeys`가 지금 명령 결합만의 값과 같다. `featureData.ext`의 모양과 값이 이 변경 전 T4-03 기준과 같아 같은 형식 3 기록끼리 origin·archive 3 바이트와 두 해시가 같다.
3. 경매를 켠 월드에서만 `ruleFeatures`에 `auction`이 들고 `featureData.ext.sliceKeys`에 `auction`이 든다. 두 해시는 T2-26 식대로 이 값을 포함한다. 이 월드는 경매 이전에 존재하지 않았으므로 보존할 옛 바이트가 없다.

읽기 호환: 규칙 기능 목록에 `auction`이 없는 기록은 지금처럼 읽힌다. `auction`이 있는데 등록되지 않은 실행본은 T2-26 거부 표의 모르는 기능 검사로 거부한다.

어느 월드에 `auction`을 켤지는 T2-26 열린 결정 U26-2(기능을 고르는 화면·프리셋·로비 규칙)의 몫이다. 이 계획은 정하지 않는다. 프리셋 `features.auction`은 그 결정의 후보 하나일 뿐이다.

소유는 둘 가운데 하나다. 총괄이 정한다(쟁점 T28-Q3).

- (가) T4-03이 T2-26에 맞춰 다시 쓸 때 넓힌 `extSliceKeys`와 `checkOrigin` 규칙을 함께 받는다. T4-03은 재검토 대기라 아직 main에 없다. 이 계획의 안이다.
- (나) T4-28이 T2-26·T4-03 병합 뒤 그 파일을 고친다. `ext/state.ts`와 엔진 `worldLoader.ts`·`replay.ts`는 명세 §7 순서에 T4-28이 이미 있다. 서버 `readView`(`apps/server/src/queries.ts`, §7은 T4-40만)와 T4-03이 만드는 `apps/server/src/game/resolver.ts`, `apps/engine/src/extState.ts`는 순서 표에 행을 더해야 한다.
