## 계획 (Claude)

### 목표

- 장수 화면에 추천 예턴 3개와 이유가 보이고 누르면 예턴에 들어간다. 같은 상태면 같은 추천이 나온다(NPC AI 판단 재사용). 국가 작전·공지 지시가 있으면 그것을 먼저 추천한다. 재야 장수에게는 나라를 추천한다 (AC-M3-13, 단위 테스트 + E2E).
- 입장 화면에서 시나리오 인물을 역할(군주·중견·부하·재야)별로 보고 골라 시작한다. 이미 사람이 맡은 인물은 목록에서 빠진다. 직접 만드는 방식도 그대로 된다 (AC-M3-14, E2E).
- 달이 바뀔 때 그달의 공개 평판 순위와 한 줄 평이 월드 정세에 나온다. 같은 사건 종류는 장수당 한 달에 한 번만 센다 (AC-M3-15, 골든 테스트).

이 작업은 규칙·엔진·API까지다. 화면과 E2E는 T3-08이 한다. 세 기능의 설계는 이 문서가 겸하며 `docs/design/`에 따로 쓰지 않는다.

### 군사 조언 (D3)

판단은 `packages/rules/src/advice/adviseGeneral(view, generalId, ctx)` 하나에 둔다. 순수 함수이며 server가 읽기 요청마다 부른다 (server → rules 의존 허용, T1-11의 precheck와 같다).

```text
재야 장수
  recommendNations(view, general) 상위 3개 → 각각 임관(nationId) 후보
  임관 사전 검사를 통과한 나라만 남긴다

소속 장수 (앞에서부터 이어 붙이고, 같은 key·인자는 앞의 것만 남긴다)
  1. 작전   내가 참여한 열린 작전의 판정이 준비됨이 아니면 operation.suggest 사본의 0번 칸
  2. 지시   국가 공지에 지시(명령 key + 인자)가 있으면 그 명령
  3. AI     chooseGeneralTurn(view, general, rngFor(seed, 'advice', tick, generalId)).candidates
            점수 내림차순 → 명령 key → 인자 정규 JSON 순
  사전 검사를 통과한 앞 3개를 낸다. 작전·지시인데 통과하지 못한 것은 skipped에 이유와 함께 둔다
```

- 같은 상태는 같은 월드 tick, 같은 장수 `turnRevision`, 같은 월드 상태를 뜻한다. RNG 스트림을 tick과 장수로 고정하고 정렬 기준을 모두 정했으므로 이 세 가지가 같으면 결과가 같다. `chosen`은 쓰지 않는다.
- 나라 추천 `recommendNations`는 `packages/rules/src/advice/`에 두고 D15 재야 인물 목록도 같은 함수를 쓴다. 기준은 장수와 그 나라 군주의 상성 거리다. 거리는 `|a − b|`가 75를 넘으면 `150 − |a − b|`로 접는다 (core2026 `df6c926` `app/game-engine/src/turn/reservedTurnHandler.ts`의 상성 거리와 같은 방식). 거리 오름차순, 같으면 도시 수 내림차순, 국가 ID 순이다. 장수나 군주의 상성이 999(상성 없음)이면 거리를 쓰지 않고 도시 수 순으로만 줄 세우며 이유에 상성 기준이 없다고 쓴다.
- 이유 문자열은 화면에 그대로 나간다. T1-09의 `reason`이 개발용 표현이면 이 작업에서 [글쓰기 규칙](../writing-style.md)에 맞게 다듬는다. 판단은 바꾸지 않는다. 작전은 목표 도시와 연월, 지시는 공지 첫 줄 40자 안쪽을 이유로 쓴다.
- 공지 지시는 `Nation.noticeDirective`(JSON, `{ commandKey, args }` 또는 null) 칸이다. `notice.nation.set`에 선택 입력 `directive`를 더하며 지금 호출은 그대로 동작한다. 저장할 때 명령 key가 장수 명령 목록과 프리셋 허용 목록에 있고 인자가 그 명령 스키마에 맞는지 확인한다.
- 추천을 누르면 화면이 기존 `turns.edit`의 `put`으로 0번 칸에 넣는다. 조언 전용 변경 API는 만들지 않는다.

API 계약 (화면이 쓸 모양):

```ts
advice.get({ worldId }) → {
  basis: { tick, revision },
  items: AdviceItem[],                          // 0~3개
  skipped: [{ source: 'operation' | 'notice', commandKey, code, message }],
}
AdviceItem = {
  source: 'operation' | 'notice' | 'ai',
  commandKey, commandName, args, argsLabel,     // argsLabel: 화면에 쓸 인자 이름 (예: 도시 이름)
  reason,
  score: number | null,                         // AI 후보만
  nation: { id, name, color } | null,           // 재야의 임관 추천만
}
notice.nation.set({ worldId, body, directive?: { commandKey, args } | null })   // T2-09 계약 확장
```

- 장수는 세션 사용자와 월드로 서버가 찾는다. 요청에 장수 ID를 받지 않는다. 장수가 없으면 `NOT_FOUND`.
- 장수 600명 월드에서 로컬 1회 100ms 미만을 목표로 재고 구현 기록에 남긴다. 부하 기준은 AC-M3-07(T3-11)이 본다.

### 역할별 입장 (D15)

역할 분류는 `packages/rules/src/entry/classifyRole(general, scenarioStat)`이다.

| 역할 | 조건 |
| ---- | ---- |
| 군주 | `officerLevel` 12 |
| 중견 | 군주가 아닌 소속 장수 중 `officerLevel`이 2~11이거나 통솔·무력·지력 중 가장 높은 값이 `stat.chiefMin`(지금 65) 이상 |
| 부하 | 소속 국가가 있고 위 둘이 아님 |
| 재야 | 소속 국가 없음 |

- 재야 판정은 `officerLevel`이 아니라 `nationId`로 한다. T1-03 bootstrap은 시나리오의 관직 0을 그대로 저장하므로 소속 장수도 `officerLevel`이 0이다.
- `stat.chiefMin`은 `resources/scenario/default.json`의 값이다. core2026은 같은 값을 태수·군사 자격의 능력치 하한으로 쓴다 (`packages/logic/src/personnel/officeRequest.ts`). 중견 기준은 이 계획의 결정이며 사용자 검토 대상이다.
- 고를 수 있는 인물: `userId`가 비었고 `activeFromYear`가 현재 게임 연도 이하다. 사망 처리는 Phase 2이므로 몰년은 보지 않는다. 월드가 PREOPEN·RUNNING일 때만 받는다.

맡기는 즉시 행동이다. 장수 생성(T1-11)과 같이 InputEvent로 엔진이 처리한다.

InputEvent 모델은 새로 만들지 않고 T1-07의 병합 계약을 인계받는다. 기준은 main `76d56d0`의 `packages/db/prisma/schema.prisma:271-294`다 (PR9 `4ad4460`의 231-254행과 같은 모양). 상태는 `PENDING`·`APPLIED`·`REJECTED` 셋이다. `(worldId, userId, idempotencyKey)`와 `(worldId, sequence)`가 고유하고 엔진이 처리한 입력은 적용이든 거절이든 `sequence`를 받는다. 착수할 때 main의 커밋 SHA와 이 위치를 구현 기록에 적는다. 76d56d0과 다르면 다른 점도 적고 main 쪽을 따른다.

엔진의 처리 순서도 인계받는다. main `76d56d0`의 `processCreation`(`apps/engine/src/inputs.ts:16-19`)은 `general.create`인 `PENDING` 행 중 id가 가장 작은 것 하나만 꺼내고 `TurnLoop.step`이 한 번에 하나씩 부른다(`apps/engine/src/turnLoop.ts:86-91`은 RUNNING이 아닐 때, 99-105행은 RUNNING일 때). 맡기는 이 옆에 따로 꺼내는 함수를 만들지 않는다. 모든 kind를 id 순서 한 줄로 꺼내는 처리기는 M2의 새 입력(T2-05·T2-07·T2-13)도 함께 쓰며 그 소유자는 U62-5에서 정한다. 이 작업은 그 처리기에 `general.possess` 갈래를 더한다. 그래서 `general.create`와 맡기를 함께 보낸 사용자의 두 입력은 id 순서로 처리된다. U62-5가 정해지고 그 처리기가 main에 들어오기 전에는 맡기 처리를 구현하지 않는다.

```text
server  entry.possess({ worldId, generalId, idempotencyKey })
          세션 확인 → 같은 사용자·키의 InputEvent가 있으면 새로 쓰지 않고 그 행의 결과를 돌려준다
          사전 검사 (안내용, 판정은 엔진 재검사)
            없는 장수 → NOT_FOUND 오류
            남이 맡음 TAKEN, 활성 전·월드 상태 NOT_ELIGIBLE, 내 장수 있음 ALREADY_HAS_GENERAL, 정원 FULL
              → InputEvent를 쓰지 않고 { status: 'rejected', rejectCode }
          InputEvent(kind 'general.possess', generalId, payload { generalId }, idempotencyKey, status PENDING)
engine  InputEvent 처리 트랜잭션 (리스·월드 행을 잠근 뒤 nextActionSequence, inputs.ts의 general.create와 같음)
          다시 검사: 사용자 ACTIVE(inputs.ts:32-34와 같은 FOR SHARE), 월드 상태, 대상 userId 비었음,
                     활성 연도, 사용자 장수 없음, 정원
          성공  General.userId = 사용자, turnRevision + 1, 군주면 Nation.isNpc = false, 맡기 로그 한 줄(아래 맡기 로그 절)
                status APPLIED, sequence, result { generalId, userId, revision, rulerNationId | null }
          거절  상태는 바꾸지 않는다
                status REJECTED, sequence, result { code: TAKEN | ALREADY_HAS_GENERAL | NOT_ELIGIBLE | FULL }
server  같은 InputEvent를 최대 5초 기다린다. 넘으면 { status: 'pending' } (T1-11과 같음)
```

- 엔진 재검사에서 사용자가 ACTIVE가 아니거나 월드 상태가 받을 수 없는 상태면 `NOT_ELIGIBLE`로 거절한다. `general.create`는 같은 경우를 `ACTOR_INACTIVE`·`WORLD_CLOSED`로 거절하지만(`inputs.ts:34-35`) 맡기의 거절 코드는 아래 네 개로 둔다. 제재된 사용자는 세션이 무효라 `entry.possessStatus`에 닿지 못한다.
- 월드 상태: 이 계획은 PREOPEN·RUNNING에서 맡기를 받는다. main의 `general.create`는 RUNNING에서만 적용된다(`inputs.ts:35`). 엔진은 RUNNING이 아닐 때도 입력 처리기를 부르므로(`turnLoop.ts:86-91`) PREOPEN 맡기는 구현할 수 있다. 직접 생성과 다르게 둘지는 사용자 검토 항목이다 (아래 사용자 검토 절).
- `idempotencyKey`는 화면이 맡기 시도 한 번마다 만드는 UUID다. 네트워크 오류나 새로고침 뒤 같은 시도를 다시 보낼 때는 같은 키를 쓴다. UUID가 아니면 `BAD_REQUEST`다. 같은 키에 다른 `generalId`가 오면 `BAD_REQUEST`이고 기존 행은 그대로 둔다. 사전 검사에서 거절되어 행이 없는 키는 다시 보내면 사전 검사부터 다시 한다.
- 정원은 월드 정원(`maxHumanGenerals`, T2-03)과 국가당 사람 장수 상한(`protection.maxGeneralsPerNation`, T2-02) 둘 다다. 어느 쪽이든 차면 `FULL`이다.
- 맡아도 능력치·금·쌀·병력·위치·턴 시각(`nextTurnTick`)·예턴 30칸은 그대로다. 그 뒤로는 사람 장수 규칙(빈칸은 휴식 또는 D12 기본 방침)을 따른다. 맡기 로그는 턴 시각을 옮기지 않고 기존 턴 로그와 따로 남는다 (아래 맡기 로그 절).
- 두 사람이 같은 인물을 동시에 고르면 `sequence` 순서대로 처리되어 뒤의 요청은 `REJECTED`·`TAKEN`이 된다. 엔진은 `userId IS NULL` 조건부 갱신으로 맡기므로 두 처리가 겹쳐도 한쪽만 성공한다.
- 한 사용자가 서로 다른 인물 둘을 다른 키로 동시에 고르거나 `general.create`와 맡기를 함께 보내면 먼저 처리된 것만 적용되고 뒤의 맡기는 `ALREADY_HAS_GENERAL`이다. 마지막 방어는 기존 General의 `(worldId, userId)` 고유 제약이다.
- 직접 생성 `general.create`는 손대지 않는다.

- 사람 장수와 NPC 장수의 턴 처리가 `userId`로 갈라지면(T1-09 NPC AI, D12 기본 방침) 재생도 재생한 `userId`로 같은 갈래를 탄다. 12개월 재생 시험에 맡은 뒤의 턴을 넣어 이것을 확인한다.

맡기 로그:

- 지금 한 장수의 로그는 `GeneralLog` 한 표이고 `@@unique([worldId, generalId, tick])`다 (main `76d56d0` `packages/db/prisma/schema.prisma:194-206`). `apps/engine/src/turnLoop.ts:158-166`은 턴을 처리할 때 그 장수의 `due.nextTurnTick`으로 이 표에 한 행을 만든다. 맡기를 처리한 tick이 그 장수의 턴 tick과 같으면 맡기 로그를 이 표에 더할 수 없다. 처리 순서를 바꿔도 두 행의 키는 같다. 그래서 맡기 로그는 `GeneralLog`에 쓰지 않는다.

  - 새 모델 `GeneralInputLog(id BigInt 자동 증가, worldId, generalId, inputEventId BigInt 고유, sequence, tick, kind, text, createdAt)`. `General`과 `InputEvent`에 외래 키를 걸고 지우기는 `GeneralLog`처럼 cascade다. `kind`는 지금 `general.possess` 하나다. `tick`은 엔진이 그 InputEvent를 처리한 월드 tick이고 `sequence`는 그 InputEvent의 `sequence`다.

- 조회는 main의 tick cursor를 그대로 쓴다. `records.general`(`apps/server/src/routers/records.ts:6-17`)은 `GeneralLog`를 tick 내림차순으로 31행 읽고 `page()`가 30행과 마지막 tick을 `nextCursor`로 낸다(`apps/server/src/queries.ts:71-76`). cursor는 숫자 문자열만 받는다(`queries.ts:8-14`). 이 형식을 바꾸지 않고 다음처럼 합친다.
  - 쪽의 경계는 `GeneralLog`만으로 정한다. 지금과 같은 31행을 읽고 `nextCursor`도 지금과 같다.
  - 그 쪽에 붙일 `GeneralInputLog`는 tick이 요청 cursor보다 작고(cursor가 없으면 제한 없음) 그 쪽의 하한 이상인 행이다. 하한은 `nextCursor`가 있으면 그 tick, 없으면 제한 없음이다. 다음 쪽은 `tick < nextCursor`로 읽으므로 같은 tick의 두 표 행이 쪽 경계에서 빠지거나 겹치지 않는다.

  - T1-12의 응답 모양 시험과 권한 시험(`reads.integration.test.ts:405-433`, `498-506`의 cursor 시험 포함)은 고치지 않고 통과해야 한다.
- 맡기 로그는 `APPLIED`로 바꾸는 엔진 트랜잭션에서 한 행만 새로 쓴다. `REJECTED`는 로그를 쓰지 않는다. 같은 키 재전송은 InputEvent를 새로 만들지 않으므로 로그도 늘지 않고 마지막 방어는 `inputEventId` 고유 키다. 고유 키 충돌은 `ON CONFLICT DO NOTHING`·upsert로 넘기지 않고 트랜잭션 오류로 드러낸다. 기존 턴 로그를 덮거나 지우지 않는다. 충돌을 피하려고 로그의 tick을 실제 처리 tick과 다른 값으로 적거나 턴 시각을 옮기지 않는다.

### 월단평 (D10)

사건은 `ReputationEvent(worldId, generalId, year, month, kind, score, tick)`에 기록한다. 고유 키 `(worldId, generalId, year, month, kind)`로 같은 종류는 장수당 한 달에 한 번만 남는다. 두 번째 기록은 충돌을 무시하고 넘어간다.

| kind | 이름 | 기록하는 때 | 대상 | 점수 (초안) |
| ---- | ---- | ----------- | ---- | ----------- |
| `conquest` | 점령 | 성벽을 넘어 도시를 점령함 | 공격 장수 | +5 |
| `victory` | 승전 | 교전에서 상대 장수를 물리침 (공격·수비 모두) | 이긴 장수 | +3 |
| `domestic` | 내정 성과 | 내정 명령으로 도시 수치나 국가 기술이 최대치에 이름 | 실행 장수 | +2 |
| `defeat` | 패전 | 교전에서 짐, 지키던 도시를 빼앗김 | 진 장수 | −2 |

- 점수는 `packages/rules/src/balance.ts`의 상수다. 순위만 바꾸는 값이라 핵심 규칙이 아니지만 처음 값은 사용자 검토 대상으로 둔다.

main `76d56d0`의 `apps/engine/src/monthly.ts:53-76`은 `monthlyTick`을 갱신한 뒤 `hashState(loadReplayState(...))`를 `YearbookSnapshot.stateHash`에 저장하고 그다음 `NationHistory`에 국가별 월간 수치를 합치고(65-75행), 마지막에 `persistRanking`으로 `RankingSnapshot`을 쓴다(76행). `packages/shared/src/node/hashState.ts`는 객체의 모든 키를 해시하므로 `ReplayState`에 키를 하나 더하면 값이 비어 있어도 해시가 달라진다. 그래서 평판 사건과 월단평을 해시에 넣는 일은 재생 형식 번호로 나눈다.

- 형식 번호는 `World.replayOrigin.version`이다. main `76d56d0`의 `apps/engine/src/world/persistence.ts:33-34`(`saveInitialWorld`)는 지금 1을 쓰고 `apps/engine/src/replay.ts:16-23`의 `ReplayOrigin`·`ReplayArchive`도 1만 있다. M2의 T2-05·T2-07·T2-13 계획이 이미 형식 2를 쓰려 하고 형식 2의 정의와 운반 경로의 소유자는 U62-5(PR #62)에서 정한다. 이 작업은 형식 번호를 따로 만들지 않는다. 착수할 때 main의 최신 형식을 N이라 하면 이 작업은 N+1 하나를 더하고 이 문서는 그것을 평판 형식이라 부른다. 착수 때 N과 그 정의 커밋 SHA·위치를 구현 기록에 적는다. U62-5가 형식을 하나로 모아 올리는 방식으로 정해지면 그 방식을 따른다.
- 평판 형식은 N 형식의 `ReplayState`에 `reputation: { events, reviews }`를 더한다. `events`는 `ReputationEvent` 행을 `(year, month, generalId, kind)` 순으로, `reviews`는 `MonthlyReview` 행을 `(year, month)` 순으로 담는다. 같은 `(generalId, year, month, kind)`의 두 번째 사건은 DB와 똑같이 더하지 않는다. 엔진의 `loadReplayState`는 월드 형식을 읽고 평판 형식일 때만 두 표를 같은 순서(`orderBy`)와 같은 모양으로 읽는다.
- 이 작업이 병합된 뒤 만드는 월드는 평판 형식을 쓴다. 이미 있는 월드는 만든 때의 형식으로 끝까지 진행하고 평판 사건 기록과 6단계가 없다. 진행 중인 월드의 재생 규칙을 중간에 바꾸지 않기 위한 판단이며 M3 공개 전에 만든 월드는 시험용이다.
- 형식 1의 시험 경로는 바꾸지 않는다. `initialReplayState(initial)`(`packages/rules/src/replay.ts:29`)를 인자 없이 부르면 지금처럼 형식 1이다. `apps/engine/src/monthly.test.ts:120`이 이렇게 부른다. 형식 선택 인자는 U62-5가 정한 모양에 더한다. `runReplayAction`은 평판 형식일 때만 턴의 평판 사건을 `reputation.events`에 더하고 월간 행동에서 6단계를 돌려 그달 월단평을 `reputation.reviews`에 더한다.
- `exportReplay`는 월드 형식을 `archive.version`으로 낸다. `replayArchive`(`apps/engine/src/replay.ts:77-146`)는 `archive.version`과 `origin.version`이 같고 알려진 형식만 받는다. 기존 형식의 검사·재생·해시는 그대로이고 평판 형식은 같은 검사에 위 재생 상태를 더한다.
- 평판 형식 월드의 월간 트랜잭션 순서는 1~5단계 쓰기 → `monthlyTick` 갱신 → 6단계(방금 끝난 달의 `ReputationEvent`를 읽어 `MonthlyReview` 한 행을 씀) → `loadReplayState` → `hashState` → `YearbookSnapshot` 쓰기 → `NationHistory` 합치기 → `persistRanking`이다. 해시를 6단계 뒤에 계산하므로 그달 `stateHash`에는 그달 월단평까지 들어간다. 순수 재생도 6단계를 마친 뒤 `replayArchive`가 해시를 계산한다.
- 월드 정세 한 줄은 `MonthlyReview.headline`이므로 재생 상태의 `reviews`에 행째로 들어간다. 따로 넣는 표는 없다.
- 1~5단계 상태, `NationHistory`의 행 수와 `data`(사건 `events`와 월간 수치를 합친 모양), `YearbookSnapshot`의 `data`·`tick`·`year`·`month`·`sequence`, `RankingSnapshot`의 `tick`·`generals`·`nations`는 형식과 상관없이 같아야 한다. `stateHash`만 형식에 따라 달라지며 각 형식 안에서 순수 재생 해시와 같은지를 따로 본다 (아래 검증의 보존·재생 줄).
- 조건은 기존 재생 시험과 월간 골든이 고치지 않고 통과하는 것이다. 단위 시험 `apps/engine/src/monthly.test.ts:23`(골든)과 120행(`initialReplayState(initial)`의 형식 1 재생), 통합 시험 `apps/engine/src/monthly.integration.test.ts:81`·`100`(같은 tick 사건과 월간 요약 합치기)·`208`(12개월 해시와 CLI)은 `saveInitialWorld`(42행)로 만든 월드를 거친다. 기본 형식이 평판 형식으로 바뀌어도 이 시험들이 그대로 통과해야 한다. 월단평을 해시에서 빼거나 대조를 건너뛰어 통과시키지 않는다.

월드 정세 줄의 저장 위치:

- `NationHistory`에는 쓰지 않는다. main `76d56d0`의 `NationHistory`(`packages/db/prisma/schema.prisma:296-304`)는 `nationId Int`가 복합 기본 키 `(worldId, tick, nationId)`에 들어간다. `data Json`에는 턴 처리의 국가 사건 글이 `events` 배열로 쌓이고(`apps/engine/src/commandPersistence.ts:97-113`) 월간 정산이 같은 행에 국가별 수치를 합친다(`apps/engine/src/monthly.ts:65-75`). 국가 없는 행은 없다. `nationId`에 0 같은 대체 값을 넣지 않고 이 표의 키와 `data` 모양도 바꾸지 않는다. `docs/product/data-model.md:73`의 `nationId(없으면 월드 정세)`는 개요이며 코드 계약이 아니다.
- 같은 `NationHistory` 자료에서 사건 전용 행을 월간 요약으로 읽어 국가 기록이 500이 되는 결함이 [#108](https://github.com/peppone-choi/opensamguk/issues/108)로 열려 있다. `records.nation`은 지금 `data.nationId`가 있는 행만 읽는다(`apps/server/src/routers/records.ts:22-33`). 이 작업은 `NationHistory`에 새 모양을 더하지 않으며 #108의 수정 범위를 건드리지 않는다. 착수 때 #108이 열려 있으면 구현 기록에 그 상태를 적는다.
- `records.world`는 T1-12가 완료한 계약이다. main `76d56d0`의 `apps/server/src/routers/records.ts:37-54`는 `YearbookSnapshot`만 tick 내림차순으로 읽어 `worldRecordInfo`(`apps/server/src/visibility.ts:127-131`)로 공개 필드를 거른다. 국가 없는 월드 기록 표는 없다. `YearbookSnapshot.data`에 월단평을 넣으면 위 기존 기록 보존 조건이 깨지므로 넣지 않는다.
- 월단평 줄은 별도 표를 만들지 않고 `MonthlyReview.headline`(문자열, 순위가 없으면 null)에 둔다. 6단계가 같은 tick의 `YearbookSnapshot`과 같은 트랜잭션에서 쓰므로 두 행의 tick이 같다.
- `records.world`는 읽은 `YearbookSnapshot` 행과 같은 `(worldId, tick)`의 `MonthlyReview`를 한 번 더 읽어, headline이 있으면 그 항목에 `review: { headline }`를 붙인다. 없으면 키를 넣지 않는다. 쪽 수, cursor, 정렬은 지금과 같다. 같은 tick의 줄을 따로 된 항목으로 두면 tick만 담는 cursor(`apps/server/src/queries.ts:71-76`)에서 쪽 경계에 걸린 줄이 빠지므로 항목을 나누지 않는다.
- 이 방식이면 월단평이 없는 항목의 모양은 지금과 같다. `apps/server/src/routers/reads.integration.test.ts:420-429`의 정확한 모양 대조와 금·쌀·해시 비공개 대조는 고치지 않고 통과해야 한다.
- 월단평 줄은 6단계 트랜잭션에서 `MonthlyReview` 새 행으로만 쓴다. 같은 tick의 `NationHistory` 국가별 행, `YearbookSnapshot`, `RankingSnapshot`을 지우거나 덮지 않는다. 월간 정산은 tick마다 한 번 커밋되므로 같은 키가 다시 오면 결함이다. 충돌은 조용히 넘기지 않고 트랜잭션 오류로 드러낸다.
- 화면의 월단평 표는 `review.*`가 주고 월드 정세 목록의 한 줄은 `records.world`가 준다. 두 값은 같은 `MonthlyReview` 행에서 나오므로 어긋나지 않는다.

API 계약:

```ts
review.latest({ worldId }) → Review | null
review.get({ worldId, year, month }) → Review | null
review.months({ worldId }) → [{ year, month }]        // 최신순 24개
Review = {
  year, month,
  entries: [{ rank, generalId, name, nation: { id, name, color } | null, score, kinds: Kind[], line }],
}
```

- 로그인한 사용자면 그 월드에 장수가 없어도 볼 수 있다 (공개 순위).
- `records.world`의 항목은 지금 모양에 `review?: { headline: string }` 하나만 더한다 (위 저장 위치 절). `records.general`·`home.get`의 장수 로그 항목은 지금 모양 그대로이고 맡기 로그는 `kind: 'possess'`다 (위 맡기 로그 절).
