## 계획 (Claude)

### 목표

- 장수 화면에 추천 예턴 3개와 이유가 보이고, 누르면 예턴에 들어간다. 같은 상태면 같은 추천이 나온다(NPC AI 판단 재사용). 국가 작전·공지 지시가 있으면 그것을 먼저 추천한다. 재야 장수에게는 나라를 추천한다 (AC-M3-13, 단위 테스트 + E2E).
- 입장 화면에서 시나리오 인물을 역할(군주·중견·부하·재야)별로 보고 골라 시작한다. 이미 사람이 맡은 인물은 목록에서 빠진다. 직접 만드는 방식도 그대로 된다 (AC-M3-14, E2E).
- 달이 바뀔 때 그달의 공개 평판 순위와 한 줄 평이 월드 정세에 나온다. 같은 사건 종류는 장수당 한 달에 한 번만 센다 (AC-M3-15, 골든 테스트).

이 작업은 규칙·엔진·API까지다. 화면과 E2E는 T3-08이 한다. 세 기능의 설계는 이 문서가 겸하며 `docs/design/`에 따로 쓰지 않는다.

### 군사 조언 (D3)

판단은 `packages/rules/src/advice/adviseGeneral(view, generalId, ctx)` 하나에 둔다. 순수 함수이며 server가 읽기 요청마다 부른다 (server → rules 의존 허용, T1-11의 precheck와 같다).

```text
재야 장수
  recommendNations(view, general) 상위 3개 → 각각 임관(nationId) 후보
  임관 사전 검사를 통과한 나라만 남긴다

소속 장수 (앞에서부터 이어 붙이고, 같은 key·인자는 앞의 것만 남긴다)
  1. 작전   내가 참여한 열린 작전의 판정이 준비됨이 아니면 operation.suggest 사본의 0번 칸
  2. 지시   국가 공지에 지시(명령 key + 인자)가 있으면 그 명령
  3. AI     chooseGeneralTurn(view, general, rngFor(seed, 'advice', tick, generalId)).candidates
            점수 내림차순 → 명령 key → 인자 정규 JSON 순
  사전 검사를 통과한 앞 3개를 낸다. 작전·지시인데 통과하지 못한 것은 skipped에 이유와 함께 둔다
```

- 같은 상태는 같은 월드 tick, 같은 장수 `turnRevision`, 같은 월드 상태를 뜻한다. RNG 스트림을 tick과 장수로 고정하고 정렬 기준을 모두 정했으므로 이 세 가지가 같으면 결과가 같다. `chosen`은 쓰지 않는다.
- 나라 추천 `recommendNations`는 `packages/rules/src/advice/`에 두고 D15 재야 인물 목록도 같은 함수를 쓴다. 기준은 장수와 그 나라 군주의 상성 거리다. 거리는 `|a − b|`가 75를 넘으면 `150 − |a − b|`로 접는다 (core2026 `df6c926` `app/game-engine/src/turn/reservedTurnHandler.ts`의 상성 거리와 같은 방식). 거리 오름차순, 같으면 도시 수 내림차순, 국가 ID 순이다. 장수나 군주의 상성이 999(상성 없음)이면 거리를 쓰지 않고 도시 수 순으로만 줄 세우며 이유에 상성 기준이 없다고 쓴다.
- 이유 문자열은 화면에 그대로 나간다. T1-09의 `reason`이 개발용 표현이면 이 작업에서 [글쓰기 규칙](../writing-style.md)에 맞게 다듬는다. 판단은 바꾸지 않는다. 작전은 목표 도시와 연월, 지시는 공지 첫 줄 40자 안쪽을 이유로 쓴다.
- 공지 지시는 `Nation.noticeDirective`(JSON, `{ commandKey, args }` 또는 null) 칸이다. `notice.nation.set`에 선택 입력 `directive`를 더하며 지금 호출은 그대로 동작한다. 저장할 때 명령 key가 장수 명령 목록과 프리셋 허용 목록에 있고 인자가 그 명령 스키마에 맞는지 확인한다.
- 추천을 누르면 화면이 기존 `turns.edit`의 `put`으로 0번 칸에 넣는다. 조언 전용 변경 API는 만들지 않는다.

API 계약 (화면이 쓸 모양):

```ts
advice.get({ worldId }) → {
  basis: { tick, revision },
  items: AdviceItem[],                          // 0~3개
  skipped: [{ source: 'operation' | 'notice', commandKey, code, message }],
}
AdviceItem = {
  source: 'operation' | 'notice' | 'ai',
  commandKey, commandName, args, argsLabel,     // argsLabel: 화면에 쓸 인자 이름 (예: 도시 이름)
  reason,
  score: number | null,                         // AI 후보만
  nation: { id, name, color } | null,           // 재야의 임관 추천만
}
notice.nation.set({ worldId, body, directive?: { commandKey, args } | null })   // T2-09 계약 확장
```

- 장수는 세션 사용자와 월드로 서버가 찾는다. 요청에 장수 ID를 받지 않는다. 장수가 없으면 `NOT_FOUND`.
- 장수 600명 월드에서 로컬 1회 100ms 미만을 목표로 재고 구현 기록에 남긴다. 부하 기준은 AC-M3-07(T3-11)이 본다.

### 역할별 입장 (D15)

역할 분류는 `packages/rules/src/entry/classifyRole(general, scenarioStat)`이다.

| 역할 | 조건 |
| ---- | ---- |
| 군주 | `officerLevel` 12 |
| 중견 | 군주가 아닌 소속 장수 중 `officerLevel`이 2~11이거나 통솔·무력·지력 중 가장 높은 값이 `stat.chiefMin`(지금 65) 이상 |
| 부하 | 소속 국가가 있고 위 둘이 아님 |
| 재야 | 소속 국가 없음 |

- 재야 판정은 `officerLevel`이 아니라 `nationId`로 한다. T1-03 bootstrap은 시나리오의 관직 0을 그대로 저장하므로 소속 장수도 `officerLevel`이 0이다.
- `stat.chiefMin`은 `resources/scenario/default.json`의 값이다. core2026은 같은 값을 태수·군사 자격의 능력치 하한으로 쓴다 (`packages/logic/src/personnel/officeRequest.ts`). 중견 기준은 이 계획의 결정이며 사용자 검토 대상이다.
- 고를 수 있는 인물: `userId`가 비었고 `activeFromYear`가 현재 게임 연도 이하다. 사망 처리는 Phase 2이므로 몰년은 보지 않는다. 월드가 PREOPEN·RUNNING일 때만 받는다.

맡기는 즉시 행동이다. 장수 생성(T1-11)과 같이 InputEvent로 엔진이 처리한다.

InputEvent 모델은 새로 만들지 않고 T1-07의 병합 계약을 인계받는다. 이 계획의 기준은 PR9(T1-07, exact `4ad446026d9e0fdd4e29e286e85ee0980c8672b1`, 계획을 쓸 때 병합 전)의 `packages/db/prisma/schema.prisma:231-254`다. 상태는 `PENDING`·`APPLIED`·`REJECTED` 셋이다. `(worldId, userId, idempotencyKey)`가 고유하고, 엔진이 처리한 입력은 적용이든 거절이든 `sequence`를 받는다. 착수할 때 main에 병합된 T1-07 커밋 SHA와 이 위치를 구현 기록에 적는다. 4ad4460과 다르면 다른 점도 적고 병합된 쪽을 따른다.

```text
server  entry.possess({ worldId, generalId, idempotencyKey })
          세션 확인 → 같은 사용자·키의 InputEvent가 있으면 새로 쓰지 않고 그 행의 결과를 돌려준다
          사전 검사 (안내용, 판정은 엔진 재검사)
            없는 장수 → NOT_FOUND 오류
            남이 맡음 TAKEN, 활성 전·월드 상태 NOT_ELIGIBLE, 내 장수 있음 ALREADY_HAS_GENERAL, 정원 FULL
              → InputEvent를 쓰지 않고 { status: 'rejected', rejectCode }
          InputEvent(kind 'general.possess', generalId, payload { generalId }, idempotencyKey, status PENDING)
engine  InputEvent 처리 트랜잭션 (월드 행을 먼저 잠그는 nextActionSequence 순서)
          다시 검사: 대상 userId 비었음, 활성 연도, 사용자 장수 없음, 정원
          성공  General.userId = 사용자, turnRevision + 1, 군주면 Nation.isNpc = false, 맡기 로그 한 줄(아래 맡기 로그 절)
                status APPLIED, sequence, result { generalId, userId, revision, rulerNationId | null }
          거절  상태는 바꾸지 않는다
                status REJECTED, sequence, result { code: TAKEN | ALREADY_HAS_GENERAL | NOT_ELIGIBLE | FULL }
server  같은 InputEvent를 최대 5초 기다린다. 넘으면 { status: 'pending' } (T1-11과 같음)
```

- `idempotencyKey`는 화면이 맡기 시도 한 번마다 만드는 UUID다. 네트워크 오류나 새로고침 뒤 같은 시도를 다시 보낼 때는 같은 키를 쓴다. UUID가 아니면 `BAD_REQUEST`다. 같은 키에 다른 `generalId`가 오면 `BAD_REQUEST`이고 기존 행은 그대로 둔다. 사전 검사에서 거절되어 행이 없는 키는 다시 보내면 사전 검사부터 다시 한다.
- 정원은 월드 정원(`maxHumanGenerals`, T2-03)과 국가당 사람 장수 상한(`protection.maxGeneralsPerNation`, T2-02) 둘 다다. 어느 쪽이든 차면 `FULL`이다.
- 맡아도 능력치·금·쌀·병력·위치·턴 시각(`nextTurnTick`)·예턴 30칸은 그대로다. 그 뒤로는 사람 장수 규칙(빈칸은 휴식 또는 D12 기본 방침)을 따른다. 맡기 로그는 턴 시각을 옮기지 않고 기존 턴 로그와 따로 남는다 (아래 맡기 로그 절).
- 두 사람이 같은 인물을 동시에 고르면 `sequence` 순서대로 처리되어 뒤의 요청은 `REJECTED`·`TAKEN`이 된다. 엔진은 `userId IS NULL` 조건부 갱신으로 맡기므로 두 처리가 겹쳐도 한쪽만 성공한다.
- 한 사용자가 서로 다른 인물 둘을 다른 키로 동시에 고르거나 `general.create`와 맡기를 함께 보내면 먼저 처리된 것만 적용되고 뒤의 맡기는 `ALREADY_HAS_GENERAL`이다. 마지막 방어는 기존 General의 `(worldId, userId)` 고유 제약이다.
- 직접 생성 `general.create`는 손대지 않는다.

결과 전달:

- 맡기 거절은 tRPC 오류가 아니라 성공 응답의 판별 union으로 돌려준다. 지금 `apps/server/src/trpc.ts:3`은 기본 `create()`라서 `TRPCError`의 `cause`가 응답에 나가지 않는다. T3-02 오류 계약(PR5 exact `dd4b29ab318c404684c8a717522612c47f513a7e`, `docs/plans/T3-02.md:105-124`)의 공개 필드 `data.reason`은 `EMAIL_NOT_VERIFIED`·`CONSENT_REQUIRED`·`TOKEN_INVALID`·`null`만 허용한다. 이 작업은 `cause`를 공개하지 않고 `data.reason`에 값을 더하지 않으며 formatter를 따로 만들지 않는다.
- 거절 코드의 타입 `PossessRejectCode = 'TAKEN' | 'ALREADY_HAS_GENERAL' | 'FULL' | 'NOT_ELIGIBLE'`은 `entry.ts`의 출력 스키마에 한 번만 적는다. T3-08은 `inferRouterOutputs<AppRouter>`로 이 타입을 읽고 목록을 화면 쪽에 다시 적지 않는다.
- tRPC 오류로 남는 것은 무인증·제재 세션 `UNAUTHORIZED`, 없는 월드·장수와 남의 키 조회 `NOT_FOUND`, 입력 형식과 키 재사용 충돌 `BAD_REQUEST`뿐이다. T3-02가 먼저 병합되어 이 절차가 `verifiedProcedure`를 쓰면 그 `FORBIDDEN`·`data.reason`도 T3-02 계약대로 나간다.

맡기의 재생:

- 순수 재생 처리는 `packages/rules/src/replay.ts`의 `applyRecordedInput`에 `general.possess` 갈래로 더한다. PR9의 이 함수(73-110행)는 `turns.set`·`general.create` 밖의 APPLIED 입력을 거부하므로 이 갈래가 없으면 맡기가 한 번이라도 있는 월드는 재생할 수 없다. 기존 두 갈래와 그 검사는 고치지 않는다.
- APPLIED 입력은 다음을 모두 확인한 뒤에만 적용하고, 하나라도 어긋나면 재생 오류로 멈춘다: `payload.generalId`·`input.generalId`·`result.generalId`가 같음, 재생 상태의 그 장수 `userId`가 null, `activeFromYear`가 그 시점 게임 연도 이하, 같은 `userId`를 가진 다른 장수가 없음, `result.revision`이 재생 상태 `revisions[id] + 1`. 적용은 `userId = result.userId`, `revisions[id] = result.revision`, `rulerNationId`가 있으면 그 국가의 `isNpc = false`다.

- 위 재생 갈래, 엔진 처리, 해시 대조 시험은 이 작업(T3-07, Codex)이 소유한다.

T1-12의 응답 모양 시험과 권한 시험은 고치지 않고 통과해야 한다.

### 월단평 (D10)

사건은 `ReputationEvent(worldId, generalId, year, month, kind, score, tick)`에 기록한다. 고유 키 `(worldId, generalId, year, month, kind)`로 같은 종류는 장수당 한 달에 한 번만 남는다. 두 번째 기록은 충돌을 무시하고 넘어간다.

| kind | 이름 | 기록하는 때 | 대상 | 점수 (초안) |
| ---- | ---- | ----------- | ---- | ----------- |
| `conquest` | 점령 | 성벽을 넘어 도시를 점령함 | 공격 장수 | +5 |
| `victory` | 승전 | 교전에서 상대 장수를 물리침 (공격·수비 모두) | 이긴 장수 | +3 |
| `domestic` | 내정 성과 | 내정 명령으로 도시 수치나 국가 기술이 최대치에 이름 | 실행 장수 | +2 |
| `defeat` | 패전 | 교전에서 짐, 지키던 도시를 빼앗김 | 진 장수 | −2 |
| `betrayal` | 배신 | 하야, 소속이 있는 채 등용 수락, 군주의 조약 파기(T2-07) | 그 장수, 파기는 군주 | −3 |

- 사건은 그것이 일어난 턴(또는 InputEvent)의 트랜잭션 안에서 상태 변경·로그와 함께 기록한다. 연월은 그 tick의 게임 날짜다. NPC 장수도 같이 센다.
- 점수는 `packages/rules/src/balance.ts`의 상수다. 순위만 바꾸는 값이라 핵심 규칙이 아니지만 처음 값은 사용자 검토 대상으로 둔다.

집계는 월간 정산 6단계다. T1-07의 1~5단계(세금·봉급 → 인구·민심 → 보급 → 외교 기한 → 연감) 뒤, 같은 트랜잭션에서 실행한다.

```text
대상 달 = 방금 끝난 달 (y, m)
점수     = 장수별 그달 사건 점수 합 (종류마다 한 번)
순위     = 점수 > 0인 장수를 점수 내림차순 → 양(+) 사건 수 내림차순 → 장수 ID 순, 상위 5명
한 줄 평 = 대표 사건 하나로 고른 문장
           대표 사건: 점수 절댓값이 큰 것, 같으면 점령 > 승전 > 내정 성과 > 배신 > 패전
           문장: 종류마다 문장 틀 3개 이상, rngFor(seed, 'review', y, m)로 1위부터 차례로 고름
저장     = MonthlyReview(worldId, year, month, tick, entries) 한 행, 고유 키 (worldId, year, month)
           순위가 있으면 월드 정세에 한 줄: "191년 3월 월단평 1위 조운, 2위 …" (아래 저장 위치 절)
           순위가 없으면 MonthlyReview는 빈 entries로 남기고 월드 정세 줄은 쓰지 않는다
```

- 순위와 한 줄 평에는 장수 이름, 소속 국가 이름, 전투·점령이 일어난 도시 이름만 쓴다. 이 셋은 이미 월드 정세와 지도에서 공개된다. 내정 도시, 병력, 국고, 예턴은 쓰지 않는다.
- 문장 틀은 `packages/rules/src/review/lines.ts`에 두고 받침에 따라 조사를 고르는 도우미를 함께 만든다. 틀은 사람이 겪은 일을 구체적으로 쓰고 근거 없는 수식을 붙이지 않는다 ([글쓰기 규칙 §7](../writing-style.md#7-디자인과-게임)). 리뷰어가 틀 전부를 읽는다.
- T1-07 월간 골든(`apps/engine/src/monthly.test.ts:23`)은 고치지 않는다. 6단계는 `runMonthly`를 고치지 않고 `packages/rules/src/monthly/`의 별도 순수 함수로 두며, 난수는 1~5단계의 `rngFor(seed, 'monthly', y, m)`와 다른 `rngFor(seed, 'review', y, m)` 스트림만 쓴다. 그래서 1~5단계의 값과 골든은 그대로다.

재생 규칙 버전과 해시:

PR9 `apps/engine/src/monthly.ts:52-71`은 `monthlyTick`을 갱신한 뒤 `hashState(loadReplayState(...))`를 `YearbookSnapshot.stateHash`에 저장하고, 그다음 `NationHistory`를 쓴다. `packages/shared/src/node/hashState.ts`는 객체의 모든 키를 해시하므로 `ReplayState`에 키를 하나 더하면 값이 비어 있어도 해시가 달라진다. 그래서 평판 사건과 월단평을 해시에 넣는 일은 재생 규칙의 버전으로 나눈다.

PR9 `schema.prisma:256-263`의 `NationHistory`는 `nationId Int`가 복합 기본 키 `(worldId, tick, nationId)`에 들어가고, `data Json`에 연감의 국가별 행을 담는다 (`apps/engine/src/monthly.ts:64-71`). 국가 없는 행이나 글 칸이 없다. `nationId`에 0 같은 대체 값을 넣지 않고 이 표의 키도 바꾸지 않는다. `docs/product/data-model.md:73`의 `nationId(없으면 월드 정세)`는 개요이며 코드 계약이 아니다.
- `records.world`의 저장·조회 계약은 T1-12가 정한다. 계획을 쓴 main `8e6b34140090ec3eef7979073dbd58308796b0e0`에서 T1-12는 `구현` 단계이고, `docs/plans/T1-12.md:45`에 절차 이름만 있을 뿐 저장 위치는 없다. 이 작업의 선행인 M2 전체가 끝나려면 M1의 T1-12도 끝나 있어야 하므로 착수 때는 병합되어 있다. 착수할 때 병합된 T1-12 커밋 SHA와, `records.world`가 읽는 schema 모델과 절차의 파일·행을 구현 기록에 적는다.
- 경우 A: 그 계약에 국가 없는 월드 기록 표가 있으면 그 표의 쓰기 방식으로 월단평 줄 한 행을 쓴다. 새 migration과 `records.ts` 수정은 하지 않는다.
- 경우 B: 그런 표가 없으면 이 작업이 소유하고 만든다.
  - 새 모델 `WorldRecord(worldId, tick, kind, data Json)`, 기본 키 `(worldId, tick, kind)`. `kind`는 지금 `monthlyReview` 하나이고 `data`는 `{ year, month, text, generalIds }`다.
  - 새 migration 하나. 기존 `NationHistory`·`YearbookSnapshot` 표와 기존 migration은 고치지 않는다.
  - `apps/server/src/routers/records.ts`의 `records.world`가 T1-12의 기존 항목과 `WorldRecord`를 함께 돌려준다. tick 내림차순이고, 같은 tick에서는 T1-12 기존 항목 뒤에 월단평 줄이 온다. cursor 형식과 페이지 크기는 T1-12 것을 따르고 항목에 `kind`를 붙여 화면이 구분하게 한다. T1-12의 응답 모양 시험과 권한 시험은 고치지 않고 통과해야 한다.
- 두 경우 모두 월단평 줄은 6단계 트랜잭션에서 새 행으로만 쓴다. 같은 tick의 `NationHistory` 국가별 행, `YearbookSnapshot`, 다른 월드 기록을 지우거나 덮지 않는다. 월간 정산은 tick마다 한 번 커밋되므로 같은 키가 다시 오면 결함이다. 충돌은 조용히 넘기지 않고 트랜잭션 오류로 드러낸다.
- 화면의 월단평 표는 `review.*`가 주고, 월드 정세 목록의 한 줄은 `records.world`가 준다. 두 값은 같은 6단계 트랜잭션에서 쓰므로 어긋나지 않는다.

API 계약:

```ts
review.latest({ worldId }) → Review | null
review.get({ worldId, year, month }) → Review | null
review.months({ worldId }) → [{ year, month }]        // 최신순 24개
Review = {
  year, month,
  entries: [{ rank, generalId, name, nation: { id, name, color } | null, score, kinds: Kind[], line }],
}
```

- 로그인한 사용자면 그 월드에 장수가 없어도 볼 수 있다 (공개 순위).
