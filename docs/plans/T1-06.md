# T1-06 엔진: 시계, 리스, 턴 실행, 재시작

> 대기열: T1-06 · AC: AC-M1-10, AC-M1-11 · 구현: Codex · 리뷰: Claude
> 선행: T1-05 · 관련: [요청·턴·저장 흐름](../developer/request-turn-persistence.md), [런타임](../architecture/runtime.md) §4

## 계획 (Claude)

### 목표

- 장수의 턴 시각이 되면 예턴 1칸이 실행되고, 결과가 로그에 남고, 예턴이 한 칸 당겨진다 (AC-M1-10).
- 처리 중 엔진을 강제 종료하고 다시 켜도 턴이 두 번 실행되거나 빠지지 않는다. 엔진 둘을 띄우면 하나만 실행권을 가진다 (AC-M1-11).

### 범위

- `packages/db`: `EngineLease(worldId, ownerId, fencingToken, expiresAt)`, `GeneralTurn(generalId, slot, commandKey, args)`, `GeneralLog`, `General.nextTurnTick`, `General.turnRevision`
- `apps/engine/src/`: `lease.ts`, `worldLoader.ts`, `turnLoop.ts`, `persist.ts`, `main.ts`

### 하지 않는 것

월간 정산(T1-07), NPC 판단(T1-09, 그 전까지 NPC 예턴은 비어 있어 휴식), 예턴 편집 API(T1-11), 일시정지 처리 이외의 시계 기능.

### 결정: 턴 배치

- 월드 생성 때 장수마다 그 달 안의 위치를 `rngFor(seed, 'turn-offset', generalId).int(0, 9_999)`로 정한다.
- `nextTurnTick = 현재 달 시작 tick + offset`. 실행하면 `+ TICKS_PER_MONTH`.
- 같은 tick에 여러 장수가 있으면 **장수 ID 오름차순**으로 실행한다 (결정성).
- 각 턴의 RNG는 `rngFor(seed, 'turn', tick, generalId)`. 다른 장수의 실행 순서가 바뀌어도 내 결과가 흔들리지 않는다.

### 결정: 실행권과 저장

```text
시작: EngineLease를 조건부로 획득 (없거나 만료면 내 것으로, fencingToken + 1)
루프: nowTick 계산 → nextTurnTick ≤ nowTick인 장수를 순서대로
  한 턴 = 예턴 0번 꺼냄 → check → execute → applyEffects (메모리 사본)
        → 한 트랜잭션: 바뀐 엔티티 + 로그 + 예턴 당김(29번은 휴식) + nextTurnTick
                      + "EngineLease.fencingToken = 내 토큰" 조건 확인
        → commit 성공 뒤에만 메모리 상태 확정
리스 갱신: 만료의 1/3마다. 갱신 실패하거나 commit에서 토큰 불일치면 즉시 멈춤
```

- 재시작하면 DB에서 월드를 다시 읽는다. 이미 commit된 턴은 `nextTurnTick`이 앞으로 갔으므로 다시 실행되지 않는다.
- commit 전에 죽은 턴은 DB에 흔적이 없으므로 다시 실행된다. RNG가 tick·장수로 정해지므로 결과도 같다.
- 엔진이 오래 멈췄다 켜지면 밀린 턴을 `nextTurnTick` 순서대로 따라잡는다 (한꺼번에 처리, 속도 제한 없음). 정책 변경은 M2.
- 시계 모드: `realtime`(벽시계)과 `manual`(테스트·시뮬레이터용, 호출할 때마다 정해진 tick까지 진행).

### 접근

1. Prisma 모델과 migration.
2. 리스: 획득·갱신·해제, 펜싱 토큰 조건부 commit 헬퍼.
3. 월드 적재 → 메모리 `WorldState`.
4. 턴 루프(manual 모드부터) → 저장 → realtime 모드.
5. `pnpm engine:run --world <id>`, dev 실행(`pnpm dev`)은 첫 RUNNING 월드를 잡는다.

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 턴 실행 | 통합(manual 시계): 예턴 [농지 개간, 휴식]을 넣고 1개월 진행 → 농업 증가, 로그 1줄, 예턴 0번이 휴식 |
| 순서 | 단위: 같은 tick 장수 3명 → ID 순 실행 |
| 중복 없음 | 통합: commit 직전 프로세스 kill(테스트 훅으로 예외) → 재시작 → 그 턴 한 번만 반영 |
| 실행권 | 통합: 엔진 둘 동시 시작 → 하나만 리스, 다른 하나는 대기. 리스 만료 뒤 넘겨받은 쪽만 commit |
| 낡은 commit | 통합: 토큰이 바뀐 뒤 이전 엔진의 commit 거부 |

## 구현 기록 (Codex)

- 바꾼 것:
  - 새 migration `20261020030000_engine_turns`: `EngineLease`, 0~29 slot CHECK가 있는 `GeneralTurn`, 장수·tick 고유 `GeneralLog`, `General.turnRevision`, 실행 순서 인덱스.
  - `lease.ts`: DB UTC 시각으로 조건부 획득·15초 만료·갱신·해제. 해제 때 토큰을 보존하고 재획득 때 증가시킨다. 만료 토큰은 갱신할 수 없다.
  - `worldLoader.ts`, `turnLoop.ts`, `persist.ts`: 매 턴 현재 월드·예턴 적재, 실행 시 재검사, tick·ID 순 처리, 시드 RNG, 상태·로그·예턴 당김·다음 tick·revision·시계 체크포인트의 원자적 저장. commit 성공 뒤에만 메모리 사본을 채택한다.
  - `main.ts`, `index.ts`: `pnpm engine:run --world <ID>`, dev 첫 RUNNING 월드 선택·리스 대기, 5초 갱신, manual/realtime, SIGINT/SIGTERM 종료. 리스 상실은 오류 종료하며 외부 종료 신호는 진행 중 트랜잭션을 취소하고 정상 종료한다.
  - bootstrap의 독립된 turn-offset RNG, DB 시각을 사용하는 운영 시계 명령, 지정된 3개 설계 문서와 파일 지도·데이터 모델을 갱신했다.
- 계획과 달라진 점과 이유:
  - 장수 ID는 월드 안에서만 고유하므로 `GeneralTurn`의 PK/FK는 `(worldId, generalId, slot)`이다.
  - 메모리 상태만 계속 사용하면 이후 T1-11 예턴 편집을 놓칠 수 있어, 매 턴 트랜잭션에서 현재 DB 상태를 다시 적재한다. 리스 → 월드 → 장수 행을 잠그고 commit 직전 소유자·토큰·만료를 재검사한다. 예턴 API도 같은 트랜잭션에서 장수 잠금 또는 revision 조건부 갱신을 해야 한다.
  - 로그는 장수·tick마다 한 행이며 복수 규칙 메시지는 줄바꿈으로 묶어 unique 제약으로 중복도 막는다. 실패한 명령은 상태 Effect 없이 실패 로그를 남기고 예턴을 소비한다.
  - 순서 검증은 단위 mock 대신 실제 DB의 3명·2개월 catch-up으로 확인했다. 예외 주입에 더해 별도 프로세스의 실제 SIGKILL(commit 직전/직후)도 검증했다. 프로세스 시작은 30초, 관련 테스트는 60초까지 기다린다.
  - 기존 월드의 저장된 nextTurnTick·초기 해시는 바꾸지 않는다. 분산 배치는 새 월드 생성부터 적용한다. 운영 중 턴 간격 변경과 NOTIFY/SSE는 이 작업에서 제공하지 않는다.
- 검증 결과:
  - `pnpm check`: Prisma 생성·전체 lint·전체 타입 검사·단위 14개 파일/103개 테스트 통과.
  - `pnpm test:int`: 실제 PostgreSQL 4개 파일·30개 테스트 통과. 턴 시각 경계·성공/실패·30칸 당김·revision·순서·catch-up·정지/재개·역행·동시 획득/프로세스·만료·낡은 토큰·전체 롤백·SIGKILL 전후 재시작·CLI 정상 종료를 포함한다.
  - `pnpm db:migrate`: 로컬 개발 DB migration 적용. 테스트 DB는 `pnpm test:int`에서 적용했다.
  - `pnpm --filter @opensamguk/db exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`: 빈 migration, DB 구조와 schema 일치.
  - `git diff --check`: 통과. 커밋·푸시는 하지 않았다. AC-M1-10·M1-11은 Claude 리뷰 전이므로 완료로 표시하지 않는다.

### 리뷰 반영 (Codex, 2026-10-20)

- 필수 1번: `controlClock`이 `World FOR UPDATE`를 먼저 획득한 뒤 최신 상태와 DB 시각을 읽는다. 엔진이 올린 revision을 보고 기다렸다가 정지·재개하므로 정상 명령이 경합 오류로 거부되지 않는다. 이미 정지한 월드의 중복 정지처럼 잘못된 전환은 계속 거부한다.
- 필수 2번: 실행할 턴이 없으면 `loadWorld`를 호출하지 않고 기존 메모리 사본을 유지한다. realtime 체크포인트는 monotonic 시계 기준 **5초마다**, 턴 실행 시에는 해당 트랜잭션에 함께 저장한다. manual은 호출한 목표 tick을 저장하고 정지 상태에서는 모두 쓰기를 생략한다.
- 체크포인트 사이 벽시계 역행도 보호하도록 `checkpointClock`에 관측한 최소 tick을 전달한다. tick만 올리고 기준 시각을 두면 시간이 중복 계산될 수 있어 기준 시각도 함께 옮긴다. 게임 규칙·자투리 tick 보존은 rules 안에 유지했다.
- 선택 지적: `LeaseLostError`의 이름·이유를 출력해 일반 실행 실패와 구분한다. 원본 DB 오류는 계속 감춰 연결 정보가 로그에 나오지 않게 한다.
- 관련 런타임·게임 시계·요청/저장 문서를 현재 동작에 맞췄다. migration·프론트 파일은 바꾸지 않았다.
- 검증: `pnpm test:int` 실제 PostgreSQL **4개 파일/33개 통과**. 새 회귀 검증은 다음과 같다.
  - PostgreSQL `pg_blocking_pids`로 운영 명령이 실제 쓰기 잠금을 기다리는 것을 확인한 후, 최신 revision으로 정지 성공.
  - `runEngine` 실행 중 pause/resume **80회 전부 성공**. 정지 중 실행 기한이 지난 턴을 넣어도 실행·로그·tick이 바뀌지 않음.
  - 실제 DB 폴링에서 5초 전까지 시계 revision 불변, 5초 경계에 1회 저장, 정지 중 쓰기 없음. `loadWorld`는 교체하지 않은 호출 관찰 spy로 **0회** 확인.
  - 저장 전 관측 tick을 유지하는 역행 통합 검증과, 기준 시각 복귀 뒤 시간 중복 계산을 막는 순수 시계 단위 검증.
- 최종 검사: `pnpm check` Prisma 생성·전체 lint·전체 타입 검사·단위 **15개 파일/106개 통과**, `git diff --check` 통과. 대기열은 `리뷰`로 돌려 Claude 재리뷰를 기다린다. 커밋·푸시는 하지 않았다.

  - `checkpointClock`이 자투리 tick을 보존한다 (100ms마다 저장해도 시계가 느려지지 않음). `databaseNow`와 `expiresAt`은 모두 UTC `timestamp`로 같은 기준.
  - `GeneralTurn`의 `(worldId, generalId, slot)` 키, `GeneralLog`의 장수·tick 고유 제약, `turnRevision` 증가는 T1-11의 revision 검사(AC-M1-08)와 맞는다. 장수 행 잠금 뒤에 읽으므로 `예턴이 변경되어…` 오류는 사실상 나지 않는다.
  - 채울 문서 3곳(runtime §1·§4, request-turn-persistence §3·§4, game-clock §5)이 채워져 있다.
- 고칠 것:
  1. **엔진이 도는 동안 `world:pause`·`resume`이 절반 가까이 실패한다.** 리뷰 재현: realtime 엔진 실행 중 `controlClock` pause/resume **80회 중 37회 실패** ("다른 명령이 먼저 시계를 바꿨습니다"). 원인은 둘이다.
     - `turnLoop.ts` `step()`이 실행할 턴이 없어도 100ms마다 `World` 행을 `FOR UPDATE`로 잡고 `clockTick`·`clockAnchorAt`·`clockRevision`을 갱신한다.
     - `world/clock.ts` `controlClock`은 행을 잠그지 않고 읽은 뒤 `clockRevision` 조건으로 갱신한다. 그사이 엔진이 revision을 올리면 실패한다.
     - 고치는 방향: `controlClock`은 읽기 전에 `World` 행을 `FOR UPDATE`로 잠가 엔진과 **기다렸다가 직렬화**한다 (game-clock §5가 이미 그렇게 적혀 있다). 그리고 엔진은 턴을 실행했을 때만, 아니면 몇 초에 한 번만 시계를 체크포인트한다.
     - 테스트: 엔진(`runEngine`)이 도는 중에 pause/resume을 여러 번 해도 모두 성공하고, 정지 동안 턴이 실행되지 않는다.
  2. **실행할 턴이 없는 100ms 폴링마다 월드 전체(`loadWorld`: 도시 94·장수 수백·외교)를 읽는다.** 1번의 쓰기와 합치면 쉬는 엔진 하나가 초당 10번씩 월드 전체를 읽고 `World` 행을 쓴다. 실행할 장수(`due`)가 없으면 적재와 쓰기를 건너뛴다.
- 고치면 좋은 것 (통과를 막지 않음):
  - `index.ts`의 `main().catch`가 모든 오류를 같은 한 줄로 바꾼다. 연결 문자열 노출을 막는 의도는 맞지만, `LeaseLostError`처럼 우리가 만든 오류는 이름·메시지를 남겨야 운영자가 "실행권 상실"과 "DB 연결 실패"를 구분한다.
