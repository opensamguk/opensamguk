### 2.2 등록

규칙 PR이 아래 세 곳에 자기 줄을 더한다([누락 명령 문서](./mvp-command-gaps.md) 3.2, 9절).

- `ext/registry.ts:3`의 `extensionCommands`에 정의 한 줄
- `ext/state.ts:23`의 `extCommandBindings`에 `{ commandKey, target: 'general', sliceKeys }` 한 줄. 상태가 없으면 `sliceKeys: []`
- 새 조각을 처음 만드는 행은 `ext/state.ts:22`의 `extSlices`에 조각 한 줄

`sliceKeys`에 넣는 조각은 같은 PR이나 먼저 병합된 PR에서 `extSlices`에 등록돼 있어야 한다. `validateRegistry`는 등록되지 않은 조각 key를 참조하는 관계를 보면 켠 명령과 상관없이 예외를 낸다(`ext/state.ts:65-68`). 이 검사는 `createExtState`의 `enabled === null` 분기보다 먼저(`:84`), 그리고 `cloneExtStateWithRegistry`에서도(`:111`) 돈다. 그래서 다른 행이 소유한 조각을 쓰는 행은 그 조각을 등록하는 행을 구현 선행에 둔다. 이 묶음에서는 `generalProficiency`(처음 쓰는 쪽은 T4-60 PR 0, [T4-60](./T4-60.md) 2.5)와 T4-25 특기 조각이 그렇다.

위치는 명세 §7 순서(T4-31 뒤 T4-57~T4-75 ID 오름차순)의 자기 자리다. 병합 직전 최신 main에서 넣고 앞 ID가 없으면 그 자리를 비워 둔 채 넣는다. 이 순서가 병합 선행을 만들지 않는다. `ext/registry.test.ts:24-29`는 운영 목록이 비어 있다고 단언하므로 처음 병합하는 확장 행이 그 단언을 실제 목록 대조로 바꾸고 시험 key 목록(`verifyCatalog`의 셋째 인자)에 자기 key를 더한다. 뒤 행은 key만 더한다.

명령 정의는 `defineCommand({ key: '…', target: '…', … })` 호출이나 객체 리터럴에 key·target을 글자 그대로 둔다. 대응표 도구(`tools/command-coverage.mjs`)는 그 두 모양만 해석하고 정의를 만드는 factory는 읽지 못한다([T4-02 리뷰](./T4-02.md#리뷰-claude), T4-05 `makeStratagem` 사례). 공통 계산은 `check`·`change` 안에서 부르는 함수로만 나눈다.

등록만으로는 어떤 월드에서도 켜지지 않는다. `createCommandResolver`는 프리셋에 켠 key만 받으므로(`resolve.ts:37-43`) T4-03 전에는 운영 경로에서 이 key가 쓰이지 않는다.

### 2.3 효과 방식

- `Effect`(`effects.ts:6-11`)의 필드 변경만으로 끝나는 명령은 [T4-05](./T4-05.md) 4.2처럼 `CommandDef`를 직접 만들어 필드 효과만 낸다. 해당: T4-59 증여, T4-64 견문(능력 경험을 뺄 때).
- 확장 상태 조각이나 `Effect`에 없는 칸(`age`, 능력치, `birthYear`, 새 장수)을 바꾸는 명령은 `defineCommand`(`support.ts:27-59`)로 복제 상태를 바꾸고 `{ kind: 'world' }` 효과 하나를 낸다. `cloneWorld`가 운영 조각 목록으로 `ext`를 복제하므로(`clone.ts:10-11`) 조각은 같은 PR에서 `extSlices`에 등록돼 있어야 한다. 해당: T4-57, T4-58, T4-60~T4-63, T4-65, T4-66.
- 두 방식을 섞지 않는다. world 효과 뒤의 필드 효과는 `applyEffects`(`effects.ts:13-40`)가 처리하지만 효과 목록 골든이 읽기 어려워진다.

### 2.4 순수성과 RNG

- `execute`는 `view`를 읽기만 한다(T4-05 4.8). 같은 `view`와 시드로 두 번 실행한 결과가 깊은 비교로 같고 `view`는 실행 전과 같다.
- RNG는 `runGeneralTurn`이 넘기는 `rngFor(seed, 'turn', tick, generalId)`(`turn.ts:77`) 하나만 쓴다. 새 스트림 이름을 만들지 않는다. 원작 `nextInt(min, max + 1)`은 `rng.int(min, max)`, `nextFloat1()`은 `rng.next()`로 옮긴다.
- 가중치 뽑기는 원작 `pickByWeight`와 같은 꼴이다. 가중치가 0 이하인 항목을 빼고 `cursor = rng.next() × 합`에서 차례로 빼며 처음 0 이하가 되는 항목을 고른다. 이 함수 `pickWeighted(rng, entries)`는 `ext/common/pick.ts`에 두고 이 묶음에서 먼저 병합하는 행이 만든다. T4-60 단련, T4-64 견문, T4-66 인재탐색이 import한다.
- 현재 시각, `Math.random()`, DB를 쓰지 않는다. 연월은 `toGameDate(view.startYear, actor.tick ?? 0)`(`clock.ts:67-72`)로 얻는다.

### 2.5 검사 실패

- 새 `Failure.code`를 만들지 않는다. 기존 20개(`types.ts:14-34`)에서 고른다. 재사용 대기·나이·상태 조건은 `BAD_STATE`, 대상 문제는 `BAD_TARGET`, 자원은 `NO_GOLD`·`NO_RICE`, 병력은 `NO_CREW`다.
- 소속·자기 도시·보급 검사는 `ownCity`(`support.ts:11-19`)를 쓰고 문구도 그대로다. 원작 `occupiedCity` + `suppliedCity`가 이것에 해당한다. 원작이 `occupiedCity`만 쓰고 보급을 보지 않는 명령은 보급 검사를 넣지 않는다(T4-61, T4-62, T4-63). 이 경우 같은 문구를 쓰는 작은 검사를 그 명령에 둔다.
- 검사 실패의 장수 로그 기록은 기존 턴 실행 경로가 한다. 확률 실패나 빈 결과는 검사 실패가 아니다.

### 2.6 로그·보고·국가 기록

원작 문구를 옮기지 않고 [글쓰기 규칙](../writing-style.md)으로 새로 쓴다. 기존 명령처럼 `명령 이름: 내용` 꼴이고(`military.ts:60`, T4-05 4.7) 이름이나 변수 뒤에는 조사를 붙이지 않는다. 장수 로그는 `logs`, 다른 장수에게 가는 알림은 `reports`, 국가 기록은 `history`다(`types.ts:41-48`). 원작의 전체 공지(`LogScope.SYSTEM`)는 K3에 따라 국가 기록으로 대신한다.

## 3. 재사용 대기 조각 (T4-57·T4-58 공유)

### 3.1 원작

원작의 재사용 대기는 명령 정의의 `getPostReqTurn()`이다. 두 특기 초기화가 60을 낸다(내정 L46-48, 전투 L46-48). 이 묶음의 다른 여덟 명령은 0이다.

### 3.2 조각 `generalCooldown`

`ext/cooldown/state.ts`(새 파일, T4-57과 T4-58 가운데 먼저 병합하는 쪽이 만든다)가 조각 하나를 낸다.

```ts
// 값: { [generalId]: { [commandKey]: readyTick } }
export const generalCooldownSlice: ExtSlice<Record<string, Record<string, number>>>;
export function cooldownReadyTick(view: WorldView, generalId: number, commandKey: string): number; // 없으면 0
export function setCooldown(state: WorldState, generalId: number, commandKey: string, readyTick: number): void;
```

- `create`는 `{}`를 낸다. 시나리오 장수와 나중에 만든 장수 모두 칸이 없으면 대기 없음이다.
- `validate`는 두 겹 객체이고 바깥 key가 양의 정수 문자열, 안쪽 key가 확장 명령 key 꼴(`^[a-z][a-z0-9_]*$`), 값이 0 이상 안전 정수인지 본다. 공통 JSON 검사(`state.ts:30-49`)는 T4-02가 먼저 한다.
- `clone`은 두 겹을 새 객체로 복제한다.
- 대기 시작 시각은 실행 tick이다. `readyTick = actor.tick + 60 × TICKS_PER_MONTH`(K5 (가), S1). 실행 검사는 `actor.tick < readyTick`이면 실패다. 그래서 실행 뒤 60번째 장수 턴에서 다시 쓸 수 있다.
- 이 조각은 장수 명령의 재사용 대기만 다룬다. 국가 명령의 재사용 대기(T4-06 등)와 하나로 둘지는 쟁점 Q57-1이다.

## 4. 기술 계약 초안 (Codex 계획 기술 검토 전)

### 4.1 특기 초기화 공통 함수

`ext/trait_reset/base.ts`(새 파일, T4-57과 T4-58 가운데 먼저 병합하는 쪽)가 검사 함수 `checkTraitReset(view, actor, slot, commandKey)`와 변경 함수 `applyTraitReset(state, actor, slot, commandKey)`를 낸다. `slot`은 `'domestic' | 'war'`이다. 정의 자체는 만들지 않는다(2.2의 대응표 도구 조건). T4-57은 `ext/reset_domestic_trait/reset_domestic_trait.ts`에서 아래 꼴로 정의한다.

```ts
export const reset_domestic_trait = defineCommand({
  key: 'reset_domestic_trait',
  name: '내정 특기 초기화',
  category: 'personal',
  target: 'general',
  args: noArgs,
  check: (view, actor) => checkTraitReset(view, actor, 'domestic', 'reset_domestic_trait'),
  change: (state, actor) => applyTraitReset(state, actor, 'domestic', 'reset_domestic_trait'),
});
```

`defineCommand`(`support.ts:27-59`)의 `category` 타입에 `personal`이 있다.

### 4.4 준비 턴

원작 준비 턴은 1이다. U-01은 원작처럼 같은 명령을 연속 칸에 예약해야 실행하는 쪽으로 결정됐고(D-027) 기간은 미결정이다. 이 명령은 T4-07이 정할 선언 자리에 준비 턴 수를 둔다. 연속 칸 수가 준비 턴 + 1인지, 중간 칸의 진행 로그를 명령이 내는지 기제가 내는지는 T4-07 계약이 정한다(쟁점 Q57-2). 명령이 낸다면 문구는 `내정 특기 초기화 준비 ({단계}/{전체})`다. 아래 검사와 효과는 마지막 칸, 곧 실제 실행 칸에서만 일어난다.
