## 0. 이 문서의 위치

[Phase 2 확장 기술 명세](./phase2-expansion.md)(이하 명세) §6의 T4-46 행, §9 U-17, AC-P2-24를 파일·시험·반영 순서로 구체화한다. 명세 §1대로 M2의 두 번째 시나리오(AC-M2-01)는 여기서 세지 않는다.

이 작업은 명세가 결정 없이 할 수 있다고 적은 후보의 로더 호환 점검을 먼저 마쳤다(4절). 그 결과 U-17에 붙일 사실이 생겼다. 후보 11개 가운데 6개는 지금 로더 검사를 그대로 통과하고 5개는 원작 자료 그대로는 월드를 만들 수 없다.

착수 조건이다.

1. 이 문서의 Codex 계획 기술 검토(G-03).
2. U-17 답(넣을 목록)과 그 목록에 걸린 U46-2·U46-3 답.
3. D-028과의 순서(T46-Q1). 지금 시나리오는 `resources/scenario/<키>.json` 파일이지만 T4-77은 내장 JSON을 초기화 SQL의 불변 판으로 옮기고 PR 2에서 파일을 지운다. 이 작업은 T4-77 PR 1보다 먼저 병합하거나 PR 1과 PR 2 사이에 병합해야 같은 길로 들어간다.

## 2. D-028과의 관계

- AC-P2-26(D-028)은 내장 JSON을 초기화 SQL의 같은 키 불변 판으로 옮기고 저장소에서 지운다. T4-77 계획은 PR 1에서 다섯 행(`che`, `1030`, `basic`, `default`, `rtk14-map`)을 SQL로 만들고 PR 2에서 JSON을 지운다. 변환기의 JSON 입력은 PR 1 동안만 있다.
- 그래서 새 시나리오가 내장 판으로 들어가는 길은 둘이다. 하나는 이 작업이 T4-77 PR 1보다 먼저 병합되어 JSON 파일로 들어가고 PR 1이 함께 SQL로 옮기는 길이다. 다른 하나는 PR 1과 PR 2 사이에 들어가 JSON 파일과 재생성한 SQL을 함께 넣는 길이다. PR 2 뒤에는 내장 판을 더할 길이 계획에 없다. T4-78의 저장소 함수로 게시하는 운영 판이 될 뿐이고 새 DB(CI)에는 생기지 않는다(T46-Q1).
- 어느 길이든 시나리오 판의 `mapKey`는 `che`다(T4-77 계약 4의 `1030`과 같음). 이름은 내용 `id`와 같은 숫자 키다(`1010` 등).
- 지도 판 고르기(T4-79)가 생겨도 이 작업의 시나리오는 모두 `che` 1판 지도를 쓴다.

## 3. 계약

### 3.1 파일 만들기

- 승인된 키마다 원작 `resources/scenario/scenario_<키>.json`을 `df6c926`에서 받아 4절의 sha256과 대조한다. 다르면 멈춘다.
- `$comment`는 `Source: core2026 df6c926 / resources/scenario/scenario_<키>.json; MIT (c) 2025 devsam. See resources/NOTICE.md.`, `id`는 키 문자열이다. 사본을 고쳤으면 `$comment` 끝에 고친 점 한 문장을 더한다.
- 쓰기는 `JSON.stringify({ $comment, id, ...원작 }, null, 2) + '\n'`이다. 원작 칸 순서와 값을 바꾸지 않는다. 고칠 때(3.2)도 해당 배열 원소만 바꾼다.
- 변환 스크립트는 커밋하지 않는다. 시험(3.3)이 결과를 묶는다.

### 3.2 사본에서 고칠 수 있는 것

U-17 답이 아래 시나리오를 넣기로 하면 사본을 이렇게 고친다. 원작 자료의 결함을 메우는 최소 수정이며 사용자 답 없이 하지 않는다.
