# 보류·제외 항목 재편입 목록

> 결정 [D-058·D-061](../product/decisions.md) · 사용자 요청 2026-11-01·02 · 상태: 실행 목록. T4-92의 상세 계획과 새 범위의 AC-P2-29~33을 등록했다. 후속 수치·상세 계획은 미확정이다.

## 배경

D-038은 통합판 v0.1의 기능 목록을 동결하면서 많은 기능을 인수 분모에서 뺐다. D-039는 공개 준비에서도 그 동결을 지켰다. D-047은 화면 개편에서 네 가지를 뺐다. 사용자가 2026-11-01 이 「하지 않는 것」 때문에 많은 기능이 빠졌다고 보고 다시 넣도록 정했다. 범위는 v0.1이 보류한 것 전부와, 제외 목록 가운데 휴대 군량·철·목재·말 자원이다. 여러 달 행군·거리별 이동(D-034)과 군현 단위 지배는 계속 제외한다.

이 문서는 다시 넣을 항목을 기존 작업에 대응시킨다. 대응할 작업이 없는 항목은 새 작업 후보로 적는다. 새 작업 후보는 아직 대기열에 올리지 않았다. 올릴 때마다 상세 계획, AC, 계획 기술 검토(G-03)를 거친다.

## 가장 빠른 개발 계획

사용자가 가장 빠른 계획을 요청했다(2026-11-01). 속도를 막는 것은 구현량보다 세 가지다. 사용자 결정이 늦게 나오는 것, 계획 검토(G-03)가 늦는 것, [Phase 2 명세](./phase2-expansion.md) §7의 공유 파일 병합 순서다. §7은 공유 파일마다 병합 순서를 정해 두었다. merge queue는 브랜치를 최신으로 맞추는 대기만 줄이고 이 선후 관계는 풀지 못한다. 그래서 구현은 처음부터 여러 브랜치에서 나란히 한다. 병합만 §7 순서를 따른다. 결정은 한 번에 모으고 새 설계 계획은 첫날부터 나란히 쓴다. 기준 인원은 이미 쓰는 병렬 세션 8~9개와 Codex 실행 작업자다. 아래 기간은 그 가정의 대략값이며 완료 약속이 아니다.

전체 기간을 정하는 것은 §7의 두 긴 사슬이다. 엔진 입력 처리 파일 사슬은 T4-56 PR 1 → T4-03 → T4-49 → T4-40 → T4-48 → T4-07 → T4-28 → T4-31 → T4-47이다. 확장 등록 사슬은 T4-02 → T4-17 → T4-20 → T4-48 → T4-52 → T4-23 → T4-53 → T4-28 → T4-31이다. 이 사슬의 앞 작업이 늦으면 전체가 늦으므로 사슬 위 작업을 먼저 맡긴다.

표는 큰 순서다. 한 작업이 등록 전·후 단계로 나뉘는 경우의 세부 병합 선행은 각 작업의 상세 계획을 따른다. 물결 4의 상세 계획은 물결 0부터 쓴다. 그러면 구현 차례가 왔을 때 G-03과 결정이 이미 끝나 있다. 같은 파일을 만지는 작업은 한 세션에 묶는다. 이렇게 하면 전체는 대략 6~9주다. 사용자 결정이 늦어지거나 G-03이 보류를 내면 그만큼 늘어난다.

더 줄이려면 §7의 등록 줄 사슬(확장 등록, 라우터 등록, export)을 「병합 직전 최신 main에서 ID 순서로 자기 줄만 더한다」는 규칙으로 바꿔 선후 관계를 없애는 방법이 있다. T4-57~T4-75에 이미 쓰는 방식이다. 이 변경은 총괄이 §7 표를 고치고 G-03을 받아야 하므로 물결 0의 결정표에 함께 올린다.

## 2026-11-02 확장 실행 순서

이 절은 D-061의 최신 범위다. 위 표의 「창고망은 넣지 않는다」와 v0.1의 해당 제외를 대체한다. 기존 기능과 새 후보는 구현을 기본 방향으로 삼는다. 이미 있는 코드는 재사용한다. 원격 main `f00ec07e`를 시작점으로 사용한다. 이전 로컬 `d82becb2`에는 이후 병합된 도시 자원·수비병, 운영·계정·부하 보완이 없어 그 시점의 목록을 최신 구현 상태로 읽지 않는다.

T4-93~96은 범위·AC 등록이며 구현 준비 완료가 아니다. 상세 계획은 각 조건을 5작업일 이하의 규칙·저장/엔진·화면·실제 인수 묶음으로 나누고 반대쪽 검토 뒤 착수한다. 전체 기능을 한 번에 켜거나 저장 칸만 더해 완료로 세지 않는다.

명령 카드는 기존 예약의 표현이다. T4-45의 소모형 패는 별도 후속으로, 패가 필요한 계략을 실행하는 엔진 트랜잭션에서 패와 자원·효과를 함께 처리한다. 동시 입력·실패·재시도에 따른 소비/반환 규칙을 그 계획에 고정한다. 기본 명령을 덱의 뽑기 운으로 막지 않는다.

자원은 정수 원장 하나에 생산·소비·출발·도착·손실의 이유를 남긴다. 창고에서 출발 차감한 양은 수송 중 재고에만 있고 도착 때 한 번 가산한다. 군량은 기존 도시/부곡 소비와 중복 차감하지 않는다. 수송은 거점 간 명령으로 처리하고 군대의 여러 달 행군을 되살리지 않는다. 경로 단절·점령·권한 상실 때 반환/노획/손실의 보존식을 상세 계획에서 정한다.

황실/봉신은 같은 월드 안의 국가 관계다. 한 국가의 상위 군주는 하나이며 순환을 거부한다. 봉신 조약을 맺었다고 사람의 예약을 대신 바꾸지 않는다. 조정 임명과 외교·공납도 기존 InputEvent 순서로 재검사하고 정산한다.

혼인과 계승은 장수 ID를 바꿔 덮어쓰지 않고 이전 인물·후계자·계승 사건을 보존한다. 사람의 동의와 단일 조작권을 확인하고 국가·직책·휘하·부곡·재산의 이전을 같은 게임 트랜잭션에서 끝낸다. NPC의 연령·사망·후계 판단은 월 tick과 시드 RNG만 사용한다. 혼인·출생의 표현은 가계 기록과 사건으로 제한한다.

유산은 종료 기수별 계정 보상과 새 장수별 사용 기록을 중복 없이 연결한다. 생성된 장수의 실제 보너스와 규칙 판을 origin에 넣어 재생 중 현재 계정 점수를 다시 조회하지 않는다. Cloudflare에서는 WorldDO와 D1을 한 트랜잭션으로 묶을 수 없으므로 동일 키의 지급/사용 요청·영수증·복구 절차가 필요하다. 지급량·상한이 정해지기 전에는 게임에 보너스를 지급하지 않는다.

### 세 채팅의 파일 소유와 공통 스타일

- 게임 기능: `codex/expanded-backlog-20261102`의 `apps/web/src/turns/`와 새 결정·AC·계획. 이후 rules/engine/server는 단계별 수정 범위를 먼저 공유한다.
- Docker: `codex/t2-15-runtime-bundles`의 배포, `shared/resource-root`·`public-images`·`request-policy`, 서버 어댑터와 이미지 외부화. D-059·D-060은 그 담당이 쓴다.
- Cloudflare: `codex/cf-p0-foundation`의 `apps/worker`·향후 `packages/cf-storage`·`docs/cloudflare/`. rules/shared/web는 upstream 변경을 정상 merge로 받는다. DO의 저장과 PG의 저장 어댑터를 게임 규칙에서 구분하지 않는다.

코드는 기존 camelCase·파일 배치·Prettier 3.9.9·ESLint 10·TS 6 strict와 한국어 문구 규칙을 따른다. 기존 helper·컴포넌트·명령 정의·InputEvent를 먼저 재사용하고 두 런타임만을 이유로 새 범용 프레임워크를 만들지 않는다. 검증·보안·접근성·데이터 손실 방지는 줄이지 않는다. Ponytail 원문은 로컬 스킬로 설치해 읽었고 프로젝트나 사용자 전역 hook은 설치하지 않았다.
