## 0. 이 문서의 위치

명세 §6 T4-20 행을 API·엔진·저장·재생 계약으로 적는다. 부대 만들기·가입·탈퇴·추방은 턴을 쓰지 않는 즉시 행동이라 API가 InputEvent로만 기록하고 엔진이 처리한다(C4, AGENTS.md §6). 집합 명령 `troop_gather`는 예턴 명령이라 T4-03의 `turns` 경로를 그대로 쓰며 이 작업이 운영 등록과 엔진 시험을 더한다.

착수 조건은 다섯이다. 이 문서의 G-03 수용, T4-49 상세 계획의 G-03 수용과 §6 쟁점의 합의, T4-19·T4-03·T4-49 구현 병합, AC-P2-11의 정식 반영이다. 명세 §6 상태는 선행 대기(C15)다. C15가 수용되기 전에는 이 작업과 T4-21을 계약 준비로 올리지 않는다(C4).

## 계획 (Claude)

### 목표

AC-P2-11의 남은 몫을 만든다.

- 부대 만들기·가입·탈퇴·추방이 C15 계약의 InputEvent로 기록되고 엔진이 처리해 `APPLIED` 또는 이유 코드가 있는 `REJECTED`로 끝난다. 결과와 부대 상태는 한 트랜잭션에 저장되고 재생된다.
- 부대장이 예약한 집합이 엔진 턴에서 실행되어 같은 국가 부대원이 부대장 도시로 모인다.

- 집합을 켜지 않은 월드에서는 부대 API가 거부되고 집합 명령이 목록에 없다. 그 월드에서도 형식 1 월드는 기록 바이트와 상태 해시가 지금과 같다. 규칙 기능 없는 형식 3 월드는 상태 해시가 같은 입력의 형식 1 월드와 같다(바이트는 비교하지 않는다, 3.2 P10).

## 2. 계약

### 2.1 저장

부대 상태는 T4-19의 `troop` 조각 하나이며 T4-03의 `WorldExtSlice` 행(월드당 key `troop` 한 행)에 저장한다. 그래서 이 작업은 schema와 migration을 고치지 않는다. 명세 C8의 S3 자리는 쓰지 않으며 뒤 작업의 migration 순서는 그대로 당겨진다(쟁점 T20-Q6).

조각은 `troop_gather`가 켜진 월드에만 있다. 끈 월드에는 행이 없고 `WorldState.ext`에도 키가 없다(C3, T4-03 E4).

### 2.2 즉시 행동 kind

| kind | payload (zod strict) | 판정 (T4-19) |
| ---- | -------------------- | ------------ |
| `troop.create` | `{ name: string }` (1~64자, 폭 검사는 판정이 한다) | `createTroop` |
| `troop.join` | `{ troopId: number }` (양의 정수) | `joinTroop` |
| `troop.leave` | `{}` | `leaveTroop` |
| `troop.kick` | `{ memberId: number }` (양의 정수) | `kickTroopMember` |

- payload에 행위 장수 번호를 넣지 않는다. 처리 때 행위 장수는 InputEvent의 `userId`로 그 월드의 장수를 다시 찾는다(C15 처리 시점 재검사). 접수 때 기록한 `generalId`와 다르면 `REJECTED` `ACTOR_CHANGED`다.
- result는 kind 공통이다. `APPLIED`: `{ troopId: number | null; changed: number[] }`. `REJECTED`: `{ code: string; message: string }`. 처리 tick과 sequence는 result에 넣지 않는다. 공통 처리기가 InputEvent의 `tick`·`sequence` 열에 쓰고 archive 3 입력의 `tick`으로 나간다(T2-26 통합 입력 처리기 6단계, 입력 재생). 코드는 T4-19 `TroopCode`에 처리기 재검사 코드(`WORLD_CLOSED`, `ACTOR_INACTIVE`, `ACTOR_CHANGED`, `COMMAND_DISABLED`)를 더한 것이다. 기능 `ext`가 꺼진 월드의 `FEATURE_DISABLED`만 공통 처리기가 처리기를 부르기 전에 낸다(T2-26 4단계). 월드 상태 판정은 처리기 몫이다(2.4 1단계).

`applyTroopInput(state, kind, payload, { generalId, tick, sequence })`가 kind를 판정 함수로 보내고 `{ state, result }`를 낸다. 성공이면 `state.ext.troop`만 바뀐 새 상태다. 실패면 상태는 그대로이고 result가 이유다. 엔진 처리와 순수 재생이 이 함수 하나를 부른다(T2-07 `applyTreatyInput`과 같은 꼴). 난수를 쓰지 않으므로 C15의 `rngFor(seed, 'input', kind, sequence)` 스트림은 만들지 않는다.

### 2.3 API (`troop` 라우터)

화면 계약은 T2-07 조약과 같은 모양을 쓴다. T4-49가 다른 공통 모양을 정하면 그것을 따른다(쟁점 T20-Q1).

```ts
type RequestId = string; // 화면이 행동 하나마다 만드는 UUID v4
type Allowed = { ok: true } | { ok: false; code: string; reason: string };
type TroopMember = { id: number; name: string; cityKey: number; cityName: string };
type TroopRow = {
  troopId: number;
  name: string;
  leader: TroopMember;
  members: TroopMember[]; // 번호 오름차순
  canJoin: Allowed; // 화면 안내용. 최종 판정은 엔진
};
type TroopList = {
  me: { generalId: number; troopId: number | null; leader: boolean; canCreate: Allowed; canLeave: Allowed } | null;
  troops: TroopRow[]; // 내 국가 부대만. 재야·장수 없음이면 []
  pending: { requestId: RequestId; kind: 'create' | 'join' | 'leave' | 'kick' }[]; // 내 처리 중 요청
};
type InputOutcome =
  | { status: 'applied'; requestId: RequestId; troopId: number | null }
  | { status: 'pending'; requestId: RequestId };
type RequestState = InputOutcome | { status: 'rejected'; requestId: RequestId; code: string; reason: string };

// troop.list({ worldId }) → TroopList                                   query
// troop.create({ worldId, requestId, name }) → InputOutcome             mutation
// troop.join({ worldId, requestId, troopId }) → InputOutcome            mutation
// troop.leave({ worldId, requestId }) → InputOutcome                    mutation
// troop.kick({ worldId, requestId, memberId }) → InputOutcome           mutation
// troop.request({ worldId, requestId }) → RequestState                  query
```

| 단계 | 하는 일 |
| ---- | ------- |
| 입력 | 모든 입력은 `z.strictObject`다. `generalId`·`userId` 같은 행위자 칸을 넣으면 `BAD_REQUEST`다 |
| 인증·월드 | `protectedProcedure`. 월드가 없으면 `NOT_FOUND`. 세션의 그 월드 장수가 없으면 변경 요청은 `PRECONDITION_FAILED` `장수가 없습니다.`, 목록은 `me: null` |
| 켜짐 | T2-26 서버 `requireRuleFeature(world, 'ext')`를 먼저 부른다. 그 다음 그 월드 resolver(T4-03 E1)에 `troop_gather`가 없으면 같은 코드와 문구로 거부한다. 여섯 절차 모두 `PRECONDITION_FAILED` `이 월드에서 켜지 않은 기능입니다.` (쟁점 T20-Q2) |
| 종료 월드 | 변경 절차 넷은 켜짐 검사 뒤 월드가 ENDED면 기존 예턴 저장과 같은 `PRECONDITION_FAILED` `종료된 월드입니다.`(`apps/server/src/routers/turns.ts:39`)로 거부하고 기록하지 않는다(C15). 읽기 둘은 그대로 된다. 접수와 처리 사이에 끝난 월드의 PENDING은 엔진 처리기가 `WORLD_CLOSED`로 닫는다(2.4 1단계) |
| 멱등 | 키는 `troop.<kind>:<requestId>`다. 같은 키가 있으면 payload를 key 순서 없이 비교해 같으면 그 입력의 지금 상태, 다르면 `CONFLICT`다. 이 경로에서는 지금 소속을 다시 보지 않는다 |
| 겹침 | 새 키인데 같은 장수의 `troop.*` `PENDING` 입력이 이미 있으면 `CONFLICT` `요청을 처리하는 중입니다.` |
| 안내 검사 | 새 요청일 때만 T4-19 판정을 지금 상태에 한 번 돌린다. 실패해도 기록은 한다. 이유는 엔진 처리 결과로만 확정한다. 접수 거부는 형식·인증·켜짐·멱등·겹침뿐이다 |
| 기록 | `PENDING` InputEvent 하나. `generalId`는 세션 장수, `payload`는 `requestId`를 뺀 내용 |
| 대기 | T2-07처럼 같은 요청 안에서 최대 5초 다시 읽는다. `APPLIED`는 `applied`, `REJECTED`는 `PRECONDITION_FAILED`와 기록된 이유 문장, 시간이 지나면 `pending` |
| 결과 회수 | `troop.request`는 세션 사용자가 만든 입력만 읽는다. 남의 `requestId`는 있어도 `NOT_FOUND`다. 두 종료 상태 모두 돌려주기 직전에 세션과 계정 `ACTIVE`를 다시 본다(T2-07 결과 회수 절) |
| 목록 | `troop.list`는 서버가 지금 상태에 `reconcileTroops`를 적용한 값에서 내 국가 부대만 낸다. 다른 국가 부대의 이름·인원은 내지 않는다. 장수 이름·도시는 같은 국가 장수라 `visibility.ts`의 공개 범위 안이다 |

목록은 `visibility.ts`(명세 §7 T4-35 → T4-12 → T4-25 → T4-38)를 고치지 않는다. 같은 국가 판정은 그 파일의 `visibility(viewer).general`을 import해 쓴다.

### 2.4 엔진 처리

`apps/engine/src/troopInputs.ts`가 kind 넷의 처리기를 등록한다. 등록 자리와 처리기 모양은 T2-26(`fa516aa` `docs/plans/T2-26.md`) 통합 입력 처리기의 `QueuedInputHandler`(`(tx, world, event, context: { tick, sequence }) => { status, result, generalId? }`)이며 T4-49가 그 위에 즉시 행동 계약을 더한다. 공통 처리기가 리스·World 잠금, id 순 꺼내기, 기능 확인, 판정 전 sequence 발급, InputEvent 종료 갱신을 맡는다. 처리기는 아래만 한다.

1. 월드 상태. 잠근 World 행의 `status`가 `RUNNING`이 아니면 게임 상태를 읽거나 쓰지 않고 `WORLD_CLOSED`로 돌려준다. T2-26 공통 처리기는 기능 검사와 결과 기록만 맡고 월드 상태를 보지 않는다. `general.create` 처리기가 지금 판정(`inputs.ts:37`)을 그대로 옮기는 것과 같은 자리다. T2-26 C2에서 처리기가 불리는 RUNNING 밖 걸음은 PREOPEN, ENDED, 경계를 넘기지 않은 PAUSED다. 그래서 종료 뒤 남은 PENDING은 여기서 거절되어 `afterEnd`로 간다. 경계를 넘긴 PAUSED 월드의 입력은 공통 처리기가 부르지 않아 PENDING으로 남는다.
2. 행위 계정이 `ACTIVE`가 아니면 `ACTOR_INACTIVE`. 그 월드의 그 계정 장수가 접수 때 `generalId`와 다르면 `ACTOR_CHANGED`. 월드가 `troop_gather`를 끈 상태면 `COMMAND_DISABLED`.
3. `loadWorld`로 읽은 상태에 `applyTroopInput`을 부른다.
4. 성공이면 T4-03 `writeWorldExtChanges`로 `troop` 행을 쓰고 `{ status: 'APPLIED', result, generalId }`를 돌려준다. 실패면 게임 상태를 쓰지 않고 `{ status: 'REJECTED', result }`를 돌려준다. 처리기는 InputEvent를 쓰지 않는다. 공통 처리기가 돌려받은 값으로 `status`·`sequence`·`tick`·`result`·`generalId`를 `where: { id, status: 'PENDING' }` 조건 갱신 한 번에 쓰고 바뀐 행이 1이 아니면 트랜잭션을 되돌린다(T2-26 6단계). 조각 쓰기와 그 갱신이 같은 트랜잭션이다(C5).

PAUSED의 처리는 위 1단계와 T2-26 C2를 따르고 C15와의 차이는 T4-49가 정한다(쟁점 T20-Q3).

부대 정리(T4-19 2.4)는 T4-49의 조각별 정리 훅에 `reconcileTroops`를 등록하는 것으로 잇는다. 그러면 부대장 하야·국가 멸망이 일어난 그 턴·월간 트랜잭션에서 조각 행도 함께 바뀐다(C15 같은 트랜잭션 범위). 훅이 없으면 이 작업을 병합하지 않는다(T4-19 T19-Q1).

### 2.5 집합 명령 연결

- 운영 등록: `extensionCommands`에 `troop_gather`, `extSlices`에 `troopSlice`, `extCommandBindings`에 `{ commandKey: 'troop_gather', target: 'general', sliceKeys: ['troop'] }`.
- 저장·사전 검사·실행·표시는 T4-03의 `turns`·`commands.list`·엔진 턴 경로를 그대로 쓴다. 이 작업은 시험만 더한다.
- 등록 뒤 T4-02 확장 대조 시험(`ext/registry.test.ts`)이 `troop_gather.test.ts`(T4-19)의 존재를 확인한다. 대응표 `troop_gather` 행의 단계 증거는 이 작업의 시험 이름과 정확 SHA로 채운다(대응표 파일은 명령 작업이 자기 행만 고친다, 명세 §7).

### 2.6 재생

순수 재생은 T2-26(`fa516aa` `docs/plans/T2-26.md`)의 `InputKindDefinition`에 부대 kind 넷을 `{ feature: 'ext', route: 'queued', apply }`로 등록한다. `apply`는 APPLIED만 받고 기록된 `input.sequence`와 `input.tick`(archive 3에서만 값이 있다)으로 `applyTroopInput`을 다시 불러 같은 result가 나오는지 확인한다. 다르면 재생 실패다. `REJECTED`는 공통 재생이 건너뛴다. 처리 tick이 그 시점 월 창 안인지는 T2-26 F15가 `input.tick`으로 본다. result에 tick이 없으므로 두 값이 어긋날 자리가 없다. 켠 월드의 기록 형식은 T2-26 origin 3·archive 3과 그 위의 T4-03 `ext` 기능 자료를 따른다.
