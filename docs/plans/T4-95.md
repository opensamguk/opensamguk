# T4-95 혼인·후계자·다세대 계승 (구현 대조판)

현재 범위는 D-065에 따라 기존 레포의 PG·서버·엔진·웹이다. 아래 CF 이식·대조 항목은 이번 작업과 완료 조건에서 제외한다.

> 대기열: T4-95 · AC: AC-P2-32 전체, AC-P2-31·AC-P2-35의 접점 몫 · 백엔드(rules·engine·server·PG): Codex · 계획·화면 설계(Artifacts)·화면 코드: Claude · 독립 리뷰: 구현하지 않은 쪽 · CF 어댑터: 기존 CF 담당 · 상태: 구현 진행 중(2026-11-03). 작업 트리 `lineage-20261103`, 기준 `cc40c7a9`(T4-94 병합 포함)와 미커밋 구현을 읽고 본문 전체를 그 계약에 맞췄다. 실측은 「검증 현황」에 적은 것만 인정한다. 정식 491명 시즌 진행, governance·campaign을 켠 실제 통합, CF는 아직 증거가 없다. AC-P2-32는 진행 중이다. 2026-11-03 사용자 확정(성별 자료, 남녀 혼인·출생, 검수 인물과 새 생성 장수부터 적용, 이름 추정 금지)과 T4-96 상한 승인(별도 작업), Codex 검토 2건(출생 금·쌀 0, 가주 부모), 사람 신원 전환 수용 조건을 유지한다

## 계획

### 목표
새 규칙 판 `lineage-v1`에서 성별 기록, 나이 증가, NPC 자동 사망·계승, 남녀 혼인(사람 동의·NPC 판정), 같은 기수 안의 출생과 능력치 물려받기, 사람의 후계 지정과 명시 확인 계승, 공석 군주 자리의 사람 명시 청구를 실제 효과까지 만든다. 계승은 조작권·직책·금·쌀·병력·부곡·휘하를 한 게임 트랜잭션에서 옮긴다. 장수 ID와 성별은 덮어쓰지 않는다. 같은 규칙·DTO·입력 기록으로 CF에서도 대조하도록 AC-P2-35 몫의 계약을 고정한다.

근거는 D-061의 두 줄이다(`decisions.md:585-586`). 혼인·혈연·후계자를 기록하고 NPC는 자동 진행하며 사람은 후계자를 지정한 뒤 직접 계승을 확정한다. 사람 장수를 수명만으로 바꾸지 않는다. 공석 군주 처리는 같은 「사람은 명시 동의로만 바뀐다」 원칙에 따라 명시 청구 방식으로 설계한다. 성별 자료와 남녀 혼인·출생 자격은 2026-11-03 사용자 확정(U95-1)이다. 나머지 수치·순위 규칙은 이 계획의 엔지니어링 제안이다.

### 완료 조건 (이 작업 한정)
- `lineage-v1`을 켠 새 원생성 월드에서 실제 PG·HTTP·엔진·화면으로 아래가 동작한다.
  - 성별: 지원 시나리오(1030·integration191)의 원생성 장수는 검수 원장의 값 또는 `UNKNOWN`, 새 생성 장수는 플레이어가 고른 `MALE`·`FEMALE`, 출생 장수는 원생성 seed 난수와 명시 config로 정한 값이 저장·재생되고 바뀌지 않는다
  - 나이 증가
  - NPC 사망과 계승, NPC 후보가 없을 때의 공석과 뒤이은 NPC 채움
  - 공석 국가의 사람 장수 `ruler.claim`
  - 사람·NPC 남녀 혼인. `UNKNOWN`과 같은 성별 쌍은 거부된다
  - 출생과 등장. 출생은 금·쌀 총량을 바꾸지 않는다(출생 장수 금·쌀 0)
  - 후계 지정과 확인 계승
  - 사람 계승 직후 같은 계정의 화면이 후계자로 바뀌고 전임자 기준으로 열린 양식·확인 대화상자가 무효가 된다
- 같은 원생성·시드·입력의 `exportReplay` 해시가 엔진 저장 상태와 같다.
- 기능을 끈 월드의 상태·해시·RNG 소비·DTO 모양이 지금과 같다. 장수에 `sex` 키가 없고 DB 열은 null이다.
- AC-P2-32의 거부 사례를 실제 저장소에서 확인한다. 대상은 자기 혼인, 성별 부적격 혼인, 중복 계승, 부적격 후계자, 타인 수락, 공석 아닌 국가 청구, 동시 청구다. 동시 입력, 사망·멸망 경계, 재시작, 재생도 함께 확인한다.
- 독립 리뷰, 필수 CI, 정상 병합을 각각 거친다. CF 동등성은 실측 뒤에만 주장한다.
- 정식 491명 시즌 진행, 성능, 128MiB, CF 통과는 이 계획에서 증명된 것으로 쓰지 않는다. 원장의 행 수·성별 분포는 원장 파일만 기록한다.

### 하지 않는 것
- 기수 간 능력치 유산(T4-96, 상한 승인됨·별도 작업). 출생 장수와 후계자는 유산을 받지 않고 `general.create` 경로에는 `sex` 한 칸만 더한다.
- 출생 때 부모 재산 이전이나 새 금·쌀 지급. 출생 장수의 돈은 이후 기존 급여·세입과 계승으로만 생긴다.
- 이혼, 입양, 비혈연 후계자(사람용), 첩·측실 같은 별도 신분.
- 사람 장수의 수명 사망·강제 교체. 사람을 동의 없이 군주로 올리기. 공석을 이유로 국가 해산.
- 후계자 없는 사망 NPC의 재산·부곡을 다른 장수(군주 포함)에게 넘기기. 사람에게 NPC 몸을 자동 배정하기.
- 진행 중 월드 자동 전환, 공개 기본 프로필, 관리자 생성 목록(`creationFeatures`)에 lineage-v1 추가.
- 이름·초상·직책·역사 상식으로 성별 추정. 원장에 없는 인물에게 성별을 정해 주는 입력·관리 도구. 성별 변경 입력.
- 성별 원장의 GameResource 게시(새 kind·enum 변경). L6 공개 프로필 작업에서 한다.
- 사료 혈연 자료 연결(T4-42 미구현). 원생성 장수 사이의 친족 관계는 비어서 시작한다.
- 새 범용 프레임워크·루프·하네스. 신원 전환을 위한 범용 전송 계층, 월드 전체 revision 잠금.

### L0 읽기 결과 (구현 전 main 기준, 2026-11-03)
구현 전에 읽은 사실이다. 줄 번호는 그 시점 기준이라 구현 뒤 달라진 곳이 있다. 「바꿈」 항목은 구현에 반영했고 실제 계약은 아래 각 절이 정한다.

- **퇴장 표지값 저장 가능**
  - DB `"activeFromYear" INTEGER NOT NULL`(`migrations/20261020000000_initial_world/migration.sql:93`). 어느 migration에도 이 열의 CHECK가 없다. int4 상한이 `2_147_483_647`이다.
  - 엔진 재생 상한 `activeFromYear: natural`(`apps/engine/src/replayCaps.ts:114-115,193`)은 안전 정수 ≥0이다. 정책 재생 스키마는 `z.number().finite()`이다(`rules/policy/replay.ts:67,80`).
  - 운영 코드에 `activeFromYear` 산술이 없다. 값을 만드는 곳은 `birthYear + 15`(`world/bootstrap.ts:264`, `general/create.ts:129`)뿐이고 나머지는 모두 `<= year`·`> year` 비교다.
  - 결론: `LINEAGE_EXITED_YEAR = 2_147_483_647`을 그대로 쓴다. 새 열은 만들지 않는다.

### 원생성 설정
`lineage-v1`은 `requires:['personnel']`이다. 다른 기능이 켜져 있으면 함께 처리한다.
- `campaign-v1`: 부곡·휘하·지시
- `policy`: 턴 방침·활동 tick
- `governance-v1`: 황실 정리

설정은 `featureData['lineage-v1']`에 zod `strictObject`로 넣는다(`lineage/config.ts`). 코드에 기본 수치를 두지 않는다. 시험 값은 `lineage/testFixture.ts`와 각 통합 시험 fixture에만 둔다. 공개 기본값은 L6 전까지 만들지 않는다.

```
{version:1,
 marriage:{minAge, maxAge(≤500), maxSpouses(1..4), kinDepth(1..4), offerMonths(1..120),
           npc:{perMonth(≤200), affinityGap(≤149), chanceBp(0..10000)}},
 birth:{minParentAge, maxParentAge, chanceBp(0..10000), comingOfAgeYears(1..120), femaleBp(0..10000),
        statSpread(≤1000), lifespan:{min,max}(1..500), givenNames:string[1..1000], compoundSurnames:string[≤100]},
 heir:{depth(1..3)},
 limits:{maxGenerals(≤10000), maxBirthsPerYear(≤1000), sentOffers, receivedOffers, worldOffers(1..200)}}
```

- 짝 규칙 칸(`marriage.pairing`)은 없다. 남녀 규칙은 확정 계약이다. 다른 짝 규칙이 생기면 `version:2`로 연다.
- `birth.femaleBp`는 출생 장수가 `FEMALE`일 확률(만분율)이다. 기본값은 없다.
- config 자체 검증: 나이·수명 `min ≤ max`, 개인 제안 상한 ≤ 월드 상한, 이름 후보는 생성 이름 규칙(`generalCreationSchema.shape.name`)을 지키고 중복이 없다.

`checkOrigin`·`initReplayState`가 확인하는 것
- `initial`에 `lineage` 칸이 없다. 재생 상태에 `lineage`가 이미 있으면 중복 초기화로 거부한다.
- `initialLineageState`: 모든 장수가 `sex ∈ {MALE, FEMALE, UNKNOWN}`을 가진다. 장수 수가 `maxGenerals` 이하이고 모든 `activeFromYear < LINEAGE_EXITED_YEAR`이다.
- 초기 `persons`는 빈 객체다. 장수마다 칸을 만들지 않는다. 출생·퇴장·후계 지정 사실이 생긴 장수만 칸을 얻는다.
- 표지값 여유는 원생성에서 따로 검사하지 않는다. 출생 때 `year > LINEAGE_MAX − max(lifespan.max, comingOfAgeYears)`이면 그 출생을 `LIMIT`로 건너뛴다.

### 성별 (U95-1 확정, 2026-11-03)

**규칙**
- 값은 `GeneralSex = 'MALE' | 'FEMALE' | 'UNKNOWN'`이다. lineage-v1 월드에서는 모든 장수가 이 칸을 가진다. 꺼진 월드에서는 칸이 없다.
- 혼인 자격: 두 장수가 모두 알려진 성별이고 서로 달라야 한다. 한쪽이라도 `UNKNOWN`이면 `SEX_UNKNOWN`, 같은 성별이면 `SEX_PAIR`이다. 사람 제안, 사람 수락, 사람→NPC 즉시 성혼, NPC 월 짝짓기가 모두 같은 `marriageEligibility`를 쓴다.
- 출생 자격: 혼인 중인 `MALE`·`FEMALE` 두 부모가 살아 있고 나이 조건에 맞아야 한다(`lineageBirthEligibility`). 성별 쌍이 어긋난 혼인은 `assertLineageFinal`이 불변식 위반으로 거부한다.
- 가주는 성별과 무관하게 제안자다. 자녀의 국가·도시·성씨는 가주를 따른다.
- 나이, 사망, NPC 계승, 후계자 자격, 공석 채움, 청구는 성별을 보지 않는다.
- 불변: 값은 원생성·생성·출생 때 한 번 정한다. 바꾸는 입력이 없다. DB 트리거가 다른 값으로의 갱신을 `23514`로 막는다.
- 이름·초상·직책·역사 상식으로 추정하지 않는다. 원장에 행이 없는 지원 시나리오 인물은 이름과 무관하게 `UNKNOWN`이다.

**시나리오 인물 자료 (출처 있는 사실만)**
- 원장은 `resources/officers/191-sex.json` 하나다. 대상 시나리오는 1030과 integration191이다.
  ```
  {version:1, scenarios:['1030','integration191'],
   review:{status:'approved', reviewer, evidence, contentSha256},
   rows:[{generalId, name, identity, sex:'MALE'|'FEMALE', sourceId, sourceRevision:'sha256:<hex>',
          evidence:{kind:'primary-text', quotes[], urls[]}}]}
  ```
  - 행에는 출처 원문이 성별을 명시한 인물만 둔다. `UNKNOWN` 행은 두지 않는다(행 없음 = `UNKNOWN`). `generalId`는 유일하다.
  - `review.contentSha256`은 `review`를 뺀 판·대상 시나리오·행 전체의 `hashState`다. `sourceRevision`은 `{identity, sex, urls, quotes}`의 `hashState`다. 페이지 HTML의 해시가 아니다.
  - 대응: 행의 `generalId`·`name`은 대상 시나리오 장수와 같아야 한다. `identity`는 `191-five-stats.json`의 같은 `generalId` 행과 같아야 한다.
- 읽기: 엔진 `loadSexLedger`(`apps/engine/src/world/resources.ts`)가 Node 파일에서 읽고 스키마·두 해시를 확인한다. 공통 생성 경계 `prepareInitialWorld`(`apps/engine/src/world/persistence.ts`)는 `lineage-v1`을 켰을 때만 이 원장을 읽는다. 끈 월드는 원장을 읽지 않고 모든 장수에 `sex` 키가 없는지만 본다. 배포 이미지는 원장과 원장 고지를 함께 복사한다(`deploy/Dockerfile`).
- 적용: rules `applySexLedger(initial, ledger)`
  - 대상 시나리오: 장수에 직접 `sex`가 있으면 거부한다. 원장 행의 ID·이름이 시나리오와 다르면 거부한다. 원장 밖 인물은 `UNKNOWN`이다.
  - 다른 시나리오: 모든 장수가 명시한 값이면 그대로(시험 fixture), 모두 없으면 전원 `UNKNOWN`이다. 일부만 지정하면 거부한다.
  - 적용 값은 재생 원본과 초기 상태 해시에 고정한다. 진행 중 월드에 원장을 다시 적용하지 않는다. 사실을 더할 때는 기존 원장을 덮지 않고 새 판으로 다룬다.
- 고지: 출처와 결합 키, 「이름 추정 없음, 행 없음은 UNKNOWN」은 원장 전용 `resources/officers/NOTICE.md`에 둔다. 기존 `resources/NOTICE.md`와 시나리오·SQL 출처 고지는 바꾸지 않는다.
- 검수: 원장 작성과 반대 담당의 독립 검수를 거쳐 `review.status='approved'`다. 원장 행 수와 성별 분포는 이 계획에 적지 않는다.

**새 생성 장수 (플레이어 선택)**
- `general.create` payload에 `sex: 'MALE' | 'FEMALE'`을 더한다(`knownGeneralSexSchema.optional()`).
  - lineage-v1 월드: 필수다. 없거나 다른 값이면 `BAD_SEX`이다. `UNKNOWN`은 고를 수 없다.
  - 그 밖의 월드: 키가 있으면 `BAD_SEX`이다. 키가 없는 기존 payload의 결과·난수 소비는 같다.
  - 서버 envelope에서 `sex` 경로의 zod 오류는 모두 `BAD_REQUEST` + `CREATION_ERRORS.BAD_SEX`로 바꾼다. 다른 칸도 함께 틀린 입력도 메시지는 `BAD_SEX`다. CF도 이 우선순위를 따른다.
- 난수를 쓰지 않는다. `buildCreatedGeneral`의 소비 순서(도시 → affinity → 턴 offset)는 바뀌지 않는다.
- 화면: `CreateGeneralPage`는 lineage 월드일 때만 성별 선택을 보인다. 기본 선택이 없어서 고르기 전에는 제출이 안 된다. 키보드로 조작할 수 있고 라벨은 「남」·「여」다. 꺼진 월드에는 선택 칸이 없다.

**출생 장수**
- `sex = rngFor(lineage.seed, 'lineage-child-sex', childId).int(0, 9_999) < config.birth.femaleBp ? 'FEMALE' : 'MALE'`(`lineage/birth.ts` 안의 식).
- 자녀마다 정확히 1번 뽑는다. `femaleBp`가 0이거나 10000이어도 뽑는다. 흐름이 자녀 id별로 따로라서 기존 흐름의 소비를 바꾸지 않는다.
- `lineage.seed`는 원생성 seed 복사본이다. 로드 때 `replayOrigin.initial.seed`와 대조한다. 규칙에 공개 기본값이 없다.

**같은 seed 재현**

| 흐름 키 | 소비 |
| --- | --- |
| `('lineage-death', id)` | 사망 판정 대상 NPC마다 사망 달 1번 |
| `('lineage', year, month)` | NPC 혼인: 짝 후보가 1명 이상인 미혼 등장 NPC마다 1번(국가 id → 장수 id 순, `UNKNOWN`이나 후보 없는 NPC는 뽑지 않음). 이어서 1월 출생: 자격 있는 혼인마다 1번(혼인 id 순, `chanceBp`와 무관). 출생 판정이 이 흐름의 마지막 소비다 |
| `('lineage-child', childId)` | 능력치(능력치 키 순) → 수명 → 이름 시작점 |

- `femaleBp`만 다른 두 월드는 첫 출생 달까지 자녀의 성별만 다르고 다른 칸은 모두 같다. 그 뒤 달은 혼인 후보가 달라 갈라질 수 있다.
- 꺼진 월드는 main과 같다.

### 상태와 저장 (상한 있음)
`WorldState.lineage?`를 nullable `World.lineageState Json?`에 저장한다. 새 이력 표는 만들지 않는다. 무한히 쌓이는 기록은 기존 `InputEvent` 결과, `GeneralLog`, `NationHistory`에 둔다. 연결 지점은 `clone.ts`, `hashState`, `worldLoader`(`readStoredLineage`), 원생성 `initialLineageState`, `initReplayState`(중복 초기화 거부), `checkArchive`, CF DTO다.

migration은 새 파일 하나 `packages/db/prisma/migrations/20261113000000_lineage_state`이고 덧붙이기만 한다. 기존 migration·enum은 고치지 않는다.

```sql
ALTER TABLE "World" ADD COLUMN "lineageState" JSONB;
ALTER TABLE "World" ADD CONSTRAINT "World_lineageState_feature_check" CHECK (

        "lineageState"->'version' = '1'::jsonb AND
        jsonb_typeof("lineageState"->'config') = 'object' AND
        jsonb_typeof("lineageState"->'persons') = 'object' AND

);

    "sex" IS NULL OR "sex" IN ('MALE', 'FEMALE', 'UNKNOWN')
);
CREATE FUNCTION "guard_general_sex_immutable"() RETURNS TRIGGER AS $$

$$ LANGUAGE plpgsql;
```

- lineage 월드에서 `sex`가 null이 아니어야 한다는 조건은 표 사이 조건이라 CHECK로 못 건다. 로드의 `storedGeneralSex`와 원생성 검사가 막는다.

```
{version:1, config, seed, monthlyTick, revision, nextOfferId, nextMarriageId,
 persons: Record<generalId, {parents:[householdGeneralId, otherId]|[], bornTick:number|null,
          exit:null|{tick, cause:'DIED'|'SUCCEEDED', activeFromYear}, successorId:number|null, heirId:number|null}>,
 marriages:[{id, a, b, householdGeneralId, sinceTick}],   // a<b, householdGeneralId ∈ {a,b}, 둘 다 살아 있는 관계만
 offers:[{id, fromId, toId, expiresTick}]}         // fromId가 성혼 때 householdGeneralId가 된다
```

- 성별은 lineage 상태가 아니라 장수 칸이다. 혼인 행이 지워진 뒤에도(퇴장) 가주 기록은 `parents[0]`에 남는다.
- `persons`는 희소하다. 원생성은 빈 객체이고 출생·퇴장·후계 지정 사실이 생긴 장수만 칸을 얻는다. 혼인은 `marriages`에만 기록한다. 칸이 없는 장수는 빈 기록으로 읽는다. 개수는 `maxGenerals` 이하다.
- `marriages`는 `maxGenerals × maxSpouses / 2` 이하, `offers`는 `worldOffers` 이하다.
- 혼인·제안의 쌍은 순서 없는 쌍으로 유일하다. `a<b` 정렬은 유일성 검사용일 뿐 자녀 소속은 `householdGeneralId`로만 정한다.
- `parents`는 `[가주, 다른 부모]` 순서다. 부·모 구분은 부모의 성별에서 읽는다. 로드 검사는 두 값이 다르고 자기 자신이 아닌지만 본다.
- `seed`는 원생성 seed를 복사하고 로드 때 `replayOrigin.initial.seed`와 대조한다. `config`도 원생성 `featureData['lineage-v1']`과 같아야 한다.
- `monthlyTick`은 World와 대조한다. 같은 달을 두 번 돌리거나 한 달을 건너뛰면 예외다.
- `readLineageState`는 구조만 본다. 스키마, id 유일·정렬, 순서 없는 쌍 유일, `householdGeneralId ∈ {a,b}`, 상한, 번호 역행을 검사한다.
- `assertLineageFinal`은 참조와 퇴장·성별 불변식을 본다. 정리 함수 출력과 월 정산 결과에 건다.
  - 퇴장 장수가 아래 어디에도 남아 있으면 예외다.
    - 부곡 owner·commander
    - 휘하 link·`PENDING` 제안
    - `PENDING`·`READY` 지시
    - `commandMeta.offers`
    - 혼인·혼인 제안·후계 지정
    - 소유자·지휘관이 둘 다 `nationId=null`이면 휘하 불변식이 통과하므로 이 검사를 lineage에 따로 둔다.
  - 모든 혼인이 `MALE`·`FEMALE` 쌍이다.
- `revision`과 번호가 `2_147_483_647`에 닿으면 입력은 `LIMIT`, 정산은 예외다.

### 퇴장 표현
사망·은퇴 장수는 `generals`에 남긴다. 이름·성별·기록·전적·휘하 출처를 보존한다. 퇴장할 때 아래처럼 바꾼다.

- `userId=null`, `nationId=null`, `officerLevel=0`, `crew=0`
- 금·쌀은 이전한 뒤 0
- `activeFromYear = LINEAGE_EXITED_YEAR(2_147_483_647)`. 원래 값은 `persons[id].exit.activeFromYear`에 보존한다.
- `cityKey`는 그대로 둔다(FK 보존, 도시는 지워지지 않는다).

이 표지는 등장 판정을 쓰는 기존 경로 전부에서 퇴장 장수를 뺀다. 판정을 보지 않는 순회도 국가·사람·병력 조건으로 빠진다. 새는 곳 3개만 고쳤다(L0). `assertLineageFinal`은 「exit ⇔ 표지값 ∧ 위 칸 값」을 양방향으로 검사한다.

코드 주석: `shortcut: 등장 연도 표지로 퇴장을 표현한다, activeFromYear를 보지 않는 새 장수 순회가 퇴장 장수를 포함하게 되면 명시 칸으로 바꾼다`.

### 행동 계약
입력 종류는 `lineage.act` 하나다. route는 queued, 멱등키는 `lineage:<uuid>`다. 행위 장수는 세션 사용자의 장수로 고정한다. 서버 사전 판정과 엔진 실행은 같은 순수 함수 `decideLineageAction(state, actorId, payload, tick)`을 쓴다. 엔진은 행위 장수 행을 잠근 뒤 `actor.userId === event.userId`를 다시 보고 다르면 `NOT_OWNER`로 거절한다. 실행 때 결과가 달라졌으면 `REJECTED`다.

적용 결과는 `{action, revision, tick, offerId?, marriageId?, householdGeneralId?, successorId?, nationId?}`, 거절 결과는 `{code, message, reason?}`다. 재생은 기록을 다시 판정해 결과 JSON을 대조한다. 공통 거절로 `FEATURE_DISABLED`·`BAD_ARGS`·`BAD_TICK`(현재 월 밖 tick)·`LIMIT`(가문 revision 한도)·`NOT_OWNER`(등장한 생존 사람 장수가 아님)가 있다.

| payload | 행위자 | 핵심 검사 |
| --- | --- | --- |
| `marriage.propose{targetGeneralId}` | 등장한 살아 있는 사람 장수 본인 | 판정 순서대로 자기 자신 `SELF`, 대상 없음·퇴장·미등장 `BAD_TARGET`, 어느 한쪽 `UNKNOWN` `SEX_UNKNOWN`, 같은 성별 `SEX_PAIR`, 나이 범위 밖 `AGE`, `kinDepth` 안 친족 `KIN`, 이미 부부·배우자 수 상한 `ALREADY_MARRIED`, 같은 순서 없는 쌍의 미결 제안 `OFFER_PENDING`(방향 무관. 상대가 먼저 보낸 제안이 있으면 새 제안을 만들지도 자동 수락하지도 않는다). 사람 대상이면 제안 상한·번호 한도 `LIMIT` 뒤 제안만 만든다. 사람 대상에는 국가 조건이 없다(다른 국가 사람에게도 제안할 수 있다). NPC 대상이면 같은 국가(둘 다 재야 포함)이고 친화 차가 `affinityGap` 이하일 때 즉시 성혼, 아니면 `NPC_REFUSED`다. 난수는 없다. 성혼하면 `householdGeneralId = 행위자`다 |
| `marriage.respond{offerId, accept}` | 제안 대상 장수의 현재 사용자 | 닫힌 제안이면 `OFFER_CLOSED`, 다른 사람이면 `NOT_PARTY`. 수락하면 혼인 자격을 다시 판정한다. 성혼하면 `householdGeneralId = offer.fromId`다. 거절해도 제안은 닫힌다 |
| `heir.designate{heirGeneralId\|null}` | 사람 장수 본인 | 어기면 `HEIR_INELIGIBLE`이고 `reason`을 붙인다. 판정 순서는 `BAD_HEIR`(자기 자신·미등장·퇴장) → `NOT_DESCENDANT`(`heir.depth` 밖) → `HEIR_CONTROLLED`(사람이 조작 중) → `HEIR_NATION`(다른 국가, 둘 다 재야는 같은 국가로 본다) → `HEIR_RESERVED`(다른 장수가 지정함)다. 성별은 보지 않는다. `null`은 지정 해제다 |
| `succession.confirm{heirGeneralId, expected}` | 사람 장수 본인 | 지정한 후계자와 다르면 `NOT_DESIGNATED`. `successionPreview`를 다시 계산하고 실패하면 그 코드를 돌려준다. 결과가 `expected`와 다르면 `PREVIEW_CHANGED`. 이전하지 못하는 항목은 `HOLDER_FULL`, `HEIR_HAS_CREW`, `HEIR_AWAY`(병력이 있는데 후계자가 다른 도시), `HEIR_CAPACITY`, `HEIR_COMMANDS_OTHERS`(후계자가 남의 부곡을 지휘)로 거부한다. 사람 계승에는 명시 손실이 없다. 엔진은 이어서 예약 변경 번호 한도를 보고 넘으면 `LIMIT`로 거절한다 |
| `ruler.claim{nationId}` | 사람 장수 본인 | 판정 순서는 `NOT_MEMBER`(행위자 국가가 아님) → `BAD_TARGET`(국가가 없거나 관문이 아닌 도시가 없음) → `NOT_VACANT`(같은 국가에 등장한 생존 `officerLevel 12` 장수가 있음)다. 효과: 행위자 `officerLevel=12`, 이전 직책은 빈다, `nation.isNpc=false`. 재산·병력·휘하는 바뀌지 않는다. 후보 순위는 없다. 입력 처리 순서에서 먼저 적용된 하나가 잇고 뒤 청구는 실행 때 다시 판정해 `NOT_VACANT`다. 월 정산의 NPC 채움과도 같은 판정이라 먼저 실행된 쪽만 적용된다 |

- **가주 부모(household) 동의 문구**: 제안 확인 대화상자(제안자)와 받은 제안 화면(수락자)에 같은 문구를 보여 준다. 「자녀는 출생 때 가주(제안한 장수 ○○)의 국가·도시를 따르고 가주의 성씨를 잇는다」. NPC 대상 즉시 성혼도 제안 전에 같은 문구를 보여 준다. 화면은 계산하지 않고 `get` 응답의 `householdGeneralId`·이름만 쓴다. 수락이 곧 동의이며 가주는 제안 생성 때 고정이라 별도 payload 칸은 없다.
- 혼인·후계 후보 목록은 `get`이 판정을 끝낸 결과를 준다. 실패 코드의 공개 범위는 「API·DTO」를 따른다. 화면은 성별로 거르지 않는다.
- `expected`는 사용자가 동의한 결과 자체인 작은 DTO다.
  ```
  {heirId, officerLevel, gold, rice, crew, unitIds[], keptRetinue[], releasedRetinue[],
   cancelledOrders[], cancelledOffers[{kind:'RETINUE'|'ASSIGNMENT', id}], governance:{throne:boolean, courtOffice|null, vassalIds[]}}
  ```
  - `crew`는 후계자 본대와 계승 뒤 후계자가 소유한 부곡의 병력 합이다.
  - `cancelledOffers`에는 휘하 제안과, 전임자를 대상으로 하거나 전임자가 발령하여 이번 계승으로 새로 닫힐 발령 제안(`assignmentCancelReason`)을 함께 넣고 종류·id 순으로 정렬한다. 계승 전부터 무효였던 다른 가문의 제안은 넣지 않는다.
  - 발령 제안은 서버 미리보기와 엔진이 같은 `pendingAssignmentsFromRows`(`rules/personnel/assignmentRows.ts`)로 `PENDING` 행을 읽는다. 서버는 personnel 월드에서만 snapshot에 합친다. 그래서 확인창과 실행 결과의 취소 목록이 같다.
  - `governance`는 계승 전후 상태에 순수 `reconcileGovernance`를 돌려 계산한다. 미리보기 전용이며 저장하지 않는다.
- `ruler.claim`의 동의 화면에는 현재 직책을 떠난다는 것, 국가가 사람 국가로 바뀌어 조약 자동 응답이 멈춘다는 것(`isNpc=false`), 국가 예턴이 자기 칸이 된다는 것을 보여 준다. 화면은 `get` 응답의 `claim:{nationId, currentOfficerLevel}`만 쓴다.
- `isNpc=false`로 바꾸는 이유: 사람 군주 국가에 NPC 조약 자동 응답이 계속되면 사람 동의 없이 조약이 체결된다. 이 값은 사람 장수가 세운 국가와 같은 기존 의미다.

### 계승 이전 (사람·NPC 공용 순수 함수)
`applySuccession(world, fromId, toId, mode:'HUMAN'|'NPC_DEATH', tick)`을 고정 순서로 적용한다. 부곡 위치는 지휘관 도시이므로 어떤 단계도 병력을 다른 도시로 옮기지 않는다. 어느 단계도 `sex`를 건드리지 않는다.

1. **조작권**: `to.userId = from.userId`, `from.userId = null`.
2. **직책**: `to.officerLevel = max(from.officerLevel, to.officerLevel)`. 같은 국가가 자격 조건이다. 더 높은 직책을 유지하며 낮은 직책의 칸은 빈다. HUMAN 계승 뒤 군주이면 `nation.isNpc=false`다. 기존 후계자의 군주 자리를 낮은 전임자 직책으로 강등하지 않는다.
3. **금·쌀**: `to`에 더한다. 32비트 상한을 넘을 때 HUMAN은 `HOLDER_FULL`로 거부하고 NPC는 초과분을 명시 손실로 남긴다.
4. **병력(휘하 기능이 없는 판)**: `from.crew > 0`인 경우만 따진다.
   - `to.crew === 0`이고 같은 도시면 `crew·crewType·train·atmos`를 옮긴다.
   - 아니면 HUMAN은 `HEIR_HAS_CREW`·`HEIR_AWAY`로 거부한다. NPC는 `crew=0`과 명시 손실로 처리한다.
5. **부곡(휘하 판)**
   - `from` 소유·`from` 지휘 부곡
     - `to`가 같은 도시면 소유자·지휘관을 `to`로 바꾼다. 상한(`leadership×100`)을 넘으면 HUMAN은 `HEIR_CAPACITY`로 거부, NPC는 초과 병력을 손실로 남긴다.
     - 다른 도시이고 병력이 있으면 HUMAN은 `HEIR_AWAY`로 거부한다. NPC는 부곡을 지우고 병력을 손실로 남긴다.
     - 병력 0이면 도시와 무관하게 소유자·지휘관을 `to`로 바꾼다.
   - `from` 소유·NPC 부장 지휘 부곡: 소유자를 `to`로 바꾼다. 부장 link를 `to` 아래로 옮긴다(6). link를 옮기지 못하면 HUMAN은 `HEIR_CAPACITY`로 거부, NPC는 그 부곡을 지우고 손실로 남긴다. 지휘관은 바꾸지 않아 위치가 그대로다.
   - 남의 부곡을 `from`이 지휘(NPC_DEATH만 가능)
     - 소유자가 같은 도시면 지휘관을 소유자로 돌린다. 상한 초과분은 손실이다.
     - 아니면 그 부곡의 병력을 0으로 하고 지휘관을 소유자로 돌린다.
   - 남의 부곡을 `to`가 지휘: HUMAN은 `HEIR_COMMANDS_OTHERS`로 거부한다. NPC_DEATH는 `to`가 NPC로 남으므로 그대로 둔다.
6. **휘하**
   - `from` 아래의 NPC는 상관을 `to`로 바꾼다. 순환이나 명망 수용량에 걸리면 관계만 해제한다.
   - `from` 아래의 사람은 관계를 해제한다. 사람의 동의 없이 상관을 바꾸지 않는다.
   - `from`이 누군가의 휘하였던 관계도 해제한다.
   - HUMAN이면 `to`의 상위 관계도 해제한다.
   - 관련 `PENDING` 휘하 제안은 `CANCELLED`로 닫는다.
   - `from` 또는 `to`가 지시자·수신자인 `PENDING`·`READY` 지시는 `CANCELLED`로 닫고 `resolvedTick`·`result`를 채운다.
7. **퇴장**: `from`을 퇴장 표현으로 바꾸고 `exit.cause`·`successorId`를 기록한다. `from`의 배우자 관계, 미결 혼인 제안, 후계 지정, `from`을 후계자로 지정한 기록, `commandMeta.offers[from]`을 지운다.
8. **재생 칸**(`lineage/control.ts`, rules 재생·엔진 처리기·월 정산 공용)
   - `lineageControlRevisions(from, to)`: 두 값 중 하나라도 `2_147_483_646`(`LINEAGE_MAX−1`) 이상이면 `LIMIT`이다. 아니면 `revisions[to] = max(from, to) + 1`, `revisions[from] = from + 1`이다. 새 값은 `turns.set` 상한 안에 있고 후계자의 새 값이 전임자의 옛 값보다 항상 커서 전임자 기준 `turns.set` 양식이 후계자 큐에 우연히 들어가지 않는다.
     - 사람 계승: 엔진 처리기가 저장 전에 먼저 검사해 `REJECTED`(`LIMIT`)로 끝낸다. 새 조작자를 편집 불가 번호로 넘기지 않는다.
     - NPC 사망 계승: 월 정산의 `resetLineageControl`이 같은 검사에서 예외를 던져 정산을 멈춘다. 불변식 위반으로 다룬다. rules와 엔진이 함께 던지므로 재생은 갈라지지 않는다. 실제 도달 가능성은 낮다.
   - `turns[to]`를 빈 큐로 바꾼다. 빈 큐는 policy 판이면 `emptyQueue()`, 아니면 `emptyTurns()`다.
   - policy 판이면 `policies[from]`과 `policies[to]`를 모두 `'none'`으로 둔다. `lastActiveTicks[from]`은 지우고 `to`가 사람이면 `[to] = tick`, 아니면 지운다.
   - HUMAN이면 `updateResidenceAnchors(…, succession:{fromId, toId})`로 후계자 앵커를 `tick`으로 둔다. 전임자는 사람이 아니게 되어 빠진다.
   - 엔진은 두 장수의 `turnRevision`·`defaultPolicy`·`lastActiveTick/At`을 `userId`·옛 `turnRevision` 조건으로 id 순 갱신하고 후계자 `GeneralTurn` 30칸을 다시 만든다(`persistLineageControl`).

사람 계승이 「동의한 미리보기와 같은 결과만, 손실 없이, 위치 이동 없이」 일어난다는 것을 rules 시험으로 고정한다. 금·쌀·병력·부곡 병력의 합과 부곡별 위치 도시가 이전 전후에 같아야 한다.

### 훅 순서 (입력·월 정산, 이중 CAS 방지)
**입력 경로 (`lineage.act`)**: 엔진 `processInputs`에서 아래 순서로 돈다.

1. `before = loadReplayState`.
2. 처리기 `processLineageInput` → `processLineageOrder`(`apps/engine/src/lineage/service.ts`)
   1. 월드 실행·계정 활성·제재·장수 존재를 확인한다(`WORLD_CLOSED`·`ACTOR_INACTIVE`·`ACTOR_SANCTIONED`·`NO_GENERAL`).
   2. `loadForGeneral`이 행위 장수 행 하나만 `FOR UPDATE`로 잡고 `loadReplayState`로 읽는다. 후계자·대상 행은 잠그지 않는다. 엔진 입력은 월드 lease 안에서 순서대로 처리되고 서버 접수는 `World FOR UPDATE`를 잡는다. 저장은 `lineageState` CAS와 `userId`·`turnRevision` 조건 갱신이라 사이에 바뀐 값이 있으면 예외로 롤백된다.
   3. `decideLineageAction`. 실패는 `{code, message, reason?}`로 `REJECTED`다.
   4. `succession.confirm`이면 `lineageControlRevisions`를 먼저 보고 `resetLineageControl`을 적용한다. `saveControl`은 전임자 `userId`를 `userId`·`turnRevision` 조건으로 먼저 비운다(바뀐 행이 1개가 아니면 예외). 그 뒤 `persistEffects(previous=before.state)`와 가문 기록을 쓰고 `persistLineageControl`을 부른다. 그래서 후계자 id가 더 작아도 유일성 위반이 없다.
   5. 다른 행동은 `save`(`persistEffects`와 가문 기록)만 한다. `persistCommandState`가 차례로 CAS한다: campaign → cityResources → logistics → governance → lineage(`persistLineageState`, 이전 값 `equals` 조건, config·seed 변경 거부).
3. `afterQueuedInput`을 배열 순서로 부르고 입력 소유 기능 자신은 건너뛴다. 순서는 campaign-v1 → governance-v1 → lineage-v1 → personnel이다.
   - campaign-v1: 제외 목록에 `'lineage.act'`가 있다. 빼면 `persistForeignCampaignInput`이 같은 입력을 `before`에 다시 적용해 campaign·governance CAS가 실패하고 황실 정리도 두 번 돈다.
   - governance-v1: `reconcileGovernanceOrder`를 한 번 부른다. 수락 때 기록한 군주 id가 바뀌었으면 봉신 계약을 해제하고 황제를 폐위하고 조정 직위와 출처 제안을 정리한다.
   - lineage-v1: 다른 기능의 입력 뒤 `reconcileLineageOrder`가 무효가 된 후계 지정·혼인 제안을 정리한다. 상태가 바뀌었을 때만 저장한다. `lineage.act` 자신은 건너뛴다.
   - personnel: `completePersonnelStep(before.state, …)`가 `syncOffices`로 바뀐 직책의 revision·tenure를 올리고 그 칸을 비운다. lineage 월드에서는 같은 장수가 직책을 유지해도 조작자(`userId`)가 바뀌면 국가 예턴 칸을 비우고 임기를 한 번 올린다. 끈 월드는 기존과 같다. 이어서 `closeInvalidOffers`가 발령 제안을 닫는다.
4. `InputEvent`를 마감한다.

**규칙 재생**: `applyRecordedInput`이 입력 `apply` 뒤 `afterAppliedInput`을 campaign-v1 → governance-v1 → lineage-v1 → personnel 순으로 부르고 입력 소유 기능은 건너뛴다. lineage-v1의 `afterAppliedInput`은 queued 입력에만 `reconcileLineage`를 돈다(`lineage/feature.ts`). 사람 계승의 재생 칸은 `lineageInputKind.apply`가 `resetLineageControl`로 엔진과 같은 값을 만든다. `hookOrder.test.ts`가 `lineage.act`의 훅 순서와 황실 reconcile 1회를 단언한다.

**`ruler.claim`**: 사람이 사람으로 남아 앵커 보정과 유일성 선해제가 없다. 나머지 훅 순서는 같다.

**월 정산**
- `monthlyOrder = ['treaty','lineage-v1','personnel','campaign-assignment-v2','logistics-v1','governance-v1']`
- governance 월 정산은 시작할 때 reconcile한다. 그래서 NPC 군주 사망의 계약 해제와 폐위는 같은 달 마지막 단계에서 한 번 일어난다. lineage 단계는 황실을 reconcile하지 않는다.
- 엔진 `persistMonthly`
  1. 장수 갱신 반복은 `before`에 없는 출생 행을 건너뛴다.
  2. 상태 CAS 묶음에 `persistLineageState`가 있다.
  3. 기능 훅 루프의 lineage-v1 훅 `persistLineageMonth`가 출생 `General` 행(금·쌀 0, `turnRevision` 0, `defaultPolicy` `'none'`, 활동·거주 tick null)과 `GeneralTurn` 30칸을 만들고 NPC 계승의 재생 칸을 `persistLineageControl`로 쓰고 가문 기록을 남긴다. treaty 다음, personnel 앞이다. 그래서 personnel이 쓰는 `GeneralLog` FK, 30칸 검사, 순위가 모두 출생 행 뒤에 온다.

### 신원 전환 (사람 계승 직후 화면)
같은 계정이 장수만 바꾸므로 계정만 보는 신원 재확인으로는 전임자 기준 양식을 막지 못한다. 새 전송 계층이나 월드 revision 잠금은 만들지 않는다.

- **활성 장수 전환**: 계승 요청이 `applied`가 되면 계정의 장수 조회(`GeneralInfo`와 각 board)를 다시 읽는다. 화면 전체의 행위 장수가 후계자로 바뀐다. 다른 탭은 다음 다시 읽기나 전송 전 다시 읽기에서 바뀐다.
- **열린 양식·확인 대화상자 무효**: 각 패널은 양식·확인 대화상자를 열 때 board의 행위 장수 id를 붙잡는다. 전송 전 다시 읽기에서 그 id가 바뀌었으면 기존 `IdentityChanged` 경로로 양식을 버리고 대화상자를 닫고 「장수가 바뀌었습니다. 화면을 다시 확인하세요」를 보인다. 자동 재전송은 없다.
  - 대상: 황실(`useGovernanceBoard`), 물류(`LogisticsPanel`), 도시 자원(`CityResourcesPanel`), 휘하·지시(`CampaignPanel`, `RetinueOrdersPanel`), 인사(`PersonnelPage`·`usePersonnelAction`), 국가 예턴(`NationTurnsPage`), 개인 턴 편집, 가문(`useLineageBoard`).
  - 행위 장수 id는 기존 칸(`viewerGeneralId`, `actorId`)을 쓴다. 칸이 없는 board 응답에만 같은 이름의 읽기 칸 1개를 더한다.
- **접수 시점 장수 확인**: 다시 읽기와 서버 접수 사이(수 ms)의 계승은 서버가 막는다. `lineage.submit`은 `expectedGeneralId`가 필수다. `governance.submit`·`logistics.submit`은 선택으로 받고 새 화면은 항상 보낸다. 서버는 `World FOR UPDATE` 안에서 세션 장수와 다르면 `CONFLICT`다. 대기 기록의 재접수도 처음 기록한 장수 id를 그대로 보낸다. 가문 접수에서 같은 요청 번호의 재전송은 기록된 장수 id와 payload가 같아야 원래 결과를 돌려준다. 다른 기존 명령 화면은 다시 조회한 장수와 예약 변경 번호·직책 임기로 이전 입력을 막는다.
  - 개인 턴은 서버 revision 409(계승 8단계)가 함께 막는다. 국가 예턴은 `syncOffices`의 직책 revision·tenure 409가 막는다.
- **이미 접수된 전임자 요청**: 기존 소유자 검사로 `REJECTED`다. 화면의 대기 기록 키와 서버 조회 키가 사용자 기준이라 같은 UUID 조회가 `rejected`로 끝난다. 이 키를 장수 기준으로 바꾸지 않는다.

### NPC 사망·계승·공석 규칙 (원생성 seed 파생 난수만)
- **사망 판정**: 사망 달은 `rngFor(seed,'lineage-death',generalId).int(1,12)`이다. 장수별 독립 흐름이라 처리 순서와 무관하다. NPC는 `year > deathYear`이거나 `year === deathYear ∧ month ≥ 사망 달`이면 사망한다. 사람 장수는 나이만 먹는다. 성별은 보지 않는다.
- **재산 후계자**: `heir.depth` 안의 직계 자손 가운데 `heirEligibility`를 통과하는 장수를 출생 연도가 이른 순, 같으면 id 순으로 고른다. 통과 조건은 살아 있는 등장 NPC, 같은 국가(둘 다 재야 포함), 다른 장수가 지정하지 않은 장수다. 사람이 지정해 둔 자녀(공동 부모가 지정한 경우 포함)는 그 사람의 계승 동의를 기다리므로 NPC 자동 계승이 가져가지 않는다. 있으면 `applySuccession(…,'NPC_DEATH')`이고 직책(군주 포함)도 잇는다.
- **재산 후계자가 없을 때**: `retireNpcWithoutHeir`로 이전 없이 퇴장한다. 금·쌀·병력·소유 부곡은 명시 손실로 남긴다(월 효과·`GeneralLog`). 남의 부곡 지휘는 위 5단계 규칙을 따른다. 군주였다면 그 국가는 공석이 된다.
- **공석 채우기**(월 단계 3b): 관문이 아닌 도시가 있고 군주가 없는 국가를 국가 id 순으로 본다. 같은 국가의 등장 생존 NPC 가운데 직책 높은 순, 같으면 id 순으로 첫 장수가 `officerLevel=12`가 되고 `nation.isNpc=true`다. 이전 직책은 비고 재산은 옮기지 않는다. NPC가 없으면 공석을 유지한다. 사람 장수는 후보에 넣지 않는다. 사람은 `ruler.claim`으로만 잇고 그때 `isNpc=false`다.

### 월 정산 단계
`settleLineageMonthly(view, tick, resources)`는 `tick !== monthlyTick + TICKS_PER_MONTH`이면 예외다.

1. 정리(`reconcileLineage`): 만료 혼인 제안, 퇴장 장수의 관계·제안, 자격을 잃은 후계 지정을 지운다.
2. 1월에 나이를 `year − birthYear`로 맞춘다(퇴장 제외).
3. NPC 사망: id 오름차순으로 판정하고 사망마다 위 규칙을 적용한다. 사람 계승과 같은 재생 칸 처리는 기능 훅이 `resetLineageControl`로 한다.
   - 3b. 공석 채우기.
4. NPC 혼인
   - 국가 id 순, 그 안에서 등장 NPC를 id 순으로 본다. `UNKNOWN`이거나 이미 혼인한 NPC는 넘어간다.
   - 짝 후보는 같은 국가의 미혼 등장 NPC 가운데 반대 성별이고 친화 차가 `npc.affinityGap` 이하이며 `marriageEligibility`를 통과하는 첫 장수다. 후보가 없으면 난수를 뽑지 않는다.
   - 후보가 있으면 `rngFor(seed,'lineage',year,month)`에서 1번 뽑고 `npc.chanceBp` 미만이면 성혼한다.
   - 순회 중인 NPC가 제안자이며 `householdGeneralId`가 된다. 순회 순서가 결정적이므로 가주도 결정적이다.
   - 월 상한은 `npc.perMonth`이다.
5. 1월 출생
   - 혼인 id 순으로 보고 `lineageBirthEligibility`를 통과한 혼인마다 같은 난수 흐름으로 `chanceBp`를 판정한다. 판정 난수는 자격 있는 혼인마다 `chanceBp`와 무관하게 1번 뽑는다.
   - 연 상한이나 `maxGenerals`에 닿으면 `skippedBirths`에 `LIMIT`을 남기고 멈춘다. 이름 소진·연도 한도는 그 혼인만 `skippedBirths`에 남긴다.
   - 금·쌀을 만들거나 옮기지 않는다.
6. `monthlyTick = tick`으로 경계를 전진시킨다. 정리까지 포함한 한 달의 `revision`은 시작 값보다 정확히 1 크다.
7. 감사: 도시·도시 자원이 바뀌었거나 금·쌀 합이 사망 손실만큼만 줄지 않았으면 예외다. 마지막에 `assertLineageFinal`을 건다.

이 단계의 사망·공석·혼인·출생 자격은 마감한 달의 연도를 쓴다. 판정에 `tick-1`을 넘긴다. 사람의 개별 입력은 기존 게임 시계의 입력 tick을 그대로 쓴다.

이 단계는 기존 월 정산(`runMonthly`) 뒤에 돈다. 그래서 그 달 급여는 사망 NPC가 받은 뒤 이전된다. 출생 장수는 등장하고 국가에 속한 뒤부터 기존 급여 대상이다.

### 출생 장수 생성 (같은 기수 안의 물려받기)
같은 기수 안의 물려받기이며 계정 저장소를 읽는 T4-96 유산과 다르다. `generateLineageChild`(`lineage/birth.ts`)가 장수만 만들고 등록·예약 칸·저장은 정산 호출자가 같은 트랜잭션에서 맡는다.

부모를 가주 h(`marriage.householdGeneralId`)와 다른 부모 o로 둔다. 능력치·친화는 대칭이라 순서와 무관하다. 장수별 흐름 `r = rngFor(seed,'lineage-child',id)`를 능력치, 수명, 이름 시작점 순서로만 소비한다. 성별은 따로 `rngFor(seed,'lineage-child-sex',id)`에서 1번 뽑는다.

| 칸 | 값 |
| --- | --- |
| `id` | `max(generals id)+1`. 퇴장 장수 id도 포함한다 |
| `sex` | 위 출생 식. `MALE` 또는 `FEMALE`이며 이후 바뀌지 않는다 |
| 능력치 | 원생성 `statRules` 키마다 `clamp(round((h+o)/2) + r.int(−statSpread..statSpread), min, max)`. 3능력치 판은 `politics`·`charm`을 쓰지 않는다. 5능력치 판은 다섯 개 모두 쓴다 |
| `affinity` | `clamp(round((h.affinity+o.affinity)/2), 1, 150)` |
| `birthYear`·`age` | 올해, 0 |
| `deathYear` | `birthYear + r.int(lifespan.min, lifespan.max)` |
| `activeFromYear` | `birthYear + comingOfAgeYears` |
| `nextTurnTick` | `tick + rngFor(seed,'turn-offset',id).int(0, TICKS_PER_MONTH−1)` |
| 소속 | 출생 순간 h의 `cityKey`와 `nationId`. 국가가 있으면 `officerLevel` 1, 재야면 0 |
| 금·쌀 | 0. 이후 돈은 기존 급여·세입과 계승으로만 생긴다 |
| 기타 | `crew·train·atmos·experience·dedication·injury` 0, 원생성 기본 병종, `userId`·`portraitId`·`personality`·`special` null |
| DB 전용 | `turnRevision` 0, `defaultPolicy` `'none'`, `lastActiveTick`·`lastActiveAt`·`residenceTick` null |

**이름**
- 성씨: h의 이름이 `compoundSurnames` 중 하나(긴 것 먼저)로 시작하면 그 성씨, 아니면 첫 글자다.
- 이름자: `givenNames`를 `r` 시작점부터 차례로 본다. 생성 이름 규칙에 맞고 기존 이름(퇴장 포함)과 겹치지 않는 첫 이름을 고른다. 이름 후보는 성별과 무관하다.
- 맞는 이름이 없으면 출생하지 않고 `NAME_EXHAUSTED`를 남긴다. 이때 성별 흐름은 소비하지 않는다.

**국가가 다른 사람 부부의 자녀 (명시 계약)**
- 자녀는 출생 순간 가주 h의 도시·국가를 따르고 h의 성씨를 잇는다. 숫자 id의 크고 작음과 부모의 성별은 소속에 쓰지 않는다.
- o가 다른 국가면 o는 그 자녀를 후계자로 지정할 수 없다(`HEIR_NATION`). 자녀가 나중에 o의 국가로 오면 지정할 수 있다.
- h가 재야면 자녀도 h 도시의 재야다.
- 이 세 경우와 「id가 더 큰 쪽이 제안한 혼인」, 「여성 장수가 제안한 혼인」을 rules·PG 시험으로 고정한다.

**기록과 재생 칸**
- `persons[child]`에 `{parents:[h,o], bornTick}`를 쓴다.
- 휘하 기능이 있으면 `campaign.sources[child] = 'lineage:<tick>#general:<id>'`이고 campaign `revision`을 올린다. 그 revision이 한도면 예외다.
- 재생 칸은 `turns[child]`가 빈 큐, `revisions` 0, 방침이 있으면 `policy.policies[child]='none'`이다(`lineage/feature.ts` `settleMonthly`).

## API·DTO
- tRPC 프로시저
  - `lineage.get{worldId, generalId?}`
  - `lineage.submit{worldId, expectedUserId, expectedGeneralId, requestId, payload}`. `expectedGeneralId`는 필수다
  - `lineage.request{worldId, requestId}`
  - 기존 `general.create`: lineage 월드에서 `sex: 'MALE'|'FEMALE'` 필수, 그 밖은 금지. 오류는 `BAD_REQUEST`(메시지 `BAD_SEX`)다.
- 등급과 접수 순서는 황실과 같다.
  - `submit`은 `worldVerifiedProcedure`, 나머지는 `protectedProcedure`다.
  - 순서: 인자 검사(`BAD_REQUEST`) → 계정 일치(`expectedUserId`, `CONFLICT`) → 세션 → `World FOR UPDATE` → 세션 재확인 → 제재(`FORBIDDEN`) → 멱등키(같은 키에 다른 장수 id·payload면 `CONFLICT`) → `RUNNING`이 아니면 `PRECONDITION_FAILED` → 정산 경계 `CONFLICT` → 세션 장수(없으면 `NOT_FOUND`, `expectedGeneralId`와 다르면 `CONFLICT`) → 받은 제안이 아닌 `marriage.respond`는 `FORBIDDEN` → `decideLineageAction`(`NOT_OWNER`·`NOT_PARTY`는 `FORBIDDEN`, 나머지는 `BAD_REQUEST`) → `PENDING` 기록.
  - `request`는 황실처럼 `(worldId, userId, idempotencyKey)`로 찾는다. 계승 뒤에도 같은 UUID로 조회된다. 다른 사용자의 요청 번호는 `NOT_FOUND`다.
  - 오류 코드 표는 `UNAUTHORIZED`·`NOT_FOUND`·`FORBIDDEN`·`BAD_REQUEST`·`CONFLICT`·`PRECONDITION_FAILED`이고 CF 대조 기준이다.
  - `auth/verificationRegistry.test.ts`에 `'lineage.submit'`이 있다.
- 조회 범위는 rules `lineage/visibility.ts` `lineageView(world, actorId, tick, focusId, detailsVisible)`가 정한다. 서버는 `detailsVisible`로 기존 `visibility(actor).general`(본인·같은 국가)을 넘긴다. 장수가 없는 사용자는 상세를 하나도 받지 않는다.
  - **공개 기본 가계**: 인물마다 `id`·`name`·`nationId`·`sex`(`UNKNOWN` 포함)·`active`·`parents`·`bornTick`·`successorId`·`exit{tick, cause}`. 혼인 목록(가주 포함), 국가별 공석 여부, 도시 이름.
  - **상세 칸**: `portraitId`·`cityKey`·`isHuman`·`activeFromYear`·`age`·`officerLevel`은 `detailsVisible`을 통과한 인물에만 붙는다.
  - **본인만(`mine`)**: 행위 장수 id, 자기 후계 지정(`heirId`), 혼인 후보와 실패, 후계 후보와 실패, 계승 미리보기와 미리보기 실패, 청구 가능할 때의 `claim:{nationId, currentOfficerLevel}`.
  - **당사자 둘만**: 자기가 보내거나 받은 혼인 제안. `householdGeneralId`와 가주의 현재 도시 `householdCityKey`는 이 제안 행에만 있다.
  - 다른 장수의 금·쌀은 기존 `visibility.ts` 범위를 넘지 않는다. 일반 장수 DTO에는 `sex`를 더하지 않는다. 가문 응답에는 `deathYear`·친화 수치·차이값이 없다.
- **후보 실패 코드의 공개 범위 (검토 N1 선택지 b)**
  - `detailsVisible`을 통과하지 못한 대상의 혼인·후계 후보 실패는 일반 코드 `UNAVAILABLE`(「지금은 이 요청을 할 수 없습니다.」)로 바꾼다. 원래 코드(`AGE`·`NPC_REFUSED`·`LIMIT`·`HEIR_CONTROLLED` 등)와 문구는 내보내지 않는다.
  - `HEIR_RESERVED`는 대상과 관계없이 항상 일반화한다. 후보 목록은 `UNAVAILABLE`이다. 접수 사전 판정의 거절 문구와 `lineage.request` 영수증은 「지금은 후계자로 지정할 수 없습니다.」이고 영수증 코드는 사유 없는 `HEIR_INELIGIBLE`이다.
  - 남는 노출: 후보마다 가능·불가 여부는 행동 자격으로 계속 보인다. 이 이진 결과에서 다른 국가 장수의 조작 구분이나 나이대를 일부 추론할 수 있다. 실제 규칙이 다른 국가 사람에게 제안을 허용하고 다른 국가 NPC에게는 허용하지 않으므로 이 차이는 없앨 수 없다. 직접 접수의 거절은 `HEIR_RESERVED`를 빼고 원래 코드·문구를 그대로 돌려준다. 다른 사람의 지정 기록이나 비공개 값을 직접 담는 칸은 없다. 다만 상세를 볼 수 있는 자기 자녀가 공개된 앞선 자격 조건을 모두 만족하고도 불가라면 다른 생존 장수의 후계 지정이 있음을 추론할 수 있다. 일반화는 원문 사유를 없애며 지정 사실의 추론까지 막지는 않는다.
- 계승 미리보기, 혼인 후보, 청구 가능 여부는 `get` 응답에 순수 함수 결과로 넣는다. 화면은 계산하지 않는다(`apps/web`은 rules를 import하지 않는다).

### rules

  - 원생성 config 누락·범위 위반·중복 초기화를 거부한다. 모르는 칸(`pairing` 포함)과 `femaleBp` 누락을 거부한다.
  - 진행 중 config·seed 변경을 거부한다.
  - 같은 달 두 번, 한 달 건너뜀은 예외다.
  - 같은 순서 없는 쌍의 혼인·제안 중복, `householdGeneralId ∉ {a,b}`는 로드 거부다. `parents`가 `[큰 id, 작은 id]`인 상태는 로드된다. 원생성 `persons`는 비어 있다.
- **성별 판 보존·원장**
  - 꺼진 월드: `InitialGeneral`·상태·해시에 `sex` 키가 없고 기존 골든과 같다. 키가 있으면 `assertGeneralSex`가 거부한다.
  - lineage 원생성: `sex`가 없거나 다른 값인 장수가 있으면 거부한다.
  - `applySexLedger`: 대상 시나리오의 직접 지정, ID·이름 불일치, 다른 시나리오의 일부 지정을 거부한다. 원장 밖 인물은 이름이 무엇이든 `UNKNOWN`이다. 스키마는 미승인 review와 중복 ID를 거부한다. 엔진 `loadSexLedger`는 해시 불일치를 거부한다.
- **생성 입력**
  - lineage 월드: `sex` 누락·`UNKNOWN`·다른 문자열은 `BAD_SEX`이고 `MALE`·`FEMALE`은 결과 장수에 그대로 들어간다.
  - 꺼진 월드: `sex` 키가 있으면 `BAD_SEX`이다. 기존 payload의 결과와 `create` 흐름 난수 소비가 같다.
  - 재생: 결과 `general.sex`가 payload와 다르거나 꺼진 월드 결과에 `sex`가 있으면 거부한다. lineage+5능력치 월드의 생성 기록이 five-stats `checkArchive`와 `replayInputs` 판별을 통과한다.
- **퇴장 표지**: 퇴장 장수가 일정, 순위, 급여, 연감, 방어자, 황실 군주 판정, 등용 대상(`BAD_TARGET`)에 나오지 않는다. `assertLineageFinal`의 잔여 참조 검사를 사례별로 1개씩 둔다.
- **혼인 거부**: 자기 혼인, `UNKNOWN` 한쪽(`SEX_UNKNOWN`), 같은 성별(`SEX_PAIR`, 남남·여여 각 1), 친족(`kinDepth` 경계 ±1), 중혼 상한, 나이 경계, 미등장·퇴장 대상, 남의 제안 수락(`NOT_PARTY`), 닫힌 제안 응답, NPC 조건(`NPC_REFUSED`). 성별 거부는 사람 제안, 사람→NPC 즉시 성혼, NPC 월 짝짓기에서 각각 확인한다.
- **혼인 중복·가주**
  - A→B 제안이 미결일 때 B→A 제안은 `OFFER_PENDING`이고 제안 수·혼인 수가 그대로다.
  - 성혼 `householdGeneralId`: 사람 제안 수락은 `offer.fromId`, 사람→NPC 즉시 성혼은 사람, NPC 월 짝짓기는 순회 중인 NPC. 여성 제안자도 가주가 된다.
- **NPC 월 짝짓기 난수**: `UNKNOWN` NPC와 후보 없는 NPC는 흐름을 소비하지 않는다.
- **후계 지정·계승 거부**
  - `HEIR_INELIGIBLE`과 `reason`: 사람 장수, 다른 국가, 미등장, 퇴장, 깊이 밖, 다른 사람이 지정한 장수(`HEIR_RESERVED`).
  - 지정과 다른 후계자(`NOT_DESIGNATED`), 같은 장수의 두 번째 계승, `expected` 불일치(`PREVIEW_CHANGED`)는 거부한다.
  - `HEIR_AWAY`·`HEIR_COMMANDS_OTHERS`·`HEIR_CAPACITY`는 각 1개 사례로 확인한다.
  - 예약 변경 번호: 어느 한쪽이 `LINEAGE_MAX−1` 이상이면 `LIMIT`, 그 아래 경계는 통과한다.
- **사람 계승 보존식**
  - 금·쌀·병력·부곡 병력 합과 부곡별 지휘관 도시가 같다. 손실은 0이다.
  - 휘하·지시·제안·발령 제안의 해제 목록이 미리보기와 같다.
  - revision: 전임자 revision이 후계자보다 큰 경우·작은 경우·같은 경우 모두 후계자 새 값 > 전임자 옛 값이다. 두 장수의 방침은 `'none'`이다.
- **NPC 계승**
  - 명시 손실 합과 보존식이 맞는다. 재산 후계자 순위를 확인한다. 사람이 지정한 자녀는 NPC 계승에서 빠진다.
  - 다른 도시 부곡 손실과 남의 부곡 지휘 반환(같은 도시·다른 도시)을 확인한다.
  - 후계자 없는 사망은 어떤 장수의 금·쌀·부곡도 늘리지 않는다.
- **공석·청구**
  - NPC 후보가 없으면 공석, 있으면 순위대로 채우고 `isNpc=true`다. 사람은 자동 즉위 0이다.
  - `ruler.claim`의 거부: 공석 아님, 다른 국가, 미등장, 퇴장, 멸망 국가.
  - 같은 달 두 청구는 앞의 것만 적용된다. 청구 뒤 `isNpc=false`이고 조약 자동 응답이 멈춘다.
  - 공석 동안 국가 예턴·NPC 인사·등용이 실행되지 않고 5~11 직책 칸은 실행된다.
- **불변식**: 휘하 불변식을 지킨다. 계승·청구 직후 `syncOffices`가 옛 군주와 청구자 옛 직책의 국가 칸을 비운다. lineage 월드에서만 같은 장수의 조작자 전환이 칸과 임기를 새로 시작한다. `assertLineageFinal`이 남녀 아닌 혼인을 거부한다.
- **황실 연동**: `governance-v1`이 함께 켜진 상태에서 사람·NPC 계승, 공석, 청구 뒤 `reconcileGovernance`가 정확히 1회 돌고 결과가 미리보기의 `governance`와 같다.
- **출생**
  - 능력치 clamp(3·5능력치 판), `affinity`, 수명, 이름 충돌과 `NAME_EXHAUSTED`, 상한 정지를 확인한다.

  - 소속·성씨는 가주를 따른다: 국가가 다른 부부, 재야 가주, id가 더 큰 장수가 제안한 혼인, 여성 장수가 제안한 혼인 각 1개.
- **자녀 성별·재현**
  - `femaleBp` 0이면 모든 자녀가 `MALE`, 10000이면 `FEMALE`이다.
  - 같은 원생성·seed를 두 번 돌리면 자녀 id·성별·능력치·이름이 같다.
  - `femaleBp`만 다른 두 월드의 첫 출생 달 자녀는 `sex`만 다르다.
  - 성별 흐름은 자녀마다 1번만 소비한다. `NAME_EXHAUSTED`이면 소비하지 않는다.
- **성별 불변**: 상한을 채운 장기 무작위 진행(계승·청구·혼인·출생 포함)에서 기존 장수의 `sex`가 처음 값과 같다.

### CF (AC-P2-35)
- CF 담당이 같은 순수 규칙·DTO로 `LineageStore`와 엔진 repository 모양을 WorldDO에 구현한다.
- 조작권 교체, 상태, 출생 행, 멱등키를 DO 트랜잭션 하나에 쓴다. 단일 조작권은 DO에서 명시적으로 검사한다.
- 장수 `sex` 칸을 같은 3값으로 저장한다. PG 트리거 대신 DO 쓰기에서 기존 값과 다르면 거부한다. 꺼진 월드는 칸이 없다.
