## 계획 (Claude)

### 목표와 AC 몫

`packages/rules`에 지도 형식 v2 schema와 초기화 자원 다섯 종류(지도, 시나리오, 병종, 기본 능력치 규칙, 초상 대응표)의 순수 검증 함수를 둔다. 함수는 입력을 바꾸지 않는다. 같은 입력이면 같은 순서의 오류·경고 목록과 판정(통과, 실패, 미완)을 돌려준다. 편집 화면과 게시 API가 같은 함수를 부르도록 공개 하위 경로 하나로 낸다.

AC-P2-27에서 이 작업이 맡는 것은 검증을 통과한 판만 게시한다는 문장의 판정 함수뿐이다. 판 복제·편집·게시·권한·감사·월드 생성 선택·E2E는 T4-78·T4-79·T4-81·T4-87 몫이므로 이 작업이 끝나도 AC-P2-27은 미완료다. AC-P2-26(DB 이전)과 AC-P2-28(바탕 그림)은 이번에 착수하지 않는다.

D-028이 정한 것은 전제로만 쓴다. 지도 단위는 도시와 연결이다. 지형은 표시 전용이다. 게시한 판은 바뀌지 않고 기존 월드와 재생은 영향받지 않는다. 지금 키(`che`, `1030`, `basic`)는 1판 별칭이고 자원은 DB로 옮기며 출처 고지는 남긴다.

### 계약

#### C1 지도 형식

`version` 칸이 없으면 v1이다. v1은 지금 `mapSchema`로 읽는다. 내장 `che`가 v1이며 원본은 고치지 않고 v1으로 검사한다. `version`이 2면 v2, 그 밖의 값은 `map-version-unknown`이다.

```ts
type Point = [number, number];             // shape: 유한수 두 개짜리 튜플
type Ring = Point[];                        // 점 수(다각형 4개 이상, 강 2개 이상)와 닫힘은 terrain 단계
type MapResourceV2 = {
  $comment?: string;                        // 출처 고지. 있으면 그대로 둔다
  version: 2;
  id: string; name: string;                 // 지금 mapSchema와 같은 조건
  canvas: { width: number; height: number }; // 양의 정수. 지도마다 둔다. 상한은 C5
  defaults: { trust: number; supplyState: 0 | 1; trade?: number; frontState?: number };
  cities: MapCity[];                        // 지금 mapSchema의 도시 칸과 같은 조건. meta 칸 없음
  terrain: { coast: Ring[]; lakes: Ring[]; mountains: Ring[]; rivers: Array<{ name?: string; points: Point[] }> };
};
```

- v2는 모든 단계에서 strict다. 위에 없는 칸은 `shape-invalid`다(제안). 내용 전체가 나중에 정규 해시(T4-77)에 들어가므로 규칙이 읽지 않는 칸이 판을 가르지 않게 한다. `defaults.trade`·`frontState`는 `che`에서 온 칸이라 유한수일 때만 받는다. v1 `mapSchema`는 이 두 칸을 검사 없이 버린다. v1을 v2로 옮길 때의 처리는 아래 `normalizeMapToV2`가 정한다. 강 `name`은 있으면 빈 글자가 아니다.
- `shape`는 점마다 유한수 두 개짜리 튜플인지만 본다. 원소가 3개인 좌표 튜플은 `shape-invalid`다. 다각형 점 4개 미만, 강 점 2개 미만, 끝 점이 첫 점과 다른 고리는 형식을 지나 `terrain` 단계의 `terrain-open`이 된다. 점 3개짜리 고리는 `terrain-open`이다.
- `terrain`과 네 층은 v2에서 모두 있어야 하고 빈 배열은 된다. C-M2의 `terrain?`는 v1에 지형이 없다는 뜻으로 읽는다.
- 캔버스 크기는 C-M2대로 지도마다 둔다. v2는 `canvas`에 양의 정수 너비·높이를 받는다. `MAP_DEFAULT_CANVAS`(700×500)는 v1을 v2로 복제할 때 붙이는 기본값이다. 신뢰할 수 없는 입력의 거대 캔버스는 C5 `RESOURCE_LIMITS`의 기술 상한으로만 막는다. 지금 `WorldMap.tsx`는 700×500 고정이고 `WorldInit`에 캔버스가 없다. 이 작업은 700×500이 아닌 지도의 표시를 지원하지 않으며 표시 연결은 인계 H1로 넘긴다.
- 좌표계는 도시와 지형이 같다. 원점은 왼쪽 위다. 경계값 0·너비·높이는 안으로 친다.
- 층의 뜻은 `sketch.ts:71-80`을 따른다. 자기 교차는 막지 않는다. 짝홀 규칙으로 칠한 결과가 하나로 정해져서다. 밑그림 5색은 rules에 두지 않고 T4-80 표를 정본으로 둔다(제안). 규칙 패키지에 표시 색을 넣지 않기 위해서다.
- `normalizeMapToV2(raw: unknown)`는 편집·복제용 사본만 만든다. 결과는 `{ ok: true; map: MapResourceV2; dropped: string[] }` 또는 `{ ok: false; report }`다. v1이면 C5 한도와 `mapSchema` 형식 검사를 지난 뒤 `$comment`(글자일 때)·`id`·`name`·`MAP_DEFAULT_CANVAS`(700×500)·`defaults`·도시 8칸·빈 지형으로 새 객체를 만든다. `defaults`의 `trust`·`supplyState`는 그대로 옮긴다. `trade`·`frontState`는 원본 v1 `defaults`에 그 키가 실제로 있고 값의 `typeof`가 `number`이며 유한수일 때만 옮긴다. 지금 `mapSchema`가 두 칸을 검사 없이 버리므로 글자·`null`·불리언·배열·객체·`NaN`·`±Infinity`도 v1 형식 검사를 지난다. 이런 값은 옮기지 않고 그 칸 경로(`defaults.trade`, `defaults.frontState`)를 `dropped`에 적는다. 키가 없으면 옮길 것이 없을 뿐 누락 진단이 아니어서 `dropped`에 적지 않는다. `che`의 `trade` 100과 `frontState` 0은 그대로 옮긴다. 원본 v1 schema·로더·자원은 바꾸지 않는다. 그 밖에 옮기지 않은 칸(맨 위 `meta`, `cities.N.meta`, 그 밖의 `defaults` 키)도 `dropped`에 점 경로로 적는다. `dropped`는 키 삽입 순서와 무관하게 C3 경로 정렬(배열 번호는 숫자 순, record 키는 UTF-16 코드 단위 순, 숫자가 먼저)로 줄 세운 뒤 점으로 잇는다. v2면 형식 검사 뒤 깊은 복사를 돌려주고 `dropped`는 빈 목록이다. 입력은 바꾸지 않는다. 멱등성은 결과 전체가 아니라 `map` 값으로 본다. `map1 = normalizeMapToV2(v1).map`, `map2 = normalizeMapToV2(map1).map`이면 `map2`는 `map1`과 깊게 같다. 첫 결과의 `dropped`에는 실제로 옮기지 않은 경로가 들어가고 두 번째 결과의 `dropped`는 `[]`다. 키 순서는 `serializeMap`(`contract.ts:188-217`)과 같게 둔다. 이 순서는 표시용이며 해시 계약이 아니다.

#### C2 공개 경로와 API

모두 `@opensamguk/rules/resource-validation`에서 낸다. 부모가 이 순수 하위 경로를 검증기 공유 범위로만 채택했다(E3, C7). 기존 root 경로의 동작·로더·schema는 바꾸지 않는다. `package.json`의 새 명시 export 한 줄은 후속 구현에서 소유 조율을 거쳐 더하며 지금 설정에는 없다. 이 경로의 파일은 zod, `world/resources.ts`, 자기 폴더와 `world/map/`만 import한다. `bootstrap.ts`·`@opensamguk/shared`는 끌어오지 않는다. DB·파일·현재 시각·난수를 쓰지 않는다.

```ts
type ResourceKind = 'MAP' | 'SCENARIO' | 'UNIT_SET' | 'STAT_RULES' | 'PORTRAIT_MAP'; // C-M1 이름
type IssueTarget =
  | { kind: 'root' }
  | { kind: 'path'; path: ReadonlyArray<string | number> }          // 형식 오류
  | { kind: 'city'; index: number }                                 // 도시 목록 번호
  | { kind: 'terrain'; layer: 'coast' | 'lakes' | 'mountains' | 'rivers'; index: number }
  | { kind: 'nation' | 'general' | 'diplomacy' | 'crewType'; index: number }; // 튜플·목록 행 번호
interface ResourceIssue {
  code: ResourceIssueCode;
  severity: 'error' | 'warning';
  message: string;                                   // 한국어 한 문장 (C5)
  target: IssueTarget;
  params: Readonly<Record<string, string | number>>; // 코드마다 키 고정
  source?: { kind: ResourceKind; index: number };    // 맥락으로 넘긴 다른 자원의 항목일 때
}
type CheckGroup = 'limits' | 'shape' | 'cities' | 'links' | 'network' | 'terrain' | 'scenario-refs'
  | 'nations' | 'generals' | 'diplomacy' | 'map-refs' | 'crew-types' | 'stat' | 'portraits';
interface ResourceReport<T> {
  kind: ResourceKind;
  status: 'pass' | 'fail' | 'incomplete';
  issues: ResourceIssue[];
  ran: CheckGroup[];
  skipped: Array<{ group: CheckGroup; reason: 'blocked' | 'context-missing' | 'context-invalid'; contextIndex?: number }>;
  truncated: boolean;
  value: T | null;                                   // 형식을 지난 값. 표시용이며 저장은 원본 그대로
}

validateMap(input: unknown, ctx?: { scenarios?: ReadonlyArray<unknown> }): ResourceReport<MapResource | MapResourceV2>;
validateScenario(input: unknown, ctx?: { map?: unknown }): ResourceReport<ScenarioResource>;
validateUnitSet(input: unknown): ResourceReport<UnitSetResource>;
validateStatRules(input: unknown): ResourceReport<{ stat: StatRules }>;
validatePortraitMap(input: unknown): ResourceReport<{ portraits: Record<string, number> }>;
validateWorldResources(input: { map: unknown; scenario: unknown; unitSet: unknown; statRules: unknown; portraitMap?: unknown }):
  { status: 'pass' | 'fail' | 'incomplete'; map: ResourceReport<unknown>; scenario: ResourceReport<unknown>;
    unitSet: ResourceReport<unknown>; statRules: ResourceReport<unknown>; portraitMap: ResourceReport<unknown> };
```

- `status`는 오류가 하나라도 있으면 `fail`이다. 오류가 없고 `skipped`가 비어 있지 않으면 `incomplete`, 둘 다 없으면 `pass`다. 경고는 판정을 바꾸지 않는다. 게시와 월드 생성은 `pass`만 받아야 한다. `incomplete`를 통과로 세지 않는다.
- `validateMap`의 `ctx.scenarios`가 `undefined`면 `scenario-refs`는 `context-missing`으로 빠진다. 빈 배열이면 확인할 시나리오가 없다는 뜻이라 돈 것으로 친다. 어떤 시나리오를 넘길지는 T4-78이 정한다. 맥락 개수·개별 한도·누적 한도·형식은 참조 검사 전에 C3의 맥락 순서로 본다.
- `validateScenario`의 `ctx.map`이 없으면 `map-refs`가 `context-missing`이다. 지도가 C5 한도나 형식 검사를 못 지나면 `contextIndex` 없는 `context-invalid`다. 지도 자체의 관계 오류(이름 중복 등)는 시나리오 오류로 옮기지 않는다. 이름 존재만 보므로 판정이 하나로 정해진다.
- `validateWorldResources`는 `buildInitialWorld`와 같은 입력 묶음을 받는 완전 검사다. 시나리오에는 그 지도를 맥락으로 넘기고 지도에는 `scenarios: []`를 넘겨 같은 참조를 두 번 알리지 않는다. `portraitMap`이 없으면 `buildInitialWorld`(`bootstrap.ts:115`)처럼 빈 대응표로 본다. 다섯 보고가 모두 `pass`일 때만 `pass`다. 시드 검사는 자원 검사가 아니라서 넣지 않는다.
- 검증기는 받은 입력과 맥락만 검사하며 넘기지 않은 대상을 검사했다고 쓰지 않는다. caller가 대상을 여러 호출로 쪼개거나 32개를 넘는 시나리오 중 일부만 넣고 나머지를 빼면 함수는 그 누락을 알 수 없다. 그렇게 쪼갠 호출을 전체 게시 통과로 세면 안 된다. 전체 대상 집합, 호출을 나눌 때의 누적 한도, 모든 보고의 `pass` 확인과 빠진 대상 없음은 caller(T4-78 등)가 책임진다.

#### C3 검사 단계와 구조가 깨진 입력

단계는 `limits` → `shape` → 관계 검사 순서로 돈다. 앞 단계에 오류가 있으면 뒤 단계는 하나도 돌지 않고 `skipped`에 `blocked`로 적힌다. 그래서 관계 검사는 늘 형식을 지난 값만 본다. 없는 칸 접근이나 `NaN` 계산이 생길 수 없다.

- `limits`는 zod 전에 C5 한도 표의 모든 칸을 세는 한정된 선행 계수다. 세는 경로의 각 단계에서 값이 `null`·원시값이 아닌지 먼저 본다. 배열은 `Array.isArray`가 참일 때만 `length`를 읽고 record는 배열이 아닌 객체일 때만 `Object.keys`로 키 수를 센다. 모양이 기대와 다르면 그 칸은 세지 않고 넘어가며 `shape`가 잡는다. 세는 순서는 C5 표의 칸 경로 순, 배열 안에서는 번호 순, record 안에서는 키를 UTF-16 코드 단위 순으로 정렬한 순서다. 배열이나 record가 자기 한도를 넘으면 그 경로에 `resource-too-large` 하나를 내고 그 안으로 내려가지 않는다. 합계 한도는 같은 순서로 더하다가 넘는 순간 그 칸 경로에 `resource-too-large` 하나를 내고 그 합계 세기를 멈춘다. 계수의 정상 빈 배열 `[]`은 0개로 세고 지금 schema대로 받는다. 초상 대응표의 `portraits`는 record라 키 수로 센다. 키가 20,001개면 `resource-too-large`이고 `shape`와 뒤 단계는 `blocked`다(V6). 한도를 지난 자료에만 zod `shape`를 돌리고 `shape`를 지난 값만 관계 검사와 참조 검사에 쓴다.
- 맥락 자원은 입력 자원 자신이 `limits`·`shape`를 지난 뒤에만 읽는다. 입력이 앞 단계에서 막히면 `scenario-refs`·`map-refs`도 `blocked`이고 맥락은 세지 않는다. `validateMap`은 이 순서로 `ctx.scenarios`를 다룬다. 먼저 배열인지와 개수를 본다. 배열이 아니면 `scenario-refs`를 `contextIndex` 없는 `context-invalid`로 뺀다. 33개 이상이면 `root` 대상 `resource-too-large` 오류 하나(`params`에 한도 이름과 32)를 내고 `scenario-refs`를 `contextIndex` 없는 `context-invalid`로 빼며 원소는 읽지 않는다. 다음으로 맥락을 넘긴 순서대로 개별 시나리오 한도(C5)로 센다. 개별 한도를 넘은 맥락은 `context-invalid`(`contextIndex`)로 빼고 누적에 더하지 않는다. 개별 한도를 지난 맥락의 국가·장수·외교·소유 도시 이름 수는 C5의 네 누적 합에 더한다. 어느 누적 합이 한도를 넘으면 넘게 만든 맥락을 `source`로 단 `root` 대상 `resource-too-large` 오류를 넘은 합마다 하나씩(국가, 장수, 외교, 소유 도시 이름 순) 내고 `scenario-refs` 전체를 `contextIndex` 없는 `context-invalid`로 빼며 참조 검사는 하지 않는다. 누적 한도를 지나면 남은 맥락마다 `shape`를 돌려 실패한 것을 `context-invalid`(`contextIndex`)로 뺀다. 그 뒤에 `shape`를 지난 맥락만 넘긴 순서로 참조 검사에 쓴다. `validateScenario`의 `ctx.map`도 지도 한도와 `shape`를 차례로 지나야 쓴다.
- 맥락이 자기 `limits`·`shape`에서 낸 오류는 이 보고로 옮기지 않는다. 원인 위치는 `contextIndex`로 가리키고 내용은 그 맥락을 자기 검증 함수로 따로 검사해 본다. 빠진 맥락이 하나라도 있으면 남은 맥락이 모두 통과해도 `pass`가 아니다. 오류가 있으면 `fail`이고 오류 없이 `skipped`만 있으면 `incomplete`다. 실패한 맥락을 빼고 남은 것만으로 통과를 세지 않는다.
- `shape`는 zod 오류 하나마다 `shape-invalid` 하나다. 대상은 `path`이고 `params.zodCode`에 zod 코드를 둔다. 경로를 원소별로 비교해(숫자는 크기, 글자는 UTF-16 코드 단위, 숫자가 먼저) 정렬하고 같으면 zod 코드 순으로 둔다. 지역 설정에 기대는 `localeCompare`는 쓰지 않는다. 능력치 규칙의 `refine` 실패만 `stat-rules-inconsistent`로 바꾼다.
- JSON으로 만들 수 있는 모든 값(객체가 아닌 값, `null`, 배열, 깊게 잘못된 모양)에서 함수는 던지지 않는다. schema가 보는 칸에 프로그램이 넣은 `NaN`·`Infinity`는 형식 오류다. v1 `defaults.trade`·`frontState`처럼 v1 schema가 버리는 칸은 형식 오류가 아니고 C1 복제 규칙을 따른다.
- 관계 검사 순서는 지도 `cities` → `links` → `network` → `terrain` → `scenario-refs`, 시나리오 `nations` → `generals` → `diplomacy` → `map-refs`다. 한 단계 안에서는 목록 번호 순서이고 한 대상 안에서는 C4 표의 위에서 아래 순서다. 같은 대상에 같은 코드가 record 키마다 나오면 키를 UTF-16 코드 단위 순으로 둔다. 지형은 해안, 호수, 산맥, 강 순서(`contract.ts:48-53`)다. 맥락 자원은 넘긴 순서다. `map-canvas-unsupported` 검사는 `cities` 그룹의 첫 검사로 돌아 `root` 대상 오류를 낸 뒤 같은 그룹의 도시 목록 번호 순 검사로 이어진다.

#### C5 문구·한도·결정성

- 문구는 합니다체 한 문장이고 글쓰기 규칙을 따른다. rules에는 받침 조사 도구가 없으므로 바뀌는 값은 괄호에 넣는다. 예: `도시 ID가 겹칩니다 (4번째 도시, ID 7).`, `연결이 한쪽에만 있습니다 (업 → 남피).` 사람이 읽는 번호는 1부터, `target.index`는 0부터다.
- 한도 `RESOURCE_LIMITS`는 총괄이 채택한 잠정 기술 한도다. 성능이나 지금 화면의 표시 지원을 승인한 값이 아니며 숫자를 임의로 바꾸지 않는다. 내장 값(도시 94, 장수 491, 국가 21, 병종 4)의 10배 이상 여유다. 요청 본문 크기 한도는 서버(T4-78) 몫이다. `limits`는 아래 표의 위에서 아래 순서로 센다(C3).

| 자원 | 세는 것 | 한도 |
| ---- | ------- | ---- |
| 지도 | 도시 | 1,000 |
| 지도 | 도시 하나의 연결 | 64 |
| 지도 | 층 하나의 선 | 2,000 |
| 지도 | 선 하나의 점 | 10,000 |
| 지도 | 지형 점 합계 | 200,000 |
| 시나리오 | 국가 | 500 |
| 시나리오 | 국가 하나의 소유 도시 이름(`nation[8]`) | 1,000 |
| 시나리오 | 소유 도시 이름 합계 | 500,000 (500×1,000) |
| 시나리오 | 장수 | 10,000 |
| 시나리오 | 외교 | 10,000 |
| 병종 | 병종 | 500 |
| 병종 | `armTypes` 키 | 500 |
| 병종 | 병종 하나의 `attackCoef`·`defenceCoef` 각 record 키 (빈 배열 `[]`은 0) | 500 |
| 병종 | 계수 키 합계 | 500,000 (2×500×500) |
| 초상 | `portraits` 키 | 20,000 |
| 지도 맥락 | `validateMap` 호출 하나의 `ctx.scenarios` 개수 | 32 |
| 지도 맥락 | 모든 맥락이 함께 쓰는 누적 국가·장수·외교·소유 도시 이름 | 500 · 10,000 · 10,000 · 500,000 |

맥락 시나리오 하나하나에도 시나리오 행의 개별 한도가 그대로 걸린다. `validateScenario`의 `ctx.map`에는 지도 행이 걸린다.
- 같은 `RESOURCE_LIMITS`에 캔버스 상한을 총괄이 채택한 잠정 기술 한도로 둔다. 한 변 4,096, 넓이(너비×높이) 4,194,304다. 이 둘은 형식을 지난 정수를 보므로 `limits`가 아니라 관계 단계의 `map-canvas-unsupported`로 낸다. 근거는 바탕 그림이 캔버스의 3배(map-editor.md §4)라는 점이다. 넓이 상한의 밑그림은 픽셀이 9배이고 RGBA로 풀면 약 151MB이며 기본 700×500은 약 12.6MB다. 계산값이며 실행해 잰 값이 아니고 실측 성능으로 세지 않는다. 신뢰할 수 없는 입력을 막는 기술 상한이며 세계 단위나 게임 수치를 정하지 않는다.
- 한도 경계 표본의 시간과 RSS는 구현 뒤 실제로 재서 공개 전에 판정한다(V14). 지금은 시간 상한도 실측값도 성능 통과 판정도 없다.
- 항목 상한은 1,000개다. 넘으면 앞 1,000개만 남기고 `truncated: true`다. `status`는 자르기 전 전체로 정한다.
- 시간 복잡도는 도시·연결·점 수에 비례하게 짠다. ID·이름은 `Map`, 연결 대칭은 도시별 `Set`으로 보고 연결망 탐색은 배열 앞에서 빼지 않고 번호로 진행한다.
- 입력을 바꾸지 않는다. `value`와 `normalizeMapToV2` 결과는 새 객체다. 같은 입력은 같은 결과이며 객체 키 삽입 순서가 달라도 항목과 `dropped` 순서가 같다. 순서는 배열 번호(숫자 순), C4 표 순서, 정렬한 record 키(UTF-16 코드 단위 순)만 쓴다. 경로 비교와 같은 경로의 tie-break는 C3 `shape` 규칙과 같다.

#### C6 기존 로더·월드 생성·해시와의 관계

- `buildInitialWorld`는 그대로 마지막 방어선이다. 검증기를 부르지 않고 던지는 문구도 그대로다. 엔진 `loadInitialWorld`도 이 작업에서 바뀌지 않는다.
- `validateWorldResources`가 `pass`면 같은 자원과 비지 않은 시드로 `buildInitialWorld`가 던지지 않는다. `buildInitialWorld`가 자원 때문에 던지는 입력(C4 근거 `생성` 행)은 모두 `fail`이다. 검증기는 그 밖의 아래 오류만큼 지금 로더보다 엄격하다. 형식에서는 v2 strict 추가 칸·강 빈 이름·정수가 아닌 캔버스·유한수가 아닌 v2 `trade`·`frontState`·원소 수가 틀린 좌표(`shape-invalid`), 2가 아닌 `version`(`map-version-unknown`), C5 한도와 맥락 개수·누적 한도(`resource-too-large`)다. 지도 관계에서는 `map-canvas-unsupported`, `city-out-of-canvas`(v1은 700×500), `network-split`, `terrain-open`, `terrain-out-of-canvas`다. 시나리오는 `scenario-nation-name-duplicate`, 병종은 `unitset-wall-missing`이다. 조언 경고(`city-name-blank`, `city-level-range`, `city-region-range`, `scenario-general-name-duplicate`, `scenario-diplomacy-duplicate`, `unitset-default-not-recruitable`, `unitset-arm-unknown`, `unitset-coef-arm-unknown`)는 판정을 바꾸지 않는다.
- v2 지도를 `buildInitialWorld`에 넣으면 `mapSchema`가 `version`·`canvas`·`terrain`·`$comment`를 버린다. 같은 도시를 가진 v1과 v2는 같은 `WorldInit`, 같은 초기 상태 해시, 같은 `resourceHash`를 낸다. 캔버스가 `WorldInit`에 없으므로 700×500이 아닌 지도를 표시하려면 판 메타데이터를 표시에 잇는 후속이 필요하다(인계 H1).
- 기존 schema를 고치지 않으므로 schema를 거친 `unitSet`·`statRules` 값이 그대로이고 `resourceHash`와 재생 고정물 해시가 바뀌지 않는다.
- 월드 초기 상태 해시(`hashState(WorldInit)`), `resourceHash`, 카탈로그 정규 해시(T4-77)는 서로 다르다. 이 작업은 셋 다 만들거나 바꾸지 않는다.

#### C7 편집 화면 임시 사본과의 경계

화면 사본 교체는 Claude 후속이며 이번에 고치지 않는다(인계 H5). T4-80이 지금 내보내는 v2와 정본 v2는 아래만 다르다.

| 항목 | T4-80 지금 | 정본 v2 | 지금 내보낸 파일 |
| ---- | ---------- | ------- | ---------------- |

칸 이름 `canvas`, 닫힌 다각형 정의, 좌표 경계 포함, 대상 모양(도시 목록 번호, 층과 번호), 코드 이름은 T4-80을 따랐다. 바꿀 양을 줄이려는 것이다.

부모가 화면 예외 E3를 `@opensamguk/rules/resource-validation` 순수 하위 경로의 검증기 공유 범위로만 채택했다. E3 한정 계약 채택이며 계획 전체 PASS나 구현 권한이 아니다. 지금 `eslint.config.js`와 `package.json`에는 E3와 새 경로가 없고 후속 구현에서 소유 조율을 거쳐 더한다.

- `@opensamguk/rules/resource-validation`의 값과 타입만 허용한다. `@opensamguk/rules` 본 경로, 다른 하위 경로, `@opensamguk/shared/node`, engine·db 값, server 값, Node 내장 모듈은 E1처럼 막는다. E1·E2 블록은 그대로 둔다.
- `tools/lint-boundaries.test.ts`에 `apps/web/src/mapEditor/validate.ts`의 허용 1건, 같은 파일의 본 경로 import 거부, `apps/web/src/main/WorldMap.tsx`와 `apps/web/src/battleSim/request.ts`의 같은 import 거부를 더한다.
- 하위 경로를 만드는 쪽이 브라우저 안전 범위를 함께 지키도록 E3 블록과 시험은 T4-76 구현 PR에서 소유 조율 뒤 더한다. 기존 root 경로의 동작·로더·schema는 바꾸지 않는다.
