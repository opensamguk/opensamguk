## 0. 이 문서의 위치

운영자가 게시한 자원 판(T4-78)을 새 월드를 만들 때 고르는 몫이다. 고를 수 있는 것은 다섯 종류 모두다. 대기열 행 이름이 지도·시나리오인 것은 운영자가 주로 바꾸는 두 가지라서다. 병종·능력치 규칙·초상 대응표 판도 같은 규칙으로 고른다. AC-P2-27의 게시한 판은 새 월드를 만들 때 고를 수 있다와 진행 중인 월드는 영향받지 않는다를 이 작업이 PostgreSQL로 증명한다.

키 규칙과 게시 판의 불변은 [T4-78 2.1](./T4-78.md#21-판의-상태와-키)을 따른다. 카탈로그에서 판을 읽는 함수는 T4-77이 `apps/engine/src/world/resources.ts`를 DB 읽기로 바꾼 결과를 쓴다. 맞출 점은 6절 쟁점 표에 둔다.

## 계획 (Claude)

### 목표

`pnpm world:create`와 관리자 월드 생성 요청이 다섯 종류의 게시 판을 키로 받아 월드를 만든다. 초안이나 없는 판, 서로 맞지 않는 조합(시나리오가 다른 지도 판을 가리킴, 시나리오가 쓰는 병종이 없음)은 이유와 함께 거부하고 월드 행을 만들지 않는다. 같은 키와 시드면 같은 초기 상태 해시가 나온다. 판 번호 1의 키(`che`, `1030`, `basic`)로 만든 월드는 지금과 상태 해시·`resourceHash`가 같다. 새 판을 게시하거나 새 판으로 월드를 만들어도 이미 있는 월드의 행과 재생 결과는 그대로다.

## 1. 지금 코드 (main `3e5b52a`)

- 명령줄은 `--preset`, `--scenario`, `--map`, `--seed`, `--turn-term`, `--end-year`, `--name`을 받는다(`apps/engine/src/cli/createWorld.ts:7-18`). 프리셋이 있으면 시나리오·지도·턴 간격의 기본값이 되고 명령줄 값이 이긴다(`:25-28`). 병종은 프리셋에서만 오고(`:34`) 없으면 `basic`이다(`apps/engine/src/world/resources.ts:23`). 능력치 규칙(`scenario/default.json`)과 초상 대응표(`portraits/rtk14-map.json`)는 고정 파일이다(`resources.ts:24-25`).
- 키 검사는 `^[a-zA-Z0-9_-]+$`이다(`resources.ts:6-9`, 프리셋도 `preset.ts:5`). `@`가 든 판 키는 지금 거부된다.
- 월드의 키는 명령줄 인자가 아니라 자원 내용의 `id`에서 온다. `buildInitialWorld`가 `scenarioKey: scenario.id`, `mapKey: map.id`, `unitSetKey: unitSet.id`를 돌려준다(`packages/rules/src/world/bootstrap.ts:264-266`). 그래서 `che`를 복제한 판의 내용 `id`가 `che`로 남아 있으면 지금 경로로는 새 판으로 만든 월드도 `mapKey = che`가 된다.
- 저장은 `saveInitialWorld`가 한 트랜잭션으로 `World`와 도시·국가·장수·외교 행을 만든다(`apps/engine/src/world/persistence.ts:34-93`). `World`에는 `scenarioKey`·`mapKey`·`unitSetKey` 열과 능력치 규칙·병종 내용 사본(`statRules`·`unitSet`)이 있다(`packages/db/prisma/schema.prisma:12-36`). 능력치 규칙과 초상 대응표의 키는 어디에도 남지 않는다.
- 재생 기록은 초기 상태 전체(`initial`)를 담고 `resourceHash`는 세 키와 `statRules`·`unitSet` 내용으로 만든다(`persistence.ts:48-59`, `replay.ts:51-59`). 자원 파일을 다시 읽지 않는다. 그래서 키가 같고 내용이 같으면 해시가 같다.
- 진행 중인 월드의 지도는 `City` 행이다(`schema.prisma:125`). 서버 지도 조회도 이 행을 읽는다. 월드를 만든 뒤에는 자원을 다시 읽는 경로가 없다.
- 시뮬레이터와 처리량 측정은 이름만 쓴다(`tools/sim/cli.ts:42` `map: 'che'`, `tools/season-throughput.ts:14`). 2.1 규칙으로 1판이 되어 바뀌지 않는다.
- T3-05 계획의 관리자 생성 요청은 `{ idempotencyKey, name, scenarioKey, mapKey, presetKey?, seed?, turnTermMinutes? }`이고 `WorldCreateRequest`에 같은 칸을 저장한 뒤 실행기가 기존 생성 함수로 만든다([T3-05 API 계약](./T3-05.md#api-계약)). 아직 main에 없다.

## 2. 계약

### 2.1 판 키

- 키 형식과 정규형은 T4-78 2.1이다. 판 번호 1은 이름만(`che`), 2 이상은 `<이름>@<번호>`(`che@2`). `che@1`도 받아 `che`로 바꾼다.
- 엔진의 키 검사를 `^[a-zA-Z0-9_-]{1,40}(@[1-9][0-9]{0,8})?$`로 넓힌다. 프리셋 키 검사는 그대로 둔다.
- 이름만 쓰면 늘 1판이다. 가장 최근 판을 고르는 별칭은 두지 않는다. 같은 명령이 날짜에 따라 다른 월드를 만들지 않게 하려는 것이다.
- 게시 판만 받는다. 초안이면 `초안은 월드 생성에 쓸 수 없습니다: <종류> <키>`, 없으면 `게시한 판이 없습니다: <종류> <키>`로 실패한다.

### 2.2 다섯 판을 정하는 순서

| 종류 | 정하는 값 (앞이 이긴다) |
| ---- | ----------------------- |
| 시나리오 | `--scenario`, 프리셋 `scenario`. 없으면 실패 (지금과 같다) |
| 지도 | `--map`, 시나리오를 프리셋에서 가져왔으면 프리셋 `map`, 고른 시나리오 판의 `mapKey` |
| 병종 | `--unit-set`, 프리셋 `unitSet`, `basic` |
| 능력치 규칙 | `--stat-rules`, 내장 능력치 규칙 판 이름 (T4-77이 붙인 이름, 6절 Q-02) |
| 초상 대응표 | `--portraits`, 내장 초상 대응표 판 이름 (같음) |

- 시나리오와 지도의 짝: 정한 지도 키가 시나리오 판의 `mapKey`와 정규형으로 같아야 한다. 다르면 `시나리오 <키>는 지도 <키>와 함께 씁니다. --map을 빼거나 <키>로 고치세요.`로 실패한다. 명령줄에서 `--scenario 1030@2`만 주고 프리셋 지도가 `che`여도 프리셋 지도는 쓰지 않고 시나리오의 짝을 쓴다. 그래서 프리셋과 새 시나리오 판을 함께 쓸 때 `--map`을 따로 줄 필요가 없다.
- 지금 쓰는 명령(`--scenario 1030 --map che`, `--preset beginner`)은 2.1 규칙으로 모두 1판이 되고 `1030`의 `mapKey`가 `che`라서 결과가 지금과 같다.

### 2.3 조합 검사와 키 덮기

1. 다섯 판을 카탈로그에서 읽는다. 게시 판은 바뀌지 않으므로 잠금은 두지 않는다.
2. T4-76의 검증 함수로 조합을 다시 본다. 시나리오와 지도 짝(게시 때 이미 본 것이지만 판 다섯을 한자리에서 다시 본다)과 시나리오가 쓰는 병종이 고른 병종 판에 모두 있는지다. 하나라도 걸리면 `월드를 만들 수 없는 조합입니다.` 아래에 코드와 문구를 줄마다 적고 실패한다. 월드 행은 생기지 않는다.
3. `buildInitialWorld`에 다섯 내용을 넘긴다(지금 `resources.ts:27`과 같다).
4. 돌려받은 상태의 `mapKey`·`scenarioKey`·`unitSetKey`를 2.1 정규형의 카탈로그 키로 덮는다. 내용의 `id`가 아니라 카탈로그 키가 월드의 키다. 1판은 정규형이 이름이고 내장 판의 내용 `id`도 같은 이름이라 덮어도 값이 바뀌지 않는다. 그래서 지금 월드와 해시가 같다.
5. 덮은 상태로 `saveInitialWorld`를 부른다. 상태 해시와 `resourceHash`는 덮은 키로 계산된다. 새 판으로 만든 월드는 키가 달라 `resourceHash`도 달라진다.

키 덮기는 엔진의 판 읽기 함수 안에서 한다. 시뮬레이터, E2E 준비, 처리량 측정도 같은 함수를 쓰므로 모두 같은 규칙을 받는다(C-M1b).

### 2.4 월드에 남기는 것

| 열 | 값 | 기존 월드 |
| -- | -- | --------- |
| `World.scenarioKey`, `mapKey`, `unitSetKey` (있음) | 2.3의 정규형 키 | 그대로 |
| `World.statRulesKey String?` (새로) | 고른 능력치 규칙 판의 정규형 키 | `null`. 내장 1판으로 읽는다 |
| `World.portraitMapKey String?` (새로) | 고른 초상 대응표 판의 정규형 키 | `null`. 내장 1판으로 읽는다 |

- 새 두 열은 재생 기록(`replayOrigin`)과 `resourceHash`에 넣지 않는다. 능력치 규칙 내용은 이미 `World.statRules`와 `initial.statRules`에 있고 초상은 장수 행의 `portraitId`로 이미 들어가 있다. 두 열은 어느 판으로 만들었는지 사람이 보는 출처다.
- 기존 행은 채우지 않는다(백필 없음). `null`의 뜻은 data-model.md에 적는다.
- 이 열을 T4-77이 만들면 이 작업은 채우기만 한다(6절 Q-01).

### 2.5 명령줄

```sh
pnpm world:create [--preset <키>] [--scenario <판 키>] [--map <판 키>] [--unit-set <판 키>] \
  [--stat-rules <판 키>] [--portraits <판 키>] --seed <문자열> --turn-term <분> --end-year <연도> --name <이름>
# 예: 새 판으로 만들기
pnpm world:create --preset regular --scenario 1030@2 --seed s1 --end-year 300 --name 군웅할거2
```

- 성공하면 지금처럼 `{ worldId, stateHash }`를 출력하고 다섯 키를 더한다: `{ worldId, stateHash, resources: { scenario, map, unitSet, statRules, portraitMap } }`.
- 실패하면 종료 코드 1이고 이유 한 줄(조합 검사는 여러 줄)을 출력한다. 지금처럼 DB 연결 전에 할 수 있는 검사(필수 인자, 키 형식)를 먼저 한다.
- T3-05가 명령줄 생성에 감사 행(`actorKind = CLI`, `world.create`)을 쓰게 하면 그 `payload`에 `resources`(다섯 정규형 키)와 `contentHashes`(다섯 정규 해시)를 넣는다.

### 2.6 관리자 생성 요청 (PR 2, T3-05 뒤)

T3-05 `admin.world.create` 입력을 아래처럼 넓힌다. 결과 모양과 비동기 흐름(`PENDING` → `DONE`·`FAILED`)은 T3-05 그대로다.

```ts
admin.world.create({
  idempotencyKey, name, presetKey?, seed?, turnTermMinutes?,
  scenarioKey?, mapKey?, unitSetKey?, statRulesKey?, portraitMapKey?, // 모두 판 키 (2.1)
}) → { requestId }
```

- 다섯 키와 프리셋의 관계는 2.2 표와 같다. `scenarioKey`와 `presetKey`가 둘 다 없으면 `BAD_REQUEST`다. T3-05의 `mapKey` 필수는 선택으로 바꾼다. 시나리오의 짝으로 정해지기 때문이다.
- API는 요청을 받을 때 키 형식을 보고, 정한 다섯 키가 모두 게시 판인지와 시나리오·지도 짝을 카탈로그에서 읽어 본다. 걸리면 `BAD_REQUEST`이고 요청 행과 감사 행을 쓰지 않는다. 문구는 2.1·2.2와 같다. 카탈로그 읽기는 게임 상태가 아니므로 API가 읽어도 AGENTS §6에 걸리지 않는다.
- `WorldCreateRequest`에 `unitSetKey String?`, `statRulesKey String?`, `portraitMapKey String?`을 더한다. 요청에는 2.2로 정한 정규형 키를 저장한다. 그래서 실행기는 같은 키로 만든다.
- 실행기는 2.3 전체를 다시 한다. 요청을 받은 뒤 바뀔 수 있는 것은 없지만(게시 판 불변) 조합 검사는 실행기만 하므로 거기서 걸리면 요청을 `FAILED`로 닫고 `error`에 2.3의 문구를 남긴다. 감사 행은 T3-05의 `world.create.applied`·`world.create.rejected`이고 `payload`에 2.5와 같은 `resources`·`contentHashes`를 넣는다.
- T3-05의 초기화(`admin.world.reset`)는 새 월드를 만들 때 기존 월드의 다섯 키를 그대로 쓴다. `statRulesKey`·`portraitMapKey`가 `null`인 옛 월드는 내장 1판이다.

## 3. 접근

1. T4-77 병합본의 판 읽기 함수를 읽고 키 해석을 2.1 정규형으로 맞춘다. 게시 판만 받는 조건과 실패 문구를 넣는다.
2. 2.3의 조합 검사와 키 덮기를 판 읽기 함수 안에 넣는다. 돌려주는 값에 고른 다섯 키와 해시를 더한다.
3. `createWorld.ts`에 옵션 셋과 2.2 순서를 넣고 출력에 `resources`를 더한다.
4. `World`의 새 두 열(Q-01)과 `saveInitialWorld`의 인자 둘을 더한다.
5. 4.1의 통합 시험을 쓰고 PR 1을 낸다.
6. T3-05 병합 뒤 2.6을 PR 2로 낸다. 4.2의 HTTP 시험을 더한다.

## 4. 검증

### 4.1 PR 1 (`pnpm test:int`, 전용 PostgreSQL)

시험 DB에는 T4-77의 초기화 SQL로 내장 판을 넣는다. 새 판은 시험 준비에서 T4-78의 `resourceStore` 함수(복제 → 저장 → 게시)로 만든다. API를 거치지 않는 것은 PR 1이 서버를 띄우지 않아서이고 게시 경로 자체의 증거는 T4-78이 낸다.

| 무엇 | 어떻게 |
| ---- | ------ |
| 1판 그대로 | `--scenario 1030 --map che`와 `--scenario 1030@1 --map che@1`, `--preset regular`로 만든 월드의 `initialStateHash`와 `resourceHash`가 이 작업 전 main에서 같은 시드로 만든 값과 같다. 기대값은 시험에 상수로 적고 구현 기록에 출처 커밋을 남긴다. 기존 `createWorld.integration.test.ts`가 고치지 않고 통과한다 |
| 결정성 | 같은 다섯 키와 시드로 두 번 → 같은 `stateHash`. 시드를 바꾸면 다름 |
| 새 판으로 생성 | `che@2`(도시 하나 옮기고 도시 하나 지움, 연결 고침), `1030@2`(`mapKey = che@2`, 지운 도시를 쓰지 않게 고침, 장수 하나 더함), `basic@2`(병종 수치 하나 바꿈), 능력치 규칙 2판(합계 바꿈)을 게시하고 `--scenario 1030@2 --unit-set basic@2 --stat-rules <이름>@2`로 생성 → `World`의 키가 `1030@2`·`che@2`·`basic@2`·`<이름>@2`, 도시 수가 93개, 옮긴 도시 좌표가 새 값, 장수 수가 1 늘어남, `World.unitSet`·`statRules`가 새 판 내용. `resourceHash`가 1판 월드와 다름 |
| 내용 `id`와 무관 | `che@2` 내용의 `id`가 `che` 그대로여도 `World.mapKey = che@2` |
| 진행 중 월드 보존 | 1판으로 월드 W1을 만들고 `world:start` 뒤 엔진 시험 도우미로 12개월을 진행한다. 새 판 넷을 게시하고 새 판으로 월드 W2를 만든다. 그 전후로 W1의 `World`·`City`·`Nation`·`General` 행 해시, `exportReplay` 결과, 12개월 순수 재생 해시가 같다. W1을 엔진이 다시 적재해도 상태 해시가 같다 |
| 기존 재생 고정물 | `apps/engine/test/fixtures/replay-v1-b8f5074.json` 재생 해시가 이 작업 전과 같다 |
| 초안 거부 | `1030`을 복제한 초안의 키로 생성 → `초안은 월드 생성에 쓸 수 없습니다`, `World` 행 수 그대로 |
| 없는 판 | `che@9` → `게시한 판이 없습니다`, 행 수 그대로 |
| 짝 불일치 | `--scenario 1030@2 --map che` → 짝 문구로 실패. `--scenario 1030@2`만 → `che@2`로 성공. `--preset regular --scenario 1030@2` → 프리셋 지도를 쓰지 않고 성공 |
| 병종 조합 | 시나리오가 쓰는 병종을 지운 병종 판을 게시하고 그 판으로 생성 → T4-76 병종 코드로 실패, 행 수 그대로 |
| 키 형식 | `che@0`, `che@`, `@2`, `che@2@3`, 41자 이름 → DB 연결 전 형식 오류 |
| 출처 열 | 새 판 월드의 `statRulesKey`·`portraitMapKey`가 고른 키. 이 작업 전에 만든 월드는 `null` |
| 시뮬레이터 | `pnpm sim --seeds 10` 결과 해시가 이 작업 전과 같다 (이름만 쓰는 경로) |

### 4.2 PR 2 (`pnpm test:int`, `pnpm test:authz`)

`admin.world.create`는 T3-05가 이미 권한 다섯 범주 증거를 낸 절차다. 이 작업은 입력만 넓히므로 그 증거를 다시 돌려 통과를 확인하고 아래를 더한다.

| 무엇 | 어떻게 |
| ---- | ------ |
| 새 판 요청 | 관리자가 `scenarioKey: '1030@2'`로 요청 → `WorldCreateRequest`에 다섯 정규형 키, 실행기 뒤 `DONE`과 4.1의 새 판 생성과 같은 월드 |
| 요청 때 거부 | 초안 키, 없는 판, 짝 불일치 → `BAD_REQUEST`, `WorldCreateRequest`·`AuditLog` 행 수 그대로 |
| 실행 때 거부 | 병종 조합이 맞지 않는 요청 → 요청은 받고 실행기가 `FAILED`, `error`에 조합 문구, `world.create.rejected` 감사 행, `World` 행 없음 |
| 감사 내용 | `world.create.applied`의 `payload.resources`와 `contentHashes`가 실제 판과 같음 |
| 잘못된 입력 | 관리자 계정이 `mapKey: 'che@0'`, 모르는 칸 → `BAD_REQUEST` (권한 대조 `invalidInput`) |
| 초기화 | `statRulesKey`가 있는 월드를 T3-05 초기화 → 새 월드의 다섯 키가 같음 |

### 4.3 증거로 인정되는 것

`pnpm check`, `pnpm test:int`(skip 0), PR 2의 `pnpm test:authz` `missing=0`, `pnpm sim --seeds 10`의 결과 해시 비교, `pnpm lint:text --strict apps/engine/src apps/server/src docs`, 정확한 SHA의 CI다. 판 읽기 mock, 카탈로그 없이 JSON 고정물로 대신한 시험은 증거가 아니다. 화면에서 판을 골라 월드를 만드는 E2E는 T4-87이 낸다.

## 8. 상대 영역에 필요한 것

- T4-87·T3-06(Claude 화면): 관리자 월드 생성 양식은 시나리오 판을 고르면 지도 칸을 그 시나리오의 `mapKey`로 채우고 바꾸지 못하게 한다(U-T79-2 기본값). 다섯 칸의 목록은 `resourceAdmin.list({ kind, status: 'PUBLISHED' })`, 보이는 값은 `meta.key`다. 요청 거부 문구는 `BAD_REQUEST`의 `message`를 그대로 보인다. 실행 실패는 T3-05 `admin.world.createStatus`의 `error`다.
- T4-87 E2E: 새 판을 게시하고 그 판으로 월드를 만든 뒤 기존 월드의 지도·장수 화면이 그대로인지 본다(map-editor §6 자원 편집 행).
- T4-85(Codex): 월드별 능력치 규칙 판 조회가 키를 낸다면 `World.statRulesKey`를 쓰고 `null`이면 내장 1판 키를 낸다.
