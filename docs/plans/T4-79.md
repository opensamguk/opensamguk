## 3. 실행 계획 (한 PR, Codex)

### 3.1 판 키의 단일 원본 (rules)

`packages/rules` 안 새 파일 하나(위치는 구현자)에 순수 함수·스키마를 둔다. rules는 server를 import하지 않는다.

- 새 이름 입력의 `resourceNameSchema`는 영문·숫자·밑줄·하이픈 1..40자로 기존 복제 입력·목록 필터와 같다. 기존 카탈로그와 월드 키에는 길이 제한이 없으므로 판 키 해석·출처 검사는 기존 긴 이름을 허용한다. 실제 central CLI 고정물의 이름도 42자다.
- `RESOURCE_VERSION_MAX = 2_147_483_647`.
- `parseResourceKey(key) → { name, version }`: 형식 `^([A-Za-z0-9_-]+)(?:@([1-9][0-9]{0,9}))?$`, 판 숫자는 `Number(...) <= 2147483647`. `@` 없으면 1판. 정규식 결과 전체가 입력과 같아야 하며 마지막 줄바꿈도 거부한다. 오류는 throw. 거부 예: `che@0`, `che@01`, `che@`, `@2`, `che@2@3`, `che@2147483648`, `che@12345678901`. 새 이름 입력에서만 41자 이상을 거부한다.
- `formatResourceKey({ name, version })`: `version === 1`이면 `name`, 아니면 `name@version`. 입력도 같은 범위로 검사한다.
- `resourceKeySchema`(zod): 파싱 후 `formatResourceKey`로 정규형 문자열 변환. 그래서 `che@1` → `che`.
- 파일 키는 분리한다: `presetKey`·`featureProfileKey`와 `preset/<key>.json`·`feature-profile/<key>.json` 경로는 지금 정규식(`createRequest.ts:15` `key`) 그대로다.
- 서버 `resourceAdmin/read.ts:9-13`의 `resourceName`은 rules의 `resourceNameSchema`를 다시 내보내는 한 줄로 바꾼다(값이 같아 동작 변화 없음, 사실 하나를 한 곳에 둔다). `packages/db/src/gameResources.ts`의 이름 검사는 그대로 둔다.
- 호출처: 엔진 `resources.ts`의 `resourceKey`, rules `createRequest.ts` 자원 다섯 칸, `resetPreparation.ts` `selectionSchema`, rules `reset.ts` 설정 세 키.
- 기존 생성 키에는 길이 상한이 없다. 정적 파일 이름뿐 아니라 42자 동적 CLI 고정물도 대조했으며 새 이름 입력만40자로 제한하고 기존 키는 보존한다.

### 3.2 선택 해석

- `resolveWorldResourceSelection`은 다섯 칸을 정규형으로 돌려준다. 기본값 판정 `options.map === 'san10'`은 `parseResourceKey(map).name === 'san10'`. 기본값은 모두 1판 이름이다.
- 1판 결과 문자열이 지금과 같아 기존 intent·resolution·초기화 비교·해시가 바뀌지 않는다.

### 3.3 DB 경로와 월드 키

1. `readInitialResources`는 칸마다 `parseResourceKey`로 `{kind,name,version}`을 만들어 `readPublishedResources`에 넘긴다. 초안·없는 판은 지금처럼 `게시 자원이 없습니다`.
2. `composeInitialWorld`의 `version !== 1` 거부를 지운다. `content.id === name` 검사는 유지한다(같은 이름 다음 판은 `id`가 이름, 새 이름 복제는 `store.ts:131`이 `id`를 새 이름으로 바꾼다).
3. `validateInitialPair` → `buildInitialWorld` 그대로. 맞지 않는 조합은 여기서 실패하고 월드 행이 생기지 않는다.
4. 결과 `WorldInit`의 세 키를 `formatResourceKey(ref)`로 덮는다. 1판은 `name === content.id`라 값이 같고 상태 해시·`resourceHash`·재생이 바이트 단위로 같다. 2판 이상은 `World` 세 열과 재생 원본 `initial`이 `che@2`를 담아 별도 DB 없이 재생 원본만으로 판이 구분된다.

선택 이유: `World` 키 열은 이미 월드의 자원 신원이고 재생·초기화가 이 값을 비교한다. 새 열을 두면 같은 사실이 두 곳에 생기고 재생 원본에는 여전히 판이 없다.

### 3.4 출처 보존 (새 열 없음)

- 요청 생성: `resolution.selection`은 정규형, `resolution.resources`는 실제 `{kind,name,version,contentHash}`. `resolution.version`·intent `version`은 1 유지. 1판 요청의 intent·resolution 바이트는 같다.
- CLI 생성: `--published`일 때만 `createWorldFromCli` 감사 `payload`를 `{ stateHash, resources }`로 넓힌다. `resources`는 실제 다섯 ref를 종류순으로 정렬한 `{kind,name,version,contentHash}` 배열(`adminResetResourcesSchema`와 같은 모양). 파일 경로는 `payload: { stateHash }` 그대로. 감사 행은 월드와 같은 트랜잭션이다.
- 능력치 규칙·초상 대응표 판은 `World` 열에 두지 않는다. 요청 월드는 resolution, CLI 월드는 감사에 남는다. `World` 새 열은 필요 없다.

### 3.5 CLI

- `--unit-set <판 키>` 추가. 우선순위 `--unit-set` > 프리셋 `unitSet` > `basic`.
- `--published`: 다섯 칸 모두 판 키를 받는다.
- 파일 경로: `name@1`은 `name`으로 받고 `@N`(N≥2)은 DB 연결 전에 `파일 자원은 1판만 있습니다. --published를 쓰세요.`로 끝낸다. 파일 경로 결과·해시는 바뀌지 않는다.
- 도움말에 `--unit-set`과 판 키 형식 한 줄. 출력 JSON 모양은 그대로.

### 3.6 관리자 요청 (rules·서버·실행기)

- `requestWorldCreateInput`·`worldCreateIntentSchema` 자원 다섯 칸을 `resourceKeySchema`로. `worldCreateIntent`는 정규형을 저장하므로 `che@1`과 `che`는 같은 `intentHash`, 같은 `idempotencyKey` 재요청은 기존 행. 다른 판(`che@2`)은 다른 hash라 `CONFLICT`. 형식 오류는 zod `BAD_REQUEST`, 요청·감사 행 없음.
- 서버는 카탈로그를 읽어 판정하지 않는다. 판 존재·조합은 실행기 `RESOURCE_INVALID` 하나로 닫는다. 거부 코드를 늘리지 않는다.
- 실행기 `createRequests.ts`는 코드 변경이 거의 없다(3.2·3.3이 판을 처리).
- 확장 설정: 비교를 그대로 둔다. 확장 설정 파일의 `scenarioKey`·`mapKey`(1판 이름)와 정규형 선택이 달라 2판 지도·시나리오와 함께 쓰면 `INPUT_INVALID`. 기존 선택 바인딩 유지다.
- 프리셋의 `scenario`·`map`·`unitSet`은 1판 이름. 요청 칸이 있으면 요청 칸이 이긴다.

### 3.7 공개 로비 제목 (`@N` 해석만)

`lobby.ts` `scenarioTitle`의 첫 줄 정규식을 `parseResourceKey(key)`로 바꾼다(형식 오류·`default`는 지금처럼 `INTERNAL_SERVER_ERROR`).
- `version === 1`(키 = 이름): PR393 동작 그대로. 파일 먼저, `ENOENT`면 게시 1판, 파일 제목만 캐시.
- `version >= 2`: 파일을 읽지 않고 `readPublishedResources(db, [{SCENARIO, name, version}])`. `id === name`(키가 아니라 이름)을 본다. DB 값은 캐시하지 않는다(PR393 규칙 유지). `db`가 없으면 오류.

### 3.8 초기화·재생

- `resetPreparation.ts`: `selectionSchema`는 `resourceKeySchema`. `selectionRefs`(`:337`)와 `verifyResetPreparation`(`:633-635`)은 `formatResourceKey(ref) === World 키`로 비교. `referenceSchema`의 `name`은 이름만이라 그대로, `version`이 1 고정이면 1..2147483647로 넓힌다(`미검증`: `referenceSchema` 정의 줄은 읽지 않았다. `checkedResource`가 이것으로 2판 행을 거부하지 않는지 구현자가 확인).
- rules `reset.ts`: `adminResetResourceSchema`의 `name`은 `resourceNameSchema`, `version`은 `z.number().int().min(1).max(2147483647)`. 설정 세 키는 `resourceKeySchema`. `:128` 비교는 `formatResourceKey(row) !== selected`. 1판 기록의 파싱 결과·해시는 같다.
- CLI 출처(`provenance`, `:253-284`): 요청·초기화 사건이 둘 다 없을 때 `tx.auditLog.findMany({ where: { worldId: world.id, actorKind: 'CLI', action: 'world.create.applied' }, orderBy: { id: 'asc' }, take: 2 })`를 읽는다(`@@index([worldId, at])` 앞열 사용).
  - 0행이거나 1행의 `payload`가 정확히 `{ stateHash }`이면 기존 CLI 월드다. 지금 `{kind:'cli'}` → `legacyResources` 추론을 바꾸지 않는다. 다만 이 경로에서 `World` 세 키 중 판이 2 이상인 것이 있으면 `PROVENANCE_INVALID`(새 판 월드를 1판 추론으로 숨기지 않는다).
  - 1행의 `payload`에 `resources`가 있으면 새 CLI 출처다. `z.strictObject({ stateHash: hash, resources: adminResetResourcesSchema })` 파싱, `targetType === 'World'`, `targetId === world.id`, `stateHash === world.initialStateHash`(`미검증`: `savePreparedInitialWorld` 반환 `stateHash`가 `World.initialStateHash`와 같은 값인지 구현자가 확인), MAP·SCENARIO·UNIT_SET의 `formatResourceKey(ref)`가 `World` 세 키와 같음. 하나라도 어긋나거나 2행 이상, 또는 `payload`가 두 모양 어디에도 맞지 않으면 `PROVENANCE_INVALID`. 레거시로 떨어지지 않는다.
  - 통과하면 요청 출처와 같은 길로 `resourcesByRefs`(정확한 판·`contentHash`)와 `originalPrepared`(원생성 상태 해시 재현)를 탄다. 이 두 단계의 실패 코드는 요청 출처와 같다(`RESOURCE_INVALID`).
  - 증거 `provenance`는 `{kind:'cli'}`, `provenanceFingerprint = hashState(refs)`로 형태를 바꾸지 않는다.
- `legacyResources`의 능력치·초상 후보를 모든 판으로 넓히지 않는다. 넓히면 기존 CLI 월드에 새 판 게시만으로 `RESOURCE_AMBIGUOUS`가 생긴다.
- 재생: `replayOrigin`·`resourceHash` 계산식과 형식은 바꾸지 않는다. 1판 월드의 원본 바이트·해시는 같고 2판 월드는 `initial`의 정규형 키와 내용만으로 재생된다(별도 DB 없음).

### 3.9 생성용 게시 판 쪽 목록 (T4-90 입력, 새 관리자 query 하나)

`creationOptions`의 입력·응답·`revision`·권한 대조·고정 프로필 계약은 바꾸지 않는다. 대신 새 query 하나를 둔다.

```ts
// apps/server/src/admin/worldCreateOptions.ts
export const creationVersionsInput = z.strictObject({
  expectedUserId: /* creationOptionsInput.expectedUserId와 같은 스키마 */,
  kind: z.enum(['MAP', 'SCENARIO', 'UNIT_SET', 'STAT_RULES', 'PORTRAIT_MAP']),
  cursor: z.string().min(1).max(200).optional(),
});
// apps/server/src/routers/admin.ts  world 라우터
creationVersions: adminProcedure.input(creationVersionsInput).query(({ ctx, input }) => getWorldCreationVersions(ctx, input))
// 응답
{ items: Array<{ key: string; name: string; version: number; contentHash: string }>; next: string | null }
```

- 동작: `creationOptions`와 같은 `expectedUserId` 확인(`UNAUTHORIZED`)·`Cache-Control: no-store`·`requireCurrentAdmin(tx, ctx, false)` 뒤 `listResources(tx, { kind, status: 'PUBLISHED', cursor }, RESOURCE_PAYLOAD_LIMITS)`를 그대로 부르고 항목을 `{ key: formatResourceKey(item), name, version, contentHash }`로 줄인다. `next`는 그대로 넘긴다.
- 고정: 한 쪽 최대 50건(기존 `listResources` 상수), cursor는 기존 UUID 기반 `base64url("1:"+id)`, 쪽마다 `next`, 마지막 쪽 `null`, `content` 없음, 순서는 기존 `id COLLATE "C"`(이름·판 순이 아님. 화면이 정렬한다). 기존 `responseMax`로 50건 전에 끊기면 `next`가 이어 준다. 한도·예산은 새로 만들거나 올리지 않는다.
- 잘못된 `kind`·cursor·추가 필드는 `BAD_REQUEST`.
- `ResourceEditorGrant`를 요구하지 않는다. 일반 관리자 읽기다(기존 `listResourceCatalog`는 그대로 편집 권한 필요).
- 판 목록 단계에서 조합을 미리 판정하지 않는다. 판정은 생성 때 실행기가 한다.

## 7. 결정 상태

사용자에게 물을 미결점은 없다. 이전 초안의 쟁점은 다음으로 닫았다.

| ID | 닫은 내용 |
| -- | ---- |
