## 0. 이 문서의 위치

명세 §6 T4-22 행을 파일·타입·검사 순서·반례로 적는다. 장비 목록(카탈로그), 장수별 장착 상태 조각, 장비매매 명령 `equipment_trade`, T4-18 합산 틀에 넣을 장비 효과 제공자다. 저장·조회 API와 등록은 T4-23, 화면은 T4-24가 한다.

원작 장비는 거의 모두 능력치(통솔·무력·지력)를 더한다(§1.2). 그런데 우리 전투 계산은 능력치를 읽지 않는다(`battle/simulate.ts:28-53`). 그래서 원작 장비를 그대로 옮기면 AC-P2-12의 전투 계산 몫이 빈다. 전투에 넣으려면 환산이 필요하다. 이 선택이 U-06·U-19 결정의 중심이다. 이 문서는 어느 쪽이든 받을 수 있는 기술 계약을 두고 선택지를 §3에 모은다. 사용자 결정 전에는 계약 준비로 올리지 않는다.

착수 조건은 넷이다. 이 문서의 G-03 수용, §3 EQ-1~EQ-7의 사용자 결정, AC-P2-12 (나)의 정식 반영, T4-18 병합(완료).

## 2. 계약

### 2.1 카탈로그

```ts
// ext/equipment/catalog.ts
export type EquipSlot = 'horse' | 'weapon' | 'book' | 'item';
export interface EquipmentDef {
  key: string; // 예: 'horse_01'. /^[a-z]+_[0-9]{2}$/
  name: string; // 표시 이름. 예: '노기'
  slot: EquipSlot;
  cost: number; // 금
  requiredSecurity: number; // 도시 치안 요구
  buyable: boolean;
  charges: number | null; // 소모 장비의 횟수. 아니면 null
  effects: readonly EquipmentEffect[];
}
export type EquipmentEffect =
  | { stage: 'domestic.score' | 'battle.dealt' | 'battle.taken'; op: 'add' | 'mul'; value: number; commandKeys?: readonly string[] }
  | { stage: 'general.stat'; stat: 'leadership' | 'strength' | 'intel'; value: number }; // EQ-2 (가)·(다)일 때만
export const equipmentCatalog: readonly EquipmentDef[];
```

- 목록과 수치는 §3 결정 결과를 그대로 적는다. 결정 전 원고에는 매매 가능 능력치 장비 18종의 이름·칸·값·치안 요구만 원작대로 적고 `effects`는 비운다.
- key는 우리 이름이다. 원작 key(`che_명마_01_노기`)를 출처 주석에 함께 적는다.
- 카탈로그는 순수 상수다. DB·파일을 읽지 않는다. 모듈을 읽을 때 key 중복, 칸·값·치안의 음수, `effects`의 유한하지 않은 값을 검사해 예외를 낸다.

### 2.2 상태 조각 `equipment`

```ts
// ext/equipment/state.ts
// interface와 선택 칸(Partial)은 JsonValue(model/world.ts:4)에 할당되지 않으므로 type alias와 index signature로 쓴다.
export type EquippedItem = { key: string; charges: number | null };
export type EquipmentSlice = {
  generals: { [generalId: string]: { [slot: string]: EquippedItem } }; // 장수 key는 10진 문자열, 칸 key는 EquipSlot 넷 중 하나(validate). 장비가 없는 장수는 key가 없다
};
export const equipmentSlice: ExtSlice<EquipmentSlice>;
```

- 형식 제약: `ExtSlice<T extends JsonValue>`(`commands/ext/state.ts:5-10`)를 만족하도록 중첩 값까지 `type` 별칭이다. 칸 key를 `EquipSlot`으로 좁히는 일은 타입이 아니라 `validate`가 한다. 구현 PR은 `as`나 `any` 없이 선언하고 `const check: JsonValue = {} as EquipmentSlice;` 컴파일 시험 한 줄을 둔다. 카탈로그 `EquipmentDef`는 조각 값이 아니라 rules 상수라 이 제약을 받지 않는다.

- `create`는 `{ generals: {} }`다. 시작할 때 누구도 장비가 없다.
- `validate`: 장수 key가 양의 정수 문자열, 칸 key가 넷 중 하나, 장비 key가 카탈로그에 있고 그 장비의 칸과 같음, `charges`가 카탈로그의 소모 여부와 맞음(소모 장비면 1 이상의 정수, 아니면 null), 장비가 하나도 없는 장수 객체는 없음.
- `clone`은 깊은 복제이며 장수 key 오름차순, 칸은 `horse`·`weapon`·`book`·`item` 순으로 다시 만든다.
- 장수가 월드에서 사라지는 경로는 지금 없다. 장비는 국가를 떠나도 장수에게 남는다(원작과 같다).

### 2.3 장비매매 명령 `equipment_trade`

| 항목 | 값 |
| ---- | -- |
| key·이름·분류 | `equipment_trade`, `장비매매`, `personal`, 대상 `general` |
| 인자 | `z.strictObject({ slot: z.enum(['horse','weapon','book','item']), itemKey: z.string().regex(...).nullable() })`. `null`이면 판매 |
| 상태 조각 | `equipment` (T4-23이 `extCommandBindings`에 등록) |
| 난수 | 쓰지 않는다 |

인자 해석(`args`의 `superRefine`): 구매 key는 카탈로그에 있고 그 칸 장비이며 `buyable`이어야 한다. 아니면 `BAD_ARGS`. 원작 `parseArgs`(`che_장비매매.ts:69-90`)와 같다.

검사 순서:

1. 장수 없음 `NO_ACTOR`.
2. 장소 (EQ-5). 원고는 군량매매와 같은 `ownCity`(국가 소속, 자기 국가 도시, 보급)다. 실패 코드도 `ownCity`의 것이다.
3. 구매일 때 도시 치안 < 요구치 `BAD_STATE` `치안이 부족합니다.` 원작 `reqCityCapacity('security', …)`와 같은 뜻이다.
4. 구매일 때 장수 금 < 값 `NO_GOLD`.
5. 판매일 때 그 칸이 비어 있음 `BAD_STATE` `팔 장비가 없습니다.`
6. 구매일 때 그 칸에 같은 장비 `BAD_STATE` `이미 가지고 있습니다.`, 그 칸 장비가 비매품 `BAD_STATE` `이미 진귀한 것을 가지고 있습니다.`

실행:

- 구매: 금 −값, 그 칸에 새 장비(소모 장비면 `charges`를 카탈로그 값으로). 이전 장비는 돌려받지 않는다(원작 `inventory.ts:204-207`). EQ-4에서 다르게 정하면 그대로 따른다.
- 판매: 금 +⌊값/2⌋, 칸을 비운다. 장수 객체에 남은 칸이 없으면 객체를 지운다.
- 경험 +10 (EQ-6).
- 로그 한 줄: `노기를 샀습니다.` 또는 `노기를 팔았습니다.` 문구는 구현 PR이 정한다.

등록 전 시험 경로: `defineCommand.execute`는 운영 등록을 쓰는 `cloneWorld`를 부르므로(`commands/support.ts:53`, `model/clone.ts:6-8`) 운영 `extSlices`에 `equipment`가 없는 동안에는 `ext.equipment`가 든 상태에서 예외가 난다. 그래서 명령 파일은 검사 `checkTrade(view, actor, args)`와 이미 복제된 상태를 바꾸는 `applyTrade(state, actor, args)`를 따로 내고 `defineCommand`의 `check`·`change`는 이 둘을 부르기만 한다. 이 작업의 시험은 `checkTrade`(복제 없음)와 `cloneWorldWithRegistry`로 시험용 등록을 넘겨 만든 상태 위의 `applyTrade`를 본다. `execute`·resolver·엔진 경로의 성공·실패 시험은 운영 등록과 함께 T4-23이 낸다.


- `view.ext?.equipment`가 없으면 빈 배열이다(T4-18 P3). 끈 월드와 장비 없는 장수는 늘 빈 배열이라 무수정자 경로를 지난다.
- 장착 장비의 `effects` 가운데 지금 단계(`context.stage`)와 `commandKey`가 맞는 것만 `Modifier`로 낸다. `source`는 `equipment:<장비 key>`다. 한 장수가 같은 장비를 두 칸에 가질 수 없으므로 `(source, op)` 중복이 생기지 않는다.
- T4-18 P1~P4를 지킨다. 난수를 쓰지 않고 `view`를 바꾸지 않으며 명령 정의를 import하지 않는다.
- `modifiers/providers.ts`에 한 줄 등록한다. 순서는 T4-18 → T4-22 → T4-25이며 특기 제공자(T4-25)보다 앞이다. 합산 순서는 T4-18 2.2가 `source` 순으로 정하므로 등록 순서는 결과를 바꾸지 않는다.

### 2.5 소모 장비

EQ-1에서 도구를 넣기로 할 때만 쓴다. 소모 장비는 효과가 들어간 계산 한 번마다 `charges`를 1 줄이고 0이면 칸을 비운다. 제공자는 순수 읽기라 줄이지 못하므로 줄이는 일은 효과를 쓴 명령의 실행 안에서 해야 한다. 그 자리는 출병·계략·턴 전 처리 등 효과마다 다르다. 원고는 소모 장비를 첫 범위에서 빼는 안(EQ-1 (가))이며 넣기로 하면 이 절을 효과별 삽입 위치까지 다시 쓴다.

### 2.6 능력치 단계 (EQ-2 (가)·(다)일 때만)

원작처럼 능력치를 더하려면 T4-18 2.6에 따라 단계를 더한다. 지금 `ModifierContext`는 `stage`와 `commandKey`만 가지고(`modifiers/index.ts:11-14`) 능력치 구분 칸이 없다. 단계 하나(`general.stat`)로는 명마의 통솔 보정과 무기의 무력 보정을 제공자가 가를 수 없다. 그래서 능력치마다 단계를 따로 둔다. 문맥 칸을 늘리지 않으므로 T4-18 2.6의 단계 추가 규칙 안에 든다.

- `ModifierStage`에 `general.stat.leadership`, `general.stat.strength`, `general.stat.intel` 셋을 더한다. 카탈로그 `effects`의 `{ stage: 'general.stat'; stat }`은 제공자가 `general.stat.<stat>` 단계로 바꿔 낸다. 그 단계와 다른 능력치의 효과는 내지 않는다.
- 함수 `effectiveStat(view, generalId, stat, commandKey)`가 `applyModifiers(base, collectModifiers(view, generalId, { stage: \`general.stat.${stat}\`, commandKey }), { min: 0 })`를 낸다. `commandKey`는 그 능력치를 읽는 명령 key(투자 8종의 key, `recruit`·`conscript`, 계략 key)이고 카탈로그의 `commandKeys`로 효과를 명령별로 좁힐 수 있다. 정수로 반올림하지 않는다. 능력치 상한 100은 두지 않는다(원작도 장비로 100을 넘긴다).
- 삽입 위치는 능력치를 읽는 명령 계산뿐이다. 내정 점수(`investment.ts:96`의 `general[spec.stat]`), 징병 상한(`military.ts:20`), 계략 확률(`stratagem/base.ts:40` 근처). NPC 판단(`npc/index.ts:116`)과 순위(`ranking.ts:58-60`)는 바꾸지 않는다. NPC가 장비를 고르지 않고(C11) 순위는 장수 본래 값을 보이는 것이 맞기 때문이다.
- 계략 파일은 T4-05 소유다. 이 단계를 넣으면 T4-05 병합 뒤 그 파일에 한 줄을 더하고 T4-05 골든이 그대로인지 확인한다.
- 무수정자 골든은 T4-18 V1(투자 8종 48건), 징병 골든, T4-05 골든이다.
- 능력치별 격리 시험(4.1 S6): 투자 8종이 쓰는 능력치는 통솔이 정착 장려·주민 선정, 무력이 치안 강화·수비 강화·성벽 보수, 지력이 농지 개간·상업 투자·기술 연구다(`commands/domestic/investment.ts:16-38`). 명마(통솔 +N)만 단 장수는 정착 장려와 주민 선정 두 점수가 모두 바뀌고 나머지 여섯은 무수정자와 같다. 무기(무력 +N)는 치안·수비·성벽 셋만, 서적(지력 +N)은 농업·상업·기술 셋만 바꾼다. 각 경우 바뀐 점수가 `effectiveStat` 값으로 다시 계산한 기대값과 같은지 본다. 셋을 함께 단 장수에서 각 능력치 단계의 수정자 목록에 다른 칸 장비가 섞이지 않는다.

EQ-2 (나)이면 이 절 전체를 하지 않는다.

## 4. 시험과 증거

모두 `packages/rules` 단위 시험이다. 시험 상태는 `packages/rules/test/commandFixture.ts`에 `ext.equipment`를 넣고 T4-02 `*WithRegistry`로 시험용 등록을 넘겨 만든다.

등록 전에 돌릴 수 있는 경로만 쓴다. `cloneWorld`를 부르는 경로(`defineCommand.execute`, `applyEffects`, `createAttackWithProviders`의 출병 실행)는 운영 등록에 `equipment`가 없어 예외를 내기 때문이다.

- 매매: §2.3의 `checkTrade`와 시험용 등록 복제 위의 `applyTrade`.
- 내정 효과: `makeInvestmentWithProviders(spec, [equipmentModifierProvider]).execute`. 투자 실행은 효과 목록만 내고 상태를 복제하지 않는다(`commands/domestic/investment.ts:90-123`).
- 전투 효과: `collectModifiersWith([equipmentModifierProvider], view, id, context)`로 모은 수정자를 `simulateBattle`에 직접 넘긴다. 출병 명령 전체(`attack.ts`는 `defineCommand`를 쓴다)를 지나는 시험은 T4-23이 운영 등록 뒤 엔진 통합으로 낸다.

### 4.0 켠·끈 월드 비교 규칙 (CMP)

T4-19~T4-29의 시험이 서로 다른 두 월드나 두 실행을 비교할 때 이 절 하나를 따른다. 시험 칸은 어느 종류인지만 적고 이 절을 가리킨다.

| 종류 | 언제 | 비교하는 것 | 지우는 것 |
| ---- | ---- | ----------- | --------- |
| CMP-A 같은 입력 전후 | 같은 시험 입력을 기준 SHA(구현 전)와 구현 SHA에서 돌린다 | 결과 직렬화 SHA-256, 적용 상태 SHA-256, 난수 호출 수, 다음 난수값을 그대로 | 없음 |
| CMP-B 기능 켬·끔 | 한쪽만 규칙 기능이나 확장 조각을 켰고 그 기능이 아무 효과를 내지 않아야 하는 사례 | 아래 정규화를 거친 결과 SHA·적용 상태 SHA·엔진 상태 해시, 그리고 난수 호출 수·다음 난수값 | 월드 상태 객체의 최상위 `ext`, `ruleFeatures` 두 키 |
| CMP-C 형식 1 ↔ 형식 3 | 같은 입력을 `replayFormat: 1` 월드와 규칙 기능 없는 형식 3 월드에서 돌린다 | 상태 해시, `initialStateHash`, `resourceHash` | 없음(기능 없는 형식 3 상태에는 두 키가 없다). origin·archive 바이트는 비교하지 않는다 |
| CMP-D 같은 형식·같은 기능 전후 | 같은 형식과 같은 기능 목록의 기록을 이 변경 전 기준 파일과 비교한다 | origin·archive 바이트, 두 해시 | 없음 |

CMP-B 정규화는 이렇게 한다. 전제가 둘 있다. 비교하는 두 상태는 지울 두 키 말고는 깊게 같아야 한다(같은 고정 상태에서 기능 목록이나 조각만 더한다. 장수 `special` 같은 다른 칸이 다르면 CMP-B를 쓰지 않는다). 그리고 그 상태를 만들고 실행하는 경로가 그 작업 시점에 실제로 돈다(확장 조각이 든 상태를 복제하는 경로는 운영 등록 뒤에만 돈다).

1. 대상: 비교하는 값 안의 모든 월드 상태 객체. 적용 상태, 명령 결과 `effects[]` 가운데 `kind: 'world'`인 항목의 `state`(출병 등 `defineCommand` 명령은 전체 상태를 여기에 싣는다, `commands/support.ts:55`), 엔진의 `loadReplayState` 결과, 재생 상태(`ReplayState.state`).
2. 지우는 것: 그 객체들의 최상위 `ext`와 `ruleFeatures` 키만. 중첩된 같은 이름이나 다른 키(`presetRules`, `commandMeta` 등), `world`가 아닌 효과, `logs`·`reports`·`history`·`battleAwards`는 그대로 둔다.
3. 방법: 시험 helper `stripFeatureKeys(value)`가 깊은 사본을 만들어 위 위치의 두 키를 지우고 `{ normalized, removed }`를 낸다. `removed`는 지운 위치(예: `effects[0].state`)마다 원래 값이다. 원래 값은 바꾸지 않는다.
4. 직렬화: 정규화한 값을 기존 골든과 같은 직렬화(`attack.test.ts`·T4-18 V1과 같은 함수)로 SHA-256한다.
5. 지운 값 검증: 켠 쪽 `removed`의 `ruleFeatures`는 그 월드의 기능 목록과 같다. `ext`는 그 시험이 기대하는 조각 값과 같다. 기능이 아무것도 바꾸지 않아야 하는 사례에서는 실행 전 상태의 `ext`와 깊게 같다. 끈 쪽 `removed`는 비어 있다. 하나라도 어긋나면 실패다.
6. 로그·보고 문구와 수치: 정규화 없이 그대로 같아야 한다.

CMP-B를 쓰는 시험: T4-22 V1·I2(결과만), [T4-23](./T4-23.md) R2·R4·P8, [T4-25](./T4-25.md) V4·F2. CMP-A: T4-18 방식 골든을 기준 SHA에서 다시 재는 시험(T4-22 V3, T4-25 V1~V3). CMP-C: [T4-20](./T4-20.md) P10, T4-23 P7, [T4-28](./T4-28.md) P11, T4-25 E2. CMP-D: T4-28 F5. 비교 시험마다 두 전제를 이 문서를 쓰며 코드와 대조한 결과다.

| ---- | ---- | ----------------------------- | ----------------------- |
