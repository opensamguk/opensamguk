# T2-20 D6 턴 알림: 디스코드 웹훅

> 대기열: T2-20 · AC: AC-M2-18 · 구현: Codex · 리뷰: Claude
> 선행: T2-09, T2-13(`turns.low`의 남은 칸) · 관련: [차별화 D6](../product/differentiation.md#d6-턴-알림-기본-포함), FR-DIF-06a

## 계획 (Claude)

### 목표

디스코드 웹훅을 등록한 사용자는 예턴 실패, 공격받음, 외교 제안 도착, 예턴 남은 칸 3칸 이하를 1분 안에 받는다.
같은 일로 두 번 보내지 않고 웹훅이 실패해도 게임 진행은 멈추지 않는다 (AC-M2-18).

### 범위

- `NotificationTarget(userId, kind: DISCORD, endpoint, events[], verifiedAt)`, `NotificationOutbox`
- engine: 해당 사건을 턴 트랜잭션 안에서 outbox에 기록
- server의 발송 작업: outbox를 읽어 웹훅 POST, 성공 표시, 재시도
- `apps/server/src/routers/notification.ts`

### 하지 않는 것

웹 푸시(M3), 이메일 알림, 디스코드 봇·OAuth.

### 결정

| 항목 | 결정 |
| ---- | ---- |
| 기록 | **outbox 방식**: 사건은 게임 트랜잭션 안에서 `NotificationOutbox(id, userId, event, payload, dedupeKey)`로 남긴다. 발송은 트랜잭션 밖 |
| 중복 기록 | `dedupeKey` 고유 제약. 같은 사건은 outbox에 한 번만 남는다. 외부 전송 중복은 이 제약으로 막지 못하고 아래 [외부 전송 정책](#외부-전송-정책-검토-r63-10-2026-10-21-정리)이 정한다 |
| 발송 | 10초마다 미발송 건을 묶어 보냄. 재시도는 외부 전송 정책의 재시도 대상만, 1·5·15분 뒤 포기 기록. 웹훅이 404·401이면 대상 비활성화 |
| 내용 | 월드 이름, 게임 연월, 한 줄 설명, 화면 링크. **다른 국가의 비밀 정보는 넣지 않는다** |
| 등록 확인 | 웹훅 등록 시 시험 메시지를 보내고 성공해야 `verifiedAt` |
| 주소 검사 | 아래 [웹훅 주소와 요청 경계](#웹훅-주소와-요청-경계-검토-r63-9-2026-10-21-추가) |
| 비밀 | 웹훅 주소는 비밀값처럼 다룬다. 로그·오류 문장·화면 입력 칸 밖에 남기지 않고 화면에는 끝 4자리만 |

사건과 중복 키 (검토 R63-10):

| 사건 | 받는 사람 | `dedupeKey` | 생기는 때와 다시 울리는 조건 |
| ---- | --------- | ----------- | ---------------------------- |
| `turn.failed` | 그 장수의 주인 | `turn-failed:<worldId>:<generalId>:<tick>` | 장수 턴의 명령이 실패한 턴 트랜잭션 |
| `attacked` | 공격받은 도시를 가진 국가의 소속 장수 주인마다 | 초안 `attacked:<worldId>:<userId>:<tick>:<attackerId>` (U63-5) | 공격한 장수의 턴 트랜잭션 |
| `diplomacy.offer` | 받는 국가의 군주·참모 주인마다 | `diplomacy-offer:<worldId>:<userId>:<treatyId>` | T2-07 제안이 엔진에서 집행된 트랜잭션 |
| `turns.low` | 그 장수의 주인 | `turns-low:<worldId>:<generalId>:<turnRevision>` | 남은 칸이 4칸 이상에서 3칸 이하로 줄어든 턴 트랜잭션. 예턴을 저장해 4칸 이상이 되면 다시 울릴 수 있다 |

- 받는 사람은 사건을 기록할 때의 소속·직책으로 정한다. 같은 사람에게 같은 키는 한 번만 남는다.
- 공격받음의 사건 단위 (검토 R63-10R, 2026-10-22 추가). 엔진은 같은 tick에 차례가 온 장수를 ID 순으로 하나씩 처리한다(`apps/engine/src/turnLoop.ts:108-111`).
  그래서 서로 다른 두 장수가 같은 tick에 같은 도시를 치면 전투가 둘이다. 예전 키 `<tick>:<cityKey>`는 두 전투를 같은 키로 만들어 둘째 알림을 고유 제약으로 지웠다.
  전투 하나는 `(worldId, tick, attackerId)`로 가린다. 전투 기록도 이 셋으로 쌓는다(`apps/engine/src/commandPersistence.ts:92-94`, `packages/db/prisma/schema.prisma:209-219`).
  초안은 전투마다 한 건이고 도시 번호는 키가 아니라 내용에 싣는다. 같은 전투를 다시 처리해도 키가 같아 한 건이다.
- 남은 칸은 30칸 중 사용자가 직접 넣은 칸(`explicit`, T2-13) 가운데 아직 실행하지 않은 칸 수다. 30칸은 늘 휴식으로 채워져 있으므로 행 수로 세지 않는다.
  그래서 `turns.low`는 T2-13의 `explicit`이 들어간 뒤에 만든다. T2-20의 선행에 T2-13을 더한다.
- 정상 경로는 사건 기록부터 1분 안이다. 외부 장애 때의 재시도 지연(1·5·15분)은 이 1분 약속에 들지 않는다.

> **사용자 결정 필요 (U63-5)**: 공격받음 알림을 전투마다 보낼지, 같은 tick·같은 도시의 전투를 한 건으로 모을지 정한다. 초안은 전투마다다.
> 모으기로 하면 전투마다 트랜잭션이 달라 기록할 때 합칠 수 없다. 아직 집지 않은 행에 건수를 더하고 이미 보낸 뒤면 새 행을 만드는 규칙이 더 필요하다.
> 결정이 나기 전에는 위 키를 확정 계약으로 쓰지 않는다. U63-4와 마찬가지로 사용자 답을 받은 뒤 구현을 마감한다.

### API 계약

```ts
notification.get() → NotificationResponse
notification.setDiscord({ url, events, generation })   // 시험 메시지 발송 후 저장
notification.setEvents({ events, generation })         // 주소를 다시 넣지 않고 알림 종류만 바꾼다
notification.removeDiscord({ generation })
```

모두 계정 단위다. 행위자는 세션의 사용자이고 입력에 사용자 ID를 받지 않는다. 무인증은 `UNAUTHORIZED`, 제재 계정은 세션이 없으므로 같다.
타입은 계약 초안이고 최종 서버 타입은 backend(Codex)가 `AppRouter`로 정한다.

v1에는 플레이어용 알림이 없었고 운영 경보만 같은 디스코드 웹훅으로 보냈다(v1 `tools/ops/daemon_health_alert.sh:185-188`: 제한 시간 10초, 429·5xx 재시도). 거기서 두 가지를 가져온다.

- 웹훅 요청 하나의 제한 시간은 10초다. 429는 `Retry-After`를 지킨 뒤 재시도 일정에 넣는다.
- 디스코드는 빈 본문을 400으로 거절한다(v1 같은 파일 `:145-148`). 시험 메시지와 알림 모두 `content`를 반드시 채운다.

### 웹훅 주소와 요청 경계 (검토 R63-9, 2026-10-21 추가)

접두어 비교 대신 URL을 파싱해 아래를 모두 만족할 때만 받는다.

- 프로토콜 `https:`, 호스트가 정확히 `discord.com` 또는 `discordapp.com`, 포트 없음(기본 443), 사용자 정보(`user:pass@`) 없음, 조각(`#`) 없음, 쿼리 없음.
- 경로가 `/api/webhooks/<숫자 ID>/<토큰>`이다. 토큰은 영문·숫자·`_`·`-`만, 길이 상한을 둔다. 저장은 파싱한 값으로 다시 만든 주소로 한다.
- 요청은 리다이렉트를 따라가지 않는다(`redirect: 'manual'`). 3xx는 실패로 보고 `GAVE_UP`으로 둔다.
- 10초 제한은 연결·TLS·본문 읽기를 합친 요청 전체에 건다.
- 결과 분류: 요청이 나가기 전 실패(주소 해석·연결 거부·TLS 실패)는 재시도, 응답을 받은 429는 재시도, 401·404는 대상 비활성화, 그 밖의 4xx와 3xx는 포기다.
  요청을 보낸 뒤 제한 시간 초과·연결 끊김, 그리고 응답을 받은 5xx는 결과 모름이다. 디스코드가 처리한 뒤 5xx를 돌려줄 수 있기 때문이다 (검토 R63-10R). 결과 모름을 어떻게 할지는 아래 U63-4가 정한다.
- 시험은 모두 시험이 띄운 localhost(`127.0.0.1`) 가짜 수신기로 보낸다. 실제 디스코드로는 보내지 않는다. 발송 함수(전송부)를 시험 코드에서 주입하고 주입한 전송부는 주소 검사를 통과한 디스코드 모양 주소(가짜 ID·토큰)를 받아 그 가짜 수신기로 보낸다.
  운영 주소 검사는 시험 때문에 느슨하게 하지 않는다. Playwright처럼 서버 프로세스 전체를 띄우는 시험에서는 시험 전용 환경변수로 가짜 수신기 주소를 준다. 서버는 그 값이 loopback 주소가 아니거나 운영 모드(`apps/server/src/server.ts:22`의 `production`)이면 시작하지 않는다.

오류 문장:

- 지금 오류 형식은 `INTERNAL_SERVER_ERROR` 말고는 `message`를 그대로 내보낸다(`apps/server/src/trpc.ts:3-11`). 그래서 디스코드 응답 본문, 예외 문장, 입력한 주소를 `message`나 로그에 넣지 않는다.
- 결과 분류마다 아래 API 계약의 고정 문장 하나로 바꾼다. 운영 로그에는 분류 이름과 상태 코드만 남긴다.

### 설정 변경 경합 (검토 R63-11, 2026-10-21 추가)

`setDiscord`는 외부 시험 전송 뒤에 저장하므로 그사이 다른 변경이 끼어들 수 있다. 사용자마다 `generation`(바꿀 때마다 1씩 오름)을 두고 아래처럼 한다.

- 저장 위치 (검토 R63-11R, 2026-10-22 추가): `generation`은 대상 행이 아니라 해제해도 지우지 않는 사용자 단위 자리에 둔다. 예를 들면 사용자마다 한 행인 알림 설정 행이나 `User`의 열이다.
  최종 모양은 Codex가 정한다. 지킬 것은 세 가지다. 해제·재등록·비활성화 어느 때도 값이 줄거나 처음으로 돌아가지 않는다. 행이 아직 없으면 0으로 본다. 그 자리는 계정이 탈퇴로 지워질 때만 함께 지운다.
  탈퇴한 계정은 `ACTIVE`가 아니라 어떤 저장도 통과하지 못하므로 값이 사라져도 옛 요청이 다시 맞아떨어지지 않는다.
- 대상 행은 등록할 때마다 새 `id`를 받는다. 재등록은 옛 행을 고치지 않고 지운 뒤 새 행을 만든다. 같은 `id`는 다시 쓰지 않는다.
- 모든 변경 요청은 화면이 마지막으로 받은 `generation`을 보낸다. 저장은 `User`가 `ACTIVE`이고 사용자의 `generation`이 같을 때만 하는 조건부 갱신이다. 같은 트랜잭션에서 `generation`을 1 올린다. 다르면 `CONFLICT`와 최신 `NotificationResponse`.
  그래서 시험 중에 해제·새 등록·종류 변경이 먼저 저장되면 늦게 끝난 시험 결과는 버려지고 해제가 되살아나지 않는다.
  해제 뒤 다시 등록해도 `generation`은 계속 오르므로, 해제 전에 받은 값을 든 늦은 요청이 다시 맞아떨어지는 일(ABA)이 없다.
- 해제는 대상 행과 그 사용자의 미발송 outbox를 지운다. 해제 뒤 같은 사용자가 다시 등록하면 새 `id`의 새 대상이다.
- 비활성(`disabled`) 대상에도 `setEvents`는 저장한다. 상태는 그대로이고 다시 등록해야 보낸다.
- 이미 outbox에 있는 사건은 보낼 때의 설정을 따른다. 보내기 직전 확인에서 그 종류가 꺼져 있으면 보내지 않고 지운다.
- 화면은 체크를 빠르게 바꿔도 요청을 하나씩 보낸다. 앞 요청이 끝나면 마지막 상태로 한 번 더 보낸다. 실패하면 서버가 준 상태로 되돌린다.

탈퇴·제재와 발송 (T3-02 계획 `dd4b29a`의 `docs/plans/T3-02.md:70-88`과 맞춤):

- 발송 작업은 POST 직전 짧은 트랜잭션에서 그 사용자의 `User` 행을 `FOR SHARE`로 잠그고 아래를 모두 다시 읽는다 (검토 R63-11R에서 종류와 대상 상태를 더함).
  사용자가 `ACTIVE`인가, 대상 행이 있고 `active`인가, 그 사건 종류가 대상의 `events`에 아직 켜져 있는가, 그 outbox 행이 아직 있고 집을 수 있는 상태인가.
  하나라도 아니면 보내지 않는다. 대상이 없거나 종류가 꺼졌으면 outbox 행을 지운다. 대상이 `disabled`이면 그 행을 `GAVE_UP`으로 둔다.
- 모두 맞으면 같은 트랜잭션에서 outbox 행을 `SENDING`으로 바꾸며 그 시도의 소유 표시(`claimId`, 시도마다 새 값)와 읽은 대상 `id`·사용자 `generation`을 행에 적는다. POST는 이 트랜잭션에서 읽은 주소로만 한다.
- 발송 결과 기록은 outbox `id`와 `claimId`가 같고 아직 `SENDING`일 때만 하는 `updateMany`다. 0행이면 무시한다. 지워진 행을 재시도로 다시 만들지 않고 재시작 정리로 `UNKNOWN`이 된 행을 늦은 결과로 덮지 않는다.
- 401·404로 대상을 비활성화할 때는 시도에 적어 둔 대상 `id`가 아직 `active`인 행만 `updateMany`로 바꾼다. 그사이 사용자가 다시 등록했으면 새 대상은 `id`가 달라 0행이다.
  예전 주소의 401·404나 늦게 끝난 결과가 새 등록을 비활성화하거나 덮지 않는다.
- 허용하는 in-flight 범위: 위 확인을 마치고 `SENDING`이 된 outbox 행마다 POST 1건이다. 확인을 마친 뒤 commit된 해제·재등록·종류 끄기·탈퇴·제재는 그 1건을 멈추지 않는다.
  그 1건은 예전 주소로, 예전 종류 설정대로 갈 수 있다. 그 뒤 결과 기록은 위 조건부 갱신만 하므로 바뀐 설정을 되돌리지 않는다. 다음 사건부터는 새 설정을 따른다.
  탈퇴·제재 commit 뒤 모든 네트워크 요청이 취소된다고 쓰지 않는다.
- 탈퇴 때 대상·outbox 삭제는 T3-02가 한다. T2-20은 위 확인과 0행 허용을 만든다.

### 외부 전송 정책 (검토 R63-10, 2026-10-21 정리)

`dedupeKey`는 사건을 두 번 기록하지 않게 할 뿐이다. 웹훅 POST가 디스코드에 닿은 뒤 응답을 잃거나, 성공 응답을 받은 뒤 DB 기록 전에 멈추면
서버는 보냈는지 알 수 없다. 이때 다시 보내면 같은 알림이 두 번 간다. 안 보내면 한 번도 안 갈 수 있다. 디스코드 웹훅에 중복을 막는 키가 있는지는
확인하지 않았으므로 이 계획은 그런 키에 기대지 않고 외부 전송이 정확히 한 번이라고 쓰지 않는다.

> **사용자 결정 필요 (U63-4)**: 결과를 모르는 전송을 다시 보낼지 정한다. AC-M2-18의 "같은 일로 두 번 보내지 않고"를 그대로 지키는 초안은 최대 1회다.
> 최소 1회로 바꾸면 드물게 같은 알림이 두 번 갈 수 있어 AC 문장도 고쳐야 한다. 결정이 바뀌면 아래 표의 `UNKNOWN` 행만 재시도로 바꾼다.

결과 분류별 두 안의 차이 (검토 R63-10R, 2026-10-22 추가). 이 표는 어느 안도 고르지 않는다.

| 경우 | 디스코드가 처리했을 수 있나 | 최대 1회 초안 | 최소 1회 안 |
| ---- | -------------------------- | ------------- | ----------- |
| 요청이 나가기 전 실패 | 없다 | 재시도 | 재시도 |
| 응답을 받은 429 | 처리하지 않았다고 본다. 디스코드 문서로 확인하지 않은 가정이고 U63-4에서 함께 확인한다 | 재시도 | 재시도 |
| 응답을 받은 5xx | 있다 | 보내지 않음. 처리하지 않았다면 이 알림은 빠진다 | 재시도. 처리했다면 두 번 간다 |
| 요청을 보낸 뒤 제한 시간 초과·연결 끊김 | 있다 | 보내지 않음. 빠질 수 있다 | 재시도. 두 번 갈 수 있다 |
| 2xx를 받은 뒤 기록 전에 멈춤 | 처리했다 | 보내지 않음 | 재시도. 두 번 간다 |

초안을 고르면 디스코드가 잠깐 5xx를 내는 동안의 알림은 빠진다. 최소 1회를 고르면 그 알림은 늦게라도 가지만 같은 알림이 두 번 올 수 있다. 어느 쪽이든 게임 진행은 영향이 없다.

초안(최대 1회)의 발송 상태:

| 상태 | 언제 | 다음 |
| ---- | ---- | ---- |
| `PENDING` | 엔진이 사건을 기록함 | 발송 작업이 집는다 |
| `SENDING` | 발송 작업이 POST 직전 확인과 함께 시도 횟수, 집은 시각, `claimId`, 대상 `id`·`generation`을 커밋함 | POST 결과에 따라 아래로 |
| `SENT` | 2xx 응답을 받고 기록함 | 끝 |
| `RETRY` | 요청이 나가기 전 실패, 또는 응답을 받은 429 | 재시도 일정. 429는 `Retry-After`를 지킨다 |
| `UNKNOWN` | 응답을 받은 5xx, 요청을 보낸 뒤 제한 시간 초과·연결 끊김, 또는 재시작 때 집은 지 1분 넘은 `SENDING`(2xx를 받고 기록 전에 멈춘 경우 포함) | 다시 보내지 않는다. 운영 로그에 분류와 건수만 남긴다 |
| `GAVE_UP` | 재시도 3번 실패, 3xx·400·그 밖의 4xx, 401·404 | 끝. 401·404는 대상 비활성화 |

- 여러 발송 작업이 같은 건을 집지 않도록 `PENDING`·`RETRY` → `SENDING` 전환은 조건부 갱신 한 번으로 한다. 집은 시각이 1분 넘은 `SENDING`은 위 표대로 `UNKNOWN`이다.
- 발송 상태는 게임 상태가 아니다. 재생과 상태 해시에 들어가지 않는다. 발송 실패가 게임 트랜잭션을 되돌리지 않는다.

### 화면(T2-21)이 기대하는 응답 모양

```ts
type NotificationEvent = 'turn.failed' | 'attacked' | 'diplomacy.offer' | 'turns.low';

type NotificationResponse = {
  discord: {
    last4: string;               // 웹훅 주소 끝 4자리. 주소 전체는 어떤 응답에도 싣지 않는다
    status: 'active' | 'disabled';
    disabledReason: 'DISCORD_GONE' | null; // 발송 중 404·401로 비활성화되면 'DISCORD_GONE'
    verifiedAt: string;          // 시험 메시지가 성공한 시각 (ISO). 저장된 대상은 모두 시험을 통과했다
    events: NotificationEvent[]; // 켠 종류. eventOptions 순서
  } | null;                      // 등록하지 않았거나 해제했으면 null
  generation: number;            // 다음 변경 요청에 그대로 보낸다. 사용자 단위 값이라 대상이 없어도 있고 해제·재등록에도 줄지 않는다
  eventOptions: { key: NotificationEvent; name: string }[];
  // 순서와 이름 고정: 예턴 실패, 공격받음, 외교 제안, 예턴 3칸 이하
};

// setDiscord·setEvents·removeDiscord 모두 성공하면 NotificationResponse를 돌려준다
// 실패는 TRPCError이고 message는 아래 고정 문장 중 하나다. 디스코드 응답·예외·주소를 넣지 않는다. 저장하지 않는다
//   BAD_REQUEST          주소 검사 실패 → "디스코드 웹훅 주소가 아닙니다." events는 비어 있어도 된다 (아무것도 보내지 않음)
//   CONFLICT             generation이 다름 → "다른 곳에서 알림 설정이 바뀌었습니다. 다시 확인해 주세요."
//   PRECONDITION_FAILED  시험 메시지 실패. 결과 분류에 따라
//                        401·404 → "웹훅을 찾을 수 없습니다. 디스코드에서 웹훅 주소를 다시 복사해 주세요."
//                        429     → "디스코드가 요청을 잠시 막았습니다. 조금 뒤 다시 시도해 주세요."
//                        제한 시간 초과·5xx·연결 실패 → "디스코드가 응답하지 않습니다. 잠시 뒤 다시 시도해 주세요."
//                        그 밖의 4xx·3xx → "디스코드가 메시지를 받지 않았습니다. 웹훅 설정을 확인해 주세요."
// setEvents는 등록된 대상이 없으면 PRECONDITION_FAILED
```

주소를 다시 입력해 `setDiscord`를 부르면 비활성화된 대상도 새로 시험하고 `active`로 돌아온다.

| T2-21 화면 요소 | 쓰는 응답 |
| --------------- | --------- |
| 등록됨 (…ab12) | `discord.last4`, `status` |
| 비활성화 안내 (다시 등록해 달라는 문장) | `status: 'disabled'`, `disabledReason` |
| 시험 보내고 저장, 실패 이유 | `setDiscord`, `TRPCError.message`(고정 문장) |
| 알림 종류 체크와 유지 | `eventOptions`, `discord.events`, `setEvents`, `generation` |
| 해제 | `removeDiscord` → `discord: null` |
| 주소를 다시 보여 주지 않음 | 응답에 주소 전체가 없음 |

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 사건 4종 | 통합(실제 DB, localhost 가짜 수신기): 각 사건 → 정상 경로에서 1분 안에 1건 |
| 공격받음 동률 | 통합(실제 DB): 서로 다른 두 장수가 같은 tick에 같은 도시를 공격 → 받는 사람마다 outbox 2건(U63-5 초안). 같은 전투를 다시 처리 → 그대로 2건 |
| 남은 칸 | 단위: 직접 넣은 칸이 4 → 3이 되는 턴에 1건, 3 → 2에서는 없음, 예턴을 저장해 4칸 이상이 된 뒤 다시 3이 되면 1건 |
| 중복 기록 | 통합: 같은 사건 재처리(엔진 재시작) → outbox 1건, 가짜 웹훅 수신 1건 |
| 결과 모름 | 통합: 가짜 웹훅이 받은 뒤 응답을 12초 늦춤 → 수신 1건, 상태 `UNKNOWN`, 재시도 없음 |
| 기록 전 종료 | 통합: 2xx를 받은 뒤 기록 전에 발송 작업을 멈추고 다시 띄움 → 다시 보내지 않음 |
| 발송 중 재시작 | 통합: POST 도중 발송 작업을 멈추고 다시 띄움 → `SENDING`이 `UNKNOWN`이 되고 다시 보내지 않음 |
| 동시 발송 | 통합: 발송 작업 두 개가 같은 미발송 건을 동시에 집음 → POST 1번 |
| 재시도와 포기 | 통합: 연결 거부 → `RETRY` 뒤 `SENT`. 429 → `Retry-After`를 지킨 뒤 재시도. 세 번 실패 → `GAVE_UP` |
| 처리 뒤 5xx | 통합: 가짜 수신기가 본문을 받아 기록한 뒤 500을 돌려줌 → 수신 1건, 상태 `UNKNOWN`, 재시도 없음(최대 1회 초안). U63-4가 최소 1회로 정해지면 같은 시험의 기대를 수신 2건으로 바꾼다 |
| 실패 격리 | 통합: 웹훅 서버가 계속 500 → 게임 턴은 정상 진행 |
| 주소 검사 | 단위: 다른 호스트, `http:`, 포트 지정, `user@` 포함, 쿼리·조각 포함, 경로·토큰 모양이 다름 → 거부. 리다이렉트 응답 → 따라가지 않고 포기 |
| 오류 문장 | API: 가짜 전송이 401·404·429·500·제한 시간·400을 돌려줌 → 고정 문장만, 응답·로그에 디스코드 본문과 주소 없음 |
| 설정 경합 | 통합(실제 DB, 가짜 수신기가 응답을 늦춤): 시험 전송 중 `removeDiscord` → 늦은 `setDiscord`는 `CONFLICT`, 대상 없음 유지. 시험 중 더 새 `setDiscord` → 늦은 쪽 `CONFLICT`, 새 대상 유지. 시험 중 `setEvents` → 늦은 등록이 덮지 않음. 시험 중 탈퇴·제재 → 저장 안 됨 |
| 세대 ABA | 통합: `generation` g로 시험 시작 → 그사이 해제와 재등록 → 늦은 g 요청 `CONFLICT`. 해제 뒤에도 `generation`이 줄지 않음 |
| 예전 주소 결과 | 통합: 대상 T1로 집은 발송이 POST 중 → 사용자가 T2로 다시 등록 → 가짜 수신기가 404 → T2는 `active` 유지, 결과 기록은 그 outbox 행에만. 같은 상황에서 늦은 2xx도 T2를 바꾸지 않음 |
| 시도 소유 | 통합: `SENDING`이 재시작 정리로 `UNKNOWN`이 된 뒤 옛 작업의 결과가 도착 → `claimId`가 달라 0행, `UNKNOWN` 유지 |
| 보낼 때 확인 | 통합: 사건 기록 뒤 그 종류를 끔·대상 해제·계정 제재 → 보내지 않고 outbox 삭제, 결과 기록 0행 무시. 대상이 `disabled` → 보내지 않고 `GAVE_UP`. 확인을 마친 뒤 종류를 끔 → 그 1건은 감, 다음 사건은 보내지 않음 |
| 권한 | API: 무인증·제재 `UNAUTHORIZED`, 다른 사용자의 대상은 읽기·바꾸기 불가, 잘못된 events·generation 거부 |
| 비활성화 | 통합: 가짜 웹훅이 404 → `status: 'disabled'`, 주소를 다시 넣으면 `active` |
| 실제 디스코드 | 이 계획의 검증에 넣지 않는다. 위 시험은 모두 localhost 가짜 수신기로 하고 실제 디스코드로 보내지 않는다. 실제 채널 확인이 필요하면 사용자가 따로 정한다(NOT_RUN) |

### 디스코드 전송 leaf 실행 계획 (2026-10-24 추가)

> 이 절은 실행 계획이고 구현 허가가 아니다. Codex 검토와 상위 허가를 받은 뒤에 구현한다. 위 절들은 그대로 두고 어긋나는 곳은 이 절 끝 [위 절과의 관계](#위-절과의-관계)에 적는다.

새로 만드는 파일은 `apps/server/src/notifications/discordWebhook.ts`와 `apps/server/src/notifications/discordWebhook.test.ts` 둘뿐이다. 이 leaf는 검사를 통과한 입력 하나를 디스코드 웹훅에 POST 한 번으로 보내고 관찰한 것을 정해진 결과 하나로 돌려준다.

화면, 저장(모델·schema·outbox), API와 `AppRouter` 연결, 발송 작업, 재시도·포기·대상 비활성화 판단, `generation`·`claimId`, 사건 기록, 탈퇴, 서버 시작·종료는 만들지 않고 있다고 쓰지도 않는다. 새 의존성, 전역 시험 timeout·lint 설정 변경, 새 환경변수도 없다.
U63-4(결과 모름과 429 정책), U63-5(공격받음 묶기), A13은 미결 그대로다. 실제 디스코드로 한 번 보내 보는 확인은 이들과 별개인 AC-M2-18의 미결 항목이다. 구현자는 사용자에게 제품 결정이나 실제 웹훅 주소·키·시험 계정을 묻지 않는다.

#### 공식 문서에서 확인한 것

Codex가 2026-10-24 읽기 전용으로 본 공식 문서다. 이 계획을 쓰면서 다시 열어 보지는 않았다.

| 문서 | 확인한 것 |
| ---- | --------- |
| [Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook) | `content`는 최대 2000 characters이고 `allowed_mentions`를 받는다. 기본 `wait=false`에서는 저장되지 않은 메시지에도 오류가 없을 수 있다. 토큰은 secure string이라고만 하고 길이 상한은 적혀 있지 않다 |
| [Snowflakes](https://docs.discord.com/developers/reference#snowflakes) | ID는 uint64이고 문자열로 나타낸다. API 기준 주소는 `https://discord.com/api`다 |
| [Exceeding a rate limit](https://docs.discord.com/developers/topics/rate-limits#exceeding-a-rate-limit) | 기다릴 초는 `Retry-After` 헤더나 본문 `retry_after`로 온다. 한도 수치를 코드에 박지 말라고 한다 |

그래서 2xx 상태는 메시지가 저장됐다는 증거가 못 된다. 이 절의 수치(주소 512자, 토큰 5..256자, `content` 2000 UTF-16 단위, 본문 16384바이트, 10000ms) 가운데 공식 문서가 정한 것은 없고 모두 프로젝트 상한이다.

#### 공개 경계

```ts
// discordWebhook.ts가 내보내는 것은 이것뿐이다
export type DiscordWebhookRequestInit = Readonly<{
  method: 'POST';
  headers: Readonly<{ 'content-type': 'application/json' }>;
  body: string;
  redirect: 'manual';
  signal: AbortSignal;
}>;
export type DiscordWebhookTransport = (url: string, init: DiscordWebhookRequestInit) => Promise<Response>;

export type DiscordWebhookStatusCategory =
  | 'STATUS_2XX' | 'STATUS_3XX' | 'STATUS_401_404' | 'STATUS_429' | 'STATUS_4XX_OTHER' | 'STATUS_5XX';

export type DiscordWebhookSendResult =
  | { kind: 'NOT_SENT'; code: 'INVALID_OPTIONS' | 'INVALID_INPUT' | 'INVALID_URL' | 'INVALID_CONTENT' | 'BODY_TOO_LARGE' }
  | { kind: 'UNKNOWN'; code: 'TRANSPORT_FAILED' | 'TIMEOUT' | 'INVALID_RESPONSE' }
  | { kind: 'HTTP_OBSERVED'; status: number; category: DiscordWebhookStatusCategory; retryAfterSeconds: number | null };

export function sendDiscordWebhook(
  input: unknown,
  options?: { transport?: DiscordWebhookTransport },
): Promise<DiscordWebhookSendResult>;

export type DiscordWebhookEndpoint = Readonly<{ endpoint: string; last4: string }>;

export function normalizeDiscordWebhookUrl(input: unknown): DiscordWebhookEndpoint | null;
```

- 주소 검사와 정규화는 모듈 안 함수 하나로 두고 `normalizeDiscordWebhookUrl`과 `sendDiscordWebhook`의 3단계가 함께 쓴다. 두 공개 함수의 주소 규칙은 같다. 본문 만들기와 `Retry-After` 해석은 내보내지 않는다. 시험은 두 공개 함수와 주입한 전송부로만 본다.
- `normalizeDiscordWebhookUrl`은 원시 문자열이 아니거나 아래 주소 검사에 걸리면 `null`을 돌려준다. throw, 로그, 네트워크 요청은 없다. 통과하면 매번 새 객체로 `{ endpoint: 정규화한 주소, last4: token.slice(-4) }`를 돌려준다.
- `endpoint`는 서버 안에서만 쓰는 비밀값이다. API 응답, 로그, 오류 문장, `DiscordWebhookSendResult`에 싣지 않는다. `last4`는 화면 마스킹에 쓰는 부분값이고 토큰이 5자 이상이라 토큰 전체와 같아지지 않는다. 저장과 API 연결은 이 leaf의 일이 아니다.
- `sendDiscordWebhook`은 throw하거나 reject하지 않는다. 어떤 경우든 위 결과 하나로 끝난다. 결과 객체는 매번 새로 만들고 위 필드 말고는 싣지 않는다.
- 결과에 입력 주소, 정규화한 주소, 토큰(끝 4자리 포함), `content`, 응답 본문, `statusText`, `Location`과 다른 헤더, 예외 객체·문장·`cause`가 들어가지 않는다. 같은 값을 throw하거나 로그로 남기지도 않는다.
- 모듈은 logger를 들이지 않고 `console`을 부르지 않으며 `process.env`를 읽지 않는다. 모듈 수준 변수에 요청 상태를 두지 않는다.
- 입력 주소는 정규화 전후 모두 비밀이다. `sendDiscordWebhook`은 이를 함수 안 지역 변수로만 들고 정규화한 주소는 전송부의 첫 인자로만 넘긴다. `last4`와 `endpoint`를 결과에 더하지 않는다.
- `options.transport`는 서버 코드가 넣는 신뢰된 의존성이고 클라이언트 입력에서 받지 않는다. 생략하면 전역 `fetch`를 그대로 쓴다. timeout을 바꾸는 옵션은 두지 않는다.
- 시험 전용 주소 입력 칸, loopback 허용, 전역 `fetch` 바꿔치기, 환경변수로 켜는 시험 경로는 만들지 않는다.
- `NOT_SENT`는 전송부를 부르기 전 검사에서 멈춘 경우뿐이고 전송부 호출은 0번이다. 검사를 통과하면 전송부를 정확히 1번 부른다. 리다이렉트를 따라가지 않고 다시 보내지 않는다. 이것은 호출 횟수 약속이며 디스코드에 정확히 한 번 닿는다는 약속은 아니다.
- 요청이 실제로 나갔는지 알려 주는 표시는 결과에 두지 않는다. 결과의 `UNKNOWN`은 이 호출의 결과를 모른다는 뜻이고 outbox 상태 `UNKNOWN`과는 별개다.

#### 검사 순서

앞 단계에서 실패하면 거기서 멈추고 그 code를 돌려준다.

| 순서 | 통과 조건 | 실패 code |
| ---- | --------- | --------- |
| 1 | `options`가 `undefined`이거나, 자기 키가 없거나 `transport` 하나뿐인 평범한 객체다. `transport`는 없거나 `undefined`이거나 함수다 | `INVALID_OPTIONS` |
| 2 | `input`이 평범한 객체(프로토타입이 `Object.prototype` 또는 `null`)이고 `Reflect.ownKeys`가 정확히 `url`, `content` 두 개다. 둘 다 값 속성(getter·setter 아님)이고 값이 원시 문자열이다 | `INVALID_INPUT` |
| 3 | 아래 주소 검사 | `INVALID_URL` |
| 4 | 아래 `content` 검사 | `INVALID_CONTENT` |
| 5 | JSON 본문이 UTF-8로 16384바이트 이하 | `BODY_TOO_LARGE` |

1·2단계는 `Object.getOwnPropertyDescriptor`로 값을 한 번씩만 읽어 지역 변수에 둔다. getter는 부르지 않는다. Proxy 등이 이 단계에서 던진 예외는 잡아서 그 단계 code로 바꾼다.
`embeds`, `files`, `username`, `avatar_url` 같은 다른 키(기호 키, 열거하지 않는 키 포함)가 있으면 걸러서 보내지 않고 입력 전체를 거부한다.

#### 주소 (`INVALID_URL`)

URL 생성자로 판단하지 않고 원문 문자열을 직접 본다. URL 생성자는 점 경로(`.`·`..`), 기본 포트, 빈 쿼리, 역슬래시, 대소문자를 고쳐 버려 원문에서 막아야 할 것을 가린다. 원문이 아래를 모두 만족해야 받는다.

- 길이 1..512이고 모든 문자가 0x21..0x7E다. 공백, 제어 문자, 비ASCII 문자는 한 글자도 없다. 유효한 주소는 길어야 313자이고 512는 긴 입력을 정규식 전에 끊는 상한이다.
- `\`, `%`, `?`, `#`, `@`가 어디에도 없다. 퍼센트 인코딩, 빈 쿼리 `?`, 빈 조각 `#`, `user@`와 맨 `@` 사용자 정보가 여기서 막힌다.
- 대소문자를 가리지 않고 `https://`로 시작한다.
- 그 뒤 첫 `/`까지가 호스트이고 소문자로 바꾸면 정확히 `discord.com` 또는 `discordapp.com`이다. 포트(`:443`과 `:`만 있는 것 포함), 끝 점(`discord.com.`), 하위 도메인(`canary.`, `ptb.`, `www.`), IP, `localhost`는 여기서 떨어진다.
- 나머지 경로가 대소문자를 가려 정확히 `/api/webhooks/{id}/{token}`이다. 끝 `/`, 더 붙은 경로(`/slack`, `/github`), 버전 경로(`/api/v10/webhooks/...`), 점 경로, `/API/` 같은 대소문자 차이는 거부한다.
- `{id}`는 `[1-9][0-9]{0,19}`이고 20자리면 같은 길이 문자열 비교로 `18446744073709551615` 이하다. `0`과 앞자리 0은 받지 않는다. `Number`로 바꾸지 않는다.
- `{token}`은 `[A-Za-z0-9_-]{5,256}`이다. 이 문자 집합과 길이는 프로젝트 상한이며 디스코드의 토큰 형식이라고 주장하지 않는다. 최소 5자는 끝 4자리를 보여 줄 때 토큰 전체가 드러나지 않게 하려는 것이다. 끝 4자리는 `normalizeDiscordWebhookUrl`의 `last4`로만 돌려준다.

통과하면 `https://discord.com/api/webhooks/{id}/{token}`으로 다시 만든다. 입력 호스트가 `discordapp.com`이거나 scheme·호스트에 대문자가 있어도 결과는 이 모양이다. 쿼리는 원문에서 거부하고 보낼 때도 붙이지 않는다(`wait`, `thread_id` 없음).

#### 내용과 본문

- `content`는 UTF-16 code unit으로 1..2000이다. 공식 2000 characters와 같은 방식으로 센다고 주장하지 않는다. UTF-16 단위 수는 code point 수나 글자 수보다 작아지지 않으므로 더 엄격한 쪽이다.
- `content.trim()`이 빈 문자열이면 거부한다. 공백, 줄바꿈, U+3000, U+00A0, U+FEFF로만 된 경우가 여기 든다. U+200B처럼 `trim`이 지우지 않는 문자는 이 검사에서 거부하지 않는다.
- 짝 없는 surrogate가 하나라도 있으면 거부한다.
- 통과한 `content`는 그대로 보낸다. 앞뒤 다듬기, 자르기, 유니코드 정규화를 하지 않는다. 줄바꿈과 다른 제어 문자도 막지 않는다.
- 본문은 `JSON.stringify({ content, allowed_mentions: { parse: [] } })`이다. 이 두 키만 이 순서로 넣는다. `allowed_mentions`는 `@everyone`·역할·사용자 언급이 알림을 울리지 못하게 막는다.
- 2000단위가 모두 `\uXXXX`로 이스케이프되는 최악(12000바이트)에 고정 필드를 더해도 16384바이트를 넘지 않는다. 그래서 5단계는 지금 입력으로는 닿지 않는 방어 검사다.
- `embeds`, `files`, `username`, `avatar_url`, `tts`, `thread_id`를 비롯한 다른 Execute Webhook 필드는 보내지 않는다.

#### 요청과 제한 시간

- 전송부는 `transport(정규화한 주소, { method: 'POST', headers: { 'content-type': 'application/json' }, body, redirect: 'manual', signal })`로 부른다. 헤더는 이것 하나다.
- 제한 시간은 10000ms 하나다. 전송부를 부르기 바로 앞에서 `AbortController`와 타이머를 만들고 거기서부터 잰다. 전송부 호출, 응답 헤더 기다림, 본문 취소가 모두 이 안에 든다.
- 전송부가 동기로 던지거나 돌려준 promise가 reject되면 `UNKNOWN`/`TRANSPORT_FAILED`다. DNS 실패, 연결 거부, TLS 실패처럼 보여도 `error.name`·`code`·`cause`를 보고 `NOT_SENT`나 재시도 분류로 바꾸지 않는다. 전송부에 들어간 뒤의 일이라 요청이 나갔는지 이 함수는 모른다.
- 돌려준 값은 `Promise.resolve`로 감싼다. `Response`가 아닌 값으로 끝나거나 status가 200..599 정수가 아니면(`Response.error()`의 0 등) `UNKNOWN`/`INVALID_RESPONSE`다.
- 10000ms 안에 `Response`가 오지 않으면 `controller.abort()`를 부르고 바로 `UNKNOWN`/`TIMEOUT`으로 끝낸다. abort를 무시하는 전송부여도 이때 끝난다.
- 전송부를 부를 때 그 promise에 미리 처리기를 달아 둔다. 끝난 뒤 resolve되든 reject되든 결과는 바뀌지 않고 unhandled rejection도 나지 않는다. 늦게 온 `Response`는 본문 취소만 시도하고 그 실패도 삼킨다.
- 제한 시간 안에 `Response`를 받으면 status와 (429일 때만) `Retry-After`를 읽고 본문은 버린다. `text()`·`json()`·`arrayBuffer()`로 읽지 않는다. 본문이 있으면 `response.body.cancel()`을 부르고 남은 제한 시간까지만 기다린다. 그 안에 안 끝나거나 실패하면 `abort()`를 부르고 넘어간다.
- 응답 헤더를 받은 뒤에는 HTTP 관찰이 이긴다. 본문 취소가 제한 시간까지 끝나지 않아도 결과는 `HTTP_OBSERVED`이고 늦어도 제한 시간에 돌려준다. status는 이미 받았고 본문 취소는 이쪽 자원 정리일 뿐이다.
- 어느 경로로 끝나든 돌려주기 전에 타이머를 지운다. 본문이 없거나 본문 취소가 남은 시간 안에 성공해 돌려줄 때는 abort하지 않는다. 취소가 실패하거나 남은 시간 안에 끝나지 않아 `HTTP_OBSERVED`를 돌려줄 때는 위처럼 abort한다.

#### 결과 분류

| 상황 | 결과 |
| ---- | ---- |
| 전송부를 부르기 전 검사 실패 | `NOT_SENT`와 단계별 code. 전송부 0번 |
| 전송부 동기 throw, reject | `UNKNOWN`/`TRANSPORT_FAILED` |
| `Response` 전에 제한 시간 | `UNKNOWN`/`TIMEOUT` |
| `Response`가 아니거나 status가 범위 밖 | `UNKNOWN`/`INVALID_RESPONSE` |
| 200..299 | `HTTP_OBSERVED`, `STATUS_2XX` |
| 300..399 | `STATUS_3XX`. `Location`을 읽지 않고 따라가지 않는다 |
| 401, 404 | `STATUS_401_404` |
| 429 | `STATUS_429` |
| 그 밖의 400..499 (400 포함) | `STATUS_4XX_OTHER` |
| 500..599 | `STATUS_5XX` |

`status`에는 받은 숫자를 그대로 싣는다. 2xx를 `SENT`, 전달 완료, 수신 확인으로 부르지 않는다. 기본 `wait=false`에서는 디스코드가 메시지를 저장했는지 응답으로 알 수 없다.
`GAVE_UP`·`RETRY` 같은 상태 전환과 대상 비활성화는 다음 leaf의 발송 작업이 정한다. Node 기본 `fetch`는 `redirect: 'manual'`에서 3xx status를 그대로 준다고 보고 시험으로 확인한다. 다르게 나오면 분류를 바꾸지 말고 구현 기록에 적어 검토를 받는다.

#### `Retry-After`

429에서만 `response.headers.get('retry-after')`를 읽는다. 다른 status에서는 읽지 않고 `retryAfterSeconds`는 `null`이다.
값이 10자 이하이고 `^(0|[1-9][0-9]{0,5})(\.[0-9]{1,3})?$`에 맞을 때만 `Number(값)`을 싣는다. 그래서 범위는 0..999999.999초다. 앞뒤 공백은 `Headers`가 이미 걷어 낸 값을 보며 모듈이 따로 다듬지 않는다.

| 헤더 값 | `retryAfterSeconds` |
| ------- | ------------------- |
| `0`, `1`, `1.5`, `0.250`, `999999.999` | `0`, `1`, `1.5`, `0.25`, `999999.999` |
| 없음, 빈 값, HTTP 날짜, `-1`, `+1`, `1e3`, `01`, `1.`, `.5`, `1.2345`, `1000000`, 여러 헤더가 합쳐진 `1, 2`, 11자 이상 | `null` |

`null`을 0초나 다른 대기 시간으로 바꾸지 않는다. 응답 본문의 `retry_after`와 전역 rate limit 헤더는 읽지 않는다. 기다리거나 다시 보내지 않고 디스코드 한도 수치도 코드에 넣지 않는다.

#### 시험 (`discordWebhook.test.ts`)

실제 디스코드로는 보내지 않는다. 기본 전송부(`fetch`)가 디스코드로 가는 경로는 이 leaf에서 시험하지 않는다(실제 디스코드 확인은 AC-M2-18의 별도 미결). 시험은 공개 함수와 주입한 전송부만 쓴다.

가짜 수신기:

- 시험 파일 안에서 `node:http` 서버를 `127.0.0.1` 포트 0으로 띄워 실제 HTTP POST를 받는다. 시험 전송부는 받은 정규화 주소와 `init`을 기록한 뒤, 주소는 버리고 `fetch('http://127.0.0.1:<포트>/hook', init)`로 보낸다.
- 운영 검사는 그대로다. 옵션 없이 `http://127.0.0.1:<포트>/api/webhooks/1/abcde`나 `https://127.0.0.1/api/webhooks/1/abcde`를 넣으면 `NOT_SENT`/`INVALID_URL`이고 서버 수신은 0건이다.
- 서버는 수신 건수, method, 경로, `content-type`, 원문 본문을 기록한다. 각 시험의 `finally`에서 `closeAllConnections()`를 부르고 `close()`를 기다리며 시험이 만든 타이머도 지운다.
- 정상 입력마다 수신 1건, `POST`, `application/json`, 본문이 `JSON.stringify({ content, allowed_mentions: { parse: [] } })`와 같은 문자열인지 본다. 전송부 호출 1번, 받은 주소가 정규화 주소, `init.redirect === 'manual'`, `init.signal`이 호출 때 abort되지 않은 `AbortSignal`인지도 본다.

| 가짜 수신기 응답 | 기대 결과 |
| ---------------- | --------- |
| 204, 본문 없음 | `HTTP_OBSERVED` 204 `STATUS_2XX`, `retryAfterSeconds: null` |
| 200, 본문에 표지 | 200 `STATUS_2XX` |
| 401, 404 | `STATUS_401_404` |
| 429, `Retry-After: 1.5` | `STATUS_429`, `1.5` |
| 429, 헤더 없이 본문 `{"retry_after": 7}` | `STATUS_429`, `null` |
| 429, `Retry-After`가 HTTP 날짜 | `STATUS_429`, `null` |
| 503, `Retry-After: 5` | `STATUS_5XX`, `null` |
| 302, 307, `Location`이 같은 서버 `/redirected` | `STATUS_3XX`, `/redirected` 수신 0건 |
| 400, 403 | `STATUS_4XX_OTHER` |
| 500 | `STATUS_5XX` |
| 요청을 받고 응답하지 않음 | `UNKNOWN`/`TIMEOUT`, 걸린 시간 10000ms 이상 11500ms 미만, 수신 1건 |
| 200 헤더와 본문 일부를 보낸 뒤 멈춤 | `HTTP_OBSERVED` 200, 11500ms 미만 |

| 서버를 닫은 뒤 그 포트로 보냄 | `UNKNOWN`/`TRANSPORT_FAILED` (`NOT_SENT` 아님) |

마지막 세 줄은 서로 다른 경우다. 헤더 뒤 멈춤은 status를 받았으므로 HTTP 관찰이다. `socket.destroy()`는 요청이 수신기에 닿은 뒤 응답 없이 끊긴 경우이고 닫힌 포트는 연결 자체가 안 된 경우다. 이 함수는 뒤의 둘을 가리지 않고 모두 `UNKNOWN`으로 돌려준다. 요청을 받은 뒤 끊긴 경우가 `NOT_SENT`가 되면 안 된다.

| abort를 무시하고 끝없이 pending | 10000ms 이상 11500ms 미만에 `UNKNOWN`/`TIMEOUT`, `signal.aborted`가 참. 그 뒤 pending을 reject하는 경우와 `Response`로 resolve하는 경우 모두 결과 그대로, `unhandledRejection` 0건 |

| 200 `Response`, 본문 `cancel()`이 reject | 곧바로 `HTTP_OBSERVED` 200 |
| 200 `Response`, 본문은 `highWaterMark: 0`인 `ReadableStream` | `pull` 0번, `cancel` 1번 |
| 429 `Response`에 위 `Retry-After` 표의 값을 하나씩 | 표의 값 |

가짜 전송부 시험은 호출 전후 `process.getActiveResourcesInfo()`의 `Timeout` 수가 같은지 본다. 실제 네트워크 경로의 제한 시간은 가짜 수신기로, abort를 무시하는 전송부는 가짜 전송부로 확인한다. 한쪽으로 다른 쪽을 갈음하지 않는다.
10초를 실제로 기다리는 시험 셋(응답하지 않음, 끝없는 pending, 끝없는 `cancel`)만 그 시험 안에서 timeout을 20000ms로 준다. 제품 10000ms, 전역 기본 timeout, worker 설정은 바꾸지 않고 시험을 skip하지 않는다. 설정 파일도 고치지 않는다.
