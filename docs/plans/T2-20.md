# T2-20 D6 턴 알림: 디스코드 웹훅

> 대기열: T2-20 · AC: AC-M2-18 · 구현: Codex · 리뷰: Claude
> 선행: T2-09 · 관련: [차별화 D6](../product/differentiation.md#d6-턴-알림-기본-포함), FR-DIF-06a

## 계획 (Claude)

### 목표

디스코드 웹훅을 등록한 사용자는 예턴 실패, 공격받음, 외교 제안 도착, 예턴 남은 칸 3칸 이하를 1분 안에 받는다.
같은 일로 두 번 보내지 않고 웹훅이 실패해도 게임 진행은 멈추지 않는다 (AC-M2-18).

### 범위

- `NotificationTarget(userId, kind: DISCORD, endpoint, events[], verifiedAt)`, `NotificationOutbox`
- engine: 해당 사건을 턴 트랜잭션 안에서 outbox에 기록
- server의 발송 작업: outbox를 읽어 웹훅 POST, 성공 표시, 재시도
- `apps/server/src/routers/notification.ts`

### 하지 않는 것

웹 푸시(M3), 이메일 알림, 디스코드 봇·OAuth.

### 결정

| 항목 | 결정 |
| ---- | ---- |
| 기록 | **outbox 방식**: 사건은 게임 트랜잭션 안에서 `NotificationOutbox(id, userId, event, payload, dedupeKey)`로 남긴다. 발송은 트랜잭션 밖 |
| 중복 기록 | `dedupeKey`(예: `turn-fail:<worldId>:<generalId>:<tick>`) 고유 제약. 같은 사건은 outbox에 한 번만 남는다. 외부 전송 중복은 이 제약으로 막지 못하고 아래 [외부 전송 정책](#외부-전송-정책-검토-r63-4-2026-10-21-추가)이 정한다 |
| 발송 | 10초마다 미발송 건을 묶어 보냄. 재시도는 외부 전송 정책의 재시도 대상만, 1·5·15분 뒤 포기 기록. 웹훅이 404·401이면 대상 비활성화 |
| 내용 | 월드 이름, 게임 연월, 한 줄 설명, 화면 링크. **다른 국가의 비밀 정보는 넣지 않는다** |
| 등록 확인 | 웹훅 등록 시 시험 메시지를 보내고 성공해야 `verifiedAt` |
| 주소 검사 | `https://discord.com/api/webhooks/` 또는 `https://discordapp.com/api/webhooks/`로 시작하는 주소만 (임의 주소로 서버가 요청을 보내지 않게) |
| 비밀 | 웹훅 주소는 비밀값처럼 다룬다. 로그에 남기지 않고 화면에는 끝 4자리만 |

### API 계약

```ts
notification.get() → NotificationResponse
notification.setDiscord({ url, events })     // 시험 메시지 발송 후 저장
notification.setEvents({ events })           // 주소를 다시 넣지 않고 알림 종류만 바꾼다
notification.removeDiscord()
```

모두 계정 단위다. 행위자는 세션의 사용자이고 입력에 사용자 ID를 받지 않는다. 무인증은 `UNAUTHORIZED`.

v1에는 플레이어용 알림이 없었고 운영 경보만 같은 디스코드 웹훅으로 보냈다(v1 `tools/ops/daemon_health_alert.sh:185-188`: 제한 시간 10초, 429·5xx 재시도). 거기서 두 가지를 가져온다.

- 웹훅 요청 하나의 제한 시간은 10초다. 429는 `Retry-After`를 지킨 뒤 재시도 일정에 넣는다.
- 디스코드는 빈 본문을 400으로 거절한다(v1 같은 파일 `:145-148`). 시험 메시지와 알림 모두 `content`를 반드시 채운다.

### 외부 전송 정책 (검토 R63-4, 2026-10-21 추가)

`dedupeKey`는 사건을 두 번 기록하지 않게 할 뿐이다. 웹훅 POST가 디스코드에 닿은 뒤 응답을 잃으면(제한 시간 초과, 연결 끊김, 발송 중 재시작)
서버는 보냈는지 알 수 없다. 이때 다시 보내면 같은 알림이 두 번 간다. 안 보내면 한 번도 안 갈 수 있다. 디스코드 웹훅에 중복을 막는 키가 있는지는
확인하지 않았으므로 이 계획은 그런 키에 기대지 않는다.

> **사용자 결정 필요**: 결과를 모르는 전송을 다시 보낼지 정한다. AC-M2-18의 "같은 일로 두 번 보내지 않고"를 그대로 지키는 초안은 최대 1회다.
> 최소 1회로 바꾸면 드물게 같은 알림이 두 번 갈 수 있어 AC 문장도 고쳐야 한다. 결정이 바뀌면 아래 표의 `UNKNOWN` 행만 재시도로 바꾼다.

초안(최대 1회)의 발송 상태:

| 상태 | 언제 | 다음 |
| ---- | ---- | ---- |
| `PENDING` | 엔진이 사건을 기록함 | 발송 작업이 집는다 |
| `SENDING` | 발송 작업이 POST 직전에 시도 횟수와 집은 시각을 커밋함 | POST 결과에 따라 아래로 |
| `SENT` | 2xx 응답을 받음 | 끝 |
| `RETRY` | 요청이 나가기 전 실패(주소 해석·연결 거부·TLS 실패), 또는 응답을 받은 429·5xx | 재시도 일정. 429는 `Retry-After`를 지킨다 |
| `UNKNOWN` | 요청을 보낸 뒤 제한 시간 10초 초과·연결 끊김, 또는 재시작 때 집은 지 1분 넘은 `SENDING` | 다시 보내지 않는다. 운영 로그에 건수만 남긴다 |
| `GAVE_UP` | 재시도 3번 실패, 400·401·404 | 끝. 401·404는 대상 비활성화 |

- 응답을 받은 5xx는 디스코드가 처리하지 않았다고 보고 재시도한다. 이 가정이 틀리면 그 경우만 중복이 생길 수 있다.
- 여러 발송 작업이 같은 건을 집지 않도록 `PENDING`·`RETRY` → `SENDING` 전환은 조건부 갱신 한 번으로 한다.
- 발송 상태는 게임 상태가 아니다. 재생과 상태 해시에 들어가지 않는다. 발송 실패가 게임 트랜잭션을 되돌리지 않는다.

### 화면(T2-21)이 기대하는 응답 모양

```ts
type NotificationEvent = 'turn.failed' | 'attacked' | 'diplomacy.offer' | 'turns.low';

type NotificationResponse = {
  discord: {
    last4: string;               // 웹훅 주소 끝 4자리. 주소 전체는 어떤 응답에도 싣지 않는다
    status: 'active' | 'disabled';
    disabledReason: 'DISCORD_GONE' | null; // 발송 중 404·401로 비활성화되면 'DISCORD_GONE'
    verifiedAt: string;          // 시험 메시지가 성공한 시각 (ISO). 저장된 대상은 모두 시험을 통과했다
    events: NotificationEvent[]; // 켠 종류. eventOptions 순서
  } | null;                      // 등록하지 않았거나 해제했으면 null
  eventOptions: { key: NotificationEvent; name: string }[];
  // 순서와 이름 고정: 예턴 실패, 공격받음, 외교 제안, 예턴 3칸 이하
};

// setDiscord·setEvents·removeDiscord 모두 성공하면 NotificationResponse를 돌려준다
// setDiscord 실패는 TRPCError이고, message는 화면에 그대로 보여 줄 쉬운 문장이다. 저장하지 않는다
//   BAD_REQUEST          디스코드 웹훅 주소가 아님 (주소 검사). events는 비어 있어도 된다 (아무것도 보내지 않음)
//   PRECONDITION_FAILED  시험 메시지 실패. 디스코드 응답에 따라
//                        401·404 → "웹훅을 찾을 수 없습니다. 디스코드에서 웹훅 주소를 다시 복사해 주세요."
//                        429     → "디스코드가 요청을 잠시 막았습니다. 조금 뒤 다시 시도해 주세요."
//                        제한 시간 초과·5xx → "디스코드가 응답하지 않습니다. 잠시 뒤 다시 시도해 주세요."
// setEvents는 등록된 대상이 없으면 PRECONDITION_FAILED
```

주소를 다시 입력해 `setDiscord`를 부르면 비활성화된 대상도 새로 시험하고 `active`로 돌아온다.

| T2-21 화면 요소 | 쓰는 응답 |
| --------------- | --------- |
| 등록됨 (…ab12) | `discord.last4`, `status` |
| 비활성화 안내 (다시 등록해 달라는 문장) | `status: 'disabled'`, `disabledReason` |
| 시험 보내고 저장, 실패 이유 | `setDiscord`, `TRPCError.message` |
| 알림 종류 체크와 유지 | `eventOptions`, `discord.events`, `setEvents` |
| 해제 | `removeDiscord` → `discord: null` |
| 주소를 다시 보여 주지 않음 | 응답에 주소 전체가 없음 |

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 사건 4종 | 통합(가짜 웹훅 서버): 각 사건 → 1분 안에 1건 |
| 중복 기록 | 통합: 같은 사건 재처리(엔진 재시작) → outbox 1건, 가짜 웹훅 수신 1건 |
| 결과 모름 | 통합: 가짜 웹훅이 받은 뒤 응답을 12초 늦춤 → 수신 1건, 상태 `UNKNOWN`, 재시도 없음 |
| 발송 중 재시작 | 통합: POST 도중 발송 작업을 멈추고 다시 띄움 → `SENDING`이 `UNKNOWN`이 되고 다시 보내지 않음 |
| 동시 발송 | 통합: 발송 작업 두 개가 같은 미발송 건을 동시에 집음 → POST 1번 |
| 실패 격리 | 통합: 웹훅 서버가 500 → 게임 턴은 정상 진행, `RETRY` 뒤 다음 시도에서 `SENT`. 연결 거부도 같은 경로 |
| 주소 검사 | 단위: 디스코드가 아닌 주소 거부 |
| 권한 | API: 무인증 `UNAUTHORIZED`, 다른 사용자의 대상은 읽기·바꾸기 불가, 어떤 응답·로그에도 주소 전체가 없음 |
| 비활성화 | 통합: 가짜 웹훅이 404 → `status: 'disabled'`, 주소를 다시 넣으면 `active` |
| 실제 1회 | 수동: 실제 디스코드 채널로 사건 1건 |
