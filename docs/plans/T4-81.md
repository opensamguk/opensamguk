# T4-81 편집 캔버스의 관리자 콘솔 연결

> 대기열: T4-81 · AC: AC-P2-27 (지도 편집의 콘솔·초안·게시 화면) · 구현: Claude · 리뷰: Codex

> 선행: [T4-80](./T4-80.md) 편집 캔버스, T4-76 형식·검증기, T4-78 초안·게시 API, T4-88 캔버스의 rules 맞추기, T3-05 관리자·감사, [T3-06](./T3-06.md) 관리자 콘솔 (조율 결정 R17) · 이어지는 작업: [T4-87](./T4-87.md) · 기준: main `3e5b52a`

## 계획 (Claude)

### 목표

운영자가 관리자 콘솔에서 지도 판을 복제해 T4-80 캔버스로 고치고 초안으로 저장한 뒤 검증을 통과한 판만 게시한다. 다른 운영자가 먼저 저장했으면 늦은 저장이 거부되고 화면이 그 사실과 다음 할 일을 보여 준다. 권한 없는 계정은 편집 화면에 들어오지 못하고 API를 직접 불러도 거부된다.

AC-P2-27 전체가 아니다. 지도 밖 자원의 표 편집은 [T4-87](./T4-87.md), 서버 권한·감사·판 불변은 T4-78, 새 판으로 월드 만들기는 T4-79 몫이다. 이 작업이 끝나도 AC-P2-27을 완료로 세지 않는다.

계약의 정본은 같은 날 쓴 T4-78 상세 계획 2.4~2.8절(절차·결과·오류·감사)과 T4-76 상세 계획 3.2절(검증 결과 모양)이다. 아래 절은 그 계약을 화면에 옮긴 것이고 두 계획과 다르면 두 계획을 따른다.

### main 기준 사실 (`3e5b52a`)

- 편집기는 `MapEditorPage`(`apps/web/src/mapEditor/MapEditorPage.tsx:23`)가 파일 선택으로 지도를 받아 내부 `Editor`(`:102`)에 넘긴다. `Editor`는 `useReducer(editorReducer, initial, initialEditor)`(`:103`)로 상태를 쥐고 밖으로 내보내는 값이 없다. 서버 판을 넣고 바뀐 지도를 읽으려면 `Editor`에 알림 하나를 더해야 한다.
- 편집 상태는 `map`·`past`·`future`·`selection`이고(`apps/web/src/mapEditor/editor.ts:15-20`) 기록은 200개까지다(`:42`). 저장 기준을 따로 두지 않는다.
- 검증은 매 편집 뒤 `validateMap(map)`(`MapEditorPage.tsx:110`)을 다시 돌린다. 지금은 화면 안 임시 함수(`apps/web/src/mapEditor/validate.ts:35`)이고 T4-88이 rules 검증기로 바꾼다. 오류가 있어도 내려받기는 막지 않고 안내만 한다(`MapEditorPage.tsx:213-216`).
- 읽기는 `parseMapJson`(`apps/web/src/mapEditor/contract.ts:149`), 쓰기는 키 순서를 고정한 `serializeMap`(`:188`)이다.
- `/dev/map-editor`는 개발 모드에서만 경로 정의를 만든다(`apps/web/src/router.tsx:250-258`, `:287`).
- 서버 오류 형식은 모든 오류의 `data.reason`을 `null`로 지운다(`apps/server/src/trpc.ts:9`). 그래서 T4-78은 늦은 저장과 검증 실패를 오류가 아니라 결과 값으로 돌려준다.
- 변경 요청은 사용자당 1분 120번이고 넘으면 `TOO_MANY_REQUESTS`와 `Retry-After`다(`apps/server/src/trpc.ts:18-25`).
- 저장하지 않은 편집을 탭에 두는 선례는 예턴 편집이다(`apps/web/src/turns/useTurnDraft.ts:37`, `:113`).
- 카탈로그 내용은 `jsonb`라 DB에서 읽으면 키 순서가 바뀐다. 해시는 키를 정렬한 정규 JSON으로 계산한다(T4-77 상세 계획, `packages/shared/src/node/hashState.ts:3-24`). 화면도 내용이 같은지 볼 때 키를 정렬해 비교한다.

### 접근

1. `Editor`를 내보낸다. 받는 값에 `onMapChange(map)`, `readOnly`, `toolbarStart`(위쪽 띠 자리)를 더한다. `readOnly`면 도구는 선택과 화면 배율만 남고 도시 칸·선 칸 입력이 꺼진다. `/dev/map-editor`는 세 값을 넘기지 않아 지금과 같다.
2. 공통부를 만든다. 주소 풀기, 목록 화면, 초안 상태(`draft.ts`의 순수 함수 + `useResourceDraft` 훅), 위쪽 띠, 게시·버리기 확인, 늦은 저장 안내, 서버 검증 목록. 순수 함수는 단위 시험으로 덮는다.
3. `MapDraftEditor`가 `resourceAdmin.get({ id })`로 판을 받아 `parseMapJson`으로 읽고 `Editor`에 넣는다. 바뀐 지도는 `serializeMap`으로 바꿔 초안 공통부에 넘긴다. 저장할 내용은 이 글자열을 다시 읽은 JSON이다.
4. 경로와 가드를 T3-06 관리자 경로 아래에 단다. 화면 코드는 관리자 청크 안에서도 다시 나눠 편집 화면에 들어갈 때만 캔버스를 불러온다.
5. E2E를 쓴다. 관리자 계정 준비는 T3-06의 `e2e/adminSetup.ts`를 쓴다.

### 경로와 가드

| 경로 | 화면 |
| ---- | ---- |
| `/admin/resources?kind=map` | 자원 판 목록. `kind`가 없으면 `map` |
| `/admin/resources/map/$name/$version` | 지도 판 편집. 게시한 판이면 읽기 전용 |

- 카탈로그 행은 UUID `id`와 `(kind, name, version)` 유일 제약을 함께 가진다. API와 감사는 `id`를 쓰고 화면 주소는 종류·이름·판 번호를 쓴다(조율 결정 R1). 주소에 들어오면 `resourceAdmin.list({ kind, name })`로 그 이름의 판을 받아 판 번호가 같은 행의 `id`를 찾고 `get({ id })`를 부른다. 없으면 없는 판 안내와 목록으로 가는 링크를 보인다. 지도 `che`와 시나리오 `che`는 `kind`로 갈린다.
- 화면 문구와 목록의 판 이름은 키 정규형으로 쓴다. 1판은 이름만(`che`), 2판부터 `<이름>@<판 번호>`(`che@2`)다(조율 결정 R4). 주소는 `$version`을 늘 숫자로 받아 `/admin/resources/map/che/1`도 같은 판이다.
- 이름 규칙은 T4-78 2.1(`^[a-zA-Z0-9_-]{1,40}$`)이 정본이다(조율 결정 R5). 주소에 그대로 넣는다.
- `$kind` 칸은 `map`·`scenario`·`unit-set`·`stat-rules`·`portrait-map`이다. 서버 종류 이름 `MAP`·`SCENARIO`·`UNIT_SET`·`STAT_RULES`·`PORTRAIT_MAP`과 일대일이다. 모르는 값이면 없는 주소 화면이다.
- 가드는 T3-06의 `/admin` 가드를 그대로 탄다. 무인증이면 로그인 화면(`next` 유지), 관리자가 아니면 404와 같은 화면이다. 이 작업이 가드를 따로 만들지 않는다.
- 자원 편집 권한을 관리자 일부에게만 주기로 정해지면(U-81-1) 목록은 보이되 복제·저장·게시·버리기가 점선이 되고 누르면 자원 편집 권한이 없다는 이유를 보인다. 서버가 `FORBIDDEN`을 주면 같은 상태로 바꾼다. 정해지기 전에는 관리자 전원이 편집한다(T4-78 2.3).
- 콘솔 메뉴에 자원 한 줄을 더한다. 위치는 T3-06이 만든 관리자 메뉴의 끝이다.

### 자원 판 목록 (공통)

```text
┌ 자원 판 ─ 지도 · 시나리오 · 병종 · 능력치 규칙 · 초상 대응표 (탭) ──────────────────────────────┐
│ 판      상태  해시      만든 사람  고친 시각         게시한 사람  게시 시각         [동작]         │
│ che@2   초안  9b07d1aa  a1b2c3d4  2026-10-24 14:02  -           -                 열기            │
│ che     게시  3fa9c2e1  초기화     2026-10-23 10:00  초기화       2026-10-23 10:00  열기 복제       │
│ [더 보기]                                                                                       │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- 탭은 `role="tablist"`이고 고른 탭이 주소 `kind`에 남는다. 목록은 `resourceAdmin.list({ kind, cursor })`이고 서버 순서(이름 오름차순, 판 번호 내림차순, 한 번에 50개)를 그대로 쓴다. `next`가 있으면 [더 보기]로 이어 받는다(조율 결정 R14).
- 상태는 `Tag`로 글자와 색을 함께 쓴다. 초안, 게시 둘이다.
- 해시는 초안에도 있다(조율 결정 R2). 앞 8자를 보이고 `title`에 전체를 둔다.
- 사람 칸은 `createdBy`·`updatedBy`·`publishedBy`다(조율 결정 R2). 응답에 표시 이름이 없으므로 사용자 UUID 앞 8자를 보이고 `title`에 전체를 둔다. `null`이면 초기화(초기화 SQL이 넣은 내장 판)다. 복제 원본 칸은 응답에 없어 두지 않는다.
- 시각은 Asia/Seoul로 보이고 `title`에 ISO 원문을 둔다(T3-06 문구와 표시).
- [복제]는 게시한 판에만 있다. 초안은 복제 원본이 될 수 없다(T4-78 2.4). 누르면 대화 상자에서 같은 이름의 다음 판(기본) 또는 새 이름을 고른다. 새 이름은 보내기 전에 이름 규칙을 칸 아래에 보이고 최종 판단은 서버다. 보내는 값은 `clone({ sourceId, name? })`이고 멱등 키는 없다(조율 결정 R14). 같은 이름에 초안이 하나뿐이라 다시 보내도 초안이 하나라서다.
- 복제 결과가 `ok`면 새 초안의 편집 화면으로 간다. `DRAFT_EXISTS`면 이 이름에 이미 초안이 있다는 안내와 [그 초안 열기]를 보인다(`draftId`로 `get`을 불러 판 번호를 얻는다). `NAME_TAKEN`이면 대화 상자의 이름 칸 아래에 이미 있는 이름이라고 보이고 창을 닫지 않는다.
- 빈 종류는 `EmptyState`, 목록을 못 받으면 `ErrorState`와 다시 시도다.

```text
┌ 위쪽 띠: che@2 · 초안 · revision 5 · 마지막 저장 14:02 · 저장하지 않은 편집 3 · 오류 1 · 경고 0 ┐
│ [초안 저장] [게시] [초안 버리기] [v2 JSON 내려받기] [밑그림 PNG 내려받기] [지도 파일 불러오기]      │
├ T4-80 편집기 (도구 · 캔버스 · 고른 것 · 검증) ──────────────────────────────────────────────────┤
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- 판을 받으면 `parseMapJson`으로 읽는다. 초안과 게시 판은 v2뿐이라(조율 결정 R8) 읽지 못하는 일은 형식이 어긋난 경우뿐이다. 그때는 편집기를 띄우지 않고 이유와 [JSON 내려받기]만 둔다.
- 저장하지 않은 편집 수는 저장 기준 지도와 지금 지도를 키를 정렬한 JSON으로 비교해 정한다. 같으면 0, 다르면 저장 뒤 쌓인 편집 기록 수다. 되돌리기로 저장 상태로 돌아오면 0이 된다.
- [지도 파일 불러오기]는 T4-80의 파일 불러오기를 이 초안 위에 얹는다. 불러온 지도는 편집 한 번으로 쌓이고 되돌릴 수 있다. 기록을 비우지 않는다는 점이 `/dev/map-editor`와 다르다. 늦은 저장 뒤 내 편집을 다시 얹을 때 쓴다(아래).
- 게시한 판은 읽기 전용이다. 위쪽 띠에 게시한 판은 고칠 수 없으니 복제해 새 초안을 만든다는 안내와 [이 판 복제]를 둔다. 내려받기 두 개는 그대로 쓴다. 밑그림 PNG는 게시한 판에서 내려받는 것이 T4-83의 입력이다.
- 검증은 T4-88이 바꾼 캔버스가 매 편집 뒤 T4-76 지도 검증기를 돌린다. 결과 모양은 T4-76의 `{ code, severity, message, target, params, resource? }` 그대로이고 게시 가능 판정은 보고서의 `ok`(심각도 `error`만 센다)다. 경고는 게시를 막지 않고 위쪽 띠와 목록에 경고로 따로 센다(조율 결정 R11).
- 지도 게시 때 시나리오 참조 검사는 서버가 한다(조율 결정 R12). 화면은 서버가 넘기는 것과 같은 범위의 게시 시나리오를 `resourceAdmin.list`·`get`으로 받아 검증기의 `scenarios`에 넣고 미리 보인다. 그 항목은 `resource`가 달려 있으므로 목록에 어느 시나리오 판의 항목인지 함께 적는다. 범위의 정본은 T4-78이다.
- `get`과 `save`가 돌려준 `issues`는 서버 기준 결과다. 화면 검증과 다르면 목록 머리에 서버 검증 결과라고 적고 서버 결과를 쓴다.

### 초안 저장

- [초안 저장]은 저장하지 않은 편집이 있을 때만 켜진다. 없으면 점선이고 누르면 저장할 편집이 없다는 이유를 보인다. 검증 오류가 있어도 저장한다. 초안은 고치는 중인 판이다.
- 보내는 값은 `resourceAdmin.save({ id, revision: 기준 revision, content })`다. `ok`면 기준 revision과 저장 기준 지도를 `meta`로 바꾸고 편집 수를 0으로 한다. 되돌리기 기록은 남긴다. 저장 뒤 되돌리면 다시 저장할 편집이 생긴다.
- 저장 중에는 버튼이 저장 중으로 바뀌고 다시 누를 수 없다. 편집은 계속할 수 있다. 저장 중에 생긴 편집은 성공 뒤에도 저장하지 않은 편집으로 남는다.
- 응답을 받지 못해 같은 내용을 다시 보냈는데 `STALE`이 오면 `get`으로 서버 내용을 받아 보낸 내용과 키를 정렬해 비교한다. 같으면 첫 요청이 이미 들어간 것이므로 성공으로 본다(T4-78 2.5의 재시도 규칙).
- 저장하지 않은 편집은 탭 `sessionStorage`에 둔다. 키는 사용자 ID, 행 `id`, 기준 revision이다. 새로 고치거나 다시 로그인해 같은 판을 열면 서버 판의 revision이 키와 같을 때만 이어서 편집할지 묻는다. 다르면 아래 늦은 저장 안내로 간다. 예턴 편집 초안(`useTurnDraft.ts:37`)과 같은 방식이다.
- 저장하지 않은 편집이 있으면 다른 콘솔 화면으로 갈 때 묻고(TanStack Router 이동 막기) 창을 닫을 때 브라우저 경고를 띄운다.
- 로그인이 풀리면 [다시 로그인] 링크를 보이고 탭 초안은 남긴다. `TOO_MANY_REQUESTS`면 `Retry-After`의 남은 시간을 보인다(T3-06과 같다). `FORBIDDEN`이면 권한 없음 상태로 바꾸고 탭 초안은 남긴다.

### 늦은 저장 거부

두 운영자가 같은 초안을 고치다 늦게 저장한 쪽이 거부된다(C-M4). 화면은 합치지 않는다.

```text
┌ 다른 곳에서 이 초안이 먼저 저장되었습니다. 내 편집 3건은 저장되지 않았습니다.          ┐
│ 서버 판: revision 6 · 14:05 저장 · 저장한 사람 c3d4e5f6                                 │
│ [내 편집 JSON 내려받기] [최신 초안 불러오기] [닫기]                                       │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- `save`·`publish`·`discard`가 `{ ok: false, reason: 'STALE', meta }`를 돌려주면 이 안내를 띄운다(조율 결정 R14). 안내는 `role="alert"`로 위쪽 띠 바로 아래에 고정한다. 보이는 값은 `meta.revision`·`meta.updatedAt`과 `meta.updatedBy` 앞 8자다.
- [내 편집 JSON 내려받기]는 지금 화면의 지도를 `serializeMap`으로 내려받는다. 파일 이름에 판 키와 기준 revision을 넣는다.
- [최신 초안 불러오기]는 내 편집을 버린다는 확인을 거친 뒤 `get`으로 서버 판을 받아 편집기를 다시 만든다. 되돌리기 기록과 탭 초안도 지운다.
- [닫기]는 안내만 접는다. 편집은 이어서 할 수 있지만 [초안 저장]은 점선이 되고 누르면 최신 초안을 먼저 불러와야 한다는 이유를 보인다. 같은 기준 revision으로 다시 보내지 않는다.
- 내 편집을 살리려면 JSON을 내려받고 최신 초안을 불러온 뒤 [지도 파일 불러오기]로 그 파일을 얹고 저장한다. 다른 운영자의 편집을 덮는다는 사실을 운영자가 알고 고르는 길이다. 덮어쓰기 버튼은 따로 두지 않는다(U-81-2). 서버에도 덮어쓰기 절차가 없다(T4-78 8절).
- 결과가 `PUBLISHED`면(다른 운영자가 저장 뒤 게시했거나 같은 판이 이미 게시됨) 안내 문장을 이 초안은 이미 게시되어 고칠 수 없다로 바꾸고 [최신 초안 불러오기] 대신 [이 판 복제]를 둔다. [이 판 복제]는 그 게시 판의 `id`로 `clone`을 부른다.
- 행이 사라졌으면(다른 운영자가 초안을 버림, `NOT_FOUND`) 이 초안은 버려졌다는 안내와 [내 편집 JSON 내려받기], 목록으로 가는 링크를 둔다.

### 게시

- [게시]는 저장하지 않은 편집이 없고 검증 보고서의 `ok`가 참일 때만 켜진다. 아니면 점선이고 누르면 먼저 초안을 저장해야 한다, 또는 검증 오류 N건을 고쳐야 한다는 이유를 보인다. 경고만 있으면 켜진다.
- 누르면 확인 대화 상자를 연다. 판 키, revision, 오류·경고 수, 그리고 게시한 판은 고칠 수 없고 새 월드를 만들 때 고를 수 있으며 진행 중인 월드는 바뀌지 않는다는 문장을 적는다. 사유 입력 칸이 있고 칸 아래에 개인정보를 쓰지 말라는 안내를 둔다(T3-06 제재 사유와 같다). 사유는 앞뒤 공백을 빼고 1~200자다. 필수인지는 U-T78-3이고 정해지기 전 기본은 필수다. 필수면 빈 칸일 때 확인 버튼이 점선이다. 확인 버튼 이름은 게시다.
- 보내는 값은 `resourceAdmin.publish({ id, revision, reason })`이다. `ok`면 읽기 전용으로 바꾸고 해시와 게시 시각을 보인다.
- `INVALID`면 서버가 준 `issues`를 검증 목록 자리에 보이고 목록 머리에 서버 검증 결과라고 적는다. 화면 검증과 서버 검증이 다르면 서버가 기준이다. 목록 항목을 누르면 캔버스가 대상을 고른다.
- `STALE`·`PUBLISHED`는 늦은 저장 안내와 같은 흐름이다.
- 응답을 못 받아 다시 보낼 때는 같은 `{ id, revision, reason }`을 보낸다. 이미 게시된 같은 revision이면 서버가 처음 결과와 같은 `ok`를 돌려준다(T4-78 2.4).

### 초안 버리기

- 한 이름에 초안은 하나뿐이다(T4-78 2.1). 남은 초안이 있으면 같은 이름을 다시 복제할 수 없으므로 [초안 버리기]를 둔다.
- 누르면 확인 대화 상자에서 이 초안의 편집이 모두 사라지고 되돌릴 수 없다는 문장과 선택 사유 칸(1~200자, 개인정보 안내 같음)을 보인다. 확인 버튼 이름은 초안 버리기다.
- 보내는 값은 `resourceAdmin.discard({ id, revision, reason? })`다. `ok`면 탭 초안을 지우고 목록으로 간다. `STALE`·`PUBLISHED`는 늦은 저장 안내와 같다.
- 게시한 판에는 버튼이 없다.

### 감사 로그

복제·저장·버리기·게시는 서버가 같은 트랜잭션에서 감사 행을 쓴다. `action`은 T4-78 2.8의 `resource.draft.create`, `resource.draft.save`, `resource.draft.discard`, `resource.publish`다(조율 결정 R14). 화면은 이 행을 따로 쓰지 않고 T3-06 감사 로그 화면(`/admin/audit`)에서 `resource.` 앞부분으로 걸러 본다.

### 문구

- 버튼은 동사로 쓴다. 초안 저장, 게시, 초안 버리기, 이 판 복제, 최신 초안 불러오기.
- 상태는 서버 값과 일대일이다. DRAFT 초안, PUBLISHED 게시. 심각도는 오류와 경고이고 색만으로 가르지 않는다.
- 오류와 안내는 [글쓰기 규칙](../writing-style.md)을 따른다.

### 상대 영역에 필요한 것

#### T4-78 (Codex) 초안·게시 API

절차·입력·결과·오류·감사는 T4-78 상세 계획 2.4~2.8이 정본이다(조율 결정 R14). 이 화면이 쓰는 것은 `resourceAdmin.list({ kind?, name?, status?, cursor? })`, `get({ id })`, `clone({ sourceId, name? })`, `save({ id, revision, content, mapKey? })`, `publish({ id, revision, reason })`, `discard({ id, revision, reason? })`와 결과의 `reason` 다섯 가지(`STALE`·`PUBLISHED`·`INVALID`·`DRAFT_EXISTS`·`NAME_TAKEN`)다. 해시 칸 이름은 조율 결정 R2의 `hash`를 따른다. 화면이 더 바라는 것은 아래다.

- 지도 게시 때 서버가 시나리오 참조 검사에 넘기는 시나리오의 범위를 2.7에 한 문장으로 적어 달라(조율 결정 R12). 화면은 같은 범위를 `list`로 골라 미리 보인다.
- `list`에 `name`만 주고 종류 없이 부르는 경우가 화면에는 없다. 주소 풀기는 늘 `kind`와 `name`을 함께 준다.

#### T4-76 (Codex) 형식·검증기

- 결과 모양 `{ code, severity, message, target, params, resource? }`와 `ok`를 그대로 쓴다(조율 결정 R11). 화면은 `target`의 `city`·`terrain`·`path`를 캔버스 대상으로 바꾸는 일을 T4-88에 맡긴다.
- 패키지 경계 예외 E3를 `apps/web/src/mapEditor/**`와 함께 `apps/web/src/admin/resources/**`, `apps/web/src/admin/maps/**`에도 열어 달라. T4-87이 종류별 검증기를 쓴다.

#### T4-88 (Claude) 캔버스의 rules 맞추기

- `Editor`가 rules 검증 보고서를 받아 오류·경고를 나눠 보이게 해 달라. 또 바깥에서 받은 서버 `issues`로 목록을 바꿔 끼울 수 있게 해 달라. 이 작업은 그 자리에 서버 결과를 넣기만 한다.

#### T3-05·T3-06 (가정, 조율 결정 R19)

- `adminProcedure`, `admin.whoami()`, `AuditLog`, `admin.audit.list`, `/admin` 가드, `e2e/adminSetup.ts`가 2026-10-23 계획 이름 그대로 들어온다고 본다.
- 관리자 경로를 어느 파일에 두는지와 메뉴 위치. 이 작업은 그 파일에 경로 두 줄과 메뉴 한 줄만 더한다.
- `e2e/adminSetup.ts`가 관리자 계정을 둘 이상 만들 수 있어야 한다.
