## 계획 (Claude)

### 목표

로그인한 사용자가 월드 ID 하나로 그 월드가 실제로 쓰는 병종표와 기본 능력치 규칙을 받는다. 응답의 병종표는 그 월드의 출병 계산(`apps/engine/src/turnLoop.ts:178`)과 사전 검사(`apps/server/src/routers/turns.ts:115`)가 읽는 값과 같고 능력치 규칙은 장수 생성 검사(`apps/server/src/routers/general.ts:39`)가 읽는 값과 같다. 다른 월드의 값이 섞이지 않는다.

이 작업이 끝나도 AC-P2-26을 완료로 세지 않는다. 화면이 번들 JSON 없이 이 응답을 쓰는 것은 T4-86, JSON 삭제와 초기화 SQL·재생 해시 대조는 T4-77 몫이다.

### API 계약

```ts
// apps/server/src/routers/resources.ts
resources.worldRules: protectedProcedure
  .input(worldInput) // { worldId: string(uuid) }, 다른 키가 있으면 BAD_REQUEST
  .query(...): Promise<WorldRules>

type WorldRules = {
  unitSetKey: string;        // World.unitSetKey 그대로
  unitSet: UnitSetResource;  // unitSetSchema.parse(World.unitSet)
  statRules: { total: number; min: number; max: number; count: 3 | 5 };
};
```

- 병종 형식은 `@opensamguk/rules`의 `UnitSetResource`다. 능력치 규칙은 저장값을 먼저 검사한 뒤 같은 트랜잭션의 `ruleFeatures`에서 3·5능력치 구분을 더한다. `general.mine`과 같은 기준이며 계정별 유산 자료는 싣지 않는다. 화면은 `AppRouter` 타입으로만 받는다(`import type`). 새 공유 타입 파일을 만들지 않는다.
- 응답 키는 위 세 개뿐이다. 월드 행의 `seed`, `replayOrigin`, `preset`, `initialStateHash`, `commandMeta` 같은 열은 넣지 않는다. 특히 `seed`는 월드 난수의 출발점이라 새면 전투 결과를 미리 맞힐 수 있다.
- 월드 상태(`PREOPEN`·`RUNNING`·`PAUSED`·`ENDED`)와 관계없이 같은 값을 준다. 이 열은 월드를 만든 뒤 바뀌지 않는다.
- 서버 캐시는 두지 않는다. 화면은 같은 월드의 값을 다시 받을 까닭이 없으므로 화면 쪽에서 오래 둔다(T4-86).

| 경우 | 오류 | 문구 |
| ---- | ---- | ---- |
| 세션 없음, 만료, 비활성·전역 제재 계정 | `UNAUTHORIZED` | 로그인이 필요합니다. |
| `worldId`가 uuid가 아님, 빠짐, 다른 키(`userId`·`generalId` 포함)가 있음 | `BAD_REQUEST` | zod 기본 문구 |
| 그 ID의 월드가 없음 | `NOT_FOUND` | 월드를 찾을 수 없습니다. (`queries.ts:39`) |
| 저장된 `unitSet`·`statRules`가 스키마를 지나지 못함 | `INTERNAL_SERVER_ERROR` | 요청을 처리하지 못했습니다. 검사 실패 내용과 저장값을 응답에 싣지 않는다 |

### 권한

- 로그인한 사용자라면 그 월드에 장수가 없어도 읽는다. `world.summary`·`world.map`과 같은 범위다(`exemptions.ts:43-49`). 병종표와 능력치 규칙은 그 월드의 모든 플레이어에게 같은 규칙 자료이고 장수·국가별 비공개 값이 없다. 장수를 만들기 전의 화면(장수 생성)도 능력치 규칙이 필요하다.
- 면제 문구: `{ path: 'resources.worldRules', category: 'otherUser', reason: '인증 사용자 공통 월드 규칙(병종표·능력치 규칙)이며 타인 소유 자원이 없다. ID 주입은 BAD_REQUEST로 거부한다.' }`
- 행위자 ID는 받지 않는다. 입력은 `worldId` 하나다.

### 접근

1. `routers/resources.ts`에 `resourcesRouter = router({ worldRules })`를 만든다. 본문은 `readWorld(ctx.db, input.worldId, (tx) => ...)` 안에서 `tx.world.findUniqueOrThrow({ where: { id }, select: { unitSetKey: true, unitSet: true, statRules: true } })`로 세 열만 읽는다. `readWorld`가 없는 월드를 `NOT_FOUND`로 바꾸고 같은 RepeatableRead 트랜잭션이라 두 번 읽는 사이에 지워져도 일관된다.
2. 값의 출처는 월드 행이고 자원 카탈로그가 아니다. 실제 출병과 사전 검사, 장수 생성 검사가 모두 이 열을 읽는다. 그래서 같은 열을 돌려주면 화면 값이 실제 월드 값과 같다는 것이 구조로 보장된다. 카탈로그에서 `unitSetKey`로 다시 찾으면 C-M1의 판 불변이 지켜지는 한 같은 값이 나오지만 키 해석(조율 결정 R4의 정규형, 1판은 `basic`이고 2판부터 `basic@2`)과 판 조회라는 두 번째 길이 생긴다. 이 선택 덕분에 T4-85 코드는 T4-77의 카탈로그 코드가 없어도 돈다(쟁점 Q2, R17로 채택). 응답의 `unitSetKey`는 월드 행 값을 그대로 옮기므로 R4 정규형이 무엇이든 이 작업은 키를 해석하지 않는다.
3. 읽은 값은 엔진 적재와 같은 식(`persistence.ts:128-129`)으로 `unitSetSchema.parse`와 `statRulesSchema.parse({ stat })`를 거쳐 응답한다. id 중복·기본 병종 존재 검사는 월드를 만들 때 했고 화면 Worker가 다시 하므로 여기서 더하지 않는다.
4. `router.ts`에 등록하고 `exemptions.ts`·`tools/authz.integration.test.ts`를 같은 PR에서 고친다 (명세 §7 C7).
5. 아래 시험을 쓴다. `pnpm check`와 `pnpm test:int`를 돌린다.
