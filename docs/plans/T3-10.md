# T3-10 반응형 375px

> 대기열: T3-10 · AC: AC-M3-08 · 구현: Claude · 리뷰: Codex
> 선행: M2 전체 (로비 T2-04, M2 화면 작업이 위쪽 띠와 메인에 더하는 것까지 끝난 뒤)

## 계획 (Claude)

### 목표

375px 폭에서 로비와 핵심 화면 6개를 가로 스크롤 없이 쓴다. 누르는 대상은 44px 이상이다 (AC-M3-08, NFR-07).

데스크톱 화면의 정보량과 조작은 그대로 둔다 (D-007). 좁은 화면에서도 같은 데이터, 같은 컨트롤, 같은 키보드 조작을 쓴다.

### 착수 조건과 승인

이 계획은 사용자가 검토한다. 검토가 끝나도 착수는 M2 관문이 모두 `완료`된 뒤다. M2 화면이 위쪽 띠·메인·표를 계속 바꾸므로 그 전에 고친 CSS는 다시 깨진다.

계획 검토, M2 선행, AC 판정, 공개 승인은 서로 다른 관문이다. 계획 PR이 합쳐져도 AC-M3-08은 미착수 상태 그대로다. 통과 표시는 구현 뒤 Codex 리뷰가 통과할 때만 붙는다. 공개 오픈 승인(T3-15)은 이 작업과 상관없이 사용자가 따로 한다.

아래 두 가지는 사용자 결정을 받아야 한다.

| 결정 | 기본안 | 거절하면 |
| ---- | ------ | -------- |
| 지도 도시 표시의 44px 예외 | 같은 화면에 44px짜리 도시 고르기 칸을 둔다. 지도 위 도시 표시는 그 동등 수단이 있으므로 크기 검사에서 뺀다 (WCAG 2.5.5의 동등 수단 예외) | 좁은 화면에서 지도 도시 표시를 누를 수 없게 하고 도시 고르기 칸만 남긴다 |
| 문장 속 링크의 44px 예외 | 기록 한 줄 안의 장수·도시 이름 링크처럼 문장 안에 든 링크는 크기 검사에서 뺀다 (WCAG 2.5.5의 문장 속 예외). M2 끝의 실제 화면에 이런 링크가 없으면 이 결정은 필요 없다 | 좁은 화면에서 문장 속 이름을 링크 아닌 글자로 두고 줄 끝에 44px 이동 버튼을 둔다 |

결정은 [결정 기록](../product/decisions.md)에 남긴 뒤 적용한다. 결정 전에는 거절안 기준으로 검사한다. AC 문장에 예외가 없으므로 기본안을 임의로 적용하지 않는다.

모든 게임 화면은 `GameLayout`을 함께 쓴다. 지금 코드에서 이미 보이는 문제는 이렇다.

- `GameLayout.module.css`의 격자가 왼쪽 열을 `--sidebar-width` 240px로 고정한다. 375px에서 본문은 135px만 남는다.
- 위쪽 띠는 한 줄 `flex`이고 줄바꿈이 없다. 월드·연월·다음 턴·메뉴 4개·로그아웃이 343px에 들어가지 않는다. M2에서 로비·국가·순위 메뉴, 안 읽음 배지, 연결 상태, 계정 메뉴가 더 붙는다.
- 메뉴 링크(`.navLink`)와 로그아웃, `DisabledReason`, 상태 화면의 다시 시도 버튼은 위아래 여백이 4px이라 높이가 30px 안팎이다.
- `--row-height` 28px 표에서 행 안의 링크·정렬 머리글은 44px이 안 된다.

이 목록은 코드를 읽고 낸 예상이다. 실제 측정은 착수 첫 단계에서 M2 완료 시점의 main으로 다시 한다 (접근 1).

로그인·가입 화면과 `/dev/ui`도 같은 검사를 돌린다. AC 판정 대상은 아니지만 공통 규칙이 함께 적용되므로 깨지면 이 작업에서 고친다. T3-03이 만드는 가입·재설정 화면은 T3-03이 맡는다.

- 대상 화면과 공통 부품(`apps/web/src/ui/*`)의 CSS 모듈. 마크업은 아래 결정에 적힌 곳만 고친다

- 채울 문서

`playwright.config.ts`는 고치지 않는다. 뷰포트는 spec 안의 `test.use`로 바꾼다. 꼭 새 project가 필요해지면 공통 설정 변경이므로 구현 기록에 이유를 쓰고 Codex 리뷰를 받는다.

### 하지 않는 것

- 햄버거 메뉴, 서랍, 아래쪽 탭 막대, 모바일 전용 주소·부품. 지금 화면을 좁은 폭에 맞게 접기만 한다.
- 표를 카드 목록으로 바꾸는 방식. 표 의미가 브라우저에 따라 사라지고 정보 밀도가 크게 준다.
- 좁은 화면에서 열이나 패널을 숨겨 정보를 빼는 것.
- 확대 막기(`maximum-scale`, `user-scalable=no`). 저시력 사용자가 확대를 못 하게 된다.
- 320px 폭과 400% 확대 기준, 실제 휴대폰·iOS Safari 시험. AC는 375px이다. 시험은 Playwright Chromium의 모바일 흉내(`isMobile`, `hasTouch`)이며 실제 기기가 아니다.
- PWA와 모바일 최적화 (Phase 3).
- 다크 모드 다듬기. `tokens.css` 주석과 UI 지침 §3이 이 일을 T3-10에 적어 두었지만 AC-M3-08에는 없다. 백로그로 옮길지 사용자에게 묻고 구현 때 두 곳의 표시를 결정에 맞게 고친다.
- 게임 규칙, API 계약, 화면 문구의 의미 변경. 승인을 기다리는 핵심 규칙 변경 10건도 이 작업에 넣지 않는다.
- 다른 T3 작업의 화면.

### 결정

좁은 화면 기준은 `max-width: 640px` 하나다. CSS 변수는 미디어 조건에 못 쓰므로 640을 상수로 쓰고 UI 지침 §5에 적는다. 641px 이상은 지금 데스크톱 배치를 그대로 쓴다.

공통 규칙은 이렇다.

- `tokens.css`에 `--tap-target: 44px`를 둔다. 좁은 화면에서 `button`, 메뉴 링크, 표 안 링크, `select`, `input`, `summary`, `[role=tab]`은 `min-height`와 `min-width`를 이 값으로 맞춘다. 체크 상자와 라디오는 감싼 `label`을 44px로 키운다.
- 좁은 화면의 `input`, `select`, `textarea` 글자는 16px(`--text-lg`)이다. iOS Safari는 16px보다 작은 입력 칸에 초점이 가면 화면을 확대해 가로 스크롤을 만든다.
- 격자·flex 자식에는 `min-width: 0`을 둔다. 글자 칸은 줄바꿈을 허용한다. 숫자 칸만 줄바꿈 금지를 유지한다.
- `html`, `body`, 화면 바깥 틀에 `overflow-x: hidden`을 쓰지 않는다. 넘치는 내용을 잘라 숨길 뿐 고치지 못한다. 검사도 이를 실패로 잡는다.
- 화면 안 가로 스크롤 상자(`overflow-x: auto`)도 쓰지 않는다. 표를 옆으로 밀어 봐야 한다면 AC 문장(가로 스크롤 없이 쓴다)에 맞지 않는다.
- 좁은 화면에서 DOM 순서와 보이는 순서를 같게 둔다. `order`, `*-reverse`, DOM과 다른 `grid-template-areas`를 쓰지 않는다. 키보드 이동 순서와 화면 낭독 순서가 눈에 보이는 순서와 어긋나지 않게 한다.
- 고정 머리글이 있는 표는 행에 `scroll-margin-top`을 두어 초점 간 행이 머리글 밑에 가려지지 않게 한다.
- 641px 이상은 데스크톱 배치이고 크기를 바꾸지 않는다. 표 행 28px, 왼쪽 열 240px, 위쪽 띠 44px, 메인 3열을 유지한다. 641~1023px에서 넘치는 곳은 이 크기를 건드리지 않고 줄바꿈과 `min-width: 0`으로만 고친다.

`GameLayout`은 좁은 화면에서 한 열이 된다. 위쪽 띠는 두 줄로 나뉜다. 첫 줄에 월드·연월·다음 턴, 둘째 줄에 메뉴와 로그아웃·계정 메뉴가 오고 둘째 줄은 넘치면 다음 줄로 접힌다. 메뉴는 숨기지 않는다. 위쪽 띠는 지금처럼 고정하지 않는다. 내 장수 요약은 위쪽 띠 아래, 본문 위에 같은 내용을 펼친 채로 둔다. 접기 단추를 두지 않는 이유는 닫힌 내용이 정보 보존 검사(검증 표)에서 빠지기 때문이다.

화면별 결정은 이렇다.

| 화면 | 좁은 화면에서 |
| ---- | ------------- |
| 로비 | 카드 안 메타 줄은 줄바꿈, 버튼은 카드 아래 줄 전체 폭 |
| 메인 | 패널 5개를 지금 DOM 순서대로 한 열. 메시지 패널은 T2-10이 정한 접이식 동작 그대로 본문 아래 |
| 지도 | SVG는 `viewBox`로 폭에 맞춘다. 고정 `width` 속성을 쓰지 않는다. 지도 위에 도시 고르기 칸(`select`, 44px)을 두고 고르면 도시 정보로 간다. 이 칸은 모든 폭에서 보인다. 키보드 사용자에게도 도움이 되고 화면이 하나로 유지된다 |
| 예턴 편집 | 표는 표로 둔다. 칸 여백을 `--space-1`로 줄이고 명령·인자·사전 검사 칸은 줄바꿈한다. 행은 누르는 대상이므로 좁은 화면에서 44px. 도구 띠는 줄바꿈. 명령 고르기 창은 폭을 `calc(100vw - 2 * var(--space-4))` 이하로 묶는다 |
| 도시·국가 정보 | `StatTable`은 그대로 맞는지 먼저 본다. 넘치면 막대 칸 폭을 줄인다. 열이 많은 장수 표는 아래 순서로 맞춘다 |
| 기록 | 탭 3개는 한 줄에 각 44px. 로그 줄은 줄바꿈. 더 보기는 44px 버튼 |

열이 많은 표는 이 순서로만 맞춘다. 먼저 칸 여백과 숫자 칸 글자를 줄이고(`--text-xs`), 글자 칸 줄바꿈을 허용한다. 그래도 넘치면 우선순위 낮은 열의 값을 같은 행 첫 칸의 둘째 줄로 옮긴다. 이때 옮긴 값 앞에 열 이름을 붙여 화면 낭독기에서도 무슨 값인지 들린다. 어느 열을 옮기는지는 M2 끝의 실제 표를 보고 정해 UI 지침 §5에 적는다. 열을 지우거나 숨기지 않는다.

공개 범위 밖 값의 이유는 지금 `title` 툴팁에만 있다(`StatTable`). 손가락 화면과 키보드에서는 보이지 않으므로, 가려진 행이 있는 표에는 표 아래에 이유 한 줄을 글자로 둔다. 모든 폭에서 같다.

새 화면 문구는 도시 고르기 칸의 이름표, 가려진 값의 이유 한 줄 정도다. [글쓰기 규칙](../writing-style.md)을 따르고 `pnpm lint:text`가 있으면 돌린다. 기존 문구는 바꾸지 않는다.

44px은 AC가 375px 폭을 말하므로 좁은 화면 기준(640px 이하)에서만 검사한다. 가로 스크롤은 모든 폭에서 검사한다. 641~1023px에서 240px 왼쪽 열 때문에 본문이 넘치면 그것도 이 작업에서 고친다 (결정의 데스크톱 항목).

측정 전에 `document.fonts.ready`를 기다린다(Pretendard가 늦게 오면 폭이 바뀐다). `page.clock`으로 시각을 고정하고 애니메이션을 끈다.

### 측정 방법 (`e2e/responsive-check.ts`)

가로 스크롤은 세 가지를 본다.

- `document.documentElement.scrollWidth`가 `window.innerWidth`를 넘지 않는다.
- 보이는 요소 가운데 오른쪽 끝이 `innerWidth`를 0.5px 넘거나 왼쪽 끝이 -0.5px보다 작은 것이 없다. 실패하면 요소 경로와 폭을 목록으로 낸다.
- 계산된 `overflow-x`가 `auto`·`scroll`이면서 `scrollWidth > clientWidth`인 요소가 없다. `html`, `body`의 `overflow-x`가 `hidden`·`clip`이면 실패다.

44px은 보이는 `a[href]`, `button`, `input`, `select`, `textarea`, `summary`, `[role=button]`, `[role=tab]`, `[role=link]`, `[tabindex]:not([tabindex="-1"])`의 `getBoundingClientRect()` 폭과 높이가 둘 다 44 이상인지 본다. 체크 상자·라디오는 감싼 `label`을 잰다. 예외는 `data-tap-exempt` 속성으로만 표시하고 허용 값은 사용자 결정을 받은 것(`map-marker`, `inline`)뿐이다. 허용 목록 밖의 값이면 실패다. 예외 개수는 결과에 따로 적는다.

정보 보존은 같은 데이터로 1280px과 375px을 비교한다. 375px 쪽이 1280px의 보이는 글자(`body`의 `innerText`를 공백으로 나눈 낱말, 개수 포함)와 초점 대상(역할과 접근 가능한 이름, `ariaSnapshot()`에서 뽑음)을 모두 가져야 한다. 표 열을 옮기면서 붙인 열 이름처럼 375px에만 더 있는 것은 허용한다. 좁은 화면에서 숨긴 내용이나 빠진 컨트롤이 있으면 여기서 걸린다. 예외 결정의 거절안이 적용되면 그 차이(지도 도시 표시의 링크 역할, 문장 속 링크)만 비교에서 빼고 뺀 항목을 결과에 적는다.

키보드·초점은 375px에서 본다. Tab으로 화면의 초점 대상을 끝까지 돈다. 초점이 간 요소는 뷰포트 안에 있어야 한다. 그 가운데 점의 `elementFromPoint`가 그 요소나 자손이면 가려지지 않은 것이다. 계산된 `outline-style`은 `none`이 아니어야 한다. 끝에서 다시 Tab하면 첫 대상으로 돌아와 갇히지 않아야 한다. 예턴 편집은 T1-15의 키보드 시험(마우스 없이 3칸 넣고 저장)을 375px에서 한 번 더 돌린다.

`viewport` 메타는 `width=device-width, initial-scale=1.0`이고 확대 막기가 없는지 본다.

검사기가 실제로 잡는지 음성 시험을 둔다. 같은 페이지에 아래를 끼워 넣었을 때 각각 실패를 돌려줘야 한다.

| 음성 시험 | 넣는 것 | 기대 |
| --------- | ------- | ---- |
| 넘치는 상자 | 폭 400px `div` | 가로 스크롤 실패, 요소 경로 보고 |
| 숨긴 넘침 | `body { overflow-x: hidden }` + 폭 400px `div` | `overflow-x` 실패 |
| 안쪽 스크롤 | `overflow-x: auto` 상자 안 폭 600px 내용 | 안쪽 스크롤 실패 |
| 작은 버튼 | 높이 40px `button` | 44px 실패 |
| 모르는 예외 | `data-tap-exempt="small"` 버튼 | 예외 값 실패 |
| 숨긴 정보 | 375px에서만 `display: none`인 문단 | 정보 보존 실패 |
| 가려진 초점 | 초점 대상 위에 `position: fixed` 덮개 | 초점 가림 실패 |

양성 시험은 대상 화면 전부가 위 검사를 통과하는 것이다.

### 데이터 시나리오

T1-16·T2-04 E2E가 쓰는 고정 시드 월드를 그대로 쓰고 화면이 가장 넓어지는 값을 더한 변형을 하나 둔다. 둘 다 공개 API(가입, 장수 생성, 예턴 저장 등)로 만든다.

| 화면 | 기본 데이터 | 넓게 만드는 변형 | 재는 상태 |
| ---- | ----------- | ---------------- | --------- |
| 로비 | 월드 3개: 진행 중(내 장수 있음), 가오픈(장수 없음), 정원 참 | 가장 긴 월드·시나리오 이름 | 로그인 함·안 함, 공지 펼침, 정원 이유 펼침, 목록 비어 있음, 불러오기 실패 |
| 메인 | 내 장수 1명, 예턴 5칸 채움, 로그 10줄 | 허용 최대 길이 장수 이름, 6자리 이상 금·쌀, 긴 로그 줄 | 기본, 발령 알림 있음, 메시지 패널 펼침, 안 읽음 배지, 연결 끊김 표시 |
| 지도 | 94도시 전부, 내 위치, 보급 끊김 1곳 | 국가 수 최대 | 기본, 도시 고르기 열림 |
| 예턴 편집 | 30칸 중 일부 채움 | 30칸 전부 인자 있는 명령, 사전 검사 경고 여러 칸 | 기본, 여러 칸 선택, 명령 고르기 열림, 인자 고르기 열림, 저장 충돌 안내, `DisabledReason` 펼침 |
| 도시 정보 | 내 도시 | 다른 국가 도시(가려진 값), 주둔 장수 많은 도시 | 기본, 가려진 값, 빈 주둔 장수 |
| 국가 정보 | 내 국가 | 소속 장수·소유 도시 가장 많은 국가, 경고 강조 항목 | 기본, 정렬 바꿈, 다른 국가(가려진 값) |
| 기록 | 탭 3개 각 10줄 이상 | 긴 줄, 더 보기 뒤 많은 줄 | 탭별, 더 보기 뒤, 빈 기록 |

최대 길이 값이 공개 API로 만들어지지 않으면(예: 큰 국고, 긴 국가 이름) 시나리오 데이터나 테스트 준비 도구가 필요하다. 이는 Codex 영역이므로 직접 만들지 않고 대기열에 Codex 작업 한 줄을 요청한다.

### 접근

1. M2 완료 시점의 main에서 `responsive-check.ts`와 spec을 먼저 넣고 돌린다. 실패 목록(화면, 뷰포트, 요소, 폭·높이)과 1280px 스크린샷을 구현 기록에 기준선으로 남긴다.
2. 토큰과 전역 규칙을 넣는다 (`--tap-target`, 좁은 화면 공통 규칙).
3. `GameLayout`을 한 열·두 줄 위쪽 띠로 바꾼다.
4. 화면별로 CSS 모듈을 고친다. 마크업은 도시 고르기 칸, 표 열 옮기기, 가려진 값 이유 줄만 손댄다.
5. 음성 시험을 넣어 검사기가 실패를 잡는지 확인한다.
6. 1280px 스크린샷을 기준선과 나란히 비교해 데스크톱이 그대로인지 본다. 다른 점이 있으면 이유를 구현 기록에 쓴다.
7. 채울 문서를 채운다.

기준선 실패가 어느 화면을 통째로 다시 짜야 고쳐지는 수준이면 멈추고 사용자에게 알린다 (AGENTS §3). 예상 분량은 2~3일이다. 1주를 넘길 것 같으면 화면 묶음별로 AC를 나눈다.
