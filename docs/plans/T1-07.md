# T1-07 월간 정산과 재생 테스트

> 대기열: T1-07 · AC: AC-M1-12, AC-M1-13 · 구현: Codex · 리뷰: Claude
> 선행: T1-06 · 관련: [게임 시계](../architecture/game-clock.md) §6, [수치 상태 정책](../numeric-state-policy.md)

## 계획 (Claude)

### 목표

- 달이 바뀌면 세금·봉급 → 인구·민심 → 보급 → 외교 기한 → 연감 순서로 처리된다 (AC-M1-12).
- 같은 시드와 같은 입력 기록으로 12개월을 다시 돌리면 상태 해시가 같다 (AC-M1-13).

### 범위

- `packages/rules/src/monthly/`: 단계별 순수 함수와 `runMonthly(state, month, rng)`
- `packages/db`: `NationHistory`, `YearbookSnapshot`, `InputEvent`(재생용 기록)
- `apps/engine`: 달 경계에서 월간 정산 실행, 같은 트랜잭션으로 저장
- `tools/replay.ts`: 기록을 다시 돌려 해시를 비교하는 스크립트

### 하지 않는 것

재해·사건·NPC 생성, 장수 나이·사망(Phase 2), 원작 수치 맞추기.

### 달 경계 결정

- 달 경계 tick(`k × 10,000`)에 도달하면, **그 tick보다 앞선 장수 턴을 모두 처리한 뒤** 월간 정산을 한 번 실행한다.
- 월간 정산은 한 트랜잭션. 펜싱 토큰 조건 포함.
- RNG는 `rngFor(seed, 'monthly', 연, 월)`. 단계 안에서 국가·도시는 ID 순으로 돈다.

### 단계별 공식 결정 (단순화, 상수는 `balance.ts`)

| 순서 | 단계 | 처리 |
| ---- | ---- | ---- |
| 1 | 세금·봉급 | 1·7월 금, 4·10월 쌀 (myosam·원작과 같은 반기 구조). 수입 = Σ 도시(상업 또는 농업 × 인구 계수 × 세율). 봉급 = 소속 장수에게 지급률만큼 나눠 줌 |
| 2 | 인구·민심 | 인구 += 정착 계수 × (인구 최대 − 인구), 세율이 높으면 민심 감소, 낮으면 증가 (core2026 `economy-and-diplomacy.md`의 5%·30% 표가 방향 참고) |
| 3 | 보급 | 수도에서 같은 나라 도시로 BFS. 끊긴 도시는 `supplied = false`, 내정치 −10%, 주둔 장수 훈련·사기 감소 |
| 4 | 외교 기한 | `untilTick`이 지난 선포는 교전으로, 불가침은 중립으로 |
| 5 | 연감 | `YearbookSnapshot`: 국가별 도시 수·장수 수·국력, **도시별 소유 국가** (D4 타임랩스가 이것만으로 재생) |

그 밖에: 15세가 된 장수의 `activeFromYear` 도달 처리(T1-03 참고), 정수화는 각 단계 끝에서 `Math.round`.

### 재생 결정

- 재생에 필요한 입력: 월드 시드, 리소스 버전, 예턴 변경 기록, `InputEvent`. 이번에는 **예턴 변경을 `InputEvent(kind: 'turns.set')`로 남긴다.**
- `tools/replay.ts --from <월드 생성 기록> --months 12`가 메모리에서 다시 돌려 매달 해시를 출력·비교한다.

### 검증

| 무엇 | 어떻게 |
| ---- | ------ |
| 순서 | 골든: 고정 시드 월드 1개월 → 기대 스냅샷 파일과 비교. 단계마다 호출 순서를 기록하는 테스트 |
| 반기 수입 | 단위: 1월 금만, 4월 쌀만 |
| 보급 | 단위: 수도-A-B 직선에서 A를 잃으면 B 끊김, 우회로가 있으면 유지 |
| 재생 | 통합: 12개월 진행 기록 → 재생 → 매달 해시 같음 |
| 결정성 lint | `Math.random` 0건 (lint가 이미 막음) |

## 구현 기록 (Codex)

- 바꾼 것: 월간 단계별 순수 함수, 달 경계 턴·정산 교차, 펜싱 트랜잭션 저장, 국가 기록·연감, 생성 원본과 InputEvent 계약, 메모리 재생과 내보내기 CLI를 추가했다. 구현은 opensamguk-implement가 전용 worktree `t_65f25b0d`에서 맡았다. 수정 범위는 `packages/rules`, `packages/db`, `apps/engine`, `tools/replay.ts`와 지정 문서다. API 구현은 T1-11 담당에게 남겼다.
- 계획과 달라진 점과 이유: 종료한 달을 경계 tick에서 정산한다. API 예턴 편집과 밀린 턴의 실제 적용 순서를 보존하려고 월드별 `actionSequence`를 기록한다. 초기 리소스 파일 경로만 저장하면 파일 교체 뒤 재생할 수 없어 전체 초기 상태와 해시를 함께 보존한다. 기존 월드의 원본은 추측하지 않는다. 장수 생성은 T1-11이 확정 결과 전체를 기록하며 재생은 그 결과를 적용한다.
- 검증 결과: PR #9의 `f02bf1271108828393e430f382412a1c20aad798`, GitHub CI [39415440569](https://github.com/peppone-choi/opensamguk/actions/runs/39415440569)에서 `pnpm check` 단위 123개, `pnpm test:int` 실제 PostgreSQL 43개, `pnpm e2e --workers=1 --reporter=line` 24개와 웹 운영 빌드가 통과했다. 신규 월간 단위 13개·DB 10개에는 골든, 반기 세입, 단계 순서, 펜싱·리스 만료 롤백, 정산 전후 실제 SIGKILL, 같은 경계 재호출, 밀린 달, 입력 사이 예턴 변경·실패·장수 생성, 12개월 해시, CLI 내보내기·재생·오류 종료가 있다. skip은 없다. 로컬 Vitest는 공유 검증 예산 대기 후 exit 75로 시작하지 못했고 우회하지 않았다. 최종 인계 SHA의 CI 결과는 카드에 고정한다. 독립 리뷰 전이며 AC 상태는 바꾸지 않았다.

- 리뷰 지적 수정: `docs/architecture/game-clock.md` §6과 `docs/numeric-state-policy.md` §2의 연결어미 뒤 쉼표 4곳을 뺐다. 뜻·서법·수치는 유지했고 두 문서의 T1-07 추가 문장에 같은 패턴이 더 없는지 확인했다.

## 2026-10-23 Windows 실행 후속 계획 (Claude)

위 계획·구현 기록·리뷰와 T1-07 `완료`, AC-M1-12·AC-M1-13 상태는 그대로 둔다. 이 절은 AC-M1-02·AC-M1-13의 기존 로컬 통합과 12개월 재생 검증 명령을 Windows에서 다시 실행할 수 있게 하는 후속 범위만 다룬다. 사용자 승인에 따른 국소 정정이다.

- 근거: 기준 main `3e5b52a`에는 WIP가 보존돼 있고 전체 통과 상태가 아니다. Windows에서 `pnpm test:int`를 돌리면 `tools/run-integration.ts`의 `spawnSync('pnpm', ...)`가 ENOENT로 끝나 migration과 통합 시험이 시작되지 않는다.
- 담당: 상세 구현은 Codex, 독립 리뷰는 Claude다. 작업실은 `E:/opensamguk-worktrees/windows-cli-validation`, 브랜치는 `codex/windows-cli-launchers`다. 이 후속 구현은 진행중이며 대기열 표와 AC 상태는 이 후속 때문에 바꾸지 않는다.
- 범위: `tools/run-integration.ts`의 하위 pnpm 실행만 고친다. `process.execPath`와 pnpm의 실제 JavaScript CLI 진입 파일을 별도 인수로 넘긴다. 진입 파일은 `pnpm test:int` 실행 환경의 `npm_execpath`를 쓸 수 있고 정확한 방식은 Codex가 기존 패키지 구조(`packageManager`, 루트 스크립트)를 보고 정한다. 진입 파일을 찾지 못하면 shell로 돌아가지 않고 실패로 끝난다. launcher는 [T1-25](./T1-25.md) 후속과 같은 것을 쓴다.
- 보존할 것: migrate 다음 vitest 순서, `DATABASE_URL`·`TEST_DATABASE_URL` 환경, `stdio: 'inherit'`, 하위 명령의 종료 코드 전달(없으면 1), 시작 실패를 오류로 끝내는 동작은 지금과 같다. `tools/test-database.ts`의 `_test` 이름 검사와 개발 DB 분리 검사도 바꾸지 않는다.
- 하지 않는 것: `shell: true`, timeout 증가, skip, mock만으로 끝낸 검증, 범용 실행 프레임워크, 루트 `package.json` 수정은 하지 않는다. `tools/command-coverage.*`(PR182 담당), `apps/web/e2e`, API·schema·엔진·게임 규칙은 건드리지 않는다.

### 2차 후속 계획 (Claude, 2026-10-23)

위 후속 계획·구현 기록과 T1-07 `완료`, AC-M1-02·AC-M1-03·AC-M1-12·AC-M1-13 상태는 그대로 둔다. 이 절은 위 기록이 범위 밖으로 남긴 pnpm 직접 호출 두 곳을 고치는 검증 유지보수만 다룬다. 이번 후속은 진행중이며 대기열 표와 AC 상태를 바꾸지 않고 AC 완료도 판정하지 않는다.

createWorld 시험은 아래처럼 고친다. AC-M1-03의 기존 시험 다섯 개, 기대값, `beforeAll`·`afterAll`의 `deleteMany`는 바꾸지 않는다.

- 엔진 파일은 자기 패키지 밖인 `tools/node-cli.ts`를 상대 경로로 import하지 않는다. `no-cross-package-relative` 위반이다. lint 설정 수정, 예외 주석, 우회 import도 하지 않는다.
- 같은 폴더의 `clock.integration.test.ts`처럼 `execFileSync(process.execPath, [...])`로 실제 TS CLI를 띄운다. 인수는 `--env-file-if-exists=.env`, `--import`, `tsx`, `apps/engine/src/cli/createWorld.ts`를 앞에 두고 기존 CLI 인수를 그 뒤에 붙인다. tsx JS CLI 진입 파일 대신 `--import tsx`를 고른 것은 엔진 시험과 감독이 이미 이 방식을 쓰기 때문이다.
- env 파일: 기존 `world:create`는 `apps/engine`에서 `--env-file-if-exists=../../.env`로 저장소 루트 `.env`를 읽는다. 시험 cwd는 지금처럼 저장소 루트(`new URL('../../../../', import.meta.url)`)이므로 `.env`가 같은 파일이다. 파일이 없으면 넘어가고 이미 있는 환경 변수가 파일 값보다 우선하는 Node 규칙도 같아서 시험이 넘기는 `DATABASE_URL`이 이긴다. 리소스는 `import.meta.url` 기준으로 읽으므로 CLI cwd가 `apps/engine`에서 루트로 바뀌어도 읽는 파일은 같다.
- 인수 경계와 출력: CLI 인수 12개는 지금과 같은 값·순서로 배열 원소 하나씩 넘긴다. 공백과 한글이 든 `CLI 통합 검증`도 한 원소다. 환경 `{ ...process.env, DATABASE_URL: url }`, `encoding: 'utf8'`, `timeout: 30_000`을 그대로 쓴다. stdout 마지막 줄의 JSON으로 해시와 월드 설정을 비교하는 검사도 그대로다. pnpm 출력 줄이 없어지므로 `-s`에 해당하는 처리는 필요 없다.
- 오류 전파: 예외를 잡지 않는다. 시작 실패, timeout, 0이 아닌 종료 코드는 지금처럼 `execFileSync` 예외가 되어 시험을 실패시킨다.
- 실패 증거: 같은 describe에 시험 하나를 더한다. 같은 실행 방식에 `--name`과 그 값만 뺀 인수를 넘기면 `execFileSync`가 예외를 내고 그 `status`는 1이다. stderr에 필수 인수 오류 문구가 있고 stdout·stderr에 DB URL이 없으며 월드 수는 그대로다. 실행 함수는 두 CLI 시험이 함께 쓰는 지역 함수 하나로 둔다.

### 2차 후속 구현 기록 (Codex, 2026-10-23)

- 기준은 PR190 `f00fe347b20af6de5ffd2747ea68b9b695e532a8`이고 작업실·브랜치는 2차 계획과 같다. 소유 코드 두 파일과 이 기록, T1-25 Windows 절의 연결 문장만 바꿨다. 기존 helper·원 PR190·참가 도구 절은 그대로다. 후속 구현 범위 리뷰를 요청한다.
- createWorld의 기존 CLI 성공 시험은 같은 인수로 실제 `createWorld.ts`를 실행하고 같은 DB 값·해시를 확인한다. Node·tsx loader, 루트 cwd·env 파일, 환경·인수 배열·30초 제한을 계획대로 썼다. 필수 `--name`만 뺀 실제 실행이 종료 코드 1, 고정 오류 문구, DB URL 비출력, 월드 수 불변인 시험 한 개를 더했다.
- 세션 준비는 같은 migrate 인수와 자식 환경·60초 제한을 보존해 `pnpmCli`로 실행한다. 첫 적용에서 전개한 `env`를 helper에 넘겼더니 Windows worker의 key가 `NPM_EXECPATH`여서 일반 객체의 `env.npm_execpath`가 없었다. 같은 자리의 `process.env.npm_execpath`는 `pnpm.cjs`를 읽었다. 실제 Claude가 이 원인을 반영해 계획을 정정했고 helper의 기존 기본값 `process.env`를 직접 읽도록 호출만 고쳤다. 임시 진단 출력은 제거했다.
- 새 전용 DB `opensamguk_windows_followup_a604fa97_test`를 만들어 migration 13개를 적용했다. 수정 전 두 파일 전체는 4개 통과, CLI 1개 실패, 준비 실패로 11개 미실행, 종료 코드 1이었다. 최종 두 파일 전체 실행은 17개 통과, skip 0, 종료 코드 0이다. `SESSION_RENEWAL_FAULT_SCOPE`와 update·read의 `SESSION_RENEWAL_COMMIT` 출력으로 실제 PostgreSQL 장애와 HTTP 커밋 경로를 확인했다.
- 실패 전달은 `npm_execpath`를 제거하고 Node와 실제 Vitest JS 진입 파일로 세션 파일 전체를 실행해 확인했다. 준비 단계의 경로 오류가 종료 코드 1로 전파됐고 11개는 실행되지 않았다. 이 실행을 성공 증거로 세지 않는다. 성공·실패 실행 전후의 DB 목록을 대조해 이번 실행이 새로 남긴 세션 DB가 0개임을 확인했다. 위 전용 DB도 검증 뒤 지웠다. 다른 DB와 프로세스는 변경하지 않았다.
- 두 코드 파일의 ESLint·Prettier, 엔진 typecheck, 바꾼 문서의 strict 문구 검사와 `git diff --check`가 통과했다. 문서는 저장소 Prettier 제외 대상이므로 전체 문서 포맷은 하지 않았다. 전체 통합·authz·check·브라우저·성능은 다시 실행하지 않았다. 남은 preset migration 직접 호출과 엔진 종료·정리 문제, 전체 AC는 이 결과로 통과 처리하지 않는다.
