## 1. 목표와 완료 조건

- 운영자가 생성 양식에서 다섯 종류(시나리오·지도·병종·능력치·초상)의 게시 판을 칸마다 고른다. 제출값은 정규형 키(`che`, `1030@2`)다.
- 완료 조건
  - 다섯 종류 모두 `next === null`까지 읽은 목록에서 고른다.
  - 시나리오와 지도는 각자 고른다. 짝 검사는 생성 시 서버가 한다(D-071).
  - 확장 프로필은 서버가 고정한 판과 기능 목록을 유지한다.
  - 기본 묶음(`san10-191`, `integration-v01`)의 제출 입력은 바뀌지 않는다.
  - FAILED 응답은 서버 `error.message`를 보인다.

## 3. 화면 설계

### 3.1 칸과 목록

- 프로필 select 아래에 다섯 칸을 `resourceLabels` 순서로 둔다. 각 칸은 `select` 하나다.
- 옵션 표시는 `name`(판 1) 또는 `name@version`이다. 값은 서버가 준 `key`다. 화면이 `@1`을 붙이지 않는다.
- kind마다 `next`가 `null`이 될 때까지 `cursor`로 이어 읽는다. 쪽 크기는 가정하지 않는다. 다섯 kind는 병렬로 읽는다.
- 한 kind가 실패하면 그 칸만 오류를 보이고 나머지는 쓴다.
- 정렬은 `name`, 같은 이름이면 `version` 오름차순이다.
- 창을 열 때와 `invalidate` 때 다시 읽는다. 늦은 응답은 기존 세대(`generation`) 패턴으로 버린다.

### 3.2 상태와 문구

| 상태 | 칸과 제출 | 문구 |
| ---- | --------- | ---- |
| 목록 읽는 중 | 잠금 | "게시된 생성 자원을 확인하고 있습니다." |
| kind 조회 실패 | 그 칸만 잠금, 다시 시도 | 기존 `ErrorState` |
| 고른 키가 목록에 없음 | 제출 잠금 | "선택한 판이 게시 목록에 없습니다: <키>" |
| 목록이 비어 있음 | 기본 묶음 키만 허용 | "게시한 <종류> 판이 없습니다." |

### 3.3 FAILED 표시

- `status: 'FAILED'`이면 `reply.error.message`를 그대로 보인다. 짝 불일치와 게시 여부 문구가 이 경로로 온다.
- 메시지가 비어 있을 때만 `createRejections[code]`를 쓴다.

## 4. 위험과 확인할 것

1. `ruleFeatures`. 칸을 하나라도 바꾸면 프로필의 `ruleFeatures`가 새 조합과 맞지 않을 수 있고 화면은 조합의 기능 목록을 알 수 없다. 일반 묶음의 판을 바꾸면 `ruleFeatures`를 생략해 엔진이 선택한 자원에서 계산한 기능을 쓴다. 이 조합은 기본 묶음에만 지정된 추가 기능을 상속하지 않는다. 확장 묶음은 변경 가능한 판을 바꿔도 기존 `ruleFeatures`를 보낸다. 서버가 확장 묶음의 기능과 해시로 대조한다. `reviewCreation`은 생략하고 `freezeCreation`은 생략을 유지해 빈 배열로 바꾸지 않는다. 둘 다 단위 시험한다. 생략한 조합의 실제 기능 목록은 서버가 계산하며 화면은 알려 주지 않는다.
2. `@` 키. 현재 HEAD의 `createRequest.ts`는 `resourceKeySchema`를 쓰며 `@2` 키를 받는다(Codex 검토에서 확인, 이전 계획의 정규식 우려는 해소). 접수부터 저장까지는 새 E2E가 확인한다.
3. 확장 묶음 고정. 칸을 열어 두면 묶음 검사에서 `INPUT_INVALID`가 난다. 그래서 서버 묶음 범위만큼 잠근다(§2).
6. 바뀐 시나리오의 요약. 기본 프로필의 시작 연도·국가 수·도시 수는 다른 시나리오·지도에는 맞지 않는다. 칸을 하나라도 바꾸면 양식과 확인 창에서 이 요약을 빼고 "시작 연도와 규모는 생성할 때 서버가 확인합니다"로 바꾼다. 종료 연도 하한도 프로필 시작 연도 대신 1로 두고 서버 검증에 맡긴다.
4. 짝 검사. 화면은 짝을 검사하지 않는다. 짝 실패는 제출 뒤 FAILED 메시지로만 드러난다. 검사를 서버 한 곳에 둔다(R24).
5. 기존 E2E. `e2e/admin-create-profile.spec.ts`, `e2e/admin-create.spec.ts`는 수정 없이 통과해야 한다.

## 8. 구현 순서

1. 단위 시험과 두 E2E의 기준선을 기록한다.
2. `adminCreateModel.ts`에 정렬·키 검사를 더한다. kind별 쪽 읽기와 다섯 칸을 `AdminCreateActions.tsx`에 붙인다. FAILED는 `error.message` 우선으로 바꾼다.
3. 단위 시험을 더하고 기존 E2E 통과를 확인한다. 새 E2E는 현재 서버 API와 실제 PostgreSQL을 사용한다. 구현 기록을 이 문서에 쓴다.

## 구현 기록 (2026-11-08, Claude)

- 변경: `adminCreateModel.ts`(칸 선택·잠금 범위·쪽 합치기·정렬·`ruleFeatures` 생략·`failureMessage`), `AdminCreateActions.tsx`(다섯 칸·kind별 병렬 쪽 읽기·재시도·세대/abort·계정 전환 시 `denied`), CSS 한 블록, 시험, E2E, Playwright 등록, 문서.
- 서버·rules·engine은 읽기만 했고 수정하지 않았다. 백엔드 변경 필요 없음. 단, `creationOptions`가 묶음 형식 번호를 내려주지 않아 화면이 `expanded-191-v3`를 키로 구분한다. 형식 번호나 잠금 칸 목록을 응답에 넣으면 이 예외를 없앨 수 있다(T4-79 후속 제안).
- 보존한 것: 조회 입력(`expandedProfiles: true`)과 `revision` 재검토 흐름, 중복 방지 키·재접수·상태 복구, 기존 두 E2E(수정 없음). 기본 묶음은 칸을 건드리지 않으면 이전과 같은 다섯 키와 10기능을 보낸다.

## Codex 기술 검토와 실행 증거

- 지도와 시나리오의 독립 선택, 다섯 종류의 페이지 처리, 이전 요청 복구와 `revision` 재확인 흐름을 확인했다. 확장 묶음에서 변경 가능한 판을 선택해도 필수 기능 목록을 유지한다.
- 실제 Chromium·HTTP·PostgreSQL에서 기존 관리자 생성 12건, 기존 프로필 5건, T4-90 전용 3건이 통과했다. 전용 시험은 정확한 판 키 저장, 조합 실패의 문구와 월드 미생성, 통합판 확장 병종 2판과 기능 목록 보존을 확인했다.
- 공개 빌드와 공개 자산 검사가 통과했다. 화면은 서버가 형식 번호를 보내지 않아 기존 확장 키를 기준으로 잠금 범위를 정한다. 알려지지 않은 확장 키는 다섯 칸을 잠근다.
- `pnpm check`가 통과했다. 전체 488파일 7,355건과 관리자 양식 집중 시험 47건을 확인했다.
