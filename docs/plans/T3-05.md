### 관리자 권한

- 관리자 API는 `adminProcedure` 하나를 거친다. `protectedProcedure` 뒤에 DB의 `role = ADMIN`을 확인하고 아니면 `FORBIDDEN`이다. 클라이언트가 보낸 값은 권한 근거로 쓰지 않는다.
- 화면이 관리자 여부를 알 때는 `admin.whoami()`를 부른다. `auth.me`의 출력 모양은 바꾸지 않는다 (T1-10·T3-02 소유).
- 관리자 지정과 해제는 API로 열지 않는다. 서버에서 `pnpm admin:grant`·`pnpm admin:revoke`를 실행하고 이메일은 명령줄 인자가 아니라 표준 입력으로 받는다. 이 명령도 `AuditLog`(`actorKind = CLI`)에 남는다.
- 관리자는 자기 자신과 다른 관리자를 제재할 수 없다. 관리자를 제재하려면 먼저 명령줄로 권한을 거둔다.

### 게임 상태를 바꾸는 조치는 엔진이 한다

API는 게임 상태와 월드 시계를 직접 쓰지 않는다 (AGENTS.md §6). 관리자 API는 요청 기록과 감사 로그만 한 트랜잭션에 쓰고 결과는 엔진 쪽 실행기가 만든다.

| 조치 | API가 쓰는 것 | 엔진 쪽 처리 |
| ---- | ------------- | ------------ |
| 월드 생성 | `WorldCreateRequest`(PENDING) + `AuditLog`(`world.create.requested`) | 실행기가 기존 월드 생성 함수로 월드를 만들고 같은 트랜잭션에서 요청을 DONE·`worldId`로, `AuditLog`(`world.create.applied`)를 남긴다. 실패하면 FAILED·오류 이유 |
| 일시정지·재개 | `InputEvent`(`kind = admin.world.pause` / `admin.world.resume`, `generalId = null`, PENDING) + `AuditLog`(`.requested`) | 실행기가 월드 행을 `FOR UPDATE`로 잠그고 기존 `controlClock`과 같은 규칙으로 시계를 바꾼다. 같은 트랜잭션에서 `nextActionSequence`를 받아 APPLIED 또는 REJECTED로 닫고 `AuditLog`(`.applied`·`.rejected`)를 쓴다 |
| 종료 | `InputEvent`(`admin.world.end`) + `AuditLog` | 월드가 PAUSED일 때만 받는다. 상태를 ENDED, `endedAt`을 기록한다. 승자 계산은 하지 않는다 (강제 종료) |
| 초기화 | `InputEvent`(`admin.world.reset`) + `AuditLog` | 아래 초기화 절 |
| 시작 | `InputEvent`(`admin.world.start`) + `AuditLog` | PREOPEN만 받는다. `controlClock`의 start 규칙 |

- 실행기는 `apps/engine/src/admin/executor.ts`이며 T2-01 감독 프로세스 안에서 돈다. 엔진 자식이 없는 PREOPEN 월드와 아직 없는 월드의 요청도 이 실행기가 처리한다. 월드 행 잠금을 먼저 잡는 기존 순서(리스 → 월드 → 장수)를 깨지 않는다.
- 관리 입력은 `actionSequence`를 받으므로 재생 기록에 들어간다. `packages/rules/src/replay.ts`는 `admin.world.*` 종류를 상태를 바꾸지 않는 입력으로 받아야 한다. 지원하지 않는 입력으로 거부하면 관리 조치가 있었던 월드의 재생이 깨진다. 상태 해시는 시계 tick을 포함하지 않으므로 일시정지·재개는 해시를 바꾸지 않는다.
- 같은 관리자와 같은 `idempotencyKey`의 재요청은 처음 요청을 그대로 돌려준다 (T1-07 InputEvent 계약).
- 기존 명령줄 `world:create|start|pause|resume`는 운영 비상용으로 남긴다. 이 작업은 각 명령이 같은 트랜잭션에서 `AuditLog`(`actorKind = CLI`)를 쓰게 한다. 명령줄 경로는 InputEvent를 거치지 않으며 이 점을 admin-console.md에 적는다.

### 초기화의 경계

초기화는 기존 월드를 지우지 않는다. 진행 기록과 재생 근거를 남기기 위해서다.

- 대상 월드가 PREOPEN·PAUSED·ENDED일 때만 받는다. RUNNING이면 `BAD_REQUEST`이며 먼저 일시정지해야 한다.
- 요청에는 월드 이름을 그대로 다시 입력한 `confirmName`과 사유(1~200자)가 있어야 한다. 이름이 다르면 `BAD_REQUEST`다.
- 실행기는 한 트랜잭션에서 기존 월드를 ENDED로 닫고 같은 시나리오·프리셋·턴 간격으로 새 월드를 PREOPEN으로 만든다. 시드는 요청에 있으면 그 값, 없으면 새로 만든다. 결과(`newWorldId`)를 InputEvent `result`와 `AuditLog`에 남긴다.
- 기존 월드의 장수·로그·InputEvent는 그대로 남는다. 사람 장수는 새 월드로 옮기지 않는다.
- 사람 장수가 있는 실제 운영 월드의 종료·초기화는 소유자 결정 사항이다. 관리자 화면은 확인 입력만 강제하고 승인 절차는 admin-console.md에 적는다. 에이전트는 실제 운영 DB에서 이 조치를 실행하지 않는다.

### 제재

| 범위 | 효과 |
| ---- | ---- |
| 계정 전체 (`worldId = null`) | 만드는 트랜잭션에서 그 사용자의 세션을 모두 지운다. 이후 로그인과 세션 확인은 지금처럼 `UNAUTHORIZED`와 같은 문구로 실패한다 (계정 존재를 드러내지 않는 T1-10 동작 유지) |
| 월드 하나 | 로그인은 된다. 그 월드의 변경 API(예턴 저장, 장수 생성, 메시지 보내기 등)는 `FORBIDDEN`, `data.reason = null`. 조회 API는 막지 않는다 |

- 세션 확인(`auth/session.ts`)에 계정 전체 제재 조회를 한 번 더한다. 월드 제재 검사는 `apps/server/src/admin/sanctionGuard.ts`의 미들웨어 하나로 두고 월드 변경 절차를 만드는 공통 빌더에 끼운다. 순서는 `protectedProcedure` → T3-02의 인증·동의 검사 → 이 제재 검사다.
- 사용자는 `sanction.mine()`으로 자기에게 걸린 유효한 월드 제재(월드 이름, 사유, 기한)를 본다. 화면 표시는 T3-06이다.
- 계정 전체 제재의 사유를 로그인 화면에 보여 주려면 `data.reason`에 새 값이 필요하다. 이 작업은 그 값을 만들지 않고 아래 사용자 결정 대기로 넘긴다.
- 제재된 사람의 장수는 이미 넣은 예턴대로 엔진이 계속 실행한다. 다시 접속하지 않는 장수와 같다 (D12).
- 해제는 `liftedAt`·`liftedBy`·`liftReason`을 채운다. 행을 지우지 않는다.

### 로그인 기록과 해시

| 항목 | 결정 |
| ---- | ---- |
| 기록 시점 | 가입 성공, 로그인 성공, 있는 계정의 로그인 실패. 없는 주소의 실패는 사용자가 없으므로 남기지 않는다 |
| IP | T3-04가 정한 `ctx.ip`(`server.ts:121`). 운영은 `TRUST_PROXY=1`로 Caddy 한 단계만 믿는다([릴리스 운영 §5](../release-operations.md#5-프록시-경로)). 저장값은 `HMAC-SHA256(AUDIT_HASH_KEY, ip)`의 hex 64자. 원문 IP는 DB·로그 어디에도 없다. IPv6는 주소 전체를 해시하므로 같은 /64 안에서 주소를 바꾸면 다른 묶음으로 보인다(T3-04 리뷰의 기록만 항목). 접두어로 묶을지는 사용자 결정 대기다 |
| 기기 | 처음 로그인·가입 때 `did` 쿠키(무작위 128비트, `HttpOnly`, `SameSite=Lax`, `Path=/`, 운영 `Secure`, 1년)를 준다. 저장값은 `HMAC-SHA256(AUDIT_HASH_KEY, did)`. 브라우저 지문 수집은 하지 않는다. 쿠키를 지우면 새 기기로 보이는 것은 받아들인다 |
| 비밀 키 | `AUDIT_HASH_KEY`는 32바이트 이상. `.env.production`에만 둔다. 운영에서 없거나 짧으면 서버가 시작을 거부한다. 시험은 주입한 키를 쓴다 |
| 키 교체 | `AUDIT_HASH_KEY_VERSION`을 올리고 새 키로 바꾼다. 조사 화면은 같은 `hashKeyVersion`끼리만 묶는다. 이전 키는 보관하지 않는다 |
| 보관 | 90일. T2-15가 만드는 매일 정리 작업(만료 세션 정리, main에는 아직 없다)에 `LoginRecord` 90일 초과 삭제를 더한다 |
| 화면 표시 | 해시 앞 8자만 묶음 이름으로 보여 준다. 해시 전체와 원문은 내보내지 않는다 |

### 탈퇴 의무 (T3-02와 함께 지킨다)

총괄 결정에 따라 탈퇴 트랜잭션은 T3-02 소유이며 다음을 모두 지운다: 세션, 계정 토큰, `NotificationTarget`의 웹훅 주소, 그 사용자의 `NotificationOutbox` 행 전부(미발송, 재시도 대기, 포기, 발송 완료를 가리지 않는다), 그리고 이 작업의 `LoginRecord` 전부와 응답의 `did` 쿠키.

탈퇴와 알림 발송이 겹칠 때의 경계는 PR #5 head `dd4b29a`의 T3-02 계획 탈퇴 절 글을 그대로 따른다. 탈퇴 commit 전에 발송 확인을 마친 발송 1건은 끝까지 갈 수 있고 탈퇴 commit 뒤에 확인을 시작한 발송은 보내지 않고 outbox 행을 지운다. 이 작업은 이 경계를 바꾸지 않는다.

- T3-05가 먼저 병합되면 T3-02가 자기 탈퇴 트랜잭션에 `LoginRecord` 삭제와 `did` 쿠키 삭제를 넣는다.
- T3-02가 먼저 병합되어 있으면 이 작업이 그 트랜잭션에 같은 두 줄을 더하고 T3-02 통합 시험에 행을 더한다.
- 로그인과 탈퇴가 겹쳐도 탈퇴 뒤에 `LoginRecord`가 생기면 안 된다. 로그인 기록을 쓰는 트랜잭션은 `User` 행을 `FOR SHARE`로 잠근 뒤 `status = ACTIVE`를 다시 확인하고 쓴다. 탈퇴는 `User` 행을 `FOR UPDATE`로 잠근다.
- `Sanction`·`AuditLog`는 탈퇴해도 남는다. 두 표에는 사용자 UUID만 있고 이메일·IP·해시를 넣지 않는다. 제재 사유 입력란은 개인정보를 쓰지 말라는 안내를 둔다 (T3-06).

### 감사 로그

- 관리자 API와 실행기, 명령줄 관리 명령의 모든 변경 조치는 그 조치와 같은 트랜잭션에서 `AuditLog` 한 행 이상을 쓴다. 감사 로그 쓰기가 실패하면 조치도 롤백된다.
- 개인정보를 내보내는 조회도 호출마다 남긴다. 대상은 이메일·계정 상태·제재·로그인 기록·공유 묶음을 응답에 싣는 절차 셋이다.

  | 절차 | `action` | 남기는 것 |
  | ---- | -------- | --------- |
  | `admin.user.search` | `user.search` | `at`, `actorUserId`, `payload = { queryKind, resultCount }`. `queryKind`는 `EMAIL_PREFIX`·`USER_ID`·`GENERAL_NAME` 중 하나다. `GENERAL_NAME`이면 `worldId` 열도 채운다. `targetId`는 비운다 |
  | `admin.user.get` | `user.view` | `at`, `actorUserId`, `targetType = USER`, `targetId = userId` |
  | `admin.investigate.shared` | `investigate.shared.view` | `at`, `actorUserId`, `worldId`, `payload = { days, groupCount }` |

- 검색 감사에는 검색어 원문, 이메일 앞부분, 장수 이름, 결과에 나온 이메일과 사용자 ID를 넣지 않는다. 사용자 ID로 찾은 경우에도 그 ID를 `targetId`나 `payload`에 넣지 않는다. 남는 것은 누가, 언제, 어떤 종류로 찾아, 몇 건을 받았는지뿐이다.
- 세 조회는 결과를 읽는 쿼리와 감사 행 쓰기를 한 트랜잭션에서 한다. 감사 행 쓰기가 실패하면 트랜잭션을 롤백하고 `INTERNAL_SERVER_ERROR`로 끝내며 결과를 응답에 싣지 않는다. 기록 없이 개인정보가 나가는 경로를 두지 않는다. 결과가 0건이어도 감사 행은 쓴다.
- `payload`에는 바뀌기 전후 값과 요청 ID만 둔다 (조회 감사는 위 표의 값만). 이메일, IP, 해시, 비밀번호, 토큰, 웹훅 주소는 넣지 않는다. 대상 사용자는 UUID로만 가리킨다.
- `action` 값: `world.create`, `world.start`, `world.pause`, `world.resume`, `world.end`, `world.reset`(각각 `.requested`·`.applied`·`.rejected`), `notice.create`, `notice.update`, `notice.hide`, `sanction.create`, `sanction.lift`, `user.search`, `user.view`, `investigate.shared.view`, `admin.grant`, `admin.revoke`.
- 수정·삭제 API는 없다. migration의 트리거가 `UPDATE`·`DELETE`를 거부한다. 보관 기한은 정하지 않고 계속 둔다. 기한을 두려면 개인정보처리방침과 함께 소유자가 정한다.
- 조회는 관리자만 한다. 필터는 기간, `action` 앞부분, 행위자, 대상, 월드이고 `id` 내림차순 커서로 50개씩 준다.

### API 계약

```ts
admin.whoami() → { admin: true }                                         // 관리자가 아니면 FORBIDDEN

admin.world.list() → [{ id, name, status, scenarioKey, presetKey, turnTermMinutes, humanGenerals,
                        heartbeat: { at, lastTick, lagMs, lastError } | null }]
admin.world.create({ idempotencyKey, name, scenarioKey, mapKey, presetKey?, seed?, turnTermMinutes? }) → { requestId }
  // presetKey는 T2-02 병합 뒤. 그 전에는 받지 않는다
admin.world.createStatus({ requestId }) → { status: 'PENDING' | 'DONE' | 'FAILED', worldId?, error? }
admin.world.control({ idempotencyKey, worldId, action: 'start' | 'pause' | 'resume' | 'end', reason })
  → { inputEventId }
admin.world.reset({ idempotencyKey, worldId, confirmName, reason, seed? }) → { inputEventId }
admin.world.request({ inputEventId }) → { status: 'PENDING' | 'APPLIED' | 'REJECTED', result }

admin.notice.list({ scope: 'LOBBY' | 'WORLD', worldId? })
admin.notice.create({ scope, worldId?, title, body }) / update({ id, title, body }) / hide({ id, reason })

admin.user.search({ query }) → [{ userId, email, status, role, createdAt, activeSanctions }]
  // query: 이메일 앞부분(3자 이상), userId, 또는 { worldId, generalName }
  // 호출마다 감사 user.search (검색 종류·결과 수만). 감사 쓰기 실패면 INTERNAL_SERVER_ERROR, 결과 없음
admin.user.get({ userId }) → { userId, email, status, role, createdAt, generals: [{ worldId, generalId, name }],
                               sanctions: [...], recentLogins: [{ at, success, ipLabel, deviceLabel }] }
  // 호출마다 감사 user.view. 실패 규칙은 search와 같다
admin.sanction.create({ userId, worldId | null, reason, expiresAt | null }) → { sanctionId }
admin.sanction.lift({ sanctionId, reason }) → { ok: true }

admin.investigate.shared({ worldId, days?: 1..90 }) →
  [{ kind: 'IP' | 'DEVICE', label, users: [{ userId, generalId, generalName, logins, lastAt }] }]
  // 그 월드에 장수가 있는 사용자만, 서로 다른 사용자 2명 이상인 묶음만
  // 호출마다 감사 investigate.shared.view. 실패 규칙은 search와 같다

admin.audit.list({ cursor?, from?, to?, action?, actorUserId?, targetId?, worldId? }) → { items, next }

sanction.mine() → [{ worldId, worldName, reason, expiresAt }]                 // 로그인 필요, 본인 것만
```

- 입력은 모두 zod `strictObject`이며 `reason`·`title`은 앞뒤 공백을 지운 1~200자, `body`는 1~2,000자다.
- 사용자 조회 결과의 `email`은 관리자 화면에만 나간다. 탈퇴 계정은 T3-02가 바꾼 `withdrawn+<userId>@invalid`가 그대로 보인다.
- 오류는 `data.code`로 구분한다. 이 작업이 새로 던지는 오류의 `data.reason`은 항상 `null`이다. 앞 단계인 T3-02 인증·동의 검사가 낸 `data.reason`은 그대로 나간다.

### 검증

통합 시험은 `pnpm test:int`의 실제 PostgreSQL과 주입한 시계로 한다. 실행기는 같은 시험 안에서 실제로 돌린다.

| 공통 | 동시성 | 두 관리자가 같은 월드를 동시에 일시정지 → 하나 APPLIED, 하나 REJECTED, 시계 변경 1회. 같은 `idempotencyKey` 동시 두 번 → 요청 1행. 제재 생성과 해제가 겹쳐도 유효 제재 판정이 한쪽 결과와 일치 |
| 공통 | 탈퇴 의무 | 탈퇴 → `LoginRecord` 0행, 응답에 `did` 삭제. 로그인과 탈퇴를 20번 동시에 경합 → 탈퇴가 이긴 모든 경우에 `LoginRecord` 0행 |
| 공통 | 비밀값 | 로그 스트림에 IP·`did`·이메일·`AUDIT_HASH_KEY` 없음. 운영 설정에서 키가 없으면 시작 실패 |

### 사용자 결정 대기

이 계획은 아래를 정하지 않는다. 정해지기 전에는 적어 둔 기본 동작으로 구현한다.

| 항목 | 기본 동작 | 정할 사람 |
| ---- | --------- | --------- |
| 계정 전체 제재 사유를 로그인 화면에 보여 줄지 | 보여 주지 않는다. 틀린 비밀번호와 같은 문구다. 보여 주려면 T3-02 소유의 `data.reason`에 새 값이 필요하다 | 소유자, T3-02 |
| IP를 HMAC 해시로만 저장, `LoginRecord` 90일, `AuditLog` 무기한 | 위 표 그대로 | 소유자 (T3-03 개인정보처리방침 초안, T3-15 공개 전 확인) |
| IPv6를 /64 접두어로 묶을지 | 주소 전체를 해시한다 | 소유자 |
| 사람 장수가 있는 운영 월드의 종료·초기화 승인 절차 | 에이전트는 실행하지 않는다. 화면은 이름 재입력과 사유만 강제한다 | 소유자 |
| 있는 계정만 실패 기록을 쓰는 데서 생기는 응답 시간 차이 | 받아들인다. 가입 `CONFLICT`(T1-10, T3-04 하지 않는 것)와 같은 수준의 계정 존재 노출이다 | 소유자 |

### 상대 영역에 필요한 것 (T3-06)

- 위 API 계약, `admin.whoami()`로 하는 가드, 월드 조치가 비동기(PENDING → APPLIED·REJECTED)라는 점과 상태 조회 API.
- E2E용 관리자 계정을 만드는 방법: 시험 준비에서 `pnpm admin:grant`를 표준 입력으로 실행한다.
- E2E가 월드 조치를 끝까지 보려면 실행기가 떠 있어야 한다. 이 작업은 `pnpm engine:run`을 `--world` 없이 띄운 T2-01 감독(`apps/engine/src/index.ts:22-26`)에서 실행기가 함께 도는지 확인하고 Playwright 실행 방법을 runtime.md에 적는다.
