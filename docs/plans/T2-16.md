### 1단계 순수 renderer

#### 파일

- `tools/docs/command-catalog.ts`: 입력 타입, `renderCommandCatalog`, `CommandCatalogError`. `node:fs`·`zod`·`@opensamguk/rules`를 import하지 않는다. 분류 순서와 이름표는 입력으로 받는다.
- `tools/docs/command-catalog.test.ts`: 정상 시험군과 오류 시험군 (아래 시험 절). `vitest.config.ts:5`가 이미 `tools/**/*.test.ts`를 포함하므로 설정은 고치지 않는다.
- 그 밖의 파일은 고치지 않는다. `tools/command-coverage.*`는 등록 key와 대응표 대조(`command-coverage.mjs:49-71`, `:946-951`)를 이미 하므로 다시 만들지 않는다.

#### 입력과 출력

```ts
export interface CatalogCategory {
  id: string;      // CommandDef.category 값
  heading: string; // ### 소제목이자 분류 열 값. 가이드 링크의 앵커가 된다
}
export interface CatalogCommand {
  target: 'general' | 'nation';
  key: string;                      // 중복 검사에만 쓴다. 표에는 내지 않는다
  category: string;                 // categories의 id
  name: string;
  summary: string;
  inputFields: readonly string[];   // 넣을 수 있는 인자 필드 이름. 넣으면 안 되는 필드는 어댑터가 미리 뺀다
  requires: readonly string[];
  cost: string | null;
  unavailableIn: readonly string[]; // 이 명령을 쓸 수 없는 프리셋 이름. 순서는 어댑터가 정한다
}
export interface CatalogInput {
  categories: readonly CatalogCategory[];        // 소제목 순서. 3단계 어댑터는 COMMAND_CATEGORIES 순서로 넣는다
  fieldLabels: Readonly<Record<string, string>>; // JSON 이름표. 인자 필드 이름 → 표에 쓸 이름
  commands: readonly CatalogCommand[];           // 등록 순서
}
export interface CatalogIssue {
  code:
    | 'DUPLICATE_KEY'      // 같은 target 안 key 중복
    | 'DUPLICATE_NAME'     // 같은 target 안 화면 이름 중복
    | 'UNKNOWN_CATEGORY'   // categories에 없는 분류
    | 'DUPLICATE_CATEGORY' // categories 안 id 중복
    | 'UNKNOWN_FIELD'      // fieldLabels에 없는 인자 필드
    | 'EMPTY_TEXT'         // 표시 문구가 value.trim() === ''
    | 'LINE_BREAK';        // 표시 문구에 LF나 CR
  path: string;            // 아래 path 형식
}
export class CommandCatalogError extends Error {
  readonly issues: readonly CatalogIssue[];
}
export function renderCommandCatalog(input: CatalogInput): string;
```

- 입력은 3단계 어댑터와 시험이 만드는 내부 DTO다. renderer는 타입이 정한 모양(문자열, 배열, `null`)을 믿고 `unknown` 입력 전체를 검사하지 않는다. 빠진 속성이나 문자열이 아닌 값은 TypeScript 타입과 3단계 어댑터가 막는다.
- 값은 식별자와 표시 문구로 나뉜다. 식별자는 `key`, `category`, `categories[].id`, `inputFields` 항목, `fieldLabels`의 키다. renderer는 식별자를 비교하고 찾는 데만 쓰고 표에 쓰지 않는다. 식별자에 새 문법 제한을 두지 않는다. 빈 `category`나 빈 `inputFields` 항목은 목록에 없으면 `UNKNOWN_CATEGORY`·`UNKNOWN_FIELD`로 걸린다. `key`의 형식(빈 문자열 포함)은 1단계에서 보지 않는다.
- 식별자의 소속과 중복은 `Set`·`Map`으로만 본다. 일반 객체를 색인으로 쓰지 않으므로 `toString`, `constructor`, `__proto__` 같은 이름도 다른 문자열과 똑같이 다룬다. 분류 id는 `Set` 하나, key와 name은 target마다 `Set` 하나씩이다.
- `fieldLabels`는 JSON 데이터 전제다. renderer는 `Object.keys(fieldLabels)`(자기 소유, 열거 가능, 문자열 키)로 `Map`을 한 번 만들고 이름표 값 검사와 `inputFields` 찾기를 모두 이 `Map`으로 한다. 상속된 키, 열거되지 않는 키, symbol 키는 이름표가 아니다. `in`, 값의 참거짓, `fieldLabels[field]` 직접 읽기로 판정하지 않는다. 접근자나 문자열이 아닌 값은 DTO 전제라 따로 검사하지 않는다.
- 표시 문구는 `name`, `summary`, `requires` 항목, 문자열인 `cost`, `unavailableIn` 항목, `fieldLabels` 값, `categories[].heading`이다. 글자 규칙은 아래 절이다. `cost: null`, `requires: []`, `unavailableIn: []`, `inputFields: []`는 정상이다.
- `renderCommandCatalog`는 입력을 바꾸지 않고 같은 입력에 같은 문자열을 돌려준다. 시각, 환경 값, 경로를 읽지 않는다.
- 모든 검사를 먼저 하고 문제가 하나라도 있으면 문서 없이 `CommandCatalogError`를 던진다. `commands`가 비어도, 행이 없어 쓰지 않을 분류의 heading과 쓰이지 않는 이름표 값도 모두 검사한다.
- 같은 target에서 두 번째 이후로 나온 쪽에 중복 issue를 붙인다. 공백뿐이거나 줄바꿈이 든 name도 그대로 중복 비교에 들어간다. 다른 target끼리 같은 key나 name은 통과다(P5). 장수 `rest`와 국가 `nation_rest`가 모두 휴식이다(`rest.ts:5-6`, `nation.ts:106-107`).
- 같은 분류가 장수·국가 두 절에 모두 나와도 거부하지 않는다. 두 절에 같은 `###` 소제목이 생긴다. 앵커 충돌 처리는 후속 의존 P4다.

`issues`는 아래 표의 검사 순서대로 쌓인다. 한 path에 여러 문제가 있으면 `EMPTY_TEXT` → `LINE_BREAK` → 중복·미등록 코드 순서다.

| 차례 | 대상 | 항목 안 순서와 코드 |
| ---- | ---- | ------------------- |
| 1 | `categories`를 앞에서부터 | `id`(`DUPLICATE_CATEGORY`) → `heading`(`EMPTY_TEXT`, `LINE_BREAK`) |
| 2 | `fieldLabels`를 `Object.keys` 순서로 | 값(`EMPTY_TEXT`, `LINE_BREAK`). 정수 모양 키가 오름차순으로 먼저, 나머지는 넣은 순서다. 따로 정렬하지 않는다 |
| 3 | `commands`를 앞에서부터 | `key`(`DUPLICATE_KEY`) → `category`(`UNKNOWN_CATEGORY`) → `name`(`EMPTY_TEXT`, `LINE_BREAK`, `DUPLICATE_NAME`) → `summary` → `inputFields` 항목 차례(`UNKNOWN_FIELD`) → `requires` 항목 차례 → 문자열인 `cost` → `unavailableIn` 항목 차례. 표시 문구는 `EMPTY_TEXT`, `LINE_BREAK` |

path 형식은 `categories[i].id`, `categories[i].heading`, `fieldLabels[k]`, `commands[i].필드`, 배열 항목은 뒤에 `[j]`를 붙인다. 번호는 0부터다. `k`는 키를 `JSON.stringify`한 문자열이라 점, 따옴표, 대괄호가 든 키도 갈리지 않는다. 예: 키 `a.b"[0]`의 path는 `fieldLabels["a.b\"[0]"]`이다.

1단계에는 바이트 비교 헬퍼를 만들지 않는다. renderer는 문자열만 돌려주고 바이트 비교는 3단계 CLI의 일이다(생성 규칙의 `--check`).

#### 출력 모양

```md
<!-- 직접 수정 금지. 생성 명령: pnpm docs:generate -->

# 명령 목록

## 장수 명령

### 내정

| 분류 | 화면 이름 | 한 줄 설명 | 대상·수량 입력 | 조건 | 비용 |
| --- | --- | --- | --- | --- | --- |
| 내정 | … | … | 없음 | 없음 | 없음 |

## 국가 명령

### 국가

| 분류 | 화면 이름 | 한 줄 설명 | 대상·수량 입력 | 조건 | 비용 |
| --- | --- | --- | --- | --- | --- |
| 국가 | … | … | … | … | … |
```

- 머리 줄과 제목 `# 명령 목록` 다음에 `## 장수 명령`, `## 국가 명령` 순서로 쓴다. 절 안 `###`은 `categories` 순서, 소제목 안 행은 `commands` 순서다. renderer는 정렬하지 않는다.
- 머리 줄 `<!-- 직접 수정 금지. 생성 명령: pnpm docs:generate -->`와 제목 `# 명령 목록`을 쓴다(P6). 기존 결정(직접 수정 금지와 생성 명령을 적는다)을 채운다.
- target마다 그 target의 행이 있는 분류만 `###`을 쓰고 행이 하나도 없는 target은 `##` 절을 쓰지 않는다(P2).
- `commands`가 비면 머리 줄, 빈 줄, 제목만 돌려준다(P3). JS 리터럴로 `'<!-- 직접 수정 금지. 생성 명령: pnpm docs:generate -->\n\n# 명령 목록\n'`이다. 이때도 선검증은 그대로라 분류나 이름표에 문제가 있으면 오류다.
- 블록 사이는 빈 줄 하나, 줄 끝은 LF, 문서 끝은 LF 하나다. 줄 끝 공백과 표 정렬 공백을 넣지 않는다. `*.md`는 프리티어 대상이 아니다(`.prettierignore:4`).
- 칸 값은 이렇다. 분류는 `heading`, 화면 이름은 `name`, 한 줄 설명은 `summary`다. 대상·수량 입력은 `inputFields`를 받은 순서대로 `fieldLabels`로 바꿔 `, `로 잇고 비면 `없음`이다. 비용은 `cost`이고 `null`이면 `없음`이다.
- 조건 칸은 `requires` 항목 뒤에 `unavailableIn`이 있을 때 `일부 월드에서는 쓸 수 없음: ` + 프리셋 이름을 `, `로 이은 항목 하나를 더하고 `<br>`로 잇는다. 둘 다 비면 `없음`이다.

#### 글자 규칙

- 검사(R63-12, P7): 모든 표시 문구에서 `value.trim() === ''`이면 `EMPTY_TEXT`, LF나 CR이 있으면 `LINE_BREAK`다. 한 값이 둘 다면(예: LF 한 글자) `EMPTY_TEXT` 다음 `LINE_BREAK`다. 앞뒤 공백은 지우지 않고 원문 그대로 쓴다.
- 바꾸기(P1, R63-12): 표 칸 값마다 먼저 `\`→`\\`로 두 배로 하고 그다음 R63-12 순서대로 `&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;`, `|`→`\|`로 바꾼다. 그 뒤에 `<br>`와 `, `로 잇는다. `없음`과 `일부 월드에서는 쓸 수 없음: `은 renderer 상수라 바꾸지 않는다.
- `heading`은 분류 칸에서는 위처럼 바꾸고 `###` 소제목 줄에는 원문 그대로 쓴다.
- 역슬래시를 먼저 두 배로 하는 이유: R63-12 규칙만 쓰면 원문 `\|`가 `\\|`가 된다. GFM 표는 뒤의 `\|`를 이스케이프된 파이프로 풀고 남은 `\|`를 다시 `|`로 풀어 원문의 역슬래시가 사라진다. 두 배로 하면 `\\\|`가 되어 GFM에서 원문 `\|`로 보인다. 역슬래시가 든 입력은 거부하지 않는다.
- 이 규칙은 GFM 기준이다. 지금 도움말 해석기에서 다르게 보이는 점은 후속 의존 Q8이다.
- 그 밖의 Markdown 기호(`*`, `` ` ``, `[` 등) 정책은 1단계 범위 밖이다. renderer는 이 기호를 바꾸지 않는다.

예는 문자를 그대로 적었다. 시험 코드의 JS 문자열 리터럴에서는 역슬래시를 한 번 더 쓴다(E3 원문은 `'a\\|b'`, 출력 칸은 `'a\\\\\\|b'`).

```text
예   원문                      출력 칸
E1   내 도시 | 보급 연결        내 도시 \| 보급 연결
E2   <b>재야</b> & 군주 제외   &lt;b&gt;재야&lt;/b&gt; &amp; 군주 제외
E3   a\|b                      a\\\|b
E4   a\b                       a\\b
```

#### 시험 (1단계)

`pnpm vitest run tools/docs/command-catalog.test.ts`로 돌린다. 정상 시험군과 오류 시험군으로 나누고 사례마다 `it.each`나 개별 `it`으로 이름을 붙여 어느 사례가 실패했는지 바로 보이게 한다. 시험 수는 정하지 않는다.
시험 입력 문구와 이름표는 시험용 값이고 제품 문구가 아니다. 분류 소제목은 지금 링크에 맞춰 `domestic` 내정, `military` 군사, `strategy` 인사, `personal` 개인, `nation` 국가로 넣는다. 아래는 계획한 시험이며 아직 작성하거나 실행하지 않았다.

기본 입력은 아래 순서로 등록한 여섯 명령이다. 조건의 E1·E2는 글자 규칙의 예다. `fieldLabels`는 객체 리터럴 `{ amount: '수량', cityKey: '도시' }`이다.
시험 표의 `'…'` 값은 JS 문자열 리터럴이다(`'\n'`은 LF 한 글자). path는 문자 그대로 적었다.

| 등록 순서 | target·분류 | key·화면 이름 | 그 밖의 값 |
| --------- | ----------- | ------------- | ---------- |
| 1 | 장수 개인 | `rest` 휴식 | 입력·조건·프리셋 없음, `cost: null` |
| 2 | 국가 국가 | `nation_rest` 휴식 | 입력·조건·프리셋 없음, `cost: null` |
| 3 | 장수 군사 | `recruit` 모병 | 입력 `['amount', 'cityKey']`, 조건 E1·E2, 비용 `금 100`, 프리셋 `['작은 월드', '빠른 월드']` |
| 4 | 장수 내정 | `farm` 농지개간 | 비용 `금 50` |
| 5 | 장수 군사 | `move` 이동 | 입력 `['cityKey']`, 프리셋 `['작은 월드']` |
| 6 | 장수 인사 | `resign` 하야 | 입력·조건·프리셋 없음, `cost: null` |

정상 시험군은 기본 입력의 전체 문자열이 기대값과 같은지 본다. 기대값에서 확인할 것은 이렇다.

- 장수 절이 내정 → 군사 → 인사 → 개인 순서이고 국가 절이 뒤다. 등록이 먼저인 휴식도 개인 소제목에 있다.
- 국가 절에는 `### 국가`만 있고 장수 절에는 `### 국가`가 없다(target별 생략, P2).
- 군사 안에서 모병이 이동보다 먼저다(등록 순서). 모병 입력 칸은 `수량, 도시`다(정렬 안 함).
- 칸 셋이 비면 `없음`이다. 이동의 조건 칸은 프리셋 항목만이다. 다른 target의 같은 이름(휴식)이 통과한다.
- 두 번 부른 결과가 같고 `\r`이 없고 끝이 LF 하나이며 얼린 입력이 바뀌지 않는다.

모병 행의 기대값(문자 그대로)은 이렇다. 한 줄 설명은 시험 값 `병사를 뽑는다`다.

```text
| 군사 | 모병 | 병사를 뽑는다 | 수량, 도시 | 내 도시 \| 보급 연결<br>&lt;b&gt;재야&lt;/b&gt; &amp; 군주 제외<br>일부 월드에서는 쓸 수 없음: 작은 월드, 빠른 월드 | 금 100 |
```

정상 시험군에 아래 사례도 넣는다. 모두 오류 없이 문서가 나온다.

| 사례 | 기본 입력에서 바꾼 것 | 기대 |
| ---- | --------------------- | ---- |
| 빈 분류 생략 | 6번(하야)을 뺌 | 장수 절에 `### 인사`가 없고 나머지는 기본 기대값과 같음 |
| 빈 절 생략 | 2번(국가 휴식)을 뺌 | `## 국가 명령` 절이 없음 |

#### 1단계에서 확인할 의존 사항

- 도움말 해석기는 HTML 문자 참조를 되돌리지 않고 `<br>`도 다루지 않는다(`markdown.ts:30-43`). 지금 화면에서는 `&amp;`, `<br>`이 글자 그대로 보인다.
  표 칸에서는 `\|`만 `|`로 풀고 다른 역슬래시 이스케이프는 풀지 않는다(`markdown.ts:50-51`). 그래서 P1로 바꾼 E3·E4는 지금 화면에서 역슬래시가 두 개로 보인다. 출력은 GFM 기준으로 두고 해석기를 맞추는 일은 Q8이다.
  해석기 수정은 프론트 담당(Claude) 일이고(Q8) 이 작업은 `apps/web`를 고치지 않는다. R63-12의 바꾸기 규칙도 약하게 하지 않는다.
- 생성물은 `docs/` 아래라 4단계 뒤에는 `pnpm lint:text --strict`(`package.json:19`) 대상이 된다. 2단계 문구가 글쓰기 검사를 통과해야 한다.
- 루트 `tsconfig.json`이 없어 `pnpm typecheck`(`pnpm -r typecheck`)가 `tools/`의 TS를 보는지 이번에 확인하지 못했다. vitest는 타입을 검사하지 않는다. 구현자가 확인해 구현 기록에 적는다.

### 후속 단계 (2~4단계)

#### 범위

- `tools/docs/generate-command-catalog.ts` → `docs/user/command-catalog.generated.md`. 3단계 어댑터와 CLI이며 1단계 `renderCommandCatalog`를 부른다.

#### 결정

- 표 열: 분류 · 화면 이름 · 한 줄 설명 · 대상·수량 입력 · 조건 · 비용. 장수 명령과 국가 명령을 나눈다.
- 프리셋별로 쓸 수 없는 명령이 있으면 `일부 월드에서는 쓸 수 없음`과 프리셋 이름을 적는다 (T2-02).
  이 열은 T2-02가 리뷰를 통과한 커밋의 프리셋 정의를 읽는다. 그 커밋 SHA를 구현 기록에 적는다. 프리셋이 하나도 없으면 빈 목록이다.
  프리셋이 레지스트리에 없는 명령 키를 가리키면 생성이 실패한다. 지금은 `presetSchema`가 이미 거부한다(`preset.ts:56-62`). 무엇을 쓸 수 없는 명령으로 볼지는 Q3이다.
- 생성 파일 머리에 직접 수정 금지와 생성 명령을 적는다.
- 설명 문구(`summary` 등)는 Codex가 규칙 기준으로 쓰고 표현 다듬기는 T2-17에서 Claude가 리뷰 때 제안한다.
- 틀은 원작 생성기(core2026 `tools/docs/generate-command-reference.mjs`, 생성물 `docs/user/command-catalog.generated.md`)의 분류별 표와 머리 경고를 따른다. 조건·비용 열은 v1 도움말의 이 명령의 규칙(누가·언제·어디에·대상·비용, v1 `web/game/components/help/HelpTopicView.tsx:44-56`)에서 가져온다. 2026-10-24 정정 때는 v1 원문을 볼 수 없어 이 근거를 다시 대조하지 않았다.

#### 가이드(T2-17)가 기대하는 생성 결과 모양

2단계는 명령 정의(`packages/rules/src/commands/types.ts:51-60`의 `CommandDef`)에 아래 필드를 더한다. 지금 `CommandDef`에는 `doc`이 없다.

```ts
interface PlayerDoc {
  summary: string;      // 한 줄. 무엇이 바뀌는지를 쓴다. 빈 문자열이면 생성 실패
  requires: string[];   // 실행 조건 한 줄씩. 조건이 없으면 [] (표에는 '없음')
  cost: string | null;  // 비용 한 줄. 없으면 null (표에는 '없음'). 공식 대신 무엇을 얼마나 쓰는지만
}
interface CommandDef<Args = unknown> {
  // 기존 필드 그대로
  doc: PlayerDoc;
}
```

공유 이름표는 아직 rules에 없다. 계획의 제안과 지금 있는 것을 나눠 적는다.

| 이름표 | 계획 제안 | 지금 있는 것 |
| ------ | --------- | ------------ |
| 분류 화면 이름 | rules 한곳의 `COMMAND_CATEGORY_NAMES`. `strategy`는 인사 | 없음. 편집기는 `CommandPicker.tsx:14-20`의 `CATEGORY_LABELS`로 `strategy`를 전략으로 보인다. 가이드는 `#인사`로 링크한다(`docs/user/commands-and-timing.md:14`) |
| 인자 필드 화면 이름 | rules 한곳의 표. 예: `cityKey` 도시, `amount` 수량, `crewType` 병종, `nationId` 국가 | 없음. 편집기는 `args.ts:13-23`의 `LABELS`로 `cityKey` 대상 도시, `crewType` 병종 번호처럼 다른 값을 쓴다 |

전략과 인사 가운데 무엇으로 통일할지는 후속 담당이 정한다(Q1). 이번 정정은 이름을 고르지 않는다. 정해질 때까지 가이드 링크 `#내정`·`#군사`·`#인사`·`#개인`·`#국가`는 그대로 둔다.

3단계 어댑터는 `CommandDef`마다 1단계 `CatalogCommand` 하나를 만든다. 예전 `CatalogRow`의 `needsInput: boolean`은 필드 이름 열을 만들 수 없고 중복 검사에 쓸 `key`도 없어 `CatalogCommand`로 바꿨다.
`inputFields`는 `z.toJSONSchema(def.args, { io: 'input' })`의 `properties` 이름에서 `not`이 있는 필드를 뺀 목록이다. 무작위 임관처럼 스키마가 빈 객체가 아니어도 넣을 필드가 없으면 `[]`이고 표에는 없음이다.

#### 생성 규칙 (검토 R63-12, 2026-10-21 추가, 2026-10-24 줄 번호와 담당 정정)

- 원천은 레지스트리 전체다(`packages/rules/src/commands/registry.ts:11-19`의 `commands`). 장수 명령과 국가 명령을 모두 담는다.
  `commands.list` API는 장수 명령만 내므로(`apps/server/src/routers/commands.ts:15-25`, `resolver.list('general')`) 원천으로 쓰지 않는다. 확장 명령(`extensionCommands`)을 넣을지는 Q3이다.
- 지금 레지스트리는 37개(장수 27, 국가 10)지만 이 수를 고정값으로 시험하지 않는다. 3단계 시험은 생성된 행 수가 그때의 레지스트리 수와 같은지만 본다. 명령이 바뀌면 다시 생성한다.
- 행은 `(target, key)`마다 하나다. 절 순서는 장수 → 국가, 소제목 순서는 `COMMAND_CATEGORIES`(`packages/rules/src/commands/types.ts:49`), 소제목 안은 등록 순서다.
  같은 target 안에서 key나 화면 이름이 겹치거나 분류가 목록에 없으면 1단계 renderer가 실패한다. target 간 같은 key는 renderer가 아니라 3단계 어댑터가 기존 레지스트리 계약대로 확인한다(P5). `doc`이 빠졌으면 2·3단계가 실패한다.
- 대상·수량 입력 열: 명령의 zod 입력 스키마(`z.toJSONSchema(def.args, { io: 'input' })`, `commands.ts:12`·`:23`과 같은 방식)에서 넣을 수 있는 필드 이름을 뽑아 rules 한곳의 화면 이름 표로 바꿔 쓴다.
  필드가 없으면 없음이다. 표에 없는 필드 이름이 나오면 renderer가 실패한다.
- 칸 글자 처리: 1단계 글자 규칙을 따른다. 줄바꿈이 있으면 실패하고 `&`·`<`·`>`를 HTML 문자 참조로, `|`를 `\|`로 바꾼 뒤에 `requires`를 `<br>`로 잇는다. 그보다 먼저 역슬래시를 두 배로 한다(P1).
- 출력은 UTF-8, 줄 끝 LF, 마지막 줄바꿈 하나다. 생성 시각·환경 값·절대 경로를 넣지 않는다. 같은 커밋에서 두 번 생성하면 바이트가 같다. 문자열은 1단계가, UTF-8 쓰기는 3단계 CLI가 맡는다.
- `pnpm docs:generate --check`는 파일을 쓰지 않는다. renderer 문자열을 BOM 없는 UTF-8로 바꾼 바이트와 저장된 파일을 읽은 그대로의 바이트를 비교해 다르면 실패한다. CRLF, BOM, 잘못된 UTF-8을 정규화하거나 디코딩해서 같게 만들지 않는다. 파일을 쓰지 않는지 보는 시험도 3단계 몫이다. `pnpm check`는 이 검사를 부른다.
- 루트 `package.json`과 `pnpm check` 연결은 T2-16 구현자(Codex) 한 사람이 한 커밋에서 바꾼다.

### 기술 선택과 남은 의존

조정자가 받아들인 1단계 기술 선택이다. 위 본문, 오류 계약, 시험 표가 이를 따른다.

| ID | 선택 |
| -- | ---- |
| P1 | 표 칸 값의 역슬래시를 다른 바꾸기보다 먼저 두 배로 하고 그 뒤 R63-12 순서로 `& < > \|`를 바꾼다(E3·E4). 역슬래시를 거부하지 않는다 |
| P2 | target마다 행이 없는 분류 소제목과 행이 없는 절을 쓰지 않는다. 편집기도 빈 분류를 숨긴다(`CommandPicker.tsx:133-136`) |
| P3 | 빈 `commands`는 머리 줄과 제목만 돌려준다. `EMPTY_CATALOG` 오류는 없다. 선검증은 그대로다 |
| P5 | renderer는 같은 target 안 key·name 중복만 오류다. target 간 같은 key는 3단계 어댑터가 기존 레지스트리 계약대로 확인한다 |
| P6 | 머리 줄 `<!-- 직접 수정 금지. 생성 명령: pnpm docs:generate -->`와 제목 `# 명령 목록`. 해석기는 주석을 지워 화면에 보이지 않는다(`markdown.ts:58`) |
| P7 | 모든 표시 문구에서 공백뿐인 값과 LF·CR을 거부한다. 앞뒤 공백은 지우지 않는다 |

후속 담당에 남은 의존 사항이다.

| ID | 무엇 | 정할 쪽 |
| -- | ---- | ------- |
| P4 | 같은 분류가 장수·국가 두 절에 나올 때의 앵커 충돌. GFM은 뒤 제목에 `-1`을 붙이고 지금 해석기 `slug`는 중복을 나누지 않는다(`markdown.ts:20-26`). 읽은 국가 명령(`nation.ts`)은 모두 `nation` 분류다. renderer는 거부하지 않는다 | 가이드 담당(T2-17, Claude) |
| Q1 | `strategy`의 화면 이름(편집기 전략, 계획·가이드 인사)과 공유 분류 이름표의 위치. 확장 계략(`ext/stratagem/fire_attack.ts:17`)도 `strategy`다 | 사용자, 후속 담당 |
| Q2 | 인자 필드 이름표의 값과 위치(편집기 `LABELS`와 맞출지), 선택 필드(원조의 `resource`·`amount`, `nation.ts:47-51`) 표시 | 사용자, Codex |
| Q3 | `unavailableIn`의 뜻. 지금 프리셋은 확장 명령을 켜는 목록이고(`preset.ts:47-50`) 기본 명령은 늘 켜져 있다(`resolve.ts:36-43`). 확장 명령을 목록에 넣을지, 켜지 않은 프리셋을 쓸 수 없는 곳으로 볼지, 프리셋 이름의 출처와 순서 | 사용자, T2-02 |
| Q8 | 도움말 해석기의 문자 참조·`<br>`·역슬래시 이스케이프 처리. 지금 화면의 표시 보장은 이 수정 뒤다 | 프론트 담당(Claude) |

### 검증

| 단계 | 무엇 | 어떻게 |
| ---- | ---- | ------ |
| 1 | 출력 계약 | 계획한 정상 시험군: 기본 입력 → 기대 문자열과 같음, 두 번 같음, LF, 끝 줄바꿈 하나, 입력 그대로. 빈 분류·절 생략, 빈 목록 문자열, target 간 같은 key, 역슬래시, 자기 소유 원형 이름 이름표 |
| 1 | 입력 검사 | 계획한 오류 시험군: 위 표의 잘못된 입력마다 정확한 `issues` 순서, 문서 없음 |
| 3 | 생성 | `pnpm docs:generate` → 행 수 = 그때 레지스트리 수, 장수·국가 명령 모두 있음 |
| 3 | 결정성 | 단위: 두 번 생성한 파일 바이트가 같음 |
| 3·4 | 최신 검사 | 명령 설명 한 줄을 바꾸고 생성 안 함 → `--check` 실패, 파일은 그대로. `pnpm check` 실패 |
| 2·3 | 누락 | 단위: 빠진 `doc` → 생성 실패 |
| 3 | 입력 열 | 단위: 넣으면 안 되는 필드(`z.never().optional()`)는 빠짐, 인자 없는 명령 → 없음 |
| 3 | 프리셋 | 단위: 프리셋 없음 → 빈 목록. 없는 명령 키는 `presetSchema` 거부가 생성 실패로 이어짐 |
