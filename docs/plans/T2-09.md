# T2-09 메시지·공지·SSE

> 대기열: T2-09 · AC: AC-M2-04, AC-M2-07 · 구현: Codex · 리뷰: Claude
> 선행: M1 전체 · 관련: [실시간 갱신](../architecture/realtime.md), FR-MSG-01~04, FR-RT-01, FR-ADM-05

## 계획 (Claude)

### 목표

- 개인·국가·외교 메시지를 주고받고 읽음이 표시된다. 공개 범위 밖 메시지 조회는 거부된다 (AC-M2-04).
- 내 턴 결과와 새 메시지가 새로고침 없이 2초 안에 화면에 보인다 (AC-M2-07).

### 범위

- `Message`, `MessageRead`, `Notice`(로비·월드), `Nation`의 국가 공지 칸과 장수의 `noticeSeen` (아래 공지 저장 모델)
- `apps/server/src/routers/message.ts`, `notice.ts`, `apps/server/src/realtime/` (SSE)
- engine·server 트랜잭션이 commit된 뒤 별도 SQL로 보내는 `pg_notify` (아래 실시간 결정)

### 하지 않는 것

첨부 이미지, 게시판(글 목록·댓글), 기밀실 열람 기록(v1 아이디어, Phase 2), 웹 푸시(M3).

### 메시지 범위 결정

| scope | 보내는 사람 | 받는 사람 | 읽을 수 있는 사람 |
| ----- | ----------- | --------- | ----------------- |
| PRIVATE | 아무 장수 | 장수 1명 | 보낸 사람, 받은 사람 |
| NATION | 국가 소속 장수 | 그 국가 | 그 국가의 현재 소속 장수 |
| DIPLOMACY | 군주·참모 | 상대 국가 | 양국의 군주·참모 |
| WORLD | 운영자 | 월드 전체 | 모두 |

- 국가를 떠나면 그 국가 메시지를 더 읽을 수 없다 (현재 소속 기준).
- 본문 1,000자, 장수당 분당 10개 제한 (도배 방지).
- **국가 공지**(myosam 지령): 군주·참모가 쓴다. 바뀌면 소속 장수가 다음 접속 때 한 번 팝업으로 본다(`noticeSeenRevision`).

### 실시간 결정 (A11, Redis 없이)

```text
게임·메시지·공지 트랜잭션 commit 성공
  → 그 결과의 알림을 별도 SQL로 pg_notify('world_<id>', {kind, scope?, target})   (target: generalId | nationId | 'world')
  → 트랜잭션이 실패하거나 롤백되면 하나도 보내지 않는다
server LISTEN → 그 월드 SSE 연결 중 지금 권한이 있는 연결에만 {kind, scope?}
web → 해당 query만 다시 조회 (알림 내용에 비밀 정보를 싣지 않는다)
```

- 종류: `turn.result`(내 턴 실행), `message.new`, `monthly.done`, `offer.new`, `treaty.new`, `notice.updated`.
- SSE 주소 `GET /sse?worldId=` (세션 쿠키로 인증). 30초마다 하트비트. 끊기면 브라우저가 다시 잇고 이어진 뒤 화면 전체를 한 번 다시 조회한다.
- 알림 전달 실패는 로그만 남기고 게임 진행에 영향을 주지 않는다. 원칙은 [실시간 갱신](../architecture/realtime.md) §1·§2와 D-014의 commit 뒤 전달이다.

트랜잭션 밖 송신 (기술 정정, 2026-10-23):

- 트랜잭션 안에서 `pg_notify`를 부르지 않는다. [PostgreSQL 18 NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html) Notes대로 알림 큐가 가득 차면 NOTIFY를 부른 트랜잭션이 COMMIT에서 실패한다.
  SAVEPOINT로 감싸도 이 실패는 막지 못한다. 그러면 알림 실패가 게임 저장을 깨므로 위 원칙과 어긋난다.
- 순서: 게임·메시지·공지 트랜잭션의 commit 성공을 확인한 뒤 그 결과의 알림만 별도 SQL로 보낸다. 송신 SQL이나 그 SQL의 commit이 실패하면 경고 로그만 남기고 이미 저장된 결과와 API 응답은 그대로 성공이다.
- payload는 종류(`kind`, `scope`)와 `target`만 싣는다. 본문, 보낸 사람, 비밀값은 싣지 않는다.
- 한계: commit과 송신 사이에 프로세스가 죽으면 그 신호는 빠진다. 다시 보내지 않고 정확히 한 번 전달도 약속하지 않는다. 빠진 신호는 다음 `ready` 재조회나 새로고침으로 메운다 (realtime.md §1).
  outbox는 두지 않는다. 디스코드 알림의 outbox(T2-20)와 다르다.
- 송신 SQL helper는 engine·server가 함께 쓰도록 `packages/db`에 두고 LISTEN 전용 연결은 `apps/server/src/realtime/`에 둔다. server가 `pg`를 직접 의존할지는 Codex가 정한다.

연결 순서와 복구 (검토 R63-4, 2026-10-21 추가):

| 경우 | 서버가 하는 일 | 화면에 생기는 일 |
| ---- | -------------- | ---------------- |
| 새 연결 | 그 월드 채널 LISTEN이 준비된 뒤에 `ready`를 보낸다 | `ready`를 받으면 전체를 다시 읽는다. 그 뒤의 알림은 놓치지 않는다 |
| 서버의 LISTEN 연결이 끊김 | 다시 LISTEN한 뒤 그 서버의 모든 SSE 연결에 `ready`를 보낸다. LISTEN 연결은 하트비트 때 `SELECT 1`로 살아 있는지 본다 | 끊긴 동안 놓친 알림은 `ready` 재조회로 메운다 |
| 서버 프로세스 종료 | 없음 | 브라우저가 다시 잇고 `ready`를 받는다 |
| commit 뒤 송신 실패, 송신 전 프로세스 종료 | 송신 실패는 경고 로그만 남긴다. 게임 결과와 API 응답은 성공 그대로다 | 그 신호는 빠진다. 다음 `ready`나 새로고침까지 화면이 낡을 수 있다 |
| 같은 알림 두 번, 순서 바뀜 | 거르지 않는다 | 알림은 무효화 신호뿐이고 재조회는 늘 최신을 읽으므로 결과가 같다 |

- 2초는 정상 경로(commit → 알림 → query 재조회 → 화면)만 약속한다. 위 장애에서는 다음 `ready`까지 화면이 낡을 수 있다. LISTEN 끊김은 하트비트 간격(30초) 안에 찾는다.
- T2-09의 SSE 수신 시험만으로 AC-M2-07을 통과시키지 않는다. AC-M2-07은 T2-10의 두 사용자 브라우저 시험으로 판정한다.

연결의 현재 권한 (검토 R63-2, 2026-10-21 추가):

- 연결할 때의 인증만 믿지 않는다. 알림을 보낼 때마다 받을 연결을 지금 DB 기준으로 다시 고른다. 세션이 유효하고(`apps/server/src/auth/session.ts:12-27`),
  계정이 `ACTIVE`이며 그 월드에 장수가 있는 연결 가운데 아래 표의 현재 소속·직책 조건을 만족하는 연결에만 보낸다.
- 조건이 깨진 연결은 알림 없이 닫는다. 하트비트 때도 세션과 계정 상태를 다시 보고 깨졌으면 닫는다. 로그아웃은 그 세션의 연결을 바로 닫는다.
- 그래서 탈국·직책 해제 뒤에는 그 국가·외교 알림의 존재와 도착 시점도 받지 않는다. 장수는 월드와 ID의 복합키로 찾는다(`packages/db/prisma/schema.prisma:158`).

### API 계약

아래 타입 하나가 계약 초안이다 (검토 R63-1, 2026-10-21 정리). 예전 요약(`createdAt`이 있던 목록)은 지웠다. `message`·`notice` 라우터는 아직
`AppRouter`에 없고 최종 서버 타입은 backend(Codex)가 정한다 (AGENTS.md §0). 화면은 그 타입만 import한다.
모든 입력의 행위 장수는 세션 사용자의 그 월드 장수다. 입력의 ID는 요청한 `worldId` 안에서만 찾는다.

```ts
type MessageScope = 'PRIVATE' | 'NATION' | 'DIPLOMACY' | 'WORLD';
type GameDate = { year: number; month: number };
type NationTag = { id: number; name: string; color: string }; // NationBadge에 그대로 넘긴다
type Party = {
  generalId: number | null; // 국가 전체·운영자면 null
  name: string;             // 보낸 때의 장수 이름. 국가 전체면 국가 이름, 운영자면 '운영자'
  nation: NationTag | null; // 보낸 때의 국가(표시용). 재야·운영자면 null
};

type MessageItem = {
  id: string;
  scope: MessageScope;
  direction: 'sent' | 'received'; // WORLD는 운영자가 아니면 항상 'received'
  from: Party;
  to: Party | null;               // PRIVATE는 장수, NATION·DIPLOMACY는 국가(generalId null), WORLD는 null
  body: string;                   // 평문. HTML로 저장하거나 돌려주지 않는다
  sentAt: string;                 // ISO 시각
  gameDate: GameDate;             // 보낸 때의 게임 연월
  read: boolean;                  // 내가 보낸 것은 항상 true
};
type MessageListResponse = { items: MessageItem[]; next: string | null };
// 볼 권한이 없는 범위는 0이 아니라 null이다. 화면은 null인 탭을 숨긴다
// (재야는 NATION·DIPLOMACY가 null, 군주·참모가 아니면 DIPLOMACY가 null)
type UnreadResponse = Record<MessageScope, number | null>;
type RecipientsResponse = {
  generals: { id: number; name: string; nation: NationTag | null }[]; // 그 월드의 공개 장수. 나 자신 제외, 이름순
  nations: NationTag[];                                               // 그 월드의 국가. 내 국가 제외, 이름순
};
type NationNoticeResponse = {
  nationId: number;         // 이 공지의 국가. markSeen에 그대로 돌려보낸다 (R63-3R)
  revision: number;         // 국가 공지를 저장할 때마다 1씩 오른다. 한 번도 쓰지 않았으면 0
  body: string;             // 비어 있으면 ''
  updatedAt: string | null; // 표시용이고 읽음 판정에 쓰지 않는다
  updatedBy: string | null; // 쓴 장수 이름
  unseen: boolean;          // body가 비어 있지 않고 이 revision을 아직 읽음 처리하지 않았다. 화면은 true일 때만 팝업
  canEdit: boolean;         // 군주·참모만 true
} | null;                   // 재야면 null
type WorldNoticeResponse = { items: { id: string; body: string; pinned: boolean; publishedAt: string }[] };

// message.list({ worldId, scope, cursor?: string }) → MessageListResponse
//   sentAt 내림차순, 같으면 id 내림차순, 한 쪽 20개. cursor는 마지막 행의 (sentAt, id)를 담은 불투명 문자열이고 더 없으면 next = null.
//   읽을 권한은 지금 소속·직책으로 정한다(아래 범위 표). 표시용 Party.nation은 보낸 때의 값이라 지금 소속과 다를 수 있다.
// message.send({ worldId, scope, toGeneralId?: number, toNationId?: number, body }) → { item: MessageItem }
//   PRIVATE는 toGeneralId, DIPLOMACY는 toNationId가 꼭 있고 NATION은 둘 다 없다(내 국가). WORLD는 API로 보내지 않는다(운영자 명령줄, 아래 공지 저장 모델).
//   화면은 받은 item을 목록 맨 위에 넣고, 같은 id가 재조회로 다시 오면 하나만 남긴다.
//   실패는 TRPCError이고 message는 입력칸 아래에 보여 줄 문장이다.
//     TOO_MANY_REQUESTS 분당 10개 초과 ("N초 뒤에 다시 보낼 수 있습니다.")
//     BAD_REQUEST       빈 본문, 1,000자 초과, 받는 사람 없음, scope와 맞지 않는 받는 사람
//     FORBIDDEN         범위 권한 없음 (군주·참모가 아닌 장수가 외교 메시지를 보냄 등)
// message.markRead({ worldId, ids: string[] }) → { updated: number; unread: UnreadResponse }
//   ids는 1~100개. 내가 지금 읽을 수 없는 id, 다른 월드 id, 없는 id는 오류 없이 건너뛴다(존재 여부를 알리지 않는다). updated는 실제로 바뀐 수다.
// message.unread({ worldId }) → UnreadResponse
// message.recipients({ worldId }) → RecipientsResponse
//   요청한 worldId의 공개 장수·국가만 준다. 이 목록은 받는 사람 고르기용이고 보낼 권한의 근거가 아니다. 권한은 send가 다시 본다.
// notice.nation.get({ worldId }) → NationNoticeResponse
// notice.nation.set({ worldId, body }) → NationNoticeResponse   본문 0~1,000자, 군주·참모가 아니면 FORBIDDEN. 빈 본문 저장도 revision을 올린다
// notice.nation.markSeen({ worldId, nationId, revision }) → NationNoticeResponse   팝업에 띄운 국가의 그 revision까지만 읽음 (아래)
// notice.world.list({ worldId }) → WorldNoticeResponse   고정 먼저, 그다음 publishedAt 최신순, 같으면 id 내림차순, 최대 20개
```

- 월드 공지 순서는 v1 공지 피드(`app/gateway-api/src/main/kotlin/opensamguk/gateway/service/NoticeService.kt:21`, 고정 우선·최신순·20건)를 따른다.
- 로비 공지 읽기는 T2-03의 `lobby.notices`가 맡는다. T2-09는 `notice.lobby.list`를 두지 않는다.

### 공지 저장 모델 (검토 R63-5, 2026-10-21 추가)

로비·월드 공지 저장과 작성 명령줄은 T2-09(Codex)가 소유하고 T2-03 `lobby.notices`가 로비 행을 읽는다. T2-03의 선행에 T2-09가 들어간다
(PR #51의 T2-03 `568678c` 선행 인계. 대기열 표의 그 칸은 PR #51 작성자가 고친다).

| 범위 | 저장 | 작성 | 읽는 곳과 순서 |
| ---- | ---- | ---- | -------------- |
| 로비 | `Notice`, `scope = LOBBY`, `worldId = null`, `title`·`body`·`publishedAt` 필수 | `pnpm notice:publish --scope lobby --title … --body-file …` | T2-03 `lobby.notices`: publishedAt 최신순, 같으면 id 내림차순, 최대 20개. `pinned`를 쓰지 않는다 |
| 월드 | `Notice`, `scope = WORLD`, `worldId` 필수, `title`은 null, `pinned` | `pnpm notice:publish --scope world --world <ID> [--pinned] --body-file …` | `notice.world.list`: 위 순서. 다른 월드 행은 읽지 않는다 |
| 국가 | `Nation`의 `notice`·`noticeRevision`·`noticeUpdatedAt`·`noticeUpdatedBy`, 장수의 `noticeSeen` | `notice.nation.set` | `notice.nation.get` |

- WORLD 메시지는 `pnpm notice:publish --scope world-message --world <ID> --body-file …`로 쓴다. `Message`(`scope = WORLD`)만 만들고 `Notice`는 만들지 않는다.
  `--scope world`는 `Notice`만 만든다. 한 명령이 둘을 함께 저장하지 않는다. 원래 계획에서 비어 있던 WORLD 메시지 저장 경로를 채운 것이다 (기술 정정, 2026-10-23).
- 명령줄은 본문을 파일로 받는다. 본문과 제목은 평문이다. 명령줄 인자에 비밀값을 넣지 않는다.
- 로비 순서와 월드 순서를 서로 옮겨 쓰지 않는다. 월드 공지의 고정 우선은 로비에 쓰지 않는다.

### 국가 공지 읽음 (검토 R63-3, 2026-10-21 추가)

국가 공지 읽음은 시각이 아니라 revision으로 정한다. 공지 A(revision 3)를 보는 중에 B(revision 4)가 저장되면 A를 닫을 때 B까지 읽음이 되면 안 된다.
revision만으로는 어느 국가의 판인지 알 수 없다. 그래서 읽음 요청은 화면에 띄운 국가와 판을 함께 보낸다 (검토 R63-3R, 2026-10-22 추가).
국가 A의 revision 3 팝업을 띄운 사이에 장수가 국가 B로 옮겼고 B도 revision 3이면, A 팝업을 닫는 요청이 보지 않은 B 공지를 읽음으로 만들면 안 된다.
`nationId`·`revision`이라는 이름과 응답 모양의 최종안은 서버 소유자(Codex)가 정한다. 지켜야 할 것은 아래 동작이다.

- 저장: 장수의 `noticeSeen = { nationId, revision }`. 국가 공지는 `revision`을 가지고 `notice.nation.set`이 같은 트랜잭션에서 1 올린다.
- 판 식별: 한 국가 안에서 revision은 저장할 때마다 오르므로 `(nationId, revision)` 한 쌍이 공지 한 판을 가리킨다. 이 전제는 국가 ID를 다시 쓰지 않는다는 데 기댄다.
  지금 엔진은 `nextNationId`를 월드에 저장하고(`apps/engine/src/commandPersistence.ts:63-69`) 국가를 지우기 전에 그 값을 먼저 정해 두므로(`packages/rules/src/commands/support.ts:61-72`)
  멸망한 국가의 ID를 새 국가에 주지 않는다. 이 동작이 바뀌면 판 식별을 서버 소유자가 다시 정한다.
- `markSeen({ nationId, revision })`은 화면이 팝업에 띄운 응답의 `nationId`와 `revision`을 그대로 보낸다. 처리 순서는 이렇다.
  1. `nationId`가 지금 내 국가가 아니면(재야 포함) 아무것도 쓰지 않고 지금 상태의 응답을 돌려준다. 오류로 만들지 않는다. 옛 팝업의 닫기가 새 국가에 적용되지 않고 화면은 돌려받은 응답의 `unseen`으로 새 국가 공지를 띄운다.
  2. 같은 국가인데 `revision`이 그 국가의 현재 revision보다 크면 `BAD_REQUEST`다.
  3. 저장된 값이 같은 국가이고 revision이 요청 이상이면 아무것도 하지 않는다. 그 밖에는 `{ nationId, revision }`으로 쓴다. 최신 revision으로 올려 주지 않는다.
- 확인과 쓰기 사이에 엔진이 소속을 바꿀 수 있다. 그래서 위 판정과 쓰기를 한 번의 조건부 갱신(장수의 현재 `nationId`가 요청 `nationId`와 같을 때만)으로 하거나,
  장수 행을 잠근 한 트랜잭션에서 한다. 소속이 이미 바뀌었으면 0행이고 1번처럼 처리한다.
- `unseen`은 `body !== '' && (noticeSeen.nationId !== 내 국가 || noticeSeen.revision < revision)`이다.
  빈 공지는 팝업하지 않는다. 다른 국가로 옮기면 새 국가 공지를 한 번 본다. 같은 시각에 두 번 고쳐도 revision이 달라 구분된다.
- 탈국한 뒤 같은 국가에 다시 들어온 경우: 재야인 동안 온 옛 닫기는 1번에 걸려 버린다. 다시 들어온 뒤 도착한 `(A, 3)` 닫기는 A의 revision 3이 그 팝업에 띄운 바로 그 판이므로 읽음으로 쓴다.
  그사이 다른 국가 공지를 읽음 처리했다면 `noticeSeen.nationId`가 바뀌어 있으므로 A 공지는 다시 한 번 뜬다.
- 탭 두 개에서 다른 판을 닫아도 같은 국가 안에서는 큰 값만 남고 다른 국가의 닫기는 1번으로 버려진다. 같은 값을 두 번 보내도 결과가 같다. 행위 장수는 세션에서 정한다.

#### SSE 이벤트

`GET /sse?worldId=` 응답은 `text/event-stream`이다. 이벤트 이름이 `kind`이고 `data`는 아래 JSON이다. 본문·보낸 사람·수치는 싣지 않는다.

```ts
type WorldEvent =
  | { kind: 'ready' } // LISTEN 준비 뒤, 연결(재연결 포함) 직후와 서버 LISTEN 복구 뒤. 화면은 이때 전체를 다시 조회한다
  | { kind: 'turn.result' }
  | { kind: 'message.new'; scope: MessageScope }
  | { kind: 'monthly.done' }
  | { kind: 'offer.new' }
  | { kind: 'treaty.new' }
  | { kind: 'notice.updated'; scope: 'nation' | 'world' };
// 하트비트는 30초마다 주석 줄(": hb")로 보내므로 화면에는 이벤트로 오지 않는다
```

| kind | 받는 연결 (보낼 때의 현재 권한 기준) |
| ---- | --------------------------------- |
| `turn.result` | 그 장수의 주인 한 명 |
| `message.new` PRIVATE | 받는 장수의 주인 (보낸 쪽은 `message.send` 응답으로 갱신) |
| `message.new` NATION | 그 국가의 현재 소속 장수 주인들 |
| `message.new` DIPLOMACY | 양국의 현재 군주·참모 |
| `message.new` WORLD, `monthly.done`, `notice.updated` world | 그 월드의 모든 연결 |
| `offer.new` | 제안을 받는 쪽 (발령은 그 장수, 조약 제안은 상대국 군주·참모) |
| `treaty.new` | 양국의 현재 소속 장수 |
| `notice.updated` nation | 그 국가의 현재 소속 장수 |

`revision`은 싣지 않는다. 화면은 알림마다 해당 query를 무효화하고 끊겼다 이어지면 `ready`를 받은 뒤 전체를 다시 읽는다. 놓친 알림은 다시 보내지 않는다. v1도 같은 방식이었다. 첫 줄 `:connected`(`app/game-api/src/main/kotlin/opensamguk/gameapi/sse/RealtimeRelayController.kt:78`), 30초 하트비트(같은 파일 `:74`), 재연결 뒤 다시 읽기(`web/game/hooks/useSSE.ts:29-32`)가 근거다.
