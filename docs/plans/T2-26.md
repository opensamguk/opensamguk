> 다음: [T2-05](./T2-05.md), [T2-07](./T2-07.md), [T2-13](./T2-13.md), [T3-07](./T3-07.md), [T3-09](./T3-09.md), [T4-03](./T4-03.md)이 이 기반 위에 입력 종류와 기능만 더한다.

AC-M1-13(같은 시드와 같은 입력 기록으로 12개월을 다시 돌리면 상태 해시가 같다)의 상태는 바꾸지 않는다. 이 작업은 그 성질을 기능이 늘어나는 월드까지 이어 가는 기반이다.

## 계획 (Claude)

### 목표

- 새 재생 형식 번호 하나(origin 3·archive 3)가 생긴다. 월드를 만들 때 켠 규칙 기능 목록이 생성 기록에 남고 엔진과 재생은 그 목록대로 규칙을 탄다.
- 기능을 켜지 않은 월드와 형식 1 월드의 상태 해시는 지금과 같다. origin 1과 archive 1·2의 뜻과 수출 바이트도 같다.
- 엔진은 모든 대기 입력을 종류와 상관없이 접수 순서 한 줄로 꺼내는 처리기 하나로 처리한다. 기능 작업은 이 처리기에 입력 종류를 등록하기만 한다.
- 새 형식 월드에서 엔진이 밀려 다음 달 경계를 넘겼으면 밀린 턴과 월간 정산을 먼저 따라잡고 그 뒤에 대기 입력을 처리한다. 형식 1 월드의 순서는 그대로다.
- 이 작업이 끝났을 때 운영 기능 목록은 비어 있다. 첫 기능은 T2-05 등 기능 작업이 등록한다.

### 범위

- `packages/rules`: 규칙 기능·입력 종류 등록 목록과 검사 함수, `WorldInit`·`WorldState`의 `ruleFeatures`, `toWorldState`의 복사, `applyRecordedInput`·`initialReplayState`의 등록 목록 사용, `RecordedInput.tick`.
- `packages/db`: 새 migration 하나(`World.replayFormat`, `World.ruleFeatures`, `InputEvent.tick`). 기존 migration은 고치지 않는다.
- `apps/engine`: `saveInitialWorld`·`readWorldState`, `loadWorld`, `loadReplayState`, `persistMonthly`의 기능 자리, `processInputs`와 `general.create` 처리기, `TurnLoop`의 C2와 시작 대조, `exportReplay`·`readArchive`·`replayArchive`·`replayToEnd`, `cli/createWorld.ts`의 `--rule-features`.
- `apps/server`: `readView`가 `ruleFeatures`를 상태에 싣고 기능 확인 함수 `requireRuleFeature` 하나를 더한다. 라우터 동작은 바꾸지 않는다.
- `tools/replay.ts`: archive 3 처리와 안내 문구.
- 시험 고정 파일: 착수 전 기준으로 만드는 archive 2 수출 고정 파일 하나와 archive 3 고정 파일.

### 하지 않는 것

- 실제 규칙 기능(인사, 조약, 방침, 평판, 관직 효과, 확장 명령)과 그 입력 종류. 각 기능 작업의 몫이다.
- origin 1 월드를 origin 3으로 올리는 변환. 형식 1 월드는 끝까지 형식 1이다.
- `turns.set`을 대기 입력으로 바꾸기. 즉시 입력은 지금처럼 API가 적용한다(열린 결정 U26-3).
- 같은 달 안에서 밀린 턴을 입력보다 먼저 처리하기(열린 결정 U26-1).
- 어떤 월드에 어떤 기능을 켤지 정하는 화면·프리셋·로비 규칙(열린 결정 U26-2).
- U62-6(형식 1 월드에서 조약을 막을지)의 답. 이 작업은 켜지 않은 기능의 입력을 거절하는 공통 틀만 만든다.
- v1·v2 골든 고정 파일, `apps/engine/test/generateReplayV1.ts`, `replayFixture.ts` 수정.
- API 응답 모양 변경. 화면에 기능 목록이 필요하면 그 기능 작업이 응답에 싣는다.

#### origin 3과 archive 3

```ts
interface ReplayOriginV3 {
  version: 3;
  initial: WorldInit; // 켠 기능이 있으면 initial.ruleFeatures 포함. 그 밖은 origin 1과 같은 모양
  initialStateHash: string; // hashState(initial), origin 1과 같은 식
  resourceHash: string; // resourceHashV3(origin)
  featureData?: Record<string, JsonValue>; // 자기 자료가 있는 기능만. 키는 initial.ruleFeatures의 부분집합. 비면 칸을 넣지 않는다
}
interface ReplayArchiveV3 extends Omit<ReplayArchiveV2, 'version' | 'origin' | 'inputs' | 'afterEnd'> {
  version: 3;
  origin: ReplayOriginV3;
  inputs: (RecordedInput & { tick: number | null })[];
  afterEnd: (RecordedInput & { tick: number | null })[];
}
```

- `resourceHashV3(origin)`는 `featureData`가 없으면 `resourceHash(origin.initial)`와 같은 값이고 있으면 `hashState({ ...resourceHash의 다섯 칸, featureData })`다. 기능 없는 월드에서 T4-77·T4-79의 `resourceHash` 동등 시험이 그대로 성립한다.
- 기능 자료는 생성 때 리소스나 프리셋에서 복사해 두는 값이다. 예: T4-03의 확장 목록·프리셋 사본·`sliceKeys`, T3-09의 관직 효과 사본. 재생은 파일을 다시 읽지 않고 이 사본만 쓴다.
- archive 3 입력의 `tick`은 대기 입력이면 엔진이 처리한 tick, 즉시 입력이면 `null`이다. archive 1·2의 입력에는 `tick` 키를 넣지 않는다.

#### 생성

- `saveInitialWorld(db, state, options)`에 `ruleFeatures?: string[]`, `featureData?: Record<string, JsonValue>`, `replayFormat?: 1 | 3`(기본 3)을 더한다. `replayFormat: 1`은 기능과 기능 자료가 없을 때만 받고 형식 1 기준 시험에 쓴다. CLI에는 열지 않는다.
- 쓰기 전에 F5~F9와 같은 검사를 지난다. 실패하면 월드 행을 만들지 않는다.
- `initial = { ...state, presetRules?, ruleFeatures? }`를 만든 뒤 지금처럼 `initialStateHash = hashState(initial)`을 잰다. 같은 트랜잭션에서 `World.replayFormat`, `World.ruleFeatures`(빈 배열 허용), `replayOrigin`을 함께 쓴다.
- `pnpm world:create`에 `--rule-features a,b`를 더한다. 지금 운영 목록이 비어 있으므로 값을 주면 F7로 거부된다.

#### DB

- 새 migration: `World.replayFormat INT NOT NULL DEFAULT 1`, `World.ruleFeatures TEXT[] NOT NULL DEFAULT '{}'`, `InputEvent.tick INT NULL`, 그리고 `status = 'PENDING'`이면 `tick IS NULL`인 검사 제약. 기존 행은 기본값으로 형식 1·빈 목록이 되어 지금 뜻과 같다.
- 두 World 열은 `replayOrigin`의 읽기용 사본이다. 정본은 `replayOrigin`이고 엔진 시작 대조가 둘이 같은지 본다. 엔진과 서버가 매 걸음 큰 `replayOrigin`을 읽지 않게 하려는 열이다.
- 생성 뒤 두 열은 바뀌지 않는다.

엔진 기능 자리는 `apps/engine`의 등록 목록 하나에 모은다.

```ts
interface EngineFeature {

  loadReplayState?(tx: Prisma.TransactionClient, worldId: string, replay: ReplayState): Promise<ReplayState>;
```

자리가 기능에 맞지 않으면 기능 작업이 해당 파일을 직접 고치고 그 계획에 이유를 적는다. 어느 쪽이든 켜지 않은 월드의 경로와 해시는 바꾸지 않는다.

#### 통합 입력 처리기

```ts
type QueuedInputHandler = (
  tx: Prisma.TransactionClient,
  world: World, // 잠근 World 행
  event: InputEvent, // PENDING
  context: { tick: number; sequence: number },
) => Promise<{ status: 'APPLIED' | 'REJECTED'; result: Prisma.InputJsonValue; generalId?: number }>;

// 호출자가 리스와 World를 잠근 뒤 같은 펜싱 트랜잭션에서 부른다. 처리했으면 true.
export async function processInputs(tx, world, tick, registry?): Promise<boolean>;
```

1. 그 월드의 PENDING 입력 가운데 id가 가장 작은 것 하나를 종류와 상관없이 꺼낸다(인덱스 `[worldId, status, id]`). 없으면 false.
2. 종류가 등록 목록에 없거나 `route`가 `direct`이면 예외를 내고 아무것도 쓰지 않는다. 그 월드 엔진은 멈춘다. 서버가 엔진보다 먼저 새 종류를 쓰지 않도록 배포는 엔진을 먼저 한다.
3. `sequence = nextActionSequence(tx, worldId)`를 판정 전에 한 번 받는다. 지금 `processCreation`도 입력 하나에 한 번 받으므로 같은 트랜잭션 안에서 값이 같다.
4. 종류의 기능이 `World.ruleFeatures`에 없으면 처리기를 부르지 않고 REJECTED, `result = { code: 'FEATURE_DISABLED', message: '이 월드에서 켜지 않은 기능입니다.' }`로 끝낸다.
5. 아니면 종류의 처리기를 `{ tick, sequence }`와 함께 부른다. 처리기는 게임 상태와 자기 표를 쓰고 결과만 돌려준다. InputEvent는 쓰지 않는다.
6. 처리기가 돌려준 값으로 `status`, `sequence`, `tick`, `result`, `generalId`를 `where: { id, status: 'PENDING' }` 조건 갱신 한 번에 쓴다. 바뀐 행이 1이 아니면 트랜잭션을 되돌린다.

- `general.create` 처리기는 지금 `processCreation`의 판정을 그대로 옮긴다. 거절 코드, 결과 모양, 장수 id 계산, 예턴 30칸 생성, `User` 행 `FOR SHARE` 잠금이 같다.
- 한 걸음에 입력은 하나만 처리한다. 지금처럼 처리하면 그 걸음을 끝낸다(`turnLoop.ts:145-151`).
- commit 전에 멈추면 트랜잭션이 되돌려져 입력은 PENDING으로 남고 sequence도 소비되지 않는다.
- rules의 대기 입력 종류마다 엔진 처리기가 정확히 하나 있어야 한다. `general.create`는 엔진 핵심 목록에, 나머지는 `engineFeatures[].queuedInputs`에 둔다. 단위 시험이 두 목록을 대조한다.

#### 처리 순서 (C2)

- RUNNING 걸음: `catchUp = world.replayFormat === 3 && boundary <= tick`(`boundary`는 `turnLoop.ts:129`, `tick`은 `:138-142`). `catchUp`이면 입력 처리를 건너뛰고 `:152-168`의 턴·월간 선택으로 간다. 선택 규칙이 경계 앞의 밀린 턴을 tick 순으로 먼저 고르고 그 뒤에 월간 정산을 고르므로 게임 시간 순서가 된다. 정산 뒤 다음 걸음에서 새 경계가 tick보다 크면 입력을 다시 먼저 처리한다.
- RUNNING이 아닌 걸음(`:113`): 형식 3이고 상태가 PAUSED이며 `world.monthlyTick + TICKS_PER_MONTH <= world.clockTick`이면 입력을 처리하지 않고 PENDING으로 둔다. 따라잡는 도중 일시정지된 월드가 재개 뒤 정산을 먼저 하게 하려는 것이다. PREOPEN과 ENDED를 포함한 그 밖은 지금처럼 `world.clockTick`으로 처리한다. ENDED 월드의 입력은 지금처럼 거절되어 `afterEnd`로 가고 F15 검사를 받지 않는다.
- 형식 1 월드는 두 갈래 모두 지금 순서다(입력 먼저).
- 이 규칙이 지켜지면 대기 입력의 처리 tick은 늘 그 시점 재생 상태의 월 창 안에 있다. 재생은 F15로 이것을 확인한다. 엔진 기록에 받은 시각이 없어도 C2 위반을 기록만 보고 찾을 수 있다.
- 즉시 입력(`turns.set`)은 C2 밖이다. API가 바로 적용하므로 밀린 턴이 새 예턴으로 실행될 수 있다. 지금 형식 1과 같은 동작이며 sequence가 실제 적용 위치를 기록하므로 재생은 맞는다(`docs/developer/request-turn-persistence.md` §5). 바꿀지는 U26-3이다.

#### 엔진 시작 대조

`TurnLoop`은 lease를 잡은 뒤 첫 걸음의 World 잠금 바로 뒤, 아무것도 쓰기 전에 한 번 `replayOrigin`을 읽어 대조한다. 어긋나면 예외로 멈추고 쓰지 않는다.

| ID | 조건 |
| -- | ---- |
| S1 | `replayOrigin`이 null인데 `replayFormat`이 1이 아니거나 `ruleFeatures`가 비지 않았다 |
| S2 | origin 형식이 1·3이 아니거나 `replayFormat`과 다르다 |
| S3 | origin 1인데 `ruleFeatures` 열이 비지 않았다 |
| S4 | origin 3의 `initial.ruleFeatures`(없으면 빈 목록)가 열과 다르다 |
| S5 | 열의 기능이 등록 목록에 없거나 F6~F9를 어긴다 |

초기 해시(F10)는 시작 대조에서 다시 재지 않는다. `exportReplay`와 재생이 잰다.

#### 입력 재생

- `applyRecordedInput(replay, input, registry = ruleRegistry)`: REJECTED는 지금처럼 바로 돌려준다(`:81`). APPLIED는 종류를 찾고 없으면 지금 문구(`재생할 수 없는 입력 종류입니다`)로 예외, 기능이 상태에 없으면 예외, 있으면 `apply`를 부른다.
- `turns.set`과 `general.create`의 검사와 오류 문구는 `apply`로 옮기기만 한다. 기능 작업이 이 두 종류의 검사를 넓혀야 하면(T2-13의 `explicit` 칸) `apply` 안에서 `hasRuleFeature`로 갈라 켠 월드에서만 넓힌다.
- 기능 작업이 tick이 필요하면 `input.tick`을 읽는다. archive 3에서만 값이 있다.

1. 기준 고정: 착수 커밋 위에서 형식 1 월드(고정 시드, `turns.set`·`general.create`의 APPLIED와 REJECTED, 종료와 `afterEnd` 포함)를 만들어 `exportReplay` 결과를 새 고정 파일로 저장한다. 출처 SHA를 구현 기록에 적는다. 그 뒤 코드를 바꾼다.
