### 기술 계약

#### E1 resolver와 확장 목록의 출처

- 월드의 확장 목록은 `presetCommands(parsePreset(World.preset))` 하나에서 나온다(T2-02 K1·K6). `World.preset`이 `null`이거나 `commands`가 `null`이면 `null`이다.
- resolver는 `resolverForPreset(preset | null)`(T2-02 K6)로 만든다. 안에서 `createCommandResolver(commands)`를 부르므로 운영 `extensionCommands`만 쓴다.
- 서버는 새 파일 `apps/server/src/game/resolver.ts`에 `worldResolver(world)`를 둔다. 엔진은 새 파일 `apps/engine/src/extState.ts`에 같은 일을 하는 함수를 따로 둔다. 둘 다 rules 함수를 부르는 얇은 함수이며 서로 import하지 않는다.
- 모듈 전역 캐시를 두지 않는다. 요청 하나, 엔진 step 하나마다 그 월드 행에서 만든다(반례 X4).
- 시험 주입 칸은 없다. 이유는 소스에 있다. `CommandSource`로 resolver와 DB만 바꿔도 `runGeneralTurn` → `applyEffects` → `cloneWorld`와 `initialReplayState` → `toWorldState`가 운영 `extSlices`(빈 배열)로 `ext`를 검증하므로 시험 조각은 모르는 key로 거부된다(`ext/state.ts:115`). 전 경로에 registry를 넘기는 것은 rules 순수 경로 재설계이고 이 계획 범위 밖이다.
- 그래서 켠 월드의 실행·저장·재생 통합은 첫 운영 등록 뒤에만 한다(단계 표의 2단계). 1단계는 운영 목록으로 지금 증명할 수 있는 것만 한다.

#### E2 서버 연결

`parseSlot`을 두 단계로 나눈다. 검사 순서가 지금과 같아야 끈 월드의 오류가 바이트 단위로 같다.

1. 트랜잭션 밖(지금 자리): `null`은 휴식이다. key가 기본 37개 또는 운영 `extensionCommands`에 있고 대상이 `general`이며 인자가 그 정의의 zod를 통과해야 한다. 확장 명령 인자는 E7 저장 가능 검사도 지난다. 실패는 지금과 같은 `BAD_REQUEST` `명령과 인자를 확인하세요.`다. 운영 확장 목록이 빈 동안 이 단계는 지금 `parseSlot`과 같다.
2. 트랜잭션 안: `requireWorld` 바로 뒤, `ENDED` 검사보다 먼저다. 입력에서 온 칸(`set`의 30칸, `edit`의 `put` 값)마다 `resolver.get(key)`가 있어야 한다. 없으면 `BAD_REQUEST` `이 월드에서 꺼진 명령입니다.`로 거부하고 아무것도 쓰지 않는다. 입력 오류가 상태 오류보다 먼저인 지금 순서를 지키는 자리다. 응답 모양은 지금 tRPC 오류 모양 그대로이고 `AppRouter` 성공 응답 타입은 바뀌지 않는다(Q5 수용).

- `edit`의 `shift`·`repeat`는 이미 저장된 칸을 다시 검사하지 않는다. 저장된 칸에 꺼진 key가 있으면(기록 파손) 엔진 실행이 `COMMAND_DISABLED` 실패 로그를 남긴다.
- `turns.precheck`: 1단계 뒤 트랜잭션 안에서 `resolver.precheck(view, { generalId, tick, unitSet }, key, args)`를 부른다. 결과는 지금처럼 `{ ok: false, ...failure }` 또는 `{ ok: true }`다. 꺼진 key는 `{ ok: false, code: 'COMMAND_DISABLED', message: '이 월드에서 꺼진 명령입니다.' }`다.
- `readView`는 E5의 두 함수로 `ext`를 얻어 지금 `toWorldState` 입력 객체에 `ext` 칸으로 더한다. T2-02가 같은 함수에 `presetRules`를 먼저 더하므로 그 위에 붙인다.
- `displaySlots(turns, resolver)`의 이름은 `resolver.get(key)?.name ?? key`다. `turns.get`, `set`·`edit` 응답, STALE 응답이 같은 함수를 지난다.
- `commands.list`는 `resolver.list('general')`을 지금과 같은 모양(`key`, `name`, `category`, `argsSchema`)으로 낸다. 끈 월드의 결과는 지금 `commandList`와 깊은 비교로 같다.
- 새 procedure를 만들지 않는다. `router.ts`, `authz/exemptions.ts`는 고치지 않는다.

#### E3 월드 생성 (형식 변환)

`saveInitialWorld(db, state: WorldInit, options)`(`world/persistence.ts:7`)가 유일한 생성 경로다. 운영에서 부르는 곳은 `cli/createWorld.ts:34`뿐이고 나머지(`test/seasonFixture.ts`, `tools/season-throughput.ts`, `e2e/rankingSeed.ts`)는 시험·도구다. 이 목록을 소스 검사 시험으로 고정한다.

확장 목록이 `null`이면 T2-02 경로 그대로다. 확장 목록이 있으면 같은 함수 안에서 이 순서로 한다.

1. `base: WorldInit`는 T2-02가 `presetRules`까지 넣은 값이다. `ext` 키가 없다.
2. 확장 상태의 입력은 `ExtInitContext`(`DeepReadonly<Omit<WorldState, 'ext'>>`)이므로 레코드 형식으로 바꾼다. `toWorldState(base)`는 `ext` 키가 없을 때 조각 검증을 하지 않고 배열을 id 레코드로 바꾼다(`model/world.ts:31-43`). 그 결과를 그대로 `createExtState(commands, context)`에 넘긴다. `WorldInit` 배열을 직접 넘기지 않는다. `presetRules`가 이 결과에 실리는 것은 T2-02 K7이 `toWorldState`에 더하는 복사에 기댄다.
3. 결과가 `undefined`이면 `initial = base`다. 값이 있으면 `initial: WorldInit = { ...base, ext }`다. `WorldInit.ext`는 이미 있는 선택 칸이다(`world/bootstrap.ts:84`).
4. `initialStateHash = hashState(initial)`이다. 기존 `World.initialStateHash` 칸에도 같은 값을 쓴다. 확장 없는 월드는 지금처럼 `hashState(base)`다.
5. 같은 트랜잭션에서 E4 행을 `initial.ext`의 조각마다 쓰고 origin 3(E8)을 쓴다.

- `createExtState`는 결합이 없는 key에서 실패한다(`ext/state.ts:89`). 운영 목록이 빈 동안 T2-02 K2 검사로 확장 목록이 있는 생성은 모두 실패한다. 이 실패 자체가 1단계 시험이다.

#### E4 저장 표

새 migration 하나(T2-02 migration 뒤)에 넣는다.

```prisma
model WorldExtSlice {
  worldId String
  key     String
  value   Json
  world   World  @relation(fields: [worldId], references: [id], onDelete: Cascade)
  @@id([worldId, key])
}
```

- 조각 하나가 한 행이다. 턴마다 바뀐 조각만 쓰고 큰 `World` 행을 다시 쓰지 않는다.
- 조각 key 집합은 생성 때 정해지고 바뀌지 않는다. 행을 더하거나 지우는 것은 생성과 월드 삭제(cascade)뿐이다.
- 확장 없는 월드에는 행이 없다. 기존 행은 backfill하지 않는다. 기존 migration 파일은 고치지 않는다.

- 루트 `packages/rules/src/index.ts`에 위 두 함수를 export한다. Q1 답으로 §7의 `ext/state.ts`·`index.ts` 행에 T4-03이 기술 소유로 들어간다. 다른 rules 파일은 고치지 않는다.
- `restoreExtState` 규칙: 확장 목록이 `null`인데 `raw`가 있으면 거부한다. 기대 집합이 비었는데 `raw`가 있거나 기대 집합이 있는데 `raw`가 없으면 거부한다. key가 하나라도 빠지거나 남으면 거부한다. 검증은 `cloneExtStateWithRegistry`와 같은 검사(JSON 형식, 예약 key, 조각 `validate`)를 쓴다.
- 서버 `readView`: `restoreExtState(commands, await readWorldExtRows(tx, worldId))`를 `toWorldState` 입력에 더한다. `toWorldState`가 한 번 더 복제·검증한다.
- 엔진 `loadWorld`: 같은 두 함수의 결과를 레코드 `WorldState`에 `...(ext ? { ext } : {})`로 더한다. 엔진은 서버를, 서버는 엔진을 import하지 않는다. 의존은 `apps/* → packages/rules`, `apps/* → packages/db`, `packages/db → packages/shared`(패키지 경계 문서의 허용 방향)뿐이다. `packages/db/package.json`에 `@opensamguk/shared`를 더한다.
- 거부는 고정 문구 예외이며 값은 로그에 넣지 않는다. 엔진은 그 월드의 step을 쓰기 전에 멈춘다. 다른 월드 진행은 지금 supervisor 동작을 바꾸지 않는다.
- lease를 잡은 뒤 처음 한 번 origin과 월드 행을 대조한다(D 표). `replayOrigin` 전체를 step마다 읽지 않는다.

#### E6 턴·월간 저장

- 턴: 장수 턴은 `runGeneralTurn(state, actor, command, seed, options, resolver)`로 부른다. 국가 명령 이름은 `resolver.get(key)?.name ?? '국가 명령'`이다.
- 같은 트랜잭션에서 `persistEffects` 다음에 `writeWorldExtChanges(tx, worldId, before.ext, next.ext)`를 부른다.
  - 두 값의 key 집합이 다르면 예외로 트랜잭션을 되돌린다.
  - 조각마다 `hashState`(정렬 key 정규 JSON)로 비교해 바뀐 행만 갱신한다. JSONB가 key 순서를 바꾸므로 `JSON.stringify` 비교를 쓰지 않는다.
  - 쓰기 전에 E7 검사를 한다.
- 월간: `persistMonthly`에서 `runMonthly`가 낸 `ext`를 같은 트랜잭션에서 먼저 쓴다. 그 뒤 `loadReplayState`로 다시 읽어 `stateHash`를 만든다. 순서는 월간 처리 → 저장 → `loadReplayState` → `stateHash`다.
- `inputs.ts`의 `general.create`는 `ext`를 바꾸지 않는다. 장수별 초기값이 필요한 조각이 생기면 그 등록 작업이 이 계약을 먼저 고친다.
