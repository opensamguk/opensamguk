### 기술 계약

#### E1 resolver와 확장 목록의 출처

- 서버·엔진에서 월드의 확장 목록은 `presetCommands(World.preset ? parsePreset(World.preset) : null)` 하나에서 나온다(`preset.ts:70-75`, T2-02 K1·K6). `World.preset`이 `null`이거나 `commands`가 `null`이면 `null`이다. 재생에서는 기록에 실린 확장 칸의 `commands`다. 그 칸이 기록의 어디에 실리는지는 E8의 미채택 복합 제안이 정한다.
- resolver는 `resolverForPreset(preset | null)`(`preset.ts:76-78`) 또는 같은 값의 `createCommandResolver(commands)`로 만든다. 운영 `extensionCommands`만 쓴다.
- 서버는 새 파일 `apps/server/src/game/resolver.ts`에 `worldResolver(world: { preset: unknown }): { commands: EnabledCommands | null; resolver: CommandResolver }`를 둔다. 엔진은 새 파일 `apps/engine/src/extState.ts`에 같은 모양의 함수와 E5·E6·D 표 함수를 둔다. 둘 다 rules 함수를 부르는 얇은 함수이며 서로 import하지 않는다. 두 새 파일과 그 시험도 지금 구현 승인이 아니다. 부모가 뒤에 명시 배정해야 만든다(E10).
- 모듈 전역 캐시를 두지 않는다. 요청 하나, 엔진 step 하나마다 그 월드 행에서 만든다(반례 X4).
- resolver는 확장 목록에서만 나온다. 기능 선택값(T2-05의 `features`, T2-13 정책 태그 같은 것)은 resolver와 한 값으로 묶지 않는다. 그 선택값의 출처를 origin 형식 번호 하나로 정하지 않는다. 기존 월드가 sequence 중간에 정책으로 전환되면 같은 origin에서도 선택값이 바뀌기 때문이다. 정책 몫은 `0bebd1f`로 수용됐다. 방침 모드는 `isPolicyMode(fromSequence, actionSequence)` 하나로 판정하고 resolver 자리(`runGeneralTurn` 여섯째, `runReplayAction` 넷째)는 그대로다. 방침 맥락은 `runGeneralTurn` 다섯째 `options`와 `ReplayState`에 실린다. 확장·인사와의 합성 경계는 E8의 미채택 복합 제안 (e)다.
- 시험 주입 칸은 없다. 이유는 소스에 있다. `CommandSource`로 resolver와 DB만 바꿔도 `runGeneralTurn` → `applyEffects` → `cloneWorld`와 `initialReplayState` → `toWorldState`가 운영 `extSlices`(빈 배열)로 `ext`를 검증하므로 시험 조각은 모르는 key로 거부된다(`ext/state.ts:141-144`). 전 경로에 registry를 넘기는 것은 rules 순수 경로 재설계이고 이 계획 범위 밖이다.
- 그래서 켠 월드의 실행·저장·재생 통합은 첫 운영 등록 뒤에만 한다(단계 표의 2a·2b). 1단계는 운영 목록으로 지금 증명할 수 있는 것만 한다.

#### E2 서버 연결

아래 서버 파일(`slots.ts`, `turns.ts`)은 지금 T2-13 단독 소유다. 이 절은 T2-13 인계 커밋 위에서 부모가 T4-03에 다시 배정한 뒤 적용할 기술 계약이다. 줄 번호는 `3e5b52a` 기준이고 인계 커밋에서 다시 맞춘다.

`parseSlot`을 두 단계로 나눈다. 검사 순서가 인계 기준과 같아야 끈 월드의 오류가 바이트 단위로 같다.

등록 base와의 충돌 (후속 명시 정정 필요): 아래 두 단계를 1a에 그대로 넣으면 계략이 등록된 base에서 끈 월드의 계략 key 저장이 달라진다. 지금은 트랜잭션 전 `명령과 인자를 확인하세요.`인데 1단계를 지나 `requireWorld`(없는 월드면 NOT_FOUND)와 `이 월드에서 꺼진 명령입니다.`가 먼저 나온다. 그래서 끈 월드에서 새 검사가 늘 통과한다는 말은 기본 37개 key에만 맞는다. 아래 두 단계는 `3e5b52a` 기준의 옛 계약이고 그 확장 key 인식과 `assertEnabledSlots`는 후속 2a 계약이다. E10 1a 준비 계약의 최소 off 제안은 1a에서 `parseSlot`과 `save` 순서를 그대로 두고 등록 포함 결합 SHA의 G3와 비교한다. 두 배치 모두 채택 전이며 새 오류 우선순위는 수용된 것이 아니다.

1. 트랜잭션 밖(지금 자리): `null`의 뜻은 T2-13 인계 형식(빈칸)을 따른다. 객체 입력은 key가 기본 37개(`commandRegistry`) 또는 운영 `extensionCommands`에 있고 대상이 `general`이며 인자가 그 정의의 zod를 통과해야 한다. 확장 명령 인자는 0단계 `assertStorableJson`(E7)도 지난다. 실패는 지금과 같은 `BAD_REQUEST` `명령과 인자를 확인하세요.`다. 운영 확장 목록이 빈 동안 이 단계는 지금 `parseSlot`과 같다.
2. 트랜잭션 안: `requireWorld`(`turns.ts:38`) 바로 뒤, `ENDED` 검사(`:39`)보다 먼저다. 새 함수 `assertEnabledSlots(resolver, turns)`가 입력에서 온 칸(`set`의 30칸, `edit`의 `put` 값)마다 `resolver.get(key)`를 본다. 없으면 `BAD_REQUEST` `이 월드에서 꺼진 명령입니다.`로 거부하고 아무것도 쓰지 않는다. 입력 오류가 상태 오류보다 먼저인 지금 순서를 지키는 자리다. 응답 모양은 지금 tRPC 오류 모양 그대로이고 `AppRouter` 성공 응답 타입은 바뀌지 않는다(Q5 수용).

#### E3 월드 생성 (형식 변환)

`saveInitialWorld(db, state: WorldInit, options)`(`world/persistence.ts:7`)가 유일한 생성 경로다. 운영에서 부르는 곳은 `cli/createWorld.ts:39`뿐이다. 시험 파일(`*.test.ts`) 밖의 나머지 호출(`apps/engine/test/seasonFixture.ts`, `tools/season-throughput.ts`, `e2e/rankingSeed.ts`)은 시험·도구다. 이 목록을 소스 검사 시험으로 고정한다.

갈래 조건은 `commands = presetCommands(preset)` 하나다. `initial.ext`가 있는지로 갈래를 정하지 않는다. 조각이 없는 확장 명령만 켠 월드(2a의 계략 4종)는 `ext`가 없어도 확장 형식으로 만들어야 하기 때문이다.

`commands`가 `null`이면 E3를 지나지 않고 그때 main의 기본 생성 경로를 그대로 탄다. 지금은 origin 1(`persistence.ts:48-59`)이다. `0bebd1f`는 정책 구현 뒤 새 월드를 origin 1과 F = 0으로 만들고 명시적 옛 형식 옵션만 F null로 둔다. 인사나 확장을 켠 새 월드의 형식은 미결이고 이 초안이 정하지 않는다(E8). 이 갈래에서는 `WorldExtSlice` 행을 쓰지 않는다.

이 분기는 확장 칸을 실을지만 정한다. 상태 없는 확장 명령만 켠 월드도 확장 칸이 필요하다는 판단까지다. 확장 칸을 어느 wire에 싣는지, 인사·정책과 함께 켜는지는 이 분기만으로 확정되지 않는다(E8 복합 제안).

`commands`가 있으면 같은 함수 안에서 이 순서로 한다. 이 갈래의 코드는 2a에서 운영 등록과 함께 넣는다(단계 표). 운영 목록이 빈 동안 도달할 수 없어 실행 증거가 없는 코드를 먼저 병합하지 않기 위해서다.

1. `base: WorldInit`는 지금 `initial`(`persistence.ts:27`)이다. `presetRules`가 있고 `ext` 키가 없다.
2. 확장 상태의 입력은 `ExtInitContext`(`DeepReadonly<Omit<WorldState, 'ext'>>`)이므로 레코드 형식으로 바꾼다. `toWorldState(base)`는 `ext` 키가 없을 때 조각 검증을 하지 않고 배열을 id 레코드로 바꾸며 `presetRules`도 옮긴다(`model/world.ts:33-47`). 그 결과를 그대로 `createExtState(commands, context)`에 넘긴다. `WorldInit` 배열을 직접 넘기지 않는다.
3. 결과가 `undefined`이면 `initial = base`다. 값이 있으면 `initial: WorldInit = { ...base, ext }`다. `WorldInit.ext`는 이미 있는 선택 칸이다(`world/bootstrap.ts:86`).
4. `initialStateHash = hashState(initial)`이다. 기존 `World.initialStateHash` 칸에도 같은 값을 쓴다.
5. 같은 트랜잭션에서 조각 행과 E8의 확장 칸을 쓴다. 확장 칸은 그때 채택된 기록 형식에 맞춘다. 조각 행은 `initial.ext` 유무로 나눈다.
   - `initial.ext`가 없으면(`extSliceKeys(commands)`가 빈 배열, 2a의 계략 4종) 저장 검사와 행 쓰기를 모두 건너뛴다. 대신 `extSliceKeys(commands).length === 0`을 확인한다. 생성 뒤 그 월드의 `WorldExtSlice`가 0행이어야 한다. `assertStorableJson`은 `undefined`를 거부하므로(`storableJson.ts:5`) 이 갈래에서 부르지 않는다.
   - `initial.ext`가 있으면 `assertStorableJson(initial.ext, 'ext')`로 고정 label을 넘겨 검사한다. 그다음 key 집합이 `extSliceKeys(commands)`와 정확히 같은지 본다. 조각마다 한 행을 쓴다.
   - 행 쓰기는 0단계와 같은 매개변수 SQL로 한다. `worldExt.ts` 옆의 새 DB 함수 `insertWorldExtSlices(tx, worldId, slices)`가 조각마다 `tx.$executeRaw` 태그 템플릿 `INSERT INTO "WorldExtSlice" ("worldId", "key", "value") VALUES (${worldId}, ${key}, ${JSON.stringify(value)}::jsonb)`를 한 번씩 실행하고 결과가 1행인지 본다. 이 함수는 2a 코드와 함께 부모 배정을 받아 만들며 지금 0단계 HEAD `31c9562`에는 더하지 않는다. 조각 값이 JSON `null`이어도 `JSON.stringify`가 문자열 `null`을 넘기므로 JSONB `null`로 저장된다. `writeWorldExtChanges`의 갱신(`worldExt.ts:44-47`)과 같은 방식이라 읽기·쓰기 표현이 하나다. Prisma `createMany`를 쓰지 않는다. `Json` 필드의 최상위 `null`은 `Prisma.JsonNull`로 따로 표시해야 JSON `null`이 되고 그렇지 않으면 DB `NULL`이나 오류가 된다. 이 구분을 생성 경로에만 하나 더 두지 않으려는 선택이다.

- 원본 빈 목록 전제에서는 확장 목록이 있는 프리셋이 생성 트랜잭션에 들어가기 전에 거부된다. `saveInitialWorld`의 `parsePreset`(`persistence.ts:25`)과 CLI 프리셋 읽기가 K2 결합 검사(`preset.ts:56-62`)로 먼저 실패한다(F10). 계략이 등록된 base에서는 계략 key가 그 검사를 지나므로 이 거부가 성립하지 않는다. 그 base에서 E3 켠 갈래 전에 그런 프리셋을 막는 것은 E10의 off-only 가드다. 그래서 1단계 B1은 원본에서는 프리셋 거부, 등록 base에서는 가드 거부만 증명한다. 확장 형식 생성은 2a, `createExtState`가 값을 내는 경로는 2b에서만 증명된다.
- `readWorldState`(`persistence.ts:97-147`)도 E5와 같은 두 함수로 `ext`를 더한다. 끈 월드는 키가 없어 지금 값과 같다. 켠 월드에서 `hashState(readWorldState(...))`가 생성 해시와 같아야 하기 때문이다.

#### E4 저장 표

정책 schema 원본은 정책 담당 `0976` 몫이다. `0bebd1f`는 `WorldExtSlice`를 정책 schema에 넣지 않는다고 적었다. 그래서 아래 모델은 정책 PR에 자동으로 들어가지 않는다. office `20261023071000_nation_offices` 저장 인계 뒤 부모가 이 모델과 `World.extSlices` 관계, `20261023072000_world_ext_slices` migration 하나만 base `d7e5868`에서 T4-03 Codex에 저장 전용으로 배정했다(E10 P-S). `0710`·`0600`·`0500`과 다른 migration은 고치지 않는다(AGENTS §9). `World`에는 `extSlices WorldExtSlice[]` 관계를 더한다. 표·열 이름은 0단계 매개변수 SQL(`worldExt.ts:16-18`, `:44-47`)이 쓰는 `"WorldExtSlice"`, `"worldId"`, `"key"`, `"value"`(JSONB)와 같아야 한다. 이름이 어긋나면 컴파일은 되고 실행에서만 실패하므로 B2를 실제 migration 위에서 다시 돈다.

```prisma
model WorldExtSlice {
  worldId String
  key     String
  value   Json
  world   World  @relation(fields: [worldId], references: [id], onDelete: Cascade)
  @@id([worldId, key])
}
```

- 조각 하나가 한 행이다. 턴마다 바뀐 조각만 쓰고 큰 `World` 행을 다시 쓰지 않는다.
- 조각 key 집합은 생성 때 정해지고 바뀌지 않는다. 행을 더하거나 지우는 것은 생성과 월드 삭제(cascade)뿐이다.
- 확장 없는 월드에는 행이 없다. 기존 행은 backfill하지 않는다. 기존 migration 파일은 고치지 않는다.
- 장수별 진행 값(F8, U-01 준비 턴)을 조각 하나에 담으면 그 조각이 거의 매 턴 바뀌어 행 JSON 전체를 다시 쓴다. 해시·롤백·적재 계약은 그대로이므로 이 계획과 충돌하지 않는다. 쓰기 양을 줄이려고 조각을 나눌지 별도 표를 둘지는 T4-07 계획이 정한다. 없는 장수를 0으로 읽는 조각이면 `general.create`(`inputs.ts`)를 고치지 않아도 된다.

#### E5 적재 (함수 하나씩, 앱 간 import 없음)

0단계에서 만든 함수를 그대로 부른다. 같은 일을 하는 함수를 앱에 다시 만들지 않는다.

#### E6 턴·월간 저장

  - 출처: DB는 `World.turnTermMinutes`다. `loadReplayState`가 방침 모드에서 그 값을 `ReplayState.policy.turnTermMinutes`로 싣는다(`141d0a2` 엔진 `monthly.ts:32-34`). 기록은 archive `config.policy.turnTermMinutes`이고 `exportReplay`가 `World.turnTermMinutes`에서 채운다(엔진 `replay.ts:137-141`). F > 0이면 F 표지 `result.turnTermMinutes`도 있고 config 값과 같아야 한다(엔진 `replay.ts:262`).
  - 전달: F = 0이면 재생 시작에서 `enableReplayPolicy(initial, config.policy.turnTermMinutes, 0)`(엔진 `replay.ts:270-275`), F > 0이면 F 표지에서 `enableReplayPolicy(replay, result.turnTermMinutes, baselineActiveTick, emptySlots)`(`:300`)다. 합성 adapter는 이 값을 `FeatureSelection.policy.turnTermMinutes`로 그대로 넘기고 바꾸거나 기본값으로 채우지 않는다.
  - 해시: `ReplayState.policy.turnTermMinutes`는 `hashState(replay)`의 입력이다. 그래서 월간 `stateHash`(DB는 `persistMonthly`의 모든 쓰기 → `monthlyTick` → `loadReplayState` → `hashState`, 재생은 `checkMonth`)와 종료 `finalStateHash`에 들어간다. F 전 `ReplayState`에는 `policy` 키가 없다. origin의 `initialStateHash`·`resourceHash`에는 들지 않고 정책 전환이 그 둘을 바꾸지 않는다.
  - 일치: F가 같아도 `turnTermMinutes`가 다르면 같은 선택이 아니다. 엔진 시작 대조와 수출은 DB `World.turnTermMinutes`, F 표지 결과, 기록 config 값이 같은지 본다. F 뒤 `World.turnTermMinutes`가 바뀌는 경로를 둘지와 그때의 뜻은 정책 계약 몫이고 이 계획이 정하지 않는다.
  - 검증 조건: 정책을 켠 복합 월드에서 DB 월간 snapshot `stateHash`와 순수 재생 해시가 같고 둘이 같은 `turnTermMinutes`를 쓴다. 반례로 같은 F에 config `turnTermMinutes`만 바꾼 기록은 표지 대조나 첫 정책 월 해시에서 거부된다. DB 값과 기록 값이 다르면 엔진 시작 대조가 쓰기 전에 멈추며 DB 행이 바뀌지 않는다.
- 확장 칸과 인사 표시는 생성 때 정해지므로 origin 쪽에 실린다. 그런데 지금 origin 1 판독기는 origin의 모르는 칸을 보지 않고 두 해시만 다시 계산한다(`replay.ts:135-137`). 그래서 확장 칸이나 인사 표시가 있는 기록은 옛 판독기와 archive 5 판독기가 모르고 성공하지 못하도록 wire에서 구분돼야 한다.

wire 구분 제안 (하나로 좁힌 기술안. 미채택이며 번호는 배정하지 않는다):

- origin 쪽: 확장이나 인사를 생성 때 켠 새 월드만 필수 capability descriptor를 가진 origin을 쓴다. 판별값은 미배정 상수 `ORIGIN_CAPS`이고 origin 1이 아니다. 모양은 `{ version: ORIGIN_CAPS, initial, initialStateHash, resourceHash, capabilities: { version: 1, ext?: ExtOriginFields, personnel?: 인사 계약의 정적 칸 } }`다. `capabilities.version`이 1이 아니거나 모르는 키가 있거나 기능 칸이 하나도 없으면 거부한다. 기능 칸이 없는 월드는 origin 1이어야 하기 때문이다.
- archive 쪽: 별도 archive 판별값이 필요하다. archive 2와 5는 origin 1만 받는다(`replay.ts:127`, `0bebd1f` B-2). 둘이 descriptor origin을 받게 넓히면 기존 archive를 재해석하게 된다. 그래서 미배정 상수 `ARCHIVE_CAPS` 하나를 둔다. 이 archive는 `ORIGIN_CAPS` origin만 받고 config는 archive 2 config에 정책 몫 `policy`(archive 5와 같은 `{ version: 1, fromSequence, turnTermMinutes }`)를 선택 칸으로 더한 모양이다. archive 1·2·5는 지금 판정 그대로이고 descriptor origin을 받지 않는다.
- 활성 기능의 원본: 확장·인사는 descriptor에 칸이 있으면 켜진 것이다. 정책은 descriptor에 두지 않는다. DB는 `World.policyFromSequence`와 표지, 기록은 archive `config.policy`가 원본이다. 그래서 정책 전환은 origin을 다시 쓰지 않는다. 기존 origin 1 월드는 전환 뒤 archive 5로 가고 descriptor origin 월드는 전환 뒤에도 같은 `ARCHIVE_CAPS`의 `config.policy`만 채운다.
- 해시: `initialStateHash`는 지금처럼 `hashState(initial)`이고 조각이 있으면 `initial.ext`가 들어간다. descriptor origin의 `resourceHash`는 `hashState({ 지금 resourceHash 입력 다섯 칸, capabilities })`다. 단독 3 초안의 옛 참고 식(확장 칸만 더함)과 다른 식이며 둘 다 채택되지 않았다. origin 1의 `resourceHash(initial)` 식은 그대로다. 두 해시는 다시 계산해 대조하는 값이며 보안이나 진위를 보장하지 않는다.
- adapter 경계: origin 종류마다 정적 adapter 하나(`origin 1 → { initial, ext: null, personnel: null }`, `ORIGIN_CAPS → descriptor에서 읽음`)와 archive 종류마다 정책 adapter 하나(`archive 1·2 → null`, `archive 5 → config.policy`, `ARCHIVE_CAPS → config.policy 또는 null`)를 두고 합성 선택 함수가 둘을 합친다. 각 archive 종류는 받는 origin 종류를 명시한다(1·2·5는 origin 1, `ARCHIVE_CAPS`는 `ORIGIN_CAPS`).
- 3·4 초안과의 관계: 이 안은 확장·인사를 한 descriptor origin으로 묶어 3·4를 따로 쓰지 않는다. 3·4 초안을 따로 채택한다면 각 origin이 정적 adapter를 하나씩 더하고 정책 F는 archive 쪽 config에서 읽는다. 어느 쪽이든 나중 정책 전환이 그 origin을 덮어쓰지 않는다. 이 안은 정책·인사 담당과 합의된 것이 아니다.

(c) projection과 거부

- F 전 projection은 정책 필드(칸 `explicit`, 방침·활동 지도)만 다룬다. `ext`, `presetRules`, `commandMeta`, `nationTurns`, `assignmentOffers`, `officeTurns`, `ReplayState.offices`는 projection 앞뒤로 그대로다.
- 합성 선택 함수가 모르는 기능 태그나 지원 목록에 없는 조합을 만나면 read(`readArchive`), load(`loadWorld`·`loadReplayState`·엔진 시작 대조), replay, export가 projection과 쓰기 전에 거부한다.
- `ext`나 인사 상태가 있는데 판독기가 그 기능을 지원하지 않으면 실패한다. 옛 허용 목록으로 그 키를 잘라 내고 성공시키지 않는다.
- `ARCHIVE_CAPS` 판독 순서 제안: 1) 외피(archive 판별값이 지원 형식인지, 받는 origin 종류와 짝이 맞는지, R11의 필수 칸 `config`·`end`·`afterEnd`·`inputs`·`months`의 존재와 기본 타입) → 2) descriptor와 기능 태그(`capabilities.version`, 모르는 키, 지원 조합) → 3) 기능별 내용(확장 R5~R8·R10·R13, 인사 계약의 검사, 정책 `config.policy`와 표지·F·`turnTermMinutes`의 관계, (f)의 입력별 kind·기능 범위·REJECTED 사유 모양) → 4) 초기 해시(R9의 `initialStateHash`·`resourceHash`) → 5) sequence 재생(입력 순서, R12, (f)의 dispatch로 고른 기능별 적용) → 6) runtime 해시(월간 `stateHash`, 종료 `finalStateHash`). archive 1·2·5의 기존 경로에는 이 순서를 소급하지 않는다. 3을 4보다 앞에 두므로 descriptor 내용 오류는 해시 불일치보다 먼저 보고된다.
- 이 순서는 새 판별값에만 건다. archive 1·2의 지금 순서(외피 → 해시 → config, `replay.ts:124-180`)와 모르는 kind의 REJECTED 수용, afterEnd 허용에는 검사를 끼워 넣지 않는다. archive 5는 `0bebd1f` 순서를 따른다.
- DB load·export도 검증을 projection과 쓰기보다 먼저 한다. 지원하지 않는 형식·조합이면 load는 쓰기 전에 실패하고 export는 파일을 내지 않는다. 검증 조건은 그 실패 뒤 `World`, `InputEvent`, 장수·칸, `WorldExtSlice`, 연감 행이 바뀌지 않는다는 것이다.

(d) 기능 off 경로와 조합 coverage

- 기능 off는 그 기능 칸이 null이라는 뜻뿐이다. 확장이 꺼져도 정책 월드의 F와 방침 상태는 그대로이고 인사 상태를 지우지 않는다.
- 확장 on은 둘로 나눈다. 조각 없는 등록 계략(`sliceKeys: []`, `ext` 키 없음, 행 0)과 조각 있는 명령(`initial.ext`와 행)이다.

지원 범위는 위 확정 조합 표의 두 줄뿐이다. 아래는 지원이 아니다. 계약안의 채택과 그 뒤 실제 증거를 나눠 적는다.

| 확장 | 인사 | 정책 | 계약 상태 | 실제 증거가 생기는 때 |
| ---- | ---- | ---- | --------- | --------------------- |
| on, 조각 없음 | 없음 | 없음 | 미채택 후보 (`ORIGIN_CAPS`, 정책 칸 없음) | 채택 뒤 계략 4종 운영 등록(2a) |
| on, 조각 없음 | 없음 | 있음 | 미채택 후보 (`ARCHIVE_CAPS`에 `config.policy`) | 채택 뒤 2a |
| on, 조각 있음 | 없음 | 있음 또는 없음 | 미채택 후보 | 채택 뒤 조각 명령 첫 운영 등록(2b) |
| 없음 | 있음 | 있음 또는 없음 | 미채택 후보. T2-05 정정 필요 | T2-05 구현 뒤 |
| on | 있음 | 있음 또는 없음 | 미채택 후보 | T2-05와 T4-50 뒤 |

- 새 확장 월드를 위 첫 줄과 둘째 줄 가운데 무엇으로 만들지는 정하지 않는다(Q8). `0bebd1f`의 새 월드 F = 0은 확장·인사가 없는 정책 단독 월드의 범위다.

- T2-05 옛 사본의 origin 4 전용 gate(인사 API가 origin 4가 아니면 거부)와 생성 때 `WorldInit`의 `ext`·`nationTurns` 금지는 이 합성과 맞지 않는다. 그 담당의 별도 정정이 필요하고 이 계획이 고치지 않는다.

(e) 합성 경계

- DB 월간: `runMonthly` 뒤 같은 트랜잭션에서 정책 쓰기, `ext` 쓰기(`persistExt`), 인사 쓰기를 마치고 `monthlyTick` → `loadReplayState` → `hashState`로 간다. 기능 쓰기는 각자 자기 표만 쓰고 남의 상태를 다시 쓰지 않는다.
- 엔진은 DB 소스로, 재생은 기록 소스로 같은 합성 선택 함수를 부른다. 같은 결과에서 resolver, 인사 `features`, `policyMode`를 꺼낸다.
- 인자 경계: `runGeneralTurn(state, actor, command, seed, options, resolver, features?)`. 다섯째 `options`는 기존 `NpcContext` 옵션(지금 `convergence`, `packages/rules/src/commands/turn.ts:15`)과 인계 때 이미 있는 옵션을 그대로 두고 방침 맥락을 덧붙인다(정책 소유). 여섯째에는 resolver만(T4-03), 그 뒤에는 인사 `features`만 둔다. 인사 자리는 T2-05 초안을 따른 제안이다. `runReplayAction(replay, seed, unitSet, resolver, features?)`이고 방침 맥락은 `ReplayState`에 있다. 한 step에서 선택을 한 번 만들고 각 자리로 나눠 넣는다. 한 기능이 다른 기능의 자리에 값을 넣지 않는다. 인사 자리와 `initialReplayState`·`applyRecordedInput`·`runMonthly`의 인사 인자 모양은 T2-05 정정 몫이고 이 제안은 자리를 비워 두는 데까지다.

(f) `ARCHIVE_CAPS` 입력 kind 검증과 dispatch 경계 (F1 정정 2)

- 반례 근거: `141d0a2`의 `validatePolicyRecordedInput`은 모든 입력에 kind 5종 enum을 먼저 건다(rules `policy/replay.ts:41-55`, `:91-92`). 그래서 인사 kind는 APPLIED든 REJECTED든 인사 분기 전에 거부된다. 엔진 `validatePolicyArchive`가 `inputs`와 `afterEnd` 전부에 이 함수를 부르고(엔진 `replay.ts:249-253`) rules `applyRecordedInput`도 `replay.policy`가 있으면 status를 보기 전에 같은 검사를 건다(rules `replay.ts:85`). archive 5 단독에서는 맞는 동작이며 결함이 아니다. 새 조합의 반례다. 이 helper를 `ARCHIVE_CAPS`에 고치지 않고 그대로 공유하면 위 두 호출 자리에서 인사 입력이 다시 거부된다.
- kind 집합 (`ARCHIVE_CAPS` 전용):

| 소유 | kind | 받는 범위 |
| ---- | ---- | --------- |
| 공통 | `turns.set`, `general.create` | 늘. 모양은 정책 규칙대로 F 전 옛 모양, F부터 정책 모양이다. 확장 on이면 `turns.set` 칸에 R12를 덧붙인다 |
| 정책 | `general.setPolicy`, `general.active` | 정책 on이고 sequence ≥ F |
| 정책 표지 | `system.policy.enable` | 정책 on이고 0 < F ≤ coverage일 때 sequence F의 APPLIED 하나 |
| 인사 | `personnel.appoint`, `personnel.dismiss`, `offer.respond`, `nationTurns.set` | 인사 on이면 sequence 1부터. 인사는 생성 때 켜지므로 정책 F 전이라는 이유로 거부하지 않는다 |

- 입력마다 검사 순서: 합성 판독기 한 곳이 envelope(sequence, `generalId`, status, kind가 켜진 기능 kind의 합집합 안인지)를 본다. 다음으로 kind의 소유 기능이 켜졌는지와 그 기능의 범위(정책 kind는 F 이후)를 본다. REJECTED는 사유 모양 `{ code, message }`만 검사하고 성공 result 필드를 요구하지 않으며 상태를 바꾸지 않고 건너뛴다. APPLIED는 소유 기능의 payload·result 검사를 거쳐 적용한다.
- dispatch: kind마다 소유 기능 하나의 검증·적용 함수만 부른다. 같은 입력을 기능별 dispatcher가 각자 다시 돌리지 않는다. 공통 kind의 적용은 하나이고 정책 on이면 그 안의 정책 갱신(활동 tick 등)이 함께 돈다. 인사 입력에 정책 전용 enum이 먼저 걸리지 않는다.
- 표지와 afterEnd: `system.policy.enable`은 정책 의미 그대로다(REJECTED 불가, sequence F, `generalId` null, config와 일치). `ARCHIVE_CAPS`의 `afterEnd`는 위 합집합과 기능 범위 안의 REJECTED만 받는다. 둘 다 새 wire 전용안이다.
- 바꾸지 않는 것: archive 1·2의 모르는 kind REJECTED 수용, archive 5의 단독 enum과 검사 순서.
- 인계 조건: 인사 kind의 payload·result·효과는 T2-05 별도 정정과 그 실제 구현 SHA로 핀한다. 정책 helper를 envelope enum 검사와 kind별 검사로 나누는 일과 `applyRecordedInput`의 정책 검사 진입을 합성 판독기 뒤로 옮기는 일은 정책 담당 `0976`의 후속 분리·합성 계약이다. 그때도 archive 5 단독 경로의 동작은 그대로여야 한다. 엔진 쪽 PENDING 처리기도 같은 kind 소유 경계를 쓰며 그 소유는 U62-5다.

위 미채택 제안이 정정·채택되기 전에는 이 계획이 복합 허용·거부 조합을 정하지 않는다.

확장 칸 (어느 형식, 어느 위치에 실리든 같은 내용). `initial`은 origin 1과 같은 `WorldInit`이고 켠 조각이 있으면 `initial.ext`가 있다. `initialReplayState`는 지금처럼 `WorldInit`을 입력으로 받는다. `resourceHash`는 선택된 origin adapter의 식으로 대조한다(아래 코드 주석).

```ts
interface ExtOriginFields {
  commands: EnabledCommands; // 정규화한 확장 목록. null 아님, 두 목록이 모두 비지 않음
  preset: JsonValue; // 생성 때의 World.preset 사본. parsePreset을 지난 정규형
  resources: Record<string, JsonValue>; // 확장 리소스 사본. 지금은 {}
  sliceKeys: string[]; // extSliceKeys(commands). 빈 배열 허용
}
// initialStateHash = hashState(initial)
// resourceHash는 origin adapter마다 다르다. origin 1 식은 지금 구현이고 단독 3 초안과 ORIGIN_CAPS 안의 식만 미채택이다
//   origin 1 (지금 그대로): resourceHash(initial) (replay.ts:51-59)
//   단독 3 초안 (옛 참고 식): hashState({ resourceHash 입력 다섯 칸, commands, preset, resources, sliceKeys })
//   ORIGIN_CAPS 안 (미채택): hashState({ resourceHash 입력 다섯 칸, capabilities })
```

- 기록 본문은 archive 2와 같은 칸(`config`, `inputs`, `months`, `end`, `afterEnd`)을 쓴다. 확장 칸이 실린 기록을 어느 wire로 수출하는지와 `replayToEnd`(`:307`)가 받는 형식은 복합 제안 (b)의 wire 구분이 채택된 뒤 정한다.

거부 표 (`readArchive`). 운영 목록이 빈 동안 확장 칸이 있는 기록은 모두 R6에서도 걸려 R7~R13을 따로 증명할 수 없다. 그래서 R1~R13의 계약은 함께 채택하되 1b 코드는 운영 목록 없이 증명되는 R1~R6만 넣고 R7~R13은 운영 등록 뒤 증명되는 2a에서 넣는다.

- 담당과 범위: Codex 채팅의 작업실 `085a`, 브랜치 `codex/t4-03-storage-foundation`. 0단계 순수·DB 함수 기반만 구현했고 이 몫은 리뷰 대기다. 공유 대기열은 부모가 합친다. T4-03 전체와 AC-P2-02 (나)는 미완료이며 1·2단계는 채택하지 않았다.
