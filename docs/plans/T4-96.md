# T4-96 허용 월드의 상한 있는 능력치 유산

현재 범위는 D-065에 따라 기존 레포의 PG·서버·엔진·웹이다. CF 이식·대조와 H5는 작업과 완료 조건에서 제외한다. CF 전용 예약·영수증 모듈은 추가하지 않는다. 실제 유산 PG·HTTP·엔진 133건과 합성 활동 10만 행의 규모 측정 1건, authz 144건, migration 2건을 함께 통과했다. 화면 단위 26건, 브라우저 2건과 전체 검사 440파일·6,853시험도 통과했다. 최종 독립 리뷰는 코드·시험 모두 통과했다. 필수 CI·정상 병합은 남았다.

> 대기열: T4-96 · AC: AC-P2-33 · 백엔드(rules·engine·server·PG): Codex · 계획·화면 설계(Artifacts)·화면 코드: Claude · 독립 리뷰: 구현하지 않은 쪽 · 근거: D-061~D-065 · 상태: 진행중(2026-11-03). T4-95 `a619a0c5`를 포함한다. 저장·엔진·서버·화면을 구현했으며 최종 검증·정상 병합 전이므로 AC는 완료가 아니다.

## 계획

### 목표
새 규칙 기능 `heritage-v1`을 켠 월드에서만 계정 유산 포인트를 쌓고 쓴다. 정상 종료한 월드가 그 월드의 사람 계정에 포인트를 한 번 지급하고 유산 월드에서 `general.create` 때 포인트로 능력치를 올린다. 관리자 종료·초기화는 그 월드에서 쓴 생성 포인트를 한 번 모두 돌려주고 새 포인트는 주지 않는다. 실제 적용값과 기능 판은 생성 기록에 고정하며 재생은 계정 잔액을 읽지 않는다. PG는 한 트랜잭션으로 끝낸다.

### 승인된 규칙 (D-062·063·064. 다시 묻지 않음)

| 항목 | 값 |
| --- | --- |
| 적용 | `heritage-v1`을 켠 월드만 지급·사용. 끈 월드는 둘 다 없다 |
| 사용 상한 | 능력치당 +3, 한 장수 합계 +6. 생성 때 붙는 보너스의 상한이다 |
| 비용 | +1당 1점 |
| 지급 상한 | 한 기수(월드)에서 계정당 최대 5점 |
| 활동 지급 | 같은 계정의 직접 명령 활동이 있는 게임 달 수가 12·24·36개월에 닿을 때마다 +1(최대 3) |
| 승리 지급 | `UNIFIED` 종료에서 승자 국가 소속이면 +2 |
| 관리자 종료·초기화 | 지급 0. 그 월드의 생성 사용 점수를 모두 반환한다. 같은 종료의 중복·재시도도 한 번만 반환한다 |
| 잔액 상한 | 없다. 6은 장수 하나에 붙는 합계 상한이지 잔액 상한이 아니다 |

이 표 밖의 자격(재위 기간, 최소 활동, 추가 비용, 은행 상한)은 만들지 않는다. 수치는 기능 판 1의 상수이고 월드 설정 칸이 아니다. 다른 수치는 `version:2`로 연다.

## 설계

### 규칙 기능
`heritage-v1`: `requires:['policy']`, `conflicts:[]`. `featureData['heritage-v1'] = {version:1}`(zod `strictObject`). `initial`에 유산 칸이 없고 `WorldState`에 상태 조각을 두지 않는다. 월 정산·입력 뒤 훅이 없다. 엔진 기능 목록에는 `{ key: 'heritage-v1' }` 1줄만 더한다.

상수(`rules/heritage/constants.ts`):
```
HERITAGE_V1 = { perStat: 3, perGeneral: 6, perSeason: 5,
                activityMonths: [12, 24, 36], winPoints: 2 }
```

### 생성 입력
- `general.create` payload에 `heritage?: Partial<Record<StatKey, 1|2|3>>`를 더한다. `StatKey`는 월드 판의 능력치 키(3개 또는 5개)다.
- `validateGeneralCreation(payload, statRules, lineage, heritage)`에 네 번째 인자를 더한다. 호출자 5곳(엔진 `inputs.ts:282`, 서버 `routers/general.ts:150`, `rules/ruleFeatures.ts:50`, `replayInputs.ts:85`, `e2e/rankingSeed.ts:67`)에 월드 기능을 넘긴다.
  - 끈 월드: 키가 있으면 `BAD_HERITAGE`.
  - 켠 월드: 키가 없으면 비용 0. 있으면 빈 객체 금지, 키는 월드 판 능력치만, 값은 정수 1~3, 합 1~6, 모든 키에서 `payload[key] + bonus[key] <= statRules.max`. 어기면 `BAD_HERITAGE`. 이 판정은 차감 전에 끝난다.
- 비용 = 보너스 합. 난수를 쓰지 않으며 `buildCreatedGeneral`의 소비 순서를 바꾸지 않는다. 능력치는 `payload + bonus`로 만든다.
- 생성 결과 기록: `result = { general, activeTick, heritage: {version:1, bonus, cost} }`. 보너스가 없으면 `heritage` 키가 없다. 이 `InputEvent.result`가 고정된 생성 기록이다.
- 새 오류: `BAD_HERITAGE`(「유산 배분을 확인하세요.」, HTTP `BAD_REQUEST`), `HERITAGE_INSUFFICIENT`(「유산 포인트가 부족합니다.」, HTTP `CONFLICT`). 두 백엔드가 같은 코드·문구·HTTP 코드를 쓴다.

### 재생 고정
- `applyCreationInput`: 켠 월드면 `result.heritage.bonus`가 payload `heritage`와 정규 JSON으로 같고 `cost`가 합과 같으며 모든 능력치가 `payload + bonus`인지 본다. 끈 월드에서 `result.heritage`나 payload `heritage`가 있으면 거부한다.
- five-stats `checkArchive`와 `replayInputs.ts:86`의 능력치 비교에 보너스를 더한다.
- `heritage-v1` `checkArchive`: APPLIED `general.create`마다 위 검사를 반복하고 `statRules.max`는 `origin.initial.statRules`로 본다.
- 재생·로드·엔진 상태 어디서도 `HeritageAccount`·`HeritageEntry`를 읽지 않는다. 반환이 일어나도 생성 기록과 재생 결과는 그대로다. 정적 시험으로 `packages/rules/src`와 엔진 재생 경로의 참조 0을 고정한다.

### 직접 명령 활동의 근거
`rules/heritage/activity.ts`에 입력 종류를 둘로 나눈다. 등록된 모든 입력 종류(`ruleRegistry.inputKinds`)가 정확히 한쪽에 있어야 하며 새 종류가 생기면 시험이 실패해 분류를 강제한다.

| 분류 | 입력 종류 |
| --- | --- |
| 활동으로 센다 | `turns.set`, `general.setPolicy`, `nationTurns.set`, `personnel.appoint`, `personnel.dismiss`, `offer.respond`, `treaty.propose`, `treaty.respond`, `treaty.break`, `campaign.relationship`, `campaign.unit`, `campaign.order`, `city.resources`, `logistics.order`, `governance.act`, `lineage.act` |
| 세지 않는다 | `general.active`(로그인·부수 기록), `general.create`, 관리자 시계·종료·초기화 종류 |

- `general.setPolicy`는 사람이 직접 고른 명령 설정이라 센다. 방침의 자동 실행은 입력 기록이 없으므로 원래 근거 행에 없다. 이 분류는 승인된 직접 명령 활동을 그대로 구현하며 새 자격 규칙을 더하지 않는다.
- 근거 행: 그 월드의 `status='APPLIED'`, 위 목록의 `kind`, `sequence <= endedSequence`인 `InputEvent`. 거부된 입력은 효과가 없으므로 세지 않는다.
- 달: `t = tick ?? result.activeTick`, 달 번호 `floor(t / TICKS_PER_MONTH)`. 목록 종류의 APPLIED 행에 `t`가 없으면 자료 손상으로 보고 예외다(정책 판 필수라 정상 경로에서는 생기지 않는다).
- 계정 단위: `(userId, 달 번호)`를 한 번만 센다. 한 계정이 전임자와 후계자로 같은 달에 여러 번 입력해도 1이다. 장수는 보지 않는다.
- 활동 점수 = `min(3, floor(달 수 / 12))`.

### 기수 지급
순수 함수 `seasonHeritageAwards({ reason, winnerNationId, generals: {userId, nationId}[], activity: {userId, kind, status, sequence, tick, result}[], endedSequence })` → `{ userId, activityMonths, activityPoints, winPoints, total }[]`(userId 오름차순, `total > 0`만).
- `reason='UNIFIED'`면 승자 소속 계정에 `winPoints=2`. `END_YEAR`는 0.
- `total = min(5, activityPoints + winPoints)`. 현재 승인 수치에서는 상한에 닿지 않지만 상한식을 그대로 둔다.
- 입력을 바꾸지 않고 같은 입력에 같은 출력을 낸다.

### 관리자 종료·초기화 반환
순수 함수 `creationRefunds({ worldId, reason: 'ADMIN_END'|'ADMIN_RESET', spends: {userId, key, delta, sequence}[], existingKeys, withdrawnUserIds })`(`rules/heritage/refund.ts`) → 넣을 항목 목록.
- 그 월드의 `CREATION_SPEND` 한 건마다 `CREATION_REFUND` 한 건을 만든다. 키는 `refund:<worldId>:<사용 순번>`, `delta = -spend.delta`이다. 원래 사용 하나에 반환 키 하나가 대응한다.
- `existingKeys`에는 반환·몰수 짝의 키를 모두 읽어 넣는다. 이미 있는 반환 키는 다시 만들지 않는다.
- 탈퇴 계정은 반환 항목과 같은 크기의 `FORFEIT` 항목 `forfeit:refund:<worldId>:<사용 순번>`을 짝으로 만든다. 잔액은 0으로 남고 탈퇴 때 몰수한 금액이 되살아나지 않는다. 두 항목 모두 원장에 남으므로 `balance = SUM(delta)`가 유지된다.
- 새 지급(`SEASON_CREDIT`)은 만들지 않는다. 장수·생성 기록·archive는 입력에 없다.
- 출력은 (userId, 사용 순번) 오름차순이고 같은 입력에 같은 출력을 낸다.

### 저장 (PG)
새 migration `20261114000000_heritage_ledger` 하나. 기존 migration·enum은 고치지 않는다. World 칸을 더하지 않으므로 World CHECK 목록 시험 6개는 바뀌지 않는다(L1에서 표 목록을 세는 시험이 있으면 그때만 1줄 더한다).

```prisma
model HeritageAccount {
  userId  String @id
  balance Int
  user    User   @relation(fields: [userId], references: [id], onDelete: NoAction)
}
model HeritageEntry {
  id        BigInt   @id @default(autoincrement())
  userId    String
  key       String   // credit:<worldId> | spend:<worldId>:<seq> | refund:<worldId>:<seq> | forfeit | forfeit:refund:<worldId>:<seq>
  kind      String   // SEASON_CREDIT | CREATION_SPEND | CREATION_REFUND | FORFEIT
  worldId   String?  // World FK 없음. 월드 삭제 뒤에도 기록을 남긴다
  delta     Int
  detail    Json
  createdAt DateTime @default(now())
  user      User     @relation(fields: [userId], references: [id], onDelete: NoAction)
  @@unique([userId, key])
  @@index([userId, id])
  @@index([worldId, kind])
}
```
SQL로 더하는 것: `balance >= 0` CHECK, `kind` 값 목록 CHECK, `kind`별 `delta` 범위 CHECK(지급 1~5, 사용 -6~-1, 반환 1~6, 몰수 < 0), `HeritageEntry` UPDATE·DELETE 금지 트리거(ERRCODE `55000`, `world_create_request_immutable` 선례). 불변식은 `balance = SUM(delta)`이다.

엔진 쪽은 `apps/engine/src/heritage/{port,repository,service}.ts`다. `service.ts`가 순수 함수를 부르고 판정하며 `PgHeritageRepository(tx)`가 SQL만 맡는다. `inputs.ts`·`turnLoop.ts`·`admin/end.ts`·`admin/reset.ts`에는 SQL·Prisma 호출을 새로 넣지 않고 이미 열린 `tx`로 service 함수를 한 줄 부른다.

잠금 순서는 모든 경로에서 같다. 대상 `User`를 userId 오름차순으로 잡고(생성·지급·반환은 `FOR SHARE`, 탈퇴는 `FOR UPDATE`) 그다음 `HeritageAccount` 행을 userId 오름차순으로 잡는다. 사용자 행을 모두 잡은 뒤 계정 행을 잡으므로 교착이 없다.

**지급** (`creditSeasonHeritage(repository, {worldId, outcome, next, endedSequence})`)
- `turnLoop.ts:389` `worldResult.create` 바로 뒤에서 `heritage-v1` 월드만 부른다. 같은 트랜잭션이다.
- 근거 행을 읽어 `seasonHeritageAwards`를 부른다. 대상 계정을 잠그고 `WITHDRAWN`이면 건너뛴다.

**사용** (`debitCreationHeritage(repository, {userId, worldId, sequence, bonus, cost})`)

**반환** (`refundWorldHeritage(repository, {worldId, reason, requestId, newWorldId?})`)
- `processAdminEnd`에서는 `end.ts:130`의 닫기 행 수 확인 바로 뒤, `processAdminReset`에서는 `reset.ts:303`의 원본 닫기 확인 바로 뒤에 부른다. 둘 다 `!code`인 분기 안이고 이어지는 `InputEvent` APPLIED 저장·감사 기록과 같은 트랜잭션이다. 거부·`deferred`에서는 부르지 않는다.

- `detail = {version:1, reason, spendKey, requestId, newWorldId?}`. `newWorldId`는 초기화 기록용이며 새 월드에 사용·잔액을 옮기지 않는다.

**탈퇴** (`server/auth/withdrawalStore.ts` → `server/heritage/pgStore.ts`의 `forfeitHeritage(tx, userId)`)
- 같은 트랜잭션에서 `User FOR UPDATE` 뒤 계정 행을 잠그고 잔액이 있으면 `forfeit` 항목(`-balance`)을 넣고 0으로 만든다.

## 검증

### rules
- 배분: 능력치 +4, 합 +7, 월드 판에 없는 키(3능력치 판의 `politics`), 0·음수·소수, 빈 객체, `payload + bonus > statRules.max`를 `BAD_HERITAGE`로 거부. 끈 월드의 키는 거부. 키 없음은 비용 0이고 기존 결과·난수 소비와 같다.
- 활동: 11개월 0, 12개월 1, 24개월 2, 36개월 3, 48개월 3. 한 달에 여러 입력·여러 장수(전임자·후계자)는 1. `general.setPolicy` APPLIED만 있는 달은 1로 센다. `general.active`·`general.create`·관리자 종류·REJECTED·`endedSequence` 뒤 입력은 0. `turns.set`은 `result.activeTick`로 달을 정한다. 분류 시험: 등록 입력 종류 전부가 정확히 한쪽에 있다.
- 지급: `UNIFIED` 승자 소속 +2, 비소속 0, `END_YEAR` 승리분 0, 합계 ≤5, 출력 정렬, 입력 불변, 같은 입력 같은 출력.

### PG 통합 (실제 DB·엔진)
- 종료 지급: 활동 36개월 계정 +3, `UNIFIED` 승자 소속 +2, `END_YEAR` 활동분만. 끈 월드는 항목 0. `general.setPolicy`만으로 활동한 달도 센다.
- 중복 종료: 지급 함수를 같은 월드로 다시 부르면 잔액·항목 수가 같다. `WorldResult` 두 번째 생성은 실패한다.
- 관리자 종료 반환: 잔액 5인 계정이 유산 월드 W에서 비용 4로 생성한 뒤 W를 관리자 종료한다. 반환 항목 1건(+4), 잔액 5, 지급 항목 0. 활동 36개월이 있어도 지급 0. 장수 능력치·생성 `InputEvent.result`·`exportReplay` 해시·종료 기록의 `finalStateHash`가 반환 전과 같다.
- 초기화 반환과 월드 구분: W1에서 사용 → W1 초기화로 W2 생성 → W1 사용만 반환. W2에서 다시 사용 → W2 초기화로 W3 생성 → W2 사용만 반환하고 W1 반환은 늘지 않는다. 새 월드에는 원장 행이 옮겨지지 않는다.
- 반복 종료·초기화: 닫힌 W에 종료·초기화를 다시 보내면 `WORLD_STATE_CHANGED`로 거부되고 반환 항목·잔액이 같다. 반환 함수를 같은 월드로 직접 다시 불러도 같다.
- 거부된 관리자 요청: `ADMIN_REQUIRED`·`WORLD_NAME_CHANGED`·`WORLD_REVISION_CHANGED` 종료와 `TARGET_EXISTS`·`RESOURCE_INVALID` 초기화, 준비 미완(`deferred`)은 반환 항목 0이고 월드가 닫히지 않는다.
- 반환 실패 롤백: 반환을 넣은 직후 실패를 주입한다(시험 전용 트리거로 `AuditLog` INSERT 실패). 반환 항목·잔액·월드 상태·`InputEvent` 상태가 모두 그대로(`PAUSED`, `PENDING`)이고 초기화면 새 월드도 없다. 다시 처리하면 한 번만 반환된다. 엔진 SIGKILL 재시작 뒤에도 같다.
- 탈퇴와 반환: 탈퇴한 계정의 사용은 반환·몰수 짝이 되고 잔액 0, `balance = SUM(delta)`이다. 탈퇴와 관리자 종료를 겹쳐 20회 보낸다. 어느 순서든 최종 잔액 0, 반환 키 1개, 불변식 유지다.
- 사용과 닫기의 경합: W에서 생성 입력이 아직 처리되지 않은 채 W가 닫히면 사용·반환 항목이 없고 잔액이 그대로다. W에서 생성이 먼저 적용되면 한 번만 반환된다. 같은 계정이 X에서 생성하는 동안 W 반환을 겹쳐 20회 보낸다. 잔액이 음수가 되지 않고 불변식이 유지된다.

## 위험
- 활동 집계는 종료 트랜잭션에서 그 월드의 입력 행을 모두 읽는다. 긴 월드에서 종료 저장이 느려질 수 있다. 실제 행 수와 시간은 H2에서 측정한다.
- 관리자 종료·초기화 트랜잭션에 반환 쓰기가 더해진다. 초기화는 기존 30초 트랜잭션 안에서 끝나야 하므로 사용 행이 많은 월드의 시간을 H2에서 잰다.
- 목록 종류의 APPLIED 행에 활동 tick이 없으면 종료 저장이 예외로 멈춘다. 손상 자료에 지급하지 않으려는 선택이며 기존 `loadReplayState`의 예외 방식과 같다.
- 승리분은 종료 순간의 소속만 본다. 종료 직전에 승자 국가로 옮긴 계정도 받는다. 승인 규칙 밖의 재위·체류 기간 조건은 두지 않았다.
- `SANCTIONED` 계정은 기존 생성 규칙대로 사용할 수 없다. 지급에서는 탈퇴만 빼고 반환은 제재 계정에도 그대로 한다.
- 화면의 잔액은 안내값이다. 다른 월드에서 먼저 쓰면 제출이 `HERITAGE_INSUFFICIENT`로 끝난다.
