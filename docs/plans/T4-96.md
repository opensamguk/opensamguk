# T4-96 허용 월드의 상한 있는 능력치 유산

> 대기열: T4-96 · AC: AC-P2-33 전체, AC-P2-35의 접점 몫 · 백엔드(rules·engine·server·PG): Codex · 계획·화면 설계(Artifacts)·화면 코드: Claude · 독립 리뷰: 구현하지 않은 쪽 · CF 어댑터: 기존 CF 담당 채팅 · 근거: D-061, D-062, D-063(2026-11-03 지급 기준 승인, root가 기록 예정) · 상태: 계획(2026-11-03). 작업 트리 `lineage-20261103`(cc40c7a9)과 미커밋 T4-95 초안을 읽었다. 구현·검증·병합 전이며 이 계획으로 AC를 완료로 바꾸지 않는다

## 계획

### 목표
새 규칙 기능 `heritage-v1`을 켠 월드에서만 계정 유산 포인트를 쌓고 쓴다. 정상 종료한 월드가 그 월드의 사람 계정에 포인트를 한 번 지급하고 유산 월드에서 `general.create` 때 포인트로 능력치를 올린다. 실제 적용값과 기능 판은 생성 기록에 고정하며 재생은 계정 잔액을 읽지 않는다. PG는 한 트랜잭션으로 끝내고 CF는 아래 「CF 조율」의 표 계약을 따른다.

### 승인된 규칙 (D-062, D-063 예정. 다시 묻지 않음)

| 항목 | 값 |
| --- | --- |
| 적용 | `heritage-v1`을 켠 월드만 지급·사용. 끈 월드는 둘 다 없다 |
| 사용 상한 | 능력치당 +3, 한 장수 합계 +6 |
| 비용 | +1당 1점 |
| 지급 상한 | 한 기수(월드)에서 계정당 최대 5점 |
| 활동 지급 | 같은 계정의 직접 명령 활동이 있는 게임 달 수가 12·24·36개월에 닿을 때마다 +1(최대 3) |
| 승리 지급 | `UNIFIED` 종료에서 승자 국가 소속이면 +2 |
| 관리자 종료·초기화 | 지급 0 |
| 잔액 상한 | 없다. 6은 장수 하나에 붙는 합계 상한이지 잔액 상한이 아니다 |

이 표 밖의 자격(재위 기간, 최소 활동, 추가 비용, 은행 상한)은 만들지 않는다. 수치는 기능 판 1의 상수이고 월드 설정 칸이 아니다. 다른 수치는 `version:2`로 연다.

### L0 읽기 결과 (cc40c7a9)
- **기존 지급 원장 없음**: T4-44 계획의 `SeasonGeneral`·`AccountTitle`은 구현되지 않았다(`schema.prisma` 전체, `accountTitle` 검색 0건). 재사용할 계정 보상 표가 없으므로 최소 원장 2개를 새로 둔다. T4-44가 뒤에 들어와도 겹치는 칸이 없다.
- **종료 이유 enum**: DB `WorldEndReason { UNIFIED, END_YEAR }`(`schema.prisma:244-247`). `WorldResult`는 이 두 경우에만 `turnLoop.ts:389` 한 곳에서 생긴다. 관리자 종료(`admin/end.ts:62-151`)와 초기화(`admin/reset.ts`)는 `WorldResult`가 없을 때만 성공하고 만들지도 않는다(`end.ts:98-102`, `reset.ts:228`). 재생 쪽 `ReplayEnd.reason`은 `'UNIFIED'|'END_YEAR'`, `AdminReplayEnd`는 `'ADMIN_END'|'ADMIN_RESET'`이다(`apps/engine/src/replay.ts:68-80`).
  - 결론: 지급은 `WorldResult` 생성 트랜잭션 안에서만 일어난다. `END_YEAR`는 활동분만, `UNIFIED`는 활동분과 승리분을 준다. 관리자 경로는 지급 코드를 거치지 않으므로 0이다.
- **승자 소속**: `seasonOutcome`의 `winnerNationId`와 같은 트랜잭션의 종료 상태 `next`(`turnLoop.ts:380-403`)를 쓴다. 종료 상태에서 `userId === U`이고 `nationId === winnerNationId`인 장수가 있으면 계정 U는 승자 소속이다. 퇴장 장수는 `userId=null`(T4-95)이라 빠지고 같은 계정의 후계자가 그 자리를 대신한다. 이 상태의 해시가 `WorldResult.finalStateHash`이다.
- **입력 기록**: `InputEvent{userId, generalId, kind, status, sequence, tick, result}`(`schema.prisma:691-710`). 재생 archive의 `RecordedInput`에는 `userId`가 없다(`rules/replay.ts:37-45`). 그래서 활동 집계는 DB(또는 DO) 입력 기록에서 하고 월드 상태 해시와 재생에는 넣지 않는다.
- **활동 tick**: queued 입력은 `replayFormat=3`에서 `tick`이 있다(`inputs.ts:257`). `nationTurns.set`은 `directTick`이다(`rules/ruleFeatures.ts:216`). `turns.set`은 `tick`이 null이고 `policy`가 켜진 월드에서만 `result.activeTick = clockTick`이 있다(`server/routers/turns.ts:106-120`). → `heritage-v1`은 `requires:['policy']`이다. 활동 근거를 남기기 위한 기술 조건이며 플레이어 자격을 늘리지 않는다.
- **수동이 아닌 활동**: `general.active`는 로그인(`server/game/policy.ts:38-62`)과 각 기능 접수의 부수 기록(`campaignApi.ts:191`, `cityResourcesApi.ts:148`, `logistics/pgStore.ts:134`, `governance/pgStore.ts:154`, `lineage/pgStore.ts:121`, `personnelAdmission.ts:124`)이다. 기본 방침 실행(`policy/execute.ts`)과 기본 휴식은 턴 실행이라 `InputEvent`를 만들지 않는다. `turns.set`·`nationTurns.set`을 만드는 곳은 서버 라우터 두 곳뿐이다(`routers/turns.ts:111`, `game/nationOfficeSlots.ts:152`).
- **생성 기록**: 재생은 `InputEvent.result.general`을 그대로 넣는다(`rules/replayInputs.ts:53-98`). 5능력치 판은 payload와 결과 능력치가 같은지 본다(`replayInputs.ts:84-88`, `rules/ruleFeatures.ts:47-58`). 유산이 붙으면 이 두 비교가 `payload + bonus`가 되어야 한다.
- **기존 능력치 상한**: 생성 payload는 `statRules`의 `min`·`max`·`total`을 따른다(`general/create.ts:93-105`). 기본 3능력치 `max 80`, 5능력치 `max 90`(`resources/scenario/*.json`, `general/fiveStats.ts:31`). DB는 5능력치 판에서 0~100 CHECK가 있다(`20261030000000_five_stats`). → 유산을 더한 최종값도 `statRules.max` 이하여야 한다. `total` 검사는 payload에만 건다.
- **동시성**: 엔진 생성은 `User`를 `FOR SHARE`로 잡는다(`inputs.ts:269`). 다른 월드 엔진도 같은 사용자에 `FOR SHARE`를 동시에 잡을 수 있어 `User` 잠금만으로는 이중 사용을 막지 못한다. 탈퇴는 `User FOR UPDATE`(`server/auth/withdrawalStore.ts:24`)이며 새 계정 표를 이 트랜잭션에 넣으라는 주석이 있다(`:56-57`).
- **대기 중 재요청**: 서버는 대기 입력과 새 payload를 칸별 `===`로 비교한다(`routers/general.ts:152-159`). 중첩 객체 `heritage`를 넣으면 같은 재요청도 409가 된다. → 정규 JSON 해시(`hashState`) 비교로 바꾼다.
- **관리자 생성 목록**: `creationFeatures`(`server/admin/worldCreateOptions.ts:20-30`)에 넣지 않는다. 공개 프로필 기본값은 이 작업에서 만들지 않는다.
- **T4-95 공유 파일**: `general/create.ts`, `replayInputs.ts`, `rules/ruleFeatures.ts`(five-stats), `apps/engine/src/inputs.ts`, `routers/general.ts`, `CreateGeneralPage.tsx`는 T4-95 미커밋 초안이 이미 고쳤다(`sex`·`lineage` 인자). 이 파일들은 T4-95 병합본 위에서 고친다.

### 하지 않는 것

- 관리자 생성 목록·공개 프로필에 `heritage-v1` 기본값 추가. 진행 중 월드 전환.
- T4-44 칭호·기수 장수 순위 표.
- 끈 월드·이전 판 월드의 소급 지급.
- 범용 계정 지갑, 포인트 이전·선물, 관리자 지급 도구.

## 설계

### 규칙 기능
`heritage-v1`: `requires:['policy']`, `conflicts:[]`. `featureData['heritage-v1'] = {version:1}`(zod `strictObject`). `initial`에 유산 칸이 없고 `WorldState`에 상태 조각을 두지 않는다. 월 정산·입력 뒤 훅이 없다. 엔진 기능 목록에는 `{ key: 'heritage-v1' }` 1줄만 더한다.

상수(`rules/heritage/constants.ts`):
```
HERITAGE_V1 = { perStat: 3, perGeneral: 6, perSeason: 5,
                activityMonths: [12, 24, 36], winPoints: 2 }
```

### 생성 입력
- `general.create` payload에 `heritage?: Partial<Record<StatKey, 1|2|3>>`를 더한다. `StatKey`는 월드 판의 능력치 키(3개 또는 5개)다.
- `validateGeneralCreation(payload, statRules, lineage, heritage)`에 네 번째 인자를 더한다. 호출자 5곳(엔진 `inputs.ts:282`, 서버 `routers/general.ts:150`, `rules/ruleFeatures.ts:50`, `replayInputs.ts:85`, `e2e/rankingSeed.ts:67`)에 월드 기능을 넘긴다.
  - 끈 월드: 키가 있으면 `BAD_HERITAGE`.
  - 켠 월드: 키가 없으면 비용 0. 있으면 빈 객체 금지, 키는 월드 판 능력치만, 값은 정수 1~3, 합 1~6, 모든 키에서 `payload[key] + bonus[key] <= statRules.max`. 어기면 `BAD_HERITAGE`. 이 판정은 차감 전에 끝난다.
- 비용 = 보너스 합. 난수를 쓰지 않으며 `buildCreatedGeneral`의 소비 순서를 바꾸지 않는다. 능력치는 `payload + bonus`로 만든다.
- 생성 결과 기록: `result = { general, activeTick, heritage: {version:1, bonus, cost} }`. 보너스가 없으면 `heritage` 키가 없다. 이 `InputEvent.result`가 고정된 생성 기록이다.
- 새 오류: `BAD_HERITAGE`(「유산 배분을 확인하세요.」, HTTP `BAD_REQUEST`), `HERITAGE_INSUFFICIENT`(「유산 포인트가 부족합니다.」, HTTP `CONFLICT`).

### 재생 고정
- `applyCreationInput`: 켠 월드면 `result.heritage.bonus`가 payload `heritage`와 정규 JSON으로 같고 `cost`가 합과 같으며 모든 능력치가 `payload + bonus`인지 본다. 끈 월드에서 `result.heritage`나 payload `heritage`가 있으면 거부한다.
- five-stats `checkArchive`와 `replayInputs.ts:86`의 능력치 비교에 보너스를 더한다.
- `heritage-v1` `checkArchive`: APPLIED `general.create`마다 위 검사를 반복하고 `statRules.max`는 `origin.initial.statRules`로 본다.
- 재생·로드·엔진 상태 어디서도 `HeritageAccount`·`HeritageEntry`를 읽지 않는다. 정적 시험으로 `packages/rules/src`와 엔진 재생 경로의 참조 0을 고정한다.

### 직접 명령 활동의 근거
`rules/heritage/activity.ts`에 입력 종류를 둘로 나눈다. 등록된 모든 입력 종류(`ruleRegistry.inputKinds`)가 정확히 한쪽에 있어야 하며 새 종류가 생기면 시험이 실패해 분류를 강제한다.

| 분류 | 입력 종류 |
| --- | --- |
| 활동으로 센다 | `turns.set`, `nationTurns.set`, `personnel.appoint`, `personnel.dismiss`, `offer.respond`, `treaty.propose`, `treaty.respond`, `treaty.break`, `campaign.relationship`, `campaign.unit`, `campaign.order`, `city.resources`, `logistics.order`, `governance.act`, `lineage.act` |
| 세지 않는다 | `general.active`(로그인·부수 기록), `general.setPolicy`(자동 실행 설정), `general.create`, 관리자 시계·종료·초기화 종류 |

- 근거 행: 그 월드의 `status='APPLIED'`, 위 목록의 `kind`, `sequence <= endedSequence`인 `InputEvent`. 거부된 입력은 효과가 없으므로 세지 않는다.
- 달: `t = tick ?? result.activeTick`, 달 번호 `floor(t / TICKS_PER_MONTH)`. 목록 종류의 APPLIED 행에 `t`가 없으면 자료 손상으로 보고 예외다(정책 판 필수라 정상 경로에서는 생기지 않는다).
- 계정 단위: `(userId, 달 번호)`를 한 번만 센다. 한 계정이 전임자와 후계자로 같은 달에 여러 번 입력해도 1이다. 장수는 보지 않는다.
- 활동 점수 = `min(3, floor(달 수 / 12))`.

### 기수 지급
순수 함수 `seasonHeritageAwards({ reason, winnerNationId, generals: {userId, nationId}[], activity: {userId, kind, status, sequence, tick, result}[], endedSequence })` → `{ userId, activityMonths, activityPoints, winPoints, total }[]`(userId 오름차순, `total > 0`만).
- `reason='UNIFIED'`면 승자 소속 계정에 `winPoints=2`. `END_YEAR`는 0.
- `total = min(5, activityPoints + winPoints)`. 현재 승인 수치에서는 상한에 닿지 않지만 상한식을 그대로 둔다.
- 입력을 바꾸지 않고 같은 입력에 같은 출력을 낸다.

### 저장 (PG)
새 migration `20261114000000_heritage_ledger` 하나. 기존 migration·enum은 고치지 않는다. World 칸을 더하지 않으므로 World CHECK 목록 시험 6개는 바뀌지 않는다(L1에서 표 목록을 세는 시험이 있으면 그때만 1줄 더한다).

```prisma
model HeritageAccount {
  userId  String @id
  balance Int
  user    User   @relation(fields: [userId], references: [id], onDelete: NoAction)
}
model HeritageEntry {
  id        BigInt   @id @default(autoincrement())
  userId    String
  key       String   // credit:<worldId> | spend:<worldId>:<sequence> | forfeit | forfeit:<ticketId>(CF)
  kind      String   // SEASON_CREDIT | CREATION_SPEND | FORFEIT
  worldId   String?  // World FK 없음. 월드 삭제 뒤에도 기록을 남긴다
  delta     Int
  detail    Json
  createdAt DateTime @default(now())
  user      User     @relation(fields: [userId], references: [id], onDelete: NoAction)
  @@unique([userId, key])
  @@index([userId, id])
}
```
SQL로 더하는 것: `balance >= 0` CHECK, `kind`별 `delta` 범위 CHECK(지급 1~5, 사용 -6~-1, 몰수 < 0), `HeritageEntry` UPDATE·DELETE 금지 트리거(ERRCODE `55000`, `world_create_request_immutable` 선례). 불변식은 `balance = SUM(delta)`이다.

**지급** (`apps/engine/src/heritage/repository.ts` `creditSeason(tx, worldId, outcome, next, endedSequence)`)
- `turnLoop.ts:389` `worldResult.create` 바로 뒤에서 `heritage-v1` 월드만 부른다. 같은 트랜잭션이다.
- 근거 행을 읽어 `seasonHeritageAwards`를 부른다. 대상 계정을 userId 오름차순으로 `User FOR SHARE` 잡고 `WITHDRAWN`이면 건너뛴다.
- `HeritageEntry`를 `ON CONFLICT DO NOTHING`으로 넣고 실제로 들어간 경우에만 `HeritageAccount`를 upsert로 늘린다. `detail = {version:1, reason, activityMonths, activityPoints, winPoints, finalStateHash}`.
- `WorldResult`가 월드당 하나(PK)이고 원장 키가 유일하므로 중복 종료·재시도에도 한 번만 지급된다.

**사용** (`debitCreation(tx, userId, worldId, sequence, bonus, cost)`)
- `processGeneralCreation`(`inputs.ts:263-340`)에서 다른 거부 판정(`ACTOR_INACTIVE`, `BAD_*`, `WORLD_FULL`, `NAME_TAKEN`)이 모두 끝난 뒤, `general.create` 쓰기 직전에 부른다. 처리기 context의 `sequence`를 쓴다.
- `UPDATE "HeritageAccount" SET balance = balance - cost WHERE "userId" = $1 AND balance >= cost`. 0행이면 아무것도 쓰지 않고 `HERITAGE_INSUFFICIENT`로 거부한다. 1행이면 `spend:<worldId>:<sequence>` 항목을 넣는다.
- 잠금 순서는 `User FOR SHARE`(기존) → `HeritageAccount` 행이다. 지급·탈퇴도 같은 순서라 교착이 없다. 두 월드의 동시 생성은 계정 행 잠금에서 줄을 서고 뒤의 것은 줄어든 잔액을 본다.
- 생성이 실패해 트랜잭션이 롤백되면 차감도 없다. PG에는 반환 경로가 필요 없다. 엔진 SIGKILL 뒤 같은 `PENDING`은 한 번만 처리되고 키 유일성이 이중 차감을 한 번 더 막는다.

**탈퇴** (`server/auth/withdrawalStore.ts`)
- 같은 트랜잭션에서 `User FOR UPDATE` 뒤 계정 행을 잠그고 잔액이 있으면 `forfeit` 항목(`-balance`)을 넣고 0으로 만든다.
- 탈퇴 뒤 생성은 기존 `ACTOR_INACTIVE`로 차감 전에 거부되고 지급은 건너뛴다. 이미 만든 장수와 생성 기록은 그대로 두며 재생도 그대로다.

### 서버

### CF 조율 (CF 담당 채팅 소유, 의존 명시)
PG는 한 트랜잭션이지만 WorldDO와 D1은 그렇지 않다. CF는 아래 계약을 지킨 어댑터를 만든다. 공유 DTO는 `rules/heritage/protocol.ts`의 zod schema다. 규칙·지급 계산·검증 함수는 PG와 같은 것을 쓴다.

| 단계 | 저장소 | 동작 |
| --- | --- | --- |
| 1 예약 | D1 | 생성 요청의 멱등키를 `ticketId`로 `HeritageTicket{ticketId, userId, worldId, cost, bonus, version:1, status:'RESERVED'}`를 넣고 잔액을 같은 batch에서 조건부 차감한다. 잔액이 모자라면 표를 만들지 않고 `HERITAGE_INSUFFICIENT` |
| 2 적용 | WorldDO | `ticketId`를 입력 봉투에 실어(payload 밖) 생성을 처리한다. 결과와 같은 DO 트랜잭션에 영수증 `{ticketId, status:'APPLIED'|'REJECTED', sequence, code?}`를 쓴다. 같은 `ticketId` 재전달은 저장된 영수증을 돌려준다 |
| 3 확정 | D1 | 영수증 `APPLIED`면 `COMMITTED`와 `spend:<worldId>:<sequence>` 항목, `REJECTED`면 `RELEASED`와 잔액 복구 |
| 복구 | D1 → WorldDO | 오래된 `RESERVED` 표는 DO에 `fenceTicket(ticketId)`를 부른다. DO는 영수증이 있으면 그대로, 없으면 `VOID` 영수증을 쓰고 돌려준다. `VOID` 뒤 늦게 도착한 같은 표의 적용은 `HERITAGE_TICKET_VOID`로 거부된다. D1은 `REJECTED`·`VOID` 영수증을 받은 뒤에만 반환한다 |
| 탈퇴 | D1 | 계정 잔액을 `forfeit`로 몰수한다. 그 뒤 반환되는 표의 금액은 잔액 대신 `forfeit:<ticketId>` 항목으로 간다 |
| 지급 | WorldDO → D1 | 종료 트랜잭션에서 `seasonHeritageAwards` 결과를 DO outbox에 쓴다. Worker가 D1에 `credit:<worldId>` 키로 `INSERT OR IGNORE`하고 확인 뒤 outbox를 지운다. 재전달은 멱등이다 |

- 금지: DO 영수증 없이 시간 초과만으로 반환·취소하기. 늦은 적용이 가능한 동안 반환하지 않는다.
- 같은 고정 입력에서 PG와 CF의 생성 결과(`result.heritage` 포함)·월드 해시·원장 항목(키 모양·delta)·잔액이 같아야 한다. `ticketId`는 생성 결과와 월드 상태에 넣지 않는다.
- CF 실측 전에는 AC-P2-35 몫을 주장하지 않는다. H1~H4는 CF 없이 시작하고 끝낼 수 있다.

## 검증

### rules
- 배분: 능력치 +4, 합 +7, 월드 판에 없는 키(3능력치 판의 `politics`), 0·음수·소수, 빈 객체, `payload + bonus > statRules.max`를 `BAD_HERITAGE`로 거부. 끈 월드의 키는 거부. 키 없음은 비용 0이고 기존 결과·난수 소비와 같다.

## 위험
- 활동 집계는 종료 트랜잭션에서 그 월드의 입력 행을 모두 읽는다. 긴 월드에서 종료 저장이 느려질 수 있다. 실제 행 수와 시간은 H2에서 측정한다.
- 목록 종류의 APPLIED 행에 활동 tick이 없으면 종료 저장이 예외로 멈춘다. 손상 자료에 지급하지 않으려는 선택이며 기존 `loadReplayState`의 예외 방식과 같다.
- 승리분은 종료 순간의 소속만 본다. 종료 직전에 승자 국가로 옮긴 계정도 받는다. 승인 규칙 밖의 재위·체류 기간 조건은 두지 않았다.
- `SANCTIONED` 계정은 기존 생성 규칙대로 사용할 수 없고 지급에서는 탈퇴만 뺀다.
- 화면의 잔액은 안내값이다. 다른 월드에서 먼저 쓰면 제출이 `HERITAGE_INSUFFICIENT`로 끝난다.
- 생성 뒤 관리자 종료·초기화 때 사용 점수를 반환할지는 사용자 선택 대기다. 반환 정책에 종속되는 구현·공개 기본값은 답변 전 확정하지 않는다.
