## 계획 (Claude)

### 목표와 AC 몫

AC-P2-26 문장 전체가 이 작업의 완료 조건이다. 월드 초기화 자원 다섯 종류(지도, 시나리오, 병종, 기본 능력치 규칙, 초상 대응표)를 DB의 판으로 읽어 월드를 만든다. 내장 JSON은 초기화 SQL로 같은 키의 불변 판이 되고 저장소에서 지워진다. 이전 전 고정물의 재생 해시와 시뮬레이션 결과가 이전 뒤에도 같다. 같은 키에 다른 내용을 넣으면 실패한다.

아래 S0~S8은 이 작업 안의 실행 순서다. 새 작업 ID나 AC가 아니며 단계 하나가 PR 하나 이하 크기다. 실제 DB 이전, 동등성 대조, JSON 삭제(S8)까지 끝나고 반대쪽 리뷰를 통과해야 AC-P2-26을 바꿀 수 있다. 앞 단계만 병합한 상태를 부분 완료로 세지 않는다.

### 계약 (제안, Codex 기술 검토 대상)

#### C1 저장 모델

설계 C-M1의 열만 둔다. 초안 하나 규칙, revision, 고친 사람, 복제 원본, 시나리오 짝 지도 칸은 T4-78·T4-79가 정하며 이 작업의 migration에 넣지 않는다.

```prisma
enum GameResourceKind {
  MAP
  SCENARIO
  UNIT_SET
  STAT_RULES
  PORTRAIT_MAP
}

enum GameResourceStatus {
  DRAFT
  PUBLISHED
}

model GameResource {
  id          String             @id @default(uuid())
  kind        GameResourceKind
  name        String
  version     Int
  status      GameResourceStatus
  content     Json               // jsonb. 원본 JSON 전체
  contentHash String             // hashState(content), 소문자 16진수 64자리
  source      String             // 출처와 라이선스 한 줄
  createdBy   String?            // 내장 판은 null. 사용자 관계는 T3-05·T4-78
  createdAt   DateTime           @default(now())
  publishedAt DateTime?

  @@unique([kind, name, version])
}
```

- 열 이름을 `contentHash`로 해 기존 `resourceHash`·`initialStateHash`와 섞이지 않게 한다(C3).
- migration에 CHECK를 손으로 더한다. `version >= 1`, `name ~ '^[a-zA-Z0-9_-]+$'`(지금 로더 정규식, 길이 상한은 T4-78), `"contentHash" ~ '^[0-9a-f]{64}$'`, `(status = 'PUBLISHED') = ("publishedAt" IS NOT NULL)`. 선례는 `20261020040000_monthly_replay`의 CHECK다.
- 게시 판 불변은 DB에서도 막는다. `BEFORE UPDATE OR DELETE` 행 트리거가 `OLD.status = 'PUBLISHED'`인 행의 갱신과 삭제를 거부한다. INSERT는 막지 않는다. 초안 행의 갱신 규칙은 T4-78이 더한다. 트리거가 있어도 읽을 때 해시를 다시 대조한다(C5).
- 기존 migration은 고치지 않는다. 새 migration의 timestamp는 지금 정하지 않고 S2 병합 직전 부모가 정한 반영 순서의 최신 기준에서 `prisma migrate dev --create-only`로 만든다(H-1). 데이터는 넣지 않는다.

#### C2 키, 판, 내용 id

- 지금 키 `che`, `1030`, `basic`과 고정 경로 `default`, `rtk14-map`은 각각 `(MAP, che, 1)`, `(SCENARIO, 1030, 1)`, `(UNIT_SET, basic, 1)`, `(STAT_RULES, default, 1)`, `(PORTRAIT_MAP, rtk14-map, 1)`이다. 판 번호 없는 지금 키가 1판의 별칭이라는 것은 D-028의 지키는 것 항목에 있다.
- 이 작업의 월드 생성은 1판만 읽는다. 키 입력 문법은 지금 정규식 그대로이고 `@` 판 문법을 열지 않는다. 기존 월드의 키, 프리셋 값, E2E와 시뮬레이터 인자는 바뀌지 않는다.
- DB 읽기 함수는 문자열 키가 아니라 `{ kind, name, version }`를 받는다. 2판 이상을 읽는 길은 함수에 있지만 1판 제한을 검사하는 곳은 합성 함수 `composeInitialWorld` 하나다(C5). 읽은 묶음이 어디서 왔든 다섯 칸 중 하나라도 `version !== 1`이면 `buildInitialWorld`를 부르기 전에 실패한다. 2판으로 만든 월드의 키를 어떻게 남길지(H-8)가 정해지기 전에 2판 월드가 1판 월드와 같은 `mapKey`·`resourceHash` 입력을 갖지 않게 하려는 것이다.
- 지도·시나리오·병종 1판은 `content.id === name`이어야 한다. 다르면 그 판의 키를 적어 실패한다. 능력치 규칙과 초상 대응표는 내용에 `id`가 없어 이름만 본다. 1판 월드의 세 키는 지금처럼 내용 `id`에서 오므로 결과가 같다(`bootstrap.ts:264-266`).
- 2판 이상의 내용 `id` 규칙, 시나리오와 짝 지도 기록(T4-76 H3), 월드에 판을 남기는 방법(T4-76 H4)은 T4-78·T4-79의 미래 계약이다. 이 작업은 편집·게시·판 고르기 화면과 API를 만들지 않는다.

#### C3 세 해시의 구분

| 해시 | 입력 | 위치 | 이 작업 |
| ---- | ---- | ---- | ------- |
| `contentHash` | 원본 JSON 파일을 `JSON.parse`한 값 전체. `$comment`와 로더 밖 칸 포함 | 새 `GameResource.contentHash` | 새로 만든다 |
| `resourceHash` | `scenarioKey`·`mapKey`·`unitSetKey`·`statRules`·`unitSet` 다섯 키 | `replay.ts:64-72`, `persistence.ts:62-68` | 바꾸지 않는다 |
| 초기 상태 해시 | `WorldInit`(프리셋이면 `presetRules` 포함) | `persistence.ts:37-38`, `replay.ts:172` | 바꾸지 않는다 |

- 원본 → SQL → jsonb → 읽은 값의 같음은 두 단언으로 본다. 읽은 값이 `JSON.parse(원본)`과 깊게 같고(`toEqual`) `hashState`가 같다. `contentHash`는 기존 `hashState`를 그대로 쓴다.
- `JSON.stringify` 글자열은 같음 판정에 쓰지 않는다. jsonb는 객체 키를 자기 순서로 저장한다. 그래서 읽은 값의 키 순서가 원본과 다를 수 있고 이것은 의미 차이가 아니다. 구현 기록에는 차이가 있는지만 적는다.
- `z.record` 칸 가운데 `armTypes`와 계수 키는 정수 모양이라 JavaScript가 숫자 순으로 둔다. `portraits` 키는 한글 이름이라 순서가 바뀔 수 있지만 `Object.hasOwn` 조회만 한다(`bootstrap.ts:222`). 다른 규칙 코드가 이 순서에 기대는지는 S3가 찾아 구현 기록에 적고 S6의 시뮬레이션 대조가 최종 확인이다.
- 숫자·문자는 바꾸지 않는다. jsonb는 `1.0`의 소수 자릿수를 보존하지만 읽으면 같은 수가 된다. 값 하나라도 다르거나 jsonb가 받지 않는 문자열(`\u0000`)이 있으면 원본을 고치지 않고 S2를 멈춘다.

#### C4 초기화 SQL과 실행 명령

- 파일은 설계 C-M1a의 `packages/db/sql/resources-init.sql`이다. JSON이 있는 동안(S2~S7)은 새 `tools/resources-sql/generate.ts`(`pnpm resources:sql`)가 다섯 파일에서 만든다. 사람이 고치지 않는다. S8 뒤에는 이 파일이 내장 1판의 원본이고 새 판은 T4-78의 길로만 넣는다.
- 각 내용은 원본 파일 글자를 dollar-quote 글자열로 넣고 `::jsonb`로 바꾼다. 원본 안에 구분자가 있으면 생성기가 실패한다. `contentHash`는 생성기가 `hashState(JSON.parse(원본))`로 계산해 적는다.
- 파일 머리에 `resources/NOTICE.md`의 core2026 `df6c926` 출처와 MIT 전문, 초상 registry·한자 독음 표 출처를 그대로 옮긴다. 각 행의 `source`에는 원본 경로와 라이선스를 한 줄로 적는다. 이것은 기존 출처 기록을 옮기는 것이며 새 권리 판단이 아니다(H-9).
- 본문은 `BEGIN`·`COMMIT`·`ROLLBACK`이 없는 단일 `DO` 문 하나다. 트랜잭션은 SQL 파일이 아니라 아래 `tools/init-resources.ts`가 연다. `DO` 문은 다섯 행을 `INSERT ... ON CONFLICT (kind, name, version) DO NOTHING`으로 넣은 뒤 같은 키의 행과 `content`(jsonb 같음), `contentHash`, `status = 'PUBLISHED'`, `source`를 대조한다. 하나라도 다르면 키를 적어 `RAISE EXCEPTION`한다. `DO UPDATE`로 덮어쓰지 않는다. 오류 문구에 내용을 넣지 않는다.
- `pnpm db:init-resources`는 새 `tools/init-resources.ts`를 돈다. 원자성의 소유자는 이 도구 하나다. `DATABASE_URL`로 연결해 한 `db.$transaction(async (tx) => …)` 안에서 (1) SQL 파일의 `DO` 문을 `tx`로 실행하고 (2) 같은 `tx`로 다섯 행을 다시 읽어 행마다 `hashState(content)`가 그 행의 `contentHash`와 같고 그 값이 S0 기준 해시와 같은지 확인한다. 둘 중 하나라도 실패하면 콜백이 던져 다섯 행이 모두 롤백된다. 모두 통과해 커밋된 뒤에만 성공을 출력한다. 그래서 형식 CHECK와 SQL 안의 대조를 통과했지만 `contentHash` 리터럴이 틀린 SQL도 커밋되지 않는다. 출력은 새로 넣은 행 수, 이미 같던 행 수, 실패한 키다. 연결 문자열과 내용은 출력하지 않는다. 실패하면 종료 코드 1이다.
- 이 명령을 부르는 곳은 단계별로 늘어난다. `tools/run-integration.ts`의 migrate 다음(S4), `ci.yml` E2E DB의 `pnpm db:migrate` 다음(S5), `simulation.yml`과 `season-throughput.yml`의 준비 단계(S6)다.

#### C5 읽는 함수의 위치와 모양

의존 방향은 [패키지 경계](../architecture/package-boundaries.md)를 따른다. `packages/db`는 `shared`만 보고 rules·engine을 import하지 않는다. `packages/rules`는 DB·파일·현재 시각·비시드 난수를 쓰지 않고 이 작업에서 고치지 않는다.

```ts
// packages/db/src/gameResources.ts (새 파일, 게임 규칙 없음)
export type GameResourceKind = 'MAP' | 'SCENARIO' | 'UNIT_SET' | 'STAT_RULES' | 'PORTRAIT_MAP';
export interface GameResourceRef { kind: GameResourceKind; name: string; version: number }
export interface PublishedResource extends GameResourceRef { content: unknown; contentHash: string; source: string }
export async function readPublishedResources(
  db: Pick<PrismaClient, 'gameResource'> | Prisma.TransactionClient,
  refs: readonly GameResourceRef[],
): Promise<PublishedResource[]>; // refs 순서대로

// apps/engine/src/world/resources.ts (기존 파일에 더함)
export interface InitialResources { map: PublishedResource; scenario: PublishedResource; unitSet: PublishedResource;
  statRules: PublishedResource; portraitMap: PublishedResource }
export async function readInitialResources(db, options: { scenario: string; map: string; unitSet?: string }): Promise<InitialResources>;
export function composeInitialWorld(resources: InitialResources, seed: string): WorldInit; // 다섯 칸 gate 뒤 buildInitialWorld
export async function loadInitialWorldFromDb(db, options: { scenario: string; map: string; seed: string; unitSet?: string }): Promise<WorldInit>;
```

- `readPublishedResources`는 이름 정규식과 판 번호(양의 정수)를 조회 전에 검사한다. `status = PUBLISHED` 행만 한 번에 읽는다. 없는 판이 있으면 모두 모아 한 오류로 던지고 `pnpm db:init-resources`를 안내한다. 읽은 행마다 `hashState(content)`를 다시 계산해 다르면 키를 적어 던진다. 파일로 돌아가는 길, 빈 값으로 넘어가는 길은 없다.
- `readInitialResources`는 다섯 판을 모두 `version: 1` 참조로 읽기만 한다. 1판 제한의 gate는 `composeInitialWorld`가 가진다. 이 함수는 먼저 다섯 칸마다 `kind`가 칸과 맞는지(`map`은 `MAP` 등), `version === 1`인지, C2의 내용 `id`·`name` 조건을 확인하고 하나라도 어기면 그 칸의 키를 적어 던진다. 모두 통과한 뒤에만 지금 `loadInitialWorld`의 `buildInitialWorld` 호출과 같은 인자를 넘긴다(`resources.ts:27`). `InitialResources`에 판을 고르는 입력이나 새 칸을 열지 않고 `buildInitialWorld`의 인자도 바꾸지 않는다. 합성이 던지면 그 판의 키를 붙여 다시 던진다. `loadInitialWorldFromDb`는 두 함수를 차례로 부를 뿐이다.
- 파일 로더 `loadInitialWorld`는 S8까지 남는다. 두 함수는 서로를 부르지 않으며 호출하는 쪽이 하나를 고른다.
- `packages/db/src/index.ts`에 export 한 줄이 필요하다. 이 파일은 다른 작업이 export를 더하는 중인 공유 파일이라 S3는 부모 조율 뒤에 고친다(H-2). 하위 경로 export로 바꾸는 안도 조율에서 고를 수 있다.
- 로비는 `readPublishedResources`로 `(SCENARIO, <키>, 1)`을 읽어 지금 `titleSchema`로 제목을 꺼낸다. 성공만 캐시하고 실패는 지금처럼 `INTERNAL_SERVER_ERROR`이며 키·경로를 노출하지 않는다.

#### C7 시험 이전 원칙

- 규칙 단위 시험에 DB를 끌어들이지 않는다. 전체 지도·시나리오가 필요한 시험은 DB를 쓰는 통합 시험으로 옮긴다. 일부만 쓰는 시험은 작은 고정물로 돈다.
- 작은 고정물은 지금 함수가 만든 `WorldInit` 결과를 그대로 저장하거나, S0에서 정한 사영을 그대로 저장한 것이다. 저장 전후 `hashState`가 그 고정물의 입력에 해당하는 S0 기준값과 같아야 한다. `monthly-initial.json`·`war-initial.json`은 `monthlyFixture()`·`warFixture()` 전체 결과와 같은 해시다. `visibility-initial.json`은 사영이라 `readFixture()` 전체 해시 `readFixtureFull`과 같지 않으며 S0의 사영 해시 `visibilitySubset`과 대조한다(S0, S1). 고정물은 `{ "$comment": "<core2026 출처와 MIT>", "initial": <WorldInit> }` 꼴이고 함수는 매번 깊은 사본을 돌려준다. 다섯 자원 파일을 다른 경로에 통째로 다시 만들지 않는다. `WorldInit.unitSet` 안의 병종 내용은 기존 `replay-v1-b8f5074.json`의 `origin.initial`처럼 고정물에 남는다.

#### C9 T4-76 자원 검증기의 쓰임

T4-76의 공개 경로 `@opensamguk/rules/resource-validation`(`packages/rules/package.json:7` → `packages/rules/src/world/validate/index.ts`)을 그대로 쓴다. 이 경로와 rules root index는 고치지 않는다. `validateWorldResources({ map, scenario, unitSet, statRules, portraitMap })`(`validate/world.ts:8-29`)는 다섯 보고와 합친 `status`를 돌려준다. 지도는 `{ scenarios: [] }` 맥락으로, 시나리오는 `{ map }` 맥락으로 검사하므로 지도·시나리오 참조 대조는 이 함수 몫이다. 합친 `status`는 `fail`이 하나라도 있으면 `fail`, 아니면 `incomplete`가 하나라도 있으면 `incomplete`, 아니면 `pass`다(`issues.ts:79`, `:136`). 이 작업은 `pass`만 통과로 세고 `incomplete`를 `pass`로 세지 않는다. 실제 `1030`은 `scenario-diplomacy-duplicate` 경고 하나가 있어도 `pass`다(`tools/resource-validate.test.ts:26-31`). 보고의 `value`(`issues.ts:84`)와 `normalizeMapToV2` 결과는 파싱·정규화한 값이다. SQL의 `content`와 `contentHash`의 입력은 C3대로 원본 JSON 전체이며 `value`나 정규화 결과를 SQL에 넣지 않는다. 부르는 곳은 셋이다. S2 `tools/resources-sql/generate.ts`는 SQL을 쓰기 전에 다섯 원본 값으로 부르고 `pass`가 아니면 실패한다. S3 `tools/resource-catalog.integration.test.ts`는 DB에서 읽은 다섯 `content`로 부른 보고가 원본으로 부른 보고와 깊게 같은지 본다. S4는 기존 실제 자원 검사 두 개(`tools/resource-validate.test.ts:25-72`)를 DB의 다섯 값으로 같은 기대 그대로 돈다. 런타임 경로(`readPublishedResources`, `composeInitialWorld`, 월드 생성 CLI, 로비)는 이 검증기를 자동으로 부르지 않는다. 경로마다 이미 정한 검사만 거친다. 월드 합성 경로(`composeInitialWorld`, 월드 생성 CLI)는 기존 `buildInitialWorld`의 zod 파싱과 거부 검사(`bootstrap.ts:102-115`)를 거친다. 로비는 C5의 기존 `titleSchema`를 거친다. DB 읽기 함수는 C5의 행 메타데이터(이름 정규식, 판 번호, `PUBLISHED`) 검사와 `hashState` 대조를 거친다. 이 절에서 런타임에 새 검증기 호출을 더하지 않는다. 기존 합성 규칙이 받는 값의 범위는 바뀌지 않는다.

#### 계약

##### 1. 저장 모델과 migration

```prisma
enum GameResourceKind {
  MAP
  SCENARIO
  UNIT_SET
  STAT_RULES
  PORTRAIT_MAP
}

enum GameResourceStatus {
  DRAFT
  PUBLISHED
}

model GameResource {
  id          String             @id @default(uuid())
  kind        GameResourceKind
  name        String
  version     Int
  status      GameResourceStatus
  content     Json               // PostgreSQL jsonb
  hash        String             // hashState(content), 64자리 소문자 16진수. 초안에도 있다
  source      String             // 출처와 라이선스 한 줄
  mapKey      String?            // 시나리오만. 함께 쓸 지도 판의 정규 키
  revision    Int                @default(0)
  createdBy   String?            // 사용자 UUID. 내장 판은 null
  updatedBy   String?
  publishedBy String?
  createdAt   DateTime           @default(now())
  updatedAt   DateTime?
  publishedAt DateTime?

  @@unique([kind, name, version])
}
```

- 조율 결정 R1·R2·R3을 따른다. API와 감사는 `id`로, 화면 주소는 `kind`·`name`·`version`으로 행을 가리킨다. 종류마다 이름 공간이 따로라 지도 `che`와 시나리오 `che`가 함께 있어도 된다.
- 사람 열 셋은 사용자 UUID 문자열이다. `User` 관계와 삭제 규칙은 T3-05 계약이 main에 없어 정하지 않는다(R19 가정). 관계가 필요하면 T4-78 migration이 더한다.
- migration에 CHECK 넷을 손으로 더한다. `version >= 1`, `name ~ '^[a-zA-Z0-9_-]{1,40}$'`(R5, T4-78 이름 규칙), `(status = 'PUBLISHED') = (publishedAt IS NOT NULL)`, `kind = 'SCENARIO' OR mapKey IS NULL`. 선례는 `20261020040000_monthly_replay`의 `InputEvent_completion`이다.
- 게시 판 불변 트리거도 이 migration에 둔다(R3). PL/pgSQL 함수 하나와 `BEFORE UPDATE OR DELETE` 트리거 하나다. `status = 'PUBLISHED'`인 행의 `UPDATE`와 `DELETE`를 거부한다. 초안 행의 `UPDATE`는 `id`·`kind`·`name`·`version`이 그대로일 때만 받는다. 초안을 저장하거나 `PUBLISHED`로 바꾸는 갱신이 여기 든다. 초안 행의 `DELETE`는 받는다(T4-78 `discard`). `INSERT`는 막지 않으므로 초기화 SQL과 부딪히지 않는다.
- 트리거가 있어도 읽을 때 해시를 다시 대조한다(계약 5). 트리거 없이 넣은 잘못된 행이나 트리거를 끄고 고친 행을 잡기 위해서다.
- migration은 병합 직전 최신 main에서 `prisma migrate dev --create-only`로 새로 만든다. 표, enum, 유일 제약, CHECK, 트리거만 있고 데이터는 넣지 않는다. 기존 migration은 고치지 않는다. 초안 하나 규칙의 부분 유일 색인은 T4-78이 더한다.

##### 2. 키와 별칭

- 입력 키는 `<이름>` 또는 `<이름>@<판 번호>`다. 정규식은 `^[a-zA-Z0-9_-]{1,40}(@[1-9][0-9]{0,8})?$`이고 판 번호는 1~999999999다. 지금 경로 이동 거부(`resources.ts:6-9`)는 이 검사로 이어진다.
- 판 번호가 없는 키는 영구히 1판이다. 최신 판이 아니다. 그래서 `che`, `1030`, `basic`으로 만든 기존 월드의 키, 프리셋 파일의 `map`·`scenario`·`unitSet` 값, E2E와 시뮬레이터 인자를 바꾸지 않는다.
- 정규 키는 1판이면 이름만(`che`), 2판부터 `<이름>@<판 번호>`(`che@2`)다(R4). 입력 `che`와 `che@1`은 같은 판이고 정규 키는 `che`다. `mapKey` 열과 월드의 키 칸에는 정규 키를 쓴다.
- 내장 1판의 이름은 지도 `che`, 시나리오 `1030`, 병종 `basic`, 능력치 규칙 `default`, 초상 대응표 `rtk14-map`이다. 앞 셋은 내용의 `id`와 같다. 뒤 둘은 내용에 `id`가 없어 파일 이름을 쓴다.
- 지도·시나리오·병종 판의 내용 `id`는 카탈로그 이름과 같다. 복제할 때 서버가 내용 `id`를 새 이름으로 바꾸므로(R7) 이 관계는 2판 이후에도 유지된다.
- 로더는 합성한 `WorldInit`의 `scenarioKey`·`mapKey`·`unitSetKey`를 읽은 판의 정규 키로 둔다. 1판은 정규 키가 내용 `id`와 같으므로 지금 결과와 같다. 2판으로 만든 월드에는 `che@2`가 들어간다. 판 고르기 입력은 T4-79가 정한다.

##### 3. 내용과 정규 해시

- `content`는 JSON 파일을 `JSON.parse`한 값 전체다. `$comment`와 로더가 쓰지 않는 칸도 남긴다.
- `hash`는 `hashState(content)`다(`packages/shared/src/node/hashState.ts`). jsonb는 키 순서를 바꾸지만 이 해시는 키를 정렬하므로 바뀌지 않는다. 숫자도 `JSON.parse`를 거치면 `1.0`과 `1`이 같다.
- 합성 결과의 같음은 `hashState`와 `toEqual`로 본다. `JSON.stringify` 글자열은 비교하지 않는다. `z.record` 칸(`portraits`, `armTypes`, 계수)의 키 순서가 jsonb를 거치며 바뀔 수 있어서다. 지금 규칙 코드에서 이 순서에 기대는 곳이 있는지 Codex가 구현 때 찾아 구현 기록에 적는다.

##### 4. 초기화 SQL과 실행 명령

- `packages/db/sql/resources-init.sql`은 `pnpm resources:sql`(새 변환기, PR 1 동안만 JSON 입력)로 만든다. 사람이 고치지 않는다.
- 파일 머리에 core2026 `df6c926` 출처와 MIT 전문, 초상 대응표의 registry·독음 표 출처를 `resources/NOTICE.md`에서 그대로 옮긴다. 각 행의 `source`에도 한 줄로 적는다.
- 본문은 PL/pgSQL `DO` 블록 한 문장이다. 실행 도구가 여러 문장을 받지 못해도 한 번에 돌고 원자적이다. 블록 안에서 들어갈 다섯 행을 임시 표에 한 번만 적는다. 그 뒤 `INSERT ... SELECT ... ON CONFLICT (kind, name, version) DO NOTHING`으로 넣고 같은 키의 행과 `content`(jsonb 같음)·`hash`·`status = 'PUBLISHED'`·`source`·`mapKey`를 대조한다. 하나라도 다르면 키를 적은 문구로 `RAISE EXCEPTION`한다.
- 시나리오 `1030` 행의 `mapKey`는 `che`다(R6). 나머지 네 행은 `null`이다.
- `id`는 SQL이 `gen_random_uuid()`(PostgreSQL 13부터 내장)로 직접 넣는다. 모델의 `@default(uuid())`는 Prisma 클라이언트가 값을 만들 뿐 DB 기본값을 만들지 않기 때문이다. 같은 선언의 `World.id`도 migration에 기본값이 없다(`packages/db/prisma/migrations/20261020000000_initial_world/migration.sql:12`). migration에 `id` 기본값은 두지 않는다. T4-78 저장소처럼 Prisma 클라이언트로 넣는 길은 클라이언트가 UUID를 만들고 원시 SQL로 넣는 길은 모두 `gen_random_uuid()`를 적는다. `publishedAt`은 처음 넣을 때의 `now()`, `revision`은 0, 사람 열 셋은 `null`이다. 이 다섯은 대조에 넣지 않는다.
- `pnpm db:init-resources`는 새 `tools/init-resources.ts`를 돈다. `DATABASE_URL`(통합 시험에서는 `run-integration.ts`가 넣는 값)에 SQL 파일을 실행한 뒤 다섯 행을 다시 읽어 `hashState(content) === hash`를 확인한다. 출력은 새로 넣은 행 수와 이미 같던 행 수, 실패면 키다. 내용과 연결 문자열은 출력하지 않는다. 이 명령은 내장 1판 SQL만 돈다. 이후 판은 T4-78 저장소 함수만 넣는다(R15).
- 이 명령을 부르는 곳은 `tools/run-integration.ts`의 migrate 다음 줄, `ci.yml`의 `pnpm db:migrate` 다음 단계, `simulation.yml`과 `season-throughput.yml`의 새 준비 단계다. 로컬은 `pnpm db:migrate` 다음에 사람이 부르고 `docs/architecture/runtime.md` §3 순서에 적는다. `pnpm db:up`은 지금도 migrate하지 않으므로 고치지 않는다(Z-7).

##### 5. 읽는 함수

```ts
// apps/engine/src/world/resources.ts
type ResourceDb = Pick<PrismaClient, 'gameResource'> | Prisma.TransactionClient;
export type ResourceKind = 'MAP' | 'SCENARIO' | 'UNIT_SET' | 'STAT_RULES' | 'PORTRAIT_MAP';
export type ResourceRow = {
  id: string;
  kind: ResourceKind;
  name: string;
  version: number;
  key: string; // 정규 키 (R4)
  hash: string;
  mapKey: string | null;
  content: unknown;
};

export function parseResourceKey(key: string): { name: string; version: number };
export async function readResources(
  db: ResourceDb,
  wanted: { kind: ResourceKind; key: string }[],

export async function readInitialResources(
  db: ResourceDb,
  options: { scenario: string; map: string; unitSet?: string; statRules?: string; portraitMap?: string },

export async function loadInitialWorld(
  db: ResourceDb,
  options: { scenario: string; map: string; seed: string; unitSet?: string; statRules?: string; portraitMap?: string },

```

- 기본값은 `unitSet = 'basic'`, `statRules = 'default'`, `portraitMap = 'rtk14-map'`이다. 지금 고정 경로와 같은 1판이다.
- `readResources`는 키를 모두 검사한 뒤 `findMany` 한 번으로 `status = PUBLISHED` 행만 읽는다. 초안은 읽지 않는다.
- 없는 판이 하나라도 있으면 모두 모아 한 오류로 던진다. 문구는 `초기화 자원이 없습니다: 지도 che@1, 시나리오 1030@1. pnpm db:init-resources를 먼저 실행하세요.` 꼴이다. 빈 지도로 넘어가지 않는다.
- 읽은 행마다 `hashState(content)`를 다시 계산해 `hash`와 다르면 그 키를 적어 던진다.
- `loadInitialWorld`는 `readInitialResources` 뒤 `buildInitialWorld`를 부르고 세 키를 정규 키로 둔다(계약 2). 지도·시나리오·병종 판의 내용 `id`가 이름과 다르면 던진다(R7). 규칙 패키지는 지금처럼 DB를 모른다 (AGENTS §6).
- 시나리오 행의 `mapKey`와 고른 지도 판이 다를 때 막을지는 T4-79가 정한다. 이 작업은 `1030`과 `che`만 쓰므로 두 값이 같다.
- 시드마다 같은 자원을 쓰는 곳(시뮬레이터)은 `readInitialResources`를 한 번 부르고 `buildInitialWorld`를 시드마다 부른다.
- `resourceRoot`와 `readFile`은 프리셋만 남는다(U-77-3 기본안). 프리셋도 옮기기로 하면 같은 길에 종류를 더한다.

##### 7. 시뮬레이터와 CI

- `pnpm sim`은 `DATABASE_URL`에서 자원을 한 번 읽는다. 쓰기는 하지 않는다. 처음 출력하는 환경 줄(`tools/sim/cli.ts:28-39`)에 다섯 자원의 키와 해시를 더한다. 어느 판으로 돌렸는지 결과 파일에 남기기 위해서다.
- `simulation.yml`에 `season-throughput.yml:15-30`과 같은 PostgreSQL 서비스와 `DATABASE_URL`을 둔다. 시뮬레이션 앞에는 `pnpm generate`·`pnpm db:migrate`·`pnpm db:init-resources`를 차례로 더한다. 결과 검사 스크립트는 그대로다.
- `seconds`는 `simulateGame` 루프만 재므로(`simulation.ts:27`, `:83`) DB 읽기 시간은 들어가지 않는다. 그래도 개발 PC에서 `pnpm sim`을 돌리려면 DB가 떠 있어야 한다. AC-M1-18 측정을 어떻게 다룰지는 U-77-2다.

##### 8. 시험 이전

설계 C-M1b의 원칙을 따른다. 전체 지도·시나리오가 필요한 시험은 DB를 쓰는 통합 시험으로 옮겨 `pnpm check`에서 빠지고 `pnpm test:int`에 들어간다. 일부만 잘라 쓰는 시험은 작은 고정물로 돈다.

- 작은 고정물: PR 1에서 JSON이 아직 있을 때 `monthlyFixture()`와 `warFixture()`의 지금 결과를 `apps/engine/test/fixtures/monthly-initial.json`, `war-initial.json`으로 한 번 저장한다. 머리 `$comment`에 core2026 출처와 MIT를 적는다. 두 함수는 이 파일을 읽어 사본을 돌려준다. 저장 전후의 `hashState`가 같음을 구현 기록에 적는다.
- 작은 고정물에는 도시 10개, 장수 10명 이하만 둔다. 전체 지도나 전체 시나리오를 시험 고정물로 다시 만들지 않는다.

##### 9. 초상 대응표 생성기

`pnpm portraits:map`은 DB의 `SCENARIO 1030` 1판을 읽어 지금과 같은 대응을 계산한다. 결과를 파일로 쓰지 않고 DB의 `PORTRAIT_MAP rtk14-map` 1판 내용과 비교해 같은지 출력한다. 다르면 종료 코드 1이다. 80% 미만 실패와 출력 문구는 지금과 같다.

초안 행을 SQL로 직접 넣지 않는다(R15). 내장 1판은 초기화 SQL이 게시 판으로 넣는다. 그 뒤 판은 T4-78 저장소 함수(`apps/server/src/admin/resourceStore.ts`)를 거쳐 감사 로그를 남긴다. 생성기 결과를 새 판으로 올리는 길은 T4-78·T4-87이 그 함수 위에 만든다. 이 작업은 비교까지만 한다.

##### 10. JSON 삭제 (PR 2)

- 다섯 파일과 변환기의 JSON 입력부, PR 1의 JSON 대조 시험을 지운다. `resources-init.sql`과 다섯 행 해시 상수 시험은 남는다.

- `tools/map-terrain/`(T4-82의 `che.v2.json`)은 편집기로 가져올 도구 입력이고 런타임이 읽지 않으므로 검사 대상이 아니다(R9). 다만 위 문자열 검사에 걸리지 않도록 그 파일과 시험은 `resources/map/` 경로를 적지 않는다.

1. PR 1 시작 전에 기준값을 잰다. 파일 로더로 1030·che·`basic`의 `hashState(initial)`(시드 `t2-02-legacy-baseline`, 지금 골든 `2952fcf8…`)와 `resourceHash`(시드 `1`), 다섯 파일의 `hashState`, 작은 시뮬레이션(시드 `1`, `maxYear` = 시작 연도 + 2)의 `stateHash`, `monthlyFixture()`·`warFixture()`의 해시를 구현 기록에 적는다.

5. 초상 생성기를 바꾸고 문서를 채운다. PR 1을 리뷰에 올린다.
6. T4-86과 지도 편집기 시험 입력 교체가 main에 들어오면 PR 2로 JSON을 지우고 정적 검사를 더한다.
