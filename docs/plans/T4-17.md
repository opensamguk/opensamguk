### 1. 목표

T4-05가 만든 계략 4종(`fire_attack` 화계, `sabotage` 파괴, `incite` 선동, `plunder` 탈취)을 운영 확장 목록 `extensionCommands`와 결합 목록 `extCommandBindings`에 올린다. 등록 뒤에도 아래가 성립해야 한다.

- 대조 도구가 함수 본문을 실행하지 않고 운영 목록 네 개를 읽는다. 그 결과는 Node와 설치된 zod로 실제 import한 목록과 순서까지 같다.
- 끈 월드(`enabled = null`)는 기본 37개의 결과·RNG 소비·상태 해시가 지금과 같다.
- 켠 월드의 네 명령 결과는 T4-05 단위 골든과 같고 `ext` 키가 생기지 않는다.
- 엔진·서버·DB·재생 기록 형식·제품 프리셋은 바뀌지 않는다.

이 목표는 AC-P2-03 (나) 가운데 등록 몫이다. 엔진 통합 증거와 AC 완료는 여기서 나오지 않는다(§10).

### 4. 분석기와 실제 정의의 충돌, 기술 계약

#### 4.1 문제

PR #182의 `readExtensionRegistryKeys`는 `ext/registry.ts`에서 출발해 const와 상대 import만 따라가며 등록 목록을 읽는다. 함수 본문은 모듈 초기화 때 실행되지 않는다는 전제로 보지 않는다. 그 전제를 지키려고 초기화 중에 호출되는 함수는 고정 신뢰 두 가지만 받는다. `support.ts`의 `defineCommand`(`:184`)와 고정 의존성 zod의 정해진 생성 API(`:80~90`)다.

현재 T4-05 정의를 그대로 등록하면 세 겹으로 거부된다.

1. `export function makeStratagem`은 함수 선언이라 `bindings`에만 들어가고 `exports`에는 없다(`:164`). 그래서 다른 파일에서 import하면 `선언 makeStratagem을 찾지 못했다`가 난다.
2. 찾더라도 const 초기값이 아니므로 값으로 읽지 못한다.
3. 호출 자체가 `defineCommand`도 zod도 아니라서 `pureInitializer`(`:273~324`)와 `value`(`:344~376`)가 모두 받지 않는다.

이 거부는 도구 결함이 아니라 계약대로의 동작이다. `makeStratagem`의 본문은 모듈 초기화 중 실제로 실행되므로 그 안에서 목록을 바꾸면 숨은 등록이 된다. F1 리뷰 두 건도 이 거부를 바꾸지 않았다.

#### 4.2 선택지

| 안 | 내용 | 판단 |
| -- | ---- | ---- |
| A 정의 구조 변경 | 네 정의를 `key`·`target` 문자열 리터럴이 직접 든 객체 리터럴로 쓴다. 공통 동작은 `base.ts`의 내보낸 함수로 옮기고 정의의 `execute`는 그 함수를 부르는 화살표 함수로 둔다. 초기화 때 사용자 함수를 호출하지 않는다 | 권고. 분석기·허용 목록을 고치지 않고 지금 분석기가 받는다. 효과와 RNG는 본문을 옮기기만 하므로 같다 |
| B 좁은 분석 계약 | `ext/stratagem/base.ts`의 `makeStratagem`을 `defineCommand`처럼 이름으로 신뢰하고 인자 객체에서 `key`를 읽으며 대상은 `general`로 고정한다 | 거절. 신뢰 대상인 `defineCommand`는 공통 파일 한 곳이지만 `makeStratagem`은 기능 파일이고 본문이 초기화 때 실행된다. 본문이 바뀌어도 도구가 모른다. 막으려면 본문 분석이나 해시 고정이 필요하고 이는 신뢰 면을 넓힌다. 이후 기능마다 같은 예외가 늘어난다 |
| C `defineCommand`로 바꾸기 | 공통 factory를 쓴다 | 거절. `defineCommand`는 상태를 복제해 `{ kind: 'world' }` 효과를 낸다(`support.ts:50~56`). T4-05 계획 §4.2·§4.8과 D-027이 받아들인 필드 효과 계약이 바뀐다 |

#### 4.3 권고 계약 (A)

`base.ts`:

| 지금 | 바꾼 뒤 |
| ---- | ------- |
| `type Spec = { key; name; stat; fields?; labels? }` | `export type StratagemSpec`. 칸은 그대로다 |
| `const argsSchema = z.strictObject({ cityKey: positive })` | `export const stratagemArgs = z.strictObject({ cityKey: positive })`. 스키마 그대로다 |
| `function check(view, actor, raw)` | `export function checkStratagem(view, actor, raw)`. 매개변수와 반환형은 그대로다. 본문은 아래 치환 1만 받는다 |
| `export function makeStratagem(spec): CommandDef`와 안쪽 `execute` | 없앤다. 안쪽 `execute` 본문을 `export function executeStratagem(spec: StratagemSpec, view: WorldView, actor: Actor, raw: unknown, rng: Rng): CommandResult`로 옮긴다. 본문은 아래 치환 1·2만 받는다. `Rng`는 `import type`으로 가져온다 |

옮길 때 허용되는 변경은 아래 기계적인 것뿐이다.

1. 식별자 `argsSchema` → `stratagemArgs`. `check` 본문의 `safeParse`(`base.ts:92`)와 `execute` 본문의 `parse`(`:118`) 두 곳이다.
2. 식별자 `check` → `checkStratagem`. `execute` 본문의 첫 검사 호출(`:116`) 한 곳이다. 정의의 `check`·`precheck` 칸 값은 명령 파일로 옮겨 간다(아래 꼴).
3. 타입 이름 `Spec` → `StratagemSpec`. 칸은 그대로다.
4. 메서드 `execute(view, actor, raw, rng) { … }`가 최상위 함수 `executeStratagem`이 된다. 본문의 `spec`은 클로저 변수에서 첫 매개변수로 바뀌고 이름은 그대로다. 나머지 네 매개변수는 지금 `CommandDef['execute']`(`types.ts:59`)에서 추론되던 형을 그대로 적는다.
5. 위로 인한 들여쓰기·줄바꿈. Prettier 결과를 따른다.

그 밖은 그대로다. 계산식·상수·비교 연산, 분기와 조건 순서, 효과 목록의 원소와 순서, 로그·보고·국가 기록의 칸과 문구, `throw` 문구, `rng.next()`·`rng.int()`의 호출 횟수·인자·순서, 본문 주석이 모두 해당한다. 리뷰는 기준 SHA(§8 2단계)와 커밋 1 사이의 공백 무시 diff에서 위 다섯 종류 말고 다른 차이가 없음을 본다. 실행 결과의 동등성은 §9.1 S8이 따로 본다.

`STRATAGEM`, `effectiveStat`, `stratagemDistance`, `stratagemDefenders`, `stratagemProbability`, `plunderYearCoefficient`와 머리 출처 주석은 그대로다.

명령 파일 네 개는 아래 꼴이다. 화계를 예로 든다. 머리의 원작 출처 두 줄은 지금 파일 그대로 둔다.

```ts
import type { CommandDef } from '../../types';
import { checkStratagem, executeStratagem, stratagemArgs, type StratagemSpec } from './base';

export const fireAttackSpec: StratagemSpec = {
  key: 'fire_attack',
  name: '화계',
  stat: 'intel',
  fields: ['agriculture', 'commerce'],
  labels: ['농업', '상업'],
};

export const fire_attack: CommandDef = {
  key: 'fire_attack',
  name: '화계',
  category: 'strategy',
  target: 'general',
  args: stratagemArgs,
  check: checkStratagem,
  precheck: checkStratagem,
  execute: (view, actor, raw, rng) => executeStratagem(fireAttackSpec, view, actor, raw, rng),
};
```

`sabotage`·`incite`·`plunder`는 지금 `makeStratagem` 인자와 같은 값으로 `sabotageSpec`·`inciteSpec`·`plunderSpec`을 두고 같은 꼴로 정의한다. `plunderSpec`에는 지금처럼 `fields`·`labels`가 없다. `index.ts`의 `stratagemCommands = [fire_attack, sabotage, incite, plunder] as const`는 그대로다.

운영 목록 두 곳은 아래처럼 고친다.

```ts
// ext/registry.ts
import type { CommandDef } from '../types';
import { stratagemCommands } from './stratagem';

export const extensionCommands: readonly CommandDef[] = [...stratagemCommands];
```

```ts
// ext/state.ts 의 결합 목록만
export const extCommandBindings: ExtStateRegistry['bindings'] = [
  { commandKey: 'fire_attack', target: 'general', sliceKeys: [] },
  { commandKey: 'sabotage', target: 'general', sliceKeys: [] },
  { commandKey: 'incite', target: 'general', sliceKeys: [] },
  { commandKey: 'plunder', target: 'general', sliceKeys: [] },
];
```

`ext/state.ts`는 명령 정의를 import하지 않는다. 순환(T4-02 2.4.1)을 피하려고 결합 행은 문자열로 쓰고 `ext/registry.test.ts`의 `verifyCatalog`가 정의 목록과 대조한다. import 경로는 `resolve.ts → ext/registry.ts → stratagem → base.ts → support.ts → model/clone.ts → ext/state.ts`이며 `ext/state.ts`가 위로 되돌아가지 않으므로 순환이 없다.

#### 4.4 정의 파일의 허용·거부 경계

계략 정의 파일과 이후 같은 꼴을 쓰는 등록 줄은 아래를 지킨다. 받는 쪽은 PR #182 분석기가 지금 받는 구문이고 거부 쪽은 지금 거부하는 구문이다. 분석기를 고치지 않고 이 경계를 시험으로 고정한다(§9.2).

| 받음 | 거부 (CLI exit 1) |
| ---- | ----------------- |
| 정의 객체 리터럴 안의 `key`·`target` 문자열 리터럴. `target`은 생략하지 않는다(factory가 아니면 기본값이 없다) | `key: fireAttackSpec.key` 같은 속성 접근, 계산된 `target` |
| 다른 칸의 문자열 리터럴, const·함수 선언을 가리키는 식별자, 화살표 함수와 메서드 | 정의 객체의 spread·계산 속성 |
| 문자열·배열 리터럴로만 된 `*Spec` const | 초기화 때 helper를 호출해 만든 spec이나 정의(`make('fire_attack')`, `makeStratagem({...})`, 임의 factory) |
| `stratagemArgs`처럼 허용 목록 안 zod 호출(`strictObject`, 지원 `positive`)로만 만든 const | `.default`·`.regex` 같은 허용 목록 밖 zod API, 음수 인자 |
| 정의 식별자의 배열과 배열 spread, `as const` | `let`, 최상위 실행문, 목록에 끼운 함수 호출 결과 |

`execute`·`check`의 본문은 명령 실행 때만 돈다. 모듈 초기화 때 사용자 함수를 호출하지 않는다는 점이 이 경계의 근거다.

#### 4.5 바뀌지 않는 것

- 공개 API: `packages/rules/src/index.ts`는 고치지 않는다. `stratagemCommands`와 네 정의의 이름, `CommandDef` 모양(`key`, `name`, `category`, `target`, `args`, `check`, `precheck`, `execute`)은 그대로다. `base.ts`에서 `makeStratagem`이 빠지고 네 이름이 새로 내보내진다. 저장소 안에서 `makeStratagem`을 쓰는 곳은 네 명령 파일뿐이다.
- 게임 효과와 RNG: `executeStratagem` 본문은 §4.3의 기계적 변경 말고는 지금 `execute` 본문과 같다. `precheck`와 `check`가 같은 함수인 것도 같다. 효과 목록 순서, 로그·보고·국가 기록 문구, 확률 판정의 `rng.next()` 한 번, 부상·피해·성장 난수 순서가 그대로다. 증거는 기존 T4-05 시험이 고친 것 없이 통과하는 것(S0)과, 코드 변경 전 고정한 기준 기록과의 전체 결과·RNG 대조(S8) 두 가지다. 기존 시험 통과 수만으로 동등성을 주장하지 않는다.
- 고정 의존성 신뢰: 분석기가 신뢰하는 것은 지금처럼 `defineCommand`와 zod의 정해진 생성 API뿐이다. support 하위 런타임 모듈 검사, type-only import·export 건너뛰기도 PR #182 그대로다.
- 대조표 집계: 기본 37개(장수 27·국가 10), 원본 90개, 분모 91개, 미해결 원본 3개가 그대로다. 확장 key 넷은 이미 대응표에 장수 명령 행으로 있으므로 도구가 새 행을 요구하지 않는다.

##### 9.1.1 S8 기준 기록 계약

기준 SHA의 구현을 시험마다 Git에서 꺼내 돌리지 않는다. 대신 변경 전 구현의 실행 결과를 코드 변경 전에 한 번 JSON으로 고정하고 그 파일이 어디서 나왔는지를 Git 이력으로 남긴다.

- 기준: §8 2단계의 `B`. 커밋 0은 `B`의 바로 위 자식이고 새 파일 두 개(`equivalence.test.ts`, `__fixtures__/equivalence.baseline.json`)만 더한다. 기준 기록 머리에 `baseSha: B`와 사례 수 12를 적는다.
- 입력: 새 제품 값이나 게임 정책을 만들지 않는다. `stratagem.test.ts`에 이미 있는 입력만 쓴다. 월드는 그 파일의 `world()`와 같은 수정(`commandWorld()`에서 다른 장수를 도시 3으로 옮기고 도시 2 값을 정함), 주체 `{ generalId: 1, tick: 0 }`, 인자 `{ cityKey: 2 }`, resolver는 `createCommandResolverWithCommands({ general: 네 key, nation: [] }, stratagemCommands)`다. 시험 파일 안에 이 입력을 다시 적는다.
- 사례: 네 명령 × 세 경우다. 성공은 시드 `stratagem-success`, 확률 실패는 시드 `seed-1`(기존 골든과 같은 시드), 검사 실패는 `gold = 0, rice = 0`으로 바꾼 월드와 시드 `stratagem-success`(기존 `NO_GOLD` 사례)다.
- 기록 칸: 사례마다 `resolver.run`의 반환값 전체(성공·확률 실패면 `effects`·`logs`·`reports`·`history`를 포함한 `CommandResult`, 검사 실패면 `Failure`), 같은 입력의 `def.check`·`def.precheck` 반환값, 검사 실패의 `def.execute` 예외 문구, RNG 흔적, 실행 뒤 같은 RNG의 다음 `next()` 값 세 개를 적는다. RNG 흔적은 실제 `createRng(시드)`를 감싸 호출마다 `{ call: 'next' | 'int(min,max)', value }`를 순서대로 적은 배열이다. 검사 실패는 흔적이 빈 배열이고 다음 세 값이 새 RNG의 처음 세 값과 같아야 한다.
- 쓰기: 환경 변수 `STRATAGEM_EQUIVALENCE_WRITE=1`일 때만 같은 시험이 기록을 계산해 파일로 쓴다. 쓰기 전에 기록 안에 `undefined`·`NaN`·`-0`이 있으면 실패한다(JSON에서 같은 값으로 돌아오지 않으므로). 커밋 0에서 한 번만 쓰기 모드로 실행하고 같은 커밋에서 읽기 모드로 다시 통과시킨 뒤 커밋한다.
- 읽기: 기본 모드는 파일을 읽어 사례마다 다시 계산한 기록과 `toStrictEqual`로 비교한다. 비교는 파싱한 값끼리 하므로 줄바꿈(CRLF) 차이는 결과에 영향이 없다.
- 출처 확인(리뷰): `git log --format=%H -- packages/rules/src/commands/ext/stratagem/__fixtures__/equivalence.baseline.json`이 커밋 0 하나만 내고 커밋 0의 부모가 `B`이며 `git diff B 커밋0 --stat`이 새 파일 두 개뿐임을 본다. 재현은 로컬 저장소에서 커밋 0을 꺼내 쓰기 모드로 다시 돌리면 같은 값이 나오는 것으로 확인한다. 이 확인은 리뷰 때 한 번이며 시험 실행에는 Git이나 네트워크가 필요 없다.
- 이후: 커밋 1·2와 병합 직전 재확인에서 기준 기록 파일을 고치지 않는다. S8이 실패하면 정의 쪽을 고치며 쓰기 모드로 기준을 다시 만들지 않는다. 기준을 바꿔야 할 사유가 생기면 계획 변경으로 부모 채팅에 올린다.
