### 1. 목표

T4-05가 만든 계략 4종(`fire_attack` 화계, `sabotage` 파괴, `incite` 선동, `plunder` 탈취)을 운영 확장 목록 `extensionCommands`와 결합 목록 `extCommandBindings`에 올린다. 등록 뒤에도 아래가 성립해야 한다.

- 대조 도구가 함수 본문을 실행하지 않고 운영 목록 네 개를 읽는다. 그 결과는 Node와 설치된 zod로 실제 import한 목록과 순서까지 같다.
- 끈 월드(`enabled = null`)는 기본 37개의 결과·RNG 소비·상태 해시가 지금과 같다.
- 켠 월드의 네 명령 결과는 T4-05 단위 골든과 같고 `ext` 키가 생기지 않는다.
- 엔진·서버·DB·재생 기록 형식·제품 프리셋은 바뀌지 않는다.

이 목표는 AC-P2-03 (나) 가운데 등록 몫이다. 엔진 통합 증거와 AC 완료는 여기서 나오지 않는다(§10).

### 4. 분석기와 실제 정의의 충돌, 기술 계약

#### 4.1 문제

PR #182의 `readExtensionRegistryKeys`는 `ext/registry.ts`에서 출발해 const와 상대 import만 따라가며 등록 목록을 읽는다. 함수 본문은 모듈 초기화 때 실행되지 않는다는 전제로 보지 않는다. 그 전제를 지키려고 초기화 중에 호출되는 함수는 고정 신뢰 두 가지만 받는다. `support.ts`의 `defineCommand`(`:184`)와 고정 의존성 zod의 정해진 생성 API(`:80~90`)다.

현재 T4-05 정의를 그대로 등록하면 세 겹으로 거부된다.

1. `export function makeStratagem`은 함수 선언이라 `bindings`에만 들어가고 `exports`에는 없다(`:164`). 그래서 다른 파일에서 import하면 `선언 makeStratagem을 찾지 못했다`가 난다.
2. 찾더라도 const 초기값이 아니므로 값으로 읽지 못한다.
3. 호출 자체가 `defineCommand`도 zod도 아니라서 `pureInitializer`(`:273~324`)와 `value`(`:344~376`)가 모두 받지 않는다.

이 거부는 도구 결함이 아니라 계약대로의 동작이다. `makeStratagem`의 본문은 모듈 초기화 중 실제로 실행되므로 그 안에서 목록을 바꾸면 숨은 등록이 된다. F1 리뷰 두 건도 이 거부를 바꾸지 않았다.

#### 4.3 권고 계약 (A)

`base.ts`:

| 지금 | 바꾼 뒤 |
| ---- | ------- |
| `type Spec = { key; name; stat; fields?; labels? }` | `export type StratagemSpec`. 칸은 그대로다 |
| `const argsSchema = z.strictObject({ cityKey: positive })` | `export const stratagemArgs = z.strictObject({ cityKey: positive })`. 스키마 그대로다 |
| `function check(view, actor, raw)` | `export function checkStratagem(view, actor, raw)`. 매개변수와 반환형은 그대로다. 본문은 아래 치환 1만 받는다 |
| `export function makeStratagem(spec): CommandDef`와 안쪽 `execute` | 없앤다. 안쪽 `execute` 본문을 `export function executeStratagem(spec: StratagemSpec, view: WorldView, actor: Actor, raw: unknown, rng: Rng): CommandResult`로 옮긴다. 본문은 아래 치환 1·2만 받는다. `Rng`는 `import type`으로 가져온다 |

옮길 때 허용되는 변경은 아래 기계적인 것뿐이다.

1. 식별자 `argsSchema` → `stratagemArgs`. `check` 본문의 `safeParse`(`base.ts:92`)와 `execute` 본문의 `parse`(`:118`) 두 곳이다.
2. 식별자 `check` → `checkStratagem`. `execute` 본문의 첫 검사 호출(`:116`) 한 곳이다. 정의의 `check`·`precheck` 칸 값은 명령 파일로 옮겨 간다(아래 꼴).
3. 타입 이름 `Spec` → `StratagemSpec`. 칸은 그대로다.
4. 메서드 `execute(view, actor, raw, rng) { … }`가 최상위 함수 `executeStratagem`이 된다. 본문의 `spec`은 클로저 변수에서 첫 매개변수로 바뀌고 이름은 그대로다. 나머지 네 매개변수는 지금 `CommandDef['execute']`(`types.ts:59`)에서 추론되던 형을 그대로 적는다.
5. 위로 인한 들여쓰기·줄바꿈. Prettier 결과를 따른다.

그 밖은 그대로다. 계산식·상수·비교 연산, 분기와 조건 순서, 효과 목록의 원소와 순서, 로그·보고·국가 기록의 칸과 문구, `throw` 문구, `rng.next()`·`rng.int()`의 호출 횟수·인자·순서, 본문 주석이 모두 해당한다. 리뷰는 기준 SHA(§8 2단계)와 커밋 1 사이의 공백 무시 diff에서 위 다섯 종류 말고 다른 차이가 없음을 본다. 실행 결과의 동등성은 §9.1 S8이 따로 본다.

`STRATAGEM`, `effectiveStat`, `stratagemDistance`, `stratagemDefenders`, `stratagemProbability`, `plunderYearCoefficient`와 머리 출처 주석은 그대로다.

명령 파일 네 개는 아래 꼴이다. 화계를 예로 든다. 머리의 원작 출처 두 줄은 지금 파일 그대로 둔다.

```ts
import type { CommandDef } from '../../types';
import { checkStratagem, executeStratagem, stratagemArgs, type StratagemSpec } from './base';

export const fireAttackSpec: StratagemSpec = {
  key: 'fire_attack',
  name: '화계',
  stat: 'intel',
  fields: ['agriculture', 'commerce'],
  labels: ['농업', '상업'],
```

#### 4.4 정의 파일의 허용·거부 경계

계략 정의 파일과 이후 같은 꼴을 쓰는 등록 줄은 아래를 지킨다. 받는 쪽은 PR #182 분석기가 지금 받는 구문이고 거부 쪽은 지금 거부하는 구문이다. 분석기를 고치지 않고 이 경계를 시험으로 고정한다(§9.2).

| 받음 | 거부 (CLI exit 1) |
| ---- | ----------------- |
| 정의 객체 리터럴 안의 `key`·`target` 문자열 리터럴. `target`은 생략하지 않는다(factory가 아니면 기본값이 없다) | `key: fireAttackSpec.key` 같은 속성 접근, 계산된 `target` |
| 다른 칸의 문자열 리터럴, const·함수 선언을 가리키는 식별자, 화살표 함수와 메서드 | 정의 객체의 spread·계산 속성 |
| 문자열·배열 리터럴로만 된 `*Spec` const | 초기화 때 helper를 호출해 만든 spec이나 정의(`make('fire_attack')`, `makeStratagem({...})`, 임의 factory) |
| `stratagemArgs`처럼 허용 목록 안 zod 호출(`strictObject`, 지원 `positive`)로만 만든 const | `.default`·`.regex` 같은 허용 목록 밖 zod API, 음수 인자 |
| 정의 식별자의 배열과 배열 spread, `as const` | `let`, 최상위 실행문, 목록에 끼운 함수 호출 결과 |

`execute`·`check`의 본문은 명령 실행 때만 돈다. 모듈 초기화 때 사용자 함수를 호출하지 않는다는 점이 이 경계의 근거다.

#### 4.5 바뀌지 않는 것

- 공개 API: `packages/rules/src/index.ts`는 고치지 않는다. `stratagemCommands`와 네 정의의 이름, `CommandDef` 모양(`key`, `name`, `category`, `target`, `args`, `check`, `precheck`, `execute`)은 그대로다. `base.ts`에서 `makeStratagem`이 빠지고 네 이름이 새로 내보내진다. 저장소 안에서 `makeStratagem`을 쓰는 곳은 네 명령 파일뿐이다.
- 게임 효과와 RNG: `executeStratagem` 본문은 §4.3의 기계적 변경 말고는 지금 `execute` 본문과 같다. `precheck`와 `check`가 같은 함수인 것도 같다. 효과 목록 순서, 로그·보고·국가 기록 문구, 확률 판정의 `rng.next()` 한 번, 부상·피해·성장 난수 순서가 그대로다. 증거는 기존 T4-05 시험이 고친 것 없이 통과하는 것(S0)과, 코드 변경 전 고정한 기준 기록과의 전체 결과·RNG 대조(S8) 두 가지다. 기존 시험 통과 수만으로 동등성을 주장하지 않는다.
- 고정 의존성 신뢰: 분석기가 신뢰하는 것은 지금처럼 `defineCommand`와 zod의 정해진 생성 API뿐이다. support 하위 런타임 모듈 검사, type-only import·export 건너뛰기도 PR #182 그대로다.
- 대조표 집계: 기본 37개(장수 27·국가 10), 원본 90개, 분모 91개, 미해결 원본 3개가 그대로다. 확장 key 넷은 이미 대응표에 장수 명령 행으로 있으므로 도구가 새 행을 요구하지 않는다.

##### 9.1.1 S8 기준 기록 계약

기준 SHA의 구현을 시험마다 Git에서 꺼내 돌리지 않는다. 대신 변경 전 구현의 실행 결과를 코드 변경 전에 한 번 JSON으로 고정하고 그 파일이 어디서 나왔는지를 Git 이력으로 남긴다.

- 기준: §8 2단계의 `B`. 커밋 0은 `B`의 바로 위 자식이고 새 파일 두 개(`equivalence.test.ts`, `__fixtures__/equivalence.baseline.json`)만 더한다. 기준 기록 머리에 `baseSha: B`와 사례 수 12를 적는다.
- 입력: 새 제품 값이나 게임 정책을 만들지 않는다. `stratagem.test.ts`에 이미 있는 입력만 쓴다. 월드는 그 파일의 `world()`와 같은 수정(`commandWorld()`에서 다른 장수를 도시 3으로 옮기고 도시 2 값을 정함), 주체 `{ generalId: 1, tick: 0 }`, 인자 `{ cityKey: 2 }`, resolver는 `createCommandResolverWithCommands({ general: 네 key, nation: [] }, stratagemCommands)`다. 시험 파일 안에 이 입력을 다시 적는다.
- 사례: 네 명령 × 세 경우다. 성공은 시드 `stratagem-success`, 확률 실패는 시드 `seed-1`(기존 골든과 같은 시드), 검사 실패는 `gold = 0, rice = 0`으로 바꾼 월드와 시드 `stratagem-success`(기존 `NO_GOLD` 사례)다.
- 기록 칸: 사례마다 `resolver.run`의 반환값 전체(성공·확률 실패면 `effects`·`logs`·`reports`·`history`를 포함한 `CommandResult`, 검사 실패면 `Failure`), 같은 입력의 `def.check`·`def.precheck` 반환값, 검사 실패의 `def.execute` 예외 문구, RNG 흔적, 실행 뒤 같은 RNG의 다음 `next()` 값 세 개를 적는다. RNG 흔적은 실제 `createRng(시드)`를 감싸 호출마다 `{ call: 'next' | 'int(min,max)', value }`를 순서대로 적은 배열이다. 검사 실패는 흔적이 빈 배열이고 다음 세 값이 새 RNG의 처음 세 값과 같아야 한다.
- 쓰기: 환경 변수 `STRATAGEM_EQUIVALENCE_WRITE=1`일 때만 같은 시험이 기록을 계산해 파일로 쓴다. 쓰기 전에 기록 안에 `undefined`·`NaN`·`-0`이 있으면 실패한다(JSON에서 같은 값으로 돌아오지 않으므로). 커밋 0에서 한 번만 쓰기 모드로 실행하고 같은 커밋에서 읽기 모드로 다시 통과시킨 뒤 커밋한다.
- 읽기: 기본 모드는 파일을 읽어 사례마다 다시 계산한 기록과 `toStrictEqual`로 비교한다. 비교는 파싱한 값끼리 하므로 줄바꿈(CRLF) 차이는 결과에 영향이 없다.
- 출처 확인(리뷰): `git log --format=%H -- packages/rules/src/commands/ext/stratagem/__fixtures__/equivalence.baseline.json`이 커밋 0 하나만 내고 커밋 0의 부모가 `B`이며 `git diff B 커밋0 --stat`이 새 파일 두 개뿐임을 본다. 재현은 로컬 저장소에서 커밋 0을 꺼내 쓰기 모드로 다시 돌리면 같은 값이 나오는 것으로 확인한다. 이 확인은 리뷰 때 한 번이며 시험 실행에는 Git이나 네트워크가 필요 없다.
- 이후: 커밋 1·2와 병합 직전 재확인에서 기준 기록 파일을 고치지 않는다. S8이 실패하면 정의 쪽을 고치며 쓰기 모드로 기준을 다시 만들지 않는다. 기준을 바꿔야 할 사유가 생기면 계획 변경으로 부모 채팅에 올린다.

##### 9.1.2 S5 순수 재생 계약

`runReplayAction`(`replay.ts:50~78`)은 `runGeneralTurn`(`commands/turn.ts:10~81`)이 돌려준 `{ state, result, nation, commandKey }` 가운데 `state`만 쓴다. 그 뒤 장수의 `nextTurnTick`을 한 달 미루고 예턴을 당기고 revision을 1 올린 `ReplayState`를 돌려준다. 실패 코드는 반환값 어디에도 없다. 따라서 두 함수의 반환값을 서로 직접 비교하지 않고 재생 반환에서 `UNKNOWN_COMMAND`·`COMMAND_DISABLED`를 판별하지 않는다. 재생은 정확한 예상 `ReplayState`와 비교하고 실패 코드는 같은 입력의 `runGeneralTurn` 결과에서 본다.

입력 `R0`는 계략 key `K`(네 key 각각)마다 새로 만든다.

- `state`: §9.1.1과 같은 `world()` 수정(`commandWorld()`에서 장수 1 말고는 도시 3으로 옮기고 도시 2 값을 정함)에 `generals[1].userId = 'user'` 한 가지를 더한다. 장수 1은 군주(`officerLevel` 12)이고 국가 1은 `isNpc`다(`commandFixture.ts:89`, `:126`). `userId`가 `null`이면 `turn.ts:24~29`의 국가 턴 NPC 분기가 장수 명령보다 먼저 돈다. 사용자를 붙이고 `nationTurns`를 두지 않아 그 분기와 NPC 장수 명령 대체(`turn.ts:59~71`)를 모두 끈다. 기존 `replay.test.ts:98`과 같은 방식이다.
- `turns`: 장수 1~4마다 `emptyTurns()`다. `turns[1][0]`만 `{ commandKey: K, args: { cityKey: 2 } }`로 바꾼다.
- `revisions`: 장수 1~4 모두 0이다. `monthlyTick`: 0이다.
- 시드는 `stratagem-replay`, `unitSet`은 `testUnits`다.

시험은 먼저 첫 액션 조건으로 `nextGameAction(R0)`가 `{ kind: 'turn', tick: 100, generalId: 1 }`임을 단언한다. 월 경계는 0 + `TICKS_PER_MONTH` = 10000이고 장수 1의 `nextTurnTick` 100이 다른 장수의 5000보다 앞선다(`commandFixture.ts:142`). 이 단언이 깨지면 아래 비교는 다른 액션을 본 것이므로 시험이 거기서 실패한다.

resolver `X`는 셋이다. 켠 운영 resolver `createCommandResolver({ general: 네 key, nation: [] })`, 없음(`undefined`), 끈 운영 resolver `createCommandResolver(null)`이다. 각 `(K, X)`마다 아래를 계산한다.

- 관측 `T = runGeneralTurn(structuredClone(R0.state), { generalId: 1, tick: 100, unitSet: testUnits }, R0.turns[1][0], 'stratagem-replay', {}, X)`.
- 재생 `R1 = runReplayAction(R0, 'stratagem-replay', testUnits, X)`.

재생의 예상값은 `T.state`로 만들고 `R1`과 `toStrictEqual`로 비교한다.

| 칸 | 예상 | 근거 |
| -- | ---- | ---- |
| `state` | `T.state`에서 `generals[1].nextTurnTick`만 100 + `TICKS_PER_MONTH` = 10100으로 바꾼 값 | `replay.ts:73~74` |
| `turns` | 장수 1만 `[...R0.turns[1].slice(1), { commandKey: 'rest', args: {} }]`이고 장수 2~4는 `R0.turns`와 같다 | `:75` |
| `revisions` | 장수 1만 1이고 장수 2~4는 0이다 | `:76` |
| `monthlyTick` | 0 그대로다 | 턴 액션은 이 칸을 바꾸지 않는다(`:57~61`은 월간 액션만) |

호출 뒤 `R0`는 호출 전에 떠 둔 깊은 복사본과 같다(`replay.ts:62`의 `structuredClone`).

실패 코드와 실행 여부는 `T`에서 본다. 세 경우 모두 `T.nation`은 `undefined`, `T.commandKey`는 `K`다.

| `X` | `T.result` | 상태 쪽 관측 |
| --- | ---------- | ------------ |
| 켠 운영 resolver | `'code' in T.result`가 거짓이다. `T.result`는 `X.run(structuredClone(R0.state), { generalId: 1, tick: 100, unitSet: testUnits, target: 'general' }, K, { cityKey: 2 }, rngFor('stratagem-replay', 'turn', 100, 1))`과 `toStrictEqual`로 같다(`turn.ts:72~78`의 실제 호출 인자와 RNG 흐름) | `R1.state.generals[1]`의 `experience`·`dedication`이 0보다 크다. 고정 장수의 시작값은 0이고 계략은 성공·확률 실패 모두 이 둘을 올린다(`base.ts:189~195`) |
| 없음 | `T.result.code`가 `UNKNOWN_COMMAND`다. 기본 `runCommand`가 계략 key를 모른다(`registry.ts:29`) | `T.state`가 `R0.state`와 `toEqual`로 같다. 따라서 `R1.state`는 장수 1의 `nextTurnTick` 말고 `R0.state`와 같다 |

12개월 재생은 켠 운영 resolver와 `K = fire_attack`인 `R0`에서 시작한다. `monthlyTick`이 120000에 이를 때까지 `runReplayAction`을 되풀이한다. 같은 입력으로 두 번 따로 계산한 최종 `ReplayState`가 `toStrictEqual`로 같고 모든 단계에서 `Object.hasOwn(state, 'ext')`가 거짓이다. 반환에 실패 코드가 없으므로 이 시험은 결정성과 `ext` 부재만 본다.

### (나)-2. 최소 첫 코드 단위

첫 단위는 `fire_attack` 하나다. 성공 하나와 대표 실패 하나를 실제 HTTP에서 시작해 엔진 실행, 같은 트랜잭션의 상태·로그 저장, 다시 읽기까지 잇는다. 나머지 `sabotage`·`incite`·`plunder`는 같은 계약을 그대로 넓힌 뒤 명령마다 따로 증거를 낸다. 네 명령의 규칙 재작성과 밸런스 재승인은 0이다.

#### (나)-2.1 대표 실패의 선택

대표 실패는 자기 국가 도시를 대상으로 저장한 `fire_attack`이다. `save`는 사전 검사를 돌리지 않으므로 HTTP 저장이 통과하고 엔진이 `BAD_TARGET`(`자기 국가 도시에는 계략을 쓸 수 없습니다.`)를 낸다. DB를 손으로 고치지 않아도 재현된다. 검사 실패는 비용·성장 효과가 없다. 이때 `GeneralLog.kind`는 `'failure'`이고 문구는 `${code}: ${message}`다(`turnLoop.ts:260-261`). 확률 실패는 검사 실패가 아니다. 비용과 성장을 쓰는 `CommandResult`이므로 `kind = 'success'`에 `화계 실패: {도시}` 로그가 남는다. 둘을 같은 실패로 세지 않는다. `{ cityKey: 0 }` 같은 인자 오류는 HTTP 입력 오류(`BAD_REQUEST`) 사례로 따로 본다.

성공 하나만으로는 S7을 채우지 못한다. 부상은 성공 뒤 대상 장수마다 따로 판정하므로((나)-11) 성공해도 부상 보고가 0개일 수 있다. 그래서 첫 성공 fixture는 mock RNG 없이 알려진 시드와 대상 도시의 장수 배치로 화계 성공과 실제 부상 보고 1건 이상이 함께 나오는 경우를 골라 고정한다. 시드는 시험 fixture 값이며 제품 값이 아니다.

미래 fixture 준비 완료 조건은 아래다. 지금 시드를 찾거나 실행하지 않았다.

- 경로: 공개 `advanceTo`·`poll`이 부르는 `TurnLoop.step`의 전체 `runGeneralTurn` 경로와 그 step이 쓰는 정확한 `rngFor(seed, 'turn', tick, generalId)` 턴 스트림을 쓴다. 명령 함수 직접 호출이나 별도 RNG 주입은 증거가 아니다.
- 고정값: 월드 seed, 실행 tick, 실행 장수·대상 도시와 그 도시의 대상 장수 목록, 예상 피해(도시 수치 변화와 부상 장수별 값), 비용(금·쌀·성장), 기대 장수 로그 문구, 부상 보고 행 수와 내용, 대상 국가 기록 사건을 fixture 파일에 적는다.
- 판정: 순수 oracle(`resolver.run` 같은 입력)과 맞추는 데서 멈추지 않는다. 실행 뒤 실제 PG의 장수·도시 행, `records.general` API가 돌려주는 장수 로그, `BattleLog`의 대상·공격자(`attackerId`) 칸, `NationHistory.data.events`의 대상 국가 사건을 fixture 값과 각각 명시 assert한다.
- 구분: `BAD_TARGET` 대표 실패(비용 0, `kind = 'failure'`)와 확률 miss(비용 부과, `CommandResult`, `kind = 'success'`, `화계 실패: {도시}`)는 다른 사례다. miss를 쓰려면 같은 조건으로 별도 시드를 고정한다.

### (나)-4. ext 단독 첫 월드의 기술 가능성

조사 중 후보였던 legacy policy ext 단독 새 월드(조약·인사 끔, `replayFormat: 'legacy'`)는 지금 API에서 불가했다. 이유는 아래다.

- 선택자가 ext 칸 origin 6을 거부한다((나)-1 마지막 행).
- legacy policy(`replayFormat: 'legacy'`, `policyFromSequence = null`) 월드는 `requirePolicyReady`(`apps/server/src/game/policy.ts:64-68`)가 `turns.set`·`turns.edit`를 `기본 방침 전환을 기다리고 있습니다.`로 막는다(`turns.ts:42`). 실제 HTTP 저장을 증명할 수 없다.
- origin 1에 켠 목록을 실으면 `presetRules`가 `commands`를 빼므로 재생이 목록을 복원하지 못한다. origin 1은 바꾸지 않는다.

계약은 ext 단독 + 조약 끔 + 인사 끔 + policy F = 0이다. F = 0은 `saveInitialWorld`가 `replayFormat`을 주지 않을 때 이미 쓰는 기본값(`persistence.ts:90`)이고 CLI도 그 기본을 쓴다(`cli/createWorld.ts:40-46`). 새 제품 선택이 아니라 지금 새 월드의 기본을 명시하는 것이다. legacy 후보는 사용자 요청이 아니라 조사 중 가정이었으므로 F = 0을 채택한다. ext 지원 첫 조합은 policy F = 0만이다. legacy와 중간 전환(F > 0)은 최초 범위 밖이며 지원 판정이 거부한다. 기존 조약 단독의 모든 policy 경로(legacy, F = 0, F > 0)는 그대로다.

#### (나)-4.1 최소 지원 계약 (정확 descriptor version 1)

아래는 T4-03 E8 `ExtOriginFields`를 좁힌 구체 계약이다. 부모가 기술 방향을 수용했고 이 절로 정본에 채택했다. 타입 블록은 실구현이 아닌 스케치다.

```ts
// origin 6 capabilities.ext와 selection.ext의 정규값 (정확 키, strict)
type ExtDescriptorV1 = {
  version: 1;
  commands: EnabledCommands; // general: 운영 등록 계략 4종의 중복 없는 정렬된 비지 않은 부분집합, nation: []
  preset: WorldPreset;       // parsePreset을 지난 완전 사본. preset.commands와 위 commands가 정확히 같다
  resources: Record<string, never>; // 실제 값은 {}, runtime은 z.strictObject({}). 비지 않으면 아직 미지원
  sliceKeys: [];             // extSliceKeys(commands)와 같다. 비지 않으면 아직 미지원
};
// origin.initial.ext는 생략, WorldExtSlice 행 0
// resourceHash = hashState(capsResourceHashInput(origin)). 식은 그대로이고 프리셋 사본을 포함한 전체 descriptor가 들어간다
```

- 운영 계략 key는 `fire_attack`, `incite`, `plunder`, `sabotage`다(`packages/rules/src/commands/ext/stratagem/*.ts`). `createCommandResolver`(`commands/resolve.ts:22-43`)는 중복·기본 key·대상만 보고 순서는 보지 않는다. 정렬과 비지 않음은 지원 판정 helper가 따로 본다.
- 새 factory가 정규 목록을 만든다. 이미 저장된 wire를 재정렬하거나 변환하지 않는다. 정렬되지 않은 기록은 원시 그대로 해시 대조는 되지만 지원 판정에서 거부된다.
- `selection.ext`는 위 정규값 그대로(또는 같은 정보를 잃지 않는 명시형)를 담는다.
- 새 지원 조합은 origin 6 + archive 6의 ext 단독 하나다. origin 1·archive 1/2/5와 조약 단독 origin 6·archive 6의 판정과 바이트는 바뀌지 않는다.
- 지원 판정과 앱은 origin descriptor, `preset` 사본, 허용 목록, `initial.presetRules`의 의미가 같은지 검증한다. 곧 `commands`가 `presetCommands(parsePreset(preset))`와 같고(R7) `initial.presetRules`가 `presetRules(parsePreset(preset))`와 같으며(R13) 앱 쪽은 `World.preset` 정규 해시와 `preset` 사본이 같다(D7).

#### (나)-5.1 지원 판정 helper 모양 (B9 소유 스케치)

```ts
// parseCapsOrigin·descriptorSchema는 그대로다. 지원 판정 경로만 이 helper를 부른다
const extDescriptorV1 = z.strictObject({
  version: z.literal(1),
  commands: z.strictObject({ general: z.array(z.string()).min(1), nation: z.array(z.string()).length(0) }),
  preset: plainObject,
  resources: z.strictObject({}),
  sliceKeys: z.array(z.string()).length(0),
});
function supportedExt(raw: unknown, initial: WorldInit): ExtDescriptorV1 {
  const ext = extDescriptorV1.parse(raw); // {}, 모르는 칸, version, 비지 않은 resources·sliceKeys 거부
  const general = ext.commands.general;
  if (general.some((key, i) => i > 0 && general[i - 1]! >= key)) throw new Error(/* 정렬·중복 */);
  createCommandResolver(ext.commands); // 기본 key, 모르는 key, 대상
  const preset = parsePreset(ext.preset);
  if (!sameCanonical(preset, ext.preset)) throw new Error(/* R13 정규형 */);
  if (!sameCanonical(presetCommands(preset), ext.commands)) throw new Error(/* R7 */);
  if (!sameCanonical(initial.presetRules, presetRules(preset))) throw new Error(/* R13 */);
  return { ...ext, preset };
}
// runCapsReplayAction 안: 조약 단독이면 지금처럼 resolver 없이 돈다
const resolver = 'ext' in selected ? createCommandResolver(selected.ext.commands) : undefined;
const next = runReplayAction(replay, seed, unitSet, resolver);
```

이 블록은 실구현이 아닌 스케치다. `sameCanonical`은 자리 표시다. rules 순수 모듈은 `node:crypto`를 쓰는 `hashState`(`packages/shared/src/node/hashState.ts:1`)를 import하지 않는다(T4-03 E8-6 import 규칙). 그래서 키 정렬 깊은 비교를 rules 안에 두거나 앱 adapter가 해시로 대조한다. 어느 쪽인지는 B9 소유자가 정한다. 오류 문구도 B9 소유자가 정한다.

새 DB 표지 열은 두지 않는다. 켠 여부는 `World.preset.commands`와 origin ext 칸의 대조로 충분하고 새 migration이 생기면 C8 순서가 하나 더 걸린다. 생성 옵트인은 DB 열이 아닌 factory 옵션 `extFormat?: 1`로 둔다((나)-7).

부모는 (나)-4.1 계약과 이 표를 수용했다. B 단계는 `3a9d62c` 위에서 strict selection union 확장과 (나)-6 조약 호환 guard를 함께 끝낸 정확 local SHA를 낸다. 그 SHA에 실제 반대쪽 리뷰의 차단 지적이 0이고 조약 호환 단위 시험과 전체 workspace 타입 검사가 통과하면 그 source를 인계받아 앱의 별도 private 구현(Ext A2·A3)을 시작할 수 있다. main 병합이나 정확 SHA CI는 private 앱 코드 착수 전 조건이 아니다. main 병합, 정확 최종 SHA CI, 정상 merge는 게시·인수 gate로 남는다. PG·HTTP·재시작 실제 실행은 여전히 부모가 슬롯별로 배정한다((나)-10). 이 계획 채택만으로 B나 Ext 코드를 시작하지 않는다.
