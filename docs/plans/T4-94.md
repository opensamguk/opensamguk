# T4-94 황실·조정·봉신 계약 (첫 구현)

> 대기열: T4-94 · AC: AC-P2-31, AC-P2-35의 해당 몫 · 백엔드(rules·engine·server·PG): Codex · 화면 코드·Artifacts: Claude · 독립 리뷰: 구현하지 않은 쪽 · CF 어댑터: 기존 CF 담당 · 상태: 구현·검증 중. 실제 PG·공개 화면·사용성·전체 검사 통과. CF·필수 CI·병합 전

## 계획

### 목표
AC-P2-31 가운데 황실 첫 집합을 실제 효과까지 구현한다. 황제 한 명, 천자 소재 거점, 정통성, 조정 세 직위(승상·대장군·사도), 양방향 봉신 계약, 실제 공납과 봉록, NPC의 제안·수락, 같은 봉신 계열 사이의 전쟁 차단이 범위다. 같은 규칙·DTO·입력 기록으로 CF에서도 대조할 수 있게 AC-P2-35 몫의 계약을 함께 고정한다. 이 작업이 끝나도 AC-P2-31·35 전체나 가문 계승을 완료로 보고하지 않는다.

사용자가 확정한 것은 황제 1명, 천자 소재 거점, 정통성이다. 나머지 설계는 Codex 기술 검토를 거친 엔지니어링 제안이다. 사람의 즉위·계약 수락·직위 수락은 명시 입력으로만 일어나고 NPC만 자동으로 판정한다. 상세 수치와 소재 거점은 원생성 config에 고정한 시험 설정이다. 역사 소재 거점과 기본 프로필은 공개하지 않는다.

### 완료 조건 (이 작업 한정)
- `governance-v1`을 켠 새 원생성 월드에서 즉위, 직위 제안·수락·효과, 양방향 봉신 제안·수락·해제·이탈, 월 공납·봉록, 정통성, NPC 판정이 실제 PG·HTTP·엔진·화면으로 동작한다.
- 같은 봉신 계열 공격은 모든 명령 소비 경로에서 거부된다. 예약해 둔 명령도 실행 때 거부된다.
- 기능을 끈 기존 월드의 상태·해시·RNG 소비가 지금과 같다.
- PG와 실제 workerd의 결과·오류·409·멱등·상태 해시·재생이 같다는 증거를 CF 담당과 함께 남긴다. 실측 전에는 통과를 주장하지 않는다.
- 독립 리뷰, 필수 CI, 정상 병합을 각각 따로 거친다.

### 하지 않는 것
가문 계승과 사망 모델, 조약 `tribute` 조항 연결(`CLAUSE_NOT_CONNECTED` 유지), 진행 중 월드 자동 전환, 역사 기본 프로필 공개, `permissions.ts`·`resolve.ts`·`treaty.ts`·`removeNation` 수정, 개인 휘하(`CampaignState.links`)·부곡·`NationOffice`·예약 칸 변경, 다른 사람에게 계약을 강제로 넘기는 경로.

### 코드에서 확인한 사실
아래 사실은 G0가 main 기준으로 다시 확인한다.
- 기능 월 정산 훅은 `settleMonthly({before, settled, tick})`이다. `settled`는 앞 기능까지 정산한 상태다. `monthlyOrder`는 `['treaty','personnel','campaign-assignment-v2','logistics-v1']`이다.
- 물류 정산은 `tick === monthlyTick + 10000`만 받는다. 입력 tick은 `[monthlyTick, monthlyTick+10000)` 안이어야 한다. World의 `monthlyTick`과 로드·조회에서 대조한다.
- `WorldState.logistics?`와 `cloneWorld`의 선택 칸 패턴이 있다. 칸이 없으면 기존 해시가 바뀌지 않는다.
- Prisma에는 `LogisticsMovement`만 있고 city-resources의 금·쌀 원장 표는 없다. 금·쌀은 월 세수·명령 등 여러 기능에서 바뀐다.
- `resolverForRuleFeatures`는 명령 바인딩도 campaign도 없으면 `undefined`를 돌려준다. 그러면 `policy/execute.ts`·`commands/turn.ts`가 기본 등록표의 `runCommand`로 빠진다.
- 명령 정의를 직접 쓰는 곳은 NPC chooser의 `check`, `campaign/orders.ts`의 `get`·`precheck`, 서버 `turns.ts`·`nationCommands.ts`·`commands.ts`·`nationOfficeSlots.ts`, `operation/suggest.ts`, `policy/index.ts`의 기본 등록표 참조다.
- 부곡 공격은 같은 키 `attack`으로 일반 공격을 대체한다. city-resources 래퍼는 `get`·`list`가 돌려주는 정의 자체를 감싼다.
- 다른 나라를 겨누는 공격 계략 키는 `fire_attack`, `sabotage`, `incite`, `plunder`다.
- 캠페인 월 훅은 현재 지휘관을 따른다. 직접 전투를 여는 월 훅은 없다. 계획 작성 때의 초기 확인이므로 구현 전에 다시 확인한다.
- `General.gold`·`Nation.gold`는 32비트 `Int`이고 `CITY_RESOURCE_MAX = 2_147_483_647`이다.

### 원생성 설정과 상태
`governance-v1`은 `requires: ['city-resources-v1','personnel','treaty']`이고 원생성에서만 켠다. `monthlyOrder` 맨 끝에 붙이므로 기존 판의 순서는 그대로다. 설정은 `featureData['governance-v1']`에 zod `strictObject`로 고정한다. 검사한 값은 상태의 `config`에 복사해 로드·내보내기 때 origin과 대조한다. 진행 중 설정 변경은 거부한다. `checkOrigin`은 `seatCityKey`가 `initial.cities`에 있고 `PASS`가 아닌지, 직위 키가 유일한지, `initial`에 governance 칸이 없는지 확인한다.

| 설정 | 시험 기본값 |
| --- | --- |
| 거점 | 가상 fixture 거점 하나(`seatCityKey`) |
| 정통성 | 거점 소유 +2, 황제국 +1, 직위당 +1(최대 3), 그 밖 −1, 범위 0..100, 즉위 최소 60 |
| 견책·이탈 | 견책 −5(같은 국가 6개월 쿨다운), 이탈 −10 |
| 공납 | `maxBp` 2000, 1회 상한 100,000 |
| 봉록 | 직위당 금 100 |
| 계약 | 제안 기한 6개월, 깊이 3(최상위 0에서 간선 3개), 면제 최대 12개월 |
| NPC | `cityRatio` 2, 수락 `maxBp` 1000, 제안 bp 500, 같은 상대 제안 쿨다운 12개월 |
| 상한 | 보낸 제안 3, 받은 제안 5, 월드 전체 200, 조정 제안 직위당 1 |

상태는 `WorldState.governance?`이고 저장은 nullable `World.governanceState Json?`이다(새 migration `governance_state`). 같은 migration에서 원장 표 `GovernanceMovement`를 만든다. `clone`, `hashState`, `worldLoader`, 원생성 `initialGovernanceState`, `initReplayState`(중복 초기화 거부), `checkArchive`, CF DTO를 같은 단계에서 연결한다. 꺼진 월드에는 칸이 없고 값이 있으면 로드 오류다.

```
{version:1, config, monthlyTick, revision, nextOfferId, nextVassalId,
 throne:{emperorGeneralId|null, emperorNationId|null, sinceTick},
 court:Record<office,{generalId, appointedTick}|null>,
 legitimacy:Record<nationId,number>,
 vassals:[{id, vassalNationId, overlordNationId, overlordMonarchId, vassalMonarchId, goldBp, riceBp, sinceTick, remitUntilTick}],
 offers:[{id, kind:'VASSAL'|'COURT', authority?:'OWN'|'EMPIRE', fromNationId, sourceMonarchId?, actorId, targetNationId|targetGeneralId, direction?, office?, goldBp?, riceBp?, expiresTick}],
 pendingRenounce:number[], censuredAt:Record<nationId,tick>, npcOfferAt:Record<'from:to',tick>}
```

검사는 둘로 나눈다. `readGovernanceState`는 구조만 본다. 스키마 모양과 id 유일·정렬 및 `monthlyTick % 10000 === 0`을 검사한다. 현재 서명으로 유효한 관계의 단일 상위·순환·깊이는 `governanceRealmIndex`가 검사한다. 현재 군주와 맞지 않는 옛 서명은 정리 때 지운다. 중복 조정 직위는 출력 검사에서 거부한다. `assertGovernanceFinal`은 참조·권한 불변식을 본다. 참조는 존재하는 국가·장수만 가리켜야 한다. 황제가 있으면 그 장수가 황제국 소속 군주(`officerLevel 12`)이며 황제국이 거점을 소유하고 봉신이 아니어야 한다. 관계의 양쪽 군주 id와 제안의 권한 문맥도 현재 상태와 맞아야 한다. 거점 소유국은 하나뿐이므로 황제도 한 명이다. 로드, 저장 직전, 입력 완료 상태에는 두 검사를 모두 적용한다. `reconcileGovernance`는 구조 검사만 요구하므로, 다른 명령이나 앞선 월 정산이 잠깐 만든 거점 상실·군주 변경·멸망 국가 참조를 의미상 무효라는 이유로 던지지 않고 정리한다.

state JSON에는 활성 관계·활성 제안·살아 있는 국가의 정통성·쿨다운 안의 키만 둔다. 끝난 제안·관계, 지난 쿨다운 키, 멸망 국가의 키는 정리 때 지운다. 무한히 쌓이는 이력은 `InputEvent` 결과, 월 효과, `NationHistory`, `GovernanceMovement`에 둔다. `revision`·`nextOfferId`·`nextVassalId`가 `2_147_483_647`에 닿으면 입력은 `LIMIT`로 거부하고 정산은 예외를 낸다.

### 행동 계약
입력 종류는 `governance.act` 하나, route는 queued, 멱등키는 `governance:<uuid>`다. 행위 장수는 세션 사용자의 장수로 고정한다. 서버 사전 판정과 엔진 실행은 같은 순수 함수 `decideGovernanceAction(state, actorId, payload, tick)`을 쓴다. 실행 때 결과가 달라졌으면 `REJECTED`다.

| payload | 행위자 | 핵심 검사 |
| --- | --- | --- |
| `throne.ascend{}` | 거점 소유국의 등장한 군주 | 황제 없음, 정통성 ≥ 60, 그 국가가 봉신 아님 |
| `throne.abdicate{}` | 황제 | 본인 의사로만 퇴위 |
| `vassal.offer{authority, targetNationId, direction, goldBp, riceBp}` | `OWN`: 자국 현 군주. `EMPIRE`: 현 황제 또는 승상 | 출처 국가는 `authority`에서 파생한다. `EMPIRE`는 `DEMAND`만. `DEMAND`면 상대가 하위, `REQUEST`면 출처 국가가 하위. `ALREADY_VASSAL`, `CYCLE`, `DEPTH`, `REALM_AT_WAR`, bp 상한 초과, 황제국의 하위화, 제안 상한 `LIMIT` |
| `vassal.respond{offerId, accept}` | 상대 국가의 현 군주 본인 | 위 검사와 권한 문맥을 모두 다시 한다. 다른 사람이면 `NOT_PARTY`. 수락 때 양쪽 군주 id 기록 |
| `vassal.release{vassalId}` | 상위 국가 현 군주. `overlordNationId === emperorNationId`인 직접 관계면 승상도 | 즉시 해제 |
| `vassal.renounce{vassalId}` | 봉신 군주 | 다음 월 정산에 해제, 봉신 정통성 −10 |
| `court.offer{office, generalId}` | 황제 | 대상은 황제국 계열의 등장한 장수. 사람이면 제안만 만들고 NPC 대상은 NPC 판정으로 수락 |
| `court.respond{offerId, accept}` | 대상 장수의 사용자 본인 | 다른 사람이면 `NOT_PARTY` |
| `court.dismiss{office}`, `court.resign{}` | 황제, 직위 보유자 | 직위 비움 |
| `court.remit{vassalId, months}` | 황제 또는 사도 | `overlordNationId === emperorNationId`인 직접 관계의 공납 면제, 12개월 이하 |
| `court.censure{nationId}` | 황제 또는 대장군 | 황제국 계열 밖 국가 정통성 −5, 같은 국가 6개월 쿨다운 |

`vassal.offer`는 임의 `sourceNationId`를 받지 않고 출처 국가를 순수 규칙에서 파생한다. `OWN`이면 세션 장수가 현 군주인 자국, `EMPIRE`면 세션 장수가 현 황제 또는 승상일 때 `throne.emperorNationId`다. 자국 군주이면서 승상인 장수는 두 문맥 가운데 하나를 명시해 고른다. 제안에는 `authority`, 출처 국가, `sourceMonarchId`(대행 장수가 아닌 출처 국가의 현 군주), 실제 발신 `actorId`를 따로 기록한다. 수락·실행 때 현 황위, 승상직, 출처 국가 군주, 권한 범위를 다시 검사하고 하나라도 어긋나면 거부한다.

조정 직위는 황제의 권한을 나누어 대행하는 모델이다. 승상의 해제와 사도의 면제는 황제국이 직접 상위인 관계에만 닿는다. 다른 봉신 영주 아래의 B→C 관계와 소득을 황실 직위만으로 없애지 않는다. 같은 왕국 안에서도 다른 국가 군주의 권한을 자의로 대신하는 경로는 없다.

깊이는 최상위 국가를 0으로 세고 간선 3개까지다. 수락 때는 새 상위 국가의 깊이 + 1 + 하위가 될 국가가 거느린 하위 트리의 높이 ≤ 3을 검사해, 함께 종속되는 하위 트리 전체의 새 깊이를 확인한다. 이미 상위가 있는 국가는 `ALREADY_VASSAL`이다. 동의 없이 다른 상위로 옮기는 경로는 없다.

사람에게 자동 수락이나 자동 즉위는 없다. 즉위 가능하면 화면에 버튼만 보인다. 결과는 `{requestId, status: pending|applied|rejected, result}`이고 적용 결과는 `{action, revision, tick, offerId?, vassalId?}`, 거절 결과는 `{code, message}`다. 재생에서 `governance.act`는 기록을 다시 판정해 결과 JSON을 대조한다.

조회는 황제, 직위 명단, 정통성, 활성 관계의 존재(상위·하위·시작 시점)를 공개한다. 세율과 면제 기한은 초기 API 계약에서 당사국 두 군주, 황제, 그리고 황제국이 직접 상위인 관계에 한해 승상·사도에게만 보인다. 제안 본문은 당사자만 본다. 공납 금액에서 잔액을 역산할 수 있으므로 `GovernanceMovement` 행과 금·쌀 잔액은 당사국 군주 밖으로 내보내지 않는다. 예외로 봉록을 받은 장수 본인은 `holder = general`, `holderId = 자기`, 양수 `delta`인 자기 입금 행만 본다. 자기 봉록을 확인하려고 거점 도시 잔액, 다른 사람 지갑, 공납 행, 같은 이체의 출금 행을 볼 수는 없다. 범위가 애매한 칸은 이 보수 기준을 따른다.

### 월 정산 순서
`governance-v1` 단계는 기존 `runMonthly`와 앞선 네 기능 정산 뒤에 한 번 열린다. `settleGovernanceMonthly(view, tick)`은 `tick !== monthlyTick + 10000`이면 예외를 낸다. 같은 달을 두 번 돌리거나 한 달을 건너뛰어도 예외다. 단계 안의 순서는 고정한다.

1. `reconcileGovernance`로 폐위·직위 해임·관계 해제를 정리한다.
2. `pendingRenounce`를 해제한다.
3. 기한이 지난 제안을 지우고 NPC가 받은 제안에 응답한다.
4. 공납과 봉록을 이체한다.
5. 정통성을 `nationId` 오름차순으로 계산하고 0..100으로 자른다.
6. NPC 군주의 즉위를 판정한다(`userId === null`일 때만).
7. NPC가 새 제안을 낸다. 사람이 받은 제안은 다음 입력을 기다린다.
8. 쿨다운이 지난 키를 지운다. `monthlyTick = tick`을 쓰고 `revision`을 올린다.

### 경제 불변식
공납은 금 1·7월, 쌀 4·10월에만 매긴다. 기준 잔액은 단계 진입 때의 `settled`에서 잡은 봉신 수도 도시 원장의 스냅숏이다. `vassalId` 오름차순으로 `want = min(floor(snap × bp / 10000), 100000)`, `paid = min(want, 현재 출처 잔액, CITY_RESOURCE_MAX − 현재 도착 잔액)`을 계산한다. 여러 봉신이 같은 수도로 보내도 넘치지 않는다. 다단 봉신은 자기 스냅숏 기준이라 이번 달 받은 공납이 위로 다시 넘어가지 않는다. `paid < want`이면 `TRUNCATED`와 두 값을 효과에 남기며 빚이나 이월은 없다. 출처 수도를 잃었거나 도착 수도를 잃었거나 면제 기간이면 `SKIPPED`다.

봉록은 직위 순서대로 거점 도시 원장의 금에서 `General.gold`로 전액만 지급한다. 거점 금이 모자라면 `SEAT_SHORT`, 받는 쪽이 32비트 상한을 넘으면 `HOLDER_FULL`로 건너뛴다. 이 단계는 `Nation.gold/rice`, `General.rice`, 물류 재고를 바꾸지 않는다.

이체 한 건은 `−출처`, `+도착` 두 행이다. `GovernanceMovement(worldId, sequence, ordinal, tick, kind: TRIBUTE|STIPEND, refId, holder: city|general, holderId, resource: gold|rice, delta, fromNationId, toNationId)`를 상태와 같은 SQL 트랜잭션에 쓰고 PK는 `(worldId, sequence, ordinal)`이다. `assertGovernanceConserved`는 단계 진입 `settled`와 단계 직후 상태만 비교한다. 보유처 × 자원마다 실제 증감은 그 보유처 행의 합과 같아야 한다. 행이 없는 보유처는 0이어야 하고 전체 행 합도 0이다. 월 세수나 다른 명령의 금·쌀 변화는 governance 원장에 넣지 않는다. 그래서 과거 governance 원장 합을 현재 도시 금과 맞추는 검증은 하지 않는다. 대신 행을 그 달 월 효과·입력 결과·sequence와 건별로 대조한다. 원생성 archive 재생으로 같은 행이 나오는지도 확인한다.

### 전쟁 불변식
같은 봉신 계열은 한 최상위 국가 아래의 모든 국가다. 수락으로 두 계열이 합쳐질 때 서로 다른 계열에 속한 두 나라 중 한 쌍이라도 `WAR`나 `DECLARED`면 `REALM_AT_WAR`로 거부한다. 기존 전쟁을 동의 없이 평화로 바꾸지 않는다. 재판정에서 계열 안의 전쟁을 발견하면 그 경로의 가장 아래 관계부터 고정 순서로 해제한다.

`createGovernanceCommandResolver(base)`를 `ruleCommands.ts`의 가장 바깥에 둔다. `get`·`list`가 돌려주는 정의의 `check`·`precheck`·`execute`와 resolver의 실행·사전 판정을 모두 감싼다. `governance-v1`이 켜진 월드에서는 resolver가 늘 정의되도록 `undefined` 조건에 넣는다. 대상이 같은 봉신 계열이면 `nation_declare`, `attack`(일반·부곡), 계략 `fire_attack`·`sabotage`·`incite`·`plunder`가 `VASSAL_BOUND`를 낸다. 이 래퍼 대상 집합은 소스에서 확인한 키로 고정해 시험으로 묶는다. G0에서 등록표와 정의 실소비처 전체를 다시 확인한다. 래퍼는 기존 `createCityResourceCommandResolver`(`cityResources/commands.ts:61-159`)의 모양을 그대로 따른다. 정의의 `check`·`precheck`는 `VASSAL_BOUND` 실패 값을 돌려준다. 정의의 `execute`는 반환형 `CommandResult`를 바꾸지 않는다. 먼저 `check`를 다시 불러 실패면 예외를 던진다. 통과하면 감싼 정의의 `execute` 결과를 `applyEffects(cloneWorld(view), effects)`로 적용하고 그 상태를 `reconcileGovernance`로 정리한 뒤 world 효과 하나로 돌려준다. 정리 결과의 `assertGovernanceFinal`은 도시 자원 래퍼가 끝 상태를 `readCityResourcesState`로 검사하는 자리에 둔다. 실패를 값으로 돌려주는 곳은 지금처럼 resolver의 `precheck`·`run`뿐이다. `run`은 인자 실패, `check` 실패, `execute` 결과 순서로 돌려준다. 실패를 결과로 돌려주는 새 `execute` 형식은 만들지 않는다. `operation/suggest.ts`는 선택 인자로 resolver를 받는다(화면 경고용). 예약 턴, 직책 칸 턴, 휘하 지시 READY, 대기 중인 `governance.act`는 실행 시점 상태로 다시 판정한다.

`reconcileGovernance`는 순수 함수다. 명령 실행 뒤, `afterAppliedInput` 뒤, 월 정산 첫 단계에서 같은 함수를 부른다. 정리할 것이 실제로 있을 때만 `revision`을 올린다. 같은 상태로 두 번 불러도 추가 변경이 없다. 판정은 지금 존재하는 상태만 본다. 황제는 장수 행 없음, 미등장, 소속 변경, 군주 아님, 국가 멸망, 거점 상실, 황제국의 봉신화 가운데 하나면 폐위되고 세 직위와 미결 조정 제안도 함께 정리한다. 직위 보유자는 장수 없음, 미등장, 황제국 계열 이탈, 본인 즉위 때 해임된다. 관계는 수락 때 기록한 양쪽 군주 id가 현 군주와 다르거나 한쪽 국가가 멸망하면 해제한다. 그 군주가 낸 미결 제안도 지운다. 제안은 `OWN`이면 `sourceMonarchId`가 출처 국가 현 군주와 다를 때, `EMPIRE`면 황제국이 바뀌었거나 발신 `actorId`가 더는 황제나 승상이 아닐 때 지운다. 입력은 구조만 맞으면 받는다. 정리 결과에는 `assertGovernanceFinal`을 건다.

### NPC 판정
NPC 군주 국가를 `nationId` 순으로 보며 난수를 쓰지 않는다. 입력은 공개 도시 수, 공개 정통성, 고정 bp뿐이고 병력·금·쌀·비공개 원장은 읽지 않는다. 강한 쪽은 내 도시 수 ≥ 상대 × 2이고 정통성이 같거나 높으면 `DEMAND`를 낸다. 약한 쪽은 반대 조건의 상대 가운데 도시 수 내림차순·`nationId` 오름차순 첫 국가에 `REQUEST`를 낸다. 한 국가는 한 달에 한 건, 같은 상대에게는 쿨다운 안에 다시 내지 않는다. 수락도 같은 비율·정통성·bp ≤ 1000 조건이다. NPC 제안도 `decideGovernanceAction`을 통과해야 한다. 상대가 사람이면 그 사람의 명시 수락만 받는다. NPC 황제의 빈 직위는 자국 NPC 장수 중 직책 높은 순, 같으면 id 순으로 채운다.

## 검증

### rules
- 같은 달 두 번, 한 달 건너뜀, 범위 밖 입력 tick이 예외다.
- 세수 달의 공납 기준이 단계 진입 `settled`다. 상한 근처 수도로 여러 봉신이 보내면 `TRUNCATED`, 32비트 근처 장수는 `HOLDER_FULL`이다.
- 총량은 같고 다른 보유처로 옮긴 변조를 보존 검사가 잡는다.
- 순환, 자기 종속, 깊이 초과(하위 트리를 거느린 국가의 수락 포함), 이중 상위·재소속, 황제국 봉신화, 직책 11·다른 나라 군주·남의 수락 위조를 거부한다.
- 권한 문맥: 임의 출처 국가 필드 거부, `EMPIRE` `REQUEST` 거부, 자국 군주 겸 승상의 두 문맥 선택, 승상 해임·황위 변경·출처 군주 교체 뒤 수락 거부. 승상 해제·사도 면제는 다른 영주의 관계에 닿지 않는다. 황제는 면제·견책을 직접 할 수 있다.
- 다른 명령이나 앞선 월 정산이 거점 상실, 군주 교체, 국가 멸망을 만든 상태에서 `reconcileGovernance`가 던지지 않고 정리한다. 같은 정리 전 상태는 `assertGovernanceFinal`에서 실패하고 정리 뒤 상태는 통과한다.
- 계열 병합의 `REALM_AT_WAR`. NPC chooser, policy, turn run, campaign order, 서버 turns·nationCommands·officeSlots, 예약 실행 모두에서 같은 봉신 계열 공격이 `VASSAL_BOUND`다.
- 폐위·해임·해제 조건 하나하나와 `reconcileGovernance` 두 번 호출의 무변화.
- NPC가 난수를 쓰지 않고 금지 필드를 읽지 않으며 사람에게 자동 수락하지 않는다.
- 상한을 채운 300개월 무작위 진행에서 state JSON 크기가 상한식 이하이고 만료 키가 남지 않는다. 번호 한도의 `LIMIT`.
- 구버전 회귀: 기능을 끈 월드(구판과 city-resources·logistics 판)의 결과·해시·RNG 소비가 기존 fixture와 같고 `monthlyOrder` 배열을 고정한다.

### PG 통합
- 저장된 `monthlyTick`이 World와 다르면 로드 실패, 꺼진 월드에 값이 있으면 로드 실패.
- 두 상위 국가 제안의 동시 수락에서 두 번째가 `ALREADY_VASSAL`, 접수와 실행 사이 군주 교체는 `REJECTED`.
- 상태와 원장 행을 함께 롤백, 커밋 뒤 실패를 롤백했다고 주장하지 않는다. 엔진 재시작 뒤 `PENDING` 처리.
- 원장 행과 월 효과·입력 결과·sequence 건별 대조, 원생성 archive 재생 해시 일치, 두 월드 격리.
- 새 열이 기존 월드에서 null이고 새 표가 비어 있음을 확인한 뒤 기존 행·골든·archive를 대조한다.

### HTTP (실제 서버)
무인증, 전역·월드 제재, 다른 사용자, `NOT_PARTY`, 정산 경계 409, 같은 요청 재전송, 같은 키 다른 payload 409, 기능을 끈 월드의 `PRECONDITION_FAILED`. 다른 사용자에게 제안 본문·세율·면제·원장·잔액이 보이지 않는다. 봉록 수령 장수에게는 자기 입금 행만 보이고 거점 잔액·다른 지갑·공납 행은 보이지 않는다.

### 브라우저 (실제 PG·HTTP)
사람 생성·건국 뒤 `REQUEST`·`DEMAND` 양방향 제안과 명시 수락, NPC 제안이 사람에게 도착, 월 진행 공납, 같은 봉신 계열 공격 거부, 즉위 버튼, 직위 제안 수락과 효과, 군주 교체로 관계 해제, 멸망 정리를 본다. 375·1440px, 키보드 조작, 재접속도 확인한다.

### CF (AC-P2-35)
CF 담당이 같은 순수 규칙과 DTO로 WorldDO 어댑터를 맞춘다. 상태·원장 행·멱등키는 한 DO 트랜잭션에 쓰고 D1과 DO를 한 트랜잭션으로 가정하지 않는다. 같은 fixture를 실제 workerd에 넣어 응답, 오류 코드, 409·멱등, 상태 해시, 재생을 PG와 대조한다. PG 통과를 CF 증거로 세지 않는다. 128MiB 메모리, 정식 491명 전체 기수, CF 통과는 측정·실행한 값만 기록하고 그 전에는 충족을 주장하지 않는다.

물류 모양을 그대로 따릅니다. 공통 추상화는 새로 만들지 않습니다.

```ts
type GovernanceIdentity = { userId: string; sessionId: string };
interface GovernanceWorld { id; status; clockTick; monthlyTick; replayFormat; ruleFeatures; replayOrigin }
interface GovernanceRequest { kind: 'governance.act'; idempotencyKey; generalId: number|null;
  status: 'PENDING'|'APPLIED'|'REJECTED'; sequence: number|null; tick: number|null; payload; result }
interface GovernanceSnapshot { authenticated; sanctioned; world: GovernanceWorld|null;
  state: WorldView|null /* 구조 검사만 한 상태 */; previous: GovernanceRequest|null }
type MovementQuery = { holder: 'city'|'general'; holderId: number;
  kinds: readonly ('TRIBUTE'|'STIPEND')[]; creditOnly: boolean };
type GovernanceAdmission = { enqueue: false } | { enqueue: true; generalId: number; payload: GovernanceActPayload };
interface GovernanceStore {
  read(id, worldId, select: (s: GovernanceSnapshot) => readonly MovementQuery[])
    : Promise<{ snapshot: GovernanceSnapshot; movements: readonly GovernanceMovementRow[] }>;
  request(id, worldId, requestId): Promise<GovernanceSnapshot>;
  submit(id, worldId, requestId, decide: (s: GovernanceSnapshot) => GovernanceAdmission): Promise<GovernanceRequest>;
}
```

- `read`
  - RepeatableRead 트랜잭션 하나에서 세션을 확인하고 상태를 읽습니다.
  - 그다음 `select(snapshot)`가 돌려준 조건으로만 원장 행을 조회합니다.
  - 조회 조건은 순수 함수 `governanceMovementScope(state, viewerGeneralId)`(rules `visibility.ts`)가 만듭니다. 공개 범위 판단은 rules에 둡니다. 어댑터는 받은 조건대로 실행만 합니다.
- `submit`
  - 순서: 세션 확인 → `World FOR UPDATE` → 세션 재확인 → 전역·월드 제재 → 멱등키 `governance:<uuid>` 조회 → `decide`(동기) → `InputEvent PENDING` + `general.active` 기록.
  - 위 순서 전체가 한 트랜잭션입니다. 물류 `pgStore.ts:115-137`과 같습니다.
- `decide`는 서비스가 넘기며 내부에서 다음을 처리합니다.
  - 인증·원생성 대조·제재 검사
  - 같은 키 같은 payload는 재전송, 다른 payload는 `CONFLICT`
  - `RUNNING`이 아니면 `PRECONDITION_FAILED`
  - `clockTick >= monthlyTick + TICKS_PER_MONTH`이면 `CONFLICT`(정산 경계 409)
  - 행위 장수는 세션 사용자의 장수로 고정
  - rules `decideGovernanceAction`
- tRPC 등급: `submit`은 `worldVerifiedProcedure`, `get`·`request`는 `protectedProcedure`(물류와 같음).
  - 미들웨어의 제재 검사는 빠른 차단용입니다. 최종 판정은 잠금 안에서 다시 합니다.
- 오류 코드 표는 물류와 같습니다(UNAUTHORIZED, NOT_FOUND, FORBIDDEN, BAD_REQUEST, CONFLICT, PRECONDITION_FAILED). CF 대조 기준으로 고정합니다.

### 5. 엄격 의미 검사의 위치 (기존 61·116줄 보정) [제안]

위험: 엔진 훅 호출 순서는 정렬 규칙이 아니라 엔진 배열의 위치로 정해집니다. governance 항목을 잘못된 위치에 넣으면 재생 해시가 갈라집니다. 5장의 훅 순서 시험이 이 위치를 고정합니다.

## 구현 검증 보충

- 새 이체 행의 `fromNationId`와 `toNationId`는 당시 당사국이다. 계약이 끝나거나 도시가 함락돼도 과거 이체의 열람 범위를 현재 도시 소유국으로 바꾸지 않는다. 공납 원장은 당사국의 현재 군주가 본다. 봉록 원장은 지급국 군주가 본다. 수령 장수 본인은 자기 양수 입금만 본다. 수령국의 다른 군주에게 개인 봉록이나 황실 출금 행을 공개하지 않는다.
- 승상·사도는 자기 국가가 하위 당사국이거나 그 아래 후손인 가지의 해제·면제를 대행하지 못한다. 상위 가지를 풀어서 이탈 대기·정통성 비용을 우회하는 경로도 막는다. 황제의 면제 권한과 각 상위 군주의 자국 계약 해제 권한은 유지한다.
- NPC는 공개 정보로 정렬한 후보 가운데 실제 행동 판정을 통과하는 첫 상대에게만 월 한 건을 제안한다. 첫 후보가 이미 봉신이거나 전쟁 중이어도 다음 유효 후보를 살핀다. 보낸 제안 상한에 닿은 국가는 후보 반복을 시작하지 않는다.
- 기존 `worldLoader.ts`와 서버 `game/queries.ts`는 이미 읽은 World 행을 순수 `readStoredGovernance`에 전달한다. 새 SQL을 넣지 않는다. 기존 `world/persistence.ts` 저장 어댑터에서 초기 JSON만 배정한다. 황실의 새 ORM·SQL·CAS·원장 쿼리는 `governance/repository.ts`와 서버 `governance/pgStore.ts`에 둔다.
- 엔진의 외부 queued 후처리는 인사 처리 전에도 실행된다. 새 사람의 거주 앵커를 요구하는 `loadReplayState` 대신 도메인 `loadWorld`만 읽는다. `campaign`의 전체 외부 입력 재생은 `governance.act`를 건너뛴다. 황실 본문에서 저장한 상태를 다시 CAS하지 않는다.
- 규칙 후처리는 등록된 route를 전달받는다. 황실은 queued 입력 뒤에만 정리한다. direct 입력에는 새 후처리를 적용하지 않는다. 기존 캠페인·인사 순서는 바꾸지 않는다.
- 실제 HTTP·PG·엔진 첫 검증은 17건이다. 두 사람의 생성·건국과 명시 즉위·계약·직위 동의를 거친다. 월 공납·봉록과 트랜잭션 롤백 및 새 엔진 재처리도 확인한다. 원생성부터 7개월을 재생한다. 정식 491명 전체 스케줄과 전체 기수 및 실제 CF 동등성의 완료 증거는 아니다.
- 프론트 코드는 Claude Code가 Artifacts 시안을 바탕으로 구현한다. Codex가 실제 검사와 독립 리뷰를 맡는다. `world.summary`의 선택 칸 `governanceEnabled`가 참일 때만 연결한다. 공식 기본 프로필은 활성화하지 않는다.


## 현재 검증 범위

- `pnpm check`: 410개 파일의 6,672개 시험을 통과했다. 확인창의 계정 전환과 내 계열·전체 계열 전환을 포함한 프론트 시험 19건도 통과했다. 변경한 화면과 저장·재생 연결부의 lint와 타입 검사도 통과했다.
- 실제 HTTP·PG·엔진 시험은 17건을 통과했다. 원생성부터 7개월의 상태 해시와 월 효과를 비교한다. DB 이체 행만 바꿔 도메인 잔액 해시를 유지해도 내보내기가 거부된다. API는 원장을 바꾸지 않는다.
- 기존 마이그레이션·제재·인증 접점의 실제 PG 시험 131건을 통과했다. 기존 원생성·해시·빈 새 칸을 보존하는 검증을 유지한다.
- 공개 빌드의 Chromium 화면 검증은 4건을 통과했다. 즉위·계약·직위 동의·봉록·대기 복구·계정 전환과 375·768·1440 폭의 다섯 탭을 확인했다. 이 화면 고정물은 원생성 NPC의 계정 연결과 일정을 통제한다. 사람 생성 증거는 별도의 HTTP 시험이며 정식 491명 전체 일정과 같은 증거로 쓰지 않는다.
- 원장 감사는 아카이브와 실제 이체 행을 같은 RepeatableRead 스냅샷에서 읽는다. 그 트랜잭션이 끝난 뒤 순수 재생과 행 비교를 한다. 긴 재생 동안 DB 트랜잭션을 열어 두지 않으며 아카이브의 전송 모양을 바꾸지 않는다.
- 확인창은 열었던 계정과 화면 세대에 묶는다. 화면이 지워지거나 계정이 바뀌면 확인창을 버린다. 렌더 전의 오래된 클릭도 ref의 화면 세대 재검사로 막는다. 처리 대기 중인 UUID와 내용은 유지한다.
- 독립 저장·API·재생 리뷰에서 지적한 긴 트랜잭션은 수정 후 재리뷰 OKAY를 받았다. 프론트는 구현하지 않은 Codex가 검토한다. 내 계열과 행동 가능한 관계를 앞에 둔다. 전체 공개 계열은 접힌 칸에서 키보드로 열어 보며 제안 입력을 보존한다. 이 사용성 보완까지 최종 검사에 포함했다.
- CF 실측과 필수 CI 및 병합은 아직 남아 있다. 공식 기본 프로필과 AC-P2-31·35 완료 상태는 바꾸지 않는다.
