### merge queue 준비 (2026-10-24, PR #231)

- 배경: main 보호 규칙이 최신 main 반영을 요구해, PR 하나를 병합할 때마다 나머지 PR이 모두 다시 동기화하고 CI를 처음부터 기다렸다. 2026-10-24 저장소를 `opensamguk/opensamguk` 조직으로 옮겼다. 그래서 조직 저장소에서만 쓸 수 있는 GitHub merge queue를 켠다.
- 바꾼 것:
  - `ci.yml`이 `merge_group` 이벤트를 받는다. 대기열이 만든 병합 결과에 필수 검사 `opensamguk-check`와 `opensamguk-database-browser`가 그대로 돈다. checkout과 `Verify source commit`은 `github.event.pull_request.head.sha`가 없으면 `github.sha`(대기열 병합 커밋)로 떨어진다.
  - 두 워크플로의 push가 main과 태그만 받는다. 작업 브랜치는 `pull_request` 실행이, 대기열 임시 브랜치 `gh-readonly-queue/**`는 `merge_group` 실행이 검사한다. 2026-10-24 오전에 PR 여럿이 동시에 push되자 CI가 커밋마다 push와 `pull_request`로 두 번 돌고 규칙을 바꾼 브랜치마다 180분짜리 시뮬레이션이 돌아, 조직의 동시 실행 한도 20개가 차고 실행 20건이 대기했다. 시뮬레이션은 필수 검사가 아니므로 main push와 `workflow_dispatch`에서만 돈다. 태그는 `tags: ['**']`로 예전처럼 받는다.
  - Playwright apt 캐시 저장 조건은 `github.event_name == 'push'`와 main이라 대기열 실행에서는 저장하지 않는다.
- 확인한 것: 두 파일을 YAML로 읽어 이벤트 목록과 push 필터를 확인했고 Prettier 검사를 통과했다. PR 이벤트 CI는 이 PR head에서 판정한다. `merge_group` 실행은 대기열을 켠 뒤에만 생기므로 이 PR에서는 확인할 수 없다.
- 대기열을 켠 뒤 확인할 것: 첫 대기열 항목에서 `merge_group` 실행이 두 필수 검사를 모두 보고하는지, `Verify source commit`이 대기열 병합 커밋과 맞는지, 작업 브랜치와 대기열 임시 브랜치에 push 실행이 생기지 않는지, 병합 뒤 main push 실행이 apt 캐시를 저장하는지 본다. 결과는 이 절 아래에 덧붙인다.
