# T4-93 철·목재·말·창고·수송망

현재 범위는 D-065에 따라 기존 레포의 PG·서버·엔진·웹이다. 아래 CF 이식·대조 항목은 이번 작업과 완료 조건에서 제외한다.

> 대기열: T4-93 · AC: AC-P2-30 · 구현: Codex(PG·rules) · 리뷰: Claude · CF 어댑터: Cloudflare 채팅

## 계획 (Claude)

### 목표
AC-P2-30 문장 그대로다. 새 판에서 철·목재·말의 생산/소비, 창고 용량, 거점 간 수송의 출발 차감·도착 가산·명시적 손실을 보존한다. 금·쌀과 병력은 이중으로 계산하지 않는다. 기존 월드 해시는 바꾸지 않는다.

### 코드에서 확인한 사실
- `city-resources-v1`(`cityResourcesFeature.ts`)은 `checkOrigin`에서 `data === undefined`를 강제한다. `cityResourceSchema`는 `strictObject{gold,rice,garrison}`이고 `version: z.literal(1)`이다. 이 스키마를 바꾸면 v1 월드의 파싱·기록 검증(`validateCityResourceRecord`)이 같이 바뀐다.
- `ext` 조각은 활성 *명령* 묶음(`extSliceKeysWithRegistry`)으로만 선택된다. `resolverForRuleFeatures`는 `sliceKeys`가 있으면 오류를 낸다. 그래서 규칙 기능 상태에는 `ext`를 다시 쓸 수 없다.
- 해시는 `hashState(replay)` 전체다. 선택 칸이 없으면 기존 해시는 그대로다. `cloneWorld`·`WorldState`는 칸을 하나씩 나열한다.
- 월 순서는 `runMonthly`(안에서 `applyCityResourceIncome`) → `settleMonthlyFeatures`(`monthlyOrder`) → 엔진 `persistMonthly` 훅이다.
- 장비는 아직 없다. T4-22 `equipment_trade`는 계획만 있고 U-06을 기다린다.
- T4-92가 `apps/web/src/turns/*`를 수정 중이다.

### 선택한 설계
1. 새 불변 규칙 기능 `logistics-v1`을 둔다. `requires: ['city-resources-v1']`이다. 진행 중 월드에는 켜지 않고 원생성에서만 켠다.
2. 정본 상태는 `WorldState.logistics?: LogisticsState`다. 새 열 `World.logisticsState Json?`에 저장한다(새 migration `2026111x_logistics_state`). 금·쌀은 계속 `cityResources`에만 있다. 이 상태는 세 재화, 창고 등급, 수송대만 가진다.
3. 초기 설정은 `featureData['logistics-v1']`에 고정한다. `checkOrigin`이 `logisticsConfigSchema`로 검사하고 특산 거점이 `initial.cities`에 있는지 대조한다.
4. 라우터는 새 `logistics` 라우터 하나로 한다(`cityResources` 확장이 아니다). 기존 `city.resources` 입력 종류와 기록 검증, v1 재생을 건드리지 않기 위해서다.
5. 새 규칙은 난수를 쓰지 않는다. 손실은 정해진 비율의 버림으로 계산한다. 그래서 기존 시드 RNG 흐름의 순서가 그대로다.
6. 새 범용 틀은 만들지 않는다. 기존 패턴을 그대로 복제·확장한다: `readCityResourcesState`, `persistCityResourcesState`, `processCityResourceInput`, `cityResourcesApi`, `createCityResourceCommandResolver` 래퍼, `CityResourcesPanel`.

### 데이터·계약

| 항목 | 모양 |

행 하나는 보유처(도시 또는 수송대) 하나만 가리킨다. 순수 함수 `assertLogisticsConserved(before, after, movements)`는 재화마다 보유처별 증감과 행 합계가 같은지 확인한다. 외부 유입·유출은 `PRODUCE·CONSUME·LOSS_*·TRADE·UPGRADE`뿐이다.

### 규칙
- **생산**: 매월 `settleLogisticsMonthly`에서 한다. 대상은 `nationId≠null`, `supplied`, `kind≠PASS`인 특산 거점이다. 생산량은 `floor(perMonth × population / populationMax)`다. 고정 순서는 ① 도착 판정, ② 생산, ③ 용량 초과분을 `LOSS_OVERFLOW`로 기록한다. `monthlyOrder` 맨 끝에 `'logistics-v1'`을 둔다. 세수 배분이 끝난 뒤라 금·쌀과 섞이지 않는다.
- **수송**: 경로는 출발 때 자기 국가 거점만 지나는 BFS로 고른다. 이웃은 `cityKey` 오름차순, 최대 `maxHops`다. 출발지 재고를 빼서 수송대에 넣는다(`DEPART`). 도착은 `arriveTick` = 출발 뒤 `ceil(hops/hopsPerMonth)`번째 월간 정산이다. 중간 위치는 없다. 군대 행군 상태를 되살리지 않는다.
- **도착 판정**(보존식):
  - 경로 전 구간과 도착지가 아직 같은 국가면 운송분에서 `floor(운송분×lossBp×hops/10000)`를 `LOSS_TRANSIT`로 빼고 나머지를 도착지에 넣는다(`ARRIVE`).
  - 경로가 끊겼거나 도착지를 잃었는데 출발지가 같은 국가면 출발지로 돌려보낸다(`RETURN`).
  - 도착지가 전쟁 중인 국가 소유면 도착지가 가진다(`CAPTURE`).
  - 그 밖에는 전량 `LOSS_TRANSIT`다.
  - 넣는 곳마다 용량 초과분은 `LOSS_OVERFLOW`다.
- **취소**: 출발지가 같은 국가일 때만 받는다. 즉시 출발지에 돌려주고 초과분은 손실로 기록한다. 이미 정산된 수송대 id는 거부한다.
- **점령**: 도시 재고는 도시에 남는다. D-040에서 금·쌀이 도시에 남는 것과 같다. 수송대는 도착 판정 때만 처리하므로 공격 명령 경로는 고치지 않는다.
- **창고**: 용량 = `base + level×perLevel`이다. `upgrade`는 그 도시의 `cityResources.gold`와 목재를 같은 상태 전이에서 뺀다.
- **소비**:
  - 모병·징병: 병종 `armType`별 `recruitPer100`을 `ceil`로 계산해 그 도시 재고에서 뺀다.
  - `wall`·`defence`: 장수가 있는 도시의 재고에서 뺀다.
  - 방식: `createLogisticsCommandResolver`가 기존 resolver를 감싼다. `check/precheck`에서 부족하면 `NO_GOODS`(Failure 코드 하나 추가)로 막고 `execute` 뒤 같은 `world` 효과에 차감을 반영한다. 기존 금·인구 비용은 그대로다.
- **NPC**: `cityNpcPreparation`의 모병 수를 재고 한도로 줄인다. 자동 매입·수송은 아래 L4 보완 계약을 따른다. 설정이 없는 월드는 기존 판단을 유지한다.

### 권한·접수·재검사·멱등
- 행위자: 서버 세션의 활성 계정, 자기 장수, 제재 없음, 등장 연도 지남. 국가 직책은 `nation_city_allocate`와 같은 `officerLevel 5~12`이고 대상 거점은 자기 국가 소유여야 한다.
- 접수: `submit`이 `cityResourcesApi.submitCityResourceRequest`와 같은 순서로 처리한다. 세션 → `ready()` 기능·origin 대조 → 제재 → 멱등키 `logistics:<uuid>`(같은 키에 다른 payload면 CONFLICT) → `RUNNING` → `applyLogisticsInput(readView)`로 미리 판정한다. 접수 단계는 `PENDING` 행과 `general.active`만 쓰고 상태는 바꾸지 않는다.
- 엔진: `processLogisticsInput`이 같은 리스·World 잠금 안에서 사용자 `FOR SHARE`, 장수 `FOR UPDATE`를 잡고 다시 판정한다. 그다음 상태·원장 행을 한 트랜잭션에 쓴다. 판정이 바뀌었으면 `REJECTED`다.

### 호환
- `world.ts`·`clone.ts`에 `logistics` 선택 칸을 더한다. 꺼진 월드에는 칸이 없다.
- `readStoredLogistics`: 기능이 꺼진 월드에 값이 있으면 오류다.
- `assertStoredLogistics`: `capsGate.ts`·`replay.ts`에서 호출한다.
- `worldLoader`·`commandPersistence`·`monthly`에 `persistLogisticsState`를 연결한다. 조건부 UPDATE(이전 JSON 일치)로 쓴다.
- `world/persistence.ts`: 생성 때 `initialLogisticsState`를 쓴다.
- `initReplayState`: 중복 초기화를 거부한다.
- `checkArchive`: 기록 모양·수량을 검사한다.
- 리셋은 기존 `featureData` 사본 경로를 쓰고 상태를 다시 초기화한다.

### 조회·화면
- 자기 국가: 소유 거점별 재고·용량·등급, 자기 수송대, 최근 원장 행.
- 원장 열람: 창고의 최근 수불 내역은 D-040의 거점 재고와 함께 거점에 남는다. 점령 뒤 현재 소유국 구성원은 이전 소유자의 해당 거점 수불도 최근 50행까지 본다. 소유권이 바뀌면 이전 소유국은 그 원장을 볼 수 없다. 국가 수송대는 계속 해당 수송대 국가에만 공개한다.
- 다른 국가: 특산 표시만 보인다(`visibility(actor).city`). 재고와 수송대는 숨긴다.
- 화면: `apps/web/src/main/LogisticsPanel.tsx`를 새로 만들어 `CityInfo.tsx`에서 `CityResourcesPanel` 아래에 붙인다. 요청 처리는 `logisticsRequest.ts`가 `cityResourceRequest.ts`와 같은 방식으로 한다. 패널 내용은 재고 막대, 보내기 폼(도착지·수량·예상 도착월·손실), 수송대 목록과 취소, 증축, 비용표다.
- `turns/*`는 T4-92 병합 뒤 모병 미리보기 한 줄만 따로 고친다.

## 기술 검토 (Codex)

2026-11-02 다음 보정을 포함해 코어 구현을 채택한다. 프론트는 Claude Code가 아티팩트로 설계·구현하며 Codex는 순수 규칙·엔진·API·PG 저장과 통합을 맡는다. HTTP 입력·응용 처리·순수 규칙·저장 어댑터의 의존 방향을 지킨다.

- 원생성의 `featureData`에서 검사한 설정을 `logistics.config`에 복사해 월간·명령도 같은 고정값을 사용한다. 로드/내보내기에서 origin과 대조하고 진행 중 설정 변경을 거부한다.
- `monthlyTick`을 상태에 보존한다. 다음 월 경계에서만 한 번 정산하며 수송 도착 시점도 같은 tick 단위다. 생산·가격·손실 곱셈은 정수 계산으로 안전한 수 범위를 넘지 않는다.
- 창고 용량은 철·목재·말 합계다. 도착 화물은 철·목재·말 순서로 남은 공간에 넣고 초과분을 손실로 적는다. 금·쌀은 기존 원장과 전송 계약을 유지한다.
- 도착 순서는 정상 도착, 적대국 도착지의 노획, 자기 출발지 반환, 전량 손실이다. 각 재화의 도시/수송대별 증감과 기록을 함께 대조한다. 경로는 고정 지도 연결을 따라 보급된 자기 거점만 지나는 최단 경로다.
- 특산표는 새 월드 생성의 명시적 설정이다. 실제 프로필 게시에 쓸 거점표는 별도 검수하고 코어·저장·재생은 설정 가능한 표와 시험 거점으로 먼저 검증한다. 임의로 기존 월드에 적용하지 않는다.
- 장비 소비는 T4-22와 연결할 후속이며 빠진 상태로 AC를 완료로 바꾸지 않는다. 초기 생산·수송 코어의 통과를 자원 확장 전체 완료로 세지 않는다.
- `LogisticsMovement`는 도시/수송대 구분·보유처 ID·재화·증감·이유를 저장한다. 월 정산/입력의 기존 action sequence와 ordinal을 고유 키로 쓴다. 상태와 기록은 같은 DB 트랜잭션에 쓴다.

## L4 NPC 보완 계약 (Claude 계획·Codex 기술 검토)

원생성 물류 설정의 선택 필드 `npc`로만 켠다. `recruitTarget`은 100~2000명 중 100의 배수이고 `maxActions`는 1~3이다. 예산·재고 목표·증축 기준은 각각 `budgetBp`, `stockCapBp`, `upgradeAtBp`로 1~10000을 받는다. 기본값을 만들거나 기존·공개 프로필에 설정을 추가하지 않는다.

- `Nation.isNpc`이고 등장한 군주가 NPC 1명인 국가만 자동 지출한다. 모집 대상은 자기 보급 거점의 전선 NPC다. 다른 국가 방문 장수와 휘하는 제외한다.
- 병종·도시 모집 한도와 전선 판정은 기존 NPC와 함수를 공유한다. 기존 명령의 우선순위와 실제 모집 인원 계산을 유지한다. 모집 한도가 100명 미만이면 남은 인원에 공통 재료 올림 비용을 적용한다.
- 월 생산·도착 뒤 수요를 계산한다. 도착 예정 화물을 빼고 재화별 여분을 보낸다. 같은 단계에서 화물을 받을 도시는 같은 재화를 다시 보내지 않는다. 거점·재화·출발 후보는 월에 따라 회전한다.
- 국가별 실제 전이 호출과 부족 후보 검사는 각각 `maxActions` 이하다. 거부도 호출 수에 센다. 후보당 두 출발지의 경로를 확인하고 실제 수송 전이에서 다시 검사한다. 도시·장수·부곡·도착 예정 화물 표는 먼저 만든다.
- 도시 진입 금의 예산 안에서 모집금을 남기고 교역한다. 필요한 공간을 확보할 때만 다른 수요에 쓸 여분을 남겨 매도한다. 매도금은 예산을 늘리지 않으며 같은 달 같은 재화를 매입·매도하지 않는다. 증축은 국가당 한 번이고 실제 도시 금과 목재를 쓴다.
- D-069의 새 선택판은 `treasuryBudgetBp` 1000을 원생성에 고정한다. 그 달의 자동 매입과 증축 지출을 국가의 모든 도시에서 합산해 정산 시점 국고의 10% 이하로 제한한다. 실제 지출은 도시 금에서 나가며 도시별 예산과 모집금 조건도 적용한다. 이 설정이 없는 판은 기존 도시별 예산을 쓴다.
- 사람과 NPC는 내부 공통 전이를 쓴다. 사람의 계정·직책·입력 검사는 기존 접수 경로에서 수행한다. NPC에 사람 행위자를 만들지 않는다. 공통 전이는 패키지 공개 진입점에 추가하지 않는다.
- NPC 원장은 기존 월 sequence의 `DEPART`, `TRADE`, `UPGRADE` 행으로 저장한다. 월드 JSON에 이력을 쌓지 않는다. 정산 효과는 `{movements}`를 유지하고 NPC가 성공한 달에 revision을 한 번 더 올린다.
- 생산·도착 뒤 상태를 기준으로 재료 보존, 도시별 금·증축 원장, 쌀·수비병·다른 월드 상태의 보존과 기존 수송대·번호 연속성을 대조한다. 증축 목재는 1 이상이므로 비용 행이 항상 있다.

실제 PG에서는 월 매입 뒤 NPC 차례의 모집, 후방 생산·수송·도착 손실·보충 뒤 모집, 저장 후 롤백·새 연결, 순수 월 효과와 원장 ordinal, 원생성 재생 해시를 검증한다. 고정물의 NPC 경쟁과 일정을 통제한 증거이며 정식 491명·전체 기수·CF 동등성·128MiB 성능 증거로 세지 않는다.

## 구현 기록 (Codex)

2026-11-02 규칙·저장·엔진 코어를 구현했다. `logistics-v1`은 새 origin에서 `city-resources-v1`과 함께 명시적으로 켠다. 고정 설정·빈 재고, 생산, 창고 용량·증축, 교역, 결정적 수송·취소·도착·반환·노획·손실, 보유처별 원장과 기능 없는 기존 해시를 보존한다. 응용 서비스는 SQL 없는 저장소 포트를 쓰며 PG 어댑터가 같은 엔진 트랜잭션에서 금·재고·원장을 한 번 쓴다. 입력 결과·순번 마감과 인사 후처리는 기존 엔진에 둔다.

검증: `pnpm check` 385파일·6488시험 통과. 물류 순수 시험은 19건이고 실제 전용 PG 통합 9건은 별도로 실행해 통과했다. PG 시험은 생성·빈 상태·설정, 같은 트랜잭션 롤백, 동시 CAS, 재접속, 실제 큐의 적용/재고 경쟁 거부, 실제 수송 도착, 교역 금·재고·원장·입력·순번의 실패 복구, 접수 뒤 권한 상실, 원장 삭제 탐지, 첫 월의 원생성 archive 재생 해시를 확인했다. 마지막 고정물·주석 변경 뒤 포맷·엔진 타입·ESLint·diff 검사도 통과했다.

큐 시험은 원생성 뒤 기존 NPC를 시험 계정에 연결하고 활동·거주 앵커를 갖춘 앞사본에서 재생한다. 이 증거를 실제 사람 생성·건국·임관의 원생성 재생으로 세지 않는다. 별도 원생성 archive 시험은 첫 월 생산만 검증한다. 조정한 NPC 차례 시각도 origin에 고정했으므로 정식491명·전체 기수의 검증은 아니다.

이 코어의 범위에는 HTTP·조회·화면과 모병·건설·장비 소비가 없었다. 실제 프로필의 특산표 게시와 기존 월드 전환은 하지 않았다. AC-P2-30·35는 미완료다.

### HTTP 접수·조회 (Codex, 2026-11-03)

`logistics.get/submit/request`를 추가했다. HTTP 어댑터는 입력·오류 변환만 하고 응용 서비스는 DB 없는 포트로 판정한다. PG 저장소가 World 잠금 아래 세션·현재 상태·멱등 키를 읽고 서비스의 동기 판정 뒤 입력과 활동만 함께 접수한다. Cloudflare 담당과 같은 동기 판정·저장소 원자성 계약을 협의했다. 앱 간 import나 새 범용 transaction 틀은 없다. 원생성 설정 판독은 rules의 순수 함수로 옮겨 엔진·조회가 같이 쓴다.

자기 국가 거점의 재고·용량·소비 설정·수송대·최근 원장·경로별 도착월과 손실률을 조회한다. 다른 국가 거점은 현재 물리적으로 있는 곳의 특산만 보며 재고·수송대·원장·가격은 숨긴다. 사람의 행위자는 세션에서 찾는다. 전역 제재·만료는 401이고 월드 제재는 쓰기를 403으로 막되 자기 읽기는 허용한다. 같은 번호의 다른 입력은 409다. 접수 시점과 엔진 실행에서 다시 판정한다.

실제 전용 PG·HTTP의 새 6건과 코어 PG 9건을 함께 실행해 15건이 통과했다. 새 시험은 실제 사람 생성→건국→생산→교역/증축→두 월 원생성 archive 재생 해시, 동시 재전송·계정 변경·위조 필드, 세션·전역/월드 제재·권한 상실, 다른 사용자에게 특산만 공개, 세 경로×다섯 권한 범주의 상태 불변을 확인했다. 월 정산 대기 때 새 접수는 409로 거절한다. 정산 뒤에는 같은 요청 번호를 접수한다. 이 경계 시험의 직접 clock 변경은 원생성 재생 증거에서 제외한다. 인증 계정·세션은 시험 DB에 준비하고 장수·건국·물류는 실제 HTTP·엔진을 거친다. 사람 생성·건국 경로는 NPC 바인딩으로 사람을 만들지 않았다. 조정한 NPC 차례는 여전히 origin에 기록하므로 정식491명·전체 기수 증거는 아니다.

HTTP 단계의 전체 검사 389파일·6,509건이 통과했다. 첫 검사에서 발견한 인증 변경 경로 목록 누락은 `logistics.submit`을 명시 등록해 고쳤다. Claude 독립 리뷰가 발견한 정산 중 500과 ETA 불일치도 고쳤으며 재리뷰는 현재 HTTP 증분을 통과로 판정했다. 월드 요약은 물류 판에만 `logisticsEnabled`를 제공한다. 목적지의 `freeCapacity`는 조회 시점의 여유이며 도착 시점의 보장이 아니다. 화면·실제 소비처·NPC 물류·CF 어댑터와 실제 양 런타임 동등성은 남아 있다. 해당 내용 없이 AC를 완료로 바꾸지 않는다.

## 모집·건설 소비 계획 (Claude, Codex 검토)

Claude는 실제 명령·NPC·저장 경로를 읽고 소비 계획을 작성했다. Codex 검토에서 두 조건을 보정했다. 한 차례의 개인·국가 명령을 합산하므로 소비가 있으면 revision이 증가해야 하며 정확히 1만 증가한다고 가정하지 않는다. 실패한 명령은 경제 상태와 RNG를 바꾸지 않는다. 로그·예턴 이동·sequence는 기존 실패 처리대로 진행한다.

`recruitPer100`은 원생성의 모든 군사 병과 비용을 명시한다. 무료 병과도 세 재화를 0으로 쓴다. 모병·징병은 실제 인원을 100명 단위로 올림한 비용을 쓴다. 성벽·수비는 성공 명령 한 번의 고정 비용을 쓴다. 상한에서 잘리거나 상승량이 0인 성공도 비용을 쓴다. 최대치·재고 부족으로 실패하면 소비가 없다. 비용 안내와 예약 전 검사는 기존 금 부족 검사와 같은 시점을 따른다.

규칙은 순수 소비 함수, 도시 모집 분기, 기존 건설 효과 앞의 물류 상태, NPC 모집 한도에만 연결한다. 엔진은 일반 차례의 최종 상태에서 도시별 음수 `CONSUME` 행을 한 번 계산하고 상태와 같은 트랜잭션에 저장한다. 수송·교역 입력의 원장 경로는 유지한다. 한 차례에 소비가 둘이면 같은 sequence의 서로 다른 ordinal로 합산한다. 일반 명령은 수송대·등급·설정·월 tick을 바꿀 수 없다. 금·쌀은 기존 도시·장수 지갑의 소비 경로를 유지하며 물류에 복제하지 않는다.

Codex의 구현과 실제 PG 저장·롤백·원생성 재생, Claude 독립 리뷰를 거친다. 장비 시스템·소비, NPC 수송, 화면 비용 안내, 기본 프로필, CF 실제 검증은 후속이다. 이 계획은 전체 AC 완료를 뜻하지 않는다.

현재 소비 증분의 전체 검사는 390파일·6,531건이 통과했다. 순수 규칙의 집중 검사는 48건이다. 실제 PG·HTTP·엔진 17건은 사람 생성·건국 뒤 기병 101명 모집·징병·성벽·수비, 철·목재·말 소비 원장과 실제 지갑·인구·수비병, 다섯 월의 원생성 재생 해시를 확인했다. SQL 저장 뒤 트랜잭션 안의 `beforeCommit` 실패는 원장·재고·금·도시·예턴·로그·순번을 함께 롤백했다. 새 엔진 객체가 같은 차례를 한 번만 처리했다. 커밋 뒤 실패를 롤백했다고 주장하지 않는다.

새 물류 migration을 기존 다섯 시험의 명시 목록에 등록했다. 새 열은 기존 월드에서 null이고 새 원장은 비어 있음을 따로 검사한 뒤 기존 행·골든·archive를 대조한다. 실제 PG의 해당 마이그레이션·확장 명령 회귀 37건이 통과했다. 기존 CI의 엔진 228통과·27건너뜀은 실패 결과다. 이를 전체 255건 통과로 합산하지 않는다. Claude 독립 재리뷰는 소비 코드와 이 시험 보완을 통과로 판정했다. 필수 CI와 정상 병합은 별도로 통과해야 한다.

## 도시 물류 화면 (Claude, Codex 검토)

새 물류 월드의 도시 정보에 창고·특산, 보내기, 수송대 취소, 증축, 교역, 최근 수불과 모병·투자 비용을 붙였다. 다른 국가는 특산만 본다. 직책이 낮으면 지시를 막는다. 병종 이름은 해당 월드의 검증한 병종표에서 온다. 비용 미리보기는 E4의 공개 순수 함수 하나를 쓴다. 최종 소비는 엔진에서 다시 판정한다.

응답을 잃은 요청은 같은 번호·내용으로만 수동 복구한다. 조회에서 404가 왔다고 접수 중인 요청을 버리거나 새 번호를 만들지 않는다. 재조회 오류에는 입력을 보존하고 새 지시를 잠근다. 계정 변경·인증/권한 상실·화면 이탈 때는 민감한 화면을 정리한다. 수송 취소 확인은 Escape로 닫고 원래 단추에 초점을 돌려준다.

Claude의 아티팩트와 실제 화면을 Codex가 검토했다. 운영 기동·인증 검증 보완을 합친 전체 검사 397파일·6,585건과 공개 빌드가 통과했다. 실제 공개 빌드·PG·HTTP·엔진·Chromium 4건은 수송/취소/99개 도착/교역/증축, 새로고침, 응답 유실 뒤 같은 번호 재접수, 재조회 오류의 입력 보존, 직책·타국 정보 가림, 375·768·1440px와 큰 수의 비용 미리보기를 확인했다. 이 화면 고정물은 origin에 기록한 NPC 일정, 시험 계정 연결·위치, 긴 병종 이름과 최대 비용을 통제했다. 실제 사람 생성·정식491명·전체 기수·CF 증거로 세지 않는다.

CI에서는 공개 빌드 뒤 네 번째 브라우저 묶음에서 `pnpm e2e:logistics`를 실행한다. 일반 개발 서버 묶음에서는 같은 파일을 제외해 빌드 전에 실행하지 않는다. 이 연결은 다른 담당의 독립 리뷰와 실제 4건 수집 확인을 통과했다. 필수 CI·정상 병합은 별도로 확인한다. 장비 소비, NPC 물류, 기본 프로필과 양 런타임의 실제 동등성은 남아 있다.

### NPC 물류 추가

선택 설정과 공통 전이, 수요별 자동 매입·수송·매도·증축을 연결했다. 설정을 빼면 JSON에 `npc` 키를 만들지 않고 기존 정산 상태를 그대로 돌려준다. 전체 수송대 상한도 사람·NPC 공통 전이에서 거부한다. 규칙·엔진 타입 검사와 관련 순수 75건을 통과했다. 이 중 새 15건은 실제 순수 NPC 차례의 모집, 수송 손실 보충, 재료별 교환, 공간 확보, 거부 포함 행동 수, 금·목재 비용, 방문·휘하 배제와 100명 미만 한도를 확인했다.

전체 검사 398파일·6,600건과 실제 PG HTTP 9건·엔진 11건을 함께 실행한 20건을 통과했다. 새 엔진 시험 2건은 월 매입 저장을 확인한 뒤 실패시켜 전체 상태·원장·월 기록을 롤백했다. 다른 월드 보존과 새 연결 재실행도 확인했다. 순수 월 효과와 저장 원장의 행·ordinal·상태 해시를 대조했다. 실제 NPC 차례의 모집·인구·재료 소비, 후방 생산·수송·도착 손실·보충과 2개월·4개월의 원생성 재생 해시도 확인했다. 이 고정물은 해당 국가에 군주와 시험 NPC만 남기고 차례를 조정했다.

추가 HTTP 회귀 시험은 실제 예약 뒤 필요한 철을 매도했다. 실행 차례에는 재료 부족으로 거부됐다. 금·인구·수비병·개인 지갑·재료를 보존하고 소비 원장을 만들지 않으며 두 달 재생 해시가 저장 기록과 일치했다.

Claude의 규칙 코드와 최종 diff·시험·문서 독립 리뷰는 차단 사항 없이 통과했다. 최종 리뷰가 요구한 현재 트리의 PG 20건 통과도 확인했다. 장비 소비, 기본 프로필, 정식 규모·기수 검증과 CF 실제 동등성이 남아 있어 AC-P2-30은 미완료다.

## 원격 실행권 검사 보완 (2026-11-04)

PR #352의 첫 원격 CI는 엔진 묶음에서 새 결합 시험 3건이 실패했다. 첫 달 실행은 마지막 `assertLease`에서 실행권 검사로 거부됐고 후속 상태·재생 검증은 첫 달 결과가 없어 실패했다. 첫 달 시험은 15.796초, 파일 10건은 20.416초였으며 단일 트랜잭션이나 `advanceTo`별 시간은 계측하지 않았다. 권한·기본 검사와 네 Chromium shard는 통과했지만 이 실패를 전체 CI 통과로 세지 않는다.

시험의 일괄 `advanceTo`에는 운영의 독립 실행권 갱신 작업이 없다. 기존 `beforeCommit` 훅에서 같은 트랜잭션의 유효한 리스를 갱신하도록 보완했다. `renewLease`는 실제 필요한 `$executeRaw`만 받도록 타입을 좁혔으며 SQL·소유자·fencing token·만료 조건·진입과 마지막 검사는 그대로다. 이미 만료한 실행권을 되살리지 않고 물리적인 commit 완료 시간의 상한을 보장한다고 쓰지 않는다. TTL·60초 시험 제한·worker·retry·skip과 원래 명단·병력·차례·결과 단언은 바꾸지 않았다.

보완 뒤 실제 PostgreSQL 선택 실행은 native 10건과 기존 리스·턴 루프 24건을 합쳐 34건 통과했다. 첫 달 실행은 54.640초였고 첫 달의 저장·재접속·재생 단언을 모두 유지했다. 엄격 도구 타입·ESLint와 전체 검사 446파일·6,963건을 통과했다. 독립 수정본 리뷰와 새 SHA 원격 CI는 별도로 확인하며 원래 실패 기록은 보존한다. AC 전체 완료는 아니다.
