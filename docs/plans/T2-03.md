## 계획 (Claude)

### 목표

로그인 뒤 로비에서 월드 목록을 보고 참가할 수 있게 하는 API (AC-M2-02).

### 범위

기본 범위 (D-025와 무관하게 한다):

- `apps/server/src/routers/lobby.ts`: `lobby.worlds`, `lobby.notices`
- 장수 생성 판정: `packages/rules`에 순수 함수 `creationBlock`을 두고 로비·`general.create` 접수·엔진 처리가 같이 쓴다. `general.ts:37`과 `inputs.ts:33`의 상태 판정을 이 함수로 바꾼다. 승인 전에는 받는 상태가 지금처럼 RUNNING 하나다. 판정 순서는 아래 기술 정정 L4다
- 착수 단계, 시나리오 이름 출처, 파일 소유는 아래 기술 정정(L1~L6)이 정한다

D-025 승인 뒤에만 하는 범위 (승인 전에는 착수하지 않는다):

- 판정에 PREOPEN 허용과 정원 줄을 켠다 (아래 판정 표의 D-025 칸)
- 월드 총정원: 새 migration으로 `World.maxHumanGenerals Int?`를 더한다. `world:create --max-generals <n>`을 필수로 받고 운영자 명령 `world:capacity --world <ID> --max-generals <n>`을 더한다
- 감독 프로세스(T2-01 `apps/engine/src/supervisor.ts`)가 PREOPEN 월드에도 자식 엔진을 띄우게 한다 (아래 T2-01 인계)

### 하지 않는 것

월드 개설 화면(M3 관리자), 참가 신청·승인 절차(참가 = 장수 생성, T1-11), 로비 공지 저장 모델과 작성 명령(T2-09), 국가별 정원(T2-02).

### 선행 인계

- T2-02: `presetName`은 T2-02가 월드에 저장하는 프리셋 사본(`World.preset`)의 `name`이다 ([T2-02](./T2-02.md) 프리셋 항목 표). T2-02 전에 만든 월드는 `World.preset`이 없으므로 `presetName`이 null이다. 화면은 null이면 프리셋 칸을 비운다.
  D-025가 승인되면 `--max-generals`는 T2-02가 `--preset`을 더한 같은 `world:create`에 붙는다. T2-03 migration 전에 만든 월드(T2-02로 만든 프리셋 월드 포함)는 `maxHumanGenerals`가 null이고 운영자가 `world:capacity`로 정해야 참가할 수 있다.
- T2-09: 로비 공지는 T2-09가 만드는 `Notice` 모델의 로비 행을 읽는다. API 이름은 `lobby.notices` 하나이고 `notice.lobby.list`는 두지 않는다.
  받는 계약은 T2-09 계획의 공지 저장 모델 표(`docs/plans/T2-09.md:157`)다. 로비 행은 `scope = LOBBY`, `worldId = null`이고 `title`·`body`·`publishedAt`이 필수다. 작성은 `pnpm notice:publish --scope lobby`가 하고 `pinned`는 쓰지 않는다.
  `lobby.notices`는 `publishedAt` 최신 순, 같으면 id 내림차순, 많아야 20개를 낸다. 월드 공지(`scope = WORLD`)와 고정 우선 순서는 로비에 섞지 않는다.
  T2-09 계획은 `notice.lobby.list`를 두지 않는다(`docs/plans/T2-09.md:148`). T2-09와 무관한 부분은 지금 착수하고 `lobby.notices`와 리뷰 요청만 T2-09 뒤로 미룬다 (아래 L1, L5).
- T2-01: T2-01 감독 프로세스는 RUNNING·PAUSED 월드만 맡는다 (`docs/plans/T2-01.md:27`). T2-01 계획과 인계는 바꾸지 않는다.
  D-025가 승인되면 PREOPEN 선택은 T2-03이 T2-01이 합쳐진 `supervisor.ts` 위에서 더한다. 자식 엔진의 리스는 T2-01과 같은 `EngineLease`다.
  PREOPEN 월드의 엔진은 생성 접수만 처리하고 tick·개인 턴·월간 정산은 돌리지 않는다. 이 동작은 지금 코드에 있다(`apps/engine/src/turnLoop.ts:86-91`, RUNNING이 아니면 `processCreation`만 부른다). `world:start` 뒤 처음 RUNNING 분기에 들어간다.
- 대기열 표(`docs/product/phases.md`)의 T2-03 선행 칸은 이 PR에서 `T2-01, T2-02, T2-09`로 맞췄다.

### 기술 정정 (2026-10-23, 계획 명확화)

근거는 source main `1285aed`다. 이 절은 범위, API 계약, 판정 표를 바꾸지 않는다. 착수 단계, 시나리오 이름을 읽는 곳, 판정 순서, 파일 소유만 정한다.
D-025 승인 뒤 범위(PREOPEN 생성, 총정원, `world:capacity`, 감독 프로세스의 PREOPEN 선택)는 계속 하지 않는다. 지금 만드는 것은 RUNNING에서만 받는 생성 판정, 공개 월드 목록, 내 장수, 로비 공지 조회다.

#### L1 착수 단계

- 단계 A는 source main `1285aed` 위에서 바로 한다. `creationBlock`과 단위 시험, `general.create`·`processCreation` 연결과 L4 회귀, `lobby.worlds`(L2 포함)다. Notice 모델과 `World.preset`이 없어도 된다.
- 단계 B는 T2-09의 Notice migration이 source main에 들어온 뒤 `lobby.notices`를 더한다. 그 전에 T2-09 작업 사본의 schema를 가져와 쓰지 않는다. 합쳐진 모델이 L5와 다르면 T2-03 쪽에서 맞춰 고치지 않고 멈춰 보고한다.
- 단계 C는 T2-02와 T2-09가 모두 source main에 합쳐진 뒤 한다. L3의 `presetName`을 잇고 아래 검증 표에서 `승인 뒤`가 없는 줄을 합친 source에서 모두 돌린다. 그다음 구현 기록을 채우고 대기열을 `리뷰`로 바꾼다.
- T2-03 리뷰 통과는 AC-M2-02 완료가 아니다. AC-M2-02의 검증은 E2E이므로 T2-04 화면까지 끝나야 하고 D-025 범위도 남아 있다.

#### L2 시나리오 이름

`World`에는 시나리오 이름 칸이 없고 `scenarioKey`만 있다(`schema.prisma:15`). 이름은 시나리오 파일의 `title`에만 있다(`resources/scenario/1030.json:4`). `scenarioKey`는 그 파일의 `id`를 그대로 저장한 값이다(`packages/rules/src/world/bootstrap.ts:262`).
서버는 `apps/engine/src/world/resources.ts`를 import하지 않는다(앱끼리 import 금지). `World`에 칸을 더하는 migration도 만들지 않는다. `World` 칸은 T2-02, T2-09, T2-24, T4-56이 바꾸는 중이다.

| 항목 | 계약 |
| ---- | ---- |
| 위치 | `apps/server/src/routers/lobby.ts` 안의 함수 `scenarioTitle(key: string): Promise<string>` 하나 |
| 경로 | `new URL('../../../../resources/scenario/', import.meta.url)` 아래 `<key>.json` 하나로 고정. `readFile`로 읽고 JSON import는 쓰지 않는다(`opensamguk/no-cross-package-relative`가 막는다) |
| 키 | `/^[a-zA-Z0-9_-]+$/`(엔진 `resources.ts:7`과 같은 식)에 맞아야 하고 `default`는 거부한다. `default.json`은 시나리오가 아니라 능력치 규칙이다(엔진 `resources.ts:18`) |
| 형식 | `@opensamguk/rules`의 `scenarioSchema.pick({ id: true, title: true })`로 검사한다. 파일의 `id`가 키와 다르면 실패다. 나머지 칸은 읽지 않는다 |
| 공개 | 응답에는 `title` 문자열만 들어간다. 파일 경로, 키, 다른 칸은 응답과 오류 메시지에 넣지 않는다 |
| 캐시 | 프로세스 안 `Map`에 성공한 title만 담는다. 실패는 담지 않는다. 리소스는 배포 중에 바뀌지 않으므로 무효화는 없다 |
| 실패 | 키 형식, 파일 없음, JSON 오류, 형식 불일치, `id` 불일치는 모두 `lobby.worlds` 전체를 `INTERNAL_SERVER_ERROR`로 끝낸다. 화면에 가는 문구는 `trpc.ts:10`의 고정 문구다 |

범용 리소스 로더, 지도·병종 읽기, 엔진 `resources.ts`를 packages로 옮기는 일은 하지 않는다.

#### L3 프리셋 이름

단계 A의 source main에는 `World.preset` 칸이 없다. 그래서 모든 월드의 `presetName`은 null이고 이것은 선행 인계의 T2-02 줄(T2-02 전에 만든 월드는 null)과 같다.
단계 C에서 `World.preset`이 null이면 null, 아니면 T2-02가 저장한 정규화 사본의 `name`을 낸다. 사본에 `name`이 없거나 빈 문자열이면 `INTERNAL_SERVER_ERROR`다.

#### L4 판정 순서

지금 접수는 상태(`general.ts:37`), 입력 검사(`:39`), 기존 장수(`:41`), 내 PENDING(`:43`) 순서다. 엔진은 상태(`inputs.ts:33`), 계정 상태(`:35`), 입력 검사(`:36`), 기존 장수(`:42`), 이름 중복(`:43`) 순서다.
판정 표는 1번 줄(내 장수가 있다)이 먼저이므로 표를 코드에 옮기면 순서가 바뀐다. 새 제품 정책이 아니라 이미 정한 판정 표를 그대로 따른 결과다. 바뀐 뒤 순서는 아래와 같다.

- 접수: `requireWorld(tx, worldId, true)` 잠금, 기존 장수와 내 PENDING 읽기, `creationBlock`(1, 2, 3, 3a번 줄), 입력 검사, 4번 줄(같은 내용이면 그 접수, 다르면 CONFLICT), 새 접수
- 엔진: `User` 행 `FOR SHARE`, 그 월드 장수 읽기, `creationBlock`(처리 중인 접수의 PENDING은 거짓), 계정 상태, 입력 검사, 이름 중복, 생성

결과가 달라지는 경우는 아래 표가 전부다. 장수가 없는 사용자의 결과는 하나도 바뀌지 않는다.

| 경우 | 접수 HTTP 지금 | 접수 HTTP 뒤 | 엔진 지금 | 엔진 뒤 |
| ---- | -------------- | ------------ | --------- | ------- |
| 장수 있음, 상태 PAUSED·ENDED·PREOPEN | `PRECONDITION_FAILED` `WORLD_CLOSED` | `CONFLICT` `ALREADY_EXISTS` | REJECTED `WORLD_CLOSED` | REJECTED `ALREADY_EXISTS` |
| 장수 있음, RUNNING, 잘못된 입력 | `BAD_REQUEST` | `CONFLICT` `ALREADY_EXISTS` | REJECTED `BAD_NAME`·`BAD_STATS`·`BAD_PORTRAIT` | REJECTED `ALREADY_EXISTS` |
| 장수 있음, RUNNING, 계정 제재 | `UNAUTHORIZED` (세션이 사라짐, `session.ts:16`) | 같음 | REJECTED `ACTOR_INACTIVE` | REJECTED `ALREADY_EXISTS` |

접수에서 거부되면 InputEvent를 만들지 않는다. 엔진 거부는 지금처럼 `result = { code, message: CREATION_ERRORS[code] }`로 남는다.

#### L5 로비 공지

조건은 `scope = LOBBY`, `worldId = null`, 정렬은 `publishedAt` 내림차순 다음 `id` 내림차순, 많아야 20개, 고르는 칸은 `id`·`title`·`body`·`publishedAt`이다. `pinned`는 읽지 않는다.
T2-09가 작업 중인 schema에서 `Notice.title`은 `String?`이고 로비 행의 title은 DB 제약 없이 `notice:publish`만 막는다. title이 null인 로비 행을 만나면 건너뛰지 않고 `INTERNAL_SERVER_ERROR`로 끝낸다. `publishedAt`은 ISO 문자열로 낸다.

### API 계약

이 타입 하나가 계약이다. 예전 요약(`presetKey`, `createdAt`이 있던 짧은 목록)은 지웠다. 구현 뒤에는 `AppRouter` 타입이 이 모양을 그대로 낸다.

```ts
type GameDate = { year: number; month: number };
type LobbyWorld = {
  id: string;
  name: string;
  status: 'PREOPEN' | 'RUNNING' | 'PAUSED' | 'ENDED'; // ENDED는 includeEnded일 때만 온다
  presetName: string | null; // 정규, 속성 등 (T2-02). T2-02 전에 만든 월드는 null
  scenarioTitle: string;
  startYear: number;
  gameDate: GameDate; // 지금 게임 연월. PREOPEN이면 시작 연월
  turnTermMinutes: number;
  startedAt: string | null; // ISO 시각. 아직 시작하지 않은 PREOPEN만 null
  humanGenerals: number; // 아래 집계 정의
  maxHumanGenerals?: number | null; // D-025 승인 뒤에만 있는 키. null이면 아직 정하지 않은 월드이고 생성을 막는다
  myGeneral: { id: number; name: string; nationName: string | null } | null; // 무인증이면 null, 재야면 nationName이 null
  createBlockedReason: string | null; // 아래 판정 표. 화면 문구 그대로
};
// lobby.worlds({ includeEnded?: boolean }) → LobbyWorld[]
//   정렬: RUNNING → PREOPEN → PAUSED → ENDED. 같은 상태면 startedAt 최신 순(null이면 createdAt), 그다음 id 순
type LobbyNotice = { id: string; title: string; body: string; publishedAt: string }; // publishedAt은 ISO 시각
// lobby.notices() → LobbyNotice[]   publishedAt 최신 순, 같으면 id 내림차순, 많아야 20개
```

- 공개 범위: 무인증도 두 API를 부른다. 응답 키는 위 타입과 같고 시드·`statRules`·`initialStateHash` 같은 월드 내부 값은 내보내지 않는다. `myGeneral`은 세션 사용자의 장수만이다.
- 무인증과 로그인한 미참가자는 둘 다 `myGeneral`이 null이다. 화면은 `auth.me`로 둘을 가른다 (T2-04). 로비 API에 사용자 필드를 따로 두지 않는다.
- 화면 요소와 필드의 대조는 [T2-04](./T2-04.md)의 v1 근거 표 오른쪽 칸에 있다. `id`는 `들어가기`·`장수 만들기` 주소에 쓴다. 나머지 필드도 모두 화면 요소 하나 이상에 쓰인다.

### 집계 정의

- `humanGenerals`는 그 월드에서 `General.userId`가 null이 아닌 행의 수다. NPC는 세지 않는다. 접수만 되고 엔진이 아직 처리하지 않은 생성(InputEvent PENDING)도 세지 않는다.

### 총정원 (D-025 승인 뒤에만)

- 출처는 `World.maxHumanGenerals`다. 운영자가 `world:create --max-generals <n>`(필수, 1 이상)으로 정하고 `world:capacity`로 바꾼다. 값은 계획에서 정하지 않는다.
- 이 migration 전에 만든 월드는 null로 남는다. 운영자가 `world:capacity`로 정하기 전까지 그 월드에서는 장수를 만들 수 없다. 국가별 정원으로 대신하지 않는다.
- `world:capacity`는 `World` 행을 `FOR UPDATE`로 잠그고 바꾼다. 지금 `humanGenerals`보다 작은 값도 받는다. 이미 있는 장수는 그대로이고 새 생성만 막힌다.
- 마지막 자리는 엔진이 정한다 (아래 판정의 마지막 자리 줄).

### 장수 생성 판정 `createBlockedReason`

위에서부터 처음 맞는 줄을 쓴다. 로비(`lobby.worlds`), 접수(`general.create`), 엔진(`processCreation`)이 같은 `creationBlock` 함수를 부르되 단계마다 넣는 값이 다르다.
D-025 칸이 `승인 뒤`인 줄은 승인 전에 없다. `승인 전`인 줄은 승인 뒤에 없다.

| 순서 | 조건 | D-025 | `createBlockedReason` (로비) | 접수 `general.create` | 엔진 `processCreation` |
| ---- | ---- | ----- | ---------------------------- | --------------------- | ---------------------- |
| 1 | 내 장수가 있다 | 항상 | null (화면은 `들어가기`) | `ALREADY_EXISTS` | `ALREADY_EXISTS` |
| 2 | 상태가 PAUSED | 항상 | `멈춘 월드입니다` | `WORLD_CLOSED` | `WORLD_CLOSED` |
| 3 | 상태가 ENDED | 항상 | `끝난 월드입니다` | `WORLD_CLOSED` | `WORLD_CLOSED` |
| 3a | 상태가 PREOPEN | 승인 전 | `아직 열리지 않은 월드입니다` | `WORLD_CLOSED` | `WORLD_CLOSED` |
| 4 | 내 생성 요청이 PENDING | 항상 | `장수를 만드는 중입니다` | 같은 내용이면 그 접수를 돌려주고 다른 내용이면 CONFLICT (`general.ts:43-55`) | 해당 없음. 엔진은 지금 처리하는 그 접수를 이 줄에 넣지 않는다 |
| 5 | `maxHumanGenerals`가 null | 승인 뒤 | `정원이 정해지지 않은 월드입니다` | `WORLD_FULL` | `WORLD_FULL` |
| 6 | `humanGenerals` ≥ `maxHumanGenerals` | 승인 뒤 | `인원이 찼습니다` | `WORLD_FULL` | `WORLD_FULL` |
| 7 | 그 밖 (승인 전 RUNNING, 승인 뒤 PREOPEN·RUNNING) | 항상 | null (화면은 `장수 만들기`) | 접수 PENDING | APPLIED |

- 함수 입력은 상태, 내 장수 유무, 내 PENDING 생성 접수 유무, `humanGenerals`, 정원 값(승인 전에는 없음)이다. 로비와 접수는 DB에서 읽은 내 PENDING 유무를 넣는다.
  엔진은 가장 오래된 PENDING 접수 하나를 집어 처리하므로(`inputs.ts:16-19`) 그 접수의 PENDING 유무를 거짓으로 넣는다. 그래서 정상 PENDING 하나는 4번 줄에서 멈추지 않고 정원 재검사와 생성까지 간다.
- 무인증이면 1번과 4번 줄을 건너뛴다. 화면은 null이면 `로그인하고 참가`, 아니면 그 이유를 보인다.
- 멈춤 월드의 조회와 생성은 다르다. 내 장수가 있는 멈춤 월드는 1번 줄에서 끝나고 화면은 `들어가기`를 연다. 장수가 없으면 2번 줄로 막는다.
- 이미 만든 장수의 결과를 다시 받는 일과 두 번째 생성은 다르다. APPLIED 뒤 같은 사용자가 `general.create`를 다시 부르면 1번 줄의 `ALREADY_EXISTS`다. 결과는 지금처럼 `general.mine`(`general.ts:97-104`)이 돌려준다.
- 3a번 줄 문구 `아직 열리지 않은 월드입니다`는 `WORLD_CLOSED`의 화면 문구만 다르다. 승인 뒤 쓰는 새 거부 코드 `WORLD_FULL`(`인원이 찼습니다`)은 `CREATION_ERRORS`에 더하고 서버 응답 코드는 `PRECONDITION_FAILED`로 둔다. 5번 줄도 같은 코드를 쓰고 문구만 다르다.
- 마지막 자리 (승인 뒤): 접수는 `requireWorld(tx, worldId, true)`의 World 잠금 안에서 판정해 뻔한 거절을 빨리 돌려준다. 엔진은 리스와 World를 잠근 같은 펜싱 트랜잭션(`turnLoop.ts:81-88`)에서 `humanGenerals`를 다시 세어 판정한다. 둘이 다르면 엔진 판정을 따른다.
- 직렬화 (승인 뒤): 엔진의 생성 처리(`turnLoop.ts:84`), `world:start`(`apps/engine/src/world/clock.ts:8`), `world:capacity`가 모두 같은 World 행을 `FOR UPDATE`로 잠근다. 시작·생성·정원 변경이 겹쳐도 하나씩 차례로 확정된다.
- 가오픈 생성 (승인 뒤): `processCreation`은 PREOPEN에서 tick을 `world.clockTick`으로 쓴다(`turnLoop.ts:86-87`). 만든 장수는 기존 `general.create` 입력 기록으로 재생되고 `world:start` 뒤 첫 월간 정산부터 다른 장수와 같이 정산된다.
- 가오픈 월드의 메인과 개인 예턴: 지금 서버는 조회에서 상태를 막지 않고(`apps/server/src/queries.ts:28-40`) 개인 예턴 저장은 ENDED만 막는다(`apps/server/src/routers/turns.ts:39`). 다음 턴 시각은 RUNNING이 아니면 null이다(`queries.ts:64-65`).
  그래서 승인 뒤 가오픈 월드에 만든 장수는 시작 전에도 메인을 보고 개인 30칸을 저장한다. T1-15·T1-16 화면이 다음 턴 시각 null을 시작 전으로 그리는지 T2-04 리뷰에서 함께 확인한다.

## 구현 기록 (Codex)

- 착수 기준: 이관 main `3e5b52a`. T2-02의 프리셋 저장과 T2-09의 Notice migration이 이 커밋에 있어 L1의 A·B·C 범위를 함께 연결했다. 두 선행 작업 전체의 완료나 독립 리뷰를 대신하지 않는다. 부모 Codex가 통합·실제 PostgreSQL·HTTP 검증·문서 기록을 맡았고 하위 Codex `lobby_backend`가 L6의 코드 파일과 단위 시험을 맡았다. 다른 병렬 작업 T4-02는 분리 작업실을 썼다.
- 바꾼 것: 공개 `lobby.worlds`·`lobby.notices`를 AppRouter에 등록했다. 실제 시나리오 제목 성공 캐시, 프리셋 이름, 상태·시작 시각·ID 정렬, 사람 장수 집계, 세션 사용자의 장수·생성 대기, 로비 공지 20개를 연결했다. `creationBlock`을 로비·생성 접수·엔진이 함께 쓴다. L4의 기존 장수 우선 판정과 허용하지 않는 입력 키의 선행 거부를 적용했다. 코드 지도를 채웠다. DB·migration·resources는 수정하지 않았다.
- 계획과 달라진 점과 이유: D-025 승인 뒤 범위는 구현하지 않았다. L4 순서대로 이름·능력치·초상 검사를 트랜잭션 안으로 옮겼다. `worldId`와 허용 키 구조는 먼저 검사하므로 `userId`·`generalId` 주입은 기존처럼 `BAD_REQUEST`다. 기존 장수가 없는 닫힌 월드의 잘못된 이름도 L4의 명시 순서에 따라 `WORLD_CLOSED`가 된다. 원래 tRPC 선검사와 달라지는 이 경우도 실제 HTTP·엔진 시험에 넣었다.

### 1차 독립 리뷰 뒤 수정

실제 Claude CLI가 정확 `7db51de`를 검토해 수정 필요로 판정했다. 실제 PostgreSQL 84개와 단위 40개를 직접 확인했지만 종료 연월과 PREOPEN 엔진 거부 시험 누락을 지적했다.
실제 엔진 종료로 로비는 192년 1월, 저장 결과와 메인은 191년 12월이 되는 반례를 재현했다. 종료 월드는 저장한 `WorldResult.endedYear`·`endedMonth`를 쓰게 고쳤다. 결과 행이 없는 이전 종료 월드는 기존 연월 계산을 유지한다.
