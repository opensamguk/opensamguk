# 결정 기록

> 방향을 바꾸는 결정은 여기에 먼저 적고 사용자 승인을 받은 뒤 문서와 코드에 반영합니다.
> 한 번 적은 결정은 지우지 않습니다. 바꿀 때는 새 번호로 적고 이전 결정에 "대체됨: D-0xx"를 붙입니다.

## 형식

```text
## D-0xx. 제목 (YYYY-MM-DD)
- 결정:
- 고른 이유:
- 버린 대안:
- 영향: (바뀌는 문서·AC)
```

## D-001. 원작 뼈대를 가져오고 규칙은 단순하게 새로 쓴다 (2026-10-20)

- **결정:** 장수 1명·예턴·월간 정산·국가·전쟁이라는 원작 핵심 루프를 유지하고 규칙은 새로 단순하게 짠다.
  원작과 1:1 동작 일치는 목표가 아니다.
- **고른 이유:** 재미가 검증된 뼈대이고 참고할 코드가 많다. 1:1 일치 검증은 core2026에서도 큰 비용이다.
- **버린 대안:** 새 시스템을 처음부터 넣기(범위 팽창 위험), 완전히 새 규칙(재미 검증 전까지 끝이 안 보임),
  core2026 포크(37.5만 줄 유지 부담, 새 게임이 아님).
- **영향:** PRD §3 비목표, 요구사항 §4

## D-002. MVP 완료 = 공개 서버 오픈, 관문 세 개로 나눈다 (2026-10-20)

- **결정:** MVP의 끝은 공개 오픈이다. 진행이 보이도록 M1(혼자+NPC 완주) → M2(지인 테스트) → M3(공개 오픈)
  관문으로 나눈다.
- **고른 이유:** 사용자가 공개 오픈을 완료 기준으로 골랐다. 지난번엔 "끝"이 안 보였으므로 중간 관문이 필요하다.
- **영향:** [단계 계획](./phases.md), [인수조건](./acceptance-criteria.md)
- **확인:** 2026-10-20 관문 순서와 나눔 확정 (D-011)

## D-003. TypeScript + React (2026-10-20)

- **결정:** 서버·엔진·규칙은 TypeScript(Node.js), 화면은 React + Vite.
- **고른 이유:** core2026의 순수 TS 규칙 코드를 바로 참고할 수 있고 이전에 React를 써 봤다.
- **버린 대안:** TS + Vue(화면 코드까지 참고 가능하나 새로 익혀야 함), Cloudflare Workers(이식 부담),
  Kotlin/Spring(core2026 참고 불가, 지난번 규모 재현 위험).

## D-004. 이미지는 ID로만 참조하고 공개 전에 교체 여부를 정한다 (2026-10-20)

- **결정:** 게임은 초상을 초상 ID(10001~11000)로만 부른다. 실제 파일 위치는 설정(base URL)으로 바꾼다.
  개발과 비공개 테스트는 기존 초상을 쓰고 공개 전에 교체 여부를 정한다.
- **배경:** opensamguk-images의 주력 초상 1,000명은 코에이 삼국지14 그림이고 `waryong/` 타일 404개는
  「제갈공명 와룡전」에서 뽑은 것이다. MIT로 깨끗한 것은 `assets/`, `web/`, `exports/`, `portraits-original/`뿐이다.
- **영향:** FR-IMG-01~04, AC-M1-20, **AC-M3-06(공개 관문)**, [이미지 자산](../image-assets.md)

## D-005. 로그인은 이메일 + 비밀번호 (2026-10-20)

- **결정:** 소셜 로그인 없이 이메일 + 비밀번호로 한다.
- **고른 이유:** 외부 서비스에 기대지 않는다.
- **감수하는 것:** 비밀번호 보관·재설정 메일·부계정 방지를 직접 만든다. 메일 발송 서비스를 M3 전에 정해야 한다(A14).
- **영향:** FR-ACC-01~08, AC-M3-01·05

## D-006. 처음부터 여러 월드 (2026-10-20)

- **결정:** 계정·로비와 월드를 나누고 여러 월드를 동시에 운영하는 구조로 만든다.
- **줄인 것:** core2026의 Gateway orchestrator(commit별 worktree·PM2 관리)는 만들지 않는다. 같은 버전의
  서버가 여러 월드를 돌린다.
- **진행 방식:** M1은 월드 1개로 검증하되 데이터와 엔진은 처음부터 `worldId`로 나눈다. 동시 2개는 M2에서 검증한다.
- **영향:** [데이터 모델](./data-model.md), [아키텍처](../architecture/overview.md), AC-M2-01~03, D5 기본 포함

## D-013. 프론트는 Vite + React SPA 유지, TypeScript는 6.0 (2026-10-20)

- **결정:** Next.js로 바꾸지 않고 Vite + React SPA를 유지한다 (D-003 확인).
- **이유:** 게임 화면은 모두 로그인 뒤라 SSR 이득이 작고 Next.js 서버가 Fastify·엔진과 역할이 겹친다. 공개 페이지가
  필요해지면 M3에서 그 부분만 따로 만든다.
- **TypeScript:** typescript-eslint 8.72가 TS 6.1 미만만 지원하므로 TS 6.0 하나를 쓴다 (TS 7 네이티브는 보류).

## D-014. M2 구조 결정 (2026-10-20, M2 계획)

- **월드마다 엔진 프로세스 하나**, 감독 프로세스가 띄우고 다시 띄운다 (T2-01). 런타임 문서의 경고 항목 해결.
- **월드는 만들 때의 프리셋 사본을 저장**해 진행 중 규칙이 바뀌지 않는다 (T2-02).
- **턴을 쓰지 않는 즉시 행동**: 임명·해임, 발령 응답, 조약 제안·수락·파기 (T2-05, T2-07). 모두 `InputEvent`로 엔진이 처리해 재생에 남는다.

- **배포는 서버 1대에 이미지 전송 방식**, 백업 7일 + 외부 복사본 (T2-15). 서버·도메인·웹훅은 사용자 준비(T2-19).

## D-018. 순위(T2-22·T2-23)를 M1과 나란히 시작한다 (2026-10-21)

- **결정:** T2-22 순위 API의 선행 조건을 "M1 전체"에서 T1-07(월간 정산, 국력 공식)과 T1-08(전쟁 결과, 전공 집계)로 줄인다. 두 작업은 완료됐다.
- **담당:** T2-22는 Codex가 맡는다. T2-23 화면은 로컬 Claude가 맡아 PR 초안으로 먼저 준비하고 API가 합쳐진 뒤 실제 데이터로 검증한다.
- **이유:** 사용자 지시. 원격 구현 서버가 M1 핵심 흐름을 맡는 동안 범위가 작고 책임을 나누기 쉬운 순위 묶음을 병행한다.
- **지킬 것:** 화면은 T2-22 계획의 API 계약만 따른다. API 없이 그린 화면은 완료 증거가 아니다(AGENTS.md §2). M1 범위와 공유 파일(`router.tsx`, `GameLayout.tsx`)은 최소한으로만 고친다.

## D-019. 다른 국가의 기술은 공개 국력에서도 역산되지 않게 한다 (2026-10-21)

- **결정:** 순위(T2-22)의 공개 국력은 원작 core2026(`df6c926`)처럼 여러 값을 섞은 합성값에 매달 시드 배율 0.95~1.05를 곱해 만든다. 다른 국가가 기술·국고·군량의 원값이나 등급을 공개 값의 산수로 알아낼 수 없어야 한다.
- **이유:** 사용자 지시("기술 등급 질문은 원작을 참고해"). 원작은 세력 일람(`app/game-frontend/src/views/NationListView.vue:199-201`)에 국력과 장수·속령만 보이고 기술은 자기 국가 화면에만 둔다. 국력은 자원/100, 기술, 보급 도시 내정, 장수 능력, (경험+공헌)/100의 합을 10으로 나누고 매달 0.95~1.05를 곱한다(`app/game-engine/src/turn/monthlyNationStatsHandler.ts:102-144`).
- **고친 것:** PR #47의 공식 `도시 + 장수 + min(11, floor(기술/1000))`은 함께 공개되는 도시·장수 수를 빼면 기술 등급(0~11)이 그대로 남는다. 2026-10-21 Mac 보조 검토가 실제 응답으로 확인했다(기술 5432 국가가 국력 8, 도시 2, 장수 1).
- **영향:** T2-22 공식과 회귀 시험. 화면(T2-23)은 국력을 숫자로만 보여 주므로 바뀌지 않는다. 배율은 `packages/shared`의 시드 RNG를 써서 재생 결정론(AC-M1-13)을 지킨다.


## D-020. 가오픈 월드의 장수 생성과 월드 총정원 (2026-10-21)

- **결정 1:** 가오픈(PREOPEN) 월드에서도 장수를 미리 만들 수 있다. 진행 중(RUNNING)과 같은 생성 규칙을 쓰고 멈춤(PAUSED)·끝남(ENDED)은 지금처럼 막는다.
- **결정 2:** 월드마다 총정원(그 월드에서 사람이 맡을 수 있는 장수 수의 상한)을 둔다. 운영자가 월드를 만들 때 정하는 필수 설정이고 기본값은 없다. 값은 따로 정한다.
  국가별 정원(T2-02 프리셋 `protection.maxGeneralsPerNation`)과는 다른 것이며 그것으로 대신하지 않는다.
- **이유:** 사용자 지시. PR #51 독립 기술 검토(R51-4)가 두 정책을 구현 때 정하도록 넘기지 말라고 요구했다.
- **영향:** T2-03(로비 API의 `createBlockedReason`, 총정원 필드와 집계), T2-04(가오픈 카드의 `장수 만들기`).
  서버 `apps/server/src/routers/general.ts:37`과 엔진 `apps/engine/src/inputs.ts:35`의 RUNNING 전용 판정을 PREOPEN까지 넓히고 정원 검사를 더한다.
  엔진이 월드를 고르는 `apps/engine/src/main.ts:33`도 RUNNING만 고르므로 가오픈 월드의 생성 접수를 처리하게 바꾼다(T2-01 월드별 엔진과 함께).
  오픈 전에 만든 장수는 기존 `general.create` 입력 기록으로 재생하고 첫 월간 정산부터 다른 장수와 같이 정산한다. 시험은 T2-03 검증 표에 있다.
