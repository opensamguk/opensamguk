> 방향을 바꾸는 결정은 여기에 먼저 적고 사용자 승인을 받은 뒤 문서와 코드에 반영합니다.

## D-001. 원작 뼈대를 가져오고 규칙은 단순하게 새로 쓴다 (2026-10-20)

- **결정:** 장수 1명·예턴·월간 정산·국가·전쟁이라는 원작 핵심 루프를 유지하고 규칙은 새로 단순하게 짠다.
  원작과 1:1 동작 일치는 목표가 아니다.
- **고른 이유:** 재미가 검증된 뼈대이고 참고할 코드가 많다. 1:1 일치 검증은 core2026에서도 큰 비용이다.
- **버린 대안:** 새 시스템을 처음부터 넣기(범위 팽창 위험), 완전히 새 규칙(재미 검증 전까지 끝이 안 보임),
  core2026 포크(37.5만 줄 유지 부담, 새 게임이 아님).
- **영향:** PRD §3 비목표, 요구사항 §4

## D-002. MVP 완료 = 공개 서버 오픈, 관문 세 개로 나눈다 (2026-10-20)

- **결정:** MVP의 끝은 공개 오픈이다. 진행이 보이도록 M1(혼자+NPC 완주) → M2(지인 테스트) → M3(공개 오픈)
  관문으로 나눈다.
- **고른 이유:** 사용자가 공개 오픈을 완료 기준으로 골랐다. 지난번엔 "끝"이 안 보였으므로 중간 관문이 필요하다.
- **영향:** [단계 계획](./phases.md), [인수조건](./acceptance-criteria.md)
- **확인:** 2026-10-20 관문 순서와 나눔 확정 (D-011)

## D-003. TypeScript + React (2026-10-20)

- **결정:** 서버·엔진·규칙은 TypeScript(Node.js), 화면은 React + Vite.
- **고른 이유:** core2026의 순수 TS 규칙 코드를 바로 참고할 수 있고 이전에 React를 써 봤다.
- **버린 대안:** TS + Vue(화면 코드까지 참고 가능하나 새로 익혀야 함), Cloudflare Workers(이식 부담),
  Kotlin/Spring(core2026 참고 불가, 지난번 규모 재현 위험).

## D-004. 이미지는 ID로만 참조하고 공개 전에 교체 여부를 정한다 (2026-10-20)

- **결정:** 게임은 초상을 초상 ID(10001~11000)로만 부른다. 실제 파일 위치는 설정(base URL)으로 바꾼다.
  개발과 비공개 테스트는 기존 초상을 쓰고 공개 전에 교체 여부를 정한다.
- **배경:** opensamguk-images의 주력 초상 1,000명은 코에이 삼국지14 그림이고 `waryong/` 타일 404개는
  「제갈공명 와룡전」에서 뽑은 것이다. MIT로 깨끗한 것은 `assets/`, `web/`, `exports/`, `portraits-original/`뿐이다.
- **영향:** FR-IMG-01~04, AC-M1-20, **AC-M3-06(공개 관문)**, [이미지 자산](../image-assets.md)

## D-005. 로그인은 이메일 + 비밀번호 (2026-10-20)

- **결정:** 소셜 로그인 없이 이메일 + 비밀번호로 한다.
- **고른 이유:** 외부 서비스에 기대지 않는다.
- **감수하는 것:** 비밀번호 보관·재설정 메일·부계정 방지를 직접 만든다. 메일 발송 서비스를 M3 전에 정해야 한다(A14).
- **영향:** FR-ACC-01~08, AC-M3-01·05

## D-006. 처음부터 여러 월드 (2026-10-20)

- **결정:** 계정·로비와 월드를 나누고 여러 월드를 동시에 운영하는 구조로 만든다.
- **줄인 것:** core2026의 Gateway orchestrator(commit별 worktree·PM2 관리)는 만들지 않는다. 같은 버전의
  서버가 여러 월드를 돌린다.
- **진행 방식:** M1은 월드 1개로 검증하되 데이터와 엔진은 처음부터 `worldId`로 나눈다. 동시 2개는 M2에서 검증한다.
- **영향:** [데이터 모델](./data-model.md), [아키텍처](../architecture/overview.md), AC-M2-01~03, D5 기본 포함

## D-013. 프론트는 Vite + React SPA 유지, TypeScript는 6.0 (2026-10-20)

- **결정:** Next.js로 바꾸지 않고 Vite + React SPA를 유지한다 (D-003 확인).

- **TypeScript:** typescript-eslint 8.72가 TS 6.1 미만만 지원하므로 TS 6.0 하나를 쓴다 (TS 7 네이티브는 보류).

## D-014. M2 구조 결정 (2026-10-20, M2 계획)

- **월드마다 엔진 프로세스 하나**, 감독 프로세스가 띄우고 다시 띄운다 (T2-01). 런타임 문서의 경고 표시 해결.

## D-019. 다른 국가의 기술은 공개 국력에서도 역산되지 않게 한다 (2026-10-21)

- **결정:** 순위(T2-22)의 공개 국력은 원작 core2026(`df6c926`)처럼 여러 값을 섞은 합성값에 매달 시드 배율 0.95~1.05를 곱해 만든다. 다른 국가가 기술·국고·군량의 원값이나 등급을 공개 값의 산수로 알아낼 수 없어야 한다.
- **이유:** 사용자 지시("기술 등급 질문은 원작을 참고해"). 원작은 세력 일람(`app/game-frontend/src/views/NationListView.vue:199-201`)에 국력과 장수·속령만 보이고 기술은 자기 국가 화면에만 둔다. 국력은 자원/100, 기술, 보급 도시 내정, 장수 능력, (경험+공헌)/100의 합을 10으로 나누고 매달 0.95~1.05를 곱한다(`app/game-engine/src/turn/monthlyNationStatsHandler.ts:102-144`).
- **고친 것:** PR #47의 공식 `도시 + 장수 + min(11, floor(기술/1000))`은 함께 공개되는 도시·장수 수를 빼면 기술 등급(0~11)이 그대로 남는다. 2026-10-21 Mac 보조 검토가 실제 응답으로 확인했다(기술 5432 국가가 국력 8, 도시 2, 장수 1).
- **영향:** T2-22 공식과 회귀 시험. 화면(T2-23)은 국력을 숫자로만 보여 주므로 바뀌지 않는다. 배율은 `packages/shared`의 시드 RNG를 써서 재생 결정론(AC-M1-13)을 지킨다.

## D-020. 메인 한 화면에서 지도와 예턴을 함께 다룬다 (2026-10-21)

- **결정:** 지도·예턴 편집·장수/도시/국가 정보·기록을 메인 작업 화면 하나에 함께 두고 그 자리에서 조작한다. 배치는 레퍼런스 R1인
  core2026 `MainView.vue`(고정 커밋 `df6c926`)의 데스크톱 배치를 따른다. 지도 1~7열과 명령 목록 8~10열이 같은 행에 있다. 지도 아래에 도시 정보,
  그 아래 국가·장수 정보, 맨 아래 기록이 온다. 명령 목록에는 30칸 예턴 편집기(T1-15 `TurnEditor`)가 들어간다.
- **이유:** 소유자 직접 지시 ("지도랑 예턴 등은 같은 메인 화면이어야 하는데? 기존의 UI 확인 해볼래?"). sources.json의 R1은 처음부터 이 결합 구성을 적었으나
  UI 지침·T1-13·T1-15·T1-16 계획이 별도 주소 중심으로 어긋났다.
- **지키는 것:** 기존 주소(`/map`, `/turns`, `/city/:key`, `/nation/:id`, `/records`)의 직접 접근·새로고침은 보조 화면으로 유지한다. 핵심 플레이는 그 주소로 옮겨 가야만 되지 않는다.
  게임 규칙·API·데이터·공개 범위·자산 권리·비용·배포 경계는 바꾸지 않는다. 원작 코드를 옮기지 않고 배치만 참고한다.
- **나눈 일:** 메인 배치·지도·조회 칸과 편집기 끼우기는 T1-16, 재사용 편집기와 훅(`apps/web/src/turns/TurnEditor.tsx`, 속성 `worldId`·`selectedCityKey`)은 T1-15.
  지도 선택은 대상 고르기의 힌트일 뿐이며 초안을 덮거나 저장하지 않는다. 메인은 지도 선택·재조회 때 편집기를 다시 만들지 않는다.
- **영향:** [UI 지침 §2·§4](../frontend-ui-guidelines.md), [T1-13](../plans/T1-13.md), [T1-16](../plans/T1-16.md), AC-M1-19 설명. 원래 계획 문구는 기록으로 둔다.

## D-021. 지인 참가 시험을 독립 에이전트 참가 시험으로 바꾸고 공개를 승인한다 (2026-10-21)

- **결정:** 소유자 원문은 “지인 시험은 같은 수의 에이전트 시험으로 대체. 공개는 승인.”이다 (2026-10-21 16:31 KST). <!-- lint-text-ignore J-2 --> 지인 참가자가 필요한 시험은 같은 수의 독립 에이전트 참가 시험으로 바꾼다. M2의 지인 5명 이상은 독립 에이전트 5명 이상이 된다. M3 공개 전 오픈 리허설도 같은 수의 독립 에이전트로 가입부터 첫 턴 결과까지 실제로 검증한다.
- **독립 참가자:** 계정과 로그인 세션이 서로 다르고 따로 실행되는 에이전트 세션이 스스로 행동을 고르면 한 명으로 센다. 참가는 실제 웹 화면이나 플레이어용 HTTP API로만 한다. NPC, 한 에이전트가 여러 계정을 돌리는 것, 같은 에이전트의 요청 수, 단순 병렬 부하는 참가자 수에 넣지 않는다. 기록 형식은 [테스트 정책](../testing-policy.md#6-독립-에이전트-참가-시험)에 있다.
- **유지하는 조건:** 월드 2개, 한 기수 완주, 오류 때문에 상태를 되돌린 일 0번, 피드백 목록, P0 0건과 P1 연결(AC-M2-12·13), 가입부터 첫 턴 결과까지 막힌 참가자 0명(AC-M3-11)은 그대로다. 시험을 하지 않았거나 일부만 했으면 해당 AC를 통과로 표시하지 않는다.
- **공개 승인:** 공개에 대한 소유자 승인은 받았다. 승인만 다시 묻거나 미결정으로 두지 않는다. 이 승인은 공개 완료, 제품 QA 통과, 배포 실행을 뜻하지 않는다. AC-M3-16을 포함한 M3 AC 전부, 정확한 SHA의 필수 검증, 교차 리뷰, 보안(AC-M3-03), 공개 이미지 권리(AC-M3-06), 백업·복구(AC-M2-09)는 그대로 통과해야 한다. 실제 운영 변경은 그때 적용되는 운영 권한과 안전 절차를 따른다.
- **면제하지 않는 것:** 사람이 하는 M1 완주 데모(AC-M1-21), 메일 발송 서비스 선택(A14, T3-01), 공개 이미지 권리 결정(T3-12)은 이 결정과 무관하게 남는다. 새 비용, GCP 기동, 운영·게임 초기화 권한도 이 승인에 들어 있지 않다.
- **일정:** 소유자 마감 지시(2026-10-21)에 따라 MVP 전체(M1·M2·M3)와 Phase 2의 목표 시각은 2026-10-21 23:59:59 KST다. Phase 3 목표 2026-10-25는 그대로다. 목표일 뿐 완료 보장이나 AC 면제가 아니다.
- **구현 착수와 최종 인수 (총괄 결정):** T2-01(새 감독 프로세스·`EngineHeartbeat`)과 T3-04(메일과 무관한 요청 제한·CSRF·현재 API 권한 대조)는 M1·M2 최종 인수 전에도 별도 worktree에서 기존 T1 코드 위에 구현을 시작할 수 있다. 대기열의 선행 칸은 main 통합과 최종 인수의 순서로 읽는다. 공통 schema·router·runtime과 공유 문서는 정해진 소유자만 고치고 최종 반영은 직렬로 한다. T3-04의 공유 요청 제한은 PR #5의 T3-04 계획에 적힌 공개 모양과 한도를 따르고 T3-02는 import만 한다. 이 허용으로 M1 완료, 아직 없는 API, 다른 미완료 관문을 통과로 세지 않는다. T2-01은 실제 월드 2개 격리 시험과 교차 리뷰를 거친 뒤 따로 통합한다. T1-16의 원래 선행·리뷰 관계와 T1-23의 실제 통합 선행은 풀지 않는다.
- **영향:** [단계 계획](./phases.md)의 일정·M2 데모·T2-18 이름·M3 리허설 안내, AC-M2-12, AC-M3-11, AC-M3-16, [T2-18 계획](../plans/T2-18.md), [T3-15 계획](../plans/T3-15.md), [테스트 정책](../testing-policy.md) §6. PRD의 M2 목표 표와 성공 지표에 남은 지인 문구보다 이 결정이 우선한다. 관문 이름(M2 지인 테스트)은 열린 PR과 충돌하지 않도록 이번에는 바꾸지 않는다.

## D-022. MVP 완료에는 모든 명령이 들어간다 (2026-10-22)

- **결정:** 소유자 원문은 “MVP 완료 시에 모든 커맨드가 다 완료 되어야 해.”다 (2026-10-22). <!-- lint-text-ignore J-2 --> MVP 명령 범위를 37개에서 전체 명령으로 바꾼다. AC-M1-14는 ID를 그대로 두고 전체 명령 수용 관문으로 고친다. 기존 37개 통과(PR #38 `81ffd1b`)는 부분집합 이력으로 남긴다.
- **분모:** 비교 기준은 core2026 `df6c926`의 장수 55개·국가 35개, 합 90개다. 90개를 그대로 되살리는 것도 아니고 37개로 줄이는 것도 아니다. 정본은 [명령 대응표](./command-coverage.json)이며 원본 ID마다 우리 명령 하나나 미해결 항목 하나가 있다. 이름을 합치거나 미구현을 빼서 분모를 줄이지 않는다. 원본 둘 이상을 한 명령으로 합치거나 원본 없는 명령을 더하려면 승인 근거가 있어야 한다.
- **승인된 대체:** D-014의 외교 명령 4개(종전·불가침·불가침 파기 제의, 원조) → 조약서 조항, 교역 명령 추가, T2-05의 발령 응답 즉시 행동은 그대로다. 원본 ID와 승인 근거를 대응표 행에 남긴다.
- **완료 판정:** 명령마다 화면, API, 권한, 엔진, 효과·비용·실패, 저장, 재시작, 재생, 독립 리뷰, exact SHA 검증, 병합 11단계가 모두 증거로 확인되거나 이유 있는 해당 없음이어야 한다. 대응표 정합 검사(`node tools/command-coverage.mjs`)와 제품 전체 완료 검사(`--require-complete`)를 따로 본다. 관문은 그 관문의 AC가 전부 ✅일 때만 통과하므로 AC-M1-14가 다시 ✅가 될 때까지 M1도 통과하지 않는다. <!-- lint-text-ignore C-5 -->
- **이 결정이 승인하지 않는 것:** Phase 2 명세(PR #67)의 계약 C13~C20, 미결정 U-01~U-21, 승인 항목 A-01~A-11의 세부 정책, 새 수치 환산. 명령이 MVP 필수가 된 것이지 그 명령의 미정 수치·정책이 정해진 것은 아니다. 미정은 대응표 행의 차단 사유로 남는다. A-02·A-03·A-04의 명령은 이 결정으로 MVP 범위에 들어오되 세부는 각 작업 계획에서 다시 받는다.
- **넓히지 않는 것:** 명령이 아닌 Phase 2 기능(경매, 토너먼트, 전투 시뮬레이터, 장비·특기의 효과 계산, D4·D7·D8·D9·D13·D14·D18, 시나리오 추가)은 MVP로 옮기지 않는다. 명령이 그 기능에 기대면(장비매매 → 장비, 특기 초기화 → 특기) 대응표의 차단 사유에 적는다. T4·AC-P2 ID는 추적 ID로 두고 M4 관문을 만들지 않는다.
